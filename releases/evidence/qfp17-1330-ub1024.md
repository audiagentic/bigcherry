## Memory mechanism

The dense fallback has `mask_all` plus an out-of-place F16 `ggml_add(sel, kq_mask)` result. At 240K/ub1024 the latter is approximately:

`245760 * 1024 * 2 bytes = 480 MiB` per Meta rank.

The prior QFP17 live-set attribution at ub1024 was approximately 1748 MiB/rank:

- kq_mask input: 480 MiB
- mask_all: 484 MiB
- out-of-place ADD result: 480 MiB
- kpool mask: 120 MiB
- other: ~180 MiB

1330 aliases the ADD result into mask_all, removing the 480 MiB live tensor. The expected peak is therefore about 1268 MiB/rank before allocator effects. Padding `n_kv+n_sel` from ~247811 to 248064 rows adds only ~0.5 MiB at ub1024. The observed transition from OOM to fit is consistent with this mechanism.

## Decode-cost disposition

1330 previously changed the dense fallback for every batch. 1332 intentionally keeps decode/MTP-sized batches (`n_tokens <= 8`) on that fallback; therefore the memory optimization also touched decode even though decode does not need the ~480 MiB ub1024 saving.

This slice gates all three 1330 behaviors on `n_tokens > 8`: in-place add, padded backing rows, and strided-mask pass-through. For <=8 tokens the original out-of-place add and reshape remain. This should remove the measured ~3% ub512 decode cost; hardware confirmation must verify it.

## ub1024 composition effects

1. **1332 token chunking.** Current 1332 uses `K=ceil(n_ubatch/C)` and only chunks when `K>=2 && n_tokens>=K && n_tokens>8`. At ub1024 with C=256, K=4 (vs 2 at ub512). Its chunked prefill path returns I32 selection indices and never executes 1330's dense causal ADD. Do not enable `BIGCHERRY_QSA_CHUNK` for the 1330 promotion arm; otherwise the two memory mechanisms are not being qualified together.
2. **1345 multi-warp MoE IDs.** Threshold is `n_tokens >= 128`. Full ub512 and ub1024 chunks both hit the same multi-warp path; only work per launch/tail distribution changes.
3. **1348 deferred MTP catch-up.** The target prompt batch is bounded by ubatch, so ub1024 makes full prompt chunks 1024 tokens instead of 512. A fixed fill has roughly half as many target submits/deferred catch-ups, each full catch-up covers twice the tokens, and the terminal flush remains once per prompt. Re-run `BIGCHERRY_MTP_PROMPT_TIMING=1` to verify overlap remains favorable.
