# rad0002_moe_remote_handoff

**Status:** validated
**Plan item:** RAD01

## Summary

Engine-side hooks (14 call sites, 4 files) for the whole-expert MoE remote hand-off.

## Outcome

Validated for the Radiance v1.14.0 production `serving-core` patch set on
3 November 2026. Qualification is profile-scoped to Qwen3.8-Flash-Next
fp8-iq4r-moe on an R9700 engine with RX 7900 XTX expert helpers. The
recorded quality, repeatability and helper-activation checks passed; this
does not establish equivalent behaviour on other models or layouts.
See the [promotion evidence](evidence/promotion.json) and
[qualification record](README.md).


## Detail

See below.

## What it does

Adds the engine side of the whole-expert MoE hand-off as thin hooks into one BigCherry-owned extension point (`abi/bc_moe_remote.h`, `core/place/bc_moe_remote.cpp`, `core/place/bc_moe_remote_place.h`, `arch/common/bc_moe_remote_block.h`, all created by this package). When the libr3moe plugin has registered and the row policy admits a step, the routes the helper owns are published to it and masked out of the local grouped GEMMs; `moe_mailbox_add` then sums the local and helper rows in slot order in place of `moe_gather`, and the standalone tensor-parallel all-reduce runs afterward. HyperConn's fused gather and reducing write are skipped, only for a connection fed by a MoE gather source, on those steps. With no plugin or an excluded row count nothing changes.

The upstream files receive 14 one-line guarded call sites (the earlier port was 20 edits and about 170 core lines):

| File | Sites |
|---|---|
| `arch/common/rad_block_moe_fp8.h` | include; `BcMoeRemote bc_remote` member; `declare` (publishes the layer map, declares the two mailbox ops from the plugin's rows); `after_route` (publish and re-scatter); `merge` (replaces the gather); `issues_ar()` (forces the block's own all-reduce while handed off) |
| `arch/common/rad_block_hc.h` | include; `takes_ar()` |
| `core/place/planner.cpp` | include; `pin_mapped` (`bc_moe_remote_pin_unit`); `weight_footprint` (`bc_moe_remote_mark_footprint`); `rank_units` (skip preplaced units, the one policy line that cannot leave the core) |
| `core/engine_bringup.cpp` | include; `bc_moe_remote_publish_placeholder` before the tier check |

All policy is in the created files and the plugin: the row gate (`R3_MOE_REMOTE_MIN_ROWS` / `MAX_ROWS`), the plugin registry (`bc_moe_remote_register`, replacing the two `dlsym` hooks; layer maps published before registration are replayed), the layer map, the `R3_MOE_WORKER_SKIP_OWNED` placement rule, the never-read mapped placeholders, and the HyperConn suppression. The shadow compare and the mask-only mode are not here: they are `rad0004_moe_remote_diagnostics`, for a diagnostic build only. A production engine that finds `R3_MOE_WORKER_SHADOW` or `R3_MOE_WORKER_MASK_ONLY` set answers "no remote rows" and says so once.

Changes of behaviour against the 1.3.0 port: the step gate is decided on the step's row count `T` everywhere (identical to the pass rows for decode-sized single-pass steps), the all-reduce is forced in `issues_ar()` so the pipelined prefill callers agree with `pass()`, and a missing mailbox op while the gate is open is a declare error.

## Why

The seam allows a helper GPU to compute cold routed experts rather than making the serving ranks repeatedly consume host-resident expert weights across the link.

## Evidence

The [v1.14.0 promotion record](README.md) gives the matched quality
checks, helper activity, captures and limits. The
[recorded promotion evidence](evidence/promotion.json) identifies the
qualified package. The older 1.3.0 measurements and 1.7.0 port history
are historical context, not current-pin performance evidence; see
[the Radiance archive](../../../../docs/archive/radiance/).


## Upstream

Local BigCherry integration patch, now validated against the pinned
Radiance v1.14.0 source. The original implementation was developed
against Radiance 1.3.0 and reworked for 1.7.0 before this promotion.
The production patch is selected by `serving-core` in
[`engines/radiance/recipes.toml`](../../recipes.toml).

# rad0005_mp4_ffmpeg6_writer

**Status:** untested
**Plan item:** MEN12

## Summary

Selects the FFmpeg 6 vs 7 avio_alloc_context write-callback signature so rad_core compiles on Ubuntu 24.04's FFmpeg 6.1.

## Outcome

untested: compile-compatibility fix, read-only callback so behavior is identical on both FFmpeg versions; not yet run through its own qualification.

## Detail

See below.

## What it does

radiance 1.8.0 adds `core/mm/mp4.cpp`, which gives `avio_alloc_context` a write callback taking `const uint8_t*`
(the FFmpeg 7 / libavformat 61 signature). FFmpeg 6.1, which Ubuntu 24.04 ships and dev uses, declares the
parameter `uint8_t*`, so `rad_core` fails to compile (`invalid conversion from int (*)(void*, const uint8_t*, int)`).
The patch selects the parameter type with `LIBAVFORMAT_VERSION_MAJOR >= 61`. The callback only reads the buffer, so
behaviour is identical on both versions.

## Why a patch

It changes upstream source, and the alternative (`RAD_WITH_FFMPEG=OFF`) would drop image, video and audio input that
the 1.7.0 build had. Installing FFmpeg 7 on the host needs the owner's consent and is not a build fix.

## Evidence needed (lightweight tier)

Enabler with no runtime path of its own: the engine builds and passes the bump gates (components-build, plugin ABI,
component tests, cpu-smoke) on dev with it applied; mechanics test and patch-lint offline. Candidate for upstream
(kept private for now).

# rad0008_hc_upmix_rt_sweep

## Summary

Adds a runtime switch (`RAD_HC_UPMIX_RT`, values "128"/"256"/"384") at the PF2 up-mix launch call site inside `hc_pf2_launch` (vendor/radiance/libr4d/r4d_hc_bf16.hip, ~line 3167 as of the 1.9.0 pin).

## Outcome

Recorded state: `validated` ([patch.toml](patch.toml)); qualification and limitations are documented below.

## Detail

**Status:** validated
**Plan item:** RAD17/RAD18

Promoted 2026-10-23: releases/evidence/rad0008_hc_upmix_rt_sweep-promotion.md.

## Outcome

Sibling investigation to RAD17 (FP8 down-product), targeting the shared BF16 up-mix kernel
instead. Per GPT dev-agent review (req_bigcherry_46bf68059a11), the diagnostic hipBLASLt
GEMM + separate epilogue approach (tools/lab/radiance/hc-upmix-epilogue-diag.hip, RAD17/RAD18)
measured 395us combined vs the fused kernel's 261us -- the separate epilogue is bandwidth-bound,
round-tripping the fp32 up-product through global memory that the fused kernel never materializes.
GPT's own decision tree rejected the GEMM-replacement angle and recommended sweeping
`hc_up_mix_wide_kernel`'s RT (rows per workgroup, selecting MW waves-per-block) instead, to test
whether occupancy/register pressure -- not grid fill, already ample at this shape -- is where any
remaining headroom is.

GPT's first proposed lever (sweeping CH, the output tile width) was checked against the real kernel
source (vendor/radiance/libr4d/r4d_hc_bf16.hip) and found infeasible as scoped: CH is not a software
parameter, it is gfx1201's native 16-wide WMMA N-dimension, hard-wired into `frag()`'s `c*16`
fragment offset and the epilogue's `lane & 15` column index. Reported this back to GPT
(req_bigcherry_0641281ad540), which then recommended the RT sweep implemented here.

RT=512 (GPT's originally-suggested "double") is a real, hardware-enforced dead end, not merely
untested: confirmed via an actual standalone compile of that kernel instantiation --
`hipcc` reported "local memory (78336) exceeds limit (65536) in void (anonymous
namespace)::hc_up_mix_wide_kernel<4, false, 512>(...)". The kernel's LDS use is
`sA[RT*kTAP] + sB[NT*kTAP]` shorts (kTAP=68, NT=64) = `RT*136 + 8704` bytes; at RT=512 that's 78336
bytes against gfx1201's 65536-byte per-workgroup LDS limit. RT=384 (60928 bytes) is the largest
legal value and replaces RT=512 as the sweep's upper point.

## What this patch does

Adds a runtime switch (`RAD_HC_UPMIX_RT`, values "128"/"256"/"384") at the PF2 up-mix launch call
site inside `hc_pf2_launch` (vendor/radiance/libr4d/r4d_hc_bf16.hip, ~line 3167 as of the 1.9.0
pin). `hc_up_mix_wide_kernel` itself is completely unchanged -- RT is already one of its template
parameters; this only changes which instantiation gets launched and with what grid. Unset or any
other value falls back to the exact original call (`RT=kPf2UpRT=256`), bit-identical to pre-patch.

Verified (this revision):

- `patch-lint`: clean (same pre-existing `max_span_lines` warning class as rad0007's own edits;
  no errors).
- Anchor match count against the real pristine vendor file: exactly 1, via a throwaway script
  (not checked in) performing the same regex substitution patch.py does, run directly against a
  scratch copy of the real vendor/radiance/libr4d/r4d_hc_bf16.hip on dev -- not the shared
  wt-accept checkout.
- Standalone `hipcc --offload-arch=gfx1201` compile of the patched file: clean, zero errors.
- `nm`/`c++filt` on the compiled object: confirms all three new instantiations
  (`hc_up_mix_wide_kernel<4, false, 128/256/384>`) are present as real compiled device code
  (`__device_stub__` symbols too), alongside the pre-existing `<4, false>`/`<4, true>` instantiations
  used elsewhere in the file.

## Anchor fix (first real build)

The first `bigcherry build --experiment hc-upmix-rt-sweep` stopped at patch application: the anchor began on the
`/* The up product and mix ... */` comment and the guard was the `RAD_HC_UPMIX_RT` string literal, but the patch
engine strips comments and string literals before matching, so the anchor matched 0 times. The earlier check used
a plain regex on the raw file and missed this. The anchor now starts at the `hipLaunchKernelGGL` call and the guard
is the `rad18_upmix_rt` variable; `apply_patch` on the pinned v1.9.0 file applies, and a second apply reports
`already-applied`.

## Hardware result (2026-10-22, gfx1201 R9700)

Built through the real pipeline (`bigcherry build --lane radiance-lab:stock:linux-radiance --experiment
hc-upmix-rt-sweep`, build plan `da22861d7c120bb8e078f39e86ca4037`) and measured with `r4d_selftest --perfhc <M> 50`
(PF2 `hc_read` whole-call time), three rounds per size with the RT order rotated each round. Every run passed the
selftest's byte-identical check of the PF2 output against the decode-tile kernels, RT=384 included (its last
workgroup covers 256 padded rows at M=2048).

| RT | M=2048 runs (us) | mean | M=4096 runs (us) | mean |
|---|---|---|---|---|
| 128 | 503.6 / 511.4 / 506.8 | 507.3 | 1250.6 / 1252.9 / 1249.9 | 1251.1 |
| 256 (production) | 515.0 / 513.2 / 517.0 | 515.1 | 1291.5 / 1293.7 / 1289.6 | 1291.6 |
| 384 | 549.4 / 560.7 / 554.1 | 554.7 | 1440.1 / 1454.6 / 1445.7 | 1446.8 |

RT=128 is faster than production at both sizes with complete separation: -1.5% of the whole call at M=2048
(about 8 us, roughly 3% of the up-mix kernel) and -3.1% at M=4096 (about 40 us). RT=384 is slower at both, in
line with the LDS-occupancy prediction (26/44/61 KB per workgroup at RT 128/256/384).

## Against the unpatched build, and across row counts

Six rotated rounds against the unpatched `radiance-lab` stock build (build plan `5e758b5e337a361e853b77e0f7beaf4c`),
all byte-identical: M=2048 stock 515.3 / patched with the original RT 516.5 / RT=128 504.7 us (-2.1%, RT=128 ahead
in all six paired rounds); M=4096 1293.1 / 1293.4 / 1252.3 us (-3.2%, complete separation). With the original RT
the patched build matches stock, so the switch itself costs nothing.

Rows sweep, stock vs RT=128 (two runs each, us): 512 169.7 vs 166.8; 768 218.5 vs 213.8; 1000 272.8 vs 268.2;
1024 276.9 vs 275.8; 1536 415.7 vs 407.4; 2047 523.3 vs 508.0; 2049 574.9 vs 552.5; 3000 833.3 vs 808.1;
6144 1702.5 vs 1649.7; 8192 2426.4 vs 2325.9. Never slower, byte-identical at every size (256 rows does not take
the PF2 form). RT=128 is therefore the patch's default; RAD_HC_UPMIX_RT=256 restores the original launch.

Evidence covers one shape (n=2560, hc=4, lr=320: Qwen3.8-Flash-Next), the only one r4d_selftest's PF2 bench runs.

# rad0009_serving_manifest

**Status:** untested
**Plan item:** RSC07

## Summary

Lets the engine start from a resolved serving manifest: `engine --manifest PATH [--role engine] [-v|-vv]`, with no command-line converter in our tooling.

## Outcome

untested: package and card-free tests exist; a manifest launch is not yet shown on hardware to parse to the same config as the argv launch.

## Detail

See below.

## What it does

`core/bc_serving_manifest.{h,cpp}` (created by the patch) hold all the logic; `core/main.cpp` gains one include and two calls, nothing else is touched (`config.cpp` and its option table are not edited, so `--manifest` is not listed in `--help`).

- Before `config_parse`, `bc_serving_engine_argv` replaces argv. With `--manifest` only `--role engine`, `-v` and `-vv` may accompany it; any other flag is an error. The manifest must have `schema_version` 1, a `values` object, `hash_algorithm` "sha256" and a `content_sha256`.
- Every `engine.<name>` value becomes `--<name with _ as ->`, in sorted key order (valued options first, then bare flags), and radiance's own parser and validation then run on it. An unknown key (not in `rad::diag::config_option_names()`) is an error naming it. The argv shape follows the JSON type alone: `true` adds a bare flag, `false` omits it (the default stands), a string adds `--flag value`, an integer or finite float is formatted exactly. Null, arrays, objects and non-finite numbers are errors. A shape the option does not accept (a value for a boolean option, `true` for an option needing an argument) is left to `config_parse`, which rejects it, and `main` exits 2.
- `engine.radiance_home` and `engine.kernels` must be present and non-empty, so `RADIANCE_HOME` and `RADIANCE_KERNELS` (which `config_parse` consults when the option is empty) cannot silently supply them.
- After a successful parse `bc_serving_mark_given` checks that every option it produced was parsed as given (else start-up fails with exit 2, e.g. a bare flag that swallowed the next one) and relabels those sources as `manifest <first 12 chars of content_sha256>` in the startup report.
- Errors print a message and `main` exits 2.

The manifest's content hash is not recomputed by the engine; `bc-serve` produces it.

## Why a patch

The engine is upstream code and reads its configuration only from the command line; the owner decision (RSC01, 2026-11-02) is that each process loads its own manifest through radiance's own option table rather than a converter generating flags.

# rad0011_plan_memory

**Status:** untested
**Plan item:** RSC03

## Summary

The engine's own memory plan (`Engine::plan()`) as a serving manifest v1 `EnginePlan`, measured or checked, through the
shared v1 library `bc_serving_v1`.

- `radiance … --plan-memory FILE` runs start-up as far as `plan()`, writes what it sized (host consumers the engine pins,
  the checkpoint store's slot, floor and want, one full-length session's KV, the per-card VRAM split including the
  resolved KV budget `kv_resolved`, and the expert plane, each with the engine function it came from) as v1 JSON through
  the generated encoder, and exits before any weight is loaded or the KV cache and arenas are allocated. bc-serve uses it
  as a measured fact, cached by container, engine build, card and planning inputs.
- `radiance … --plan-check FILE --plan-check-floor-ppm N` reads FILE (a plan bc-serve measured) through the shared strict
  reader and, right after the VRAM split and **before any pool is configured**, checks the live plan against it (spec
  section 5.2): stable facts by exact equality (`BC_CFG_PLAN_MISMATCH`, exit 2) and admission on the live split, with
  `kv_required` from the calibrated backing floor `N` (`BC_CFG_ADMISSION_REFUSED`, exit 4). The result is printed once:
  `plan check: admitted` with its margins, or the refusal in the shared `radiance: config: CODE (RAD_E_X, n)` format.
  The two flags go together, `N` is range-checked by the manifest's own validator, and they are interim: the v1
  manifest's `engine_view` replaces them at the slice 6 cutover (RSC08).

## Outcome

untested: package and card-free tests exist; the plan check has not yet run on hardware (a fresh plan, a restart that is
admitted and a one-byte drift that is refused), nor an identity run against main.

## Detail

See below.

## What it does

`core/bc_plan_memory.{h,cpp}` and `core/bc_plan_check.{h,cpp}` (created by the patch) hold the logic. Upstream files gain
only thin calls: `core/main.cpp` one include and one call that takes the plan flags off the command line before rad0009's
manifest reader sees them; `core/engine_bringup.cpp` one include, one call at the end of `plan()`'s VRAM split that
records (and with `--plan-check`, checks) its sizes, and one call after `plan()` in `start()` that writes the plan and
exits; `core/CMakeLists.txt` includes BigCherry's `components/serving/bc_serving_v1.cmake` and links `bc_serving_v1` into
`rad_core`. The build tool passes that file as `-DBC_SERVING_V1_CMAKE` (engine.toml `repo-paths`); without it configure
fails closed. Without the plan flags the calls do nothing.

The query runs the engine's real bring-up up to `plan()`, so it needs the engine card: bc-serve runs it on the serve
path, under the launch's own lease, never from `--explain` or `--dry-run`.
