- chg_20260805_050646_fixed-a-dispatch-bug-where-the_5680: Enforce candidate src0 type in dispatch eligibility across all four matmul families, and verify the HI09 MMVQ forced-geometry routing on gfx1100 hardware for the first time.

Every generated candidate names one src0 type in its stable name (mmvq:q8_0:, mmq:q8_0:, mmf:f32:), but the type never reached ggml_hip_variant_params, so no can_execute predicate could check it. Because every family's launch path dispatches on the runtime tensor type, candidates were ruled eligible for, measured on, and declared winners of signatures of a different type. - chg_20260805_070912_fixed-the-saved-results-format_5368: Fix the replay cache entry format so tuned winners can round-trip, and document the remaining gap between tuning output and production.

The cache entry carried dispatch digest, signature digest, name offset, primary, secondary, width, acc_f16 and fallback, followed by two reserved bytes named ENT_SEEDED that nothing read. ggml_hip_variant_params has two further members and neither round-tripped.

small_k was missing. Every top winner on the real MTP workload is an sk1 geometry (RV10: w6:nw4:rpb4:sk1 at 19.65 percent, w4 at 17.09, w5 at 19.12, w3 at 14.18). Replayed as sk0 they name a different compiled instance, and the (w6,nw4,rpb4,sk0) combination is not generated, so the launch would reach the HI09 missing-instance abort rather than merely losing the improvement.

src0_type was missing because RV01 added it to the struct earlier in this same session without extending the serialisation. A replayed candidate would carry type 0, meaning F32, and be rejected by its own family's can_execute on every quantised signature, silently falling back to native. That was a regression introduced by RV01 and is now closed.

So replay would have failed on precisely the results worth replaying: sk1 geometries aborting, everything else quietly reverting to native. Latent only because nothing has ever written a cache.

ENT_SMALL_K and ENT_SRC0_TYPE now occupy the reserved bytes and are read into the winner's variant params. ENT_SIZE is unchanged and no format version bump was required, since nothing has ever written this format and no cache exists to be misread. The entry layout now has no spare bytes, so any future field needs a version bump.

Also recorded in RV09: the writer itself does not exist, which is now the highest-value remaining work, and two design questions it forces. First, the loader rejects a cache whose manifest hash differs from the build's, and a production build wanting only the winning instances will have a different manifest from the tuning build, so either the cache is re-emitted against the production manifest or the pruned set must preserve the hash. Second, replay-full and replay-slim appear in VARIANT_SETS and nowhere else - the mechanism for slimming a catalog down to the winners is declared but unimplemented.

- chg_20260805_071838_completed-the-pipeline-that-ca_3350: Build the replay cache writer and verify the complete tune-to-production chain on the real workload for the first time.

tools/bigcherry/replay_cache.py mirrors hip-autotune-replay.cpp byte for byte: magic 0x59484342, container and artifact versions, signature and hardware schema versions, the 16-byte manifest hash, a blake2b-16 content checksum personalised llama-dispatch, a string table and fixed-size entries. Written in Python for the same reason record mode is - nothing in the production link path should be able to write this format, and a run killed partway still yields a usable cache from whatever its JSONL flushed, with truncated final lines tolerated by construction.
