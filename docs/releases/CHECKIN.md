# Check-In Summary

Total changes: 39

- Validated HIP autotune code against docs: 11 items confirmed completed, 2 in progress
- Updated plans with PACK_REVIEW action items from reference docs
- Documented PACK_REVIEW action item incorporation in plan items
- Fixed a dispatch bug where the autotuner could measure a kernel variant built for one quantisation type against a matrix of a different type, producing either a crash or a recorded winner that misnamed what actually ran. The MMVQ explicit-geometry path is now verified on AMD gfx1100 hardware, where several tuned geometries measurably beat the built-in defaults.
- Fixed a crash where the autotuner could route a matrix multiplication to a kernel family that does not implement that quantisation format, aborting the run. Tuning sweeps now complete across every quantised format on AMD gfx1100.
- The autotuner now completes a full matrix-multiplication tuning sweep on AMD gfx1100 hardware. Fixed three further crashes: kernel variants being selected on hardware that cannot run them, an unchecked requirement that activations be 32-bit floats, and the tuner attempting to take timings inside a GPU graph capture.
- Validated the tuning fixes on a second GPU architecture (RDNA4), where a full sweep now completes cleanly with no errors. Identified that roughly a third of the generated kernel candidates target datacentre-class AMD hardware and are correctly skipped on consumer cards, but are currently reported in a misleading way.
- Kernel variants that require datacentre-class AMD hardware are now correctly identified as unsupported on consumer cards up front, rather than being re-examined for every matrix multiplication and reported under a misleading reason.
- Measured which kernel-selection strategies actually pay off. Most of the gain comes from choosing among parameters the upstream library already compiles, rather than from the newly generated kernel variants - a result that redirects where further optimisation effort should go.
- Measured kernel tuning on both GPU generations and found the benefit is strongly architecture-dependent: the generated kernel variants deliver a 16% median speed-up on the target hardware while being nearly worthless on the newer generation. A single variant that was previously impossible to select accounts for most of that gain.
- Added a generated reference document cataloguing every kernel candidate alongside how it actually performed on each GPU tested, so future work can check what exists, what can run where, and what has ever been measured.
- Established a working pipeline for capturing real workload profiles from a running inference server with speculative decoding enabled, and documented how to build, test and measure the project on every supported configuration.
- Tuned the real production workload for the first time and found that 79% of matrix operations run faster with a tuned kernel variant, with the best gains of 14-20% concentrated exactly where predicted. The results cannot yet be saved and reused, which is now the most valuable remaining work.
- Fixed the saved-results format so the best-performing kernel selections can actually be reloaded; previously the two settings that matter most to the fastest variants were silently dropped, which would have caused crashes or a quiet fallback to default behaviour.
- Completed the pipeline that carries tuning results into a running server: measured kernel choices can now be saved and reloaded, verified with every matrix operation served from the saved selections and no gaps. Overall throughput was unchanged in this test, so the per-operation gains have not yet been shown to translate into faster inference.
- Added the ability to build a production binary containing only the kernel variants a tuning run actually selected, cutting the candidate set by 81 percent. Also quantified the benefit of tuning: matrix multiplication time drops by about 7.5 percent, which is too small to observe through the current end-to-end benchmark.
- Tuning results now record enough information to be reused across rebuilds. Also corrected two earlier verification claims: a slimmed production build silently discards all tuning because the lookup key includes the build's own identity, and an earlier no-gaps result had not actually enabled gap reporting.
- Tuning results now survive a rebuild. Previously any change to the kernel catalogue or an upstream update silently discarded every tuned result; they are now reused, and flagged as possibly out of date when the build has changed underneath them.
- Added an automated check that catches a class of bug which previously required hours of hardware testing to find, and which had twice caused the fastest kernel variants to be silently unreachable.
- The coverage report now states whether saved tuning results were actually used and whether they are out of date, rather than only reporting that every operation went through the dispatch layer - two things that look identical in the previous output.
- Validated kernel dispatch across single and multiple GPUs, three GPU generations, tensor splitting and GPU graph capture. Mixing different GPU generations in one tensor split crashes in the upstream library itself, independently of this work.
- Found and fixed a build setting that was halving multi-GPU performance, restoring prefill throughput to match the production configuration. Also established that the long-context workload exercises 51% more distinct operations than the short-context tests everything had been tuned against.
- Tested whether a compile-time flag that prefers quantised matrix-multiply kernels improves generation speed. It makes no difference on this hardware because those kernels are already the default choice for this model format, and the automatic tuning covers the same decision with per-shape measurements.
- Discovered that automatic tuning had been measuring only a fifth of the work the model actually does, because the test workload did not produce the shapes that dominate real use. After correcting it, tuning cuts matrix-multiplication time by 10 percent, with individual operations up to three times faster than the built-in choice.
- Measured the finished system end to end: automatically tuned kernel selection makes prompt processing 1.7 to 4.4 percent faster than the built-in defaults, verified across interleaved runs with no overlap between the two configurations. Generation speed is unchanged.
- Published a detailed per-operation tuning report showing which kernel was selected for each of the busiest operations and how close the alternatives were, along with three concrete opportunities for further improvement.
- Investigated an apparent flaw in kernel selection and found the selection logic correct; the real issue was that the quick screening pass used too few timing samples to rank candidates reliably. Correcting it confirmed the diagnosis but changed overall performance by a negligible amount.
- Planned two new optimisation projects for gfx1100: exact-shape WMMA kernel (HI25) and Q8_1 activation reuse with K-tile tuning (HI26). Strategy inverted based on hipEngine's 44% regression — start from proven LDS decomposition, not green-field WMMA.
- Updated the tuning skills so future Windows Gemma runs use the working command and validate generated measurements before accepting results.
- Made the tuning instructions reusable for any GGUF model family instead of naming a specific model.
- Added a reusable skill for measuring before-versus-after tuning performance without model-family-specific assumptions.
- Added a safe opt-in shutdown endpoint so Windows benchmark runs can flush tuning data instead of losing measurements on process termination.
- Added optional per-cache-entry replay diagnostics with no production runtime overhead, then used them to verify which tuned candidates actually ran.
- Updated the handoff document with the latest build, replay evidence, benchmark comparison, and next steps.
- Fixed the missing Gemma signature import path: new tuning runs preserve shapes in measurements, and existing databases can be enriched from diagnostic JSONL sources.
- Expanded the HIP autotune plan with implementation-level detail for improving tuning quality: statistical confidence in winner selection, measurement-effort budgeting by signature impact, measurement fidelity, an offline model for what tuning is worth, and generalising winners across similar signatures.
- The HIP autotune engine now requires statistical confidence (not just a faster median) before replacing native, ranks candidates on whichever of GPU or host-submission time actually binds, and rejects noisy or non-deterministic candidates instead of silently keeping them as winners.
- Expanded four planned autotune work items (adaptive screening, measurement fidelity, impact modelling, winner generalisation) from designs into implementation-ready specifications with verified, paste-ready code.
- Specified how tuned results survive llama.cpp upgrades with per-release history, and added a plan item for recording which workload and machine settings each tune was measured under.
