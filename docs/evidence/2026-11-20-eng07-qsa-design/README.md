# ENG07: QSA block-key quantisation (design only)

**20 November 2026 | Status: proposal, no implementation or GPU results.**

Scope: the separate, resident QSA block-key KV group on Flash-Next with the already-qualified main-attention `bf16_i8` cache. Existing `bf16_i8` and `fp8` behaviour and defaults remain untouched. Source below is frozen candidate `<work-root path>` at `3deabdaeca17b58bad90d332f4b204cf7bb8a10e` unless noted. Confirm ranges on the exact production composition before patch authoring; v1.17 source uses different line numbers and control flow.

## Recommendation and discrepancy in the plan

Prototype **signed int8 with four f16 scales per 128-dimension QSA key** (group of 32) as the quality-first format, then compare **int8 with one f16 scale per entire block** and **native finite E4M3**. All formats are opt-in; score selected-block stability must pass before serving-performance qualification. Do not reuse `bf16_i8` attention K/V layout for this artificial block-key group.

ENG07's "43.06 KiB whole-cache page" and projected "1.306-1.31x" need reconciliation. VTP44 reports bf16 reference as **48.00 KiB attention + 3.00 KiB QSA = 51.00 KiB per 4-token logical page**, and existing bf16_i8 as **36.75 KiB attention + 3.00 KiB QSA = 39.75 KiB**, giving 51 / 39.75 = **1.2830189x**. Compressing only QSA while keeping the bf16 reference unchanged would predict **1.330-1.333x logical KV ratio**, before pool alignment, other KV groups, metadata and allocator overhead. The card's "3.25 KiB with scales" is not the **current** group size; currently it is 3.00 KiB. Do not edit the card in this design-only task: flag these differences for measurement.

ENG06's eight-session Flash-Next bf16_i8 admission was **5,470,191,215 bytes short**, while at four sessions it served. Even a perfect 96 MiB saving per 256K sequence is **768 MiB across eight sequences**, far too little to solve the 5.47 GB deficit. This is a modest capacity/traffic experiment, not an eight-session fix.

## 2. Exact QSA bytes at 262,144-token context

262,144 tokens / ratio 4 = **65,536 block-key pages per QSA layer**. At **12 QSA layers**, there are **786,432 page rows**. The table shows total **logical QSA group bytes for one sequence**, excluding tail, other KV groups, allocator/page-table metadata and alignment. f16 scale is two bytes.

| Format | Bytes per 128-key page | Total exact bytes at 256K | MiB | Bytes and MiB saved vs bf16 |
|---|---:|---:|---:|---:|
| Baseline bf16 | 128 * 2 = **256** | **201,326,592** | **192.0** | 0 |
| Signed i8 + **one f16 scale per block** | 128 + 2 = **130** | **102,236,160** | **97.5** | **99,090,432 = 94.5 MiB** |
| Signed i8 + **four f16 scales (per 32)** | 128 + 8 = **136** | **106,954,752** | **102.0** | **94,371,840 = 90.0 MiB** |
| Finite E4M3, unscaled | **128** | **100,663,296** | **96.0** | **100,663,296 = 96.0 MiB** |
| Optional E4M3 + one f16 block scale | **130** | **102,236,160** | **97.5** | **99,090,432 = 94.5 MiB** |

**Physical-pitch caveat:** 130 and 136 bytes are not multiples of 16. If **each page is padded to 144 bytes**, either i8 mode consumes **113,246,208 bytes = 108 MiB**, saving only **88,080,384 bytes = 84 MiB**; at a 160-byte pitch savings are 72 MiB, and at 256 bytes there are **no savings**. If tight byte strides are supported, use them with byte-accurate addressing and explicitly safe unaligned loads; never infer physical bytes from a logical row type alone. A 128-byte E4M3 row naturally meets a 16-byte pitch. Verify actual `rad_kv_layer_bytes`, admission and pool/host mirror allocation.

At four tokens across twelve QSA layers, candidate QSA bytes are: i8/block **1.5234375 KiB**, i8/group32 **1.59375 KiB**, unscaled E4M3 **1.5 KiB**, or padded 144-B page **1.6875 KiB**. Adding unchanged bf16_i8 attention **36.75 KiB** gives predicted KV-only capacity ratios against unchanged bf16 total 51 KiB of **1.33252x, 1.33007x, 1.33333x, and 1.32683x** respectively. These are NOT measured engine token/session capacities.

## 3. Codec, writer, reader and cost

**i8/group32, preferred quality probe.** Quantise **after** the existing bf16 block key construction: for four 32-dimensional groups compute `absmax`, choose strictly positive f16 scale rounded **up** from `max(absmax/127, min_scale)` (mirror proven bf16_i8 V contract, including finite-scale bounds), and store `clamp(rintf(x/scale), -127, 127)` as signed i8 plus four scales at an explicitly versioned byte offset. Dequant is `float(i8) * float(f16_scale)` inline in the scorer. Define all-zero, nonfinite, extremely small/large vectors and saturation behaviour and test against CPU reference. Four scales reduce error when RMSNorm/rotation creates uneven dimension amplitudes. Quantise a block atomically enough that readers never see a new key paired with stale scale bytes.

**i8/one-scale alternative.** Same algorithm but one absmax and f16 scale across all 128 dimensions. Fewer loads/broadcasts, but more distortion where one large coordinate determines the scale. Its six logical saved bytes versus group32 vanish under 144-byte per-page padding. Pick it only if actual selection and kernel timing justify the change.

**E4M3.** A simple 128-byte native finite E4M3 control with no scale, plus optionally a one-scale E4M3 control to test dynamic-range effects. Decode to f32/bf16 in the scorer. Avoid assuming that results from attention `bf16_fp8` V apply to the **selection-index** keys; dynamic range and ranking are different problems.

**Writer changes:** extend/create a codec-specialised `qsa_block_key` HIP producer, maintaining mean-f32 -> bf16 rounding -> RMSNorm -> positional RoPE -> bf16 key rounding. Add max reductions, f16-scale calculation and code stores after that. No second conversion kernel, no always-resident bf16 shadow pages. Use `page[b]` and existing work-list semantics, including skipped pages, grouped prefill, mixed sequences, MTP and checkpoint snapshot/rollback.

**Reader changes:** add a new codec-specific `qsa_score` kernel row instead of reinterpreting existing bf16 row. Scalar score (`r4d_qsa_score_bf16.hip:63-~220`): issue vector code loads + scale, dequant once to register f32 for each block and reuse across four query rows and all four heads. Matrix score (`:~240-345`): dequant codes **inside the 16-block by 16-query tile** into bf16 fragments for WMMA; retain head-wise ReLU order and float score outputs. Never allocate/launch a full bf16 converted-history buffer. Extend shapes in `r4d_shapes.cpp`, registry `r4d_rows.cpp`, CPU `libref`, and actual cache row-pitch/operand dtype in core. Existing scalar and matrix paths have slightly different sum order even on bf16; compare both to bf16 oracle and to each other, including near-ties. Preserve `qsa_score` -inf for missing page and deterministic `qsa_select`.

**Expected cost, not an assertion of speed:** per distinct full-history 256K key scan, across 12 layers, naive compulsory QSA reads fall from 192 MiB to 96-108 MiB depending on format/pitch, **before** memory caching and sharing across query tiles. Writer now performs max-reductions; reader now performs scale loads and per-element dequant. Matrix BF16 fragment conversion, register pressure/LDS broadcasts, and reduced occupancy/spills can outweigh less DRAM traffic; short contexts are launch-bound. Measure scalar/matrix `qsa_score` microbench on both GPU types, memory bytes/bandwidth, register counts, scratch, 248-256K decode, and end-to-end TTFT. Do not predict a percentage throughput gain without a device A/B.

## 4. Selection accuracy and long-context trace

For bf16 block key `k_b`, quant-dequant key `k'_b=k_b+e_b` and per-head query `q_h`, approximate bound (excluding differing reductions):

`abs(score'_b-score_b) <= sum_h abs(dot(q_h,e_b)) / sqrt(128)`.

ReLU is 1-Lipschitz. With uniform score error <= eps, a strict kth-vs-(k+1)th margin exceeding `2*eps` guarantees no boundary reversal; otherwise a tiny numeric perturbation may **change which attention pages are read**. Quality risk is discontinuous selection, not just averaged logit noise. Exact tie handling and low-index priority, zero/negative zero, absent pages and nonfinite scores are correctness issues.

**Paired trace, same query tensors.** Record a fixed long-context baseline's per-layer QSA query vector, complete bf16 block keys, logical block-index -> QSA physical page map, attention table, positions, reference per-block score and selected logical block IDs. Evaluate the quantized scorer on *those exact tensors*, ideally two score paths from one frozen trace, not two independently generating sessions (which would diverge before selection). Trace 48K, **100K**, **248K** and **262,144 within max-context limits**, with decode, prefill, speculative verify, mixed lengths, 12 QSA layers and MTP. Report sample coverage and the actual effective token counts. Head-level dot error is diagnostic, but **selection belongs to (query/token, layer)**, not (token, head, layer), because the four heads' positive scores are combined.

Primary metric per scored (query, layer): **selected-block overlap = |topK_quant intersect topK_bf16| / |topK_bf16|** on complete *logical block IDs*, excluding the separately appended partial block. Also report exact-set agreement %, changed-block count, symmetric difference, reference recall, Jaccard, p1/p5/median/min overlap, per-length/layer buckets, ranking flip distribution, score error and the kth/(k+1)th margin. Identify whether missed blocks contain a needle; optionally weight disagreements by baseline score margin or attention contribution. Different physical page allocations across runs must not count as flips.

**Correctness gate:** below **2051** tokens, all complete blocks must be selected identically, in proper order, plus same partial block and `seqused`. On the frozen synthetic cases require 100% set agreement and byte-correct codec/reader math. Above boundary, refuse on any bug-induced invalid page, systematic/large-margin flip or missing known needle-bearing block. **Do not manufacture a 99% aggregate-overlap threshold.** Run the pilot, publish its per-layer error distribution, and predeclare an acceptable top-k overlap/error budget with the owner before the device A/B. If the measured overlap is unacceptable, reject the codec immediately, even if average KLD looks fine.

## 6. Qualification and A/B gates

- **A/B arms:** A = unchanged bf16_i8 attention + bf16 QSA; B = same attention + i8/group32 QSA; C = same + i8/one-scale; D = same + E4M3. Include bf16-all and fp8-default only as contextual references. Pin exact model, source/build IDs, layout, heat/policy, power, topology, prompt tokens and GPU lease. Fresh run records and provenance for every arm.
- **Selection first:** paired recorded trace at 48K, 100K, 248K/256K; full per-layer overlap, exact-set agreement and disagreement/margin reports; reject if tracing fails or selection gate fails. Check CPU/libref vs device (including scalar and WMMA), visible/hidden first-token bounds and MTP.
- **KLD:** long corpus vs bf16, **mean no worse than the ENG06 bf16_i8 bar 0.00269** (ENG06 cites 0.002685), plus top1 match, high-percentile position KLD, and repeats to quantify arithmetic/chunking noise. Flash-Next VTP44 reports a KLD arithmetic-noise floor, therefore mean KLD alone never establishes key-selection safety.
- **Needles:** `tools/lab/radiance/needle_probe.py` with identical cases across arms (10%, 50%, 90% insertion, three repeats; exact code, temperature 0) at 48K and **100K** plus **near 256K** with output headroom. Require no new misses against same-day A and bf16, **18/18** at 48K+100K wherever the baseline can pass. Historical Flash-Next bf16_i8 is **9/9 at 48K and 8/9 at 100K**, not 18/18; rebaseline and explain all misses with selected needle-block traces rather than asserting a historic 18/18.
- **Speed/capacity:** `flashnext-parity.sh` measure and compare, at least **two independent launches** per arm, 451s warmup, same 4-GPU helpers/live-policy provenance, matched **4-session** admission, ABBA order if possible. Log 1/4-stream decode and 248K/256K decode, 44K document and 100K/256K prefill, TTFT, scorer microbench, kernel spills, bytes/page and available KV tokens. Reject any reproducible >3% decode/TTFT regression beyond measured noise or memory-accounting mismatch; no goal of making 8-session bf16_i8 start.
- **Verdict:** ship only as a **new non-default opt-in** if selection agreement, KLD, 100K/256K needle retrieval, all-plugin numeric and performance gates pass, with measured capacity. Otherwise reject and retain baseline, publishing overlap, top-k margins, KLD, needle failure cases and admission logs. Do not promote the managed patch on compile-only proof.

## 7. Unresolved risks

1. **Allocator/ABI page format:** arbitrary 128-code + f16 sidecar is not a standard bf16_i8 attention row. Missing byte-pitch, pool/mirror/restore or layout-version support can erase savings or corrupt keys; investigate before writing a patch.
2. **Ranking sensitivity:** small absolute errors flip top-512 boundaries; no justified nonzero top-k overlap tolerance exists yet. Long-context fixed-query traces and needle-block attribution are the decisive scientific evidence.
3. **Device cost:** quant decoder and bf16 WMMA fragment conversion may increase VGPR/LDS, reducing occupancy on gfx1100; the 2x smaller BK byte stream does not guarantee faster scores or end-to-end decode.
4. **State/history correctness:** deferred writer order, per-layer tail, speculative rollback, MTP, prefix reuse, dense-resident QSA versus streamed attention and partial-page handling all need device-backed proof.
5. **Source drift and capacity arithmetic:** pinned v1.17 and frozen ABI44 composition differ. Design numbers are logical-byte predictions; actual group pitch, max-session capacity and KLD must be observed. No code, GPU run, patch lifecycle change or production recipe edit is authorised by this document.
