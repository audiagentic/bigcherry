## Step 2 — measured larger-pool long-8 experiment

The candidate **production** build (`radiance:stock:linux-radiance: ok`, build plan `083f6f787cfcfc3f0876ff2a5e0379bf`) on the corrected derivation completed a cold/warm pair in `long8-rerun-2/long-8.json`:
- cold: **26.6264 ms/step**, 113.736 estimated stream decode tokens/s, acceptance 0.6667, 255501 prefill tokens;
- warm: **29.8786 ms/step**, 87.595 estimated stream decode tokens/s, acceptance 0.5544, **13 prefill tokens** (prefix hit);
- benchmark target 256000 prompt tokens, 253773 tokenized prompt reported per stream, 256 generated tokens each round, one stream, two reps.

Warm is 7.5214 ms/step (20.1%) better than the original 2.2 37.4 ms result, but 3.2786 ms/step (12.3%) worse than 1.17's 26.6 ms. This is an association with the larger pool, not causal proof of tier demotion; the runs differ by commit/build, although warm acceptance and step count match.

A fresh counter-backed rerun `long8-rerun-3` failed before benchmarking: cold native-v3 startup consumed the 650 s readiness deadline in fingerprinting and measurement; the owner stopped cleanly. Reusing that measurement work directory then failed strict stored-replay validation (`BC_CFG_PLAN_MISMATCH: stored semantic execution projection differs from current config/variants`). No timing was generated by either failed attempt. The subsequent fresh-directory rerun is documented in Step 3.

There is **no isolated expert-loan disable/limit switch** exposed to this native serving configuration. `--deterministic` would turn off lending (`engine_bringup.cpp`) but also pins expert placement and changes the run's policy, is mapped under lab `spec.experiment`, and cannot be treated as a controlled loan-only arm under a production manifest. No loan-only timing is claimed.

## Step 3 — production-candidate rerun and tier-counter verdict

The owning source fix is **already committed as `696deedc1`** in `components/serving/v2/admission.cpp::refit_serving_pools`, called by `rad0011_plan_memory` during measured native startup. Rather than throwing away optional measured KV headroom when exact MiB weights and KV rounding barely exceed claimable memory, the fix fits the largest admissible pool at or below the measured preference, subject to the calibrated minimum and expert floor. No second source fix was justified by this experiment. The production engine and serving binaries in build plan `083f6f787cfcfc3f0876ff2a5e0379bf` were compiled **after** that fix and were used for both successful warm runs; this step verified that build instead of claiming a new production compilation. A nice-19 incremental S5 test build reported `ninja: no work to do`, then `bc_s5_refusal_test` exited 0.

The fresh independent run `long8-rerun-4/long-8.json` completed on the fixed production build under a GPU lease, with **26.4219 ms/step cold** (85 steps, 0.6667 acceptance, 255501 prefill tokens) and **29.9093 ms/step warm** (95 steps, 0.5544 acceptance, 13 prefill tokens). Warm was 87.56 aggregate output tok/s, p50 stream gap 34.143 ms. The first successful fixed run was 29.8786 ms warm; repeat difference 0.0307 ms. Original 2.2 warm was 37.3919 ms (95 steps, 0.5544 acceptance, 13 prefill tokens); the corrected pool improves by **7.4826 ms/step, 20.0%** at the same work/acceptance. It remains **3.2626 ms/step, 12.2%** slower than 1.17's 26.6467 ms warm. The old 1.17 cold was 29.1854 ms, original 2.2 cold 26.8111 ms.

The engine's own `/sessions` counters were sampled every 2 seconds into `tier-samples.jsonl`. At **0.205 seconds before warm start**, the pool held **253784 tokens** (`pool.tokens_used`) consuming **3,820,729,364 B**, out of `pool.tokens_total=1445720` tokens. The host prefix tier held **24,950,016 B**; the separately enumerated small *idle* sessions accounted for 537 host blocks and 0 device blocks, not the active long prompt. At **1.796 seconds into the 3.034-second warm round**, the pool still held 253784 tokens; host bytes remained 24,950,016. Movement counters were unchanged: `to_host=441`, `dropped=455`, `promoted=14`, `host_drops=0`, `restore_cuts=0`; `stall.restores=1`, `restore_ms=0.490292`. The one restore and the other movements accumulated **before** warm. No new host-tier movement/restore was observed at the sampled warm point; the last ~1.2 seconds of warm were not sampled after completion. This is strong evidence that the **fixed 2.2 warm long prefix was maintained in GPU KV** rather than restored wholesale from host. It does **not** prove the original 17.61-GiB 2.2 build demoted the long prefix, nor establish 1.17's per-round residency: those builds have no saved per-round `/sessions` samples.

**Verdict:** the source fix restored the measured KV allocation and removed roughly 20% of the bad warm-step latency without changing decode-step count, prefix hit length or draft acceptance. The remaining ~3.26 ms versus 1.17 is unresolved and must not be attributed to tier restores without a comparable 1.17 and pre-fix 2.2 capture. No standalone loan-only switch is available, and the `--deterministic` multi-behaviour experiment was not run.

## Subsequent disposition

The pool refit shipped; the later [warm-step study](RUM09-WARM-STEP.md) attributed the remaining cross-release discrepancy to batch composition. This report is historical evidence, not a claim of an unresolved regression.
