## Approved implementation design (single note)

**Decision:** replace only BigCherry's `abi/bc_moe_remote.h` and consumers, not upstream Radiance `rad_abi.h`, `RadKernelInfo::init/fini` or plugin layout fingerprint. Exactly one Engine-owned remote generation binding holds a frozen typed policy, size-checked *context-aware* callback table, layer maps and burst state; libr3moe's opaque per-binding `HookState` owns existing Ledger, rank events, HelperWatch and GPU buffers. The native Engine owner and claimed TP group are separate from the helper session, placement epoch/slot and 16-byte StepTicket.

**Discovery / lifetime:** upstream Registry discovers **static** plugin kernel rows before Engine claims its TP group. Bind after native `rad_engine_claim` and before declaration, resolving the factory on the *already loaded* `Registry::plugin("libr3moe")->handle` (RTLD_LOCAL). Kernel instances receive `tp_group` at `init`, borrow the owned generation and release it at upstream `fini`. Reuse `rad_bc_shared_slot` and `rad0017` rendezvous/deferred free. If shared slots cannot identify the borrowing Engine, at most one *non-owning* group→binding lookup is permitted **at init only**, erased before numeric group reuse. One minimal exclusive helper-on owner claim is permitted; native arch claim does not protect against different architecture plugins.

**No alternate implementation:** delete the existing DSO constructor/destructor, global callback registration, per-call manifest reads, map replay, TLS-selected ownership, duplicate placement or cleanup controller; no compatibility shim, additional policy parser, registry, loader or collective. Do not call plugin callbacks while holding a layer map mutex. Keep helper-off graphs without mailbox ops. HyperConn, placement, block declaration and runtime must ask the same bound policy predicate. Rank ticket can remain a value **only** if its associated Engine binding is explicit and validated; never use TLS to select policy or transport.

**Stop ordering:** on success: close admission, cancel only unused unbound ahead tail, complete bound current/ahead parent and rank seal/host_done, wait helper/rank proof, join worker/snapshot/placement threads, drain native Engine GPU streams, invoke per-instance `fini`, detach and free transport, then release exclusive helper claim. On fault: poison existing Ledger + TP group, unblock peers, join/drain and use the same release tail. Failed rank publication must not free peer-visible device pointers until all peers unwind. Clean success must not call `Ledger::interrupt` before proof.

**Performance constraint:** no new lock, allocation or group lookup on normal per-step decode/prefill; all changes to state ownership happen at Engine bind/declaration/kernel init/cleanup. Each slice records removed code, tests, hot-path cost and commit. Do not claim latency improvement without uninstrumented measurement.

## S1 sequencing decision (resolved)

The lead chose option (a): S1 removes `bc_moe_remote_register`, `g_plugin`, DSO constructor registration and the unscoped callback route together, and binds through an explicit factory on the already-loaded plugin handle; per-generation HookState ownership and full teardown stay in S2. Implemented as: `bc_moe_remote_open(handle, slot_base, ranks, limit)` (after `rad_engine_claim`, before declare) finds `bc_moe_remote_plugin_open` with `dlsym` on `Registry::plugin("libr3moe")->handle`; the Engine's `BcMoeRemoteAdmission` owns the opaque generation; consumers hold it through `Geom::bc_remote` (found once by `bc_moe_remote_lookup(rad_build_slot(ctx))` in `geom_from`), `Program::ctx` (planner, bring-up) and `Ctx` (rank thread hands generation and ticket in; no thread-local). The slot table holds non-owning pointers, is written only on open/close and read at init time. Publication order: refuse a bound slot before the factory runs, run the factory, publish each slot by compare-and-swap from empty (release); close clears the slots before the plugin close; a closed generation stays allocated until destroy and refuses every call with `BC_MOE_REMOTE_STALE`.

## S2: hook state in the generation

`R3MoeHook` (the former process-wide `HookState`) is allocated by `bc_moe_remote_plugin_open` and is the `self` of the engine's callback table; `cb_close` closes the mailbox, unpublishes the hook and frees it (explicit close/detach), so the generation owns the Ledger, rank events, HelperWatch and GPU buffers. Every internal function takes the state; threads are started with it. The seven direct `r3_moe_*` entry points take the hook as their first argument and refuse a null, stale or foreign handle with `RAD_E_STATE` before any side effect. Kernels reach their hook through the engine's claimed `tp_group` (already passed to every kernel `init`; it is the span base the generation opened): `r3_moe_hook_for_group(tp_group)` returns the live hook only when its `slot_base` matches. One helper segment exists per process, so `g_live` (non-owning, one pointer) holds the live hook: it is what makes a second helper-on engine get BUSY before anything is mapped, and what the entry points compare handles against. It is written only at open/close. Handles are serials, not addresses (S3): `LiveHook<T>` (`hook_identity.h`, tested on the host) assigns a nonzero never-reused serial at publish, so a handle from a closed generation cannot match a later hook allocated at the same address. **`g_live` is the one remaining process-wide object and it is inherent**: the helper segment is a single named, process-wide resource, so at most one hook can be live. It is a non-owning mutual-exclusion and lookup pointer only; no policy or state hangs off it, the generation owns everything and its close frees it. The "no process-global" clause is read as: no process-global *engine state, policy or ownership*; this pointer is the resource's exclusion record. The hook publishes before `open_mailbox` (its placement thread starts inside and calls the entry points by serial) and unpublishes on a failed open.

## S4: clean stop, fault stop, partial initialization, concurrent refusal

**Stop kinds.** A clean stop is one where `wait_finished` proved every bound ticket terminal (`BcMoeRemoteAdmission::clean()`); it never calls the plugin's `fault` wake, so a healthy ledger is never interrupted. The old unconditional `shutdown()` after the server returns is now `if (!clean()) fault();`; `fail_loop` and the drain-deadline fatal call `fault()`. The plugin decides again at `close`: `Ledger::clean_stop()` (not interrupted, not faulted, no outstanding ticket) closes with `wake()` only (no state change) and joins the placement thread with no deadline: the thread leaves on its own (its loop checks the stop flag each iteration, and every wait in a cycle ends at that wait's own protocol deadline, where `Ledger::wait_drained` turns a miss into a ledger fault and a helper fault ends the loop), so a stuck cycle shows as a fault state rather than a literal timeout here. A fault, or tickets that never retired, interrupt the ledger. Ledger interruption is therefore only ever a fault response. The stop order the engine already follows (finish admission, cancel unused tail, bound parents prove, helper/rank proof, join threads, drain streams, kernel fini, detach, release) is unchanged; ranks and kernel instances are gone before the generation closes.

**Partial initialization.** The unwind lives in rad0017's lifecycle (RUM02 slice 4: published peer pointers are retained until the owner retires them, the failed rendezvous refuses reuse). `radiance_ar_allocation_test` now fails either rank after both published, checks that the other still holds all eight allocations until the owner retires, that a further init in the failed group by the same owner is refused with no allocation, that a second retirement is idempotent and that a replacement owner reuses the group. The libr3moe open already unwinds on failure (`abandon_mailbox`, unpublish, delete).

**Second helper-on engine.** The helper segment is one process-wide resource: `LiveHook` publishes one hook; a second `bc_moe_remote_plugin_open` returns BUSY before the hook is allocated or any segment is mapped, and the engine refuses its own bound slots before calling the factory (`moe_remote_generation_test`). A helper-off engine has no generation and never touches either, so it coexists. Real BUSY with a live helper needs a card (smoke).
