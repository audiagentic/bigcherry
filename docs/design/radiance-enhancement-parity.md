## 1. Scope and decision rule

Preserve every active enhancement, including features not exercised by the four currently served containers, optional/diagnostic recipes and supported architecture/shape boundaries. Preserve its public option/row/layout/quality/performance contract (unless owner approves an explicit changed contract). Do not preserve duplicate source text for its own sake. A failed anchor is a port task, not retirement evidence. No active patch, rewrite block, component or diagnostic is removed merely because upstream removed a quant or current YAMLs do not select it. Unused encoding-specific code may be archived after checking all active capabilities/consumers, with explicit owner approval where capability is actually lost. Preserve original code/results and a viable old-pin rollback. Do not carry retired upstream kernels back indiscriminately: if the only implementation supports an encoding native 2.3 refuses, classify as an explicit compatibility conflict, retain historical code and seek decision on narrow port or retirement. No silent deletion or state demotion. Untested/diagnostic packages remain in their existing class; never promote via incidental selection.

Use Git, existing patch metadata, recipes, origin manifests, rewrite declarations, component targets and existing evidence. Derive the inventory from active patch directory (not recursive archive), recipe source resolution, native rewrite files/blocks plus rewrites.txt, origins and component sources. Retain historical archive separately. Record one short disposition per item in existing bump evidence README/table, grouped when tests are shared, with patch/row/block identifiers, affected capability/consumer, target upstream source/commit, outcome, minimal test and result reference, remaining local delta and successor/rollback if retired. No new schema, CLI, database, blanket compatibility shim, or duplicate plan. Exact inventory must match at final review; new main items added mid-bump require re-triage. The snapshot below is a work allocation, not a new canonical patch catalogue.

Disposition: unchanged/compatible (source proof + normal compile); port (native incomplete, no need to benchmark it); partial adoption (native foundation + retain delta); candidate replacement (prove before removing); conflict/blocked (no equivalent, owner decision); archive (approved equivalent/obsolete capability and evidence). Unqualified is not PASS. For an adoption whose equivalence is clear by inspection (e.g. comment-only or exact helper rename) compile/contract fixture suffices; semantic/performance changes require real oracle and relevant performance check.

## 2. Controlled comparisons without a full engine

A = previous qualified 2.2 BigCherry behaviour, B = 2.3 native candidate with only focal enhancement absent, C = 2.3 candidate retaining/reconciling the focal enhancement. Preserve unrelated dependencies and configuration in B/C (same source/SDK/flags/architecture/provider/inputs/geometry); use small matched fixtures or standalone plugin units, not bare upstream with all BigCherry features absent. If B cannot express the old contract by inspection or refuses the shape, record counterexample and port C; do not build B just to confirm known missing functionality. If B passes independent oracle and A contract, no need to build C. If B/C need different ABI, run separately matched binaries and compare outputs/records; never load old ABI plugins into new engine. Old evidence may supply A if its exact scope/identity/measurements are relevant; do not rerun old release by default. Compare A to target for preserved contract; B vs C same pin for attribution. A cross-pin speed change alone cannot identify a local patch's benefit.

Use actual production contract in the fixture (not a second implementation duplicating the code under test). Existing text-anchor tests prove composition, not algorithm correctness; add the smallest actual callable unit/fake dependency in existing owner if missing. Prefer a deterministic known expected result or existing independent reference; not only B==C. For unchanged mathematical contract use exact integer/byte output (including BF16 conversion and layout roundtrip where specified); an intentionally different arithmetic path requires the existing accepted quality budget and owner decision if behavior changes. Resource records/spills and cold/warm replay only for affected performance-sensitive rows, with old established noise/repeat criteria; widen targeted points if inconclusive, no arbitrary extra rounds. Reuse proof where changed dependencies cannot affect it; record why. Compile failures, skipped required cases, unknown closure/row coverage, stale references or performance ambiguity are nonpasses, not silent successes.
