## Scope and acceptance rule — owner direction, 2026-11-25

Keep this a small native-launch cutover, not a general serving rewrite. This rule supersedes broader implementation and test suggestions in the earlier reviews and plan notes.

- Preserve existing working behavior and reuse its implementation: native parser/Fleet, owner, resource checks, helper transport, cache, power controller and receipts. Remove the executable manifest and obsolete launch plumbing only. Move authored serving policy to YAML; do not redesign unrelated configuration, discovery, calibration, release inventory or evidence formats.
- Use existing raw YAML snapshot, typed arguments and transport where sufficient. Add a narrow native hook only for a demonstrated missing capability. No new identity/hash scheme, generic descriptor, registry, parser, allocator, scheduler, supervisor or test framework. Do not rename or reorganize code solely for aesthetics.
- Reuse existing tests and evidence. One cheap parser/extension/roster check for shipped YAMLs, one affected integrated build and existing CI, then one shared installed dense TP3 and helper/MoE lifecycle/parity cohort (reuse Gate E and existing acceptance tools). Exercise measurement and named reuse, quality and actual power apply/restore in those same runs where applicable. Add a hardware case only when it exercises a materially different changed path not covered by these runs. No all-config GPU matrix, all-controls power sweep or rerun of historical experiments as a blanket migration or bump gate. Repeat timing only when needed to distinguish regression from noise under existing RHP12 rules; reuse a valid required cohort rather than run it again.
- Keep existing numerical, resource, lease/restore, admission and no-regression requirements. Use existing targeted negative tests plus only missing cases for changed behavior. Do not weaken a required gate, relabel untested as passed, or ship an unsupported regression. Historical independent tasks remain with their owners; prove their relevant obligations or record outstanding work, not repeat unrelated acceptance just because S18 lands. Any newly required capability or genuine regression is a blocker.
- Keep the existing variant authored-diff check (port is an operational endpoint, its existing exclusion is intentional); compare native effective values only where migration changes interpretation. Preserve authored port, use existing lab YAML editor. Keep existing approved packer/installer lists and equality test; unifying their generation is optional cleanup, not a new roster system or cutover prerequisite.
- Restore named power profiles through the existing controller and per-device resolution. Stock remains no-write; real qualified minimum-cap apply/restore is the first end-to-end nonstock test. Keep clock/voltage capability, including paired undervolt, but no blanket retuning or default activation. Reuse existing qualification/readback and calibration compatibility checks, extend only missing actual settings fields. A new or changed unqualified setting is refused, not silently applied.

Stop when native YAML starts the same supported workloads with preserved features, reliable ownership and existing acceptance; capture remains output-only. Do not add features, new research, generalized abstractions or exhaustive matrices to this migration.

## 1. Decision and non-negotiable end state

An operator authors **one native Radiance deployment YAML**. Native keys are native keys; BigCherry-specific authored intent lives in its existing closed `x-bigcherry` namespace. All authored **serving** policy (including the site and reusable power profile rules) uses YAML, with one authority per field. Non-serving build recipes, patch metadata, release manifests and historical measurement formats are not a new migration project. Machine facts, capability probes, measured memory, chosen BDFs, per-launch endpoints and generation identities are derived or observed, not manually authored model options.

The owner remains the existing C++ `bc-serve`; its child invokes the actual pinned Radiance native entry `radiance --config FILE`. Helpers are launched from the same admitted YAML and an assigned role, not from a generated all-process configuration. Remove `--manifest` as an executable input for owner, engine, helper, measurement, quality, experiment and replay paths. No manifest -> YAML translator, new launch JSON/YAML envelope, flattened flag list, getenv tuning surface, wrapper around the old reader, alternate "v4" contract, or compatibility path. No dual feature flag after cutover; rollback is to the previously installed matched release, never an older reader in the new binary. A run may still be captured as a manifest **output** if that is the least disruptive evidence format. It must not be the input to any launch, be required to derive one, be read by an engine/helper to start, or grant authority to apply power. Named config restarts may reuse validated measurement data; an archived run record may point a human at its saved YAML but cannot start a process.

Use the upstream native single-model fleet startup and HTTP front rather than our parallel managed front, if the exact-source tests demonstrate equivalent startup, admission, readiness and drain. The design makes that the required target, not an optional legacy fallback. If native Fleet cannot meet a necessary property, make a narrow, reviewed managed patch at that actual boundary, with implementation in owned code; do not clone Fleet. Multi-model sharing/parking/hot reload is **not** in scope (RUM10 explicitly deprecated by owner); fail closed for unsupported managed modes. Standalone unowned native Radiance remains normal stock behavior; no BigCherry hardware mutation without an authorized owner.

### Why this is needed

RUM04 successfully replaced authored TOML layouts and the v2 reader and accepted 16 native YAML configs. It explicitly retained the generated v3 measured execution envelope. Its acceptance was not a no-manifest-launch gate. Actual code in session.cpp at the audited revision uses `--manifest` for helpers (2683), measuring engine (3481), final engine (3671), stored replay (3955); owner forks `--write-manifest` (3417/3557). The documented operator start --manifest is a real executable input. Native YAML bytes are embedded in spec.native_config; the engine bridge replays them into Config. The patch still owns a separate managed Engine/front path. In bc_serving_manifest.cpp:157–395 the bridge recognizes the manifest and synthesizes remaining argv, :408–519 reparses native Config and injects derived host/rank settings, :519ff manages HTTP front, :655ff runs the alternative managed engine entry; g_store/g_ptrs/g_label and manifest-labelled provenance are remnants. Some names/comments say v1/v2 although the active contract is v3. Removing only the JSON parser or renaming it would leave the problem.

Pinned upstream source verified from the local mirror (git show b6b8751:core/main.cpp, core/fleet/config.{h,cpp}, core/fleet/fleet.cpp): native main accepts --config FILE and --check; load parses YAML, applies native unsupported checks; online calls fleet::run, offline uses native Engine construction, with one model. Fleet::load_op at ~1887 chooses cards and instantiates Engine; Fleet::run at ~2869 preloads a single model before listener; use_broker() at ~497 is false for one model; reload loop checks g_hup at ~2813. Older mirror revision 3deabdae showed the same flow, but the actual pin is the authority. Fleet::parse(text,origin,out) exists; load is the disk path. Do not assume stock accepts our helper/KV/measurement extensions, that a path under /proc/self/fd resolves relative model paths correctly, or that the stock front is semantically identical to the current managed front. Prove those boundaries.

## 3. Runtime boundary: configuration is YAML, measured facts are not configuration

There is no technical need for a child to read an all-process execution document. However, there is a real need to transport a small set of owner-derived data (e.g. exact per-rank BDF order, memory admission, shared helper generation) across process boundaries. Removing them would break safety. Reuse existing typed component/domain interfaces and existing process-boundary primitives. Do not invent a generic "LaunchContext" containing all old spec fields. A narrow admission input is acceptable only for a consumer that cannot obtain the fact from native YAML, native allocation or existing shared transport. **No new general-purpose manifest format, file, version, serializer or CLI.** Each remaining fact needs a named producer, consumer, derivation, lifetime and negative test. Owner does not launch from its recorded output.

Proposed boundary:
- Owner reads authored YAML once, bounds size, verifies exact UTF-8 bytes and root, seals raw YAML in memfd (not JSON envelope embedding YAML). Retain NativeConfigSnapshot read/sha256/root and existing FD lifecycle; refactor from_manifest/manifest_field out of execution. Inspect matched engine with the identical bytes and resolution root; no GPU, no write authorization. Use directory FD + child-local fchdir and frozen canonical model/runtime roots; test upstream relative-file resolution, native parser diagnostics, symlink/author-file replacement, namespace and environment. Raw YAML memfd via native `--config /proc/self/fd/N` preserves native invocation; if upstream load reopens/derives wrong parent path, patch the existing load seam to consume sealed bytes and explicit root, via native fleet::parse. No second parser or generated effective YAML to hide derived facts.
- At the native load seam, managed owner identity is recognized through the existing restricted inherited descriptor mechanism; verify full seals, expected parent/owner, exact YAML digest/root, matched binary/SDK/model identity, ordered physical devices. Reject missing/invalid admission for managed-only x-bigcherry requirements; never silently run without helpers/power when a managed start fails. Ordinary upstream unowned YAML continues native execution, and no hardware power mutation occurs in it. Define precise managed-vs-standalone behavior when x-bigcherry contains helpers or apply intent: refuse unsupported requested functionality rather than claim it happened. Stock upstream unmodified binary ignores x-* by design; docs distinguish that limitation.
- Keep only data-plane needed startup values: typed existing resource measurement/expected plan and ordered selected-device identity for engine; shared remote transport generation, independently checked owner map and one helper role/derived budget for workers; per-run ephemeral trace/heat nonce/output handles. Prefer existing shared-memory generation/control publication and existing typed plan/rank-demand receipt types; for an input not already transported, use a bounded, sealed inherited role-specific FD, using existing type/size and lifetime checks, with no native option mirror. It is not persisted or user-editable, contains neither YAML nor full system snapshot, and is not a replay input. Reuse existing owner/generation and snapshot checks; no pathname reopened after validation. Avoid a new aggregate descriptor containing all domains. ABI names illustrative until implementation review. Strict C++17-safe boundaries for patch/component callbacks; use existing Guarded callback boundary. No per-step allocation, policy parse or sysfs write.
- Native parser and extension settings must be derived once from the same YAML bytes. Native core obtains its native Config normally; BC engine settings (bc_engine_settings.h and typed plugin getters) derive from the existing extension schema plus genuinely derived transport facts. Workers decode same extension, then receive only assigned device, role budget, model/build identity and shared transport facts. Worker must independently validate plan_owners against the published ownership and supported formats, not merely trust owner digest. Avoid worker reading full native FleetConfig if not required; it may use native parser's matched model identity result, never a second handwritten native settings table.
- Native derived host-pool/prefix/checkpoint, rank-devices are bound at the actual Config seam *before* any Fleet reservation/queue/Engine allocation uses them. Apply only absent/auto or exactly agreeing authored fields. Current prepare_native_engine_config handles per-rank vs aggregate pool MiB, checkpoint sentinel, offline differences and exact rank-devices checks: retain semantics, not its manifest dependency. Do not regenerate native YAML with these values or overwrite explicit author choices. Use existing resource planner and native validation to derive, not a second allocator.
- Native online enters Fleet::run, not bc_serving_managed_front. Native one-model preload before listener, but Fleet opens/trims/reopens reserve queues, has own failure paths and load state; new queue/cgroup/host accounting must be measured, not assumed equal to managed direct Engine startup. Bind admitted Config before Fleet::load_op's pools/choose_cards/reservations, verify chosen local devices before Engine construction, retain rad0011 check at actual memory plan before weights; no broker for single model. Keep managed one-model restrictions, refuse park/reload/extra models until separately authorized; patch reload guard at native loop before it reopens path. Preserve front auth, model aliases/health, metrics, cancellation, drain and timeouts, including failed load before listener; remove custom front once same-build native gate passes. Offline quality and plan-only use native offline Engine path with a minimal plan-measure enhancement as needed; ensure exact same selected rank order/masks, no listener, correct helper lifecycle and offline KV semantics. Do not bring back old native flag projection. Runtime plan output path/diagnostic handles are operation inputs, not engine configuration.
- Owner holds exclusive lease and admitted native bytes from before power/child mutation through verified process exit and exact restoration. Native engine/helper receive only physical device visibility needed; preserve ROCR/HIP and child-local mapping, disjoint helpers. Admission fails before child GPU initialization on mismatched role/build/root/owner/descriptor. Native Engine plan must check live host/VRAM/pin/expected plan before weights and emit structured refusal for bounded remeasurement. No new shared-card scheduler, host allocator or fleet broker.

### 4.1 Concrete runtime sequence (illustrative pseudocode, not a new API)

```text
serve(config_yaml, site_yaml, authorization):
  snapshot = seal_original_yaml(config_yaml, root)
  native = matched_engine.inspect(snapshot)       // stock parser; no GPU
  intent = decode_existing_extension(snapshot)
  selected = select_ordered_physical_devices(native, intent, discover())
  policy = resolve_power(intent, site_yaml, selected, fresh_probe, qualification)
  verify_owner_lease_and_policy(policy, authorization)
  verify_model_build_roots_and_resource_preconditions()
  transaction.begin(policy)                      // durable exact originals, readback
  plan = validated_cached_measurement_or_measure(snapshot, selected, policy)
  recheck_live_room_and_effective_power(plan)
  launch_helpers(snapshot, role, existing_transport_and_derived_budget)
  exec_native("--config", snapshot_fd_path)       // typed expected plan only, no full manifest
  require_native_preweight_admission_and_health_canary()
  capture_run_record(snapshot, plan, effective_policy, receipts)
  stop/drain/reap_all_children()
  transaction.restore_and_verify()
  release_lease()
```
Measurement itself may start temporary helpers and native measuring engine after apply; reap them before final start, keep same admitted policy and selected identities throughout. No extra GPU child before power admission. If any failure occurs after first write, owner drains/reaps then restores before lease release. If owner dies, stale journal blocks mutation until verified authorized recovery; do not claim SIGKILL guarantees without proof. Named replay starts from current YAML and site, checks matching measurement key and live room, not from capture. If capture fails, durable journal and required run records still enforce safe cleanup; owner must surface capture failure according to existing record policy.

### 4.2 Implementation seams verified at c41676c90 / Radiance b6b8751 (2.2.0)

This is the implementation checklist for the existing owners, not another architecture. Source review only; the interfaces below describe the required changes, not implemented APIs. Retain current behavior unless explicitly removing the launch document.
