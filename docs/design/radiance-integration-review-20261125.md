### 2.1 Native IQR is NOT general local IQR replacement

Candidate libr3d/r3d_i8_gemm_rows.h declares packed gemm_nt_q_iqr for i8a8h, group128, M 1–2048, N and K multiples of 128. Actual layout inspect in r3d_iqr_layout.cpp restricts fwht128, computed trellis MAD, U3/U4/U5 only, L16 (65536 table entries), run rows 128/256, 4-plane BF16 row-group or 5-plane factored F32 scale. It checks run divisibility and weight table consistency in relayout. Private raw packed layout tag r3d.iqr.mad.raw.v1 is distinct from the generated library's layouts. The r3d_gemm_iqr.hip iqr_scalar kernel is one output per thread walking K in 128-element groups; explicitly rounded FP32 group folds and one BF16 conversion. The optional operands are refused if present; malformed packed header returns early in device kernel, so launch success alone is not data-validity proof. CMake includes the row and layout only when R3D_GPU_TARGETS STREQUAL "gfx1100"; a build with several target strings can omit it. 88b5a04a adds builder and host/device tests but those were not run here.

Our important 6/7-bit computed-trellis forms (and L15, table/chained and bias variants) are not established by this row. It must not be the sole provider for those local workloads. Even supported u3/u4/u5 needs actual selected layout/relayout/unrelayout, operand availability and row selection from the real builder, byte/canonical rounding comparisons and performance. A scalar correctness row is not proof of WMMA throughput. Use RCS25 discrete test for supported forms; then RCS15 exact same-source arms A generated/BC, B native libr3d, C reference; separately mark unsupported shapes. Do not use A on one pin and B on another to attribute provider speed. Native int8 row in same header declares group128 BF16 group scales and every M, with LDS 128x128 path above M=128; the local source-backed IQ8R two-level U8 × BF16 row-scale group256 case in RUM15 is a different format/rounding problem. Inspect actual model headers, not the recipe name. No automatic native adoption for u6/u7, group256, special head/TP or KV forms. Preserve current optimized production provider until matched acceptance.

### 2.2 Loader reality and simple versioning

Upstream core/plugin/loader.cpp stage_ uses RTLD_LOCAL, existing rad_plugin_abi_version AND rad_plugin_abi_layout, then native rad_plugin_info. Same ABI integer different layout is explicitly refused. Native loader commits in hierarchy order; an explicit kernel hierarchy is exclusive, but a missing requested name only logs a warning and a plugin can decline a machine (RAD_E_UNSUPPORTED); it may therefore select a base/ref row unless a managed deployment checks intended coverage. Schema disagreement across providers is refused; the same schema is a normal re-declaration, and multiple valid rows for the same op are expected. Do not prohibit the intended overlay/base overlap. Use native plugin+row identity and actual winning row for each domain, arch, parameters and encoding; reject accidental duplicate plugin identity or inconsistent positional schema, unapproved shadows, missing required provider or unexpected ref/CPU fallback. Validate per-device code objects as native loader does, not build_target text alone. Test order both overlay-first and base-only; compare row contracts including shape, relayout/unrelayout, init/fini, tuning and chaining; ensure removing overlay restores baseline. No second loader, new versioned descriptor export, composition hash or ABI fingerprint scheme. Retain the upstream layout fingerprint and existing artifact checks, which are not new security machinery. Name/version/upstream release plus existing native ABI/layout check and plain row-comparison test suffice. RCS22 optional later family composition uses native loader and existing exports unless a real missing feature is demonstrated.
