# Source/patch identity hardening: transactional apply_all + patch semantics epoch (L1.1/L1.2)

## Description

Review found apply_all() (tools/bigcherry/patch/apply.py) simulates all edits in memory first, then replays sequentially against disk -- the second pass is not guaranteed atomic, so a mid-run failure (e.g. a later patch's simulated match no longer holds once earlier writes changed on-disk state some other way, or a real I/O failure) can leave the tree partially patched with no rollback, poisoning that content-addressed cache directory. Verified real by reading apply_all(): two-pass design confirmed (in-memory simulate pass proves ordering validity, second real-write pass touches disk with no temp-file/rollback mechanism). Separately, patch identity today hashes only patch.py implementation bytes (see registry/patchset digest logic) -- it does NOT capture apply.py/core/csource.py's own patch-application semantics (anchor matching, noise stripping, guard handling, replace_all, applies_if, span limits, newline/encoding behavior), so a semantics change in those shared modules can silently change output bytes while every patch's own digest is unchanged.

## Steps

1.1 Transactional apply_all: prefer writing to temp files and rolling back all originals on any failure (simplest fit for the current file-list architecture), OR materialize into a temp worktree and promote atomically -- pick whichever fits workspace.materialize()'s existing directory model with least disruption.
1.2 Add PATTERN_APPLICATION_SEMANTICS_VERSION (or similarly named) constant to patch/apply.py or core/csource.py; thread it into every materialization plan identity that applies patches (source.py's _make_source_identity_v2 and campaign/source.py's resolve_materialization_identity, wherever patch bytes currently enter identity); bump only when apply.py/csource.py's actual output-affecting behavior changes, never for docstring/comment-only edits.
