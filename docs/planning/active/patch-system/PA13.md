# Source/patch identity hardening: unify canonical-campaign and HI82 source authority (Layer 7)

## Description

Review's central architectural recommendation: canonical campaign (campaign/source.py, campaign/build.py) and HI82 (patch/source.py) currently duplicate source-authority logic with different gaps in each (comparison table: canonical checks ignored-files and has output-derived source ID but no live-HEAD/object-format reuse check or compile-time re-attestation; HI82 checks live HEAD but not ignored-files, has atomic writes but no output-derived source ID). Review recommends extracting one shared tools/bigcherry/source/materialization.py owning ResolvedPatchInput, ResolvedOverlayInput, MaterializationPlan, SourceAttestation dataclasses and resolve_materialization_plan/materialization_plan_id/materialize/attest_source/verify_source/remove_materialization operations, with both campaign and patch/source.py consuming it instead of each carrying separate tree/manifest authorities.

## Steps

This is explicitly a LATER, larger consolidation -- do not start until PA06-PA12 have landed individually and their real call-site shapes are well understood. At that point: 1. Design the shared materialization.py module's exact API against the now-hardened individual implementations (not from scratch). 2. Migrate canonical campaign to consume it. 3. Migrate HI82/patch source.py to consume it. 4. Remove the now-duplicate logic from both original locations.

## Detailed Solution & Technical Design

Investigation (forked agent, 2026-08-27, grounded in real current source of tools/bigcherry/patch/source.py, tools/bigcherry/campaign/source.py, tools/bigcherry/campaign/build.py, tools/bigcherry/source/workspace.py, tools/bigcherry/source/identity.py) found PA13's original description is STALE -- most of the specific gaps it names were already closed by PA06-PA12. The real remaining problem is different and narrower than originally scoped:

**source/identity.py is ALREADY the shared Layer-7 primitive** for the pure-identity operations (git_tree_oid, verify_source_attestation, atomic_write_json with read_only, plan_lock, source_slice_id) -- both campaign and patch/source.py already import and use these directly. PA06-PA12 did that half of the unification already.

**What's still duplicated is the plan->identity->materialize->verify ORCHESTRATION**, and a full read of both files (not just their comparison table) shows the two orchestrations differ in more than just 'gaps' -- they are genuinely different designs:
- Identity payload shape: HI82's v2 schema (resolved_revision + overlay_digest + ordered composition + patch_application_semantics_version, hashed as `source_key`) vs campaign's `resolve_materialization_identity()`/`materialization_plan_id()` (a different dict shape including patch_set_id/classification, different hash function -- blake2b vs HI82's sha256-based _stable_digest).
- Overlay digest algorithm: HI82 sha256-over-sorted-(relpath,sha256)-JSON; campaign blake2b with a versioned personalization string, computed two different ways in two different functions (_overlay_content_hash reading disk directly, _overlay_hash_from_inputs from pre-resolved ResolvedOverlayInput).
- HI82 has SourceTransform/variant materialization (subject-vs-control content-addressed transforms with full callable-fingerprinting via bytecode/globals/closure inspection) -- campaign has no equivalent concept at all.
- HI82 has _verify_by_rematerialization() (PA14): a full re-run of add-worktree+apply-composition+transform into a scratch dir, diffing tree OIDs, as the only check not dependent on trusting previously-written manifest fields. Campaign's materialize_source() re-verifies attestation and re-derives source_slice_id/source_plan_id/materialization_plan_id from the now-verified tree, but does NOT re-materialize from scratch to prove the manifest's OWN claimed composition actually produces that tree.
- HI82 writes its manifest read_only=True; campaign's atomic_write_json call for _source_metadata_path does not pass read_only=True (a real, narrow, easy-to-fix asymmetry).
- Both independently implement _add_worktree-equivalent logic and failure cleanup (HI82's _materialize_v2 vs campaign's materialize()+_materialize_source_locked's BaseException cleanup block) with different but overlapping care about partial-failure state.

**Open question for GPT to help resolve before any implementation**: given how much genuinely differs (not just 'missing checks' but different identity shapes, different variant-transform needs, different failure-cleanup shapes), is a literal shared materialize()/verify_source() function actually the right target -- or would backporting ONLY the two concrete missing safety properties (read_only manifest write for campaign; a re-materialization proof option for campaign) into campaign's EXISTING implementation deliver the real safety benefit with far less risk than unifying the orchestration layer itself? The original PA13 description's 'do not attempt until PA06-PA12 land, needs its own dedicated review pass' guidance was written before this level of detail was known.
