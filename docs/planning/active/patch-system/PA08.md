# Source/patch identity hardening: canonical campaign cache-reuse live HEAD/object-format checks (L2.1/L2.2/L2.3)

## Description

Review found campaign/build.py's materialize_source() re-hashes the tree and re-derives source IDs on cache hit, but never checks `git rev-parse HEAD == expected upstream revision` -- two commits can share a tree OID but differ in commit identity, and tooling embeds the wrong revision even though bytes match. Separately, re-derivation of source_slice_id on reuse uses the persisted git_object_format from cached metadata instead of querying the live worktree (`git rev-parse --show-object-format`) -- a forged metadata record can change both fields consistently and pass. Also: resolve_materialization_identity() (campaign/source.py) hashes patch implementations and overlay bytes once, but workspace.materialize() independently re-walks/re-resolves patches and overlay later -- a patch or overlay file changing between those two steps (TOCTOU) means the cache directory stays keyed from the old identity while consuming new bytes. None of these three have been read/verified against current source yet in this session -- read campaign/build.py::materialize_source() and campaign/source.py::resolve_materialization_identity() before implementing to confirm exact call sites match the review's description.

## Steps

1. In materialize_source()'s reuse path, add live checks: actual HEAD == expected revision, actual tree OID == expected tree OID (already done per review), actual object format == expected object format (querying live Git, never trusting persisted metadata for this).
2. Resolve patch/overlay inputs ONCE into an immutable object (ResolvedPatchInput/ResolvedOverlayInput per review's suggested shape) at plan-resolution time; have workspace.materialize() consume that resolved composition and recheck each byte immediately before use rather than calling resolve_exact() a second time independently.
