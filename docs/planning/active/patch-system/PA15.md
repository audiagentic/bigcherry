# Cross-process build-directory race in campaign/workers.py's build worker (no lock analogous to plan_lock)

## Description

dev-gpt-agent's investigation (2026-08-26) into the highest-value remaining validation work found a genuinely new gap, not caught by either prior adversarial review round: make_build_worker() (tools/bigcherry/campaign/workers.py) uses a shared content-addressed build_dir (build_directory(context, source_slice_id, build_plan)), creates it with build_dir.mkdir(parents=True, exist_ok=True), then independently decides reuse-vs-fresh-compile -- with NO lock analogous to PA12's plan_lock() (source/identity.py), which protects the exactly analogous source-materialization race. Confirmed real by grepping campaign/workers.py: zero references to plan_lock anywhere in the file. Two processes targeting the same (source_slice_id, build_plan_id) can both enter the fresh-build branch; with different generated_compile_inputs_hash values under the same BuildPlan, interleaved CMake configure/build could silently misbind a binary to the wrong compile-input identity.

## Steps

1. Reproduce/characterize the race: two independent processes targeting the same (source_slice_id, build_plan_id), synchronized so both observe no metadata, both entering the fresh-build branch concurrently.
2. Test both identical generated inputs AND (more importantly) different generated_compile_inputs_hash values under the same BuildPlan -- assert they cannot configure/build the same CMake directory concurrently and cannot publish binary metadata claiming compile-input identity A while the binary was actually built after B's configure ran.
3. Fix: wrap the build worker's inspect-cache -> configure -> build -> publish-metadata sequence in a plan_lock() call keyed by (source_slice_id, build_plan_id), matching PA12's pattern exactly -- source materialization already solved this identical class of problem with an OS lock; the build path should reuse the same primitive, not invent a new one.
