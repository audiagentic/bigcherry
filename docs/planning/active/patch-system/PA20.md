# Split patch-set.framework into core-serving/tuning-scaffolding/qualification-observability

## Description

User-directed design question (2026-09-11): "As we are now splitting the tuning side of bc into a separate set of patches/functionality beyond that optimization enhancement patches - should we separate out tune replay patch code into specific patches and a core group so we can isolate our tuning overhead from just base level bc updates?"

Motivated by GP14's finding (BC baseline measured ~5.9% slower than native llama.cpp) -- but real investigation same day found that specific overhead question is ALREADY solved by this project's existing build-option axis (bigcherry-native:stock, dispatch layer compiled out entirely, measured 103.51 t/s, matches native llama.cpp's 102.61 t/s within noise -- see GP14, closed as methodology artifact, not a real problem). So this item is NOT about fixing a measured runtime-overhead bug -- that's resolved. It is about whether config/recipes.toml's [patch-set.framework] (14 patches, unconditionally bundled into every single BC build/source with no way to select a subset) should be structurally split for independent reasons: dependency isolation, smaller production patch surface, cleaner pin-bump/rebase attribution, ability to PROVE a deployment carries no tuner/SQLite/measurement machinery, and independently qualifying "serving correctness" vs "tuning-campaign correctness".

GPT design verdict (dev-gpt-agent, session ses_e54497072d354cbe, req_92858eeca17545c8): RECOMMENDS doing the split. Real quote: "the compelling benefit is not another ~6% performance recovery -- the build flags already solved that. It is establishing a hard architectural boundary where production replay can be built, rebased, audited, and qualified without carrying the machinery used to discover its winners."

## Notes

GPT's classification of the 14 patches (verbatim), by execution dependency (does production replay mode actually need it), NOT by which workflow originally introduced it -- GPT explicitly warns the dangerous failure mode is misclassifying something as tuning-only when replay actually depends on it:

core-serving (needed for ANY BC deployment using tuned/replayed dispatch):
- 0100_cmake_options (SPLIT -- only its generic replay/dispatch build plumbing; NOT the GGML_HIP_AUTOTUNE+SQLite/tuner-linkage half, which moves to tuning-scaffolding)
- 0200_dispatch_hook ("fundamental production replay interception point")
- 0300_mmq_forced_j / 0400_mmvf_forced_block / 0500_mmf_forced_nwarps / 0600_mmvq_geometry / 0650_mmvq_native_variant -- GPT recommends KEEPING these in core-serving, not moving them to tuning: "replay must retain it if promoted winners encode/select [this parameter]"; explicit caution -- "the only reason to move any of them into tuning would be code-level proof that replay winners never use their forced-value path", and given replay applies the promoted winner through the SAME dispatch mechanism, removing this plumbing from serving "is more likely to silently change winner execution than to simplify it." Do NOT reclassify these without that proof first.

tuning-scaffolding (only needed for record/tune/promote campaign, never at production replay time):
- 0100's autotune/SQLite half (the other split piece)
- 0700_coverage_counters ("campaign reach/coverage measurement only")
- 0810_replay_hit_diagnostics ("explicitly unnecessary for production replay; production configuration intentionally compiles it out" -- this patch's OWN stated intent already says this)
- 0820_measurement_signature_shapes ("measurement-record metadata only")
- 0900_pool_workspace_metrics ("candidate/workspace measurement only")

qualification-observability (NEITHER core-serving nor tuning -- its own third bucket):
- 0830_split_reduce_telemetry -- GPT explicit: "Production qualification/observability capability. Do not falsely classify it as tuning." This is the patch GP04/GP05/HI18's real production reduction-byte-histogram evidence came from -- real production telemetry, not a tuning-campaign artifact. Put in its own small qualification-observability patch-set, optionally composed into qualification sources/builds.

Excluded from all three buckets (belong elsewhere, don't contaminate serving/tuning definitions):
- 0800_server_shutdown_endpoint -- "operational/test orchestration"
- 1100_hi70_direct_op_evidence -- "validation/test corpus"

Proposed target structure (3 semantic patch-sets, not 2):
```
core-serving: [0100-replay-half, 0200, 0300, 0400, 0500, 0600, 0650]
tuning-scaffolding: [0100-autotune-half, 0700, 0810, 0820, 0900]
qualification-observability: [0830]
```
Proposed new sources (explicit intent, replacing the current framework/bigcherry-native ambiguity):
```
bigcherry-serving:       core-serving + production enhancement patches
bigcherry-tuning:        core-serving + tuning-scaffolding + required enhancement patches
bigcherry-qualification: core-serving + qualification-observability (+ tuning-scaffolding only for campaigns that need it)
```
GPT explicit: "Do not create a permanent framework compatibility umbrella. That would defeat the project's migrate-up doctrine" -- i.e. no long-lived alias for the old `framework`/`bigcherry-native` names once migrated (matches this project's own CLAUDE.md 'no legacy, always migrate up' rule).

GPT's recommended sequencing (do in this order, each step gated before the next):
1. Establish dependency truth FIRST: a mechanical check/test proving a known promoted replay database/winner set executes identically under the proposed core-serving source -- specifically exercise every 0300-0650 winner dimension. This is the proof gate for whether 0300-0650 truly belong in core-serving as classified above.
2. Split 0100 first (separate generic replay/dispatch CMake definitions from autotune/SQLite dependencies) -- "this is what makes a genuinely tuner-free compile/link graph possible."
3. Add the new patch-sets and sources (bigcherry-serving, bigcherry-tuning, bigcherry-qualification) WITHOUT changing campaign behavior yet.
4. Migrate ALL references atomically in one series: config/recipes.toml's [[trees]], lane/source mappings, validation-campaign profiles, benchmark orchestration, CI, documentation, scripts -- anything matching `framework` or `bigcherry-native`. Campaigns that record candidates move to bigcherry-tuning; production replay moves to bigcherry-serving; GP04/GP05/HI18-style telemetry work moves to bigcherry-qualification.
5. Run equivalence gates BEFORE deleting old names: serving replay correctness, representative performance sanity, tuner campaign smoke test, qualification telemetry test, patch dependency/static validation.
6. Delete patch-set.framework and the superseded source name in the SAME migration series. No long-lived alias or compatibility shim -- per this project's own doctrine.

IMPORTANT CONTEXT: this is explicitly NOT about fixing a performance bug (GP14 already resolved that via existing build options, closed same day). This is a pure architecture/auditability improvement. Given the real risk GPT flags (misclassifying core-serving plumbing as tuning-only could silently change which winner a replay build actually executes) and the explicit 'no compatibility shim, single atomic migration' requirement, this needs deliberate user sign-off before implementation starts -- it is a one-shot, irreversible-in-spirit migration touching build/release infrastructure other concurrent sessions also depend on (config/recipes.toml is shared, actively-edited state).
