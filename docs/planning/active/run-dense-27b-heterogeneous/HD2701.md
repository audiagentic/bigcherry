# Dense 27B on two gfx1100 XTX plus gfx1201 R9700: profile-derived placement, KV ownership and quantization

## Description

Owner 2026-11-09: prepare for Qwen4-27B dense using the already registered Qwen3.8-27B
model as a proxy. Explore whether a heterogeneous 3-GPU setup is beneficial,
including per-layer placement and hybrid (two XTX tensor ranks plus R9700
full-layer stages). Evaluate real link, compute and KV costs rather than
assuming more cards is better. Do not claim Qwen4-specific support or
architecture until weights and model card are released.

The system has two gfx1100 RX 7900 XTX 24GB and one gfx1201 R9700 32GB.
An additional gfx1030 6900 XT 16GB is available as an optional control, not
a forced fourth rank. No GPU peer access assumption. Existing Radiance
qwen27b-2xtx uses TP2, host-memory wht6 reduction and FP8 KV; llama.cpp
tierL-qwen27b-q8 is 29,047,086,048 bytes and already registered for TP2.

## Steps

1. Card-free source, model and topology inventory. Preserve the pinned vendor
   tree; record existing Radiance dense TP2 layout, llama.cpp GGUF lane, known
   heterogeneous RCCL viability/safety and actual per-card ownership of KV,
   recurrent, model weights, allocator and intermediate graph buffers.
2. Card-free contiguous-stage solver, test harness and conservative per-device
   VRAM model. Test three layer stages, two-XTX TP2 control, R9700 control,
   and conceptual TP2-XTX + R9700 hybrid. Include per-architecture measured
   compute, transport and reserve fields; reject missing costs and infeasible
   partitions. Keep synthetic demonstration explicitly separate from evidence.
3. Under exclusive lease, qualified controls: one XTX, the R9700, dual-XTX
   TP2. Compare the SAME model/quant/context; model-size permitting.
   Profile GEMM/GDN/attention, decode M1/2/4/8, MTP verify, pp512/2048/8192,
   context 8K/32K/64K, and 1/4/8 concurrent streams. Reuse KAB01/rad-kbench
   before any kernel edits.
4. Try a short isolated llama.cpp three-card -sm layer canary. Inspect actual
   GPU allocations, physical split ratio and response correctness. Prior
   multi-GPU 27B validation had a non-tensor load crash at a pinned build:
   never assume a layer run will load or that -ts alone balances speed.
   Time per-stage compute, boundary transfers and pipeline fill/drain.
5. Head division and KV checks: TP2 full-attention KV heads are rank-local,
   not one shared cache. Qwen3.8-27B 16 attention layers, 4 KV heads/head
   dimension 256, 32768 context, FP16 -> 2 GiB logical full-attention KV;
   one GiB per rank under even TP2 sharding, plus recurrent GDN state and
   other allocations. Four heads cannot divide evenly over TP3, so test
   support/replication explicitly. Measure allocated bytes by device and
   session, and never infer KV quant support for llama.cpp -sm tensor from
   Radiance's independent FP8 KV backend.
6. Measure dense cross-stage activations separately from RAD50's MoE FP16
   CPU combine result plane. Exercise host relay and CPU push only behind
   isolated producer/consumer ordering and safety gates. Required invariant:
   no staged data consumed before it is fully visible; no reuse before
   ACK; bounded failures and no per-layer blocking CPU-driven orchestration.
7. Hybrid TP2-XTX + R9700 graph design review: split only at whole-layer
   boundaries; TP2 reductions stay within XTX pair; convert replicated or
   sharded activation into full-width R9700 input once per boundary and
   reverse if needed. R9700 owns its own KV/GDN state. Account for
   recomputation, buffers, host synchronization, mixed gfx11/gfx12 kernels,
   long-prefill boundaries and recurrent continuation. This is NOT yet a
   supported -sm tensor + layer configuration.
8. Quantization sweep: same released checkpoint, quality reference Q8_0,
   Q6_K / Q5_K_M / Q4_K_M when available, and Radiance-specific MXFP4/FP8
   separately. Record actual file and allocated size, per-device headroom,
   all-context quality/KL, KV dtype and sustained speed. Q8 single R9700
   may be tight despite a 29.05GB GGUF because KV and runtime need space.
9. At Qwen4-27B release, first confirm official model card, source weights,
   license, tokenizer, architecture/heads, attention vs GDN/recurrent/state,
   supported conversion and exact numerical baseline. Re-run memory,
   shape, kernel and parity checks; Qwen3.8 surrogates are not Qwen4 data.
10. Only after all safety, model and performance gates: optional
    engine-supported heterogeneous stage scheduler behind opt-in, with
    A/B parity and explicit separate review. Do not change production
    defaults as part of this experimental planning branch.

## Detailed Solution & Technical Design

Compare candidate topologies without conflating memory fit with compute speed:

- XTX TP2: one tensor-parallel engine; 2 ranks, local KV/attention heads,
  all-reduce on each supported layer. This is the known control.
- Heterogeneous layer3: three contiguous blocks of complete layers,
  different GPUs. Each layer executes once, with local KV/GDN state.
  Single-request decode is serial across stages; benefits, if any, come
  from format/architecture-specific faster kernels or pipeline concurrency.
- Hybrid TP2 + R9700: stage group {XTX0,XTX1} operating TP2 plus a
  disjoint R9700 TP1 stage. No R9700 participation in TP2 reductions;
  requires explicit graph boundaries and activation ownership transfers.
- TP3 is not a default: mixed-rank collective stragglers and uneven KV
  head divisibility can make it slower, incorrect or unsupported. Keep
  diagnostic only after a separate admission/correctness check.

The offline estimator evaluates contiguous cut combinations with per-stage
execution time, transfer and device-resident weights, KV and state. Optimise
single-request latency separately from multi-session pipeline interval, and
treat the latter only as an optimistic bound. All measured input must carry
evidence_id and use captured costs. Model/quant/copies are not silently
replaced by synthetic inputs. No backend launch is hidden in the solver.

RAD50 is an experimental CPU-BAR proof branch and RAD51 a separately gated
MoE serving-integration design. Neither authorizes a dense inference CPU
orchestration rewrite; any dense handoff must reuse established safe
visibility mechanisms and prove the critical path with its own measurements.

## Validation

- Card-free tests for correct 64-layer expansion, contiguous partition,
  objective-aware cut choices, impossible VRAM allocation, under-accounted
  memory, device overlap, missing profiles/links, synthetic input rejection,
  full-attention KV byte math and TP3 head incompatibility.
- GPU measurement only under exclusive lease, after qualified identical
  quant/model baselines, self-consistent device allocations and exact
  continuation/quality parity. Use real saved test prompts and
  established benchmark evidence recipes rather than invented values.
- A/B controls must preserve workload, quality target and model, log
  p50/p95/p99, VRAM per GPU, copy/collective and compute fractions, and
  throughput with repeat/arm order. Crash, stale read, GPU hang, no
  improvement or missing evidence ends that experimental stage.

## Effort & Risk

Large. Hard risks: unsupported Qwen4 architecture; mixed gfx11/gfx12
kernel coverage, three-rank head shape, heterogeneous RCCL admission,
scheduler and reduction stragglers, PCIe/handoff overhead and CPU wakeup,
incomplete KV/GDN ownership, aggressive quants breaking long-context
quality, and concurrent sessions overrunning VRAM.

## Standards

Experimental branch/worktree, no vendor changes, no production defaults,
no shared branch mutation or unreviewed GPU kernels. Use agent-lease for
all hardware work; only compare like-for-like models/quants. Preserve
machine-independent recipes; keep captured local paths and identities out
of tracked docs. Separate architecture facts from surrogates and estimates.

## Acceptance Criteria

1. Offline estimator + tests with unsafe/missing data rejected and clear
   synthetic/measurement provenance.
2. Measured per-device VRAM breakdown (weights, KV, state and allocator)
   and model head-division compatibility, for TP2 and tested alternatives.
3. Matched end-to-end 27B controls for XTX, R9700 and dual-XTX TP2.
4. Three-layer split canary or explicit hard failure with reason.
5. Isolated critical-path transfer and publication evidence before a
   hybrid serving implementation is considered.
6. Measured quality-qualified quant/placement Pareto comparison across
   context, MTP and concurrency; Qwen4 requires renewed model gate.
7. Any proposed production integration must have separate opt-in
   architecture review and same-session superiority evidence.
