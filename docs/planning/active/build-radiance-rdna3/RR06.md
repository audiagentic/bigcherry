# A reference check for the MXFP4 GEMMs on gfx1100 (kdev oracle)

## Description

radiance's rad-kbench skips every MXFP4 GEMM case for the MXFP4 Qwen3.8-27B container: 'blk.N.ffn_gate_up.weight as fp4_e2m1*e8m0[1x32] does not make the operand b the reference reads: its plane holds 178257920 elements and the reader wants 89128960' (13 shapes, run fx-mxfp4, 2026-10-10). So the kernels that are 88% of decode time have no per-kernel check; the only evidence is unchanged greedy text. Native kernels (RR07, RR08) change summation order and operand formats, so they need a numeric oracle before they replace anything.

## Steps

1. Read rad_kbench.cpp's operand reader for fp4_e2m1*e8m0 and libref's gemm_nt_q to find why the element count is doubled (nibbles counted as elements against a byte plane, or the container's plane carries codes and exponents together). 2. If it is a reader bug that a small local patch fixes, carry it as a radiance source rewrite in the libr3 build tree only if that also fixes rad-kbench; otherwise go to step 3. 3. Build the oracle in the kdev harness (engines/radiance/kernels/kdev): a host reference for gemm_nt_q MXFP4 x fp8 written from the format definition (E2M1 codes, E8M0 exponent per 32 of K, Wref fold, fp8 activations with a per-row or per-(row,128) f32 scale), f32 accumulation, bf16 result. 4. A driver that draws operands with a fixed seed for the 27B's five shapes (N=34816 K=5120, N=5120 K=17408, N=16384 K=5120, N=5120 K=6144, N=12288 K=5120) and M in {1, 2, 4, 8, 16, 64, 128, 512}, runs a named libr3 kernel on the card and compares with the host reference: rel_l2 and max abs error per case, inside guarded allocations. 5. Run it on libr4d on the R9700 first: radiance's own kernel must pass, which validates the oracle. 6. Run the emulated libr3 kernel and the current native form on the XTX.

## Validation

libr4d on gfx1201 passes every case at the tolerance rad-kbench uses for gemm_nt_q (read it from the fixture run: worst rel_l2 for the fp8 GEMMs was 1.7e-04). The emulated and native libr3 kernels on gfx1100 pass the same cases. A deliberately wrong kernel (one nibble table entry changed) fails.

## Effort & Risk

Medium. Risk: reproducing the exact operand layout the kernel expects (weight in fragment-order slots, Wref, Ws) needs the engine's layout hook; if the hook is not callable from a plugin harness, the driver goes through rad-kbench's own -m path with a fixed reader instead.

## Standards

The oracle is written from the format, not copied from the kernel under test. Same seed, same bytes for every kernel compared.
