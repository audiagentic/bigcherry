# Decode on gfx1100 as a vector kernel: MXFP4 GEMV for M <= 4

## Description

At decode radiance's MXFP4 GEMM (r4d_gemm_mxfp4a8_decode, one-fragment form) spends a 16-row WMMA fragment on one token: 15/16 of the matrix compute produces rows nobody asked for. On the R9700 the WMMA is fast enough that the kernel still runs near the memory rate; on the XTX it is compute-bound (332 us for 89 MB of gate/up weight = 268 GB/s of a 960 GB/s card). hipfire's XTX decode uses no matrix instruction (gemv_hfp4g32.gfx1100.hip, gemv_hfq4g256.gfx1100.hip, Apache-2.0): one weight row a 32-thread block, 4-bit codes through a 16-entry table, four interleaved accumulators, no shared-memory staging of weights; it reports about 650 GiB/s on this card. Build that shape for radiance's MXFP4 layout and register it in libr3 ahead of the WMMA kernel for small M.

## Steps

1. Read r4d_gemm_args.h / the registry row of gemm_mxfp4a8_decode for the exact operand and scratch contract and how a second row for the same op is ordered (RAD row priority, max_m hooks). 2. Write the kernel for M = 1, per-row activation scale, unsplit, as a kdev candidate. 3. Check against the RR06 oracle on the five 27B shapes. 4. Time it in kdev against the native WMMA form on the same bytes; sweep waves per block (4, 8), rows per wave (16, 32), accumulators (2, 4), temporal vs non-temporal loads. 5. Add the (row, 128) activation scale grid. 6. Add M = 2..4. 7. Register in libr3 with the M bound; R3_GEMV=OFF builds without it. 8. Serve test: text, decode tok/s median of three, per-op profile. 9. Decide the M crossover from measurements (where the WMMA form becomes faster).

## Detailed Solution & Technical Design

Kernel gemm_mxfp4a8_gemv_gfx11 (libr3-owned source, not a rewrite of a libr4d unit). Operands as r4d_gemm_mxfp4a8_decode takes them: A fp8 [M,K] with f32 scale per row or per (row, 128 of K); W 4-bit codes in fragment-order slots ([N/16][K/16][32 lanes] dwords, lane = (k half << 4) | (n & 15), 8 codes a dword), Ws E8M0 per (32 of K, n), Wref per n; C bf16 [M,N]. Stage once per block into shared memory: the M activation rows widened from fp8 to f32 with the scale applied (M=1: 5120 x 4 B = 20 KiB; K=17408: 68 KiB, so f16 for K > 8192 = 34 KiB, or two passes over K). Each wave owns 16 output rows n (the 16 lanes x 2 halves of one slot group); each lane reads its dword of 8 codes per 16-of-K step straight from global memory with a non-temporal load, decodes through a 16-entry signed E2M1 table held in registers (two v_perm lookups as r4d_mxfp4_unpack8 does, or shifts), multiplies by the block exponent once per 32 of K, and accumulates in f32 with four interleaved partial sums per row. Lane halves hold k 0-7 and k 8-15 of the same row, so the row sum is one cross-lane add at the end (one ds_bpermute per row, not per step). Split-K across workgroups is kept from the upstream plan (mxd_plan) only if the grid is short of blocks; start unsplit. M = 2..4: the same weight stream against M staged rows, M accumulator sets. Selection: libr3's registry offers this row for gemm_nt_q MXFP4 with M <= 4 (tunable R3_GEMV_MAX_M) and the WMMA kernel above it.

## Effort & Risk

Large, advanced. Risks: the fragment-order weight layout was laid out for the WMMA kernel, and a lane's 8 codes are for one row at 8 of 16 k, so reading it as a row stream needs the same slot arithmetic as the upstream loader; shared-memory size for K=17408 at f32; the drafter verify step uses M up to its window (check the actual M distribution with the profile before fixing the crossover). If the memory rate is not reached, the next lever is the weight layout itself (a row-major copy made at load by the layout hook), which is a separate item.
