# gfx1100 follow-ups after the two GEMMs: int8 route, attention, logits, weight layout

## Description

Candidates that only make sense once RR07 and RR08 are in and a new profile shows what is left. Each is taken up only if it is in the top shares of the decode or prefill profile at that point.

## Steps

A. Row-major weight slots for libr3: radiance lays the 4-bit weight out in gfx12 fragment order through a layout hook; a libr3 layout that puts a row's 16 codes in one 8-byte slot removes the second load a step in RR08 and simplifies RR07. Needs the hook to be selectable per kernel library. B. Integer route: quantise activations to int8 in groups of 32 and multiply the 4-bit weights with the gfx11 integer WMMA (iu8 with 4-dword operands, iu4 at K=16), as hipfire's gemm_mq4_packed.gfx1100.hip does; hipfire reports +22% prefill over its f16 route on one fixture. For MXFP4 the weight is a float code with a block exponent, so the integer form needs the E2M1 magnitudes mapped to integers (x2: 0,1,2,3,4,6,8,12) and the exponent applied per 32 of K outside the WMMA, which means one WMMA accumulator per exponent block (K=32) rather than per slab; measure whether that still wins. C. Attention: attn_prefill_h256_gqa6_bf16kv is 6.4x and attn_decode_h256_gqa6_bf16kv 4.2x the R9700 on the MXFP4 fixture; both use bf16 WMMA and the transposed load, so the native form is bf16 fragments read row-wise plus a shared-memory transpose in place of the emulated global_load_tr. D. logits_gemm bf16 (n_vocab 248320 x 5120, 1.6 ms, 2.8% of decode): a GEMV form like RR07 for bf16 weights. E. gdn_chunk_scan (3.1x) and attn_vit (2.9x) native forms if a Flash-Next or vision workload makes them matter.

## Validation

Each candidate: rad-kbench (bf16 kernels are covered by the recorded fixtures) or the RR06 oracle (MXFP4), kdev timing against the kernel it replaces on the same bytes, then serve medians. A candidate that does not move the serve median is not registered.

## Effort & Risk

Each is medium to large. B has a real chance of not paying for MXFP4 because of the per-32 exponent. C depends on how much of the attention kernel's cost is the emulated transposed load, which the profile will show.
