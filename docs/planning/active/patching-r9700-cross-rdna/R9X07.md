# R9X07 — AllReduce WHT/compressed-wire extraction into the existing provider stack

Status: planned
Proposed patch: `1308_r9x_allreduce_wht`
Depends on: R9X01 and current collective benchmarks
External source: `kernels/r9k_ar.hip`, `kernels/r9k_ar_wht.hip`, `kernels/r9k_ar4.hip`, `r9700_vllm/comm/r4d_ar.py`
Existing BigCherry owners: 1001, 1244, 1250, 1252, 1272, 1275, 1276, 1277, 1290, 1291

## Goal

Extract any useful WHT/low-bit/one-shot collective ideas from r9700-stack into BigCherry's existing HIP AllReduce provider framework. Do **not** add another parallel provider unless the current provider interface cannot express the protocol.

## Exact BigCherry mapping

`patches/1291_ar_cpu_root/patch.py` targets `ggml/src/ggml-cuda/ggml-cuda.cu`, `common/arg.cpp`, and `tools/llama-bench/llama-bench.cpp`. The current collective family already includes internal, n-way/root, q8/compressed wire, P2P, adaptive, tracing and CPU-root work (`1001`, `1244`, `1250`, `1252`, `1272`, `1275`, `1276`, `1277`, `1291`). Start from those implementations and `tools/lab/rccl/` measurements.

Current production fact to preserve in the plan: small decode reductions can favor CPU-root when RCCL/SHM has high fixed latency, while large host round trips lose to RCCL. Therefore WHT/compression is interesting only if encode+transport+decode beats the existing size-based choices.

## Implementation

1. Characterize r9k AR variants: rank count, peer-access assumptions, synchronization primitive, message-size window, error introduced by transform/quantization, and whether WHT helps compression or transport topology.
2. Map its transport onto existing BigCherry `try_allreduce`/adaptive dispatch. Reuse provider state and trace/census infrastructure.
3. Build a lab microbenchmark first under `tools/lab/rccl/` (or current collective lab location) for 2/3/4 ranks and 10 KB, 40 KB, 120 KB, 640 KB, 3.3 MB, 6.5 MB, 10 MB. Compare RCCL, current internal/adaptive/cpu-root, and candidate.
4. Only then create `1308`; keep exact f32 path available and make lossy wire explicitly opt-in until model-level quality is established.
5. Adaptive selector should choose the measured winner by rank count/message class/topology; no universal threshold copied from r9700-stack.

## RDNA adaptation

Collective algorithms are mostly `common`; arch-specific work is the transform/pack kernel and system-scope synchronization support. RDNA4/RDNA3/RDNA2 each need verified atomics/memory-scope behavior and tuned pack kernels. P2P assumptions must be topology capability checks, not architecture checks. Brutus-style no-working-P2P configurations are first-class.

## Validation

Exact protocol: bitwise/deterministic comparison where promised, uncomputed meta-rank contributes zero exactly as 1291/RCCL semantics require, graph capture/replay, repeated epochs/wraparound, mixed rank ownership. Lossy protocol: tensor error distribution plus greedy/output parity and quality suite before any default use. Performance: stream-ordered latency, host/GPU utilization, E2E prefill/decode/MTP.

Acceptance: 1308 must occupy a size/topology region where it beats every current provider and must fall through elsewhere. If r9k's gain relies on P2P unavailable on target systems or loses after transform overhead, close as rejected with benchmark evidence.
