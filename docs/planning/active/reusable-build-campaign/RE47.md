Fix: use the DFS post-order directly (or numeric order only as a tie-breaker among nodes with no remaining unresolved dependency), with a test using a deliberately-scrambled numeric-order dependency chain (a lower-numbered patch REQUIRES a higher-numbered one) proving the old behavior was wrong and the new behavior is right.
[NOT STARTED] patch_catalog.py's CatalogSnapshot.metadata field is a plain (mutable) dict on a frozen dataclass, and build_snapshot()'s digest only hashes sorted metadata.keys() -- never the CatalogEntry values -- so an entry's kind/backend/etc field can change with no snapshot digest change. Fix: make metadata a genuinely immutable mapping and hash canonically-serialized CatalogEntry values, not just keys; add a regression test proving an existing entry's VALUE change (e.g. a kind edit with no key added/removed) now changes the digest. Also confirm build_snapshot() should call the existing (separate) cross_check() function to validate 1:1 module/metadata coverage.
