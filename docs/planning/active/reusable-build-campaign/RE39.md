# Introduce CatalogSnapshot: one immutable patch-catalog read per command/campaign

## Description

External patch-management review, P1: patch resolution currently repeatedly scans, parses, and hashes the patches/ tree across a single command/campaign run -- not expensive at today's ~34-file scale, but unnecessary, and creates multiple reads of what should conceptually be one immutable catalogue. Not a resolver correctness bug (unlike RE30's own resolve_lane() bugs, fixed separately this session) -- this is a structural cleanup that also becomes a real prerequisite for safely doing anything recursive/nested with patches/ later (RE38's kind-based folder split).

## Steps

Introduce a CatalogSnapshot dataclass: root, modules (the discovered PatchModule list), by_id (dict), digest (a stable hash of the whole catalogue's content). Build it once at command/campaign start; thread it through resolve_lane/resolve_patch_set, materialize_source, build planning, and reporting instead of each of those independently calling patchset.catalog()/discover_modules(). Benefits: one source of truth per run, fewer filesystem scans, no mid-run catalogue drift (a patch file edited mid-run can't produce inconsistent results between two separate scans), simpler tests (construct one fixture, pass it everywhere), faster as patch count grows.
