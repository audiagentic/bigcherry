# Supersede RE30's backend-first folder decision with kind-based patches/framework|fixes|experiments split

## Description

RE30's own notes recorded an earlier 'Folder decision' (2026-08-20): adopt a backend-first physical split (patches/common/, patches/hip/, patches/vulkan/, patches/upstream/) once the first Vulkan patch lands, and explicitly reject lifecycle folders such as framework/, enhancement/, or experiment/, reasoning that 'those classifications change on promotion and must remain metadata tags'. An external patch-management review document proposes the opposite axis: patches/framework/, patches/fixes/, patches/experiments/, patches/_shared/ (a kind/purpose-based split), with a real argument against backend-first splitting (many real changes are backend-neutral or cross-cutting -- prompt-cache fixes, graph changes, model-load representation).

This item resolves that conflict in favour of the kind-based split, reconciling with (not contradicting) the deeper principle both documents actually share: physical folders should be coarse, exactly one axis, with metadata carrying everything else. Two concrete facts settle which axis wins today: (1) tools/bigcherry/patch_catalog.py + patches/catalog.toml (built earlier this same session, RE30 phase 1) ALREADY implements a `kind` field (framework | upstream-backport | enhancement) populated for all ~34 current patches -- this is real, existing, populated metadata, whereas `backend` is populated but currently uniform (every patch today is backend=hip; zero Vulkan patches exist yet, since RE30 Phase 3's real dispatch-hook work hasn't started). A folder axis with zero variance today (backend) is objectively less useful for browsing than one with four real, populated categories (kind). (2) The old decision's stated objection -- 'those classifications change on promotion' -- does not actually apply to the new document's specific definition: the new document explicitly keeps STATE (validated/untested/rejected, i.e. approval/promotion status) as separate metadata from the four-bucket CLASS, which is about PURPOSE (why does this patch exist), not approval. A promoted, validated experiment is still, by purpose, an experiment -- it does not need to move folders when its state changes from untested to validated. The old decision conflated 'lifecycle' (state) with 'purpose' (kind); they are different axes, and only kind is being proposed as the folder key.

## Steps

When that item is picked up, use: patches/framework/, patches/fixes/, patches/experiments/, patches/_shared/ (non-patch helper code, excluded from discovery). A backend sub-split (experiments/hip/, experiments/vulkan/) should be deferred until real Vulkan patches actually exist -- do not pre-create an empty experiments/vulkan/ directory speculatively.
