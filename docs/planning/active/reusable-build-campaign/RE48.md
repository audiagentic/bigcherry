# Pin-consistency guard: one command that detects vendor-checkout / pin / release-record / cross-tree desync, plus the canonical pin-bump procedure

## Description

On 2026-08-21 the project simultaneously carried three upstream revisions across its working surfaces with no tool detecting it:

| surface | value |
| --- | --- |
| config/recipes.toml | pinned = b10502 (0adcc3bb) |
| H: vendor/llama.cpp checkout | 4801e3c = b10362, patches applied |
| J:/Brutus vendor checkout | 0adcc3bb = b10502, stage generated |
| J:/Brutus bigcherry code rev | 5020c68 (4 commits behind H: 202a0c1) |
| S1 kernel-fraction traces | 22dc605 = b10257 |
| releases/ records | b10502 audited, b10362 patched, b10257 patched |

Both recent incidents share this root cause: the S1 stale-trace incident (kernel-fraction evidence captured on the wrong pin) and the J: tooling gap (the 27B campaign ran on pre-HI67-slice-3 promotion tooling, forcing a workarounded S6). The existing machinery is per-surface: `bigcherry repin` moves the pin, `bigcherry pull` moves the checkout, `releases.py` tracks evidence records with `validate_index_consistency()` (index vs source records only), and campaign machinery binds its own descriptor to `upstream_revision`. Nothing reads all surfaces together, so a forgotten bump is indistinguishable from a legitimate mid-rebase state. `doctor` prints `pinned=b10502` but never compares it to the actual vendor HEAD.

## Steps

- 1. Implement tools/bigcherry/pin_status.py with build_pin_status() (pure, testable surface reader) and a verdict engine: consistent / mid-rebase / drift (+ per-surface unavailable/unreachable markers that never fake a verdict)
- 2. Register bigcherry pin-status CLI subcommand (--strict, --json, --remote NAME for remote trees)
- 3. Add remote-tree support: a new optional [trees] section in config v2 (alias, remote path, label); read via git ls-remote + one SSH probe; unreachable = reported, not failed
- 4. Wire the pin-status section into doctor output (informational; doctor does not gain a new exit code)
- 5. Write docs/reference/PIN_BUMP.md: the canonical bump procedure + the full revision-bound invalidation surface + the completion rule
- 6. Tests: tools/tests/test_pin_status.py covering the five local verdict scenarios + strict/JSON modes + remote (file:// and unreachable)
- 7. Run pin-status against the real tree, record its 2026-08-21 output (expected: mid-rebase, H: vendor b10362 vs pin b10502) in the release notes; commit the tooling before the rebase completes so the guard exists when the bump finishes

## Detailed Solution & Technical Design

### The invariant

One project state may legitimately span two revisions (a bump in flight: pin already at the new tag, checkout not yet pulled, or checkout pulled but not yet audited). What must never be possible is a state where NO surface agrees and nothing is named as in-flight. The tool's job is to NAME the state and fail closed when it is unnamed.

### Surfaces read (all local, read-only, no writes — this command must never mutate)

| # | surface | source | field(s) |
| --- | --- | --- | --- |
| 1 | pin | config/recipes.toml + upstream resolve | pinned ref, resolved SHA |
| 2 | vendor checkout | vendor/llama.cpp git | HEAD SHA, tag of HEAD (if any), dirty counts (modified/untracked) |
| 3 | release records | releases/index.json + releases/*.json | per-revision slug/revision/stage/manifest_hash |
| 4 | campaign artifacts | artifacts/<rev>/*build-descriptor*.json | upstream_revision per descriptor (informational; multiple revisions may coexist legitimately) |
| 5 | bigcherry code rev | project git | HEAD SHA (informational) |
| 6 | remote trees | config [trees] + SSH/ls-remote | same 1-5 subset for the named tree |

### Verdict engine

Core comparison: vendor HEAD SHA vs pinned SHA (both fully resolved; `pull`/`repin` already have upstream.resolve_ref for the pin side).

- **consistent** — vendor HEAD == pinned SHA. (Dirty tracked files are EXPECTED after patch application: reported as counts, never a verdict input. Untracked files are reported, not failed.)
- **mid-rebase** — vendor HEAD != pinned SHA AND a release record exists for the vendor revision (i.e. the old revision is a known, audited stop — the checkout is sitting at a legitimate previous pin, the move is in flight). The record's stage is shown; a mid-rebase from a `broken`-stage record is escalated to drift.
- **drift** — vendor HEAD != pinned SHA AND no release record for the vendor revision (the checkout is at an unknown revision: forgotten bump, manual checkout, corrupted state). This is the failure the tool exists to catch.
- **unavailable** — vendor checkout missing or not a git repo. Reported per surface; the overall verdict is `unavailable`, and `--strict` fails it (a missing checkout is never a pass).

Campaign descriptors (surface 4) are advisory: they list which revisions have build evidence on disk. A descriptor at the pinned SHA is a positive signal; older descriptors are normal (the artifacts/ layout is per-revision by design) and are never drift. One exception: a descriptor at the pinned SHA whose `stage` field is missing its downstream siblings that releases/ claims are done (e.g. release record says `tuned` but no tune descriptor exists) is reported as an `evidence-gap` warning, not a verdict change — the evidence stores are separate systems and reconciliation is a human call.

Remote trees (surface 6) each get their own local-style verdict computed from the probe (git ls-remote for the vendor HEAD is not possible over SSH without a shell — the probe runs one remote command that returns vendor HEAD, pinned ref, and bigcherry HEAD as three lines). Unreachable = `unreachable` marker, never a verdict failure, and never a `--strict` failure (network outages must not block a pipeline gate).

### Why the verdict is keyed on release records, not history

`git` history in the vendor checkout can tell you whether the vendor HEAD is an ANCESTOR of the pin, but ancestry is the wrong test: a rebase from b10362 to a pin that rewrote no shared history is still a bump, and a vendor checkout at a commit between two release tags is drift even though it is "in the range". A release record is the project's own declaration that a revision was pulled, audited, and named — exactly the declaration whose absence is the failure mode. It also makes the tool testable without a real upstream clone: a fake record is a JSON file.

### CLI shape

    bigcherry pin-status [--strict] [--json] [--remote NAME] [--all-remotes]

Human output (one block per tree, local first):

    pin-status: H: (local)
      pin           b10502 -> 0adcc3bb5710 (resolved)
      vendor HEAD   4801e3c567d5 (tag b10362)  [11 modified, 0 untracked]
      releases      b10502 audited | b10362 patched | b10257 patched
      descriptors   0adcc3bb5710 (generated)  4801e3c567d5 (generated)
      bigcherry     202a0c1
      VERDICT       mid-rebase (vendor at prior pin b10362, record stage patched)

    pin-status: brutus (remote)
      vendor HEAD   0adcc3bb5710   pin b10502   bigcherry 5020c68 (3 behind local)
      VERDICT       consistent

Exit codes: 0 = consistent or mid-rebase (mid-rebase is legitimate); 1 = drift or unavailable (or either of those under --strict applied to remote verdicts); 2 = config error. `--strict` semantics: the default gate mode treats mid-rebase as a PASS with a loud printed warning (a pipeline may legitimately start mid-bump once the new pin is pulled — but in practice the pipeline runs FROM a specific tree, so the gate that matters is the tree's own verdict); --strict additionally fails mid-rebase (for use by the bump-completion rule, not by pipelines).

### doctor integration

`doctor.build_report()` gains a `pin_status` section (the full report dict, rendered as one status line per tree). Doctor's exit code is UNCHANGED — doctor stays an information tool; the gate is `pin-status --strict`.

### config [trees] (config v2, additive)

    [trees]
    [[trees.remote]]
    name = "brutus"
    alias = "brutus"            # ssh alias, as in ~/.ssh/config
    path = "/mnt/vault/development/llmhosts/bigcherry"

Optional; absent means local-only. Config v2 loader gets the section (default empty list); unknown fields rejected (config v2 is strict by convention).

### Remote probe protocol (one SSH command, no repo sync implied)

    ssh <alias> 'cd <path> && echo VENDOR $(git -C vendor/llama.cpp rev-parse HEAD 2>/dev/null || echo none) && echo PIN $(sed -n "s/^pinned = \"\(.*\)\"/\1/p" config/recipes.toml 2>/dev/null || echo none) && echo HEAD $(git rev-parse HEAD 2>/dev/null || echo none)'

10s timeout, parsed line-by-line; any parse failure → unreachable. The remote verdict compares remote vendor HEAD vs remote pinned ref (resolved locally against OUR upstream clone — the remote has no network obligation), so the remote report is only as fresh as the local pin resolution; this is stated in the output, not hidden.

### docs/reference/PIN_BUMP.md (the procedure the guard enforces)

The bump procedure, ordered, with the completion rule last:

1. `bigcherry repin <tag>` — moves ONLY the pin (existing semantics: one-line regex rewrite of recipes.toml). Commit immediately: a committed pin move is the declaration that a bump is in flight — this is what turns the next state into mid-rebase instead of drift.
2. `bigcherry pull --recipe bigcherry` — moves the checkout to the pin.
3. Re-verify patches: run the rebase review (A-list style, per docs/reference/PIN_REBASE_REVIEW_B10502.md as the template), fix superseded/failed patches, `bigcherry audit` (advances the release record pulled→audited).
4. `pin-status` — must show mid-rebase→consistent as surfaces complete; record evidence gaps.
5. Rebuild campaign surfaces on the new tree (descriptor regeneration, build dirs), then `pin-status` again.
6. Invalidate revision-bound artifacts — the explicit list, maintained here: kernel-fraction traces (pin-specific kernel names: S1b proved the mmvq small_k name changes between pins with zero behaviour change — a name-keyed comparison across pins is meaningless), tune measurements + journals (per-pin, per-build-identity), replay caches + dispatch DBs (v4 rerun_required across pins is the designed path), inventory DBs, campaign descriptors, build directories, any committed evidence bundle that names a source_revision (its README must state which pin it belongs to — the h36-campaign bundle is the template).
7. Completion rule: the bump is DONE only when `pin-status --strict` reports `consistent` for every reachable tree AND the invalidation list has been walked. Record the pin-status output (verbatim) in the release record notes. Tag `supports/<release>` only after.

Step ordering is load-bearing: the pin move is committed BEFORE the checkout moves, which is precisely what makes the intermediate state nameable as mid-rebase by the verdict engine. A manual `git -C vendor/llama.cpp checkout <sha>` that skips the pin move is what produced the S1 incident class, and it is what the tool now names drift.

## Standards

Read-only tooling: must not mutate any surface (the guard that exists to be trusted must itself be side-effect-free). Config v2 strictness: unknown fields rejected. Verdicts are fail-closed — unavailable/unreachable are named states, never downgraded to pass, except where explicitly designed (remote unreachable never fails --strict; local unavailable always does).
