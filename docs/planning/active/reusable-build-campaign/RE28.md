# Promotion rejects confirmation evidence: %.3f serialization collapses distinct paired-round timings into a spurious tie

## Description

First real-hardware run to ever reach RE15 stage E (promotion) -- possible only after RE27 restored the replay v2 resolution classification -- hit a new, previously-undiscovered producer/validator inconsistency: `tune_promotion.PromotionError: confirmation rounds do not match paired samples`.

## Detailed Solution & Technical Design

Root cause (confirmed via direct inspection of runs/da2a0e6059d0/tune-direct-op/measurements.jsonl, index 11, dispatch 17278fd307bd0e0f184b100d892ee7c0): the C++ tuner (hip-autotune-tuner.cu) computes confirmation_wins/confirmation_rounds via its paired sign test at full double precision (~line 2686-2688), correctly treating round 58's native/winner timings as distinct (no tie) and declaring rounds=100. But samples_json() (line 1289, `snprintf(buf, sizeof(buf), "%.3f", v[i])`) serializes confirmation_native_us/confirmation_winner_us to only 3 decimal microseconds. Round 58's two distinct full-precision values both round to the displayed 61.520, so tune_promotion.py's `_paired_rounds()` (tools/bigcherry/tune_promotion.py:217-258), which deliberately recomputes wins/rounds from the *persisted* (rounded) arrays as an offline audit, sees an exact tie (a!=b test fails) and excludes it -- computing 99 finite pairs against a declared 100, raising PromotionError.

This is a genuine producer/validator precision mismatch, not a data-corruption bug: the tuner's own accounting is correct, but the artifact it persists does not carry enough precision for an offline reader to reproduce that accounting exactly. Two candidate fixes:
1. Increase samples_json() precision (e.g. %.6f) so serialized values essentially never collide -- more artifact bytes, no behavior change to the tuner itself.
2. Give tune_promotion.py's tie test a tolerance matching the serialization granularity (e.g. treat |a-b| < 0.001 as a tie) instead of exact equality, and require the C++ side use the same tolerance in its own sign test for consistency.
Probably (1) is the smaller, more defensible fix -- it makes the artifact self-consistent rather than teaching two independent implementations the same magic tolerance.
