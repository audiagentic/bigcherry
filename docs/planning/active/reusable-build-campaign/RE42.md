# Split resolver into resolve_exact() (fail-closed, explicit) and expand_composition() (dependency-closure expansion)

## Description

config/recipes.toml currently duplicates dependency chains by hand -- e.g. [experiment.rd43-only] repeats [experiment.rd39-42-only]'s single patch plus its own, and [experiment.rd44-only] repeats BOTH prior experiments' patches plus its own (three separate manually-maintained lists that must stay in sync as new RD items are added). An external patch-management review recommends this become metadata-driven: a caller should be able to request just 'RD44' and have the real dependency chain (1215, 1216, 1217) expand automatically from patch metadata (see the sibling item extending patch_catalog.py with REQUIRES).

## Steps

Keep the existing resolve_exact()-shaped low-level resolver exactly as-is in spirit: every dependency must be explicit in the ids it's given, fail closed on anything missing -- this is the safety property to preserve, not replace. Add a new expand_composition() layer above it: given a requested experiment/patch id, walk REQUIRES metadata to compute the full dependency closure, SHOW that expansion to the caller (CLI output, report, whatever consumes it) so no patch is ever silently added without being visible, then hand the complete expanded set to resolve_exact() unchanged. Once this lands, config/recipes.toml's [experiment.*] entries can shrink to naming just the terminal patch, with prerequisites resolved from metadata instead of hand-copied lists -- but do NOT do that recipes.toml simplification in the same change as introducing expand_composition() itself; land the resolver capability first, prove it against the existing hand-written chains (expansion must produce byte-identical results to today's manual lists), then simplify recipes.toml as a clearly separate, easy-to-revert follow-up.
