## Detailed Solution & Technical Design

**Decision.** Patchable Vulkan builds are feasible immediately: source materialisation, patch application, source-slice identity, build publication and runtime-bundle publication are backend-neutral. Full HIP-style dispatch parity is feasible but must be a parallel Vulkan-native implementation. HIP types, C++ launch paths, manifest format and replay reader must remain HIP-only. CONFIRMED by real implementation: the backend-adapter split (campaign_build.cmake_configure_args(backend=...)) and the stock lane both work exactly as designed.

**Pinned upstream seam.** `ggml_vk_mul_mat_q_f16` owns the full quantisation/dequantisation/matmul/split-K recipe and derives tensors, layouts, precision, temporary buffers and split-K. `ggml_vk_guess_matmul_pipeline` returns existing small/medium/large/aligned `vk_pipeline` objects. `ggml_vk_dispatch_pipeline` binds a pipeline, descriptor set and push constants to a command buffer and calls `dispatch`. GLSL is compiled to SPIR-V through `vulkan-shaders-gen`, and `ggml_vk_create_pipeline` creates pipelines with specialization constants and resource/feature checks. The existing `GGML_VK_PERF_LOGGER` query-pool timestamps prove GPU timing is available, but its graph-wide logging/synchronisation must not be reused as the tuner verbatim. A candidate must therefore be a complete executable **pipeline recipe** -- preparation, main pipeline and optional reduction -- not just the final dispatch. This seam has NOT been re-verified against the b10502 pin's exact current line numbers/symbols since the original b10362-era investigation -- re-verify before writing real dispatch-hook code (steps 3+).

**Native architecture.** Add a `src/ggml/src/ggml-vulkan/bigcherry/vk-autotune-*` subtree, guarded by `GGML_VULKAN_AUTOTUNE` / `GGML_VULKAN_DISPATCH_REPLAY`: versioned Vulkan signature/hardware/digest types (DONE -- vk-autotune-types.h/vk-autotune-replay.h exist, provisional); generated registry/manifest/build hash; record; resolver; tuner; replay; coverage and attempt journal (all NOT STARTED). The narrow hook belongs immediately before the stock MUL_MAT/MUL_MAT_ID recipe choice, never in generic `ggml_vk_dispatch_pipeline`. A declined or replay-miss binding falls through to unmodified upstream native selection. The first vertical slice contains native plus explicitly requested existing small/medium/large/aligned matmul recipe variants; new GLSL kernels come later. Each candidate preflights feature bits, storage/workgroup/shared-memory limits, alignment/layout, types/precision and full-recipe availability -- this preflight is exactly what RE32's capability-ABI gap blocks today (ggml_vk_hardware_key_v1 deliberately omits the extensions/limits data can_execute() would need).

**Identity and persistence.** Hardware identity needs backend=`vulkan`, vendor/device ID plus stable device class/UUID, driver and Vulkan API version, subgroup properties, applicable extensions/features and limits, and glslc/SPIR-V/source fingerprint. The signature needs operation, all dimensions/strides/types, output/accumulation precision, layout/alignment, batching, conversion/quantisation path, split-K and fusion/graph conditions. DONE: chose parallel `vk_*` SQLite tables (not a backend-discriminator column) to keep every existing HIP table/CHECK/reader untouched -- schema bumped 4->5 with a real, tested in-place migration preserving existing data. Vulkan replay uses a distinct magic ('BCVK', byte-order-corrected after a GPT review catch) and version from HIP's.

**Campaign, patches and audit.** `campaign_build.cmake_configure_args` currently always emitted `AMDGPU_TARGETS` and HIP generated-inventory options for every backend -- DONE: split into backend-aware adapters, HIP path byte-identical (regression-tested), Vulkan adapter supplies `GGML_VULKAN=ON`. Separate Vulkan source/build/platform triplets exist (`vulkan-stock`/`vulkan-stock`/`vulkan-linux`) but only the stock lane is real; record/tune/replay lanes don't exist yet. Vulkan SDK/glslc/SPIRV-Headers identity capture -- NOT done (RE33). A shader patch covering `vulkan-shaders/*.comp` and host pipeline declaration/creation/selection -- NOT started, zero Vulkan patches exist in the tree yet. The existing strict source audit was correctly refactored into an explicit Vulkan profile (source_audit.vulkan_audit()) that validates CMake/generator seam.

**Rollout/non-goals.** Proceed stock patch validation -> record-only MUL_MAT -> existing-pipeline candidates -> tuning -> replay -> experimental GLSL candidates. Do not port HIP/RD patches, generalize the HIP dispatcher first, alter HIP replay/cache compatibility or claim multi-backend cache reuse. The Vulkan tuner must create pipelines outside timing, warm up, timestamp the full recipe, submit/wait once per timed sample, check all Vulkan/device-lost failures, validate numerical output against native and poison/fallback on a failed measurement. Each driver/device class needs real-hardware evidence; HIP Brutus evidence does not qualify Vulkan.

PR #27952 is the first concrete post-existing-pipeline experimental GLSL candidate for this initiative. Treat the implementation as a complete Vulkan recipe: F32 activation preparation to Q8_1 where required, CM1 main pipeline, and split-K/reduction stages where applicable. CM1 eligibility must be capability-driven, including cooperative-matrix type/shape properties, subgroup and subgroup-size-control, shared-memory limits, integer cooperative support, quant-specific requirements, device/driver/ICD identity, and shader/toolchain digest. Preserve native fallback whenever the candidate is unavailable, rejected, fails pipeline creation, or is not selected. Capture PR #27952 at an immutable head and diff it against the current pin (not the PR base); revalidate the existing Vulkan seams at the current pin before implementation. Do not copy HIP candidate structs, launch abstractions, or replay formats.

Patch retirement boundary: when the pinned vendor contains an equivalent of PR #27952, audit semantic equivalence, retire 1246, retain/rebase 1247, invalidate shader/build identities, and rerun correctness/performance. Keep `can_execute_CM1` separate from `auto_eligible_CM1`: correctness/capability eligibility must not encode RDNA4 performance exclusions. Strict force must return cannot_execute rather than silently selecting native; automatic/replay misses may fall back to native with visible reason.

## Effort & Risk

Overall: XL/high risk for full parity, M/medium risk for a stock patchable lane (the stock lane is now DONE and was genuinely M-effort as predicted).

Primary risks: (1) a candidate represents multiple command-buffer operations, so partial timing creates false winners; (2) pipeline creation and shader compilation must be outside timing and bound to driver/glslc/SPIR-V identity; (3) Vulkan device/driver extensions and limits vary more by ICD than HIP's target strings -- CONFIRMED real by RE32's finding that ggml_vk_hardware_key_v1 as currently scaffolded cannot support real eligibility checks; (4) upstream graph fusion, asynchronous submissions and temporary-buffer reuse complicate isolation/correctness; (5) the existing HIP SQL/cache assumptions would corrupt compatibility if merely relabelled -- AVOIDED by choosing parallel vk_* tables over a discriminator column. Mitigation is a strict one-family vertical slice, backend-specific identity/cache formats, native fallback on every uncertainty, pristine-build tests and real-device evidence before expansion -- this discipline held for the stock lane and should continue.
