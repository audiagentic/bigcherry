# Evaluate adding Vulkan as a tunable build line (patchable, campaign/tune/replay-capable like HIP)

## Description

Deep evaluation completed (2026-08-20). Vulkan can be added as a patchable campaign build line now, but HIP tune/replay parity is a separate, backend-native implementation—not a flag or a port of HIP launch code. Recommendation: approve a staged Vulkan initiative beginning with an independently usable stock/patch-validation lane and a bounded MUL_MAT record/tune/replay vertical slice. Do not add Vulkan by widening HIP types, feature flags, manifests, or replay cache readers.

## Steps

1. Establish a Vulkan stock lane and a separate Vulkan platform/toolchain contract. Build `GGML_VULKAN=ON`, package the executable plus `libggml-vulkan` runtime closure, and run a real GPU smoke before any tuning code is introduced.
2. Make patch/source validation backend-aware: add a Vulkan audit profile and Vulkan-specific patch groups. The current strict audit is deliberately HIP/MMQ/rocBLAS-specific and must not be used to bless a Vulkan overlay.
3. Deliver record-only for one operation family—initially `MUL_MAT` including its preparation/quantize/dequant/split-K recipe. Emit a canonical Vulkan signature, a device/driver/shader hardware key, and the upstream-native selected pipeline. Persist it through a backend-namespaced schema/adapter.
4. Add a small, explicitly generated candidate set for the same family. Candidates describe a complete executable pipeline recipe, not a HIP-shaped kernel launcher. Create pipelines before measurement; reject unsupported extension/device/limits combinations before recording a candidate result.
5. Add the Vulkan tuning transaction: correctness against the native output, warm-up, command-buffer timestamp measurement, synchronisation/failure handling, robust winner selection, and a process-local binding cache. Keep the existing HIP tuner unchanged.
6. Add a Vulkan replay artifact and resolver. It must reject a mismatched Vulkan manifest, signature schema, device/driver/feature/shader fingerprint, or unavailable candidate; a miss falls back to upstream native selection and is observable.
7. Wire Vulkan record/tune/replay lanes into the reusable campaign graph with Vulkan runtime smoke and evidence gates. Only after one complete real-device lifecycle is proven should the lane be eligible for experimental kernel patches or production replay use.

## Detailed Solution & Technical Design

**Decision.** Patchable Vulkan builds are feasible immediately: source materialisation, patch application, source-slice identity, build publication and runtime-bundle publication are backend-neutral. Full HIP-style dispatch parity is feasible but must be a parallel Vulkan-native implementation. HIP types, C++ launch paths, manifest format and replay reader must remain HIP-only.

**Pinned upstream seam.** `ggml_vk_mul_mat_q_f16` owns the full quantisation/dequantisation/matmul/split-K recipe and derives tensors, layouts, precision, temporary buffers and split-K. `ggml_vk_guess_matmul_pipeline` returns existing small/medium/large/aligned `vk_pipeline` objects. `ggml_vk_dispatch_pipeline` binds a pipeline, descriptor set and push constants to a command buffer and calls `dispatch`. GLSL is compiled to SPIR-V through `vulkan-shaders-gen`, and `ggml_vk_create_pipeline` creates pipelines with specialization constants and resource/feature checks. The existing `GGML_VK_PERF_LOGGER` query-pool timestamps prove GPU timing is available, but its graph-wide logging/synchronisation must not be reused as the tuner verbatim. A candidate must therefore be a complete executable **pipeline recipe**—preparation, main pipeline and optional reduction—not just the final dispatch.

**Native architecture.** Add a `src/ggml/src/ggml-vulkan/bigcherry/vk-autotune-*` subtree, guarded by `GGML_VULKAN_AUTOTUNE` / `GGML_VULKAN_DISPATCH_REPLAY`: versioned Vulkan signature/hardware/digest types; generated registry/manifest/build hash; record; resolver; tuner; replay; coverage and attempt journal. The narrow hook belongs immediately before the stock MUL_MAT/MUL_MAT_ID recipe choice, never in generic `ggml_vk_dispatch_pipeline`. A declined or replay-miss binding falls through to unmodified upstream native selection. The first vertical slice contains native plus explicitly requested existing small/medium/large/aligned matmul recipe variants; new GLSL kernels come later. Each candidate preflights feature bits, storage/workgroup/shared-memory limits, alignment/layout, types/precision and full-recipe availability.

**Identity and persistence.** Hardware identity needs backend=`vulkan`, vendor/device ID plus stable device class/UUID, driver and Vulkan API version, subgroup properties, applicable extensions/features and limits, and glslc/SPIR-V/source fingerprint. The signature needs operation, all dimensions/strides/types, output/accumulation precision, layout/alignment, batching, conversion/quantisation path, split-K and fusion/graph conditions. The current SQLite DDL/replay tooling is HIP-named and family-constrained. Preserve HIP wire compatibility; add a backend discriminator plus Vulkan payload through reviewed schema work or parallel Vulkan tables, and give Vulkan replay a distinct magic/version. Replay must bind manifest, schemas, hardware/shader fingerprint and candidate descriptor hash, then fail closed to observable native fallback.

**Campaign, patches and audit.** `campaign_build.cmake_configure_args` currently always emits `AMDGPU_TARGETS` and HIP generated-inventory options. Split it into backend-aware adapters before adding Vulkan: the Vulkan adapter supplies `GGML_VULKAN=ON`, Vulkan SDK/glslc/SPIRV-Headers identity and optional validation/test flags, with no ROCm-target semantics. Add separate Vulkan source/build/platform triplets and stock/record/tune/replay lanes; parameterise bundle/smoke handling for `libggml-vulkan` and selected ICD/device. A shader patch must cover both `vulkan-shaders/*.comp` and host pipeline declaration/creation/selection; add Vulkan framework/experimental patch sets. The existing strict source audit correctly checks HIP/MMQ/rocBLAS contracts, so refactor it to an explicit Vulkan profile that validates CMake/generator seam, shader discovery, matmul/dispatch anchors and declared candidate registration.

**Rollout/non-goals.** Proceed stock patch validation → record-only MUL_MAT → existing-pipeline candidates → tuning → replay → experimental GLSL candidates. Do not port HIP/RD patches, generalize the HIP dispatcher first, alter HIP replay/cache compatibility or claim multi-backend cache reuse. The Vulkan tuner must create pipelines outside timing, warm up, timestamp the full recipe, submit/wait once per timed sample, check all Vulkan/device-lost failures, validate numerical output against native and poison/fallback on a failed measurement. Each driver/device class needs real-hardware evidence; HIP Brutus evidence does not qualify Vulkan.

## Code Samples & Guidance

Proposed configuration shape (names illustrative; exact schema follows the backend-adapter design review):

```toml
[build.vulkan-stock]
options = { GGML_VULKAN = "ON" }
needs = []

[build.vulkan-record]
options = { GGML_VULKAN = "ON", GGML_VULKAN_AUTOTUNE = "ON", GGML_VULKAN_AUTOTUNE_RECORD = "ON" }
variant-set = "vk-inventory"
needs = []

[build.vulkan-tune]
options = { GGML_VULKAN = "ON", GGML_VULKAN_AUTOTUNE = "ON" }
variant-set = "vk-workload-max"
needs = ["vk-inventory"]

[build.vulkan-replay]
options = { GGML_VULKAN = "ON", GGML_VULKAN_DISPATCH_REPLAY = "ON" }
variant-set = "vk-replay"
needs = ["vk-inventory", "vk-promoted-winners"]
```

The native integration must preserve this shape:

```cpp
auto native = ggml_vk_native_mul_mat_recipe(ctx, src0, src1, dst);
auto binding = ggml_vk_dispatch_resolve(ctx, signature, hardware, native);
if (!binding.valid || !ggml_vk_launch_recipe(ctx, subctx, binding, src0, src1, dst)) {
    ggml_vk_launch_recipe(ctx, subctx, native, src0, src1, dst);
}
```

`launch_recipe` is Vulkan-specific. It may bind one or more `vk_pipeline` objects, descriptors, push constants and a split-K reduction; it is not a `__global__` function-pointer wrapper.

## Validation

Validation is staged and hardware-backed:

1. Unit/contract tests: config rejects HIP+Vulkan mixed dispatch configurations; build identity changes with glslc/Vulkan toolchain and shader bytes; Vulkan audit rejects missing host/shader registrations; candidates reject unsupported features/limits; cache/DB readers reject cross-backend or mismatched schema/manifest/fingerprint records.
2. Pristine-overlay test: materialise the pinned vendor revision, apply exactly the Vulkan patch group, run the Vulkan audit, configure and compile shaders + host backend. Verify shader edits change generated compile input identity and build bytes.
3. Stock runtime: enumerate intended Vulkan device/ICD, load the published runtime bundle, and run a known model smoke plus upstream Vulkan backend tests/`GGML_VULKAN_CHECK_RESULTS` where supported.
4. Record proof: one real Vulkan device records parser-clean canonical MUL_MAT observations with native pipeline recipe, complete signature/hardware/shader provenance, and no artifact when record mode is disabled.
5. Tuner proof: on the same fixed driver/device, forced native and every initial candidate pass numerical correctness; warm-up samples are excluded; timestamp/fence failures fail closed; repeated measurements are stable enough for the documented selection rule; a forced bad candidate cannot be promoted.
6. Replay proof: export winners, start a replay-only binary that does not include the tuner/SQLite, demonstrate exact hits choose the stored Vulkan recipe, and demonstrate stale manifest/driver/feature/shader/candidate conditions fall back to native with visible miss classification.
7. Campaign proof: complete a fresh source→record→tune→promotion→replay chain from ArtifactStore-published Vulkan bundles and verify no HIP artifact/cache/winner can enter the Vulkan lane.

## Effort & Risk

Overall: XL/high risk for full parity, M/medium risk for a stock patchable lane.

Primary risks: (1) a candidate represents multiple command-buffer operations, so partial timing creates false winners; (2) pipeline creation and shader compilation must be outside timing and bound to driver/glslc/SPIR-V identity; (3) Vulkan device/driver extensions and limits vary more by ICD than HIP's target strings; (4) upstream graph fusion, asynchronous submissions and temporary-buffer reuse complicate isolation/correctness; (5) the existing HIP SQL/cache assumptions will corrupt compatibility if merely relabelled. Mitigation is a strict one-family vertical slice, backend-specific identity/cache formats, native fallback on every uncertainty, pristine-build tests and real-device evidence before expansion.

## Standards

Apply the existing BigCherry identity, immutable-artifact, source-audit-before-patching, fail-closed replay, native-fallback and real-hardware-validation principles. Create a sibling Vulkan autotune standard before implementation; it must define candidate/recipe identity, command-buffer timing boundaries, feature/fingerprint compatibility, correctness requirements, cache ABI and disabled-mode behaviour. HIP_AUTOTUNE_STANDARDS.md remains authoritative only for HIP and must not be silently broadened to Vulkan.
