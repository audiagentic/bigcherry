## Description

Add explicit DB schema v3 migration and carry source/build/workload/campaign identities through inventory, measurements, promotion, replay, and bundles.

## Steps



## Detailed Solution & Technical Design

SUBSTANTIAL DESIGN (RV48 audit - genuinely unfinished). VERIFIED: schema migration 0003_campaign_identity.sql exists and adds source_slice_id, build_plan_id, effective_build_id, campaign_run_id, workload_id with the stated intent that production writes fill them - but current producers do NOT populate them: inventory.py's two build-row INSERTs still use only the legacy fields (source_revision, source_dirty hardcoded 0, manifest_hash, schema versions, variant_set, descriptor hash), and the measurements loader locates builds primarily by revision/manifest/variant.

REQUIRED: (1) For production-created DB records, source_slice_id, build_plan_id, effective_build_id, workload_id and producer campaign/run identity are REQUIRED where semantically applicable; NULL remains legal only for historical schema-2/imported diagnostic data. (2) Build-row identity based on actual source/build identities, not just source revision + manifest. (3) Observation/measurement/winner rows retain the producer namespace and workload. (4) KEEP PORTABLE REPLAY IDENTITY CLEAN: the replay format intentionally uses portable hardware/signature/objective identity with source/build information as provenance - do not 'fix' campaign identity by contaminating the portable dispatch key; instead exported replay artifacts carry a provenance-bearing descriptor/bundle identifying the campaign/promotion/build that produced the portable cache (ties into RE08's ArtifactDescriptor).
