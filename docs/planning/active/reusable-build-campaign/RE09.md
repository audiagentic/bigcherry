# Migrate dispatch DB and tuning artifacts to campaign identities

## Description

Add explicit DB schema v3 migration and carry source/build/workload/campaign identities through inventory, measurements, promotion, replay, and bundles.

## Steps



## Detailed Solution & Technical Design

GPT-auto-agent full implementation plan (2026-08-17), third priority after RE25/RE10 -- this is schema v4, the real fix for the build-row identity boundary this item's interim fail-closed check (commit 35477db) deliberately deferred. New sql/migrations/0004_build_campaign_identity.sql: rebuild the build table (SQLite can't drop a table-level UNIQUE constraint via ALTER) with a new provenance_class TEXT CHECK IN ('campaign','legacy-imported') column, a partial UNIQUE index build_campaign_identity_uq ON build(source_slice_id,build_plan_id,effective_build_id) WHERE provenance_class='campaign', and the OLD legacy unique combination preserved as build_legacy_identity_uq WHERE provenance_class='legacy-imported' (so historical/imported data keeps its old dedup behavior). Migration backfills provenance_class from whether the four campaign columns are all non-null. CURRENT_DB_SCHEMA_VERSION bumps to '4'.

inventory.py: new CampaignDatabaseIdentity frozen dataclass (source_slice_id,build_plan_id,effective_build_id,campaign_run_id,workload_id) replaces the five loose keyword args on build_database()/load_measurements() -- identity=None means diagnostic/imported (do not upgrade a self-asserted header field into trusted identity). Build lookup becomes two clean branches: WHERE provenance_class='campaign' AND (source_slice_id,build_plan_id,effective_build_id)=? for campaign identity, vs the old legacy-key lookup WHERE provenance_class='legacy-imported' for identity=None -- the current 'reject on any disagreement' workaround goes away because v4 can now correctly represent two distinct real identities under one legacy key instead of colliding.

After RE10 lands: TuneStageResult gains a database_ref -- tune stage copies the inventory-stage SQLite artifact, calls load_measurements(...,identity=...), publishes the result as a NEW immutable dispatch-db ArtifactRef (never mutates an earlier ArtifactStore entry in place).

Tests (test_re09_schema_v4.py, real SQLite): two campaign builds sharing a legacy key but distinct real identity create two build rows (the exact case commit 35477db could only reject, not correctly represent); same campaign triple on a later run reuses one row; campaign and legacy-imported rows coexist under identical old key; migrate a real schema-v3 fixture with FK children and run PRAGMA foreign_key_check; replay cache wire bytes are byte-identical before/after this migration for the same input (campaign DB identity must never leak into the portable dispatch key, per this project's own PORTABLE REPLAY IDENTITY CLEAN standard).

## Notes

RE09 remains in_progress. Follow-up (commit 35477db) closed a residual the second GPT review pass found in the fail-closed build-row-disagreement fix from the prior pass: the check only rejected when BOTH existing and incoming identity were non-NULL and disagreed, missing the migration-era case where an existing row's identity is still NULL (predates campaign identity) and a later campaign-aware load claims it -- two DIFFERENT campaign-aware loads sharing that legacy key could both silently succeed against the same still-NULL row. Fixed: reject whenever incoming is non-NULL and existing != incoming (covers existing=NULL too), per GPT's explicit recommendation; deliberately still does not backfill old NULL rows (would retroactively relabel pre-existing evidence's provenance) and still does not widen the row-identity/UNIQUE-constraint boundary itself (separate schema migration, not attempted). Verified with a new real test reproducing the exact migration-era scenario. Verified on Windows and Brutus; full suite green both places.

Still open: the schema migration for requirement 2 (widening build-row identity itself), and requirement 4 (replay artifact provenance descriptor/bundle, ties to RE25).
