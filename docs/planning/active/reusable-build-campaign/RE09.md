# Migrate dispatch DB and tuning artifacts to campaign identities

## Description

Add explicit DB schema v3 migration and carry source/build/workload/campaign identities through inventory, measurements, promotion, replay, and bundles.

## Steps



## Detailed Solution & Technical Design

SUBSTANTIAL DESIGN (RV48 audit - genuinely unfinished). VERIFIED: schema migration 0003_campaign_identity.sql exists and adds source_slice_id, build_plan_id, effective_build_id, campaign_run_id, workload_id with the stated intent that production writes fill them - but current producers do NOT populate them: inventory.py's two build-row INSERTs still use only the legacy fields (source_revision, source_dirty hardcoded 0, manifest_hash, schema versions, variant_set, descriptor hash), and the measurements loader locates builds primarily by revision/manifest/variant.

REQUIRED: (1) For production-created DB records, source_slice_id, build_plan_id, effective_build_id, workload_id and producer campaign/run identity are REQUIRED where semantically applicable; NULL remains legal only for historical schema-2/imported diagnostic data. (2) Build-row identity based on actual source/build identities, not just source revision + manifest. (3) Observation/measurement/winner rows retain the producer namespace and workload. (4) KEEP PORTABLE REPLAY IDENTITY CLEAN: the replay format intentionally uses portable hardware/signature/objective identity with source/build information as provenance - do not 'fix' campaign identity by contaminating the portable dispatch key; instead exported replay artifacts carry a provenance-bearing descriptor/bundle identifying the campaign/promotion/build that produced the portable cache (ties into RE08's ArtifactDescriptor).

## Notes

RE09 (2026-08-17, commits 947e5b6, 42f7a62): campaign identity is now populated on all four inventory.py write paths -- build_database()'s build/observation rows AND load_measurements()'s build/measurement/winner rows. Both functions accept the same optional (source_slice_id, build_plan_id, effective_build_id, campaign_run_id, workload_id) kwargs, falling back to header.get(...) then NULL. Wired through `inventory record`'s CLI as optional flags. Real DB round-trip tests prove both the populated and NULL-fallback (legacy/imported data) cases across every affected table. Verified on Windows and Brutus; full suite green both places (902 local, 33/33 in test_inventory.py on Linux).

REMAINING, NOT DONE (deliberately, not an oversight): RE09 requirement 2 -- 'build-row identity based on actual source/build identities, not just source revision + manifest' -- is NOT closed. I attempted to widen load_measurements()'s build-row lookup to also match on source_slice_id/build_plan_id, which immediately hit the build table's existing UNIQUE constraint (source_revision, manifest_hash, signature_schema, hardware_schema, variant_set, build_descriptor_hash) -- it does not include the new identity columns, so two campaign runs sharing those five fields but genuinely different source/build identity would either collide (current behavior, unchanged) or the widened lookup would raise IntegrityError against the narrower constraint (what actually happened when I tried it, confirmed by a real test that hit sqlite3.IntegrityError). Reverted that part; the columns are populated but do not yet participate in row identity/dedup. Properly closing this needs a real schema migration extending the UNIQUE index -- a bigger, more careful decision on a live production DB constraint than this pass should make unilaterally. Recommend the next pass on RE09 start here, with real historical-DB migration testing, not just column addition.

Also still open: requirement 4 (provenance-bearing descriptor/bundle for exported replay artifacts, ties to RE25's ArtifactDescriptor work) -- not started.
