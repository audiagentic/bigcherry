# Cut over campaign execution and retire legacy mutable mechanics

## Description

Route normal campaign execution through the new source/build services, prove legacy/new parity, then remove duplicated mutable-checkout assumptions.

## Steps

1. Freeze a parity fixture: one pinned llama.cpp release, exact production patch set, architecture/target, toolchain, inventory/workload, normal campaign shape. Capture legacy path's source state, manifest, descriptor, candidate set, smoke result as reference evidence.
2. Migrate stages behind the new services incrementally (PipelineService/CampaignGraph/CampaignRun/ArtifactStore/BuildPlan/workspace.materialize -- confirmed zero production callers today, only exercised by their own unit tests), but keep normal execution on the legacy path until parity is proven. Each migrated stage must consume explicit identities/artifact refs, not cwd/checkout/prior-stage-build-dir/release-record state.
3. Shadow-run the new path end-to-end against the fixture in a fully separate work root -- must not share checkout, generated directory, CMake build dir, or ArtifactStore namespace with the legacy run.
4. Machine-generated parity comparison (not visual/log diff): source (effective Git tree OID/source-slice ID + exact patch IDs/order/hashes), manifest+descriptor (canonical semantic content, not paths/timestamps), build (BuildPlan ID + effective build ID recompute, expected toolchain, actual binary SHA-256 via validate_reuse() semantics), candidate coverage (exact stable-ID set equality, not just count equality).
5. Runtime parity: at least one real gfx1100 smoke using the artifact resolved from the new descriptor/store (not a manually selected binary path).
6. Negative/fail-closed parity: deliberately tamper each of source/patch-order/inventory-source-slice/published-artifact/descriptor/binary/provenance-namespace/build-dir-reuse/cross-campaign-artifact and confirm every case fails closed before downstream work happens.
7. Flip normal/default execution to the new path with no automatic fallback; legacy path may remain only as an explicit diagnostic/compatibility command.
8. Only then delete legacy mutable-checkout mechanics: tree-state switching (_ensure_tree_state, _reset_tree), the checkout-path-suffixed _build_dir identity, GENERATED_IN_TREE in-checkout generation output, and any tests/CLI code that assume them.

## Detailed Solution & Technical Design

Investigation finding (2026-08-16): every new-service class already exists and is unit-tested but has ZERO production callers anywhere in the repo (checked via grep across tools/bigcherry and docs/scripts) -- PipelineService, CampaignGraph, CampaignRun, ResourceLock, ArtifactStore, BuildPlan, workspace.materialize. 'Normal campaign execution' today is entirely the legacy path in __main__.py's cmd_build, operating on one shared mutable checkout (paths.llama_root()). There is no campaign orchestrator script anywhere; the Brutus campaign-*.sqlite/log artifacts produced this session were built by manually invoking the legacy CLI per build variant (build/bigcherry-tune, build/bigcherry-record, etc).

Root coupling identified (confirmed against source, not assumed): the checkout is used as an implicit inter-stage state bus, not just a mutable git tree. Concretely:
- `_generate_for()`/`GENERATED_IN_TREE` (tools/bigcherry/__main__.py ~L320) writes hip-autotune-registry.inc, manifest, descriptor, mmvq-instances etc DIRECTLY INTO THE SHARED CHECKOUT. A later stage reads these by conventional in-tree path, not by artifact reference -- this is why generate must run immediately before the build that consumes it and why variants must stay sequential (cannot safely share this mutable generated state).
- `_build_dir()` (tools/bigcherry/__main__.py L299) identity is recipe+build name plus a checkout-path hash suffix for non-default roots -- NOT content-addressed by effective source tree + complete build plan. Contrast with the new `builds.build_directory()` = work_root/builds/<source_slice_id>/<build_plan_id>, whose `validate_reuse()` additionally recomputes effective configure record, toolchain identity, and binary SHA-256.
- `_reset_tree()`/`_ensure_tree_state()` flip the ONE shared checkout between recipes rather than materializing an isolated worktree per build (workspace.materialize exists for exactly this and is unused).

Additional integration hazard for the new path itself (not yet built, but must be designed in from the start): PipelineService checks provenance compatibility on ArtifactRef inputs/outputs but does not itself verify ArtifactRef.path bytes match content_hash -- ArtifactStore provides that verification and immutable-publish semantics separately. RE14's executor wiring must make artifact consumption require ArtifactStore-verified bytes, not provenance-field agreement alone. Similarly CampaignRun's reuse hook must validate recorded output hashes/artifacts, not trust StageRecord alone.

Removal criterion (do not delete legacy code before all of this holds): a clean-room pinned campaign through the new path produces source/patch/manifest/descriptor/candidate parity against the legacy reference, a hash-verified real-GPU smoke succeeds, a second execution demonstrates identity-safe reuse/resume from an empty work root, all deliberate mismatch/tamper cases fail closed, and the default campaign path contains no implicit fallback to legacy.

Scope note re: RE15 overlap -- if legacy and new paths both produce the same complete candidate universe (e.g. the same 101 applicable candidates from the RE09 replay-full investigation) and the new binary passes real-GPU smoke, RE14 does not need to wait on RE15's remaining 25-candidate correctness-evidence gap to close -- that gap is acceptance evidence across candidates, whereas RE14 is proving cutover did not alter which candidates exist or how they're identified/built. Only let the missing 25 block RE14 if they reveal an actual difference between the two execution paths.

### Round 6 (2026-08-16): real code review of commit 644c0ee, fixes applied and re-proven on Brutus.

After committing/pushing 644c0ee, asked gpt-auto-agent to review the actual resulting code (not the design in the abstract) -- campaign_execution.py and campaign_workers.py pasted in full. Gateway retrieval failed twice more (same known bug), succeeded on a third attempt within the same session (per updated working practice: reuse the session, retry retrieval rather than resubmitting fresh). The review found real, verified bugs:

1. **Split-brain identity (highest priority, confirmed real)**: CampaignRun hashes its stage spec from the frozen StageNode.source_slice_id/build_plan_id/workload_id, but CampaignStageExecutor never validated the executor's actual mutable identity state against those frozen fields. re14_real_run.py built build_stage_graph(...workload_id="pending"...) BEFORE generate ran, then set executor.workload_id = <real value> AFTER, without ever rebuilding the graph -- so CampaignRun's own spec identity and the artifacts actually produced could disagree. Root-caused and fixed two ways: (a) re14_real_run.py now computes workload_id = inventory_ref.content_hash (deterministically knowable before generate runs, since make_generate_worker already derives it that way) and builds the graph with the REAL value from the start, eliminating the placeholder entirely; (b) CampaignStageExecutor now has _require_node_identity_agreement(), called before every generate/build/smoke execution, that hard-fails on any StageNode/executor identity disagreement as defense in depth. My own FullChainTests fixture had baked in the exact same 'pending'-placeholder bug in its test graph construction -- caught immediately when the new check correctly rejected it.
2. **BuildPlan.inventory_hash left None** despite the build genuinely depending on inventory content, and despite validate_reuse()-style reuse being keyed partly on build_plan_id -- meaning two tune builds with different inventory content could silently collide on the same build_plan_id/build directory/artifact path. Fixed: re14_real_run.py now passes inventory_hash=inventory_digest into BuildPlan.
3. **cmake was fed the caller's original --inventory file path, not the verified ArtifactStore copy** -- a real provenance violation (publish inventory A, generate from A, mutate the original file to B, build compiles against B, provenance still claims A). Fixed: build worker now receives inventory_ref.path.
4. **campaign.run_id recorded in every artifact's provenance but never enforced** across the build/smoke stage boundary, so an artifact from a different campaign run with coincidentally-matching source/build/workload identity could pass -- inconsistent with RE14's own documented cross-campaign-artifact negative-parity criterion. Fixed: workload_expected() (build/smoke only, not generate -- inventory may legitimately predate the run) now includes campaign.run_id.
5. **AMDGPU_TARGETS always comes from platform.targets, never BuildPlan.targets/--arch** -- meaning the session's earlier 'single-arch (gfx1100) vs multi-arch (gfx1100+gfx1201+gfx1030)' framing was WRONG: both real runs used --platform linux-multi and therefore both actually compiled for all three of its declared targets regardless of --arch. --arch only ever affected which architectures autotune_catalog.build_manifest() generates CATALOG candidates for, not what CMake compiles. Corrected here rather than left standing; re14_real_run.py now passes platform_cfg.targets into BuildPlan.targets directly so the plan is at least truthful about what actually gets compiled, instead of silently diverging from it.
6. **smoke worker's next() binary selection was unguarded** (silently takes whichever 'binary'-kind input comes first) -- safe today's strictly linear graph, unsafe as a general multi-parent-node contract. Fixed to exact-cardinality (list + length check), matching the build worker's existing pattern.
7. **smoke result recorded only binary_hash**, not what it was actually smoked against -- two different models/settings against the same binary would be indistinguishable evidence. Fixed: smoke result now includes model_hash, model_path, n_prompt, n_gen, split_mode.
8. **chmod scope**: 0o111 (all-execute) was functionally fine but broader than needed for a same-user store. Narrowed to stat.S_IXUSR (owner-execute only).
9. **Build was redundantly returning generate's manifest ArtifactRef as its own output** (on top of round-5's fix of not re-publishing it) -- simplified further: build now returns only the binary it actually produced; the manifest remains available via executor.outputs[generate_stage_id].

5 new tests (NodeIdentityAgreementTests) proving the split-brain check actually catches each mismatch type (source_slice_id/build_plan_id/workload_id, both on generate and build/smoke) plus a positive case. Full suite 497/497 (2 pre-existing unrelated failures). All fixes re-verified with a THIRD real end-to-end Brutus run (gfx1100, 241.7 t/s) -- smoke result now genuinely includes model_hash/model_path/n_prompt/n_gen/split_mode, confirmed in the real run's output, not just unit-tested.

Still correctly NOT done, per the review's own explicit scoping: (a) neither this round's nor round 5's real runs actually invoked CampaignRun.execute() -- re14_real_run.py calls each stage executor directly in sequence, so CampaignRun's own spec-hashing/scheduling/ResourceLock/reuse/blocking behavior remains real-code-exercised only by its own pre-existing unit tests, not by any of these hardware runs; (b) the generated/ directory (registry.inc etc) build reads by run_id convention is still an unverified side-channel outside the formal ArtifactRef/PipelineService boundary -- flagged by the review as higher-priority than this session had been treating it, still not hardened (would need a canonical generated-tree.json of relative-path+SHA-256 published and re-verified before configure, or a tar/archive artifact); (c) build does not yet use builds.validate_reuse()-style reuse semantics -- it always compiles into whatever build_directory() resolves to, with no proper existing-artifact validation before accepting a possible prior build; (d) toolchain_request/environment BuildPlan fields remain unpopulated even though the real compiler paths are known (platform.c_compiler/cxx_compiler) -- plan construction and actual cmake argument construction remain two parallel implementations that already drifted once (finding #5) and could drift again undetected without one going through the other. None of these four are quick fixes; each needs its own real-hardware proof cycle like the identity fixes just got, not just a code change.
