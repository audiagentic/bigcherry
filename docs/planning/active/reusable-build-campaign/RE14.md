# Cut over campaign execution and retire legacy mutable mechanics

## Description

Route normal campaign execution through the new source/build services, prove legacy/new parity, then remove duplicated mutable-checkout assumptions.

## Steps

1. Freeze a parity fixture: one pinned llama.cpp release, exact production patch set, architecture/target, toolchain, inventory/workload, normal campaign shape. Capture legacy path's source state, manifest, descriptor, candidate set, smoke result as reference evidence.
2. Migrate stages behind the new services incrementally (PipelineService/CampaignGraph/CampaignRun/ArtifactStore/BuildPlan/workspace.materialize -- confirmed zero production callers today, only exercised by their own unit tests), but keep normal execution on the legacy path until parity is proven. Each migrated stage must consume explicit identities/artifact refs, not cwd/checkout/prior-stage-build-dir/release-record state.
3. Shadow-run the new path end-to-end against the fixture in a fully separate work root -- must not share checkout, generated directory, CMake build dir, or ArtifactStore namespace with the legacy run.
4. Machine-generated parity comparison (not visual/log diff): source (effective Git tree OID/source-slice ID + exact patch IDs/order/hashes), manifest+descriptor (canonical semantic content, not paths/timestamps), build (BuildPlan ID + effective build ID recompute, expected toolchain, actual binary SHA-256 via validate_reuse() semantics), candidate coverage (exact stable-ID set equality, not just count equality).
5. Runtime parity: at least one real gfx1100 smoke using the artifact resolved from the new descriptor/store (not a manually selected binary path).
6. Negative/fail-closed parity: deliberately tamper each of source/patch-order/inventory-source-slice/published-artifact/descriptor/binary/provenance-namespace/build-dir-reuse/cross-campaign-artifact and confirm every case fails closed before downstream work happens.
7. Flip normal/default execution to the new path with no automatic fallback; legacy path may remain only as an explicit diagnostic/compatibility command.
8. Only then delete legacy mutable-checkout mechanics: tree-state switching (_ensure_tree_state, _reset_tree), the checkout-path-suffixed _build_dir identity, GENERATED_IN_TREE in-checkout generation output, and any tests/CLI code that assume them.

## Detailed Solution & Technical Design

Investigation finding (2026-08-16): every new-service class already exists and is unit-tested but has ZERO production callers anywhere in the repo (checked via grep across tools/bigcherry and docs/scripts) -- PipelineService, CampaignGraph, CampaignRun, ResourceLock, ArtifactStore, BuildPlan, workspace.materialize. 'Normal campaign execution' today is entirely the legacy path in __main__.py's cmd_build, operating on one shared mutable checkout (paths.llama_root()). There is no campaign orchestrator script anywhere; the Brutus campaign-*.sqlite/log artifacts produced this session were built by manually invoking the legacy CLI per build variant (build/bigcherry-tune, build/bigcherry-record, etc).

Root coupling identified (confirmed against source, not assumed): the checkout is used as an implicit inter-stage state bus, not just a mutable git tree. Concretely:
- `_generate_for()`/`GENERATED_IN_TREE` (tools/bigcherry/__main__.py ~L320) writes hip-autotune-registry.inc, manifest, descriptor, mmvq-instances etc DIRECTLY INTO THE SHARED CHECKOUT. A later stage reads these by conventional in-tree path, not by artifact reference -- this is why generate must run immediately before the build that consumes it and why variants must stay sequential (cannot safely share this mutable generated state).
- `_build_dir()` (tools/bigcherry/__main__.py L299) identity is recipe+build name plus a checkout-path hash suffix for non-default roots -- NOT content-addressed by effective source tree + complete build plan. Contrast with the new `builds.build_directory()` = work_root/builds/<source_slice_id>/<build_plan_id>, whose `validate_reuse()` additionally recomputes effective configure record, toolchain identity, and binary SHA-256.
- `_reset_tree()`/`_ensure_tree_state()` flip the ONE shared checkout between recipes rather than materializing an isolated worktree per build (workspace.materialize exists for exactly this and is unused).

Additional integration hazard for the new path itself (not yet built, but must be designed in from the start): PipelineService checks provenance compatibility on ArtifactRef inputs/outputs but does not itself verify ArtifactRef.path bytes match content_hash -- ArtifactStore provides that verification and immutable-publish semantics separately. RE14's executor wiring must make artifact consumption require ArtifactStore-verified bytes, not provenance-field agreement alone. Similarly CampaignRun's reuse hook must validate recorded output hashes/artifacts, not trust StageRecord alone.

Removal criterion (do not delete legacy code before all of this holds): a clean-room pinned campaign through the new path produces source/patch/manifest/descriptor/candidate parity against the legacy reference, a hash-verified real-GPU smoke succeeds, a second execution demonstrates identity-safe reuse/resume from an empty work root, all deliberate mismatch/tamper cases fail closed, and the default campaign path contains no implicit fallback to legacy.

Scope note re: RE15 overlap -- if legacy and new paths both produce the same complete candidate universe (e.g. the same 101 applicable candidates from the RE09 replay-full investigation) and the new binary passes real-GPU smoke, RE14 does not need to wait on RE15's remaining 25-candidate correctness-evidence gap to close -- that gap is acceptance evidence across candidates, whereas RE14 is proving cutover did not alter which candidates exist or how they're identified/built. Only let the missing 25 block RE14 if they reveal an actual difference between the two execution paths.

### MAJOR MILESTONE 2026-08-16 (round 5): first real end-to-end run of the new campaign path, on Brutus, against real ROCm/HIP, real GPU hardware.

tools/bigcherry/re14_real_run.py (new, not a permanent CLI -- a standalone proof harness) + tools/bigcherry/campaign_workers.py (new: real generate/build/smoke worker implementations wiring CampaignStageExecutor to autotune_catalog.build_manifest/emit, real cmake/ninja compilation, and a real llama-bench subprocess). Ran the full materialize -> generate -> build -> runtime-smoke chain for the bigcherry/tune/linux-multi lane, TWICE, both passing completely:

- Single-arch (gfx1100): avg_ts=251.4 t/s generation on RX 7900 XTX.
- Full platform.linux-multi arch set (gfx1100,gfx1201,gfx1030 together, matching the real recipes.toml platform definition exactly): avg_ts=306.4 t/s generation, real materialize+generate+404/404-object-compile+smoke, all through the new isolated/content-addressed/provenance-verified path.

GPUs confirmed idle and no orphaned processes after both runs.

Getting the first run working surfaced and fixed THREE real bugs that no amount of design review (this session's three gpt-auto-agent rounds) had caught, because none of it had ever actually run:

1. **source_identity.git_tree_oid() rejected every modified-tracked-file (`M`) status line as 'unexpected', not only genuinely-unexpected untracked files.** Since patches exist specifically to modify existing tracked upstream files, this meant workspace.materialize() could never succeed against ANY source with real patches -- a total, previously-undetected blocker in code from round 1 that had been verified only by reading, never by running (its own test suite never exercised materialize() with a non-empty patch set). Fixed: only `??` (untracked) files are checked against allowed_untracked now; modifications to already-tracked files are never rejected, since the tree OID computed afterward already captures them correctly. 4 new/existing tests in test_source_identity.py, including one proving the fix does NOT become blanket-permissive (a genuine stray untracked file alongside a legitimate patch modification is still rejected).
2. **ArtifactStore.publish_file() does not preserve the executable bit** (a correct, general design choice for a store meant mostly for JSON/data artifacts) -- so a published binary artifact could not actually be executed for runtime-smoke. Fixed narrowly in campaign_workers.py's build worker (chmod +x after publish), not inside ArtifactStore itself, since only a caller that specifically knows it published a binary should make that call.
3. **The build worker was redundantly re-publishing generate's manifest.json under a second, build-scoped ArtifactStore path** -- and since the raw manifest JSON embeds a real-time generated_at (manifest_hash deliberately excludes it, but the raw file bytes don't), a second run's manifest had different bytes than the first's at the same nominally-content-addressed path, correctly triggering ArtifactStore's immutability rejection ('immutable artifact already exists with different bytes'). This is exactly the generated_at/manifest_hash byte-instability gpt-auto-agent's round 2 review predicted in the abstract ('I would not use this as an immutable store path ... unless the manifest timestamp is deliberately normalized') -- now empirically confirmed, not just theorized. Fixed by not re-publishing at all: the build stage references generate's already-published, already-verified ArtifactRef directly instead of minting a redundant path for the same content.

All three fixes verified on both local (492/492, 2 pre-existing unrelated failures) and Brutus (42/42 new-module tests) before the fixes stopped surfacing new failures; the second (multi-arch) real run hit none of these three issues, confirming the fixes generalize rather than being single-run flukes.

Still not done: the RE14 sequencing plan's steps 3-6 (shadow-run against a frozen parity FIXTURE with a pinned comparison to the legacy path's output, negative/tamper-case testing, machine-generated parity report) have not been executed -- this round proved the new path CAN run correctly end to end, twice, not yet that it matches the legacy path's output on the same inputs. That comparison (using parity.py from round 1, reconciled with round 2's alternate comparisons.py-based design that was never built) is the next real step. No CLI entrypoint (re14_real_run.py is a proof harness, not `python -m bigcherry campaign run`). Legacy cmd_build fully untouched throughout.
