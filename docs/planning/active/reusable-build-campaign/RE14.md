## Detailed Solution & Technical Design

Investigation finding (2026-08-16): every new-service class already exists and is unit-tested but has ZERO production callers anywhere in the repo (checked via grep across tools/bigcherry and docs/scripts) -- PipelineService, CampaignGraph, CampaignRun, ResourceLock, ArtifactStore, BuildPlan, workspace.materialize. 'Normal campaign execution' today is entirely the legacy path in __main__.py's cmd_build, operating on one shared mutable checkout (paths.llama_root()). There is no campaign orchestrator script anywhere; the Brutus campaign-*.sqlite/log artifacts produced this session were built by manually invoking the legacy CLI per build variant (build/bigcherry-tune, build/bigcherry-record, etc).

Root coupling identified (confirmed against source, not assumed): the checkout is used as an implicit inter-stage state bus, not just a mutable git tree. Concretely:
- `_generate_for()`/`GENERATED_IN_TREE` (tools/bigcherry/__main__.py ~L320) writes hip-autotune-registry.inc, manifest, descriptor, mmvq-instances etc DIRECTLY INTO THE SHARED CHECKOUT. A later stage reads these by conventional in-tree path, not by artifact reference -- this is why generate must run immediately before the build that consumes it and why variants must stay sequential (cannot safely share this mutable generated state).
- `_build_dir()` (tools/bigcherry/__main__.py L299) identity is recipe+build name plus a checkout-path hash suffix for non-default roots -- NOT content-addressed by effective source tree + complete build plan. Contrast with the new `builds.build_directory()` = work_root/builds/<source_slice_id>/<build_plan_id>, whose `validate_reuse()` additionally recomputes effective configure record, toolchain identity, and binary SHA-256.
- `_reset_tree()`/`_ensure_tree_state()` flip the ONE shared checkout between recipes rather than materializing an isolated worktree per build (workspace.materialize exists for exactly this and is unused).

Additional integration hazard for the new path itself (not yet built, but must be designed in from the start): PipelineService checks provenance compatibility on ArtifactRef inputs/outputs but does not itself verify ArtifactRef.path bytes match content_hash -- ArtifactStore provides that verification and immutable-publish semantics separately. RE14's executor wiring must make artifact consumption require ArtifactStore-verified bytes, not provenance-field agreement alone. Similarly CampaignRun's reuse hook must validate recorded output hashes/artifacts, not trust StageRecord alone.

Removal criterion (do not delete legacy code before all of this holds): a clean-room pinned campaign through the new path produces source/patch/manifest/descriptor/candidate parity against the legacy reference, a hash-verified real-GPU smoke succeeds, a second execution demonstrates identity-safe reuse/resume from an empty work root, all deliberate mismatch/tamper cases fail closed, and the default campaign path contains no implicit fallback to legacy.

Scope note re: RE15 overlap -- if legacy and new paths both produce the same complete candidate universe (e.g. the same 101 applicable candidates from the RE09 replay-full investigation) and the new binary passes real-GPU smoke, RE14 does not need to wait on RE15's remaining 25-candidate correctness-evidence gap to close -- that gap is acceptance evidence across candidates, whereas RE14 is proving cutover did not alter which candidates exist or how they're identified/built. Only let the missing 25 block RE14 if they reveal an actual difference between the two execution paths.

**GPT's recommendation, verified against source before recording (config.py's v2 Build.needs IS a real frozenset[str]; recipes.py's _load_v2_compat DOES compress it back to a single legacy string, exactly as claimed):**

Do NOT reimplement legacy's recipe/tree-state mechanics on the new architecture. Build a thin canonical multi-LANE orchestrator over canonical v2 source/build/platform identities (not legacy recipes/groups/states, which are transitional compat-only concepts). Sequential execution of N lanes is fine for RE14 -- no need to unify into one giant CampaignGraph.
