# Extend patch_catalog.py metadata: PLAN_IDS, BACKENDS, SUBSYSTEMS, REQUIRES, CONFLICTS, HARDWARE

## Description

tools/bigcherry/patch_catalog.py + patches/catalog.toml (built earlier this session, RE30 phase 1) already carries kind/origin/backend/state per patch, cross-checked 1:1 against every discoverable module. An external patch-management review recommends extending this with fields the catalog doesn't have yet: PLAN_IDS (plural -- a patch can serve more than one RD/EX/HI plan item; today's catalog only has a singular plan-item field on some entries), BACKENDS (plural, for a future patch that legitimately spans hip+vulkan), SUBSYSTEMS (free-form tags like moe/graph/streams -- explicitly NOT a folder axis, useful metadata only, per both the review and RE38's reconciliation), REQUIRES/CONFLICTS (patch-to-patch dependency/conflict declarations, currently only expressed indirectly via anchor collisions like RD12/RD17's known conflict, or manually duplicated dependency chains in config/recipes.toml's [experiment.*] entries), HARDWARE (architecture/device-class constraints, e.g. gfx1151-only).

## Steps

Add these as optional fields (not mandatory on every existing patch immediately -- match the catalog's existing incremental-adoption pattern). Backfill REQUIRES for the currently-known real dependency chains that config/recipes.toml already encodes manually (e.g. [experiment.rd44-only]'s hand-listed 1215+1216+1217 chain) so RE40 (resolve_exact/expand_composition split) has real data to work from. Cross-check test (patches/catalog.toml has 1:1 coverage with discoverable modules) must keep passing with the new optional fields present on some entries and absent on others.
