# Implement campaign DAG, resource ownership, locks, and resume

## Description

Build typed campaign plans/runs, graphlib ordering, GPU/build/source claims, immutable stage evidence, failure blocking, and hash-validated resume.

## Steps



## Detailed Solution & Technical Design

DURABLE RUN PROTOCOL (RV48 audit - significantly open). VERIFIED: CampaignGraph, failure-descendant blocking and ResourceLock exist; but CampaignRun.records is process memory only (root is resolved but never used to save/load stage records), the reuse helper documents that cross-process resume does not exist, and the per-stage spec hash covers only stage_id/kind/source_slice_id/build_plan_id/workload_id/dependencies - NOT e.g. model hash, prompt/generation lengths or smoke environment (the smoke RESULT records those facts, but CampaignRun's reusable-stage identity does not).

REQUIRED: (1) Before work starts, write an IMMUTABLE/ATOMIC campaign intent containing the campaign request/profile identity, resolved lane identities and operation-spec hashes. (2) After an output is published AND byte-verified, atomically persist a stage result containing the exact ArtifactDescriptors (RE08). (3) On resume: re-read the intent, reject any request/config mismatch, rehydrate output artifacts, verify EVERY byte, only then permit reuse. A stage found in 'running' state after process death must not magically become success. (4) Add an immutable operation_spec_hash / typed stage-spec payload to each StageNode so a resumed stage identity knows its full spec, not just source/build/workload/dependencies. (5) Formalise GPU assignments here: campaign_plan already accepts explicit gpu_resource_ids and the canonical planner intentionally does NOT derive them from architecture/platform - a scheduler/execution-assignment layer supplies physical GPU resource IDs separately from build platform configuration.
