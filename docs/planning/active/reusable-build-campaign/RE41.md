# Decision: no physical patch-folder move — metadata + CLI filtering is sufficient

## Description

Supersedes BOTH prior folder proposals for patches/: RE30's own earlier 'Folder decision' (backend-first: common/hip/vulkan/upstream) AND the external Patch Management design doc's proposal (kind-first: framework/fixes/experiments/_shared). User's direct call, 2026-08-20: if patch_catalog.py's metadata (kind/origin/backend/state, already built and populated for all ~34 current patches) already answers every classification question a folder split would answer, then folders add migration risk (RE30's own 'Deep implementation validation' note already found the move 'cannot be a simple git mv' -- several tests hard-code flat patches/<id>.py paths) for a benefit a CLI view delivers for free and with zero path churn.

## Steps

Keep patches/ flat, indefinitely, as the default -- not a temporary fallback pending a future move. The functional equivalent of folder browsability is `bigcherry patch list --kind framework` / `--backend hip` / `--state validated` etc, filtering the existing patch_catalog.py metadata (this CLI work is separately tracked -- see the sibling 'patch list/explain/graph CLI' item filed this session). Only reconsider a physical split later if the CLI+metadata approach is demonstrated insufficient at real scale (a concrete pain point, not a hypothetical one) -- do not pre-emptively migrate files against a problem that hasn't actually occurred.
