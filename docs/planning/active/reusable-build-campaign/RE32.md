# Vulkan candidate eligibility ABI: can_execute() cannot evaluate real Vulkan capability yet

## Description

GPT review of RE30's Vulkan autotune scaffolding (vk-autotune-types.h) found a real design gap: ggml_vk_hardware_key_v1 deliberately omits extensions/limits/driver version (they were designed to travel separately as canonical JSON), but ggml_vk_can_execute_fn and ggml_vk_replay_lookup both receive only that reduced hardware key. This means can_execute() structurally cannot evaluate the real Vulkan eligibility question (does this device support the extension/limits this candidate needs) with the data it's currently given. The header's own comment already flags this ('Phase 3 will likely need to widen what can_execute/ggml_vk_candidate_descriptor receive, which may not be an additive change') but there is no tracked decision or design for what the real shape should be.

## Steps

Before Phase 3 implementation starts, decide the real shape can_execute needs: either widen the function signature to also receive the canonical JSON capability payload (extensions/limits/driver version), or fold a resolved capability struct into ggml_vk_hardware_key_v1 itself. Whichever is chosen, it is a real API-shape decision for currently-unintegrated scaffolding -- better to decide it deliberately now than let it become a breaking change to something already treated as load-bearing later. Update ggml_vk_candidate_descriptor/can_execute accordingly and add a real test proving eligibility can actually reject an unsupported extension/limits combination, which no current test does (the existing scaffolding tests only prove structural things -- byte layout, digest determinism -- not real eligibility logic).
