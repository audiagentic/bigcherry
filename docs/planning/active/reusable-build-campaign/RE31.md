# Vulkan-aware device-visibility wiring for build's runtime smoke path

## Description

Make build runtime smoke backend-aware. The existing RuntimeSmokeSpec and worker accept generic environment mappings; only the CLI convenience layer is HIP-specific.

## Steps

Add a backend-to-environment adapter, select it from the planned lane/backend, preserve HIP_VISIBLE_DEVICES behavior, add GGML_VK_VISIBLE_DEVICES for Vulkan, reject ambiguous mixed visibility inputs, and pass the selected environment unchanged to runtime smoke.

## Detailed Solution & Technical Design

Generalize smoke_environment_for_hip_devices() into smoke_environment_for_backend(backend, visible_devices), or provide two thin adapters over one validated mapping builder. Keep device visibility out of generic smoke execution. Derive backend from the lane/platform rather than a caller boolean where possible, so a Vulkan lane cannot accidentally receive HIP_VISIBLE_DEVICES.

## Code Samples & Guidance

```python
# campaign_lane.py
VISIBLE_ENV = {"hip": "HIP_VISIBLE_DEVICES", "vulkan": "GGML_VK_VISIBLE_DEVICES"}
def smoke_environment_for_backend(backend: str, visible_devices: str | None):
    if visible_devices is None:
        return ()
    try:
        variable = VISIBLE_ENV[backend]
    except KeyError:
        raise ValueError(f"unsupported smoke backend: {backend}")
    if not visible_devices.strip():
        raise ValueError("visible device selection must not be empty")
    return ((variable, visible_devices), ("PATH", os.environ.get("PATH", "")))
```
In `cmd_build_new`, derive `backend = cfg.sources[selector.source].backend` per planned lane; if one request contains mixed backends, carry the backend on `CampaignLane` and compute the environment in planner expansion rather than passing one request-global HIP tuple.
