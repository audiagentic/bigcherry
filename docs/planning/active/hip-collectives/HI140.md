# Qwen3.8-Flash 3-GPU/4-GPU tensor-split benchmark matrix

## Description

User-authored (2026-08-29) exploratory benchmark runsheet for a new model, Qwen3.8-Flash, across 3-GPU (R9700 32GB + 2x XTX 24GB) and 4-GPU (adding the 6900XT 16GB on chipset PCIe x4) Brutus configurations. Keep Engram/PLE in RAM/NVMe; keep normal compute weights and MoE experts in VRAM. Secondary to HI138's RCCL heterogeneous qualification for GPU time -- design/queue now, execute once HI138's Phase-1 hardware gates (RQ04-RQ08) are clear of the GPUs.

## Steps

3-GPU tests (R9700 32GB + 2x XTX 24GB), all at 40/30/30 split unless noted:
1. Baseline: 32K context, F16 KV, ubatch 1024.
2. Main baseline: 128K context, F16 KV, ubatch 1024.
3. Prefill test: 128K context, F16 KV, ubatch 2048.
4. Larger context: 192K context, F16 KV, ubatch 1024.
5. Maximum context: 262K context, F16 KV, ubatch 512 then 1024.
6. XTX-heavy split: 38/31/31, 128K context, otherwise best settings above.
7. R9700-heavy split: 42/29/29, 128K context, otherwise best settings above.
8. KV test: best split, 128K context, Q8_0 KV versus F16.
9. MTP test: best 128K configuration plus MTP.
10. Final 3-GPU test: best settings plus MTP at 192K and 262K.

Measure: pp512, pp4096, tg128, tg512, VRAM per GPU, RAM use, MTP acceptance rate.

4-GPU tests (R9700 + 2x XTX + 6900XT 16GB on chipset PCIe x4 -- use 3-GPU result as control; expect the 6900XT to hurt decode via chipset-crossing traffic unless layer placement avoids it):
1. Control: R9700+2xXTX only, same best 128K configuration.
2. Tiny 6900XT split: ~38/29/29/4 -- does merely involving the 6900XT hurt decode?
3. Small 6900XT split: ~36/28/28/8.
4. Medium 6900XT split: ~34/27/27/12.
5. Larger 6900XT split: ~32/26/26/16.
6. Best 4-GPU split at 128K, increase ubatch as far as VRAM permits.
7. Best 4-GPU split at 192K F16 KV.
8. Best 4-GPU split at 262K F16 KV.
9. Best 4-GPU configuration plus MTP.
10. Best 3-GPU versus best 4-GPU, identical context/KV/ubatch, direct comparison.

Key question: does the 6900XT's extra 16GB VRAM headroom (larger ubatch/context/MTP) outweigh the chipset PCIe x4 crossing cost -- not expected to help raw decode unless layer placement avoids frequent cross-boundary traffic.

### gpt feasibility verdict (2026-08-29): BLOCKED-PREFLIGHT, not hardware-ready

Two no-GPU blockers must be resolved before any hardware execution:

1. **VRAM/model identity unverified.** Model is likely Qwen3.8-Flash-Next: 125B backbone/6B active + 51B N-gram/PLE embedding + ~4B MTP, 48 layers, native 262,144 context. Official FP8 is ~172.8GiB -- 80/96GB aggregate VRAM cannot hold it even with tensor parallelism; a substantially quantized GGUF + PLE offload is mandatory. Approximate F16 attention-KV-only estimates (excludes QSA indexer/GDN state, workspaces, ubatch scratch): 32K~0.75GiB, 128K~3GiB, 192K~4.5GiB, 262K~6GiB. The runsheet's 40/30/30 and 32/26/26/16 splits are HYPOTHESES, not established-fit configurations, until checked against the real GGUF.
2. **b10502 (this branch's pin) predates Qwen3.8-Flash-Next/qwen4exp support entirely.** Upstream llama.cpp first added qwen4exp at b10660. No pushed BigCherry backport found. PLE ("Engram") is real model terminology (Qwen's own term for the 51B N-gram embedding designed for host offload) -- current llama.cpp places it on CPU via mmap/file-backed paging, not a distinct NVMe backend; "keep in RAM/NVMe" is really "CPU placement + mmap." Do not schedule hardware until the benchmark source slice with qwen4exp support is identified.

Other findings:
- 6900XT/chipset framing needs rewording, not abandoning: HI84 already found NO PCIe P2P bridge exists anywhere on this box, so all cross-GPU traffic is already host-staged regardless of chipset vs CPU-attached slots -- the 6900XT doesn't uniquely add "chipset crossing," it adds a bandwidth-constrained x4/chipset ENDPOINT leg to transfers involving it, which can still be materially slower and can contend on the chipset uplink. Reframe as "x4 endpoint penalty under host-staged tensor reduction/copies" and measure negotiated link width/speed directly.
- MTP is algorithmically orthogonal to patch 1225/RCCL-vs-META reduction-provider selection -- does not bypass the fail-closed guard. Test MTP only after base topology is established; Qwen3.8-Flash-Next-specific MTP behavior on whatever source slice is used still needs separate verification.
- Runsheet gap: pp512/pp4096/tg128/tg512 at a given -c value tests allocation capacity, not performance AT that occupied context depth. For the long-context question, must measure decode/prefill at representative RESIDENT depths (~32K, ~128K, then 192K/262K), not just context-limit values -- recent qwen4exp/HIP reports (different hardware) already show context-depth-dependent decode degradation on AMD.

### Required no-GPU preflight before scheduling hardware
- Identify exact Qwen3.8-Flash-Next GGUF filename, quant, total bytes, PLE tensor bytes, MTP presence.
- Identify the llama.cpp source revision/backport that actually supports qwen4exp.
- Verify PLE CPU/mmap placement on that revision.
- Derive per-GPU static-weight budget for every proposed -ts ratio.
- Reserve measured/estimated KV + workspace + ubatch headroom rather than allocating 100% VRAM to weights.

### Minimal first hardware stage (once preflight clears and HI138 frees the GPUs)
1. 3G control: 40/30/30, 128K, F16 KV, ub1024, MTP off.
2. 4G tiny: ~38/29/29/4, identical workload -- does merely involving the 6900XT hurt?
3. 4G medium: ~34/27/27/12, identical workload -- does useful VRAM contribution compensate?
4. Only if #3 is competitive: 4G 16% split and/or larger ubatch.
5. Only if 4G provides real headroom: one capacity discriminator at 192K/262K that 3G cannot fit/run efficiently.
6. MTP only on the winning 3G and 4G configurations.
Use 3 reps for screening; expand only the winner/control pair to stronger repetition. Do NOT run all 20 original configurations initially.
