# Q3_K HIP MMVQ VDR2: narrow RDNA3/RDNA4 admission of upstream #30517

## Decision (2026-10-18; BCOP296)

**Pending / receipt-first; no implementation or GPU run queued.** Upstream llama.cpp [#30517](https://github.com/ggml-org/llama.cpp/pull/30517), merged 2026-10-17 at 13:35 UTC (merge `2744e48d1e88d7416224e92bf58d4ffedda4a205`), supplies a **new Q3_K VDR=2** MMVQ integer-dot and packed-scale layout. The pinned BigCherry llama.cpp b11552 (`23b0202a189c44a54625aadcb37a946dd1d6278d`) uses `VDR_Q3_K_Q8_1_MMVQ=1`. This is **not** the recently audited Q2_K VDR2 (PKC05), Q6_K VDR2 (rejected 1204), IQ MMVQ (QFP10/1273), Q8_0/Q6_K raw-F32 activation (1241/1274), or MoE helper WMMA (RAD06). Admit only Q3_K, initially dense width-1 decode on one physical RDNA GPU; do not port the entire upstream PR as a bundled BigCherry optimisation.

### Source/data-flow and physical-work boundary

Pinned `ggml/src/ggml-cuda/mmvq.cu::ggml_cuda_mul_mat_vec_q` allocates `src1_q8_1` from `ctx.pool()`, quantizes the input via `quantize_row_q8_1_cuda` on the same stream, then calls `mul_mat_vec_q_switch_type` -> `mul_mat_vec_q_switch_ncols_dst<GGML_TYPE_Q3_K>` -> `mul_mat_vec_q`. The generic kernel sets `qi`, `vdr`, `nwarps`, `rows_per_cuda_block`, and `blocks_per_iter = vdr*nwarps*warp_size/qi`; for each thread `kqs = vdr*(tid % (qi/vdr))`. The `has_ids && ncols_dst>1` branch selects a **different** `mul_mat_vec_q_moe` kernel and must remain a negative control initially. Q8_1 scratch lifetime and stream/graph ordering stay with the existing pool and producer; VDR2 does **not** eliminate the Q8_1 conversion or any model-layer dispatch.

Pinned `vecdotq.cuh::vec_dot_q3_K_q8_1` loads Q3 low bits (`qs`), high mask (`hmask`), 12-byte packed scales, F16 block scale, Q8_1 activations and their scales. `vec_dot_q3_K_q8_1_impl_mmvq` performs `QR3_K=4` groups of integer `dp4a` followed by scaled F32 accumulation. #30517 changes VDR 1 -> 2, preloads two adjacent packed low/high words, shares the extracted scale and Q8_1 scale over both, and replaces the old signed-byte `__vsub4` with **two integer dp4a contributions**: `dp4a(vl|vh,u)` and `dp4a(0xFCFCFCFC,u)`. The latter encodes four signed -4 bytes. This is algebraically equivalent for the Q3 high-mask convention but changes F32 accumulation grouping: do not promise bit identity or unchanged MTP acceptance.

At Q3_K `qi=16`, wave32 and baseline `nwarps=1` on RDNA3_0/RDNA4 width1, VDR1 covers 2 quant blocks/32-thread iteration; VDR2 covers 4. The 256-value Q3_K weight block is 110 bytes, so K=4096 implies 16 blocks / 1760 **logical weight bytes per output row**, unchanged by VDR2. Q8_1 quantization and output writes are unchanged. This halves K-loop trips in the ideal long-row case, **not** memory bytes, kernel launches, FLOPs or exposed wall time; added registers/dp4a and tails can offset savings. Collect compiled VGPR/SGPR, scratch/spills, LDS, occupancy, wave32, integer dot instruction count, cache misses, clocks, launches and actual completed rows. Check that `0600_mmvq_geometry` template modifications and `0650_mmvq_native_variant` forced geometry still compose; do not create a parallel launch table.

**Architecture/dispatch trap:** #30517 adds two-rows-per-block for the **GENERIC** table, not RDNA3_0 or RDNA4. The new GCN width2/3 Q3_K nwarps=1 adjustment is **GCN only**, not an RDNA tuning result. Pinned RDNA3_0 and RDNA4 width1 Q3_K select one warp and one row/block; `small_k` is disabled on RDNA. Any proposed RDNA row-tile or nwarps change is a separate geometry hypothesis under 0600/0650, not part of the Q3_K VDR2 test. Keep gfx1030, GCN/CDNA, all other quants, F32-act paths, MMQ prefill and Vulkan unchanged.

### Evidence and cheapest discriminator

- **Upstream measurements, not BigCherry:** #30517 reports gfx1151 Q3_K MMVQ kernel 1.08x at width1, 1.23x at width2, 1.29x at width4 and 1.37x at width8; Qwen3.5-4B Q3_K_S `tg128` 69.70 -> 72.58 t/s (~4.1%). An upstream PR commenter measured **R9700 gfx1201 on Windows** Q3_K width1 kernel 40.7 -> 28.2 us (~1.44x), and Qwen3.5-4B Q3_K_S `tg128` 135.2 -> 142.1 t/s (~5.1%). Different pins, OS, models, clocks and quant mixes: **none is a BigCherry gfx1201/gfx1100 result**. On MI50/GCN, width2/3 initially regressed and needed a GCN-specific warp-table fix; do not extrapolate the PR as universally positive.
- Independent [llama.cpp Q3_K_S RDNA4 discussion #22663](https://github.com/ggml-org/llama.cpp/discussions/22663) reports gfx1200 HIP Q3_K 122.21 us vs Vulkan 88.14 us at an N=1 4096x14336 op, plus Q3_K_S vs Q5_K_M decode 58.03 vs 50.41 t/s despite different weight sizes. This is an **external same-card comparison**, not proof that VDR2 cures the difference. vLLM's ROCm quantized GEMM/attention paths and SGLang's GGUF quant dispatch do not provide a bit-compatible `block_q3_K × block_q8_1` replacement; use them only as mechanism/negative-route references, not an AMD speedup estimate.
- **This audit's disposable host-only fixtures:** 256 seeded random Q3 packed blocks × 8 lane pairs × 2 adjacent chunks × 4 scale/dot groups = **16,384/16,384 exact integer-dot + packed-scale comparisons** between source-shaped VDR1 and proposed VDR2; 0 mismatches. A separate synthetic F32 grouping fixture found **2,394/4,096 non-bit-identical** pair sums. Neither fixture executes HIP, reproduces compiler contraction, validates logits, or establishes GPU correctness. It specifically **rejects the assumption of F32 bit identity**.
- No BigCherry Q3_K-specific, current-pin per-kernel or end-to-end A/B was identified in the inspected planning/patch/PR scope. BigCherry's historical 1204 Q6_K VDR2 gfx1201 decode +0.204%, CI95 [+0.094,+0.330] failed its promotion threshold, with a small prefill regression; this is a **separate quant path** and a caution against automatic adoption.

### Bounded implementation / rejection sequence

**Gate 0 — route and ceiling, no patch or hardware queue.** First inspect the actual BigCherry model inventory and archived runs for an all-GPU Q3_K_S GGUF (not Q3_K in a few sensitive layers), exact model digest, build pin, `--split-mode`, Q3_K op counts and width1 decode critical-path wall fraction. Record per-device physical UUID (dual gfx1100 must not alias), Q8_1 quantization launches/bytes, Q3_K MMVQ launches/duration, expected vs executed row/block counts, context, ubatch, MTP depth, GPU/CPU synchronization, transfers and cache-resident versus streaming working set. For an optimistic 1.44x kernel speedup, a 3% E2E target requires **>=9.5% exposed baseline wall time** in affected work; for 1.08x, **>=39.3%**. These are Amdahl admission ceilings, not predicted speedups. If no route/model, no isolated time, or ceiling <3%, terminate `NO_Q3_ROUTE`, `NO_EXPOSED_COST` or `BELOW_CEILING` without building a candidate. Do not queue overlapping RAD06 lanes.

**Gate 1 — one isolated candidate only if Gate 0 passes.** Use the existing llama.cpp patch-package convention to port only #30517's `GGML_TYPE_Q3_K` `VDR=2`, Q3 packed scale/high-mask integer-dot and required signature changes into `vecdotq.cuh`; retain upstream stock `mmvq.cu` dispatch, RDNA row geometry and other quant types. If the helper signature change requires changing non-Q3 call sites, fail closed; do not smuggle Q2_K/Q6_K or generic row-tiling into the patch. Verify clean b11552 composition after 0600/0650/1274, exact one-site anchors, idempotence, fallback, no default-on switch and forced geometry controls. Use existing patch validation/contract and test-backend-ops producers; no new allocator, scheduler, telemetry subsystem or global dispatch table.

**Gate 2 — correctness before timing.** Packed Q3 vectors must include all 6-bit signed scales, every low/high-mask pattern, 32-bit signed integer overflow guards, F16 block scales including negative/subnormal/extreme finite values, Q8_1 signed activations and zero blocks, K tails and rows crossing workgroup boundaries. Run baseline and candidate `test-backend-ops` Q3_K MUL_MAT width1 and width2/3/4/5/8 with exact expected output count, bounded error vs stock/CPU and full-vocabulary logits/KLD/greedy/MTP acceptance; **do not require impossible bit identity**, but record first divergent op and predeclare tolerances. Repeat same-process requests, ubatch changes, 8K/80K contexts, graph capture/replay/rebind and cancellation. Test negative controls Q2_K/Q6_K/Q4_K/Q8_0, MoE `MUL_MAT_ID`, prefill MMQ, forced-autotune, gfx1030 and unrelated RAD06 helper. Reject `NUMERIC_DRIFT`, `MISSING_WORK`, `GRAPH_LIFETIME_FAIL`, or `WRONG_ROUTE`.

**Gate 3 — hardware promotion only after prior gates.** Compare same pinned baseline versus isolated Q3_K VDR2 on gfx1100 and gfx1201 independently; start single GPU to avoid no-P2P PCIe/AR/rank-skew confounds, then use a separately eligible dual-XTX control if warranted. Dense width1 `tg128/tg512`, widths2/4/5 MTP verify, pp512 unchanged control; record exact Q3_K kernel, Q8_1 conversion, total critical-path wall, bytes, VGPR/SGPR/spills, occupancy, graph nodes, clocks and energy. >=4 independent sessions/architecture, >=10 paired balanced rounds/session, CI95-low >=3% E2E on a **declared eligible route**, <=1% unaffected controls, no material logits/KLD/acceptance drift or missing physical work. If not, `NO_GAIN`/ `REGRESSION`; retain stock. A pure kernel microbenchmark win cannot promote a production default.
