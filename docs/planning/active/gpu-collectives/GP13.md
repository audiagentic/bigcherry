# Brutus kernel PCIe P2P DMA quirk for dual-XTX: patch, build, and boot on ROCm-validated 7.0.13 line

## Description

Brutus's two 7900 XTX GPUs (0000:03:00.0, 0000:06:00.0, sitting under Alder Lake PEG-bifurcated root ports 0000:00:01.0/00:01.1) reported no PCIe P2P DMA capability (`hipDeviceCanAccessPeer` == 0 for all pairs) under the stock kernel, because the generic in-tree p2pdma host-bridge whitelist rejects this platform. This work adds a narrowly-scoped kernel quirk that permits P2P specifically between those two GPUs (by exact PCI vendor/device ID + BDF + root-port ancestry) without loosening policy for the other two GPUs on the box (R9700 at 09:00.0, RX 6900 XT at 17:00.0), then gets that kernel safely built and booted on a shared, live dev/production box.

Result: P2P DMA is now live between the two XTXs only. Measured direct P2P bandwidth ~10.4 GB/s vs ~6.85 GB/s host-staged (~1.5x at steady state, up to 12x at small transfer sizes where staging overhead dominates). This changes the ceiling RCCL/HIP collectives between the two XTXs can hit, and is directly relevant to the GP11 native/bc-rccl/bc-hybrid dispatch comparisons -- those were all measured under the host-staged ceiling; re-running that comparison and the mtp-dual order-effect discriminator on this kernel is recommended follow-up.

## Steps

1. Patch `drivers/pci/p2pdma.c`: add `brutus_xtx_endpoint_match()` (exact vendor 0x1002 + device 0x744c + domain/bus/devfn match on both endpoints) and `brutus_xtx_p2pdma_quirk()` (root-port ancestry walk requiring both endpoints under 0000:00:01.0/00:01.1), gated into the `map_through_host_bridge` fallback in `calc_map_type_and_dist()`.
2. First patch draft (v1) matched only on root-port ancestry, not endpoint identity -- would have silently widened to any device pair under those root ports on any similar-topology machine. Caught by external GPT review; fixed in v2 by adding the endpoint-identity check before the ancestry walk.
3. v2 review also flagged a doc-comment placement bug (the diff deleted the original `calc_map_type_and_dist()` doc comment instead of preserving it below the new helper) and an overclaim in the new comment ("cannot widen on any other machine" -- untrue, it's topology-based not host-identity-based). Fixed in v3.
4. Built against a `7.3-rc1` mainline snapshot first (tree was already at that HEAD). Full kernel build succeeded, but a second independent GPT research request flagged this as unsafe for live use: the exact build predated AMD's `amd-drm-fixes-7.3-2026-09-03` (MES/GPUVM/KFD queue-reset fixes), ROCm 7.14 is only officially validated against kernel `7.0`, and there was no P2P-subsystem reason to need 7.3 at all (the 7.3 PCI merge barely touched p2pdma.c). Decision: abandon the 7.3-rc1 boot, backport the same patch onto `v7.0.13` instead (fetched as a tag from the separate linux-stable tree, since torvalds/linux mainline doesn't carry stable point-release tags). Patch applied cleanly with zero drift.
5. Root filesystem was at 7.9GB free / 99% full on Brutus -- blocked any build. Root cause was NOT the kernel tree; `/var/lib/containerd` held 297GB of Docker image layers with zero live containers referencing them (many old vLLM/ROCm images, tens of GB each). `docker image prune -a` reclaimed 36GB net (179GB free after), touching only unreferenced images -- verified every live production container (llama-swap, grafana, prometheus, samba, netdata, bigcherry-toolchest, etc.) first.
6. Build environment gaps hit and fixed: missing `libdw-dev` (needed by `scripts/gendwarfksyms`, unrelated to our patch) -- installed via apt. Config copied from the running kernel referenced Ubuntu-specific cert paths (`debian/canonical-certs.pem`) that don't exist in a vanilla source tree -- cleared `CONFIG_SYSTEM_TRUSTED_KEYS`/`CONFIG_SYSTEM_REVOCATION_KEYS` (safe since Secure Boot is disabled on this box).
7. First boot attempt of the patched 7.0.13 kernel failed: out-of-memory during early boot, kernel panic, fell back to the original kernel (GRUB fallback + physical console access worked as designed). Root cause: `make modules_install` doesn't replicate Ubuntu's packaging step of stripping debug info into a separate dbgsym package, so modules were installed with full embedded DWARF5+BTF debug info (`CONFIG_DEBUG_INFO=y` was present in the shipped .config). Modules dir was 8.4GB vs 165MB stock; initramfs was 651MB vs ~78-82MB for every other installed kernel, and unpacking that into early-boot RAM OOM'd. Fixed by stripping debug info from every installed `.ko` (`strip --strip-debug`) and recompressing with zstd (module dir dropped to 146MB), then regenerating the initramfs (dropped to 81.5MB, in line with the other kernels). Second boot succeeded cleanly.
8. Before the reboot, un-hid the GRUB menu (`GRUB_TIMEOUT_STYLE=menu`, `GRUB_TIMEOUT=10`, was previously hidden with 0s timeout) so a fallback kernel is actually selectable at the physical keyboard -- this is what let the first failed boot recover cleanly. Confirmed physical keyboard access to Brutus before proceeding with any reboot.
9. Post-boot validation: `rocm-smi` clean (all 4 GPUs healthy, sane temps/power), no amdgpu/KFD errors in dmesg, then `hipDeviceCanAccessPeer` across all 4x3=12 directed device pairs -- only 0<->1 (the two XTXs) show P2P access, everything touching the R9700 or 6900 XT remains 0, confirming the endpoint-identity scoping holds correctly on real hardware.
10. Wrote and ran a P2P bandwidth microbenchmark (`hipMemcpy` direct vs host-staged, 1MB-1GB transfer sizes): ~10.4 GB/s direct vs ~6.85 GB/s staged at steady state (~1.5x), up to 12x at 1MB transfers.

CORRECTION (2026-09-05): the P2P bandwidth numbers originally reported in this item's description/steps (10.4 GB/s direct vs 6.85 GB/s host-staged, ~1.5x-12x) are RETRACTED. They came from `/tmp/p2p_bw.cpp`, which used the same uncorrectness-checked "pull" configuration (current device = destination) that GP11 independently found silently returns zeros/garbage on this hardware class. Re-ran with GP11's own validated diagnostic (`/tmp/p2p_bwval.cpp`, already staged on Brutus) against the current kernel: confirmed bit-for-bit reproduction of the same corruption -- 262144/262144 elements wrong, first element 0.000 instead of 3.000, in the pull direction; the mirrored push-direction copy (current device = source) is correct.

Re-measured with a new correctness-validated push-mode benchmark (`/tmp/p2p_bw_push.cpp`, per-element checked every run, all sizes report bad=0):
- 1MB: push-p2p=5.83 GB/s, host-staged=4.07 GB/s, speedup=1.43x
- 16MB: 6.78 vs 4.89 GB/s, 1.39x
- 64MB: 6.80 vs 5.08 GB/s, 1.34x
- 256MB: 6.80 vs 5.06 GB/s, 1.34x
- 1GB: 6.44 vs 6.26 GB/s, 1.03x (essentially parity)

So the real, validated finding is a modest 1.3-1.4x P2P advantage at small/medium transfer sizes that shrinks to near-parity at 1GB, NOT the previously claimed 1.5x-12x range. This independently corroborates GP11's closed finding (see cross-reference below) on a different code path: GP11 tested kernel-side peer stores/loads for its N=3 internal AllReduce and found host staging wins outright by 8-31% once corrected, because the bifurcated x8/x8 CPU lanes let host staging drive both links concurrently near full Gen4 x8 line rate while P2P must hairpin through the Alder Lake root complex. This item's plain hipMemcpy DMA-engine push copies retain a smaller real edge at sub-256MB sizes rather than GP11's outright loss, but the same structural cause (bifurcated dual-link host staging closing the gap as size grows) is visible in both datasets.

CROSS-REFERENCE -- GP11 P2P AllReduce investigation (bigcherry repo, independent of this Brutus kernel-patch track): GP11 built a standalone N=3 internal AllReduce and found (1) kernel-side direct P2P loads are non-functional on gfx1100/ROCm/PCIe-switch config despite hipDeviceCanAccessPeer=1 (pulls silently return zero -- same posted-write/non-posted-read split as this item's retracted number), (2) peer-directed writes need HSA_DISABLE_CACHE=1 or hipDeviceMallocUncached to flush reliably (__threadfence_system does not emit the needed L2 writeback on gfx1100), (3) even once correct, host staging wins by 8-31% across 8 sizes because of the same bifurcated x8/x8 dual-link effect measured above. GP11's verdict: "P2P closed on measured grounds" for the internal AllReduce use case. This item's kernel kernel-quirk work (enabling P2P DMA mapping at all, which GP11 assumed/required as a precondition) remains valid and independently useful, but the original inflated bandwidth claim that motivated re-running GP11's RCCL/hybrid dispatch comparisons under this kernel should NOT be used to justify that follow-up -- the real, corrected number does not change the GP11 conclusion.
