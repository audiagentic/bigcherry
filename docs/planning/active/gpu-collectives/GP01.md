# RCCL Phase 2: topology-aware qualification/tuning/replay for the RCCL-viable device subset

## Description

Re-homed from docs/planning/active/hip-collectives/HI156.md (superseded there, full content preserved) into a dedicated multi-GPU plan group so this box's multi-GPU/RCCL work is contained in one place rather than spread across hip-collectives.

HI138 (docs/planning/completed/hip-collectives/HI138.md, closed 2026-08-29, Outcome B) definitively established that RCCL AllReduce is viable and crash-free for any tensor-split topology on Brutus EXCLUDING physical device 3 (the RX 6900XT, permanently limited to META by a real, non-fixable hardware constraint -- its chipset-routed PCIe root port has no AtomicOps completion capability). Confirmed empirically (20/20 reps): {0,1}, {0,2}, {1,2}, {0,1,2} all pass RCCL cleanly, including the real heterogeneous XTX+R9700 (gfx1100+gfx1201) pair.

Why this matters: HI18's own evidence shows RCCL is ~40x faster than META on the validated homogeneous pair. The same speed advantage should be available for the R9700-inclusive heterogeneous/3-GPU subset ({0,2}, {1,2}, {0,1,2}) once qualified -- this is real, uncaptured wall-clock-reduction opportunity for any workload that can avoid device 3.

## Steps

Per HI138's own Phase 2 procedure (P2.1-P2.11, referenced in docs/reference/testing/RCCL_HETEROGENEOUS_RUNBOOK.md):
1. Define the candidate schema and qualification key for the RCCL-viable subset (topology identity must exclude device 3 by construction -- never attempt to re-qualify device 3, that question is permanently closed by HI138).
2. Crash-isolated qualification per topology: {0,1} (homogeneous control, already known-good via HI18), {0,2}, {1,2} (heterogeneous 2-GPU), {0,1,2} (heterogeneous 3-GPU).
3. Reuse tools/bigcherry/profiling/rccl_qualify.py (already built and tested, RQ01-RQ03 landed commit 6b360a5, hardened by GP07) for the crash-isolated harness.
4. Bind qualification result to the same portable topology-identity contract HI138 established (topology_id + device_arches only -- no ordinal/BDF/UUID/hostname), plus GP07's RCCLCompatibilityRevision.
5. Once qualified, wire into production selection (alongside GP03's consolidated dispatch) so the R9700-inclusive subset actually uses RCCL in real serving rather than always falling back to META.
6. ACTIVE-TUNING TRACK (added 2026-09-02 per gpt-dev-agent review, operator direction to 'improve RCCL where it is currently supported', not just extend coverage): for each qualified (revision, topology), benchmark RCCL's own DEFAULT plan against its controllable algorithm/protocol candidates (RCCL_OVERRIDE_ALGO/PROTO -- GP07's rccl_qualify.py already supports requesting these; channels/chunk-size only if the exact pinned RCCL build genuinely exposes a verified, observable control, not invented from another RCCL/NCCL version's API surface, per the runbook's own P2.2 rule). Any microbenchmark-level winner over RCCL's default MUST be re-verified through GP08's full end-to-end OPTIMIZE comparison before being treated as a real win -- a microbenchmark improvement that doesn't survive full-stack measurement is not a promotable result. If no candidate beats RCCL's own default for a given (revision, topology), record that explicitly and keep RCCL's default as the winner -- a negative result here is a real, useful finding, not a gap to keep re-chasing.
