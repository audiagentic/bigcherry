# Pin MTP head tensors to a single GPU via --override-tensor to avoid cross-GPU AllReduce on the draft path

## Description

Qwen3.8-27B's MTP (multi-token prediction) head is loaded as a native, same-file MTP head (mparams.load_mtp=true in common_model_params_to_llama, common/common.cpp:1714), not a separate draft model. Traced common_speculative_init_result's MTP init path (common/speculative.cpp ~2555-2599): it reuses the SAME mparams built from the top-level params for the MTP context, so params.speculative.draft.devices (--spec-draft-device/-devd/--device-draft) and --spec-draft-ngl/-ngld are never read on this path (confirmed via grep -- zero references in speculative.cpp). Those flags only affect the classic separate-draft-model case (Eagle/dflash-style, a distinct gguf). Net effect: the MTP head currently inherits the main model's tensor-split placement across both GPUs by default, meaning its forward pass pays the same cross-GPU AllReduce cost every decode step that GP03's profiling found consumes ~9.6% of decode wall time -- and MTP's own repeated small forward passes (once per decode step, to produce draft tokens) are exactly the small/frequent/latency-sensitive collective profile that cost is concentrated in.

MTP/NextN tensors have a distinct, addressable naming pattern in llama-arch.cpp:569-576: top-level nextn.pre_projection/nextn.post_projection, and per-block blk.%d.nextn.{eh_proj,embed_tokens,enorm,hnorm,shared_head_head,shared_head_norm}. llama.cpp already has a real, existing mechanism for per-tensor buffer-type placement independent of the main tensor-split: --override-tensor/-ot "<tensor name pattern>=<buffer type>" (common/arg.cpp:2776-2780), which populates params.tensor_buft_overrides and is honored by common_model_params_to_llama regardless of MTP's shared-mparams path (since it's applied at the same model-load call, not a separate draft-specific path). This should let us pin the entire MTP head to one GPU's buffer type (e.g. -ot "nextn\\..*=CUDA0") while the main model stays tensor-split across both GPUs -- eliminating cross-GPU AllReduce specifically for MTP's own forward passes, without touching main-model throughput.

## Notes

Raised by operator 2026-09-02 while GP11's root_kernel race investigation (gpt-dev-agent) was in flight -- explicitly scoped as a parallel, independent experiment to run while waiting, not a blocker on GP11. Code-path analysis (not yet hardware-validated) done same day: common/speculative.cpp:2565-2593, common/common.cpp:1680-1717, common/arg.cpp:2776-2780, src/llama-arch.cpp:569-576.

Real hardware test (2026-09-02): baseline (MTP tensor-split, no override) ran clean via bigcherry.bench.server_completion against the mtp-27b-v1 corpus (48 real requests): predicted_tps mean=68.20/median=67.63, draft_acceptance mean=0.5874/median=0.5812. This is the number any pinning attempt needs to beat.

Pinned attempt (-ot "nextn\\..*=ROCm0", -sm tensor, otherwise identical launch) CRASHED on model load:
  ggml-backend.cpp:940: pre-allocated tensor (blk.64.nextn.eh_proj.weight) in a buffer (ROCm0) that cannot run the operation (NONE)
The override DID apply (the tensor landed on ROCm0 as requested), but broke an assumption in SPLIT_MODE_TENSOR's graph construction -- llm-arch.cpp classifies NEXTN_EH_PROJ etc. as LLM_TENSOR_LAYER_REPEATING, and the tensor-split graph builder apparently expects those tensors to stay consistent with whatever per-layer split scheme it computes, not be independently pinned to a single device via a blanket buffer-type override. Forcing just those tensors onto one device left a downstream op (view/reshape, shown as op type NONE) with a backend mismatch, and ggml_abort() fired at load time.

This is a real, informative negative result for the NAIVE override approach -- not a dead end for the underlying idea, but it means simply appending -ot won't work with -sm tensor; it would need either (a) a different split mode where nextn tensors aren't graph-coupled to the main split scheme, or (b) a real code change in the tensor-split graph builder to treat NEXTN/MTP tensors as a genuinely independent subgraph that's allowed its own device placement (i.e., real patch work, not a CLI-only experiment as originally scoped).

Next step before further investment: check whether -sm layer (row-split) or -sm none (single-GPU main model) tolerate the same -ot override without crashing -- would at least confirm whether the crash is SPLIT_MODE_TENSOR-specific or general. If it's SPLIT_MODE_TENSOR-specific, that's consistent with GP03's own established real production config (tensor-split is the production-recommended split mode for this box), meaning a real fix would need actual llama.cpp graph-builder changes, elevating this from GP12's original S/low-risk CLI-only scope to real patch-level work -- worth flagging to the user before continuing rather than silently expanding scope.
