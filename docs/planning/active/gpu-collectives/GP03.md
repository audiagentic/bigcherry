# Size-adaptive internal/RCCL AllReduce provider dispatch -- eliminate the pp regression

## Description

1001_hip_internal_allreduce (validated 2026-08-31) enables an internal, non-RCCL AllReduce path on HIP that is a real, large win for decode (+17.33% TPS on MTP completion-bench, +6.88% t/s on plain tg128 llama-bench, both dual RX 7900 XTX gfx1100) but a severe regression for prefill (-32% to -34% t/s on pp512/pp2048/pp4096, same hardware, same tensor-split config).

GOAL, CONFIRMED (2026-09-02): isolate pp (prefill) from the regression via per-call provider dispatch, keeping tg's real win -- NOT rewriting internal's own copy-engine algorithm (that was briefly explored as a stretch goal, then correctly redirected back to the original, simpler scope).

SOURCE ARCHAEOLOGY DONE (2026-09-02): the per-call dispatch mechanism needed for this ALREADY EXISTS in ggml-cuda.cu and is ALREADY COMPILED into production builds. `ggml_backend_cuda_comm_allreduce_tensor()` (the real per-tensor entry point, wired to the backend's set_tensor_async hook) already calls `ggml_backend_cuda_comm_try_reduce_plan(comm_ctx, tensors, requested_provider)` EVERY reduction, where requested_provider comes from `ggml_backend_cuda_comm_reduce_plan()`. That function already understands three plan values per call: "auto" (use whatever comm_ctx->try_allreduce was set to at session init -- i.e. GGML_CUDA_ALLREDUCE's choice), "rccl" (force RCCL for just this call, regardless of the committed provider), "meta" (decline, let the butterfly/META path handle it). This whole mechanism is gated behind the GGML_HIP_DISPATCH compile flag, which is automatically ON whenever GGML_HIP_AUTOTUNE is ON (confirmed via CMakeCache.txt on a real production build) -- i.e. it is live in the bigcherry/bigcherry-native builds already being shipped and tested, not dead/experimental code.

THE ACTUAL GAP: `ggml_backend_cuda_comm_reduce_plan()` (ggml-cuda.cu ~line 1316) currently just reads a static env var (GGML_HIP_REDUCE_PLAN) and returns the same value on every call -- it has no access to the tensor/reduction size and makes no size-based decision. This is a small, surgical fix, not new plumbing: thread the tensor byte-size through to this function (it's already available in ggml_backend_cuda_comm_allreduce_tensor's `tensors` argument) and have it return "rccl" above a crossover threshold, "auto" below it.

## Steps

1. Confirm the exact crossover point with a finer llama-bench sweep if needed (pp512 already shows -33.66% with internal, tg128 already shows +6.88% -- the byte-size gap between these is large, likely a wide safe zone for the threshold, but confirm before committing to a specific default).
2. Patch ggml_backend_cuda_comm_reduce_plan() (ggml-cuda.cu) to accept the reduction's byte size (available via the tensors array already passed to its caller, ggml_backend_cuda_comm_allreduce_tensor) and return "rccl" when size exceeds a threshold (env-overridable, e.g. GGML_HIP_REDUCE_RCCL_THRESHOLD, matching this project's existing GGML_CUDA_AR_COPY_THRESHOLD/GGML_CUDA_AR_BF16_THRESHOLD naming convention), "auto" otherwise.
3. Set GGML_CUDA_ALLREDUCE=internal as the committed base provider in the runtime profile that adopts this (so "auto" resolves to the fast decode path); the new per-call rccl override handles prefill.
4. Build as a new BigCherry patch (source lives at ggml/src/ggml-cuda/ggml-cuda.cu, in the existing patch numbering scheme near 0830_split_reduce_telemetry / 1001_hip_internal_allreduce).
5. Validate with the same 3-arm-plus methodology already used for 1001: correctness via the HI18 SPLIT_REDUCE probe, performance via paired completion-bench (decode, should retain ~+17%) AND llama-bench pp512/pp2048/pp4096 (prefill, should now match RCCL-only's numbers, not internal-only's regressed ones) -- confirm no regression anywhere across the full size range, not just at the two previously-tested extremes.
6. Only then consider promoting into a production runtime-profile.

IMPLEMENTED AND VALIDATED on Brutus (2026-09-02).

Root cause chain found during implementation:
1. Wrote the size-adaptive per-call dispatch (ggml_backend_cuda_comm_reduce_plan(nbytes) threshold on GGML_HIP_REDUCE_RCCL_THRESHOLD, default 256KB; ggml_backend_cuda_comm_try_reduce_plan() rccl branch uses a secondary ncclCommInitAll() brought up alongside the internal ar_pipeline in ggml_backend_cuda_comm_init_internal()) in ggml-cuda.cu -- this logic was correct from the start (confirmed via debug fprintf: nbytes/threshold/decision computed correctly, rccl branch reached correctly).
2. First real validation showed the rccl branch's guard always failing: comms.size()=0 despite backends.size()=2, so every "rccl" decision silently fell through and produced no measurable change.
3. Root cause: the private scratch source tree used for this work never had patch 1001_hip_internal_allreduce applied. ggml_cuda_ar_pipeline_init() has two implementations in allreduce.cu -- a real CUDA one and a stub gated by `#if !defined(GGML_USE_HIP) && !defined(GGML_USE_MUSA)` that unconditionally returns nullptr on HIP. Patch 1001 flips that guard to `#if !defined(GGML_USE_MUSA)` plus maps pinned-host-memory APIs and swaps __nanosleep for __builtin_amdgcn_s_sleep(4) in vendors/hip.h. Without it, GGML_CUDA_ALLREDUCE=internal was silently falling back to the meta-backend butterfly path the whole session -- so my added secondary-NCCL-init code (inside the `if (ret->ar_pipeline)` branch) never executed at all.
4. Applied patch 1001's exact edits to the scratch tree, rebuilt, reran. Fixed immediately: ar_pipeline_init now returns non-null, secondary ncclCommInitAll succeeds (rc=0, comms.size()=2), rccl branch's guard passes.

Validated real numbers (2x RX 7900 XTX, HIP_VISIBLE_DEVICES=0,1, GGML_CUDA_ALLREDUCE=internal, GGML_CUDA_AR_BF16_THRESHOLD=0, -sm tensor -fa on -b 2048 -ub 512, r=3) vs. patch 1001's own SUMMARY.md baselines:

| metric | RCCL baseline | internal-only baseline | GP03 dispatch |
|---|---|---|---|
| pp512 | 1504.67 | 998.21 (-33.7%) | 1502.49 (matches RCCL) |
| pp2048 | 1447.58 | 980.64 (-32.3%) | 1451.17 (matches RCCL) |
| pp4096 | 1431.77 | 972.08 (-32.1%) | 1435.27 (matches RCCL) |
| tg128 | 33.69 | 36.01 (+6.9%) | 37.23 (+10.5%, decode win preserved and slightly improved) |

pp regression eliminated; tg decode win retained. Goal achieved exactly as scoped (per-call provider dispatch, not an internal-algorithm rewrite).

- Heterogeneous-topology validation (2026-09-02): tested beyond the {0,1} pair the fix was validated on.

- {1,2} (7900 XTX + R9700): clean, no crash. pp512=1283.78, tg32=30.46.
- {0,3} (7900 XTX + 6900XT, device 3 = the HI138-excluded chipset-routed GPU): CRASHES. GP03's secondary ncclCommInitAll() succeeds at init time (rc=0, comms.size()=2) -- it has no HI138/device-3 awareness -- so the rccl-branch guard passes, and the first pp-sized reduction hard-aborts inside ggml_backend_cuda_comm_allreduce_nccl (GGML_ASSERT/ggml_cuda_error), identical failure mode to raw GGML_CUDA_ALLREDUCE=nccl on this topology. This is NOT a safe fallback -- it's a hard crash, worse than doing nothing, on any topology that includes device 3.

Implication: GP03's patch MUST NOT ship without wiring in the device-3 guard from patch 1225 (GP02's scope) first, or GP03 needs to consume GP01's qualified-topology list directly and refuse to bring up the secondary NCCL communicator (fall back to internal/butterfly instead) whenever device 3 is in the active device set. Recorded here as a hard blocking dependency: GP03 must not be packaged/shipped independently of GP02's guard landing, or without GP03 itself checking topology before calling ncclCommInitAll a second time.
