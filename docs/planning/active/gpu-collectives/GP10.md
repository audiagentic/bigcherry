# Base-level (sub-llama.cpp) collective testing harness -- fast iteration on transforms without a full model/build cycle

## Description

Per explicit operator direction (2026-09-02): 'we should build tooling that allows us to test this at base level rather than always going through llamacpp or bc to validate and test - that way we can quickly assert failure or success - test out other transforms or methods to improve on base or our own.'

Today, testing a candidate collective mechanism (a new algorithm/protocol choice, a chunking strategy, the hierarchical bridge idea in GP09, an RCCL rebuild) requires either (a) rccl_qualify.py driving raw all_reduce_perf directly -- fast, but only tests RCCL's OWN candidates (algorithm/protocol/channels), not a genuinely different transform BigCherry might invent, or (b) building a full patched llama.cpp binary and running llama-bench/completion-bench -- correct as final validation, but slow (full rebuild cycle) and conflates the transform's own real cost with the full inference stack's overhead, making it hard to cheaply iterate on a transform idea before committing to a real patch.

This item closes that gap: a base-level harness that can run a candidate reduction TRANSFORM (not just RCCL algorithm/protocol selection) directly against real GPU memory -- a minimal hipMalloc + transfer + reduce + verify loop, independent of both RCCL Tests' own binary and llama.cpp's full build -- so a candidate like GP09's pinned-host bridge idea can be measured for its own real latency/bandwidth cost in isolation, in seconds not a rebuild cycle, before any decision to wire it into ggml-cuda.cu at all.

## Steps

1. Survey what already exists before building anything new: rccl_qualify.py (drives real all_reduce_perf, RCCL's own candidates only), the standalone hipMalloc+ncclAllReduce reproducer mentioned in GP05's investigation trail (real, already built once this session for a different purpose -- check if it's still on Brutus or needs rebuilding), patches/1001_hip_internal_allreduce's own pinned-host pipeline (a real, working example of a non-RCCL transform already in the tree to use as a design reference).
2. Define a minimal harness contract: given a transform function (Python-callable or a small compiled C++/HIP binary this tool drives), a topology, and a data size/pattern, run it directly against real GPU memory and report correctness (vs. an independent reference) + real latency/bandwidth -- no model, no llama.cpp, no full BigCherry build required.
3. Support at minimum: (a) raw RCCL candidates (delegate to existing rccl_qualify.py machinery, don't reimplement), (b) a pinned-host-copy transform (the GP09 bridge idea's core primitive, and patch 1001's own mechanism), (c) a slot for a genuinely new candidate transform without requiring this tool's own code to change for each new idea -- a plugin/callback shape, not a hardcoded list.
4. Wire GP09's first real candidate (the hierarchical bridge's pinned-host hop) through this harness as its first real use case.
5. Document clearly where this fits relative to GP07 (RCCL-candidate qualification) and GP08 (full-stack optimize/benchmark) -- this is the FAST, CHEAP, EARLY-ITERATION tier; GP07/GP08 remain the tiers that gate real production decisions. A pass here is encouraging, not sufficient, evidence -- final validation still goes through GP08's full-stack comparison against the required baselines.
