# Device-3 / PCI-atomics-incapable topology: safe AND performant fallback investigation (go/no-go against META)

## Description

Per explicit operator direction (2026-09-02): the aim for PCI-limited topologies (currently: any group including physical device 3, the RX 6900XT, whose chipset-routed PCIe root port lacks AtomicOps completion capability per HI138) is not merely to fail SAFELY (already true today -- these topologies fall back to META) but to find a fallback that is also PERFORMANT -- faster than META/layer-split for that exact topology. If no such mechanism can be found, that is a legitimate, documented negative result, not a gap to keep chasing; META/layer-split remains the shipped path for device-3-inclusive topologies in that case.

Explicit success/failure bar (operator's own words): 'if its slower than layer split or meta then we have failed in that scenario.' A candidate mechanism only ships if real hardware measurement shows it beats META (and beats -sm layer, if that's ever a live comparison for this topology) for the actual topology it targets. No candidate ships on correctness/safety alone.

Candidate mechanisms to investigate, in order of estimated cost/value (per gpt-dev-agent's earlier deep-dive research, this session's earlier RCCL-alternatives investigation):

1. Hierarchical safe-subset bridge (gpt's top recommendation): device 3's contribution crosses the slow PCH-routed link exactly once each direction via a pinned-host D2H/H2D hop into/out of the RCCL-safe subset (e.g. {0,1,2}), with the fast RCCL-safe subset handling the actual collective. Device 3 never joins the RCCL communicator or launches an RCCL kernel at all -- avoids the hostcall/AtomicOps requirement entirely by construction, not by working around it.
2. RCCL 2.27.7 hostcall-free rebuild: independently-reported evidence that an older RCCL build (NDEBUG, older device-build path) can produce hidden_hostcall_buffer==0 on gfx1030, structurally avoiding the ROCclr AQL dispatch rejection HI138 identified -- reported working on gfx1100 hardware by that source, NOT yet hardware-tested on gfx1030 by anyone. Cheap to test (structural check of the linked kernel metadata, then a real {0,3} qualification run) relative to (1)'s implementation cost -- worth ruling in/out FIRST before investing in (1).
3. Plain pinned-host N-way reduction for ANY topology size (not just device-3-specific) -- Gloo's CUDA-unavailable design as a reference (copy to pinned host, reduce on host, copy back), simpler and more general than patch 1001's existing 2-device-only internal pipeline, could serve device-3 topologies of any size where (1) doesn't apply cleanly.

Do not build a full patch for any of these before proving the mechanism's real performance advantage at the base level (GP10) first -- this item's validation gate is real hardware numbers, not code review.

## Steps

1. Test candidate 2 first (cheapest): verify structurally whether an RCCL 2.27.7 rebuild on this box's toolchain actually produces hidden_hostcall_buffer==0 for gfx1030 (llvm-readobj --notes AMDGPU_METADATA, same technique HI138 used). If it does, run a real {0,3} qualification through GP07's hardened rccl_qualify.py -- PASS or FAIL is definitive and cheap either way.
2. If candidate 2 fails (hostcall requirement persists, or the rebuild doesn't apply cleanly to this ROCm version): prototype candidate 1 (hierarchical bridge) at the BASE level (GP10's tooling, not full llama.cpp) first -- measure the D2H/H2D pinned-host hop's real latency/bandwidth cost in isolation before wiring it into ggml-cuda.cu at all.
3. Only once a candidate shows real promise at the base level: implement it as an actual BigCherry patch, validate via GP08's OPTIMIZE tool against the required baselines (native llama.cpp RCCL, META/layer-split) for the {0,3} (and {0,1,3}, {0,1,2,3} if relevant) topology specifically.
4. If no candidate beats META for a given device-3-inclusive topology: close this item for that topology with a documented negative result (real numbers, not just 'we tried') -- META/layer-split remains authoritative there. Do not ship a slower-but-safe alternative.
