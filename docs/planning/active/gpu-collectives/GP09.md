# Device-3 / PCI-atomics-incapable topology: safe AND performant fallback investigation (go/no-go against META)

## Description

Per explicit operator direction (2026-09-02): the aim for PCI-limited topologies (currently: any group including physical device 3, the RX 6900XT, whose chipset-routed PCIe root port lacks AtomicOps completion capability per HI138) is not merely to fail SAFELY (already true today -- these topologies fall back to META) but to find a fallback that is also PERFORMANT -- faster than META/layer-split for that exact topology. If no such mechanism can be found, that is a legitimate, documented negative result, not a gap to keep chasing; META/layer-split remains the shipped path for device-3-inclusive topologies in that case.

Explicit success/failure bar (operator's own words): 'if its slower than layer split or meta then we have failed in that scenario.' A candidate mechanism only ships if real hardware measurement shows it beats META (and beats -sm layer, if that's ever a live comparison for this topology) for the actual topology it targets. No candidate ships on correctness/safety alone.

EXECUTION ORDER vs. EXPECTED PERFORMANCE PRIORITY (clarified 2026-09-02 per gpt-dev-agent review -- these are two different orderings, do not conflate them):
- Execution order (cheapest/fastest-to-rule-in-or-out first): (1) RCCL 2.27.7 structural + real probe, (2) hierarchical bridge, (3) general pinned-host N-way.
- Expected fallback-performance priority (which is actually likely to WIN if all three turn out feasible): the hierarchical bridge is the most deliberately-designed-for-this-exact-constraint candidate and should be treated as the real target; general pinned-host N-way is the last resort; RCCL 2.27.7 is a cheap, high-uncertainty probe -- test it first because it's cheap, NOT because it's expected to be fastest. A structural PASS on 2.27.7 does not by itself imply speed: the underlying failure HI138 localized is a hostcall/AtomicOps ADMISSION check, not proof the real data path is fast once admitted -- device 3's PCIe link is still the same bandwidth-limited chipset-routed path either way. Do not skip the 2.27.7 probe because of this -- it's cheap enough to run regardless -- but do not assume structural success implies it will clear the performance bar either; measure it.

{0,3} SPECIAL CASE (clarified 2026-09-02): for exactly this pair, the 'RCCL-safe subset' the hierarchical bridge would bridge INTO is just device 0 alone (a single GPU) -- there is no multi-GPU RCCL subset collective to run for {0,3} specifically. The bridge degenerates to: device 3 does its local reduction contribution, transfers it via pinned host to device 0, device 0 combines locally, transfers the result back. This is a real, valid mechanism (worth measuring), but it is architecturally different from the {0,1,3}/{0,1,2,3} case where the bridge target actually is a multi-GPU RCCL-safe subset -- treat {0,3} as its own measured case, don't assume the {0,1,3} bridge design transfers unchanged.

Candidate mechanisms:

1. RCCL 2.27.7 hostcall-free rebuild: independently-reported evidence that an older RCCL build (NDEBUG, older device-build path) can produce hidden_hostcall_buffer==0 on gfx1030, structurally avoiding the ROCclr AQL dispatch rejection HI138 identified -- reported working on gfx1100 hardware by that source, NOT yet hardware-tested on gfx1030 by anyone. Cheapest to test.
2. Hierarchical safe-subset bridge: device 3's contribution crosses the slow PCH-routed link exactly once each direction via a pinned-host D2H/H2D hop into/out of the RCCL-safe subset, with the fast RCCL-safe subset (or, for {0,3} specifically, a single other GPU) handling the actual combination. Device 3 never joins an RCCL communicator or launches an RCCL kernel at all -- avoids the hostcall/AtomicOps requirement entirely by construction, not by working around it. Most likely real winner if RCCL 2.27.7 doesn't pan out.
3. Plain pinned-host N-way reduction for ANY topology size -- Gloo's CUDA-unavailable design as a reference, simpler and more general than patch 1001's existing 2-device-only internal pipeline. Last resort.

Do not build a full patch for any of these before proving the mechanism's real performance advantage at the base level (GP10) first -- this item's validation gate is real hardware numbers, not code review.

## Steps

1. Test candidate 1 (RCCL 2.27.7) first (cheapest, execution-order-first -- NOT because it's expected fastest, see performance-priority note above): verify structurally whether an RCCL 2.27.7 rebuild on this box's toolchain actually produces hidden_hostcall_buffer==0 for gfx1030 (llvm-readobj --notes AMDGPU_METADATA, same technique HI138 used). If it does, run a real {0,3} qualification through GP07's hardened rccl_qualify.py, AND immediately measure its real latency/bandwidth (not just pass/fail) -- a structural+crash-free PASS that's still slower than META fails this item's bar just as much as a crash does.
2. Regardless of (1)'s outcome, prototype candidate 2 (hierarchical bridge) at the BASE level (GP10's tooling, not full llama.cpp) -- measure the D2H/H2D pinned-host hop's real latency/bandwidth cost in isolation. Test {0,3}'s single-GPU-target degenerate case separately from any {0,1,3}/{0,1,2,3} multi-GPU-subset case.
3. Only once a candidate shows real promise at the base level: implement it as an actual BigCherry patch, validate via GP08's OPTIMIZE tool against the required baselines (native llama.cpp RCCL where applicable, META/layer-split) for the specific topology it targets.
4. If no candidate beats META for a given device-3-inclusive topology: close this item for that topology with a documented negative result (real numbers, not just 'we tried') -- META/layer-split remains authoritative there. Do not ship a slower-but-safe alternative.
