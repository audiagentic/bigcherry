# Generalize the internal AllReduce pipeline beyond n_devices==2 (N-way ring/tree)

## Description

Patch 1001_hip_internal_allreduce's pinned-host-memory AllReduce pipeline (`ggml_cuda_ar_pipeline_init` in allreduce.cu) hard-rejects anything but exactly 2 devices:

```cpp
if (n_devices != 2) {
    GGML_LOG_DEBUG("internal AllReduce only supports n_devices=2 (got %zu); falling back\n", n_devices);
    return nullptr;
}
```

This is a real algorithmic constraint, not an oversight: the pipeline is a direct pairwise scheme -- two GPUs ping-pong through a pinned host-mapped buffer with a device-side spin-wait/signal handshake between exactly rank 0 and rank 1. It was originally an upstream PR (#27825) designed specifically as a low-latency 2-GPU optimization, not a general N-way ring or tree reduction.

Consequence, confirmed on real hardware (2026-09-02, GP03 3-GPU validation): GGML_CUDA_ALLREDUCE=hybrid (patch 0840, GP03's consolidated dispatch) correctly falls through to pure RCCL for any 3+ device topology, since `have_internal` is always false there -- {0,1,2} numbers on real hardware tracked native RCCL almost exactly (pp512 1322.92 vs 1327.99, tg128 35.91 vs 35.87), confirming the fallback itself is correct and safe, but it also means hybrid's whole per-call decode-side win (the +3.9% to +51% improvement validated on {0,1}) is currently UNAVAILABLE for any qualified 3+ device topology (GP01's {0,1,2} subset, once GP06/GP02 unblock it for production use). The decode-side benefit that makes hybrid worth shipping on 2 GPUs is simply not present at all above 2 GPUs today.

This item is to design and implement a real N-way variant of the internal pipeline's pairwise scheme (ring topology with N pinned buffers and a matching handshake protocol, or a tree reduction), so hybrid's decode-side win can extend to GP01's qualified 3-GPU subset -- not a dispatch fix, real algorithm work.

## Steps

GP10 harness result (2026-09-02): the naive star-pattern N-way extension of patch 1001's pairwise mechanism scales roughly linearly in N-1 (real hardware, {0,1}->{0,1,2}: +68% to +79% latency) -- a structural property of every-rank-reads-every-peer, not an artifact of the harness's minimal (1-block, unvectorized) kernel. Do not implement the star extension.

Candidate designs to try next, cheapest/most-informative first (2026-09-02, expanded per operator direction after reviewing alternatives):
1. Reduce-to-root + broadcast: designate one rank as root; each of the other N-1 ranks does exactly one pairwise handshake with the root only (not with each other) -- reuses 1001's proven pairwise mechanism almost unchanged, just applied N-1 times from a common root. Root's handshakes with different peers can run on independent per-peer streams concurrently rather than ring's forced sequential N-1 stages, so this may beat ring's latency for small N (3-4 devices) despite moving the same total data. Cheapest next experiment -- try this BEFORE ring since it reuses more of the already-proven code.
2. Ring: each rank passes its partial sum to exactly one neighbor per step, N-1 steps, O(1) peer-interaction cost per rank per step. Try if (1) doesn't show a good result, or as a direct comparison once (1) has real numbers.
3. Binary/binomial tree: log2(N) levels instead of N-1 steps -- doesn't really differ from (1)/(2) until N > ~4-5, which is outside this box's real topology space (GP01 qualifies up to {0,1,2} only). Low priority, do only if N grows in a future topology.
4. Diagnostic prerequisite for interpreting any of the above: isolate WHERE 1001's real +17% tg win over RCCL at N=2 actually comes from -- avoiding RCCL's per-call launch/setup overhead on small latency-sensitive messages (a fixed cost, which any low-hop-count N-way design should preserve), vs more efficient PCIe path use (a bandwidth-scaling cost, where RCCL's own ring may already be close to optimal at N=3). Cheap to check in the harness (compare per-call fixed overhead component directly) and materially changes which of 1-3 is worth pursuing.
5. Legitimate negative-result exit: if the root-reduce experiment also shows unfavorable scaling once the diagnostic in (4) is understood, close this item with a documented real-numbers negative result rather than forcing a design to work -- same discipline GP09/GP01's active-tuning track already applied this session.

RACE FIXED AND CONFIRMED (2026-09-02, round 3). gpt-dev-agent root-caused the intermittent root_kernel correctness failure to a real, concrete bug in the harness's mapped-pointer setup (not a fence/ordering race): hipHostGetDevicePointer() was called ONCE for the peer-pointer table and arrival array, with whichever device happened to be current at that point in main() (the last device from the earlier per-device alloc loop) -- that single alias was then shared across every rank's kernel launch on every device. HIP does not guarantee a device-pointer alias resolved under one device's context is valid when dereferenced by a DIFFERENT device's kernel. This exactly matched the observed pattern: aliases resolved under device 2's context -> root=2 always clean; root=0 (furthest from device 2) showed the rare failures.

Fix applied: resolve a SEPARATE alias table per CONSUMING device (loop over every device, hipSetDevice to it, resolve hipHostGetDevicePointer for the arrival array AND for every peer's stage buffer under THAT device's context, store in a real device-side array via hipMalloc+hipMemcpy). Also hardened both leaf and root signal paths with a second __threadfence_system() immediately after ar_signal_set() (matching production allreduce.cu's exact protocol), per gpt's recommendation, though gpt assessed this as unlikely to have been the actual cause.

Stress validation post-fix: 3000/3000 reps clean (500 reps x 2 batches x 3 roots, {0,1,2}, 2621440 F32 elements, the exact config that previously failed ~1/270). Zero failures. The fused reduce-to-root+broadcast design is now CORRECTNESS-CONFIRMED and can move to optimization/production consideration.

### Feasibility of widening the ncols_dst==1 gate -- source-verified

Both caveats raised above are now resolved against the pinned source.

**Caveat 2 (do fused instantiations exist for ncols>1?) -- NO, and it is a
hard stop, not just a predicate.** mmvq.cu:861-872,
`mul_mat_vec_q_switch_fusion`:

```cpp
if constexpr (c_ncols_dst == 1) {
    if (has_fusion) { ... launch mul_mat_vec_q<type, c_ncols_dst, true, ...>; return; }
}
GGML_ASSERT(!has_fusion && "fusion only supported for ncols_dst=1");
```

The fused template is instantiated only inside `if constexpr (c_ncols_dst ==
1)`, so for ncols>1 it is never emitted at all, backed by a runtime assert.
Widening therefore needs new instantiations (compile-time and code-size cost),
not just an eligibility-predicate edit.

**Caveat 1 (is the gate correctness or conservatism?) -- CONSERVATISM.** The
fused kernel body is already written generically over ncols_dst:

```cpp
float x_biases[ncols_dst]    = { 0.0f };
float gate_biases[ncols_dst] = { 0.0f };
...
for (int j = 0; j < ncols_dst; ++j) {
    x_biases[j] = x_bias[j * stride_col_dst + threadIdx.x];
}
```

Bias/gate-bias prefetch, the per-column accumulation, and the GLU combine
(`switch (active_glu)`) all sit inside `for (int j = 0; j < ncols_dst; ++j)`
loops, and the kernel's own comment reads "Block: (warp_size, ncols_dst) --
each warp handles one token independently." There is no single-column
assumption in the arithmetic.

**Consequence:** the change is plausible and bounded -- drop the `if constexpr
(c_ncols_dst == 1)` guard, relax the assert, and widen the two host-side
eligibility predicates (ggml-cuda.cu:1774-1777 MMVF and 1804-1807 MMVQ) from
`!= 1` to a small-ncols allowance. The real costs are template instantiation
count and the correctness validation upstream evidently did not want to own.

**Still NOT established (do not skip before implementing):**
* whether the host-side fusion-args plumbing (`ggml_cuda_mm_fusion_args_*`,
  and the gate tensor's own shape/stride expectations in
  `ggml_cuda_should_fuse_mul_mat_vec_q`'s callers) is equally ncols-generic --
  only the device kernel has been read;
* the compile-time/code-size delta from the extra instantiations, which on this
  project's build times is a real cost to measure, not assume;
* whether bigcherry's own 0200_dispatch_hook / 0650_mmvq_native_variant layers
  interact with the fusion path at ncols>1 (they converge on the same native
  `ggml_cuda_mul_mat_vec_q` seam, per RD09's notes);
* any numerical difference versus the unfused path at ncols>1 -- fusion
  changes accumulation/rounding structure, so the gate is
  tolerance-comparison, not bit-identity.

## reframes several plan items at once

While sizing RD09/RD12 from the decode trace, the MMVQ kernel template

| dispatches | shape | has_fusion |
|---|---|---|
| 112,110 (91%) | ncols=6 | **false** |
| 7,848 | ncols=1 | false |

Root cause found in upstream source, vendor/llama.cpp/ggml/src/ggml-cuda/

and the identical gate at 1774-1777 for the MMVF path.

This workload runs at **ncols_dst == 6** because MTP speculative decoding
verifies spec_draft_n_max=5 drafted tokens + 1. Multiple independent
optimizations in this codebase are hard-gated to ncols_dst == 1 and are
therefore **structurally disabled on 91% of decode work**:

* upstream MUL_MAT+GLU fusion (the gate quoted above);
* RD33's activation-quantization bypass (its own gate is `ncols_dst == 1`) --
  this is the already-recorded explanation for RD33's null result, and it is
  the SAME root cause, not a coincidence.

That single pattern also explains, without further hypothesis:
* why the trace shows `quantize_q8_1 -> MMVQ -> quantize_q8_1 -> MMVQ` for
  every one of the 20,561 same-shape MMVQ pairs, rather than one fused op;
* why 30,500 separate `unary_gated_op_kernel` dispatches (38.2ms) exist at all
  -- the SwiGLU that fusion would have absorbed;
* why 7,345 of those pairs are immediately followed by `unary_gated_op_kernel`
  (FFN gate/up, the textbook fusable shape).

### Note the kernel itself is not the blocker

`has_fusion` is a template parameter of the MMVQ kernel, and the fused code

restriction is in the ELIGIBILITY predicate, not the compute. Whether
instantiations exist for (ncols>1, has_fusion=true) needs checking in
`mul_mat_vec_q_switch_fusion` (mmvq.cu:849) before assuming a gate relaxation
is cheap -- if the instantiations are absent, this becomes a template/codegen
size question as well as a correctness one.

Rather than treating RD09 / RD12 / RD33 as three separate candidates, the
highest-value question is a single one: **can the ncols_dst==1 gates be safely
widened to the small-ncols range that MTP speculative decode actually
produces (n_max+1, i.e. 5-6 today, and a tunable)?** That one change would
unblock fusion and RD33 simultaneously, and would reduce dispatch count -- the
demonstrated bottleneck -- rather than making individual kernels faster.

## 2026-09-04 (final): P2P is SOLVABLE but LOSES -- plus two real optimization leads

Research pass (gpt-dev-agent req_cea35a9e3b4f440a + web research + hardware

### Correction: the mid-kernel flush problem is a known HIP gap, and fixable

AMD's own HIP documentation states __threadfence_system() requires an L2

hipDeviceMallocUncached) -- added as the --uncached flag. This is NOT the same
as hipDeviceMallocFinegrained, which was tested earlier and does not help.
With --uncached and no global env var, p2p-push is fully correct at every size.

|---|---|---|---|

## 2026-09-04 (later): P2P failure ROOT-CAUSED -- and the 10.4 GB/s finding retracted

The earlier entry concluded "kernel-side P2P doesn't work, treat as SDMA-only."
That was directionally right but the stated mechanism was wrong, and it missed a
second, independent blocker. Full diagnosis run on brutus (0<->1) with six
standalone HIP programs, now preserved under
tools/lab/gp10-collective-harness/p2p-diagnostics/ with a README.

Critically, the new p2p_diag.cpp adds a **local-read control arm** the original
probe lacked -- it passes, so the harness itself is sound and the failures are real.

### Finding 1: pull operations silently return zeros; pushes work

| Operation | Result |
|---|---|
| local read (control) | OK |
| kernel peer read, either direction | 0.000 |
| kernel peer WRITE | correct, validated exact to 67 MB, scalar and float4 |
| hipMemcpyPeer, both directions | all zeros, all sizes |
| hipMemcpy D2D/Default, current device = DESTINATION | all zeros |
| hipMemcpy D2D/Default, current device = SOURCE | correct |

This is the classic PCIe split -- posted writes traverse the path, non-posted
reads needing a completion round-trip do not. It is precisely why NCCL/RCCL are
architected around pushing into remote buffers rather than pulling from them.
gpt-dev-agent's recommended design (peer reads) had the data flow backwards.
The coarse-vs-fine-grain hypothesis was a red herring: fine-grain memory under
HSA_FORCE_FINE_GRAIN_PCIE=1 fails identically, because grain was never the issue.

### Finding 2 (decisive): peer writes don't drain until the writing kernel retires

Implemented the correct NCCL-style push design as --mode p2p-push (write payload
into the peer's exchange buffer, signal a flag in peer VRAM after a fence --
posted writes to the same target stay ordered -- spin on our OWN local flag,
then reduce from two local operands). It deadlocks.

Root cause, isolated in p2p_spin.cpp: a kernel spinning on a flag NEVER observes
a peer write issued by a concurrently-resident kernel on the other GPU.
2,000,000 iterations each of sys-scope acquire load, system-scope atomic RMW,
non-temporal load, volatile load, and fence-then-load all failed; a host readback
immediately after the writer retired saw the value. The atomic-RMW arm is what
makes this conclusive -- an RMW cannot be served from a stale cache line, so the
data is genuinely not in the destination's memory yet. **This is a writer-side
flush problem, not a reader-side cache-coherency problem**, and
__threadfence_system() does not flush peer-directed writes here. (An earlier
L2-staleness hypothesis was tested in p2p_coh.cpp and disproved: a kernel
launched after the writer completes sees the write with any load flavour.)

### Retraction: the "10.4 GB/s P2P (1.5x host-staged)" number is INVALID

The separate agent's /tmp/p2p_bw.cpp performs no correctness validation and uses
the pull configuration (current device = destination). Re-running its exact
configuration with validation added (p2p_bwval.cpp): 262144/262144 elements
wrong, all zeros. It was timing a copy that transferred nothing -- which is also
why it looked fast. The same copy with the current device set to the source is
correct. Any GP11 reasoning that leaned on that 1.5x figure should be discarded.

### Conclusion for GP11 (unchanged verdict, now properly evidenced)

Either finding alone is fatal to a low-latency P2P collective here. Together
they rule out any single-kernel fine-grained handshake between these two GPUs,
pull-based or push-based. P2P could only work as push-kernel -> kernel boundary
-> reduce-kernel, whose launch and sync overhead exceeds the entire theoretical
saving at decode message sizes. The production pinned-host-memory design works
precisely BECAUSE host-memory writes are immediately visible to the peer -- this
is now a positively-justified design choice, not just the incumbent.

### Safety note (worth carrying beyond GP11)

The silent-zero behaviour on pulls is a genuine data-corruption hazard on this
machine: a device-to-device copy between GPUs 0 and 1 issued with the
destination device current returns zeros and reports success, with no error and
no fault. RCCL currently selects SHM transport for this pair so production paths
are unaffected today, but any future change enabling a D2D or hipMemcpyPeer path
between these GPUs would corrupt silently. Recorded in the diagnostics README.

## 2026-09-04: P2P-direct-load kernel prototype -- CONCLUSIVE NEGATIVE RESULT

Context: a separate concurrent agent session enabled real hipDeviceCanAccessPeer=1
between the two RX 7900 XTXs (GPU0<->GPU1) on brutus via a kernel/BIOS change
(custom kernel, two reboots). Raw hipMemcpy P2P bandwidth confirmed at 10.4 GB/s
direct vs 6.85 GB/s host-staged. RCCL itself does NOT use this (RCCL 2.27.7 caps
Intel x86 P2P eligibility at PATH_PXB; this topology classifies PATH_PHB -> SHM
fallback, confirmed via NCCL_DEBUG=INFO, gpt-dev-agent req_9d9d432819ae46f3).

Built tools/lab/gp10-collective-harness/p2p_direct_allreduce.cpp (commit
252960f8) to prototype gpt's recommended design: replace bigcherry's internal
AllReduce PAYLOAD staging (patches 1001/1244) with a direct kernel-side load
from the peer GPU's raw device pointer, keeping the existing pinned-host
arrival-token handshake for signaling only. --mode host (reproduces production
design) validated correct. --mode p2p (direct peer dereference) failed
correctness deterministically on every size/rep: remote contribution reads
back as exactly zero (input[0][i], not corrupted noise) -- e.g. rank0 got
-0.223167 == its own local input[0][0], want 0.260546 (0.483713 peer
contribution silently dropped).

Escalated to gpt-dev-agent (req_877e043460c94bd8) for a deep dive. Diagnosis:
ROCm's own kernel-side P2P tests (RCCL's p2p_latency_test) allocate the
peer-visible buffer with hipExtMallocWithFlags(..., hipDeviceMallocFinegrained)
under HSA_FORCE_FINE_GRAIN_PCIE=1, not plain coarse-grain hipMalloc -- so the
failure might be a coarse-memory peer-visibility/coherency gap rather than
total kernel-P2P failure on this stack. Recommended discriminator matrix
before building any fallback design.

Implemented gpt's discriminators in the same harness: --mode probe-coarse /
probe-fine (minimal <<<1,1>>> out[0]=peer[0] kernel, no handshake, no
vectorization, peer element overwritten with a fresh sentinel via host
hipMemcpy immediately before every rep so each result classifies as
current/stale/zero/other) and --peer-order enable-first|alloc-first (rules out
a peer-enable-timing/mapping-order runtime bug). Ran on real hardware (brutus,
0<->1):

- Arm A (coarse, enable-first): 20/20 reps class=zero.
- Arm C (coarse, alloc-first -- peer buffer allocated BEFORE
  hipDeviceEnablePeerAccess): 20/20 reps class=zero. Rules out allocation
  order as the cause.
- Arm B (fine-grain, hipExtMallocWithFlags(hipDeviceMallocFinegrained),
  HSA_FORCE_FINE_GRAIN_PCIE=1 set): 20/20 reps class=zero. Identical failure
  even under gpt's exact recommended fine-grain/env-var repro.

Per gpt's own interpretation guide ("both fail while hipMemcpyPeer passes =>
treat as effectively SDMA-only despite the HIP capability report"): this is
conclusive. **Kernel-side (compute-shader) direct P2P loads do not work on
this box** -- coarse or fine-grain memory, either peer-access ordering --
despite hipDeviceCanAccessPeer=1 and working hipMemcpy-based P2P (DMA engine
transfers are fine; direct pointer dereference from a running kernel reads
back zero). Root mechanism unconfirmed (likely an IOMMU/ACS-passthrough gap
for this device pair given they sit behind a PCIe switch/riser splitting the
CPU's lanes, each device in a separate IOMMU group -- DMA-engine copies go
through driver-managed IOMMU-mapped transfers regardless, but raw in-kernel
peer addressing may need IOMMU passthrough/ACS override this box doesn't have
for this pair; not verified further since it's moot for the design decision).

**Decision: do not pursue a P2P-direct-load kernel design for bigcollective's
internal AllReduce.** The only remaining P2P avenue per gpt's fallback
guidance is hipMemcpyPeerAsync into a local staging buffer + local add kernel
(a new arm, not yet built) -- but gpt's own numbers (6.85->10.4 GB/s implies
only ~1.5/3.0/6.0us ideal savings at 30/60/120KB) make this marginal at best
for typical decode message sizes, and copy-submission/sync overhead could
easily consume the whole saving below ~120KB. Not pursued further under GP11;
if revisited, scope as a separate small spike, not a GP11 blocker.
