# Generalize the internal AllReduce pipeline beyond n_devices==2 (N-way ring/tree)

## Description

Patch 1001_hip_internal_allreduce's pinned-host-memory AllReduce pipeline (`ggml_cuda_ar_pipeline_init` in allreduce.cu) hard-rejects anything but exactly 2 devices:

```cpp
if (n_devices != 2) {
    GGML_LOG_DEBUG("internal AllReduce only supports n_devices=2 (got %zu); falling back\n", n_devices);
    return nullptr;
}
```

This is a real algorithmic constraint, not an oversight: the pipeline is a direct pairwise scheme -- two GPUs ping-pong through a pinned host-mapped buffer with a device-side spin-wait/signal handshake between exactly rank 0 and rank 1. It was originally an upstream PR (#27825) designed specifically as a low-latency 2-GPU optimization, not a general N-way ring or tree reduction.

Consequence, confirmed on real hardware (2026-09-02, GP03 3-GPU validation): GGML_CUDA_ALLREDUCE=hybrid (patch 0840, GP03's consolidated dispatch) correctly falls through to pure RCCL for any 3+ device topology, since `have_internal` is always false there -- {0,1,2} numbers on real hardware tracked native RCCL almost exactly (pp512 1322.92 vs 1327.99, tg128 35.91 vs 35.87), confirming the fallback itself is correct and safe, but it also means hybrid's whole per-call decode-side win (the +3.9% to +51% improvement validated on {0,1}) is currently UNAVAILABLE for any qualified 3+ device topology (GP01's {0,1,2} subset, once GP06/GP02 unblock it for production use). The decode-side benefit that makes hybrid worth shipping on 2 GPUs is simply not present at all above 2 GPUs today.

This item is to design and implement a real N-way variant of the internal pipeline's pairwise scheme (ring topology with N pinned buffers and a matching handshake protocol, or a tree reduction), so hybrid's decode-side win can extend to GP01's qualified 3-GPU subset -- not a dispatch fix, real algorithm work.

## Steps

GP10 harness result (2026-09-02): the naive star-pattern N-way extension of patch 1001's pairwise mechanism scales roughly linearly in N-1 (real hardware, {0,1}->{0,1,2}: +68% to +79% latency) -- a structural property of every-rank-reads-every-peer, not an artifact of the harness's minimal (1-block, unvectorized) kernel. Do not implement the star extension.

Candidate designs to try next, cheapest/most-informative first (2026-09-02, expanded per operator direction after reviewing alternatives):
1. Reduce-to-root + broadcast: designate one rank as root; each of the other N-1 ranks does exactly one pairwise handshake with the root only (not with each other) -- reuses 1001's proven pairwise mechanism almost unchanged, just applied N-1 times from a common root. Root's handshakes with different peers can run on independent per-peer streams concurrently rather than ring's forced sequential N-1 stages, so this may beat ring's latency for small N (3-4 devices) despite moving the same total data. Cheapest next experiment -- try this BEFORE ring since it reuses more of the already-proven code.
2. Ring: each rank passes its partial sum to exactly one neighbor per step, N-1 steps, O(1) peer-interaction cost per rank per step. Try if (1) doesn't show a good result, or as a direct comparison once (1) has real numbers.
3. Binary/binomial tree: log2(N) levels instead of N-1 steps -- doesn't really differ from (1)/(2) until N > ~4-5, which is outside this box's real topology space (GP01 qualifies up to {0,1,2} only). Low priority, do only if N grows in a future topology.
4. Diagnostic prerequisite for interpreting any of the above: isolate WHERE 1001's real +17% tg win over RCCL at N=2 actually comes from -- avoiding RCCL's per-call launch/setup overhead on small latency-sensitive messages (a fixed cost, which any low-hop-count N-way design should preserve), vs more efficient PCIe path use (a bandwidth-scaling cost, where RCCL's own ring may already be close to optimal at N=3). Cheap to check in the harness (compare per-call fixed overhead component directly) and materially changes which of 1-3 is worth pursuing.
5. Legitimate negative-result exit: if the root-reduce experiment also shows unfavorable scaling once the diagnostic in (4) is understood, close this item with a documented real-numbers negative result rather than forcing a design to work -- same discipline GP09/GP01's active-tuning track already applied this session.

## Notes

Not currently blocking anything -- GP01's {0,1,2} qualification and GP03's consolidated dispatch both already degrade safely to pure RCCL for 3+ devices today (confirmed on real hardware, no bug). This item exists to capture a real, quantified opportunity cost (hybrid's proven decode win is unavailable above 2 GPUs), not to fix a defect. Depends on GP01 (3-GPU subset must be qualified/production-safe first) and benefits from GP10 (base-level harness) for cheap go/no-go before committing to the full implementation -- same discipline GP09 applies to its own candidate mechanisms.

GP10's harness (tools/lab/gp10-collective-harness/nway_star_allreduce.cpp) produced a real, cheap first signal (2026-09-02) that changes this item's recommended design BEFORE any full implementation: a direct star-pattern generalization of patch 1001's pairwise mechanism (every rank spins on and reads all N-1 peers) scales roughly linearly in N-1 (real hardware: +68% to +79% going from N=2 to N=3 at production-realistic sizes, on {0,1}/{0,1,2}). Patch 1001's real production win over RCCL at N=2 was already a modest +17% tg -- a mechanism whose overhead grows linearly in N-1 is likely to lose that margin by N=3 regardless of kernel-level optimization (multi-block vectorization, matching production's real 1001 kernel), since this is a structural property of the star topology, not an implementation gap this harness's simplicity introduced.

Recommendation before committing to a full ggml-cuda.cu implementation: do NOT implement the direct star/all-to-all N-way extension. Next real step is to add a RING-topology variant to the same GP10 harness (each rank passes its partial sum to exactly one neighbor per step, N-1 steps total, O(1) peer-interaction cost per rank per step rather than O(N-1)) and get a real go/no-go signal on THAT design before writing any production patch. This is the same cheap-iteration discipline GP10 exists for -- do not skip straight to a full implementation on the strength of the star result alone (it was never the recommended design, just the simplest one to test first).

2026-09-02 round 2 (post gpt review): fixed two real bugs reviewer-gpt-agent found in the star harness (arrival slots weren't actually cache-line-separated -- ARRIVAL_STRIDE_INTS was defined but unused; correctness was only checked on rank 0's warmup rep). Added --blocks (production-shaped 8-block grid, matching GGML_CUDA_AR_KERNEL_BLOCKS) and float4 vectorized copies. Implemented dev-gpt-agent's recommended fused reduce-to-root+broadcast design (one kernel launch per rank, root reduces and republishes for leaves to read -- no independent concurrent root streams, since root's reads from every leaf cross its own single PCIe endpoint regardless of stream count, per gpt's PCIe-topology correction).

CORRECTED star results (8-block, vectorized, {0,1}->{0,1,2}, real hardware): far better than the original naive-kernel numbers suggested. 30720 elem: N=2 62.44us (RCCL: 61.9us, essentially TIED), N=3 101.20us (RCCL: 87.8us, only +15%). 2621440 elem: N=2 3592.75us (RCCL: 1432.0us, 2.5x), N=3 7036.81us (RCCL: 3671.0us, 1.9x). The N=2->N=3 relative scaling is still present (+62% small, +96% large) but the absolute picture is now much more competitive than the naive kernel implied -- gpt's caution that 'do not conclude star is unfixably bad from a naive kernel' was correct and material.

ROOT mode results (8-block, vectorized, N=3, real hardware): 30720 elem, root=0(XTX): 114.08us; root=2(R9700): 100.52us. 2621440 elem, root=2: 5253.49us (beats star's 7036.81us, still behind RCCL's 3671.0us). root=0 large-size: 8438us AND one correctness failure (max_abs_err=2.78) on the very first run out of ~270 total reps observed across repeated stress runs at that exact config (0 failures in the following ~265 reps) -- a real, rare, intermittent race, same category/severity class as GP06's Tree+LL finding (passes almost always, fails occasionally under real repeated use). NOT yet root-caused. Root choice matters: R9700-as-root (root=2) is faster than XTX-as-root (root=0) at large size, plausibly because concentrating reads on the R9700's PCIe link vs the busier XTX0 link differs -- worth the --root sweep gpt recommended.

Open items before this could ever be considered for production: (1) root-cause and fix the intermittent correctness race (rate ~1/270 reps at N=3/root=0/large-size) -- do not productionize on top of an unexplained rare correctness fault, full stop; (2) run gpt's recommended dense size-sweep (4B..1MB) with alpha/beta (fixed-overhead vs bandwidth) decomposition plus a signal-only floor measurement, to determine whether 1001's real N=2 production win is a fixed-overhead story (favors root, which this data already looks consistent with at small sizes) or a bandwidth story (favors segmented multi-root, per gpt's fallback design); (3) segmented multi-root candidate (gpt's stronger bandwidth-oriented fallback, described in GP11's steps) not yet implemented -- try only if root shows a large-size bandwidth ceiling after (2); (4) real production-realism check: this harness's numbers are raw collective time only, not the real end-to-end call overhead RCCL pays in the actual llama.cpp dispatch path (patch 1001's own +17% N=2 win included avoiding that overhead) -- GP08's full-stack OPTIMIZE comparison is still the only tier that can confirm a real win, this harness stays encouraging-not-sufficient evidence per its own charter.

Given the still-open correctness question, do NOT implement this as a production patch yet. Next real step is root-causing the intermittent race before any further latency optimization work.

RACE FIXED AND CONFIRMED (2026-09-02, round 3). gpt-dev-agent root-caused the intermittent root_kernel correctness failure to a real, concrete bug in the harness's mapped-pointer setup (not a fence/ordering race): hipHostGetDevicePointer() was called ONCE for the peer-pointer table and arrival array, with whichever device happened to be current at that point in main() (the last device from the earlier per-device alloc loop) -- that single alias was then shared across every rank's kernel launch on every device. HIP does not guarantee a device-pointer alias resolved under one device's context is valid when dereferenced by a DIFFERENT device's kernel. This exactly matched the observed pattern: aliases resolved under device 2's context -> root=2 always clean; root=0 (furthest from device 2) showed the rare failures.

Fix applied: resolve a SEPARATE alias table per CONSUMING device (loop over every device, hipSetDevice to it, resolve hipHostGetDevicePointer for the arrival array AND for every peer's stage buffer under THAT device's context, store in a real device-side array via hipMalloc+hipMemcpy). Also hardened both leaf and root signal paths with a second __threadfence_system() immediately after ar_signal_set() (matching production allreduce.cu's exact protocol), per gpt's recommendation, though gpt assessed this as unlikely to have been the actual cause.

Stress validation post-fix: 3000/3000 reps clean (500 reps x 2 batches x 3 roots, {0,1,2}, 2621440 F32 elements, the exact config that previously failed ~1/270). Zero failures. The fused reduce-to-root+broadcast design is now CORRECTNESS-CONFIRMED and can move to optimization/production consideration.

Current best numbers (8-block, vectorized, real hardware): root=2(R9700) large-size 5269-5280us (vs RCCL's 3671us, 1.4x behind); root=0/1(XTX) large-size ~8400-8740us (worse than root=2 -- R9700-as-root benefits from being the least loaded PCIe endpoint). Small/decode-realistic size (30720 elem) not yet re-measured against the fixed+hardened kernel -- do that next, it's the size that matters most for the real production use case.

gpt also provided a concrete N=3 optimization (independent float4 loads of both leaf buffers before summing, rather than the current serial dependent-add loop, to let both PCIe reads be outstanding simultaneously) and cautioned against chasing large-size (10MB) bandwidth as the primary success criterion -- production's own real pinned-host AllReduce already loses to RCCL by ~32-34% at large/prefill sizes and is meant to be size-dispatched back to RCCL there (same as patch 1001's real design); the decode-realistic small-size numbers are what should decide GP11's actual go/no-go.

Next steps: (1) re-run the small-size (30720 elem) sweep against the fixed+hardened root_kernel and star_kernel to get the real decision-relevant numbers; (2) apply gpt's N=3 independent-load optimization; (3) only then move toward GP08's full-stack OPTIMIZE validation if the small-size numbers look competitive.
