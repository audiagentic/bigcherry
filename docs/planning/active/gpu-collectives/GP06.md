# RCCL 2.30.4 regression: HI138/GP01-confirmed-viable {0,2} pair crashes -- pin/qualify exact RCCL version before GP01 Phase 2

## Description

HI138 (closed 2026-08-29, Outcome B) confirmed 20/20 real-hardware repetitions that RCCL is viable and crash-free for {0,1}, {0,2}, {1,2}, {0,1,2} (any topology excluding physical device 3, the RX 6900XT) using RCCL rebuilt from ROCm/rccl commit 57e58688 (reports as RCCL 2.28.3).

Real hardware finding, 2026-09-02 (this session, independent of GP04/GP05's investigation): testing the same {0,2} pair (XTX + R9700, gfx1100+gfx1201) against RCCL 2.30.4 (this box's /home/audumla/rocm-7.14 install, the RCCL version used for this session's other HI18 work) CRASHES -- same failure class HI138 already characterized (RCCL communicator hard-aborts). Re-tested against RCCL 1.0.70204 (/opt/rocm-7.2.4, and the newly-created vendor/rocm/7.2.4-merged -- see TO01) with a fully self-consistent toolchain (compiler+RCCL from the same install, ruling out an ABI-mismatch confound): {0,2} PASSES cleanly (valid=True, correct=True via the HI18 SPLIT_REDUCE probe), matching HI138's original result. {0,3} and {2,3} (both including device 3) FAIL on both RCCL versions, consistent with HI138's root cause (device 3's chipset-routed PCH root port lacks PCIe AtomicOps capability -- an RCCL-version-independent hardware limitation).

So: HI138's Phase 1 closure and GP01's planned Phase 2 qualification were both established/scoped against RCCL 2.28.3-era builds. This box's newer default RCCL (2.30.4) appears to have REGRESSED the {0,2}/{1,2} viability HI138 confirmed -- a real, version-specific finding neither HI138 nor GP01 anticipated.

## Steps

1. Confirm the regression is real and repeatable: run HI138's own P1.12 gate (20 fresh-process repetitions) for {0,2} and {1,2} against RCCL 2.30.4, not just the single confirming run done this session.
2. Bisect or diff RCCL 2.28.3 vs 2.30.4 (both real, available builds on Brutus: /opt/rocm-7.2.4 vs /home/audumla/rocm-7.14) for the source-level change that reintroduced the failure -- likely somewhere in generic-kernel/hostcall-metadata generation, per HI138's own root-cause mechanism.
3. Update GP01's qualification scope to pin an exact RCCL version (RCCLCompatibilityRevision per RCCL_HETEROGENEOUS_RUNBOOK.md P2.1) rather than assuming any RCCL build on this box behaves identically -- Phase 2 must qualify against the SAME RCCL revision that will actually ship, not just 'RCCL' as an unversioned concept.
4. Decide: pin bigcherry's default RCCL to the known-good 2.28.3-era build (vendor/rocm/7.2.4, now also available as vendor/rocm/7.2.4-merged with a working compiler+RCCL combo), or investigate/fix whatever regressed in 2.30.4 if the newer version is otherwise preferred.
