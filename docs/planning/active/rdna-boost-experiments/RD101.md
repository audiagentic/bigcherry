# Evaluate BridgeSpec (kdheeraj-p/bridgespec) -- HIP MTP/DFlash speculative decoding sidecars + gfx1100 MMVQ tuning

## Description

External research project surfaced 2026-08-27, worth an initial evaluation: https://github.com/kdheeraj-p/bridgespec -- 'Experimental AMD RDNA3 speculative decoding for llama.cpp: HIP MTP and DFlash drafter sidecars, tooling for generated sliced vocabulary heads, and tuned small-batch MMVQ kernels for gfx1100.' MIT licensed, research-preview status, validated on Windows 11 + one RX 7900 XTX + ROCm 7.2 + Qwen3.8-27B -- directly overlapping our own hardware/model target (gfx1100, Qwen3.8-27B family) and problem space (this session's own HI130 dual-XTX MTP tuning work).

What it claims: a C sidecar ABI that moves the serial MTP/DFlash drafter out of llama-server into a separate HIP process (external KV state, host-mediated, not zero-copy interop), plus its own gfx1100 MMVQ tuning for verification widths 2-8, plus tooling to generate a sliced 40,960-row draft vocabulary head + deterministic full-vocabulary ID remap from user-supplied models. Reports a controlled local A/B (Vulkan MTP control vs Vulkan target + HIP MTP: 104.5 vs 106.9 code tok/s, 117.7 vs 120.7 agentic-edit tok/s) and a higher, less-controlled 'development high-water' HIP DFlash result (146.0 tok/s agentic-edit, 95.5% acceptance, explicitly flagged as not representative of production-wide throughput).

Author is notably careful about evidence quality: explicitly separates 'controlled local A/B' from 'development high-water', flags workload/cache/context/acceptance sensitivity, states the repo does NOT include raw per-request logs or a public benchmark harness (so cross-machine reproducibility is not claimed), and warns against co-residing two 27B profiles on a 24GB card due to silent shared-memory-spill throughput loss (no OOM error) -- a real, specific operational gotcha worth checking against our own dual-XTX/R9700 memory-budget work (HI130's runtime-profile VRAM preflight).
