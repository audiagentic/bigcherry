# Q4_K MMVQ wide-load / x4 activation / VDR candidate family (AMD #84 + #88 as one experiment)

## Description

One bounded experiment family (NOT two items) covering the Q4_K MMVQ structural work demonstrated by AMD-Ecosystem PR #84 (1b600a34d0f6, open: RADV-inspired Q4_K vec_dot, block_q8_1_x4 activation layout, 128-bit weight + activation loads, 4x K-loop unroll, sched_group_barrier, Q4_K-specific lower nwarps; ~4.4% kernel-time reduction on a major Gemma-4 FFN decode shape) and PR #88 (0c92c50b57dc, open: widen Q4_K MMVQ weight ownership so one thread owns a 32-byte Q4_K group via two global_load_b128-friendly loads, VDR=8; typical ~1-2% decode gain). The parameters interact; evaluate them as one family with ablations.

Hypothesis: for Q4_K MMVQ decode on gfx1100/gfx1201, one or more of {A x4 q8_1 activation packing, B 128-bit Q4_K weight loads, C 128-bit activation loads, D VDR=8/wider per-thread ownership, E 4x K-loop unroll, F sched_group_barrier, G Q4_K-specific nwarps} improves memory-level parallelism or reduces load overhead. Do NOT assume the gfx1151 winning combination is the gfx1100/gfx1201 winner.

CRITICAL NUMERICAL CONTRACT (the #84 lesson is load-bearing): an x4 activation producer must be inseparable from a matching consumer -- AMD's first x4 implementation stored the wrong scale/sum semantic for the Q4_K minimum term, looked mostly correct, and failed only intermittently/data-dependently. Every candidate must pass direct backend correctness across many seeds, long K, repeated same-seed runs, with machine-readable max abs/rel error, BEFORE any performance result is considered.

Relationship to RD08 (Q6_K VDR=2, materialized as patch 1204): useful precedent for containing a quant-specific MMVQ candidate; do NOT merge Q4_K work into RD08.
