# HIP peer-to-peer copy corruption on Windows/RDNA4 (from RD74 fork investigation)

## Description

Filed from RD74's closure (fork investigation of MrLordCat/llama.cpp-rdna-lab, 2026-08-20). While the fork was testing RD74's ORIGINAL hypothesis (pinned host staging -- which it REJECTED with real negative data), the investigation surfaced a different, genuinely useful finding: HIP peer-to-peer copy corrupts data on a Windows / RDNA4 configuration.

This was NOT RD74's hypothesis, so it is tracked here rather than mutating RD74 into an unrelated bug. Relevance to BigCherry is unconfirmed: SPLIT_REDUCE uses peer access (hipDeviceCanAccessPeer / peer-copy in the reduction path), so a peer-copy corruption bug on a Windows+RDNA4 config could matter IF such a config is ever a deployment target. The local Windows workstation is gfx1100 (RDNA3); Brutus is Linux -- so Windows/RDNA4 is not a current known deployment, which is why this is a low-priority assess-first item, not an active defect.

## Steps

- Assess relevance: does BigCherry perform HIP peer-to-peer copy on any Windows/RDNA4 configuration it targets? (SPLIT_REDUCE peer-access path is the likely exposure.)
- If a relevant config exists: reproduce the peer-copy corruption on real Windows/RDNA4 hardware with a minimal reproducer (copy a known buffer peer->peer, checksum), capture the exact failure signature, and determine scope (all peer copies? specific sizes/strides?).
- If no relevant config exists: close as not-applicable to current deployment targets, retaining the reproducer evidence in the fork findings.
