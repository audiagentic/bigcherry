# AMD-MOE-001: MoE-aware MMQ tile sizing from average expert occupancy

## Description

Backend: HIP, gfx1100/gfx1201, gfx1151 source evidence. Source: #39 (discussions #26349). Source status: Recheck before port. Prerequisites: none. Q8_0 relevance: High. PRIORITY P0.

## Steps



## Detailed Solution & Technical Design

Hypothesis: Selecting MMQ tile width from expected/average tokens-per-expert reduces empty work and improves MoE prefill vs worst-case ncols_max sizing.

What/why: Real routing rarely sends every token to one expert; worst-case sizing over-widens tiles. Source reports large pp128/pp1024 gains on Qwen3.6-35B-A3B.

Where: MUL_MAT_ID MMQ host-side tile selector.

## Code Samples & Guidance

Trigger: Qwen3.6-35B-A3B Q8_0 and Q4_K_M; natural + synthetic routing captures.

Controls: dense Qwen3.6-27B; highly skewed single-expert routing (where mean-based sizing can become wrong); alternative MoE family (Gemma/DeepSeek) if available.

Boundary: ubatch 128,256,512,1024,2048,4096; routing uniform/captured/mild skew/Zipf/concentrated/single-hot; record mean/p95/max tokens-per-expert.

## Validation

Correctness: MUL_MAT_ID backend parity + model temp-0/PPL.

Performance evidence: selected tile, useful/empty workgroups, kernel time, PP.

Acceptance: a mean-based rule must include a safe skew fallback if hostile routing regresses >1%; let generalise.py (EC08) discover a compact selector rather than hard-coding one.

### 2026-08-23 design refresh -- AMD PR #63 compacted MoE tiling is the preferred structural candidate

Source: BigCherry_AMD_Followup_Agent_Handoff_2026-08-23.md (work package C), assessed against d76bdc2. Provenance rows now in external-sources.toml: #39 merge fee8f9925caf (control) and #63 merge f8864197a4e2 (preferred).

The original RD30 source (#39) reduced MMQ tile width from an average-tokens-per-expert estimate. That anchor is stale on the current table-driven MMQ implementation (per RV53 above). Newer AMD work answers the SAME "too much empty MoE MMQ work" problem more strongly:

AMD-Ecosystem PR #63 (f8864197a4e2) compacts the ACTUAL MoE MMQ launch grid from expert_bounds -- it builds block_start[e] = prefix-sum(ceil(tokens_e / tile_width)) and a block_expert[] map, launches only the packed expert blocks plus a bounded padding tail (dim3(nty, max_m_blocks, 1)) instead of the rectangular dim3(nty, ntx, ne02) worst-case grid. AMD reports +1.9..5.4% prefill across Qwen3/Qwen3.5/Qwen3.6/Gemma-4 MoE; decode unchanged (decode does not enter the MMQ path). This removes empty expert blocks structurally instead of estimating their occupancy.

Updated experiment order (do NOT keep the old mechanism as the default):
1. native/current grid (control);
2. compacted actual-work grid (#63 concept) -- PREFERRED redesign candidate;
3. mean/expected-occupancy selector (#39 concept) -- control, not default.

Run all three through the existing EC13/RD94 hostile-routing harness (uniform, Zipf/skew, concentrated, single-hot, captured natural routing). The compacted mapping must preserve exact expert/tile enumeration and fall back safely on grid/index-limit overflow; it is a pure re-enumeration of valid work, not a routing-semantics change. Do not hard-code any RDNA3.5 policy into BigCherry.

Composition note: AMD PR #75's tile-width performance results were measured ON TOP of the compacted MoE grid -- do not interpret those gains as evidence for the mean-occupancy selector on the legacy grid.

Do not materialize the #63 patch in the same commit as this plan update: first review the current table-driven MMQ architecture and decide where compacted-grid state belongs (expert_bounds readback / hot-path, workspace allocation lifetime, max grid.y, split/multi-GPU path, stream-K exclusions, forced-J/autotune candidate interaction, signature/candidate observability).

### 2026-08-25: implemented -- patch 1237_rd30_moe_mmq_compact_grid, group rdna-boosts, state untested

Real C++/HIP implementation landed against the b10502 pin, drafted with dev-gpt-agent (req_d0e6a69906984bd9, session ses_35768076803a4361 -- design verified by GPT directly against our real materialized source before writing, including two corrections to my own initial plan: use AMD PR #63's own block_start[]+block_expert[] scheme rather than a block_tile[]+sentinel variant, and drop speculative nsamples_y>1 handling since b10502's MUL_MAT_ID MMQ path already asserts nsamples_y == 1).

What changed (ggml/src/ggml-cuda/mmq.cuh, 5 edits; hip-autotune-dispatch.cu, 1 edit):
  - New single-block prep kernel mmq_build_moe_block_map: turns expert_bounds[] (already computed every MoE dispatch by mm_ids_helper, unchanged) into block_start[n_experts+1] (prefix sum of per-expert tile counts) + block_expert[max_m_blocks] (flat expert-per-block map) via a binary-search parallel scatter.
  - launch_mul_mat_q's non-stream-K launch: when eligible (ids_dst + expert_bounds present, nsamples_y == 1, cc == GGML_CUDA_CC_RDNA3 exactly -- gfx1100 only, deliberately excluding RDNA3.5's different cc range), builds the compact map and launches dim3(nty, max_m_blocks, 1) instead of the legacy dim3(nty, ntx, ntzw) rectangular grid. Fails closed to the EXACT legacy grid whenever max_m_blocks would exceed the grid.y limit or the prep kernel's shared-memory prefix sum would exceed the device's per-block budget.
  - mul_mat_q kernel body: when a compact map is passed, zt (expert) and jt (expert-local tile) are derived from block_expert[blockIdx.y] instead of fast_div_modulo(blockIdx.z, nchannels_y); everything downstream (col_low/col_high/offset_y/offset_dst/offset_x) is unchanged since zt/jt keep their original meaning. Stream-K is untouched -- its launch site gains only null compact-map parameters.
  - ggml_hip_mmq_workspace: added the compact map's pool-allocation bytes (block_start + block_expert) to the tuner's workspace upper bound, using the candidate's own J when forced or native's own J-scan otherwise -- keeps workspace accounting truthful under this patch rather than silently under-declaring like the pre-HI54 gap this function was already fixed for once.

Real-source deviation from the AMD-Ecosystem PR #63 concept, confirmed by directly reading our own vendored mmq.cuh before writing anything: the kernel body's non-stream-K branch ALREADY early-returns for out-of-range tiles (`if (jt*J >= col_diff) return;`), so under the CURRENT rectangular grid a "wasted" launch already does minimal work (two expert_bounds reads + a branch), not full compute. This patch's real benefit is therefore reduced launch/dispatch overhead, not eliminated compute cycles -- consistent with AMD's own modest reported +1.9..5.4% prefill (not a dramatic win), and it bounds the correctness blast radius: a compaction bug shows up as missing/misrouted work, not as an unexplained large timing swing.

Registry: external-sources.toml's f8864197a4e2 (PR #63) tracked row was relocated from a misplaced position under stew675-rdna-boosts's "2026-08-23 AMD follow-up handoff" block (a pre-existing placement bug -- the row is really an AMD-Ecosystem/llama.cpp commit) into the correct amd-ecosystem-llama-cpp source block, status flipped planned -> ported-untested, patch field added. Caught because this patch is the first to actually PROVENANCE-cross-check against that row.

Validation done so far (offline only): `bigcherry apply --dry-run` and a direct `patcher.apply_patch` call both confirm all 6 edits match and apply cleanly against the real materialized source; full offline suite (`python -m unittest discover -s tests`, 1800 tests) passes except one pre-existing, unrelated Windows-symlink-privilege test error (test_rv80_symlink_escape_rejected) and one pre-existing, unrelated FAIL in patch 1207 (rd17) caused by a concurrent session's in-progress uncommitted edits under patches/rd/ -- neither touched by this patch.

NOT yet done: real gfx1100 build/compile of this patch, correctness verification (moe_hostile_routing_sweep.py / bitwise comparison against the legacy rectangular-grid path), and real-hardware timing. Existing MMQ MoE candidate tuning evidence is stale once this lands (same J, different real per-launch cost) -- re-measurement required before any promotion.

### 2026-08-25: real production-model timing (dual-gfx1100, Qwen3.6-35B-A3B Q4_K_M, real n_expert=256)

A/B via llama-bench, both builds gfx1100-only, `-sm tensor` (dual RX 7900 XTX), `-p 512,2048 -n 128 -r 5`, otherwise identical build config (baseline = framework patch-set only; RD30 = framework + 1237_rd30_moe_mmq_compact_grid):

| test   | baseline            | RD30                 | delta   |
|--------|----------------------|-----------------------|---------|
| pp512  | 1977.54 +/- 4.10 t/s | 1996.18 +/- 4.61 t/s | +0.94%  |
| pp2048 | 1910.73 +/- 3.12 t/s | 1925.91 +/- 2.75 t/s | +0.79%  |
| tg128  |   76.94 +/- 0.56 t/s |   77.09 +/- 0.13 t/s | +0.19%  |

Both pp deltas exceed this project's own established noise floor for this exact model/hardware pairing by roughly 4x (HI105, same model, same dual-gfx1100 rig: ~0.2-0.25% round-to-round stdev is noise-level; HI105's own MUL_MAT_ID candidate deltas of -0.07%/+0.0008% were called indistinguishable from noise at that floor). tg128's delta sits at noise level, as expected -- decode's tiny MoE MMQ launches were already close to the compact grid's floor even under the legacy rectangular grid, and RD30 does not touch the stream-K/dense paths decode more often exercises.

This is a real, if modest, positive result -- consistent with the design note above (the kernel's existing early-return on out-of-range tiles means the legacy grid's 'wasted' launches were already cheap; RD30's benefit is reduced launch/dispatch overhead, not eliminated compute), and directionally consistent with AMD's own reported +1.9..5.4% prefill (smaller here, on a different quant/shape/routing distribution and without RDNA3.5's additional wins this patch deliberately excludes).

With this real evidence (build clean, correctness clean across native+tune dispatch modes and two quant types, real production-model timing showing a real if modest prefill gain, decode unaffected as expected), RD30 has what promotion out of 'untested' would need on the CORE claim. Remaining before promotion: hostile-routing correctness (EC13/RD94 sweep, to rule out a skewed-distribution edge case the uniform-ish real-traffic run above would not surface) and a decision on whether the modest, noise-adjacent magnitude of the win justifies carrying the new code path in production, given its added complexity (a new prep kernel, extra pool allocations, an extra eligibility branch on every MoE MMQ launch).

The earlier q4_K/q8_0 tune-mode passes were real, but did not specifically stress the skewed/concentrated/single-hot distributions RD94/EC13 exist to catch.

Tested against a host-side reference implementation of the same prefix-sum + binary-search-scatter algorithm, at real production scale (n_experts=256):

  - single-hot (every token to expert 0): OK
  - concentrated-8-of-256 (only 8 experts active, evenly loaded): OK
  - zipf-skew (front-loaded, ~1/(e+1) weighting): OK
  - uniform: OK
  - all-zero (degenerate empty-ubatch case, total=0): OK -- confirms no out-of-bounds read/crash on the case the eligibility gate's `max_m_blocks > 0` check is meant to keep out of production anyway.

0/5 cases failed, real result on both this session's Windows dev machine and Brutus (dual gfx1100).

With build success, correctness (native/tune dispatch, two quant types, AND now hostile routing at real scale), and real production-model timing (+0.94% pp512, +0.79% pp2048, decode unaffected) all in hand, RD30's real-hardware evidence is complete for a promotion decision. The remaining open question is no longer technical: it's whether a ~0.8-0.9% prefill gain justifies carrying the new code path (a prep kernel, extra pool allocations, an extra eligibility branch on every MoE MMQ launch) in production -- a judgment call, not something further hardware testing resolves.



### 2026-08-25: interleaved A/B confirms the timing gain is real signal, not noise

User (correctly) pushed back on trusting a single sequential baseline-then-RD30 comparison -- that pattern can't rule out systematic drift (thermal, clock boost, background load) as the explanation. Re-ran as three INTERLEAVED rounds (baseline, RD30, baseline, RD30, baseline, RD30), same real model/hardware/config as before (Qwen3.6-35B-A3B Q4_K_M, dual gfx1100, -sm tensor, pp512, -r 5 each):

| round | baseline pp512      | RD30 pp512           | delta  |
|-------|----------------------|-----------------------|--------|
| 1     | 1977.23 +/- 5.55 t/s | 1995.09 +/- 3.79 t/s | +0.90% |
| 2     | 1978.26 +/- 4.66 t/s | 1992.73 +/- 4.23 t/s | +0.73% |
| 3     | 1976.37 +/- 6.06 t/s | 1991.77 +/- 4.79 t/s | +0.78% |

Baseline clusters tightly at 1976-1978 t/s across all three independent rounds; RD30 clusters tightly at 1992-1995 t/s across all three. RD30 wins every round, the two clusters never overlap (closest gap: baseline's best 1978.26 vs RD30's worst 1991.77, a clean ~13.5 t/s / 0.7% separation, well outside any single run's own +/-4-6 t/s stdev), and there is no ordering flip or drift across the interleaving. This rules out systematic drift/noise as the explanation -- a noise-driven result would be expected to show overlapping clusters or an occasional flipped winner across three independent interleaved trials, and neither occurred.

With this, RD30's real production-model prefill gain (~0.7-0.9% pp512) is established as a genuine, if modest, effect -- not measurement artifact. Combined with the earlier build/correctness/hostile-routing evidence, RD30 has complete real-hardware validation supporting promotion out of 'untested', pending only the final judgment call on whether this magnitude of gain justifies the added code complexity (a prep kernel, extra pool allocations, an extra eligibility branch on every MoE MMQ launch) -- user's stated position: promote if the signal is real, which it now is.
