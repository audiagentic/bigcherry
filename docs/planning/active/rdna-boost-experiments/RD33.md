# AMD-MMV-001: Decode matvec without Q8_1 activation quantization

## Description

Backend: HIP; source default RDNA3.5, validate gfx1100/gfx1201. Source: AMD PR Set 2 matvec item. Source status: Recheck before port. Prerequisites: none. Q8_0 relevance: Medium.

## Steps



## Detailed Solution & Technical Design

Hypothesis: For n=1 bandwidth-bound decode, skipping the q8_1 activation quantization pass and dequantizing weights directly can reduce overhead.

What/why: Activation quantization is pure overhead when matvec decode is bandwidth-dominated. AMD's set includes this plus a fused gate+up SwiGLU variant.

Where: single-column quantized matvec path.

## Code Samples & Guidance

Trigger: Qwen3.6 dense Q4/Q6/Q8 decode signatures; small/medium dense models (expose launch overhead).

Controls: prefill/small-batch n>1; large MoE expert matmuls; accuracy-sensitive quants.

Boundary: ncols_dst 1,2,3,4,8; model sizes 4B,9B,27B; context 0/64K/128K.

## Validation

Correctness: backend parity + PPL; arithmetic changes may need tolerance rather than byte identity.

Performance evidence: tg128/512, kernel count, activation-quantize time removed.

Acceptance: only enable for n=1 (or proven narrow range) if E2E decode gain >1% and quality gate passes.

AUDITED 2026-08-27 (real source read against the current pinned tree, not the PR-era description): premise CONFIRMED CURRENT, not stale (unlike RD29's dead PR anchor).

`ggml_cuda_mul_mat_vec_q()` in vendor/llama.cpp/ggml/src/ggml-cuda/mmvq.cu:1384-1487 is the live, unified MMVQ entry point (same function BigCherry's HI13 dispatch-tuning hooks into, per its own inline comment). It unconditionally calls `quantize_row_q8_1_cuda(...)` (line 1487) to convert the F32 activation (`src1`) into `block_q8_1` format as a SEPARATE GPU kernel launch, before the matvec kernel itself runs -- for every call, with no bypass for `ne11==1` (single-column decode: the dominant shape for MTP speculative-verify and ordinary autoregressive generation). `ggml_cuda_op_mul_mat_vec_q` (line 1537) receives the already-quantized `src1_ddq_i` as input -- confirming activation quantization is a real, distinct, currently-unconditional stage upstream of the matvec compute, exactly as RD33's hypothesis describes.

This is a genuine, currently-live optimization target: for n=1 decode, RD33 proposes dequantizing weights directly against the F32 activation instead, skipping the quantize_row_q8_1_cuda launch (and its associated `ggml_cuda_pool_alloc<char> src1_q8_1` allocation) entirely for that shape. Recommended via gpt negotiation (2026-08-27, req_5436006e21144205/req_37924cdc23964f01) as the top-ranked next structural experiment for the dense-27B+MTP+dual-XTX workload, given HI130's autotune-dispatch-tuning null result (candidate SELECTION among existing kernels shows no measurable win; this instead REMOVES a real pipeline stage). Ranked above RD87 (hipBLASLt, shovel-ready but likely doesn't dominate Q8_0 decode), RD28 (MMQ tile-width, applies mainly to M>8 verification batches, not typical n=1 decode), and RD29 (tiny-M Q8_0 kernel, needs a from-scratch design, no existing code to A/B).

**Acceptance methodology (gpt-negotiated, grounded in our own measured noise floor of 0.5-0.9% repetition SD on this exact hardware/model)**: interleaved paired A/B (not sequential), 10 observations/arm as an initial screen -- immediate PASS only at >=1.5% delta with paired 95% CI excluding zero; a 0.5-1.5% observed gain requires extending to ~40 observations/arm (fewer if paired-drift correlation helps) before calling it real, rather than being dismissed as sub-1% noise (RD30 already demonstrated a real 0.7-0.9% effect at this same noise floor). **FINAL CONVERGED VERDICT, 2026-08-27: NULL RESULT (no measurable effect, not a win, not a real regression).**

Following gpt's decision tree (session ses_fec603fc33ee4089, req_2e505d0b414d47a4): ran the cheap kernel-resource diagnostic before spending more benchmark time. rocprofv3 --kernel-trace --stats on the exact n=1 Q8_0 MUL_MAT test-backend-ops case, baseline vs RD33 test-backend-ops binaries (same lane, isolated experiment): **VGPR=24, SGPR=128, Scratch=0 -- IDENTICAL on both builds**, across all 14 real kernel launches captured. This falsifies the register-pressure/occupancy-regression hypothesis per gpt's own settling criteria. In this isolated microbenchmark, RD33's total kernel duration (~84.8us across 14 launches) was marginally LOWER than baseline's (~85.9us) -- opposite direction from the noisy server-level result.

Ran a second full server-level A/B round (same seeded/deterministic methodology) to check whether round 1's negative delta was real:
- baseline round 1: pp4096=1222.1+-15.8, tg128=101.2+-1.1, tg512=99.5+-0.5
- baseline round 2: pp4096=1226.9+-3.5, tg128=101.1+-0.4, tg512=99.7+-0.3
- RD33 round 1: pp4096=1203.8+-30.0, tg128=97.4+-5.9, tg512=98.4+-1.8
- RD33 round 2: pp4096=1224.7+-3.6, tg128=101.4+-0.5, tg512=100.3+-0.3

**Key finding**: round 1 was noisy for BOTH baseline AND RD33 (baseline round 1's own stddev was ~4x its round 2 value) -- this was an ambient system-noise window affecting the whole measurement, not something RD33's kernel caused. Round 2, with tight noise on both sides, shows RD33 essentially matching baseline (tg128 +0.3%, tg512 +0.6%, both trivial/within noise).

**Final honest verdict**: RD33 is CORRECT (48/48 test-backend-ops, kernel resource profile identical to baseline, no occupancy/register regression) but shows NO measurable performance benefit on this workload/hardware -- neither a real win nor a real regression. The original round-1 'regression-leaning' signal was noise, now explained and resolved, not a real effect requiring further diagnosis.

**Disposition**: park RD33 as a validated-correct, null-performance-effect patch. Do not promote to production (no benefit to justify carrying the extra code path). Do not chase further -- gpt's own criteria for stopping ('same resources, no scratch -> resource-pressure hypothesis falsified' + 'paired confirmation converges to ~0%') are both met. Real, useful negative result: skipping q8_1 activation quantization for Q8_0 n=1 decode does not measurably help on gfx1100 for this workload -- the quantization stage's cost is apparently small enough (or sufficiently overlapped/hidden) that removing it doesn't move the needle. This is itself valuable evidence against continuing to chase 'remove a pipeline stage'-style optimizations blindly without profiling first.
