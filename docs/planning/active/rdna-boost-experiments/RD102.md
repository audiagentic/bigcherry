# RD08-VDR2-NUMERIC: new contract testing RD08's VDR2 kernel under numerical-equivalence (not bit-identical) acceptance

## Description

RD08's real --run-rd08-contract qualification (2026-09-01, gfx1100, current pin b10705, gpt-oss-20B Q6_K) failed correctly at the bit_identical correctness gate: subject (VDR2) and control (VDR1) digests genuinely differ on all 5 tested decode shapes, even though their NMSE-style error vs a CPU reference matches to ~10 significant figures (well within BigCherry's normal tuning tolerance) and performance/regression gates both pass (target_kernel_gain_pct=0.43% vs 0.3% required; max_control_regression_pct=0.0% vs 1% budget). Luna and GPT (independently, both asked the same question) agreed: RD08's bit_identical requirement must NOT be weakened after seeing this result -- it was a deliberate, documented contract-design choice (EC02/EC07) specifically testing the fork author's stated bit-identical claim, and that claim is now real-hardware-disproven. Do not mutate RD08's original claim.

Both independently suggested the correct path if VDR2 is still worth pursuing: a SEPARATE, new experiment contract with an explicitly numerical-equivalence (NMSE-tolerance-based) hypothesis, matching BigCherry's own normal dispatch-candidate correctness model, rather than retroactively changing what RD08 claims. This item tracks that follow-up: design and land a new contract (working id RD08-VDR2-NUMERIC or similar) that tests VDR2 as a numerically-equivalent-but-not-bit-identical decode kernel, with explicit acceptance criteria that acknowledge non-bit-identical output is acceptable for THIS contract's claim (unlike RD08's).

## Notes

Real determinism risk this new contract must explicitly address before promotion, not just measure NMSE and declare victory: RD26 (docs/planning -- decode vs speculative-verify bit-identity) already establishes that bit-identical output across decode/verify batches is a soundness precondition for MTP's speculative accept/reject logic in this codebase. A numerically-close-but-not-bit-identical kernel candidate can silently flip accept/reject decisions if draft and verify passes end up using different kernel variants for the same logical operation, and per-step numerical drift compounds over autoregressive generation. Any new numerical-equivalence contract for VDR2 must either (a) prove draft and verify always route through the SAME kernel variant in production (so cross-variant drift never actually occurs), or (b) explicitly scope acceptance to exclude speculative-decode/MTP workloads, or (c) measure and bound end-to-end output-trajectory divergence directly, not just single-call NMSE. Do not promote VDR2 under a numerical-equivalence contract without addressing this.

Also pending, separate from the new-contract question: patches/1204_rd08_q6k_mmvq_vdr2/validation/rd08_correctness.py has a real, unrelated harness bug -- find_digest_for_tensor()/find_metric_for_tensor() search test-backend-ops stderr for a tensor named "dst", but test_mul_mat's real output tensor (confirmed in vendor/llama.cpp/tests/test-backend-ops.cpp) is always named "out". Every digest comparison has been silently returning None/None and failing for the wrong reason. Both Luna and GPT recommend fixing this (dst->out) regardless of the numeric-equivalence question, adding a regression test, and re-running --run-rd08-contract so committed evidence reflects the real digest mismatch instead of the misleading None/None failure. This is separate, smaller, uncontroversial work that should probably land first.
