# HIPBLAS-001: Offline hipBLASLt tuning for captured llama.cpp GEMM signatures

## Description

Backend: HIP, gfx1100/gfx1201. Source: AMD hipBLASLt offline tuning documentation. Source status: Recheck before port. Prerequisites: none. Q8_0 relevance: Very high. PRIORITY P0 -- "very low implementation risk; establishes vendor-library headroom before new kernels."

## Detailed Solution & Technical Design

Hypothesis: hipBLASLt's default heuristic isn't always optimal for llama.cpp's exact GEMM signatures; offline-tuned solution files can improve selected large-M prefill ops.

What/why: Low-cost way to test vendor-library headroom before writing kernels.

Where: benchmark/build environment; no llama.cpp code change initially.

## Code Samples & Guidance

Trigger: all captured hipBLASLt signatures from Qwen3.6-27B Q8 and 35B MoE.

Controls: native MMQ/MMVQ and untuned hipBLASLt.

Boundary: dedupe M/N/K/transposes/types; tune top time x calls shapes.

**Root cause**: AMD's ROCm packaging (both apt and the Windows HIP SDK) ships the hipBLASLt runtime library only. The client/bench tools are built from the `ROCm/hipBLASLt` GitHub source tree with `-DBUILD_CLIENTS=ON`, which additionally requires Tensile (AMD's kernel-generation/tuning framework) and is a substantially larger build than the library itself -- not a quick install, a real from-source build.

**Concrete next step for whoever picks this up**: clone `https://github.com/ROCm/hipBLASLt` at the tag matching the installed library version (1.2.2), build with `-DBUILD_CLIENTS=ON` against the Brutus ROCm 7.2.4 toolchain (or a matching vendored version), producing `hipblaslt-bench`. This is real, scoped, buildable work -- not blocked on anything external -- but is large enough (Tensile dependency, a full from-source build) to be its own slice rather than bundled into this investigation. Until that lands, this item's actual offline-tuning work cannot start.

### 2026-08-23 -- gfortran, Boost, msgpack-cxx all resolved; hit the REAL structural blocker (scope escalation, not another package)

With gfortran + libboost-dev + libmsgpack-cxx-dev installed and --skip_rocroller passed, configure got much further (found BLAS/LAPACK/OpenMP/Boost/msgpack-cxx cleanly) but hit `add_subdirectory(../../shared/origami)` -- same class of missing-sibling-directory error as rocroller, but origami has no `--skip_origami` install.sh flag. Tried `-DROCM_LIBS_SUPERBUILD=ON` (the CMakeLists.txt condition gating that add_subdirectory) to bypass it -- this does skip building origami from source, but then fails differently: `target_link_libraries` for both `hipblaslt` (wants `roc::hipblas-common`, which IS installed via apt but its find_package/target isn't wired up outside a real superbuild) and `tensilelite-host` (wants `roc::origami`, which has NO apt package at all) can't find their imported targets.

**Root cause, now confirmed rather than guessed**: this hipBLASLt tag is written to be built as part of AMD's `ROCm/rocm-libraries` monorepo (confirmed to exist: `github.com/ROCm/rocm-libraries`, "super repo for rocm libraries", ~7GB reported repo size), not as a standalone clone -- `shared/origami` and `shared/rocroller` are sibling projects in that monorepo, not separate apt-installable libraries or optional standalone components. A standalone `git clone ROCm/hipBLASLt` genuinely cannot produce `hipblaslt-bench` at this tag without either (a) cloning the much larger monorepo instead (a materially bigger undertaking than originally scoped -- itself needing space/time to clone and its own configure debugging), or (b) finding an older hipBLASLt tag that predates this monorepo restructuring and still builds standalone (not yet checked -- worth trying before committing to the monorepo clone, since the client tool's actual functionality needed for offline GEMM tuning is unlikely to depend on whatever origami/rocroller provide).

**Stopped here to report the scope escalation** rather than silently start a ~7GB clone and an unknown amount of further monorepo-specific configure debugging -- this is no longer "one more apt package," it's a different-shaped problem than RD87 was originally scoped for.

**Next step options, in order of trying**: (1) try an OLDER hipBLASLt tag (e.g. rocm-6.x series, before the shared/origami and shared/rocroller split existed) that may still build standalone against the same installed ROCm 7.2.4 runtime libraries -- cheapest to try first; (2) if no older tag works, clone `ROCm/rocm-libraries` instead and locate hipBLASLt's real position within it -- larger, real, but well-defined follow-up work, not blocked on anything external.

**Full reproducible recipe, start to finish, for whoever needs to rebuild or extend this:**

1. Sparse-clone `ROCm/rocm-libraries` into `vendor/` (gitignored, same convention as `vendor/llama.cpp`/`vendor/rocm/<version>`):
   ```bash
   cd ~/bigcherry/vendor && git clone --filter=blob:none --sparse --branch develop https://github.com/ROCm/rocm-libraries.git
   cd rocm-libraries && git sparse-checkout set projects/hipblaslt shared/origami shared/rocroller shared/tensile shared/mxdatagenerator shared/stinkytofu shared/ctest shared/primbench
   ```
   (~6.2GB on disk after checkout.)
2. System packages needed beyond a normal ROCm dev install (all real apt packages, all installed by the owner this session): `gfortran`, `libboost-dev`, `libmsgpack-cxx-dev`.
3. GTest/GMock: no apt-installable client-skip flag exists in this tag's build system, so a userspace extraction was used instead of another sudo round: `apt-get download libgtest-dev libgmock-dev && dpkg-deb -x *.deb ~/local-gtest/extracted/` -- ships precompiled `.a` libs in a correctly-nested `usr/` tree (matches the real system layout exactly, so `CMakeConfig.cmake`'s relative `PACKAGE_PREFIX_DIR` math resolves correctly with no shim editing needed). Pointed at via `CMAKE_PREFIX_PATH=/home/audumla/local-gtest/extracted/usr`.
4. This monorepo copy's `install.sh` is a DEPRECATED wrapper -- do not use it (it doesn't recognize several real flags like `--cpu_ref_lib`). Use the real `invoke`-based interface (`tasks.py`) directly. `invoke` itself has to be in a venv OUTSIDE the `build/` directory (a `rm -rf build` for a clean reconfigure would otherwise delete it too): `python3 -m venv ~/bigcherry/vendor/rocm-libraries/invoke-venv && ~/bigcherry/vendor/rocm-libraries/invoke-venv/bin/pip install invoke`.
5. Tensile's own Python codegen (`tensilelite/Tensile`) needs its `requirements.txt` (joblib, msgpack, numpy, pyyaml, etc.) importable by whichever `python3` CMake's `find_package(Python3)` resolves to -- the SYSTEM python3 is externally-managed (PEP 668, no bare `pip install --user`) and does NOT have these by default. Install them into the SAME invoke-venv (`invoke-venv/bin/pip install -r tensilelite/requirements.txt`) and put that venv's `bin/` FIRST on `PATH` before configuring, so CMake's Python3 detection picks the venv interpreter instead of `/usr/bin/python3`.
6. Build command, from `projects/hipblaslt`:
   ```bash
   PATH=/home/audumla/bigcherry/vendor/rocm-libraries/invoke-venv/bin:$PATH \
   CMAKE_PREFIX_PATH=/home/audumla/local-gtest/extracted/usr \
   /home/audumla/bigcherry/vendor/rocm-libraries/invoke-venv/bin/invoke build \
     --clients --architecture gfx1100 --cpu-ref-lib lapack
   ```
7. **Runtime**: the built `hipblaslt-bench` needs `libomp.so` on `LD_LIBRARY_PATH` -- not present under the active `/opt/rocm` symlink target on this box, but IS present at `/opt/rocm-7.2.4/lib/llvm/lib/libomp.so`. Run as:
   ```bash
   LD_LIBRARY_PATH=/opt/rocm-7.2.4/lib/llvm/lib:/opt/rocm/lib \
   ~/bigcherry/vendor/rocm-libraries/projects/hipblaslt/hipblaslt-install/bin/hipblaslt-bench -m <M> -n <N> -k <K> --precision <type>
   ```

Binary locations: `~/bigcherry/vendor/rocm-libraries/projects/hipblaslt/hipblaslt-install/bin/hipblaslt-bench` (installed copy) and `.../build/release/clients/hipblaslt-bench` (build-tree copy); several `hipblaslt-bench-extop-*`/`hipblaslt-bench-groupedgemm-*` variants also built alongside it.
