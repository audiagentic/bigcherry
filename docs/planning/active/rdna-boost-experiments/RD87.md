### 2026-08-23 -- tooling gap confirmed directly (superseding the earlier vague 'not available' note)

Checked directly via SSH on Brutus (10.10.100.10), not assumed: `hipblaslt` and `hipblaslt-dev` ARE installed (apt, 1.2.2.70204-93~24.04) -- the runtime library and dev headers are present and already what BigCherry's own HIP builds link against. The offline-tuning CLIENT binary (`hipblaslt-bench`, the actual tool this item needs to drive offline tuning) is NOT present anywhere on Brutus's filesystem (confirmed via `find /` and `dpkg -L` on both installed packages -- neither package ships it) and has no dedicated apt package (`apt-cache search hipblaslt` shows only the library/dev packages, no `hipblaslt-clients` or similar). Also checked the local Windows workstation's vendored ROCm 7.1 install (`vendor/rocm/7.1`) -- same result: `libhipblaslt.dll` and headers present, no bench/client executable anywhere under the tree.

**Root cause**: AMD's ROCm packaging (both apt and the Windows HIP SDK) ships the hipBLASLt runtime library only. The client/bench tools are built from the `ROCm/hipBLASLt` GitHub source tree with `-DBUILD_CLIENTS=ON`, which additionally requires Tensile (AMD's kernel-generation/tuning framework) and is a substantially larger build than the library itself -- not a quick install, a real from-source build.

**Concrete next step for whoever picks this up**: clone `https://github.com/ROCm/hipBLASLt` at the tag matching the installed library version (1.2.2), build with `-DBUILD_CLIENTS=ON` against the Brutus ROCm 7.2.4 toolchain (or a matching vendored version), producing `hipblaslt-bench`. This is real, scoped, buildable work -- not blocked on anything external -- but is large enough (Tensile dependency, a full from-source build) to be its own slice rather than bundled into this investigation. Until that lands, this item's actual offline-tuning work cannot start.

### Toolchain/dependency formalization note (owner request, 2026-08-23)

The project's existing toolchain-vendoring convention (`vendor/rocm/<version>/`, `tools/rocm-env.sh`/`.ps1`, documented in `docs/reference/BUILD.md`'s Windows/Linux sections, captured into build-identity by `tools/bigcherry/toolchain.py`) already covers the ROCm/HIP compiler+library case well and should be reused as-is for any hipBLASLt client build, not a new parallel mechanism. What's missing is a place that inventories *which* dependencies are vendored/needed and their acquisition path when they're not a straight ROCm-install copy (like hipBLASLt's clients, which need a separate from-source build even though the library itself comes from the same ROCm install). Recommend adding a short 'Known gaps' subsection to BUILD.md naming this one concretely, rather than a new doc -- see the BUILD.md edit landing alongside this note.
