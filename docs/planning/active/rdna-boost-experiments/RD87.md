## Detailed Solution & Technical Design

Hypothesis: hipBLASLt's default heuristic isn't always optimal for llama.cpp's exact GEMM signatures; offline-tuned solution files can improve selected large-M prefill ops.

What/why: Low-cost way to test vendor-library headroom before writing kernels.

Where: benchmark/build environment; no llama.cpp code change initially.

Boundary: dedupe M/N/K/transposes/types; tune top time x calls shapes.

### 2026-08-23 -- tooling gap confirmed directly (superseding the earlier vague 'not available' note)

Checked directly via SSH on Brutus (10.10.100.10), not assumed: `hipblaslt` and `hipblaslt-dev` ARE installed (apt, 1.2.2.70204-93~24.04) -- the runtime library and dev headers are present and already what BigCherry's own HIP builds link against. The offline-tuning CLIENT binary (`hipblaslt-bench`, the actual tool this item needs to drive offline tuning) is NOT present anywhere on Brutus's filesystem (confirmed via `find /` and `dpkg -L` on both installed packages -- neither package ships it) and has no dedicated apt package (`apt-cache search hipblaslt` shows only the library/dev packages, no `hipblaslt-clients` or similar). Also checked the local Windows workstation's vendored ROCm 7.1 install (`vendor/rocm/7.1`) -- same result: `libhipblaslt.dll` and headers present, no bench/client executable anywhere under the tree.

**Root cause**: AMD's ROCm packaging (both apt and the Windows HIP SDK) ships the hipBLASLt runtime library only. The client/bench tools are built from the `ROCm/hipBLASLt` GitHub source tree with `-DBUILD_CLIENTS=ON`, which additionally requires Tensile (AMD's kernel-generation/tuning framework) and is a substantially larger build than the library itself -- not a quick install, a real from-source build.

**Concrete next step for whoever picks this up**: clone `https://github.com/ROCm/hipBLASLt` at the tag matching the installed library version (1.2.2), build with `-DBUILD_CLIENTS=ON` against the Brutus ROCm 7.2.4 toolchain (or a matching vendored version), producing `hipblaslt-bench`. This is real, scoped, buildable work -- not blocked on anything external -- but is large enough (Tensile dependency, a full from-source build) to be its own slice rather than bundled into this investigation. Until that lands, this item's actual offline-tuning work cannot start.

### Toolchain/dependency formalization note (owner request, 2026-08-23)

### 2026-08-23 -- tooling gap confirmed directly, then a real build attempt (blocked on one missing system package)

Confirmed via SSH on Brutus: `hipblaslt`/`hipblaslt-dev` (1.2.2.70204-93~24.04, ROCm 7.2.4) are installed; `hipblaslt-bench` (the client this item needs) is absent everywhere (checked `dpkg -L` on both packages and `find /`) and has no apt package.

**Real build attempt, same session**: cloned `ROCm/hipBLASLt` at tag `rocm-7.2.4` (matching the installed library exactly) to `~/build-hipblaslt/hipBLASLt` on Brutus (~5.1GB, gitignored under `vendor/` per the project's existing pattern -- not committed). `./install.sh -c -a gfx1100` (client build, targeting the actual production GPU architecture first) hit a real, single, precise blocker: `CMakeLists.txt:134 (enable_language)` unconditionally requires a Fortran compiler (`FC=gfortran`) -- this fires even with `--cpu_ref_lib lapack` (tried explicitly; still requires Fortran, presumably for LAPACK's own Fortran interface, not just BLIS as first assumed). `gfortran` is not installed on Brutus and there is no passwordless sudo available to this session (`sudo -n true` fails).

Tried a real workaround before giving up: `apt-get download gfortran gfortran-13 libgfortran-13-dev` (no privileges needed) and extracted the `.deb`s into a user-local prefix -- the `gfortran`/`gfortran-13` binaries turned out to be symlinks to `x86_64-linux-gnu-gfortran-13`, which ships in a DIFFERENT package (`gcc-13`'s Fortran variant) not included in what was downloaded, and assembling a genuinely working Fortran toolchain from user-extracted packages without root is a real rabbit hole for what is otherwise a one-line fix. Stopped there rather than keep escalating a workaround for a missing system package.

**Concrete, now very precisely scoped, next step**: run `sudo apt install gfortran` on Brutus (one package, no other blockers found -- msgpack/HIPBLASLT_ENABLE_FETCH already resolved automatically via CMake FetchContent during configure, BLIS's own gfortran requirement was successfully avoided via `--cpu_ref_lib lapack`), then re-run `cd ~/build-hipblaslt/hipBLASLt && ./install.sh -c -a gfx1100 --cpu_ref_lib lapack`. This needs a human with sudo on Brutus; it is the one remaining blocker for the whole item. Build time after that is unknown but should be assumed to be long (Tensile GEMM kernel generation) -- expect to run it as a background/detached process, not something to wait on synchronously.
