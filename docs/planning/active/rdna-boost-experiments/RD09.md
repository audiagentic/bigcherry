Future foundational Q8_1 activation cache experiment from ff6fde5, explicitly overlapping HI26 and serving as the only base for its dependent Q8 children.

**Fork mechanism:** cache storage lives on ggml_backend_cuda_context; ggml_backend_cuda_graph_compute() clears the logical cache at the start of every graph execution; ggml_cuda_mul_mat_vec_q() replaces its per-call ggml_cuda_pool_alloc + quantize_row_q8_1_cuda with a cache lookup, quantizing only on a miss.

**Real correctness weakness found in the fork (must NOT be reproduced):** its cache key uses view-root pointer + shape/stride/stream but NOT the actual view data address/offset -- two views of the same root with identical shape/strides but different offsets can collide. This is exactly the false-hit risk this item's own risk statement warns about. Fix: add the exact view data address/offset into the key (see key struct below).

**Second fork choice to reject:** its cache arena is relocatable (grows by allocating new + copying + freeing old), which conflicts with HIP/CUDA graph-capture lifetime (captured buffer addresses must stay stable once a graph is recorded). Adaptation: use stable retained slabs (survive until backend-context destruction; logical entries/bump positions reset each generation), hard byte+entry cap, native-path fallback on exhaustion, never grow while capture is active.

**Integration point:** at MMVQ materialization inside ggml_cuda_mul_mat_vec_q() -- NOT the 0200_dispatch_hook.py layer, and NOT a graph rewrite. 0200 intercepts selection at ggml_cuda_mul_mat; 0650_mmvq_native_variant threads forced geometry back down through the native ggml_cuda_mul_mat_vec_q() path, so native and BigCherry-forced MMVQ variants already converge at the exact seam RD09 needs -- 0200 stays completely unaware of RD09.

**Cache key** (strengthened vs fork): { generation (uint64), view_root (tensor identity ptr), data (exact view byte start -- the fork's missing field), stream_no, ne0/ne0_padded/ne1/ne2/ne3, s1/s2/s3 }. Device is NOT in the key (cache is owned by one ggml_backend_cuda_context already); keep device id as diagnostic/assertion metadata only. Stream stays in the key -- no cross-stream reuse.

**API shape:** separate find/reserve/publish (a miss must not become a visible cache entry before the producer kernel is at least enqueued) -- `find(key)` -> on miss `reserve(bytes)` -> on success `quantize_row_q8_1_cuda(...)` then `publish(key, reserved)`; on reserve failure, fall back to the exact current native allocation/quantizer path. This reserve->launch->publish shape is deliberately the same API RD10/RD11/RD24 will need for their own direct-Q8 producers.

**Validation approach:** the canonical correctness reference stays quantize_row_q8_1_cuda() itself (deterministic on this pin; type_src0 arg is unused). A `verify` mode does an expensive independent re-quantize + full byte-compare on every cache hit -- final-logit equality alone is explicitly called out as too weak for this foundation. Required correctness matrix before any performance work: same-tensor-twice->hit+exact bytes; same-root-different-offset->MUST miss (non-negotiable -- proves the fork's key weakness is fixed); dimension/stride change->miss; different stream->miss; new generation->miss; address reused by a different tensor in the same generation->miss; capacity exhausted->native fallback with exact output; dual-GPU/tensor-split->per-backend cache isolation; direct-producer prefill->exact match vs standalone quantizer. Graph-capture validation is a SEPARATE, later step: exhaust key correctness with graphs disabled first, only then enable graphs (no synchronous byte verification inside capture) and confirm warm-up/capture/replay/stable-addresses/output-parity/no-slab-growth-during-capture.

**Env gating:** `GGML_HIP_Q8_1_CACHE_MODE=off|on|verify` (default off; off must be byte-for-byte the current unmodified path), plus `GGML_HIP_Q8_1_CACHE_STATS=1` for counters (lookups/hits/misses/quantize-launches-saved/capacity-bypasses/capture-capacity-bypasses/bytes/high-water/generations/verify-mismatches). Deliberately kept INDEPENDENT of GGML_HIP_DISPATCH_MODE (native/record/tune/replay) -- RD09 is an activation-materialization optimization underneath MMVQ that must behave identically regardless of how MMVQ geometry was chosen; coupling the two would poison the native control.
