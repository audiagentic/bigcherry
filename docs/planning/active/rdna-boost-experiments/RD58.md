## Notes

Multi-GPU correctness item -- may also fit the hip-autotune plan; filed under rdna-boost-experiments per the backlog doc's primary recommendation, cross-check placement if it turns out to fit hip-autotune's domain better. From docs/reference/BigCherry_External_AMD_RDNA_Experiment_Backlog.md §4. Filed as part of the 65-item backlog batch (2026-08-20).

Implemented (2026-08-24) as patches/1234_rd58_pin_state_buffer_multigpu_restore.py, ported from ggml-org/llama.cpp PR #27405 (closed by a maintainer 2026-08-20 redirecting to rocm/rocm-systems#4817, not because the fix was disputed -- verified via `gh pr view`/`gh api`, not assumed). Root cause: with 2+ HIP devices in one process, ROCm's on-the-fly pageable-memory mapping for an async H2D copy can be torn down mid-transfer, faulting the SDMA engine. Registers the state-restore buffer as portable pinned host memory for the duration of the restore. Deliberate deviation from the source PR (agreed with dev-gpt-agent before implementing): removed the unconditional failure-path log line (the backend returning 'no' to a register request when GGML_CUDA_REGISTER_HOST is unset is not an error), kept the success diagnostic as the real-hardware activation proof.

**Real-hardware finding and fix (2026-08-24)**: initial validation attempts via llama-server's HTTP slot save/restore API showed zero faults across 190 cycles, but this was later found to be because that HTTP path uses a completely different file-streaming code route (`state_seq_load_file`) that never touches the patched function at all. Switched to llama.cpp's own real `test-save-load-state` test binary (Test 4, 'seq copy (host)'), which does exercise the exact patched API. Discovered via direct debug instrumentation that the registration loop -- ported faithfully from the source PR -- never activated under `-sm tensor` (BigCherry's actual production dual-GPU topology): tensor-split wraps the real per-device HIP backends in a single 'Meta' scheduling device with no registry of its own (confirmed stock upstream `ggml-backend-meta.cpp` behavior, not a BigCherry regression; most likely affects the source PR's own mechanism too on any tensor-split deployment, though not verified against the PR author's own test config). Consulted dev-gpt-agent, which confirmed the gap and designed the fix: flatten any Meta-typed device into its real underlying per-device backends first, using two functions (`ggml_backend_meta_dev_n_devs`/`ggml_backend_meta_dev_simple_dev`) that already existed in upstream `ggml-backend-meta.cpp` but were file-local `static` -- exposed as public API via two small sibling patch edits (linkage change only, zero logic change) in `ggml-backend.h`/`ggml-backend-meta.cpp`.

**Final real-hardware confirmation (2026-08-24, Brutus, dual-XTX, -sm tensor, GGML_CUDA_REGISTER_HOST=1)**: after the fix, the activation diagnostic (`pinned state buffer (55970556 bytes) for restore`) fires reliably -- confirmed on every single cycle across 150 repeated real host-path restore cycles (55.97MB real state buffer, well over the 1MiB threshold), zero HIP faults, zero crashes, correct byte count on every cycle. All 5 of llama.cpp's own upstream save/load-state tests pass. This is the exact production topology and confirms the fix genuinely activates where it needs to.

**Not yet done**: the original ROCm SDMA fault itself was never reproduced on Brutus (0 faults observed in control across 190+340 combined cycles, single-GPU-architecture-consistent hardware, ROCm 7.2 -- same version as the bug reporter). This doesn't disprove the bug (it's real, open, explicitly affects RX 7900 XTX per the ROCm issue, and is described as intermittent/timing-dependent), it just means Brutus's specific timing/driver conditions haven't hit it in the cycles tested. So: mechanism now correctly activates in production topology and causes no regressions/correctness issues in every real test run; the actual fault it targets remains unreproduced here. STATE stays 'untested' pending either a reproduction of the original fault or a longer/more adversarial soak test.

**Tooling note (unrelated to RD58 itself, flagged for future investigation)**: found that the full `bigcherry apply --groups rdna-boosts --states untested` CLI command can report `[ok] ... 1 applied` for a file while the write does not actually take effect, when the overall selection also contains an unrelated failing patch (the pre-existing RD17 anchor mismatch from another agent's in-progress work).
