# Build-plan lock reuse race (fixed) + unexplained instant-ok-with-no-artifact symptom (still open)

## Description

CORRECTED FINDING (2026-08-26, same investigation as originally filed): the earlier hypothesis -- that the tune-mode measurements JSONL header is missing `variant_set`/`build_descriptor_hash` due to a C++ header-writer bug in hip-autotune-tuner.cu -- was WRONG. Root-caused by comparing embedded provenance against the actual filesystem state:

- The tune-mode measurements header's `source_revision` field reads `4801e3c567d5131dd41b387df5f2d4b1370d92be`. This is NOT the commit the Brutus tree was fast-forwarded to earlier this session (`67fdade...`, itself now behind local HEAD `fb97717c5acd531175c93c500a62e0f53fcba25a`). It exactly matches a pre-existing `artifacts/4801e3c567d5/` directory that was already on disk before this session's `bigcherry build --lane bigcherry:tune:linux-multi ...` run.
- `build/bigcherry-tune/bin/libggml-hip.so` is a symlink to `libggml-hip.so.0.19.0`, dated Aug 12 -- an old SONAME never bumped to `.0.20.2`. Yet `hip-autotune-tuner.cu.o` under the same build tree WAS recompiled today (fresh mtime), and the `bigcherry build` command printed a full ninja recompilation log ending in `bigcherry:tune:linux-multi: ok build_plan_id=...`.
- i.e. object files were rebuilt, but the versioned shared library was never relinked/republished, and the lane's working tree was never actually re-checked-out against current HEAD -- the command reports success while continuing to serve an old binary from a previous, unrelated build of that lane.
- By contrast, `build/bigcherry-record/bin/libggml-hip.so` correctly resolves to `.0.20.2` (Aug 20) -- so this isn't universal breakage, but it is NOT reliably tied to 'did this session's build succeed', since record's binary is ALSO several commits behind current HEAD (source_revision matches `artifacts/0adcc3bb5710/`, not `67fdade`/`fb97717`).

Net effect: a `bigcherry build` lane reporting `ok` is not sufficient evidence that the resulting binary reflects the current tree -- there is no verification step tying the published binary's embedded source_revision back to the requested build's actual git HEAD.

## Steps

1. Identify why `build/bigcherry-tune`'s link step didn't rerun despite object recompilation (check CMake target dependency graph / SONAME handling for ggml-hip in this lane's CMakeLists, and whether the lane's checkout step re-applies patches/re-syncs to HEAD before invoking cmake/ninja, or trusts an existing checkout).
2. Add a build-time or post-build assertion: after any `bigcherry build --lane` reports `ok`, verify the published binary's embedded `source_revision` (queryable via the JSONL header emitted by any dispatch-mode run, or a `--version`/build-info endpoint) matches the git HEAD the build was requested against. Fail closed (non-zero exit / explicit warning) on mismatch rather than silently serving stale output.
3. Re-run the full record -> tune -> inventory tuning -> tune-promote -> replay chain from a lane verified to be built from current HEAD, to get a real, trustworthy e2e result.
4. The originally-filed hypothesis (JSONL header schema gap in hip-autotune-tuner.cu) should be re-examined ONLY if it still reproduces from a lane confirmed to be freshly built from current HEAD -- it may turn out record-mode and tune-mode header schemas are simply from different, non-contemporaneous commits and the schema itself is fine.

LIVE REPRODUCTION (2026-08-26, later same session): confirmed and escalated the root cause with a decisive, reproducible live test on Brutus.

1. Deleted `build/bigcherry-tune` and `build/bigcherry-record` entirely (487M/667M respectively) to force a genuinely from-scratch build.
2. Ran `bigcherry build --lane bigcherry:record:linux-multi --lane bigcherry:tune:linux-multi --lane llama-native:stock:linux-multi --lane bigcherry-native:control:linux-multi` (no --inventory, deliberately, to see tune fail closed on its real declared dependency -- it did, correctly: `FAILED -- build 'tune' input mismatch: missing=['inventory']`).
3. The other three lanes reported `ok` in under a second, with a 5-line total log (no ninja/cmake output at all). `bigcherry:record:linux-multi`'s reported `build_plan_id=37c7235fcf67b5197885027bffae993f` is IDENTICAL to a build_plan_id from an earlier build in this same session (before the directory was deleted). `find / -iname '*37c7235fcf67b5197885027bffae993f*'` across the whole Brutus filesystem returns nothing -- no artifact, no build directory, no cache file anywhere contains this ID except the campaign engine's own success report.
4. Cross-checked with `bigcherry pin-status`: vendor/llama.cpp is correctly pinned and consistent at `0adcc3bb5710` (tag b10502) -- so this is NOT a case of the canonical upstream checkout being stale (that part of the system works correctly, per its own verdict). The staleness is specific to whatever layer decides a given (source_slice, build_plan_id) is already 'done' and skips both compilation AND artifact re-publication, without checking the target build directory actually exists.

**This changes the fix's required scope.** The general-purpose agent's static-analysis pass (see Detailed Solution below) correctly identified `_source_attestation()` in `tools/bigcherry/campaign/workers.py` trusting a cached `<source_root>.metadata.json` without re-deriving live git facts as A real gap -- but live reproduction shows the deeper problem is at the BUILD-PLAN level, not just the source-materialization level: `tools/bigcherry/campaign/build.py`'s `materialize_source()`/`_materialize_source_locked()` (lines 325-430ish) DOES correctly re-verify `source_tree_oid` against live git before reusing a cached source directory (fail-closed design, confirmed by reading the code) -- that part looks sound. The bug is downstream of source materialization, in whatever decides a BUILD (not just the source slice) is already complete: something is persisting build-plan success across separate `bigcherry build` CLI invocations (separate OS processes) and treating a `build_plan_id` match as sufficient to report `ok` WITHOUT verifying the corresponding build directory/binary still physically exists on disk. `tools/bigcherry/campaign/execution.py`'s `make_artifact_reuse_checker()` explicitly does the right thing (verifies via `ArtifactStore.verify()`) but its own docstring states it is 'only valid within the same process/executor instance' and that cross-process resume 'needs persisted StageRecords and a way to rehydrate ArtifactRefs from disk, neither of which exists yet' -- yet we just observed exactly that cross-process reuse happening in production. Whatever mechanism IS doing this cross-process reuse was not yet located in this session and needs a real code trace of the `bigcherry build --lane` CLI entrypoint (tools/bigcherry/cli/main.py's build command handler) through to wherever build_plan_id gets checked against a persisted store BEFORE compilation is invoked, with a `git status`-style existence check added at that exact point (verify the destination directory/expected binary exists, not just that a plan_id string was seen before).

**Updated concrete next step**: trace `bigcherry build --lane` end-to-end (tools/bigcherry/cli/main.py -> campaign/build.py's top-level lane build function, NOT materialize_source specifically) to find the actual short-circuit that let `bigcherry:record:linux-multi` report `ok` in <1s with zero build output and no artifact on disk, for a build_plan_id that had never been built in this process's lifetime (fresh CLI invocation, fresh Python process). This is the real, still-open root cause. Do not assume it is the same code path documented in the Detailed Solution section below (materialize_source) -- that path was read directly and appears to fail closed correctly; the actual bug is elsewhere in the build-plan-level short-circuit.

FURTHER LIVE CONFIRMATION (2026-08-26, same session, ruling out alternate explanations): re-ran `bigcherry build --lane bigcherry:record:linux-multi` TWICE more after the finding above -- once with a unique `--run-id`, once with `--model <path> --hip-visible-devices 0` (the exact flags that DID trigger real ~10-minute ninja compilation earlier this session). Both times: identical result, `bigcherry:record:linux-multi: ok build_plan_id=37c7235fcf67b5197885027bffae993f workload_id=None`, single-line log, sub-second completion, `build/bigcherry-record/` never created on disk. This rules out (a) --run-id being part of the cache key, (b) --model being required to force a real build (workload_id staying None despite --model being passed shows the runtime-smoke validation path itself is also being skipped), and (c) this being expected 'plan-only, no --model' dry-run behavior. It is a real, deterministic, cross-process cache/short-circuit bug: given this exact source+patch+build-option identity, `bigcherry build --lane bigcherry:record:linux-multi` will NEVER compile again on this Brutus checkout no matter what flags are passed, despite the build directory not existing. `artifacts-store` (the ArtifactStore root referenced in tools/bigcherry/cli/build.py's `cmd_build_new`) does not exist anywhere on the Brutus filesystem either (`find` from repo root and from `/` both return nothing) -- so whatever is short-circuiting is NOT going through `ArtifactStore.verify()`/`make_artifact_reuse_checker()` (which would correctly fail closed against a missing store) -- it is a different, so-far-unlocated success-reporting path in `tools/bigcherry/campaign/planner.py`'s `plan()`/`run_campaign()` (both imported directly in cli/build.py's `cmd_build_new`) that decides to report `ok` for a lane without ever invoking a compiler. This should be the very next code-reading target: trace `run_campaign()` in campaign/planner.py to find where/why it returns a synthetic success `StageRecord` (build_plan_id computed but no executor dispatch) for this specific lane. Recommend a dedicated code-reading pass on planner.py specifically (not build.py/workers.py, which were already checked and look correct) before attempting any further live builds -- at this point every build in this session for bigcherry:record and bigcherry:tune lanes should be treated as UNVERIFIED/PROBABLY FAKE, including the ones earlier in this session that appeared to show real ninja output (those had different build_plan_ids from a still-earlier point and may have been genuinely real -- but this specific plan_id, once computed once, now short-circuits permanently). No further live GPU/build validation attempted after this finding -- the build result itself cannot be trusted until this is root-caused in code, so any downstream GPU capture would be validating against an unknown/possibly-wrong binary.

RESOLVED (partially), 2026-08-26, commit 2a88de9: confirmed and fixed a real P0 concurrency defect via a deep-review round-trip with reviewer-gpt-agent.

**Confirmed root cause of the CONCURRENCY-CORRUPTION half of this investigation**: `tools/bigcherry/core/resources.py`'s `ResourceLock.release()` had no ownership check -- it deleted whatever `owner.json`/lock directory it found at `self.path`, regardless of whether THIS instance's `acquire()` had ever succeeded. `campaign/campaign.py`'s `CampaignRun.execute()` builds a `ResourceLock` object for every resource claim a stage declares and, in its `finally` block, calls `release()` on every one of them whose `inspect()` shows a live lock -- including locks this process never actually acquired (e.g. because a contending process already held it and `acquire()` raised `ResourceError`). Under real contention (this Brutus tree is a documented shared multi-agent working tree, `AGENTS.md`), a losing process's cleanup could therefore delete the WINNING process's still-live build lock mid-compile, letting a third process acquire the same `build-<build_plan_id>.lock` resource and start building into the same content-addressed directory while the first process was still using it -- a real mechanism for corrupted/mixed build outputs under concurrent bigcherry build invocations.

**Fix (commit 2a88de9)**: `ResourceLock` now tracks `self._acquired`, set `True` only on a successful `acquire()` and cleared on `release()`; `release()` is a no-op unless `self._acquired` is `True`, so a losing contender can never delete a lock it doesn't own. Added `tools/tests/campaign/test_campaign_graph.py::test_release_never_deletes_a_lock_this_instance_did_not_acquire`, which reproduces exactly this scenario (winner acquires, loser's acquire() raises, loser's release() must not touch the winner's live lock, a third contender must still see the resource as claimed) -- verified this test fails without the fix and passes with it. Full offline suite: 1986/1986 passing (1985 baseline + 1 new), `OK (skipped=7)`.

**NOT yet explained -- item stays open for this**: the original live-reproduced symptom that started this investigation -- `bigcherry build --lane bigcherry:record:linux-multi` returning `ok build_plan_id=<X>` in under a second with ZERO compilation and no artifact anywhere on disk (confirmed via `find` across the correct `~/.cache/bigcherry` work_root, not the legacy `repo/build/` path this investigation initially and wrongly checked) -- is NOT fully explained by the lock-ownership bug above. reviewer-gpt-agent traced the single-process control flow (`plan()` -> `run_campaign()` -> `execute_campaign_lane()` -> `PipelineService` -> `make_build_worker().run_build()`) exhaustively and confirmed there is no code path in it that can print `ok` without either a cache-hit against a REAL validated existing binary or a real compile+link; contention on the build lock makes the LOSING process's stage `failed`/`blocked`, never `ok`. When the exact same build_plan_id was reproduced from a genuinely empty cache, it DID compile for real (~10 min, full ninja log) and land at the expected `~/.cache/bigcherry/builds/<slice>/<plan>/` path -- so the deterministic ID computation and the normal cache-hit/build logic are both confirmed correct in isolation.

Open question: was the earlier instant-fake-`ok` a transient effect of the now-fixed lock bug in a way not yet precisely modeled (e.g. a losing contender's stage somehow still recording `succeeded`/`reused` rather than `failed` under some interleaving not yet traced), or a separate, still-unlocated issue? Lower priority now that the more severe corruption bug (a lock being stolen out from under an in-progress build) is fixed -- but if it recurs, capture a live repro (build_plan_id, exact timing of any concurrent `bigcherry build` invocations from other sessions on the same Brutus host, and the full stdout/stderr of the offending invocation) before further live debugging, since single-process static analysis has now been exhausted twice without finding a matching code path.
