# UP-VK-005: Vulkan tensor-parallel AllReduce -- upstream PR/issue tracking and BigCherry adoption path

## Description

BigCherry's dual-XTX production profile uses `-sm tensor` (RCCL/HIP tensor-parallel), and GP13's investigation this session established that Vulkan cannot do the equivalent today -- but the gap is narrower and more actively worked than an initial source scan suggested, and there is real, verified upstream prior art worth adopting rather than building from scratch.

**Initial (incomplete) finding**: direct inspection of the current llama.cpp vendor tree found `-sm tensor`'s cross-GPU AllReduce (`ggml_backend_cuda_comm_allreduce_nccl/_internal/_tensor` in `ggml-cuda.cu`) is CUDA/HIP-only; `ggml-vulkan.cpp` has zero occurrences of `split_buffer_type`, `SPLIT_MODE_TENSOR`, or any `comm_allreduce`-equivalent. `-sm row` also fails outright on our HIP build ("device ROCm0 does not support split buffers"), confirming split-mode support is uneven even within a single backend.

**Corrected finding (via dev-gpt-agent research, all citations independently verified against live GitHub state with `gh pr view`/`gh issue view` before being trusted -- five of five checked out exactly as described)**: upstream has NOT stood still on this.

- **PR #19378** (merged 2026-04-09) -- "ggml: backend-agnostic tensor parallelism (experimental)". Added a generic, backend-agnostic AllReduce fallback via a meta-backend, so `-sm tensor` can technically execute on ANY backend today, including Vulkan -- just through a slow, CPU-barriered generic path, not a Vulkan-native one. This single PR invalidates the naive "Vulkan has no comm_allreduce therefore -sm tensor cannot run on Vulkan" conclusion.
- **Issue #22648** (open) -- "vulkan tensor parallelism support", the dedicated Vulkan TP tracker. Confirms the generic fallback is "crazy slow, especially on vulkan" and has segfaulted. Links a working experimental fork (TheBlueMatt/llama.cpp:claude-tensor-par) which the branch author says they left unfinished after getting pulled onto unrelated Mesa optimization work -- not abandoned due to rejection.
- **PR #22514** (merged 2026-04-30) -- added Vulkan `get/set_tensor_2d` ops explicitly for TP support.
- **PR #23480** (merged 2026-05-29) -- fixed a real correctness bug (corrupted output) in the generic meta-backend AllReduce fallback specifically on Vulkan.
- **Issue #22197** (open) -- "ggml-backend-meta: multi buffers are unsupported leading to vulkan segfault". THIS is the real structural blocker: the graph allocator assumes a 1:1 abstract-buffer-to-physical-buffer mapping; tensor parallelism fundamentally needs one abstract buffer mapped to multiple physical buffers. Per gpt-dev-agent's research, maintainer JohannesGaessler's objection to PR #25051 was specifically about this allocator model, not about Vulkan TP being unwanted.
- **PR #25051** (open draft) -- "vulkan: add allreduce function with cross-device CPU proxy and fix Tensor Parallel crash [EXPERIMENTAL]". The actual answer to "is anyone building this": a real Vulkan-specialized AllReduce (GPU-pipelined, host-staged transfers, timeline-semaphore synchronization, chunked/overlapped), author-reported ~2.5-3x over the generic fallback. Also attempted direct cross-device memory import via `VkImportMemoryFdInfoKHR`, which was correctly identified as invalid Vulkan usage (that extension requires the exported memory to originate on the same physical device) -- real P2P would need device groups or a future vendor extension, not this approach.
- **Discussion #22463** (open) -- community discussion explicitly about improving Vulkan multi-GPU/TP, cross-links #22648/#22197/#25051.

**Vulkan API-level assessment** (architectural reasoning from the research, not a direct citation -- treat as sound but slightly lower-confidence than the PR/issue facts above): Vulkan already has what a *correct* (if not maximally fast) AllReduce needs -- `VK_KHR_device_group` (core since 1.1, multi-physical-GPU under one logical device, `vkGetDeviceGroupPeerMemoryFeatures()`), timeline semaphores, and external memory/semaphore sharing -- PR #25051 proves this by existing. What's missing is (a) a standardized NCCL/RCCL-equivalent collective API at the Vulkan level (there isn't one, cross-vendor), and (b) universal, portable direct GPU<->GPU P2P -- device groups are the standards-compliant route but are narrower than CUDA/HIP peer access.

**Maintainer intent**: no evidence this is a stated non-goal. Evidence points to "wanted, experimental, blocked on the allocator refactor (#22197), under-resourced" -- current docs keep `-sm tensor` marked experimental and explicitly warn only CUDA/NVIDIA has expected good performance, which is consistent with active-but-incomplete rather than abandoned.

**Third-party prior art** (lower confidence, architectural relevance only): MLC LLM / Apache TVM has `tensor_parallel_shards` and a real Disco distributed runtime with AllReduce/AllGather/Broadcast/Scatter abstractions, but its optimized collective implementations wire NCCL/CUDA IPC under CUDA -- no confirmed production Vulkan-native NCCL-equivalent collective was found anywhere. MLC issue #3487 reproduces `tensor_parallel_shards=2` failing on two AMD GPUs via Vulkan (illegal SPIR-V barrier in TVM's compilation), which proves Vulkan TP is an exercised/intended path elsewhere too, but not that the collective problem is solved there either.

**Relationship to existing plan items**: this sits alongside RD55/RD59/RD60/RD65 (UP-VK-001..004, individual Vulkan kernel-correctness/perf ports) but is a materially larger, structural undertaking (graph allocator model change, not a kernel swap) -- and it directly bears on RD57's still-open, user-deferred question about whether a third backend lane should generalize RE30's Vulkan-build-stream scope. This item should be resolved/considered together with that decision, not in isolation. Also relevant: GP13 (Brutus PCIe P2P DMA kernel patch) established that even HIP/CUDA's own P2P story is topology-fragile and needs correctness re-verification per platform -- any Vulkan P2P work inherits the same caution (verify actual data movement, not just capability-reporting).

## Steps

1. Do NOT attempt to build a Vulkan AllReduce from scratch. First decide (with RD57's deferred backend-lane-scoping question) whether Vulkan TP is in scope for BigCherry at all, given production currently runs HIP/RCCL exclusively and no BigCherry build has `GGML_VULKAN=ON`.
2. If in scope: assess rebasing/cherry-picking onto the post-#19378 meta-backend architecture as pinned in BigCherry's vendor llama.cpp tree (check current pin's ancestry against 2026-04-09 first -- RD68 already established the discipline of verifying Vulkan baseline PRs are ancestral before any Vulkan lane work; apply the same check here for #19378/#22514/#23480).
3. Treat PR #25051 as prior art / a code source for the Vulkan-native AllReduce (GPU-pipelined, host-staged, timeline-semaphore design), NOT as a mergeable dependency -- it is an open draft with a rejected allocator workaround bundled in; extract only the AllReduce mechanism, not the multi-buffer allocator hack.
4. The real, upstream-relevant, scoped contribution opportunity (if BigCherry wants to invest here rather than just wait) is Issue #22197's allocator fix: generalizing the graph allocator's abstract-buffer-to-physical-buffer mapping from 1:1 to 1:N. This is the actual blocker maintainers want solved before Vulkan TP can land cleanly upstream.
5. Before any implementation work: re-verify all citations above against current GitHub state (they were verified 2026-09-05; PR/issue states change) -- do not trust this document's citations as still-current without a fresh check if picked up much later.
6. If pursued, apply GP13's correctness discipline: any Vulkan cross-device data movement must be validated with the same per-element sentinel-pattern approach as `tools/tests/fixtures/hardware/p2p_copy_correctness_test.cpp`, not just capability queries -- "reports success but copies wrong data" is a demonstrated real failure mode on this project's actual GPU fleet, not a hypothetical.
