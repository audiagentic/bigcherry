# HI54: isolated pool-cache clear/rebase protocol (exact placement invariant)

## Description

Pre-reset time_candidate() had an exact protocol for isolated (non-interleaved) workspace measurement: clear the legacy pool reuse cache BEFORE warmup (not after), let warmup perform and cache the candidate's own real allocation, then rebase the pool high-water mark to the post-warmup baseline before timing. Getting the clear/rebase ordering wrong corrupts the very measurement HI40 exists to produce -- clearing after warmup makes the first timed sample pay a fresh allocation and inflates its own workspace measurement.

## Steps



## Detailed Solution & Technical Design

Sequence (from BigCherry_Missed_Work_Addendum.md section 5, addendum's own source pointer: pre-reset ~record 1673):

```
isolated candidate measurement only:
    clear legacy pool reuse cache      <- BEFORE warmup
warmup candidate (performs its own allocation, returns it to cache)
sync
reset/rebase pool high-water mark to live baseline
time samples                            <- reuses the candidate's own cached buffer
```

Why before warmup: clear -> warmup allocates -> warmup returns that exact-sized buffer to the pool's reuse cache -> timed samples reuse the candidate's own buffer, so what's being measured is genuinely this candidate's steady-state footprint, not a cold-allocation artifact.

Why only at isolated sites: final/confirmation rounds intentionally interleave candidates and deliberately share cache state (this is what makes interleaved timing comparable across candidates in the same round -- see HI34/HI12's interleaving rationale). Clearing there would repeatedly evict buffers other candidates in the same round still need, corrupting THEIR measurements instead.

Invariants to preserve exactly when this lands (do not treat as a generic allocator optimization -- it is part of the measurement model):
- `bc_workspace_clear_cache()` only at isolated pool-peak-evidence sites, never during interleaved final/confirmation rounds.
- call before warmup, not after.
- warmup completes and synchronizes before the rebase.
- `bc_workspace_reset_peak()` (or equivalent) runs after warmup, capturing the live baseline.
- recorded peak is the candidate's increment over that baseline, not an absolute pool size.
