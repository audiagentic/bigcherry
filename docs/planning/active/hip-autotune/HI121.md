# Dispatch signature identity v3: two-axis semantic content + producer capability model

## Description

Follow-up to HI119's schema-v2 bump (2026-08-25). That bump fixed a real bug (a pre-HI118 schema-1 signature's flags==0 in bits 7-10 cannot be trusted to mean 'no bias/scale') but did so by folding `schema_version` into the flat semantic-digest hash, which invalidates EVERY signature's digest on any bump, not just the op classes actually affected by the reinterpretation that motivated it.

Two rounds of adversarial review with dev-gpt-agent (same session as HI119's review, 2026-08-25/26) converged on a corrected architecture: separate 'what this dispatch actually has' (semantic content, stays hashed) from 'what this producer's code knew how to correctly evaluate' (producer capabilities, a new non-hashed compatibility gate) -- two independent bitsets, not one bitmap replacing schema_version. gpt-dev-agent's own first answer proposed a single wide capability bitmap and initially recommended deferring implementation to a future schema bump; after direct pushback (my own objection: one bitmap can't carry both 'value' and 'was this ever evaluated' without ambiguity) it retracted that recommendation and endorsed building the two-axis model now, specifically because we are mid-migration (schema-v2 hardware revalidation not yet done) and waiting would mean doing the hardware pass twice.

This item is the live design-and-build doc for that redesign, iterated collaboratively with dev-gpt-agent via the ag-agents-gateway review loop (adversarial, not rubber-stamp) rather than decided unilaterally. Committed and pushed after each real revision so dev-gpt-agent (GitHub-only access) can read the current state directly.

### THE BLOCKER: source-pattern-matching is not strong enough capability authority -- amend before M0
Round 7's `derive_producer_capabilities(root)` (grant a capability when Python's source-text inspection sees both the enum bit and the matching evaluator assignment) has a real false-positive failure mode, distinct from the safe false-negative case:
- Refactor moves/renames the assignment -> parser misses it -> false NEGATIVE -> unnecessary rerun -> SAFE.
- Assignment's exact text still matches, but the surrounding predicate became wrong / the assignment became unreachable / the value is later overwritten / a helper's semantics changed / the wrong fusion object is inspected -> parser still grants the capability -> false POSITIVE -> **unsafe measurement reuse**. Unacceptable, since a capability bit IS a permission grant.

**Required amendment**: replace behavioral source-text inspection with an explicit, source-OWNED, self-declared capability constant -- NOT full C++ runtime producer_capabilities[128] machinery, just a small compile-time declaration:
```c
// hip-autotune-types.h -- amends round 6's 'no C++ code' claim with this one small addition
#define GGML_HIP_PRODUCER_CAPABILITIES_LO UINT64_C(0x000000000000001f)
#define GGML_HIP_PRODUCER_CAPABILITIES_HI UINT64_C(0x0000000000000000)
```
Python parses this DECLARATION (not behavior) from the materialized source root. The compiled record/tuner producer ALSO emits these same two values in its JSON header. New authority chain:
```
source-owned capability declaration (the #define above)
  -> Python manifest generation reads the declaration (not source behavior)
  -> manifest/hash/descriptor bind it
  -> compiled producer emits the SAME declaration in its own header
  -> ingest requires: producer header mask == manifest mask (closes a real second gap too --
     see M2 gate below)
```
Why this is strictly better: a semantically-neutral refactor no longer changes capability detection at all (the declaration doesn't move just because code around it does); when evaluator semantics genuinely change or a bug is found, the declaration itself changes from CAP_X_V1 to CAP_X_V2, exactly matching the already-designed governance model (round 4's Finding 5). Focused signature-construction tests then validate the declaration is TRUTHFUL (does the compiled behavior really match what's declared) -- regex is no longer being asked to prove semantic correctness by itself, only to read an explicit assertion and the tests separately verify that assertion holds.

This does not touch production dispatch, replay, resolver, kernel launch, or any hot path -- it is a metadata-only compile-time constant, consistent with the spirit (if not the letter) of 'no C++ runtime capability code'.

### M2 gate strengthened (closes a second real gap the original gate missed)
Original round-7 gate (tamper the manifest's capability mask post hoc, expect rejection) only proves post-generation tampering resistance. It does NOT catch: manifest generated from source root B, but the actual compiled binary was built from source root A, while manifest B remains internally self-consistent -- with source-inspection-only authority, ingest cannot detect this mismatch at all. The compile-time self-report above closes this directly. **New highest-signal M2 gate**: root A declares capability mask A, root B declares mask B; generate the manifest from root B; have the (real or simulated) producer artifact/header report compiled mask A; attempt ingest -> must REJECT, no `build_capability` row written. Also require ALL of: `header.producer_capabilities == manifest.producer_capabilities`, `header.manifest_hash == manifest.manifest_hash`, `header.build_descriptor_hash == manifest.build_descriptor.descriptor_hash`.

### Real, concrete value (not manufactured) -- what becomes possible that isn't safe today
1. **Selective measurement reuse**: today, ANY schema-adjacent change rejects every measurement globally. With capabilities: `required_caps(plain MUL_MAT) = CORE` means an old plain-MUL_MAT measurement stays usable across a bump that only adds fusion-presence knowledge; only rows whose op-class actually needed the new knowledge (e.g. fused GLU) get correctly rejected. 2. **Targeted evaluator revocation**: if a capability's detection logic (e.g. HI118's own X_BIAS/GATE_BIAS/X_SCALE/GATE_SCALE checks) is later found buggy, `CAP_X_V1 -> CAP_X_V2` invalidates only the dependent measurements -- today's only tool for this is another blanket schema bump.
3. **Durable multi-generation measurement store**: the DB can hold measurements from producers at different capability/knowledge levels simultaneously and let each consumer (a specific target build) select only what's semantically valid for it -- real reuse across sessions/builds, not just within one.
4. **Vulkan backend (strongest future-feature case)**: vk-autotune-types.h already mirrors HIP's OLD linear-schema-version design and is still unintegrated scaffolding (not yet operational). Adopting the two-axis model for HIP now, before Vulkan's runtime work goes live, avoids Vulkan accumulating the exact same debt HIP just had to pay down mid-session.

- Kernel A/B or canary rollout: BigCherry already has candidate identity, generations, per-entry provenance -- capabilities only matter there if the rollout ALSO changes signature interpretation, which most rollouts won't.

- Mixed-fleet single-shared-cache serving: possible, but only with the heavier per-entry runtime design (S3/S4) -- not needed if each target build gets its own target-specific replay export instead (see M4 below).

Revised smallest-useful-implementation, capturing the real value above without touching the production C++ resolver at all:
```
M0 -- Freeze signature identity epoch at 2. New policy: additive/scoped semantic fields do NOT
      bump epoch; epoch changes only for genuine incompatible canonicalization-algorithm changes.

      keep only rows where (exact semantic digest) AND (producer_caps superset required_caps);
      omit/rerun everything else. The resulting cache is an ORDINARY v5 replay cache -- the

```
Key framing: **measurement DB = durable multi-generation knowledge store; replay cache = a cheap, target-specific PROJECTION of only the measurements safe for that one binary.** This captures the real value (selective reuse, clean revocation, multi-generation storage, Vulkan groundwork) while keeping the production resolver exactly as simple and fail-closed as it is today. **New governance rule, added as a hard requirement, not optional:** capability meanings are immutable once allocated (matches the existing append-only registry rule) -- a discovered evaluator bug is handled by (1) allocating a NEW corrected bit `CAP_X_V2` (never redefining `CAP_X_V1`), (2) `required_capabilities()` is updated to require V2 going forward, (3) V1 stays permanently tombstoned/historical, never redefined, (4) every V1-only row fails closed under the new requirement unless separately revalidated/re-attested. Deliberately conservative default: invalidate ALL V1-claiming measurements for that capability rather than building a fine-grained allow/deny list for 'only the actually-buggy subset' -- the existing per-entry provenance (manifest_hash, source_revision_digest, generation) already preserves the ability to do selective forensic recovery later if that ever proves worth building.

## Agreed target architecture (dev-gpt-agent, round 2, after adversarial pushback)

Two independent axes, not one bitmap:

1. **Semantic content flags** (existing `flags` field, extended as needed) -- 'this dispatch actually HAS property X'. Stays in the hashed canonical representation. This is what `flags` already correctly does today.
2. **`producer_capabilities`** (NEW, proposed 128 bits / 2x uint64_t) -- 'this producer's code knew how to correctly determine X'. NOT part of the semantic digest. Used only as a compatibility gate at lookup time: `(producer_caps & required_capabilities(signature)) == required_capabilities(signature)`.

`required_capabilities(signature)` must be computed from whether a semantic question COULD apply to this signature's class (op/fusion kind/etc), not from whether the currently-observed flags happen to show the property set -- getting this backwards recreates the exact 'zero means absent or unknown' ambiguity one level up.

### Today's real (not speculative) capability allocation
- `cap0 = CORE_SIGNATURE_V1`: producer correctly evaluates all original v1 identity (op/types/prec, coarse fusion+glu_op, extents/strides, expert counts, flags bits 0-6). Every historical schema-1 producer implicitly has this.
- `cap1 = FUSION_AUX_PRESENCE_V1`: producer explicitly evaluates x_bias/gate_bias/x_scale/gate_scale (HI118), making flags bits 7-10 authoritative rather than 'maybe just not implemented yet'. Only schema-2-and-later producers have this.

Worked examples (confirmed against real fields):
- Plain Q8_0 MUL_MAT: `required = CORE_SIGNATURE_V1` only (fusion genuinely inapplicable) -- a schema-1 measurement remains reusable under this model, unlike the blanket v1->v2 bump that invalidated it anyway.
- Real HI108 routed fused GLU (fusion=GATE, no bias/scale): `required = CORE_SIGNATURE_V1 | FUSION_AUX_PRESENCE_V1` -- an old schema-1 producer's zero bits 7-10 are NOT authoritative, so this measurement genuinely needs re-evaluation regardless of the two-axis model (this part of the v1->v2 invalidation was real, not collateral).
- Fused GLU with gate bias (hypothetical, not currently in production per HI108's GGUF inspection): content flags differ (FUSION_GATE_BIAS set) so digest naturally differs anyway; also requires FUSION_AUX_PRESENCE_V1.

### Versioning axes that remain, now cleanly separated by purpose
- `GGML_HIP_REPLAY_VERSION`: physical replay-cache byte layout (currently 5) -- unrelated to semantic content.
- Semantic canonicalization/encoding algorithm version: changes only when the canonicalization ALGORITHM itself changes (not when a new capability is added) -- expected to change extremely rarely.
- dispatch_db SQL schema_version (currently 6): physical/logical DB schema, independent axis, already separate.

### Migration strategy for schema_version's CURRENT value (open decision, not yet made)
Two options identified, not yet chosen:
- **(A) Clean break now**: remove schema_version from canonical semantics entirely, rehash everything under the new identity model, add producer_capabilities from scratch. Architecturally cleaner, one more digest migration on top of the v1->v2 one just shipped.
- **(B) Freeze current value**: keep schema_version=2 permanently as a fixed 'identity_epoch' inside canonical identity (never incremented again for capability additions); producer_capabilities takes over all FUTURE compatibility decisions. Minimizes immediate disruption, leaves one historical wart.

gpt-dev-agent's live recommendation (round 2): (A), specifically because schema-v2 hardware revalidation has not yet happened -- doing (A) after that revalidation would waste the hardware pass a second time. Not yet independently verified/challenged by a further round -- flag for the next discussion round.

### Proposed build scope (gpt-dev-agent's round-2 proposal, not yet critiqued further)
1. Semantic signature: remove schema_version from canonical semantics; flags remain actual-property bits; future boolean semantic additions consume content bits; future non-boolean fields scoped to applicable op/domain sections only (not unconditionally hashed for every signature).
2. Producer capabilities: 128 bits (2x uint64_t), cap0=CORE_SIGNATURE_V1, cap1=FUSION_AUX_PRESENCE_V1, append-only allocation registry (mirroring dispatch_abi.py's own C++/Python agreement-test pattern) -- numeric IDs permanent, never renamed, retired bits tombstoned not reused.
3. Record/DB: record producer_capabilities per build row; historical schema-1 rows map to CORE_SIGNATURE_V1 only, schema-2 rows map to CORE_SIGNATURE_V1|FUSION_AUX_PRESENCE_V1.
4. Replay: v6 entry format carries producer_capabilities PER ENTRY, not cache-global -- replay already retains per-entry generation/provenance, and a merged cache can contain entries from producers with different capability levels.
5. Lookup: exact semantic digest match, AND `(producer_caps & required_caps(signature)) == required_caps(signature)`, AND existing candidate/provenance/can_execute gates (unchanged).
6. Physical versioning: retain GGML_HIP_REPLAY_VERSION and DB schema_version as-is; add/freeze a separate non-hashed semantic-encoding-format identifier only if truly needed (not yet established that it is).
