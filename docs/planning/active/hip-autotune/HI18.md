# Tune the multi-device allreduce algorithm (SPLIT_REDUCE)

## Description

`ggml-cuda.cu` selects one of three allreduce implementations at backend
construction and never revisits the choice
([ggml-cuda.cu:1135-1195](../../../../vendor/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu#L1135-L1195)):

```text
ggml_backend_cuda_comm_try_allreduce_butterfly    (assigned first)
ggml_backend_cuda_comm_try_allreduce_internal     (conditionally overrides)
ggml_backend_cuda_comm_try_allreduce_nccl         (conditionally overrides)
```

Three real implementations, one static selection, zero measurement. This sits
directly on the path of the configuration the project exists to optimise: 2× XTX,
`split_mode tensor`, RCCL enabled. Every tensor-split matmul pays this cost and
none of it is currently attributed.

## Candidate identity

```text
(preferred_algorithm, fallback_policy)
```

`device_count` and `topology` are **execution context**, not candidate identity —
they describe the machine, not the choice. They belong in the hardware key and
in eligibility, alongside peer accessibility, reduction element type and count,
and split geometry.

Initial candidate set:

```text
(nccl,      none)
(internal,  none)
(butterfly, none)
(nccl,      internal_then_butterfly)
(internal,  butterfly)
(auto,      upstream_default)
```

## Steps

- Add a SPLIT_REDUCE family and its collection point at the allreduce call, with
  the existing `ggml_hip_dispatch_scope` re-entrancy guard
- Define a reduction signature: element type, element count, device count,
  topology, split geometry, peer accessibility. This is **not** a matmul
  signature — it needs its own struct and its own key
- Make `try_allreduce` selectable per call rather than fixed at backend
  construction, via a defaulted parameter (Option C)
- Implement the three `fallback_policy = none` candidates first — these are the
  measurement candidates
- Record `observed.reduce_algorithm`, `observed.fallback_depth` and
  `observed.fallback_chain` on every call
- Only then add the fallback-enabled candidates, which reproduce production
  resilience
- Extend the hardware key so a 2-device topology and a 4-device topology do not
  share a winner

## Detailed Solution & Technical Design

The fallback-enabled candidates are **inadmissible as evidence about an
algorithm** unless actual-path telemetry is recorded. `winner = nccl` is false
if the call fell through to butterfly, and the failure is silent — a fallback
chain reports success either way. So telemetry is a prerequisite for those
candidates, not a follow-up: implement the `none` variants and the telemetry
first, and gate the fallback variants behind it.

The static selection at backend construction is the reason this is invisible
today. Making it per-call is the whole mechanism; the rest is signature and
eligibility work.

Measurement is harder than for matmul: an allreduce spans devices, so
complete-path timing (standards 7.1) must cover the slowest participant, not the
launching one. Time the operation from the host across a device-wide sync rather
than with per-device events, and record which device was the straggler.

## Validation

- On the 2× XTX rig with `-sm tensor`, all three algorithms produce bitwise or
  tolerance-equal results against the native path
- `observed.reduce_algorithm` matches the requested algorithm for every
  `fallback_policy = none` candidate; any mismatch fails the run rather than
  being recorded
- A fallback-enabled candidate that actually falls back records a non-zero
  `fallback_depth` and is excluded from algorithm-level conclusions
- Single-device runs generate no SPLIT_REDUCE candidates at all
- Disabling RCCL at build time removes the `nccl` candidates from the manifest
  rather than producing eligible-but-failing ones

## Effort & Risk

Medium-high risk, and the risk is measurement validity rather than
implementation. A multi-device operation is easy to time wrongly — the launching
device finishing is not the operation finishing. Verify the timing methodology
against a deliberately imbalanced split before trusting any winner.

Requires the 2-GPU server; cannot be validated on the single-GPU workstation.

## Standards
