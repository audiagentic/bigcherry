# Tune the multi-device allreduce algorithm (SPLIT_REDUCE)

## Description

The reduction signature and strict telemetry contract are complete, and REDUCE-1 now provides opt-in per-call AUTO/RCCL/META provider selection without mutating the shared communication context. The default `GGML_HIP_REDUCE_PLAN=auto` path preserves the established provider/fallback behavior. Complete-path timing, explicit-plan correctness comparison, topology-aware hardware-key integration, candidate measurement, and promotion remain open. The pinned Brutus HIP backend does not support row-split buffers; validated HI18 evidence uses the working two-GPU tensor-split path.

## Steps

- Add a SPLIT_REDUCE family and its collection point at the allreduce call, retaining the existing `ggml_hip_dispatch_scope` re-entrancy guard.
- **Implemented first runtime contract:** define a reduction-only signature separate from matmul identity. The producer records version 1 element count/type, four-dimensional slice geometry, a topology key from `hipDeviceCanAccessPeer`, and complete/partial/unknown peer-access status. The key excludes raw device ordinals so later hardware grouping can remain topology-based.
- Validate the signature offline before candidate normalization: require version and cross-field agreement, reject malformed shape/topology values, derive a stable signature key, and mark unknown peer accessibility non-promotable.
- Define the remaining reduction signature inputs: device count, topology, split geometry and peer accessibility. Keep raw ordinals as evidence only; do not put them in candidate identity.
- [x] Make `try_allreduce` selectable per call rather than fixed at backend construction, via the opt-in `GGML_HIP_REDUCE_PLAN=auto|rccl|meta` seam; the default AUTO path preserves production behavior.
- [x] Add an opt-in `GGML_HIP_REDUCE_TIMING=sync` telemetry mode that synchronizes every participating HIP device, restores the caller's device, and labels synchronization failures non-promotable; keep host-control timing as the default.
- Implement the three `fallback_policy = none` candidates first — these are the measurement candidates.
- Record `observed.reduce_algorithm`, `observed.fallback_depth` and `observed.fallback_chain` on every call.
- Only then add fallback-enabled candidates, which reproduce production resilience.
- Extend the hardware key so a 2-device topology and a 4-device topology do not share a winner.

## Detailed Solution & Technical Design

The fallback-enabled candidates are **inadmissible as evidence about an
algorithm** unless actual-path telemetry is recorded. `winner = nccl` is false
if the call fell through to butterfly, and the failure is silent — a fallback
chain reports success either way. So telemetry is a prerequisite for those
candidates, not a follow-up: implement the `none` variants and the telemetry
first, and gate the fallback variants behind it.

The static selection at backend construction is the reason this is invisible
today. Making it per-call is the whole mechanism; the rest is signature and
eligibility work.

Measurement is harder than for matmul: an allreduce spans devices, so
complete-path timing (standards 7.1) must cover the slowest participant, not the
launching one. Time the operation from the host across a device-wide sync rather
than with per-device events, and record which device was the straggler.

## Effort & Risk

Medium-high risk, and the risk is measurement validity rather than
implementation. A multi-device operation is easy to time wrongly — the launching
device finishing is not the operation finishing. Verify the timing methodology
against a deliberately imbalanced split before trusting any winner.

Requires the 2-GPU server; cannot be validated on the single-GPU workstation.
