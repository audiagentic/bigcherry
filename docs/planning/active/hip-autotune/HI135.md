# Unexplained intra-device Rect copy triggered by 6900XT presence in tensor-split topology

## Description

Real, reproducible finding from HI134's investigation (which was scoped to META's reduction path and explicitly excludes this): under -sm tensor with the RDNA2 6900XT (physical device 3) participating in the device group, a same-device (intra-GPU) __amd_rocclr_copyBufferRectAligned copy occurs on the OTHER devices (the RDNA3 XTX pair, ranks 0/1) -- NOT on the 6900XT itself. ~250-258 calls per profiled pass, 2.5-3.4ms mean duration each (up to ~9.5ms p95), ~650ms-860ms total per pass. Decisively established as unrelated to META's reduction transfers: real memory_copy_trace.csv analysis (hi134-stage-attribution-01) shows META's actual FOLD/BUTTERFLY/COPY_BACK transfers are all host-staged HOST_TO_DEVICE/DEVICE_TO_HOST copies (no P2P on this box, per HI84) in the thousands per pass, scaling linearly with the real reduction count -- entirely separate from the 250 DEVICE_TO_DEVICE same-agent (source==destination) copies that match the Rect count exactly.

## Steps

1. Confirmed present: -sm tensor + device 3 (6900XT) anywhere in the group, {0,1,3} and {0,1,2,3} (both HI134 profile-campaign runs).
2. Confirmed absent: {0,1,2} (no 6900XT), and {0,1,3} under -sm layer (never touches comm_ctx/META at all) -- so it requires BOTH tensor-split AND the 6900XT's presence, but the copy itself executes on the XTX devices, not the 6900XT.
3. Not yet investigated: what actually triggers this copy. Candidate causes to check first: tensor-split shard/weight buffer allocation or layout differences specific to a heterogeneous (mixed-arch) device group (e.g. a different buffer pool/alignment path chosen when device capabilities differ across the group), KV-cache/context buffer management specific to tensor-split with a mixed-arch group, or a scheduler/backend-sched buffer-repacking step unrelated to allreduce.
4. Correlate against hip_api_trace.csv / correlation IDs in the same profiled window to find the actual call site (which ggml op or buffer-management function issues this copy) -- same rocprofv3 --sys-trace artifacts already on Brutus for hi134-stage-attribution-01 can be reused, or a fresh short capture.
5. Once attributed to a real call site, assess whether it's on the critical path (exposed) or hidden under other GPU work before considering it worth fixing.
