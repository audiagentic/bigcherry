# bigcherry tune-campaign: single-command record->tune->correctness->promote->replay orchestrator

## Description

Turn the full manual record -> tune -> correctness-evidence -> promote -> replay-export -> replay-verify pipeline (validated end-to-end by hand this session on Brutus, real dual-XTX + single-GPU R9700 runs, 20/39 candidates genuinely promoted with real correctness evidence) into a single repeatable, deterministic `bigcherry tune-campaign` command, so it can be kicked off as a standard workflow rather than requiring an operator/agent to manually chain ~12 commands and work around several real gotchas live.

Design direction confirmed via reviewer-gpt-agent consultation (2026-08-27, session ses_fec603fc33ee4089): implement as a new production orchestrator, NOT a promotion of the existing tools/bigcherry/e2e_smoke_campaign.py unchanged (that file encodes smoke-only policy -- HIP_LAUNCH_BLOCKING=1, reduced final-samples -- but already proves the record->inventory->tune->DB->promote->correctness->re-promote->export->replay sequencing works and its server-lifecycle/request-runner code should be extracted and reused).

## Steps

1. New module tools/bigcherry/tuning/workflow.py implementing the full orchestration (record build -> run record server -> inventory -> tune build -> run tune server -> DB load -> first tune_promotion.promote() -> for rejected_no_correctness_evidence candidates: correctness build (tune lane + experiment=hi105-correctness + bin/test-backend-ops) -> generate evidence via HI80 library functions against the correctness build's own isolated source_root -> re-promote -> tuning.replay.build() using the TUNE build's own manifest_ref (not a regenerated manifest) -> replay build with inventory+promoted winners -> replay verification run).
2. Thin CLI wrapper: tools/bigcherry/cli/tuning.py::cmd_tune_campaign, new `bigcherry tune-campaign --model M --platform P --devices D --runtime-profile NAME [--workdir DIR]` subcommand wired into cli/main.py.
3. Expose `source_root` on CampaignLaneResult (already exists internally as _MaterializedLaneSource.source_root) so the correctness-evidence step's --llama-root can be read directly from the correctness build's own lane result instead of searching ~/.cache/bigcherry/sources/ by mtime.
4. Persist one workflow receipt per campaign run containing every build/source/artifact identity (run_id, source_slice_id, build_plan_id per stage, manifest_ref, dispatch cache path, promoted count, effective runtime-profile/context) -- add `build --json` / a persisted lane-result.json so this data is actually capturable (current CLI only prints build_plan_id/workload_id to stdout).
5. Fix releases/*.json false-dirty noise at its root cause: ReleaseRecord.save()/_rebuild_index() unconditionally rewrite updated_at/generated_at even when substantive content is unchanged, which trips require_clean_bigcherry() after an idempotent audit/apply/generate run. Make persistence content-aware: compare substantive document/index content first, skip the write entirely when unchanged. (Do NOT whitelist releases/ in require_clean_bigcherry() -- real release-record edits must stay visible as dirty-tree signal.) Separately, tune-campaign itself must use campaign APIs exclusively and never invoke legacy shared-checkout audit/apply/generate, sidestepping this class of interference entirely.
6. Add named, versioned runtime profiles (e.g. production-dual-xtx: split=tensor, flash-attn=on, production context; production-safe-single: tune_ctx=4096) carrying server args + tuner settings together, selected via --runtime-profile. Tune-mode context must be bounded by default (do not inherit the model's own max context, which OOM'd during a real single-GPU R9700 27B tune run this session) -- default matches e2e_smoke_campaign's existing 4096 default, explicit --tune-context N or profile override to change it, and the EFFECTIVE context actually used must be recorded in the workflow receipt (never silently auto-shrunk after a crash -- fail closed with a clear VRAM-preflight rejection instead if an explicitly requested context is unsafe for the target GPU(s)).
7. Re-verify the replay coverage finding from the live dual-XTX run this session (real GGML_HIP_DISPATCH_COVERAGE output showed `exact: 0, rerun_required: 51, misses: 14, stale: true` out of 52 cache entries) using the tune build's OWN manifest_ref (per point 1) instead of a hand-regenerated manifest, to determine whether that resolves the near-total rerun/stale result or whether it's a separate, real gap worth its own investigation.

## Architecture

`tools/bigcherry/tuning/workflow.py` (new) orchestrates the 6 stages by calling existing campaign/tuning APIs directly (no shelling out to the `bigcherry` CLI internally) -- `tools/bigcherry/cli/tuning.py::cmd_tune_campaign` (new) is a thin argparse wrapper that builds a `ProjectContext`/`ArtifactStore` and calls `workflow.run_tune_campaign(...)`, mirroring exactly how `cli/build.py::cmd_build_new` wraps `campaign/planner.py`.

## WorkflowReceipt schema

```python
@dataclass(frozen=True)
class StageIdentity:
    run_id: str
    source_slice_id: str
    build_plan_id: str
    manifest_path: str | None       # str(Path), None when stage has no generate stage
    source_root: str                # str(Path) -- requires CampaignLaneResult.source_root

@dataclass(frozen=True)
class WorkflowReceipt:
    schema_version: int
    campaign_run_id: str
    model_path: str
    platform_name: str
    devices: str
    runtime_profile_name: str
    effective_tune_context: int          # the ACTUAL -c value used for tune, never silently changed
    record: StageIdentity
    tune: StageIdentity
    correctness: StageIdentity | None    # None if every candidate already had evidence (rare) or 0 non-native winners
    replay: StageIdentity | None         # None if 0 promoted -- see 'promoted == 0' handling below
    promoted_before_evidence: int
    promoted_after_evidence: int
    dispatch_cache_path: str | None
    replay_coverage: dict | None         # verbatim contents of coverage.json when replay ran
    started_at: str                      # ISO8601
    finished_at: str
```

Written once at the end via `source_identity.atomic_write_json` (same temp+fsync+os.replace pattern already used by `build.py`'s metadata writer) to `<workdir>/tune-campaign-receipt.json`, and also published to ArtifactStore under `tune-campaigns/<campaign_run_id>/receipt.json` so it's discoverable the same way build artifacts are.

If `promoted_after_evidence == 0`: still write a full receipt (replay/dispatch_cache_path/replay_coverage all None), do not attempt replay against an empty winner set, and return successfully -- 0 promoted is a valid, honest outcome (confirmed by this session's own real single-request smoke runs), not a workflow error.

## Runtime profiles

class RuntimeProfile:
    name: str
    server_args: tuple[str, ...]      # e.g. ('-sm', 'tensor', '--flash-attn', 'on', ...)

### VRAM preflight (new `tools/bigcherry/core/gpu.py`)

```python
def free_vram_bytes(device_indices: tuple[int, ...]) -> dict[int, int]:
    """subprocess.run(['rocm-smi', '--showmeminfo', 'vram', '--json'], capture_output=True,
    text=True, check=True); parse per-GPU 'VRAM Total Memory (B)' minus
    'VRAM Total Used Memory (B)' for each requested index. Raises GpuQueryError
    on a non-zero exit or unparseable output -- never silently returns {} or
    fabricates zero/unlimited."""

def preflight_context(
    *, profile: "RuntimeProfile", devices: tuple[int, ...], stage: str,   # 'tune' or 'record'/'replay'
) -> None:
    """Checks free_vram_bytes(devices) against profile.min_free_vram_bytes_per_device
    for EVERY requested device (a tensor-split run needs headroom on all of them,
    not just one). Raises GpuPreflightError with a message naming the exact
    device(s) and byte counts on failure -- e.g. 'GPU 2: 1.2GiB free, need >= 2.0GiB
    for runtime-profile production-dual-xtx's tune stage'. Called by
    workflow.py's _stage_tune BEFORE launching the server -- fail closed with a
    clear, actionable error instead of letting the process OOM/crash mid-run
    (this session's real Qwen3.8-27B/R9700 OOM). Never auto-shrinks the context;
    the operator must pick a different --runtime-profile or free VRAM themselves."""
```

This directly encodes this session's real single-GPU R9700 lesson (default context OOM'd; explicit `-c 4096` fixed it) as a fail-closed, discoverable check rather than a crash an operator has to interpret.
