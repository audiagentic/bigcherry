# bigcherry tune-campaign: single-command record->tune->correctness->promote->replay orchestrator

## Description

Turn the full manual record -> tune -> correctness-evidence -> promote -> replay-export -> replay-verify pipeline (validated end-to-end by hand this session on Brutus, real dual-XTX + single-GPU R9700 runs, 20/39 candidates genuinely promoted with real correctness evidence) into a single repeatable, deterministic `bigcherry tune-campaign` command, so it can be kicked off as a standard workflow rather than requiring an operator/agent to manually chain ~12 commands and work around several real gotchas live.

Design direction confirmed via reviewer-gpt-agent consultation (2026-08-27, session ses_fec603fc33ee4089): implement as a new production orchestrator, NOT a promotion of the existing tools/bigcherry/e2e_smoke_campaign.py unchanged (that file encodes smoke-only policy -- HIP_LAUNCH_BLOCKING=1, reduced final-samples -- but already proves the record->inventory->tune->DB->promote->correctness->re-promote->export->replay sequencing works and its server-lifecycle/request-runner code should be extracted and reused).

**REAL VANILLA-LLAMACPP BASELINE, ADDED 2026-08-27**: built stock upstream ggml-org/llama.cpp @ 0adcc3bb571011bff8b91335d0728a82845c421b (bc-branch's own pinned rev) via the campaign engine's existing `llama-native:stock:linux-multi` lane (`bigcherry build --lane llama-native:stock:linux-multi`) -- no bigcherry overlay, no patches, no autotune options (`options = {}` per config/recipes.toml [build.stock]). Full 4-way real comparison:
- vanilla upstream llama.cpp (no patches, no autotune): pp4096=1224.2 (+-10.9), tg128=84.8 (+-2.7), tg512=79.8 (+-18.5)
- bigcherry record-binary, MODE=native: pp4096=1215.7 (+-21.5), tg128=87.7 (+-5.6), tg512=82.0 (+-14.2)
- bigcherry replay-binary, MODE=replay (0% real cache hits): pp4096=1225.7 (+-10.9), tg128=97.4 (+-2.2), tg512=97.2 (+-18.4)
- bigcherry replay-binary, MODE=native: pp4096=1228.1 (+-11.0), tg128=98.0 (+-3.7), tg512=110.0 (+-0.1)

Vanilla upstream and bigcherry's record-binary are statistically indistinguishable (~82-88 t/s tg) -- both are real 'no dispatch tuning' baselines and agree with each other, which is itself a useful cross-check that the bigcherry overlay/patch stack does not regress plain dispatch. The replay-configured binary (both its native and replay/miss modes) is consistently ~15-30% faster on tg128/tg512 than either baseline. Since replay-native approx= replay-replay-miss (already established), this gap is confirmed NOT to be dispatch-tuning routing (0% real hits) -- it is a genuine, reproducible build-configuration effect tied to compiling with GGML_HIP_DISPATCH_REPLAY vs GGML_HIP_AUTOTUNE_RECORD / no dispatch layer at all, independent of whether any tuned candidate is ever actually selected. Worth its own investigation eventually (why does the replay build's compiled code path run faster even with no cache hits?) but is NOT evidence of a tuning win and should not be reported as one.

**Honest bottom line**: no real autotune-driven improvement over vanilla llama.cpp has been demonstrated. bigcherry's replay build is faster than vanilla today, but for build-configuration reasons unrelated to tuning. The two real fixes still required before a genuine tuning-vs-vanilla comparison is possible: (1) per-candidate replay freshness (replace whole-manifest-hash matching) so replay mode can actually get real cache hits; (2) once real hits exist, compare replay-binary MODE=replay (real hits) vs replay-binary MODE=native on the SAME binary -- that isolates tuning as the only variable. Only after that should vanilla-llama.cpp be brought back in as the outer baseline again.

**ROOT-CAUSE FIX IMPLEMENTED AND VERIFIED, 2026-08-27**: gpt review (req_ec659ded425c4335) confirmed the manifest-hash mismatch was a stage-ORDERING bug in workflow.py, not a design gap -- `replay_mod.build()` already correctly rebinds every cache entry to whatever manifest it's given (tune workload-max and replay replay-full legitimately differ by design, since variant_set is baked into manifest_hash). The bug: HI130 exported the cache against tune_result.manifest_ref BEFORE building the replay lane, so every entry was stamped with tune's hash while the replay binary embeds its own (different) replay-full hash -- guaranteed stale/RERUN_REQUIRED on every dispatch, no matter what.

Fix (workflow.py): reordered to build the replay lane FIRST (_stage_replay_build), THEN export the cache against replay_result.manifest_ref/source_root (_stage_replay_export, params renamed tune_manifest_path/tune_source_root -> target_manifest_path/target_source_root to make this explicit), THEN verify (_stage_replay_verify) against that exact binary+cache pair. _stage_replay_verify now also fails loudly (raises TuneCampaignError) if coverage reports stale=true or rerun_required>0, so this exact defect class cannot silently regress into a 'successful' campaign run that never used tuned dispatch. No C++ change, no freshness-check relaxation, no production recipes.toml/build.replay semantics change -- exactly as gpt recommended (explicitly rejected options (a) forcing replay to workload-max, and (b) relying on replay-slim's non-existent special freshness tolerance).

Full offline test suite green (2228 passed, 6 skipped, 133 subtests) after the change; tools/tests/tuning/test_workflow.py's 4 tests pass unchanged (they test the pure-Python helpers, not the live ordering). NOT YET verified live on real hardware -- next live tune-campaign run on Brutus should show replay_coverage with exact>0 and stale=false/rerun_required=0 for the first time; that live confirmation is the remaining validation step before this can be called fully closed.

## Architecture

`tools/bigcherry/tuning/workflow.py` (new) orchestrates the 6 stages by calling existing campaign/tuning APIs directly (no shelling out to the `bigcherry` CLI internally) -- `tools/bigcherry/cli/tuning.py::cmd_tune_campaign` (new) is a thin argparse wrapper that builds a `ProjectContext`/`ArtifactStore` and calls `workflow.run_tune_campaign(...)`, mirroring exactly how `cli/build.py::cmd_build_new` wraps `campaign/planner.py`.

## WorkflowReceipt schema

```python
@dataclass(frozen=True)
class StageIdentity:
    run_id: str
    source_slice_id: str
    build_plan_id: str
    manifest_path: str | None       # str(Path), None when stage has no generate stage
    source_root: str                # str(Path) -- requires CampaignLaneResult.source_root

@dataclass(frozen=True)
class WorkflowReceipt:
    schema_version: int
    campaign_run_id: str
    model_path: str
    platform_name: str
    devices: str
    runtime_profile_name: str
    effective_tune_context: int          # the ACTUAL -c value used for tune, never silently changed
    record: StageIdentity
    tune: StageIdentity
    correctness: StageIdentity | None    # None if every candidate already had evidence (rare) or 0 non-native winners
    replay: StageIdentity | None         # None if 0 promoted -- see 'promoted == 0' handling below
    promoted_before_evidence: int
    promoted_after_evidence: int
    dispatch_cache_path: str | None
    replay_coverage: dict | None         # verbatim contents of coverage.json when replay ran
    started_at: str                      # ISO8601
    finished_at: str
```

Written once at the end via `source_identity.atomic_write_json` (same temp+fsync+os.replace pattern already used by `build.py`'s metadata writer) to `<workdir>/tune-campaign-receipt.json`, and also published to ArtifactStore under `tune-campaigns/<campaign_run_id>/receipt.json` so it's discoverable the same way build artifacts are.

If `promoted_after_evidence == 0`: still write a full receipt (replay/dispatch_cache_path/replay_coverage all None), do not attempt replay against an empty winner set, and return successfully -- 0 promoted is a valid, honest outcome (confirmed by this session's own real single-request smoke runs), not a workflow error.

### VRAM preflight (new `tools/bigcherry/core/gpu.py`)

```python
def free_vram_bytes(device_indices: tuple[int, ...]) -> dict[int, int]:
    """subprocess.run(['rocm-smi', '--showmeminfo', 'vram', '--json'], capture_output=True,
    text=True, check=True); parse per-GPU 'VRAM Total Memory (B)' minus
    'VRAM Total Used Memory (B)' for each requested index. Raises GpuQueryError
    on a non-zero exit or unparseable output -- never silently returns {} or
    fabricates zero/unlimited."""

def preflight_context(
    *, profile: "RuntimeProfile", devices: tuple[int, ...], stage: str,   # 'tune' or 'record'/'replay'
) -> None:
    """Checks free_vram_bytes(devices) against profile.min_free_vram_bytes_per_device
    for EVERY requested device (a tensor-split run needs headroom on all of them,
    not just one). Raises GpuPreflightError with a message naming the exact
    device(s) and byte counts on failure -- e.g. 'GPU 2: 1.2GiB free, need >= 2.0GiB
    for runtime-profile production-dual-xtx's tune stage'. Called by
    workflow.py's _stage_tune BEFORE launching the server -- fail closed with a
    clear, actionable error instead of letting the process OOM/crash mid-run
    (this session's real Qwen3.8-27B/R9700 OOM). Never auto-shrinks the context;
    the operator must pick a different --runtime-profile or free VRAM themselves."""
```
