# Signature identity completeness: ids fields, quantized stride normalisation, and a maintained proof table

## Description

The owner asked whether the cache key is built from all factors used for kernel selection, and why no review ever raised it. dev-gpt-agent (req_6075d7c2055c4aa2) reviewed the actual fields and gave a split verdict: for NATIVE FAMILY SELECTION on the ordinary q8_0 workload it finds no missing selector input, but it will NOT call the key repository-wide complete. Three concrete findings.

(1) cc / warp_size outside the signature is SOUND. L1 partitions by device and the disk identity carries architecture (derived from cc) and wave_size (= warp_size). Duplicating them inside the operation signature is unnecessary -- PROVIDED the architecture-code mapping stays injective for every cc distinction the helpers care about. That proviso is currently unstated and unenforced.

(2) ids is a real key-completeness hole for operation identity, though not for native family choice. native_select only branches on ids != nullptr, and its MMID geometry comes from src/dst fields already signed. But downstream KERNELS can consume ids layout, type and strides, and the signature records only HAS_IDS and ids->ne[0] (as n_expert_used). Nothing captures ids type, strides, or other extents. This needs an explicit invariant proving every dispatched MUL_MAT_ID has the same derivable ids type/layout -- otherwise two operations needing different kernels can collide on one key.

(3) Stride normalisation needs a proof, and has a comment/code mismatch. ggml_hip_fill_strides computes out[i] = nb[i] * block / element for ALL FOUR dimensions, but the adjacent comment states nb[0] is kept as a byte count -- the implementation does not special-case i == 0. Fix the mismatch regardless of the rest.

For non-quantized MMF/MMVF inputs, normalised stride plus type is effectively lossless under ordinary GGML stride invariants. For QUANTIZED layouts, floor(nb*block/type_size) is not mathematically injective over arbitrary byte strides. Contiguity bits do not restore information lost by the normalisation. So there must be a proof that legal GGML quantized strides are restricted to values where the conversion is exact.

Also: repository-wide completeness is ALREADY known false -- the source documents signature-coverage exceptions around experimental fusion patches (e.g. RD17 x_scale_channel_dst).

## Steps

1. Fix the ggml_hip_fill_strides comment/code mismatch on nb[0].
2. Add static_assert on sizeof(ggml_hip_dispatch_signature_v1). gpt computes 232 bytes with ordinary 8-byte alignment padding, not the 224 I claimed; pin whichever is true so it cannot drift silently.
3. State and enforce the injectivity proviso for architecture-code vs cc.
4. Establish the ids invariant, or add the missing ids fields to the signature.
5. Prove exactness of the quantized stride normalisation over legal GGML strides, or stop normalising.
6. Build the maintained proof table (below).

## Detailed Solution & Technical Design

WHY NO REVIEW CAUGHT THIS -- gpt's process answer, which is the part worth keeping.

This is a cross-cutting identity-completeness defect class. The property 'the cache key injectively represents everything that determines which kernel is correct' spans: the key producer, upstream selector/helper reads, candidate legality (can_execute), executor reads, the enclosing hardware identity, and any later patch that adds semantics.

A patch-local review can verify every one of those components in isolation and still never ask whether their UNION is injectively represented by the key. No reviewer was negligent; the review unit is the patch, and the defect lives between patches.

Remedy: a maintained proof table with columns

  semantic/selection input | source reader | signature field | hardware field | derived invariant

Any change to a selector, can_execute, executor, fusion or transform must update and revalidate that table. That converts an invisible cross-cutting property into a reviewable artifact with an owner.

## Code Samples & Guidance

Do NOT narrow extents to int32_t globally -- GGML dimensions are 64-bit and narrowing creates collisions unless a hard bound is established and enforced. Do NOT drop stride slots until the proof table shows them irrelevant to ALL replayable candidates and executors, not merely to native selection. Struct shrinking is low priority: the expensive work is metadata/helper calls, not clearing another cache line.

## Notes

make_signature cost, same review: likely ranking is (1) the backend indirect get_alloc_size path, (2) 3x ggml_is_contiguous + ggml_nbytes, (3) 24 metadata loads/copies, (4) the memset -- which is probably the cheapest, a ~230-byte hot stack zero being a few vector stores.

The real waste is that the exact bad-padding predicate is computed TWICE per dispatch: once in native_select and again in make_signature. gpt warns against a global tensor-pointer cache for it, since safe reuse needs invalidation covering tensor shape/type, buffer identity, buffer usage, allocation size and view_src. Correct fix is a per-dispatch derived-facts structure consumed by both the selector and the signature builder, or graph-lifetime node metadata.
