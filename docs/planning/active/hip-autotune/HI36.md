# Winner generalisation — make a tuned result cover signatures it was never measured on

## Description

A winner is stored against an exact dispatch digest, which hashes every extent, stride and flag of the operation. Two signatures differing in one dimension the winning kernel does not specialise on are, to the cache, unrelated. The consequence is measured and severe.

**The Gemma E4B run (HANDOFF, 2026-08-07): 21 replay-entry hits against 100 misses**, on the same model the cache was tuned for. The strongest tuned winners never executed. The stated conclusion — "the cache was produced by a different workload" — is true and incomplete: the deeper reason a slightly different workload produces almost no hits is that the key admits no notion of similarity at all.

The same rigidity caps what tuning can ever be worth. Every measured signature costs seconds of GPU time and covers exactly one shape. At 245,760 context with MTP draft widths 1..5, the reachable signature space is far larger than any tuning run will visit, so coverage is permanently partial and the tail is permanently native.

`COVERAGE_AUDIT.md` records the mirror-image problem and calls it circular:

> `alignment_class`, `occupancy_bucket` and `offset_modulo` are defined in the ABI but never populated. That follows standards 5.5 (promote a refinement only once measurement proves it changes the winner), but it is circular: nothing can prove it while nothing populates them.

Coarsening and refining are the same question — *which signature dimensions actually change the winner* — asked in two directions. This item answers it with data already on disk before proposing any ABI change.

## Steps

1. **Offline agreement analysis first, no code change.** Group every recorded winner by candidate-relevant dimensions and measure how often signatures sharing a group share a winner. This runs against existing measurements files and costs nothing.
2. **Derive the per-family generalisation key** from what the analysis shows, rather than from what the kernels are assumed to care about.
3. **Quantify the gain** before building it: replay the Gemma E4B miss log against the proposed key and count how many of the 100 misses a generalised lookup would have converted.
4. **Implement the two-level lookup** in the replay resolver — exact digest first, generalised digest second, native third — with `can_execute` re-verified before launch, as it already is.
5. **Mark generalised hits distinctly** in coverage and diagnostics. A generalised hit is weaker evidence than an exact one and must never be counted as the same thing.
6. **Close the refinement circularity** by running the reverse experiment on one refinement: populate `alignment_class`, tune, and compare winners either side of the split.

## Detailed Solution & Technical Design

### Step 1 — the analysis that decides everything else

This is the part that must not be skipped, and it needs no GPU.

For each family, form candidate groups from the dimensions the winning candidate
is actually parameterised on, and ask how often a group agrees on one winner.

| Family | Candidate is parameterised on | Proposed group key |
| --- | --- | --- |
| MMQ | `(kernel_type, J, impl_fallback)` — and `fallback` derives from row divisibility | `(src0_type, K, N mod 128 == 0)` |
| MMVQ | `(kernel_type, width, nwarps, rows_per_block, small_k)` | `(src0_type, K, ncols_dst)` |
| MMVF | `(kernel_type, width, block_size, accumulator)` | `(src0_type, K, ncols_dst, prec)` |
| MMF | `(kernel_type, width, nwarps)` | `(src0_type, K, ncols_dst)` |
| BLAS | one opaque candidate | no grouping until HI17 |

The conspicuous omission is **M** — the src0 row count. If the analysis shows
winners agree across M within a group, the key can drop it and one measurement
covers every layer width in the model. If it does not, M stays and the ceiling on
generalisation is much lower.

`TUNING-DETAIL.md` contains enough to guess the answer, and the guess cuts both
ways. Four separate MMVQ signatures at width 5 with different M —
`021751e78d1d49e0` (M=8704), `e7c8abf6f5d4c97d` (M=5120), `858c79fbfc355cd6`
(M=512), `286e24a5f6d96b13` (M=5120, K=8704) — pick three different winners
(`w5:nw4:rpb4:sk1`, `w5:nw2:rpb2:sk0`, `w5:nw8:rpb2:sk0`). So M matters for MMVQ,
at least sometimes. But look at the margins: on `858c79fbfc355cd6` the winner is
14.40 us and `w5:nw4:rpb4:sk1` — the winner of two of its neighbours — is not
far behind. **The right question is not whether the winner is identical but
whether the generalised winner is within noise of the exact one**, and that is
precisely what the analysis must compute:

```
regret(sig) = 100 x (generalised_winner_median - exact_winner_median)
              / exact_winner_median
```

A generalisation is worth having when median regret is small and the tail is
bounded — not when winners agree exactly. Agreement is too strict a test and
would reject a scheme that captures nearly all the value.

Crucially, `regret` is computable from data already on disk: every candidate's
median is in the measurements file for every signature, so for any proposed
grouping the exact cost of generalising can be evaluated without running
anything.

### Step 3 — quantify against the failure that motivated it

`replay-hit-misses.jsonl` from the Gemma E4B run has the 100 missed signatures.
For each, form the proposed group key, look for a tuned winner in the same group,
and count conversions. That converts "generalisation should help" into "it
converts N of 100 misses at median regret R%", which is a number the
implementation can be justified or rejected against.

If it converts fewer than half, the key is too strict or the workload difference
is deeper than shape granularity, and the item should stop there.

### Step 4 — the lookup, and why it is safe

```
1. exact dispatch digest        -> winner, provenance = exact
2. generalised digest           -> winner, provenance = generalised
3. native                       -> provenance = miss
```

The safety argument is already built and does not need extending. HANDOFF
records that the guards are per entry, not per key: the loader drops entries
naming candidates this binary lacks, and **the resolver re-runs `can_execute`
before launching a stored winner**. A generalised winner passes through exactly
those guards, so the failure mode is an eligible-but-suboptimal candidate —
strictly better than the native fallback it replaces, up to the regret measured
in step 1.

This is the same reasoning HI23 used to downgrade a manifest mismatch from
rejection to a warning, and it should be stated the same way.

Cost at runtime is one extra hash and one extra hash-map probe, on the cold path
only — the process-level `g_bindings` cache (`hip-autotune-dispatch.cu:373-393`)
absorbs every subsequent call for that signature. Production replay pays nothing
per launch, which is the constraint that matters.

### Step 5 — provenance, or the number becomes a lie

The coverage report already learned this lesson once: HANDOFF records that
`dispatched == executed` was mistaken for "the cache was used" and produced a
wrong conclusion in RV12, which is why `replay: {entries, misses, stale}` now
sits beside the totals.

Generalised hits repeat the trap in a subtler form. A run reporting 100% hits
where most are generalised has *not* been validated the way an exact-hit run
has. Report the three provenances separately everywhere they appear — coverage
JSON, hit log, `bigcherry.impact` — and have HI35's impact model discount
generalised entries by their measured regret rather than crediting them with the
exact winner's saving.

### Step 6 — the refinement direction

Same machinery, opposite sign. Populate `alignment_class` (log2 of the common
alignment of src0/src1/dst — the field is already defined at
`hip-autotune-types.h:155`), tune a workload where it varies, and compare
winners across the split. If they differ beyond noise, standards 5.5 is
satisfied and the refinement is promoted; if not, the field is recorded as
tested-and-rejected so the circularity does not have to be rediscovered.

This is a small experiment that has been blocked for a documented reason that
dissolves once the comparison tooling from step 1 exists.

## Code Samples & Guidance

### Two findings that shrink the implementation substantially

**No cache-format change is needed.** The item proposed "a second section in the
cache file". Reading the loader:

- `g_winners` is a single `unordered_map<ggml_hip_digest, Winner>` keyed on the
  dispatch digest (`hip-autotune-replay.cpp:74`);
- `ggml_hip_replay_lookup` **ignores its `signature_digest` argument entirely** —
  `GGML_UNUSED(signature_digest)` is the first line of the body;
- the exporter already writes 16 zero bytes at `ENT_SIGNATURE`, marked
  "unused by lookup" (`replay_cache.py:180`).

So a generalised winner is an *ordinary entry stored under the generalised
digest*. Lookup needs no new function, the loader needs no new section, the
header needs no new field, and `GGML_HIP_REPLAY_VERSION` does not move.
Provenance is not stored at all — the caller knows which digest it probed with,
so which probe succeeded *is* the provenance.

One counter does need help: `ggml_hip_replay_entry_count()` would silently
include generalised entries and inflate the number the coverage report calls
"entries". There is no spare byte in the entry — `seeded` and `reserved` were
repurposed into `small_k` and `src0_type` (`hip-autotune-replay.cpp:140-141`) —
but the 16 unused `ENT_SIGNATURE` bytes are free and are all-zero in every cache
in existence. `ENT_SIGNATURE[0] = 1` marks a generalised entry, is unambiguous
against every prior file, and changes no offset.

**The generalised digest should reuse the existing canonical JSON, not a new
serialiser.** OVERVIEW principle 8 is explicit that a cross-language identity
divergence "does not fail loudly — every lookup simply misses and falls back to
native, and the system appears to work while doing nothing". A second
hand-written serialiser on each side is a second chance at exactly that. Instead:
zero the masked fields on a *copy of the signature struct* and hash the existing
canonical JSON of that copy. The C++ side reuses
`ggml_hip_signature_json`; the Python side reuses the `canonical` object it
already has and `json.dumps(..., sort_keys=True, separators=(",", ":"))`, which
is byte-identical to the C++ writer by construction (`hip-autotune-signature.cpp:20-25`).
Only the *mask* has to agree, and a mask is a list of field names that can be
pinned by test vector.

Zero the masked fields rather than removing them: the key set stays fixed, so
the JSON shape never varies and a mask change cannot silently reshape the
document.

### The mask, in terms of the actual signature fields

Mapping the proposed group keys onto `ggml_hip_dispatch_signature_v1`:

| Concept | Field |
| --- | --- |
| K | `ne0[0]` (and `ne1[0]`, the same value) |
| M — src0 rows | `ne0[1]`, `ned[0]` |
| ncols_dst — the draft width | `ned[1]` (and `ne1[1]`) |
| MMQ's `fallback` predicate | derived: `(ne0[1] % 128) != 0` |

```cpp
// Kept:    schema_version, op, src0_type, src1_type, dst_type, prec, fusion,
//          glu_op, flags, n_expert, n_expert_used, ne0[0] (K), ned[1] (width)
// Zeroed:  ne0[2..3], ne1[1..3], ned[0], ned[2..3], and all of nb0/nb1/nbd
// Reduced: ne0[1] -> the fallback predicate, 0 or 1
//
// The strides go because they are a function of M and of the allocation, not
// of anything a kernel specialises on; contiguity, which kernels *do* branch
// on, is already in `flags` and is kept.
//
// ne0[1] is not simply dropped for MMQ: `mul_mat_q_switch_J` selects on row
// divisibility, so the group must not merge a divisible shape with an
// indivisible one. Reducing the field to the predicate keeps exactly the
// distinction the kernel makes and discards the rest, which is the whole idea
// of a generalisation key stated in one line of code.
ggml_hip_dispatch_signature_v1 ggml_hip_generalised_signature(
        const ggml_hip_dispatch_signature_v1 & sig,
        ggml_hip_kernel_family family) {
    ggml_hip_dispatch_signature_v1 g = sig;
    const bool fallback = (sig.ne0[1] % 128) != 0;

    for (int i = 1; i < 4; ++i) { g.ne0[i] = 0; g.ne1[i] = 0; }
    g.ned[0] = 0;
    g.ned[2] = g.ned[3] = 0;
    for (int i = 0; i < 4; ++i) { g.nb0[i] = 0; g.nb1[i] = 0; g.nbd[i] = 0; }
    g.ne1[1] = 0;                       // duplicated by ned[1], which is kept

    if (family == GGML_HIP_FAMILY_MMQ) {
        g.ne0[1] = fallback ? 1 : 0;
    }
    // Refinements are excluded by passing include_refinements = false below;
    // a generalisation key that carried a refinement would be a contradiction.
    g.has_refinements = 0;
    g.alignment_class = g.occupancy_bucket = g.offset_modulo = 0;
    return g;
}

// A distinct personalisation, so a generalised digest and a real signature
// digest over coincidentally identical bytes cannot collide into one key
// (standards 5.4, the same reasoning that separates the signature and hardware
// prefixes).
#define GGML_HIP_PERSON_GENERAL "llama-hip-genrl"

ggml_hip_digest ggml_hip_generalised_digest(
        const ggml_hip_dispatch_signature_v1 & sig,
        ggml_hip_kernel_family family) {
    const ggml_hip_dispatch_signature_v1 g =
        ggml_hip_generalised_signature(sig, family);
    return ggml_hip_digest_of(ggml_hip_signature_json(g, false),
                              GGML_HIP_PERSON_GENERAL);
}
```

The Python mirror, in `tools/bigcherry/generalise.py`:

```python
_ZEROED_SCALARS = ()
_ZEROED_ARRAYS = {
    "ne0": (2, 3),
    "ne1": (1, 2, 3),
    "ned": (0, 2, 3),
    "nb0": (0, 1, 2, 3),
    "nb1": (0, 1, 2, 3),
    "nbd": (0, 1, 2, 3),
}


def generalised_canonical(canonical: dict, family: str) -> dict:
    """The C++ mask, applied to the canonical JSON object.

    Byte-for-byte identity with C++ comes for free: the C++ writer emits keys
    in alphabetical order with no whitespace, which is exactly
    json.dumps(sort_keys=True, separators=(",", ":")). So the only thing that
    can drift between the two sides is *which fields the mask zeroes*, and that
    is pinned by the shared test vectors below rather than by two independently
    maintained serialisers.
    """
    g = copy.deepcopy(canonical)
    fallback = 1 if (g["ne0"][1] % 128) != 0 else 0
    for key, indices in _ZEROED_ARRAYS.items():
        for i in indices:
            g[key][i] = 0
    g["ne0"][1] = fallback if family == "mmq" else 0
    return g
```

Unanimity is reported but is **not** the decision criterion; regret is. A group
where two winners alternate with 0.3% between them is a good generalisation and
a bad unanimity score.

```python
def regret_table(results, calls, group_key):
    """Cost of serving every signature in a group with one winner.

    Computable entirely offline: every candidate's median for every signature
    is already in the measurements file, so any proposed grouping can be priced
    exactly without running anything on a GPU.

    The criterion is regret, not agreement. Two winners alternating within a
    group at 0.3% apart is a *good* generalisation; requiring identical winners
    would reject it and most of the value with it.
    """
    groups = collections.defaultdict(list)
    for result in results:
        key = group_key(result)
        if key is not None:
            groups[key].append(result)

    rows = []
    for key, members in groups.items():
        # The group's representative is the winner of its highest-impact
        # member, because that is what a real cache ends up storing: the
        # exporter emits one entry per group and the hottest signature is the
        # one whose tune ran first and last.
        representative = max(
            members,
            key=lambda r: calls.get(r["signature"], 0) * _native_median(r),
        )
        rep_name = representative.get("winner", "")

        for result in members:
            ok = {
                c["name"]: c
                for c in result.get("candidates", [])
                if c.get("status") == "ok" and c.get("median_us")
            }
            exact = ok.get(result.get("winner", ""))
            if exact is None:
                continue                 # rejected signature: no claim to make
            generalised = ok.get(rep_name)
            if generalised is None:
                # The representative was not even eligible here. That is the
                # finding -- the grouping is too coarse for this family -- and
                # not a bug, so it is a row rather than a skip.
                rows.append(
                    {"key": key, "signature": result["signature"],
                     "regret_pct": None, "status": "ineligible"}
                )
                continue
            rows.append(
                {
                    "key": key,
                    "signature": result["signature"],
                    "regret_pct": 100.0
                    * (generalised["median_us"] - exact["median_us"])
                    / exact["median_us"],
                    "calls": calls.get(result["signature"], 0),
                    "status": "ok",
                }
            )
    return rows
```

Regret must be weighted by calls before it is quoted as a single number: a 15%
regret on a 52-call signature and a 0.1% regret on a 110,160-call one are not
things to average unweighted. Report both the unweighted distribution (which
bounds the worst case) and the call-weighted median (which is the expected cost).

#### Where the group key comes from, per file generation

`family` is not a field in a result line, and neither is the shape:

- **new-format measurements** carry `canonical` on the result line and `native`
  names the family — self-contained;
- **old-format measurements** (`tune9b`, `tune4b-bench`, and everything RV19 was
  computed from) carry neither, so the shape comes from joining the record
  file's `observation.canonical` on the signature digest, and the family from
  `observation.native`;
- **the miss log** carries `canonical` *and* `fallback` (the native stable
  name), so `--what-if` is self-contained against it. Verified against
  `replay-hit-misses.jsonl`, whose lines look like
  `{"dispatch":…,"signature":…,"calls":1,"fallback":"mmvq:native:v1","canonical":{…}}`.

All three paths must exist. Requiring the new format would mean the analysis
cannot be run against the data that motivated the item.

### Step 4 — the two-level lookup

`hip-autotune-dispatch.cu:425-444`, replacing the replay branch:

```cpp
#ifdef GGML_HIP_DISPATCH_REPLAY
    if (mode == GGML_HIP_DISPATCH_MODE_REPLAY) {
        const ggml_hip_candidate_descriptor * winner = nullptr;
        ggml_hip_variant_params variant = {};

        // Two-level lookup. The guards that make this safe already exist and
        // are not weakened: the loader drops entries naming candidates this
        // binary lacks, and the block below re-runs can_execute before
        // anything launches (:448-454). So the worst case for a generalised
        // winner is an eligible but suboptimal candidate -- strictly better
        // than the native fallback it replaces, bounded by the regret measured
        // offline in step 1.
        //
        // Cost is one extra hash and one extra probe, on the cold path only:
        // g_bindings (:373-393) absorbs every later call for this key, so
        // production replay pays nothing per launch.
        if (ggml_hip_replay_lookup(dispatch_digest, signature_digest,
                                   &winner, &variant)) {
            binding.candidate  = winner;
            binding.variant    = variant;
            binding.from_cache = true;
            ggml_hip_coverage_count_replay(GGML_HIP_REPLAY_EXACT);
#ifdef GGML_HIP_REPLAY_DIAGNOSTICS
            ggml_hip_replay_record_hit(dispatch_digest, signature_digest, winner);
#endif
        } else if (ggml_hip_replay_generalise_enabled() &&
                   ggml_hip_replay_lookup(
                       ggml_hip_dispatch_digest(
                           hardware_digest,
                           ggml_hip_generalised_digest(
                               sig, (ggml_hip_kernel_family) native.candidate->family),
                           "latency"),
                       signature_digest, &winner, &variant)) {
            binding.candidate  = winner;
            binding.variant    = variant;
            binding.from_cache = true;
            ggml_hip_coverage_count_replay(GGML_HIP_REPLAY_GENERALISED);
        } else {
            // Standards 9.2: a miss falls back to native and records the miss.
            ggml_hip_replay_record_miss(dispatch_digest, signature_digest, sig,
                                        hw, native.candidate);
            ggml_hip_coverage_count_replay(GGML_HIP_REPLAY_MISS);
        }
    }
#endif
```

winner back to native *after* the counter has been incremented, so the run would
report a generalised hit for a launch that ran native. Move the count below the
guard, or decrement there — the first is cleaner:

```cpp

            && (!ggml_hip_candidate_supports_arch(*binding.candidate, hw)

        binding.variant    = native.variant;
        binding.from_cache = false;
        provenance         = GGML_HIP_REPLAY_MISS;   // it did not serve
    }
```

### The exporter — `tools/bigcherry/replay_cache.py`

Generalised entries come from the same measurements file as the exact ones, so
no new tuning run produces one:

```python
    # Generalised entries: one per group, keyed on the generalised dispatch
    # digest. Ordinary entries in every respect -- same layout, same lookup,
    # same per-entry guards -- so the loader needs no new section and
    # GGML_HIP_REPLAY_VERSION does not move. ENT_SIGNATURE[0] marks them, using
    # 16 bytes that have been written as zero and read by nothing since HI11.
    for key, representative in generalise.group_representatives(results, calls):
        packed += generalised_dispatch_digest(representative, hardware_digest)
        packed += b"\x01" + b"\x00" * (DIGEST_BYTES - 1)   # ENT_SIGNATURE marker
        ...                                                 # unchanged tail
```

An exact entry and a generalised entry can only collide if a 128-bit digest
under `llama-dispatch` over a generalised signature equals one over a real
signature; the distinct `llama-hip-genrl` prefix inside makes that a coincidence
rather than a structural possibility. Assert on collision at export anyway — it
is a dict insert, it costs nothing, and a silent overwrite would replace a
measured winner with a generalised one.

### Cross-language test vectors — the part most likely to be skipped

A second digest is a second opportunity for the silent-miss failure OVERVIEW
principle 8 describes. Pin it the way the exact digest is pinned:

```python
class GeneralisedDigest(unittest.TestCase):
    def test_matches_cpp_vectors(self):
        """Fixed canonical signatures -> fixed generalised digests.

        The vectors are generated once by a C++ harness and checked in. Without
        them a mask that drifts on one side produces a cache whose every
        generalised lookup misses -- and a run that misses every generalised
        lookup looks exactly like a run with generalisation disabled, which is
        the failure mode that goes unnoticed for months.
        """

    def test_mask_is_stable_under_M(self):
        """Two signatures differing only in ne0[1] (with the same divisibility)
        produce the same generalised digest, and differ from one where the
        divisibility flips."""

    def test_mask_separates_width(self):
        """ned[1] = 1 and ned[1] = 5 never share a generalised digest."""

    def test_generalised_never_equals_exact(self):
        """Distinct personalisation: no signature hashes to its own
        generalised key."""
```

```python
class RegretAnalysis(unittest.TestCase):
    def test_representative_has_zero_regret(self):
        """A signature that is its own group representative regrets nothing.
```

## Validation

### Step 1 — analysis

- Runs against the RV19 artifacts and reproduces the MMVQ observation by hand:
  `021751e78d1d49e0`, `e7c8abf6f5d4c97d`, `858c79fbfc355cd6` and
  `286e24a5f6d96b13` are all width-5 MMVQ with three different winners, so the
  tool must report that group as non-unanimous with a non-zero regret. If it
  reports unanimity there, the grouping or the join is wrong.
- Regret is zero for every signature that is its own group representative — a
  trivial invariant that catches an indexing error immediately.
- `--group-by family,src0_type,K,ncols_dst,M` (i.e. no generalisation) yields
  zero regret everywhere. Any other result means the analysis is not measuring
  what it claims.

### Step 3 — the go/no-go

- The what-if against `replay-hit-misses.jsonl` produces a conversion count and
  a regret distribution, and the decision to proceed is recorded with those
  numbers attached.

### Step 4 — lookup

- **C++ and Python agree on the generalised digest**, pinned by test vectors, as
  the exact digest already is. OVERVIEW principle 8 is explicit that a
  cross-language identity divergence "does not fail loudly — every lookup simply
  misses and falls back to native, and the system appears to work while doing
  nothing". A second digest is a second opportunity for exactly that.
- With generalisation disabled, hit and miss counts are byte-identical to today.
- A generalised winner that fails `can_execute` falls through to native, and the
  coverage report shows a miss rather than a hit.
- Re-run the Gemma E4B replay: hits rise from 21 toward the predicted figure,
  and the split between exact and generalised matches the offline what-if.
- No throughput regression on the exactly-tuned MTP workload — those signatures
  still hit exactly and must not be routed through the generalised path.

### Step 6 — refinement

- `alignment_class` populated, a workload tuned where it varies, and winners
  compared across the split with HI12's confidence test applied. The result is
  recorded either way, which is what breaks the circularity — a documented
  negative is as useful here as a positive.

## Effort & Risk

L, but front-loaded with cheap analysis that can cancel the expensive part.

**Steps 1-3 are offline, cost a day, and are worth doing regardless.** They
produce a per-family statement about which signature dimensions change the
winner, which is a thing the project should know and currently does not — and
which `COVERAGE_AUDIT.md` explicitly flags as blocked.

**Steps 4-5 are a cache-format and ABI change** and should only start if step 3
converts a worthwhile share of the misses.

**The real risk is credibility, not correctness.** The runtime guards make a
wrong generalisation safe to execute; what it is not safe to do is *report* a
generalised hit as a tuned result. If provenance tracking is skipped or
collapsed into one counter, the project acquires a coverage number that reads
like validation and is not — the same error RV12 already made once with
`dispatched == executed`.

**Sequencing.** After HI19 (which formalises the signature/candidate separation
this depends on) and after HI35 (whose impact model must discount generalised
entries, and which supplies the call weighting the regret analysis needs).
Independent of HI34, though a residency finding there would change the regret
numbers and the analysis would need re-running.

matters is what it costs to serve the group with one winner, and a group whose
