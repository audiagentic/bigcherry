# Provenance capture — make a tuning artifact self-describing, and the database joinable

## Description

> **Status note (2026-08-13).** The defect descriptions and design below preserve
> the pre-remediation rationale. Bounded loader/schema slices have since landed:
> measurements now join on `variant_set`, resolve hardware from each result
> digest, persist `tuning_run` identity and workload digest metadata, and retain
> the available HIP/build provenance. Remaining scope is producer-side
> completeness (workload/config/diagnostic emission), remaining ROCm/revision
> fields where the runtime can provide them, and hardware-backed round-trip
> validation. Keep the historical analysis below as the reason for the fields
> and tests; do not treat its present-tense defect wording as current state.

HI23 makes a winner survive an upgrade and keeps per-release history. This item is about everything *around* that winner: what workload it was measured for, on what machine, under what settings, and whether the database can answer either question.

Three gaps, all found by reading the tree rather than inferred.

**The database is not joinable.** `load_measurements` hardcodes `variant_set` to the literal `"tuning"` (`tools/bigcherry/inventory.py:414`) because the measurements header does not carry it — the record header does. `variant_set` is part of `build`'s UNIQUE key, so a record-mode load and a tuning load of the same build create **two disjoint `build` rows**, and no SQL join from `observation` to `winner` works. Worse, hardware is bound with `SELECT hardware_id FROM hardware LIMIT 1` (`:424`) while the hardware digest sits on every result line, so on a multi-GPU or multi-machine database winners are attributed to an arbitrary GPU class. `rocm_version` and `bigcherry_revision` are never written, and `hip_version` is in the header and dropped on the floor.

**Nothing records the model.** `ggml_hip_diagnostics` is declared at `hip-autotune-signature.h:40` and referenced nowhere in the tree. `observation.diagnostics_json` defaults to `'{}'` and is never populated. So HANDOFF's "the cache was produced by a different workload" — the Gemma E4B run, 21 replay hits against 100 misses — is a conclusion reached after the fact by a human, and there is no field anywhere that could have said it beforehand.

**The run does not record what it did.** The measurements header carries `final_samples` and `alpha` and nothing else from `ggml_hip_tuner_config`. A run with `GGML_HIP_TUNE_SCREEN_SAMPLES=15` is indistinguishable from a default one — which directly undermines HI24's central comparison, adaptive screening against uniform 15-sample screening. There is also no per-signature timestamp, so ordering and thermal-drift effects cannot be reconstructed from an artifact even though HI24's canary exists to detect them.

Advisory throughout: everything here is recorded, reported and joinable. Nothing gates a cache load. That is the same reasoning that moved the manifest check off the dispatch key and onto a flag in HI23, and it should not be relitigated per field.

## Steps

1. **Fix the three database defects.** Carry `variant_set` in the measurements header; bind hardware from the digest already on each result line; store `hip_version`, `rocm_version` and `bigcherry_revision`. Small, independently valuable, and unblocks every SQL question below.
2. **Add a `tuning_run` table.** `build` is a namespace, not a run; two tunes of the same build with different sample counts currently overwrite each other. One row per run holds the config, the timestamps, the workload identity and the machine state.
3. **Derive a workload digest** — blake2b over the sorted set of observed signature digests. Emitted by record mode and by the tuner, recomputable in Python from any artifact. No plumbing across the ggml/llama boundary.
4. **Accept an operator label**, `GGML_HIP_TUNE_WORKLOAD`, for the human-readable half. A digest says "different"; a label says "different from what".
5. **Emit the whole tuner config**, generated from one field list so a new knob cannot be added without being recorded.
6. **Report call-weighted coverage of a cache against a record** — the Gemma E4B number, stated properly and computed before a run rather than after it.
7. **Per-signature timestamp**, and optionally clock/thermal state at run start and end.
8. **Populate `observation.diagnostics_json`**, or delete `ggml_hip_diagnostics`. A struct that has been declared and unused since HI05 is either a plan or a lie.

## Detailed Solution & Technical Design

### Part 1 — why the database cannot currently answer anything

The three defects compound. `build` is keyed
`UNIQUE (source_revision, manifest_hash, signature_schema, hardware_schema, variant_set)`.
Record mode inserts with the record header's real `variant_set` (`workload-max`);
tuning mode inserts the literal `"tuning"`. Same revision, same manifest, two
rows. `observation` hangs off the first, `winner` and `measurement` off the
second, and every join in `report.py`'s `read_hot_signatures` — which joins
`observation` to `winner` on `build_id` — returns nothing.

That is why `read_hot_signatures` exists as a SQLite query nobody's report
depends on, and why `TUNING-DETAIL.md` was produced by joining two JSONL files
in Python instead. The database has been carrying the data and been unable to
relate it.

The hardware defect is the more serious one because it is silently *wrong*
rather than merely empty. `SELECT hardware_id FROM hardware LIMIT 1` binds every
winner to whichever GPU class happens to be first in the table. On a single-GPU
database that is accidentally correct; on the two-card gfx1100 target, or on any
database that has ever seen two machines, it attributes winners to hardware they
were never measured on. Standards 10.2 exists precisely to make hardware a first
class part of the key, and this discards it at the last step. The digest is on
every result line (`"hardware":"c789bd69..."`), so the fix is to use it.

### Part 2 — identity without crossing the ggml/llama boundary

The model is loaded by llama; `ggml-cuda` has no access to its metadata, and
bigcherry is an overlay rather than a fork, so plumbing model identity down
through the backend interface is exactly the kind of change the project avoids.
Two mechanisms that need none of it:

**The workload digest is derived from the signatures themselves.** The set of
shapes a model produces *is* its fingerprint: layer widths, head dimensions,
context, MTP draft widths all show up as distinct signatures. Hash the sorted
set and you have an identity for model + configuration that costs nothing and
needs no new instrumentation.

Hash **presence, not frequency**. Call counts vary with run length, so including
them would give two runs of the same model two different identities — which is
the opposite of what the field is for.

**Equality is the wrong test, though, and this is the important part.** Any new
shape — a longer context, one more draft width — changes the digest completely,
so digest equality would report "different workload" for a run that overlaps
95%. What actually matters is *overlap*, and specifically call-weighted overlap:

```
covered_share = sum(calls[s] for s in observed if s in tuned) / sum(calls[s] for s in observed)
```

That is the Gemma E4B number stated properly. "21 hits, 100 misses" is an
unweighted signature count; the weighted figure could be far better or far worse
and nobody knows which, because the 21 might be the hot ones. The digest is for
cheap identity; the overlap is for the decision.

**Advisory, per the owner's direction.** Both are recorded and reported. Neither
gates a load, neither downgrades an entry to stale, neither refuses a cache. The
precedent is HI23's manifest check: moving it from the key to a flag turned a
silent total miss into a labelled condition and lost no safety, because the
guards that protect correctness are per entry and still run.

### Part 3 — recording what the run actually did

`ggml_hip_tuner_config` has 18 fields after HI12's E-series and will have 25
after HI24 and HI34. Two of them reach the artifact. The failure mode is not
hypothetical: HI12's E6 exists because RV01–RV05 were invalidated by an
unrecorded build-side difference, and `inventory.py:404-406` carries a comment
about `compiler` being written by the tuner and dropped by the loader for weeks
— "exactly the class of defect E6 exists to close".

So do not emit the fields by hand. Generate the environment overrides *and* the
header emitter from one list, so adding a knob without recording it stops being
possible rather than being something to remember.

**A `tuning_run` table, because `build` is not a run.** `build` is a namespace:
revision, manifest, ABI, variant set. Two tunes of that build at different
sample counts, or on different days at different temperatures, are two runs, and
today the second silently `INSERT OR REPLACE`s the first. For the comparisons
HI34 and HI35 need — same signatures, two conditions — both must survive.

Run identity derives from a hash of the header, so reloading one file twice is
idempotent while two genuinely different runs are retained.

**Machine state is worth having and is the one part that is Linux-specific.**
SGPU clock, memory clock, junction temperature and package power at run start
and end bound the thermal drift that HI24's canary currently detects only
indirectly. They come from sysfs, which means mapping a HIP device ordinal to a
DRM card — `hipDeviceGetPCIBusId` then `/sys/bus/pci/devices/<bdf>/drm/card*`.
That is a dozen lines and no dependency, but it is also the least important part
of this item and should land last, if at all.

Hardware stops being whatever is first in the table:

```python
def _hardware_id_for(connection, hardware_hex: str) -> int:
    """Resolve the hardware row from the digest on the result line.

    Replaces `SELECT hardware_id FROM hardware LIMIT 1`, which bound every
    winner to an arbitrary GPU class. On a single-GPU database that is
    accidentally right; on the two-card target, or on any database that has
    seen two machines, it attributes winners to hardware they were never
    measured on -- discarding at the last step the thing standards 10.2 exists
    to make part of the key.

    A measurements file carries the digest but not the key's fields, so a row
    created from measurements alone is a stub. That is honest and joinable;
    the previous behaviour was neither. A later record-mode load fills it in.
    """
    digest = bytes.fromhex(hardware_hex)
    row = connection.execute(
        "SELECT hardware_id FROM hardware WHERE hardware_digest = ?", (digest,)
    ).fetchone()
    if row:
        return row[0]
    cursor = connection.execute(
        "INSERT INTO hardware (hardware_digest, architecture, "
        "architecture_code, wave_size, compute_units, feature_flags, "
        "canonical_json) VALUES (?, 'unknown', 0, 0, 0, 0, '{}')",
        (digest,),
    )
    return cursor.lastrowid
```

Note this is per result line, not once per file: a multi-GPU tune with unequal
tensor split produces different signatures *and* can produce different hardware
digests, and both belong to their own rows.

### Part 2 — the workload digest

```cpp
// blake2b over the sorted set of observed signature digests.
//
// Presence, not frequency: call counts vary with run length, so hashing them
// would give two runs of the same model two different identities, which is the
// opposite of the point. Sorted, because a hash map's iteration order is not
// a property of the workload.
//
// This needs nothing from llama.cpp. The set of shapes a model produces is its
// fingerprint -- layer widths, head dimensions, context, MTP draft widths all
// appear as distinct signatures -- so identity comes free from data the record
// already holds, without plumbing model metadata across the ggml boundary.
#define GGML_HIP_PERSON_WORKLOAD "llama-workload"

ggml_hip_digest ggml_hip_workload_digest(
        const std::vector<ggml_hip_digest> & signatures) {
    std::vector<ggml_hip_digest> sorted = signatures;
    std::sort(sorted.begin(), sorted.end(),
              [](const ggml_hip_digest & a, const ggml_hip_digest & b) {
                  return memcmp(a.bytes, b.bytes, GGML_HIP_DIGEST_BYTES) < 0;
              });
    std::string blob;
    blob.reserve(sorted.size() * GGML_HIP_DIGEST_BYTES);
    for (const ggml_hip_digest & d : sorted) {
        blob.append((const char *) d.bytes, GGML_HIP_DIGEST_BYTES);
    }
    ggml_hip_digest out;
    ggml_hip_blake2b(out.bytes, GGML_HIP_DIGEST_BYTES,
                     blob.data(), blob.size(), GGML_HIP_PERSON_WORKLOAD);
    return out;
}
```

Emitted in both flush paths — `ggml_hip_record_flush` over its observations and
`ggml_hip_tuner_flush` over `g_results` — plus the operator's label:

The Python mirror, so it can be recomputed from any artifact on disk:

```python
def workload_digest(signatures: Iterable[str]) -> str:
    """Mirror of ggml_hip_workload_digest. Sorted set, presence not frequency."""
    blob = b"".join(bytes.fromhex(s) for s in sorted(set(signatures)))
    return hashlib.blake2b(
        blob, digest_size=16, person=b"llama-workload"
    ).hexdigest()
```

#### The number that actually decides things

```python
def workload_overlap(record: Record, tuned_signatures: set[str]) -> dict:
    """How much of this workload has a tuned winner, weighted by calls.

    Digest equality is too strict to be useful: one extra context length or
    draft width changes it completely, so a 95%-overlapping workload reports
    as "different". Overlap is the decision; the digest is only cheap identity.

    And weighted, not counted. HANDOFF's "21 replay-entry hits against 100
    misses" is an unweighted signature count, so it cannot distinguish a cache
    covering the 21 hottest signatures from one covering the 21 coldest --
    which are opposite conclusions about whether that run was tuned.
    """
    total = covered = 0
    covered_signatures = 0
    for observation in record.observations:
        calls = int(observation.get("calls", 0))
        total += calls
        if observation["signature"] in tuned_signatures:
            covered += calls
            covered_signatures += 1
    return {
        "signatures_observed": len(record.observations),
        "signatures_covered": covered_signatures,
        "calls_observed": total,
        "calls_covered": covered,
        "covered_share_pct": 100.0 * covered / total if total else 0.0,
    }
```

### The schema

```sql
-- One row per tuning run. `build` is a namespace -- revision, manifest, ABI,
-- variant set -- and two tunes of one build at different sample counts, or on
-- different days at different temperatures, are two runs. Today the second
-- INSERT OR REPLACEs the first, so the comparisons HI34 and HI35 both need --
-- same signatures, two conditions -- cannot be held in the database at all.
CREATE TABLE IF NOT EXISTS tuning_run (
    run_id            INTEGER PRIMARY KEY,
    build_id          INTEGER NOT NULL REFERENCES build(build_id),
    run_digest        BLOB    NOT NULL UNIQUE,  -- blake2b of the header
    workload_digest   BLOB,
    workload_label    TEXT,
    started_at        TEXT,
    finished_at       TEXT,
    host_sync_overhead_us REAL,
    config_json       TEXT NOT NULL DEFAULT '{}',
    machine_json      TEXT NOT NULL DEFAULT '{}',
    created_at        TEXT NOT NULL DEFAULT (datetime('now'))
);

ALTER TABLE measurement ADD COLUMN run_id INTEGER REFERENCES tuning_run(run_id);
ALTER TABLE winner      ADD COLUMN run_id INTEGER REFERENCES tuning_run(run_id);
ALTER TABLE build       ADD COLUMN hip_version TEXT;
```

`run_digest` is the blake2b of the header line, which makes reloading one file
twice idempotent while keeping two genuinely different runs. Adding `run_id` to
the `measurement` and `winner` UNIQUE constraints is what actually retains both
runs, and SQLite cannot alter a constraint — so that part is a table rebuild
(`CREATE ... AS SELECT`, drop, rename) inside one transaction, not an `ALTER`.
Worth doing once, here, rather than discovering it later.

All of it goes through the guarded helper from HI34, since `dispatch-db.sql` is
`CREATE TABLE IF NOT EXISTS` throughout and adds nothing to a database that
already exists:

```python
_ensure_column(connection, "measurement", "run_id", "INTEGER")
_ensure_column(connection, "winner", "run_id", "INTEGER")
_ensure_column(connection, "build", "hip_version", "TEXT")
```


to have fired.

## Validation

### The database becomes joinable

- **The join that has never worked.** Load a record file and its measurements file into one database, then `SELECT` observations joined to winners on `build_id`. Today this returns zero rows because the two loads create disjoint `build` rows; it must return one row per tuned signature. This is the acceptance criterion for part 1 — everything else in it is subordinate.
- A tuning load and a record load of the same build produce **one** `build` row, not two.
- Winners are attributed to the hardware digest on their own result line. Construct a database with two hardware rows and confirm no winner is bound to the wrong one — the current `LIMIT 1` behaviour fails this by construction, which is why it needs a test rather than an inspection.
- `hip_version`, `rocm_version` and `bigcherry_revision` survive the round trip.
- An older measurements file with no `variant_set` still loads, falling back rather than failing.

### Run identity

- Two tunes of one build at different `final_samples` produce two `tuning_run` rows and retain both sets of measurements. Today the second overwrites the first.
- Loading one measurements file twice is idempotent: one run row, no duplicated measurements.
- `config_json` reflects the environment the run actually used. Set `GGML_HIP_TUNE_SCREEN_SAMPLES=15` and confirm it appears — this is the case HI24's central comparison depends on and that nothing currently records.
- **Adding a config field without recording it is not possible.** Add a field to `GGML_HIP_TUNER_CONFIG_FIELDS`, rebuild, and confirm it appears in the header with no other edit. A test that asserts the header's `config` key set equals the macro's field set catches the omission that recurred with `compiler`.

### Workload identity

- The digest is stable across two runs of the same model at different token counts — presence, not frequency. If it moves, call counts have leaked into the hash.
- The digest is stable across a rebuild and across an llama.cpp upgrade: it is a property of the workload, not of the binary.
- C++ and Python agree, pinned by test vector. Same reasoning as HI36's digest vectors, and the same silent failure if they diverge.
- Adding one signature to a workload changes the digest completely **and** moves the overlap by roughly one signature's share. That contrast is the argument for reporting both, and the test should assert it rather than leaving it as prose.
- **The Gemma E4B case, restated.** `workload-check` against that record and cache reports the call-weighted covered share, not only 21-of-121. Whatever the number turns out to be, it is recorded in HANDOFF, replacing the unweighted count currently quoted there.
- Advisory holds: with a completely mismatched workload the cache still loads, its winners are still used, hit and miss counts are byte-identical to a run without the field, and the only difference is what is reported.

### Machine state

- Absent rather than zero when sysfs cannot be read. A zeroed junction temperature is a false measurement; an omitted one is an honest gap.
- On a run that heats the GPU, `junction_c_end` exceeds `junction_c_start`. If it does not, the mapping from HIP ordinal to DRM card is wrong and every value is another card's.

## Effort & Risk

M, and almost all of it is Python against artifacts that already exist.

**Part 1 is a defect fix and should go first**, independent of everything else
in the plan. The database has been accumulating unjoinable data for the whole
project, and the hardware binding is not merely empty but wrong — it attributes
winners to GPU classes they were never measured on, which is a claim rather than
an absence. Nothing downstream can be trusted until it is fixed, and no other
item needs to land first.

**Part 2 has no runtime risk at all**, being advisory by construction: a digest
and a label that are recorded, reported, and never consulted at load time. The
only real risk is the C++/Python digest divergence, which is the same failure
OVERVIEW principle 8 describes — it does not fail loudly, it just makes two
artifacts disagree quietly — and it is handled the same way, with pinned test
vectors.

**Part 3's risk is the schema rebuild.** Adding `run_id` to the `UNIQUE`
constraints on `measurement` and `winner` cannot be done with `ALTER TABLE` in
SQLite; it needs create-copy-drop-rename in one transaction. Straightforward,
but it rewrites tables holding measurements that cost GPU hours, so it takes a
backup and a round-trip test rather than a careful hand.

**Sequencing.** Part 1 immediately. Part 2 before HI36, whose regret analysis
wants the call weighting and whose motivating failure is the workload-mismatch
this makes computable. Part 3 before HI34's residency experiment, which is
precisely the two-runs-of-one-build comparison that currently cannot be stored.

**What this does not do**, and should not be expected to: it produces no
speedup. It makes existing measurements analysable and future ones
self-describing. The argument for it is that four other items in this plan —
HI23, HI34, HI35, HI36 — all consume provenance that is not currently recorded,
and each would otherwise reimplement a partial version of it.

## Standards

5.1 and 15.1 (diagnostic identity travels beside the signature and never reaches the digest) are the standards this finally implements — `ggml_hip_diagnostics` has been the declared mechanism since HI05 and has never been populated, and `observation.diagnostics_json` has defaulted to `'{}'` since the schema was written.

10.2 (hardware key) is being *repaired*: binding winners with `SELECT hardware_id FROM hardware LIMIT 1` discards at the storage layer the distinction the key exists to make.

13.1 (software namespace) — this continues HI23's amendment, that provenance is recorded and reported rather than hashed into a key. The workload digest is the same principle applied to the workload rather than to the build, and is advisory for the same reason.

7.4 (hot-signature ranking) gains the call-weighted coverage figure, which is the ranking's natural companion: it says what share of the ranked workload a cache actually serves.
