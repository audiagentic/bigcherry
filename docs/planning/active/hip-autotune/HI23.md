# Portable tuning keys: survive rebuilds, keep per-release history, prefer the newest

## Description

Tuning results are currently destroyed by any rebuild that changes the candidate set or the upstream revision, because both are hashed **into the lookup key**.

`ggml_hip_dispatch_digest` (hip-autotune-signature.cpp:165) builds the key from hardware digest, signature digest, objective, **`GGML_HIP_AUTOTUNE_MANIFEST_HASH_STR`** and **`GGML_HIP_AUTOTUNE_SOURCE_REVISION_STR`**. Standards 13.1 justifies this: a build against a different candidate set must not resolve to winners measured by the previous one.

Sound in intent, but it makes the key do a job the header already does, and the collateral damage is severe:

- **`replay-slim` cannot work at all.** Slimming necessarily changes the candidate set, so every key changes and the entire cache is orphaned. Measured 2026-08-05: a slim build produced 81 missed signatures whose digests were *entirely disjoint* from the 95 tuned ones. See RV12.
- **It fails silently.** The cache header carries its own manifest hash and that check passes, so the loader reports "95 winner(s) loaded" while not one is reachable. Nothing in the system can tell the difference between "cache orphaned" and "workload changed".
- **Every upstream bump discards all tuning.** A tuning run costs real GPU hours; today a routine `bigcherry pull` throws it away with no warning and no way to reuse it.

Wanted instead: a winner stays usable across rebuilds, its provenance is visible, results accumulate per release, and the newest applicable result wins.

## Steps

1. **Record the key components** (do this first, it is small and unblocks everything). The tuner's result records currently carry only the final `dispatch` digest, so no tool can compute any other key from a measurements file. Emit `signature` and `hardware` digest hex alongside it. Without this, even a one-off migration script is impossible.
2. Add `ggml_hip_portable_digest(hardware, signature, objective)` to hip-autotune-signature.{h,cpp}. Keep `ggml_hip_dispatch_digest` — record mode and the measurement database still want a build-scoped identity.
3. Bump `GGML_HIP_REPLAY_VERSION` to 2. The entry layout has no spare bytes left (RV09 used the last two for `small_k`/`src0_type`), so provenance needs a real format change.
4. Extend the entry: manifest hash (16 B), source revision digest (16 B), generation (u32). Allow several entries per key; keep them contiguous and sorted by generation descending so lookup takes the first match.
5. Replace the `g_winners` map with portable key → small vector, and implement the fresh/stale/miss resolution above.
6. Teach `replay_cache.py` to emit v2, to merge with an existing cache, and to bound generations per key.
7. Make `replay-slim` re-key rather than copy digests verbatim — the bug this item exists to fix.
8. Add the fresh/stale/miss counts to the coverage report.

## Detailed Solution & Technical Design

### The key becomes portable; provenance becomes data

Split what is currently one digest into two concepts.

**Portable key** — `ggml_hip_portable_digest(hardware, signature, objective)`. Hardware, signature and objective only. This answers "the same work on the same GPU", which is genuinely what a winner is about, and it does not move when the catalog or upstream does.

**Provenance** — manifest hash, source revision and a release generation, stored **per entry** as data rather than mixed into the key.

Standards 13.1's intent is preserved and arguably better served: the check becomes explicit and reportable instead of being an invisible key collision. Today a mismatched candidate set is indistinguishable from an unseen signature; afterwards it is a labelled, counted, warnable condition.

### Reuse is safe, and the guard already exists

A winner from an older build names a candidate by stable name and carries its own variant params, so it is self-describing. Two protections are already in place and do the real work:

- The loader **drops entries whose stable name this binary does not carry** (hip-autotune-replay.cpp:262), so a candidate removed by slimming or an upstream change cannot be launched.
- The resolver already refuses a stored winner that `can_execute` rejects: *"A stored winner that cannot run on this hardware, or that has since been blacklisted, must not be launched merely because it was once the winner."*

So a stale winner is *valid* — it is an eligible candidate for that signature — it is merely possibly no longer *optimal*, because it was chosen from a different option set. That is a quality question, not a correctness one, and it is exactly what a staleness flag should communicate.

### Lookup: prefer exact, fall back to newest, always report

Entries form a small list per portable key. Resolution order:

1. An entry whose manifest hash **and** source revision match this build — **fresh**, use it silently.
2. Otherwise the entry with the highest generation — **stale**, use it and count it.
3. Nothing — miss, native fallback, as today.

`generation` is a monotonic integer so "newer wins" is well defined; a git SHA is not orderable. Derive it from the upstream release tag (`b10227` → 10227), falling back to the record's build timestamp when a shallow clone has no tag. The release record already tracks `release_tag`.

### Reporting

One `call_once` summary at load: how many entries are fresh, how many stale, and the revision they came from. Stale is normal and expected after an upstream bump; silence is what must be avoided. Extend the coverage report with fresh/stale/miss counts so "is this build actually tuned" is answerable from an artifact rather than from log scraping.

### Accumulating across releases

The writer merges rather than overwrites: read an existing cache, add the new run's entries, keep older generations for the same portable key. Bound it — keep the newest N (2 or 3) generations per key so a long-lived cache cannot grow without limit. Merging in Python keeps the production link path read-only, consistent with the existing decision.

## Effort & Risk

**L, and the risk is concentrated in one place:** loosening the key is exactly the guard standards 13.1 put there deliberately. The argument for doing it is that the guard is enforced twice — the cache header already carries the manifest hash and rejects a mismatch, and the loader already drops unknown candidate names — so removing it from the *key* loses no safety while turning a silent total miss into a labelled, counted condition.

Get the review of that reasoning before writing the C++; if the owner disagrees, the alternative is to keep the key as-is and have `replay-slim` inherit the parent manifest's hash, which is narrower but leaves upstream bumps still discarding everything.

Step 1 is independently worth doing whatever is decided, and carries no risk.

## Standards

13.1 (software namespace in the dispatch key) is the standard being revised, not ignored — propose amending it to "provenance is recorded and enforced at load, and reported per lookup" rather than "provenance is hashed into the key". 9.2 (miss falls back to native) is unchanged. 15.2 (process cache on the hot path) is unaffected: resolution happens once per signature on the cold path.

## Interim measure IMPLEMENTED and VERIFIED 2026-08-05

Steps 1 and a simplified form of 2/5 are done. Steps 3, 4, 6, 7, 8 (v2 format, per-entry provenance, generations, merge, coverage counts) remain.

**What changed**

1. **The tuner records the key's components.** `Result` carries `signature_digest` and `hardware_digest`, emitted as hex alongside `dispatch` in every result record. Previously only the composite was written, so nothing could compute an alternative key from a measurements file — not a re-key, not a migration, not an offline comparison. Verified: 1155 of 1155 result records carry both.
2. **The key is portable.** `ggml_hip_dispatch_digest` now hashes hardware, signature and objective only; `GGML_HIP_AUTOTUNE_MANIFEST_HASH_STR` and `GGML_HIP_AUTOTUNE_SOURCE_REVISION_STR` are out of it.
3. **The manifest check moved from the key to a flag.** A mismatch used to reject the cache; it now loads, uses the winners, and warns. Added `ggml_hip_replay_is_stale()` and `g_stale` so the coverage report can state it — a log line in a week-old server is not a usable answer to "is this build tuned".

**Why loosening the key was safe.** The guards that protect correctness are per entry, not per key, and both still run: the loader drops any entry naming a candidate this binary does not carry, and the resolver re-runs `can_execute` before launching a stored winner. An old winner is therefore still *valid*; it may merely no longer be *optimal*, having been chosen from a different option set. That is exactly what the staleness flag communicates, and it replaces a silent total miss with a labelled condition.

**Verification** — tune under `workload-max`, generate `replay-slim` (35 candidates, manifest `13fc4790`), export, rebuild, replay, on gfx1100:

| Case | Cache | Dispatched | Misses | Warning |
| --- | --- | --- | --- | --- |
| Before this change | 95 winners | 14476/14476 | **81**, zero digest overlap | none |
| Slim, matching cache | 1155 winners | 1188/1188 | **1** | none, correctly |
| Slim, **mismatched** cache (`d64e79c8` against build `13fc4790`) | 1155 winners | 1188/1188 | **1** | **fires, winners still used** |

Both halves of the request hold: the tune survives a rebuild that changes the candidate set, and an out-of-date tune is used *and* flagged.

**Consequence to be aware of:** changing the digest invalidated every measurement taken before it, including the 95-winner MTP run behind RV10 and RV11. Those conclusions stand as measurements; the cache built from them is keyed the old way and needs a re-tune to be usable.

**Still to do** — the parts that need the deeper design: per-entry provenance so a cache can hold winners from several builds at once, a monotonic generation so "newest wins" is well defined, merging in the writer, bounding retained generations, and fresh/stale/miss counts in the coverage report. Until those land, a cache holds exactly one generation and re-tuning replaces it wholesale.
