# Portable tuning keys: survive rebuilds, keep per-release history, prefer the newest

## Description

Tuning results are currently destroyed by any rebuild that changes the candidate set or the upstream revision, because both are hashed **into the lookup key**.

`ggml_hip_dispatch_digest` (hip-autotune-signature.cpp:165) builds the key from hardware digest, signature digest, objective, **`GGML_HIP_AUTOTUNE_MANIFEST_HASH_STR`** and **`GGML_HIP_AUTOTUNE_SOURCE_REVISION_STR`**. Standards 13.1 justifies this: a build against a different candidate set must not resolve to winners measured by the previous one.

Sound in intent, but it makes the key do a job the header already does, and the collateral damage is severe:

- **`replay-slim` cannot work at all.** Slimming necessarily changes the candidate set, so every key changes and the entire cache is orphaned. Measured 2026-08-05: a slim build produced 81 missed signatures whose digests were *entirely disjoint* from the 95 tuned ones. See RV12.
- **It fails silently.** The cache header carries its own manifest hash and that check passes, so the loader reports "95 winner(s) loaded" while not one is reachable. Nothing in the system can tell the difference between "cache orphaned" and "workload changed".
- **Every upstream bump discards all tuning.** A tuning run costs real GPU hours; today a routine `bigcherry pull` throws it away with no warning and no way to reuse it.

Wanted instead: a winner stays usable across rebuilds, its provenance is visible, results accumulate per release, and the newest applicable result wins.

## Steps

1. **Record the key components** (do this first, it is small and unblocks everything). The tuner's result records currently carry only the final `dispatch` digest, so no tool can compute any other key from a measurements file. Emit `signature` and `hardware` digest hex alongside it. Without this, even a one-off migration script is impossible.
2. Add `ggml_hip_portable_digest(hardware, signature, objective)` to hip-autotune-signature.{h,cpp}. Keep `ggml_hip_dispatch_digest` — record mode and the measurement database still want a build-scoped identity.
3. Bump `GGML_HIP_REPLAY_VERSION` to 2. The entry layout has no spare bytes left (RV09 used the last two for `small_k`/`src0_type`), so provenance needs a real format change.
4. Extend the entry: manifest hash (16 B), source revision digest (16 B), generation (u32). Allow several entries per key; keep them contiguous and sorted by generation descending so lookup takes the first match.
5. Replace the `g_winners` map with portable key → small vector, and implement the fresh/stale/miss resolution above.
6. Teach `replay_cache.py` to emit v2, to merge with an existing cache, and to bound generations per key.
7. Make `replay-slim` re-key rather than copy digests verbatim — the bug this item exists to fix.
8. Add the fresh/stale/miss counts to the coverage report.

## Detailed Solution & Technical Design

### The key becomes portable; provenance becomes data

Split what is currently one digest into two concepts.

**Portable key** — `ggml_hip_portable_digest(hardware, signature, objective)`. Hardware, signature and objective only. This answers "the same work on the same GPU", which is genuinely what a winner is about, and it does not move when the catalog or upstream does.

**Provenance** — manifest hash, source revision and a release generation, stored **per entry** as data rather than mixed into the key.

Standards 13.1's intent is preserved and arguably better served: the check becomes explicit and reportable instead of being an invisible key collision. Today a mismatched candidate set is indistinguishable from an unseen signature; afterwards it is a labelled, counted, warnable condition.

### Reuse is safe, and the guard already exists

A winner from an older build names a candidate by stable name and carries its own variant params, so it is self-describing. Two protections are already in place and do the real work:

- The loader **drops entries whose stable name this binary does not carry** (hip-autotune-replay.cpp:262), so a candidate removed by slimming or an upstream change cannot be launched.
- The resolver already refuses a stored winner that `can_execute` rejects: *"A stored winner that cannot run on this hardware, or that has since been blacklisted, must not be launched merely because it was once the winner."*

So a stale winner is *valid* — it is an eligible candidate for that signature — it is merely possibly no longer *optimal*, because it was chosen from a different option set. That is a quality question, not a correctness one, and it is exactly what a staleness flag should communicate.

### Lookup: prefer exact, fall back to newest, always report

Entries form a small list per portable key. Resolution order:

1. An entry whose manifest hash **and** source revision match this build — **fresh**, use it silently.
2. Otherwise the entry with the highest generation — **stale**, use it and count it.
3. Nothing — miss, native fallback, as today.

`generation` is a monotonic integer so "newer wins" is well defined; a git SHA is not orderable. Derive it from the upstream release tag (`b10227` → 10227), falling back to the record's build timestamp when a shallow clone has no tag. The release record already tracks `release_tag`.

### Reporting

One `call_once` summary at load: how many entries are fresh, how many stale, and the revision they came from. Stale is normal and expected after an upstream bump; silence is what must be avoided. Extend the coverage report with fresh/stale/miss counts so "is this build actually tuned" is answerable from an artifact rather than from log scraping.

### Accumulating across releases

The writer merges rather than overwrites: read an existing cache, add the new run's entries, keep older generations for the same portable key. Bound it — keep the newest N (2 or 3) generations per key so a long-lived cache cannot grow without limit. Merging in Python keeps the production link path read-only, consistent with the existing decision.

### What the format has to carry, and why the entry has no room

The current entry is exactly full. From `hip-autotune-replay.cpp:114-142`:

```
ENT_DISPATCH   0   16     ENT_ACC_F16   48   1
ENT_SIGNATURE  16  16     ENT_FALLBACK  49   1
ENT_NAME_OFF   32   4     ENT_SMALL_K   50   1
ENT_PRIMARY    36   4     ENT_SRC0_TYPE 51   1
ENT_SECONDARY  40   4     -----------------------
ENT_WIDTH      44   4     ENT_SIZE          52
```

`seeded` and `reserved` were spent on `small_k` and `src0_type` in RV09, and the
comment there says so. There is no spare byte, so provenance needs a real
version bump — which is step 3 and is not avoidable.

(`ENT_SIGNATURE`'s 16 bytes are written as zero and read by nothing, and HI36
claims byte 0 of that range as a generalised-entry marker. The two items must
not both claim it: **v2 gives `ENT_SIGNATURE` its real meaning back** — the
signature digest — and HI36's marker moves to its own `ENT_FLAGS` byte in the
v2 layout below. Land whichever first, but the layout is shared.)

```
// v2. ENT_SIZE 88.
ENT_DISPATCH    0   16   portable key: hardware + signature + objective
ENT_SIGNATURE  16   16   the signature digest, now actually written
ENT_NAME_OFF   32    4
ENT_PRIMARY    36    4
ENT_SECONDARY  40    4
ENT_WIDTH      44    4
ENT_ACC_F16    48    1
ENT_FALLBACK   49    1
ENT_SMALL_K    50    1
ENT_SRC0_TYPE  51    1
ENT_MANIFEST   52   16   provenance: the catalog this winner was chosen from
ENT_REVISION   68   16   provenance: blake2b-16 of the source revision string
ENT_GENERATION 84    4   monotonic; newest wins
// ENT_FLAGS would be byte 88 -> ENT_SIZE 89; pad to 92 for alignment, or take
// the top bit of ENT_GENERATION. Prefer the explicit byte: a flags field that
// is a stolen bit is how the reserved bytes were lost in the first place.
```

1155 entries × 88 B ≈ 100 KB, × 3 generations ≈ 300 KB. Size is not a
constraint here and should not shape the design.

### Generation is derived in Python, never in C++

`generation` must be monotonic so "newer wins" is well defined, and a git SHA is
not orderable. The upstream release tag is (`b10227` → `10227`), and it lives in
the release record that `releases.py` already maintains — not in the C++ build
hash header. So the exporter computes it and the loader only reads a `uint32`:

```python
def generation_of(record: releases.ReleaseRecord) -> int:
    """Monotonic ordering key for 'which tune is newer'.

    From the upstream release tag, because a git SHA has no order. A shallow
    clone often has no tag (`git describe --exact-match` fails, which is why
    _record_for tolerates an empty tag), so fall back to the build timestamp --
    still monotonic, still comparable against a tag-derived value because tags
    are ~10^4 and epoch minutes are ~10^7, so an untagged build always sorts
    newer than a tagged one. That is the correct bias: an untagged build is one
    someone made deliberately, just now.
    """
    match = re.fullmatch(r"b(\d+)", record.release_tag or "")
    if match:
        return int(match.group(1))
    return int(time.time() // 60)
```

The `fresh` test needs the same revision digest on both sides. Reuse the hash
that is already there rather than inventing an encoding:

```python
# replay_cache.py -- blake2b_digest() already exists and is already the
# project's content hash. The C++ side computes the identical value from
# GGML_HIP_AUTOTUNE_SOURCE_REVISION_STR with ggml_hip_blake2b and the same
# person, so `fresh` is a memcmp and not a string comparison.
revision_digest = blake2b_digest(source_revision.encode("ascii"))
```

### Lookup: a flat array and a span, not a map of vectors

The obvious shape is `unordered_map<digest, vector<Winner>>`, and it is the
wrong one: it allocates once per key, and this file's whole character is one
pass over a mapped buffer with no per-entry allocation. Sort at write time and
index into a flat array instead.

```cpp
// Entries are written sorted by (dispatch_digest, generation descending), so
// every key's generations are contiguous and the newest is first. Lookup then
// needs one probe and a short forward scan, and the common case -- one
// generation -- is a probe and a single compare.
struct WinnerSpan {
    uint32_t first;   // index into g_entries
    uint32_t count;
};

std::vector<Winner> g_entries;   // flat, in file order after filtering
std::unordered_map<ggml_hip_digest, WinnerSpan, DigestHash, DigestEqual> g_index;
```

**Build the index after filtering, not before.** The loader already drops
entries naming a candidate this binary does not carry
(`hip-autotune-replay.cpp`, the `ggml_hip_registry_find` guard) — that is one of
the two protections the whole safety argument rests on. Filtering after indexing
would leave spans pointing at removed entries, and a key whose every generation
was dropped must not resolve to anything at all.

```cpp
enum ggml_hip_replay_provenance {
    GGML_HIP_REPLAY_FRESH = 0,  // manifest AND revision match this build
    GGML_HIP_REPLAY_STALE,      // an older generation, still valid
    GGML_HIP_REPLAY_MISS,
};

// Prefer exact, fall back to newest, always report.
//
// A stale winner is *valid*: it names a candidate by stable name, carries its
// own variant params, survived the load-time registry guard, and is about to
// face can_execute in the resolver. What it may no longer be is *optimal* --
// it was chosen from a different option set. That is a quality question, and a
// counted, labelled staleness is the honest way to say it. The alternative,
// which is what shipped before HI23's interim measure, was a silent total miss
// indistinguishable from an unseen signature.
bool ggml_hip_replay_lookup(const ggml_hip_digest & dispatch_digest,
                            const ggml_hip_digest & signature_digest,
                            const ggml_hip_candidate_descriptor ** out_candidate,
                            ggml_hip_variant_params * out_variant,
                            ggml_hip_replay_provenance * out_provenance) {
    GGML_UNUSED(signature_digest);
    ggml_hip_replay_init();

    const auto found = g_index.find(dispatch_digest);
    if (found == g_index.end()) {
        *out_provenance = GGML_HIP_REPLAY_MISS;
        return false;
    }

    const WinnerSpan span = found->second;
    for (uint32_t i = 0; i < span.count; ++i) {
        const Winner & w = g_entries[span.first + i];
        if (w.fresh) {                       // computed once at load, not here
            *out_candidate  = w.candidate;
            *out_variant    = w.variant;
            *out_provenance = GGML_HIP_REPLAY_FRESH;
            return true;
        }
    }
    // Sorted generation-descending, so index 0 is the newest survivor.
    const Winner & newest = g_entries[span.first];
    *out_candidate  = newest.candidate;
    *out_variant    = newest.variant;
    *out_provenance = GGML_HIP_REPLAY_STALE;
    return true;
}
```

`w.fresh` is resolved at load by comparing each entry's `ENT_MANIFEST` and
`ENT_REVISION` against this build's, so the hot path does no digest comparison
beyond the map probe. That keeps step 5 consistent with standards 15.2 and with
the process cache above it — the whole resolution happens once per signature.

### Composition with HI36

HI36 adds a second *key* (exact then generalised); this item adds a second
dimension *within* a key (fresh then stale). They are orthogonal and must be
counted as a product, not merged into one enum — a generalised stale hit is the
weakest evidence the system can produce and needs to be visible as such:

```cpp
// [exact|generalised] x [fresh|stale], plus miss. Two counters, not one
// five-valued enum: RV12 already cost one wrong conclusion by collapsing two
// independent facts (dispatched, cache-used) into a single number.
uint64_t g_replay_counts[2][2];
uint64_t g_replay_misses;
```

### The writer: merge, do not overwrite

`replay_cache.py` can only write. Step 6 needs a reader first, and it has to
read v1 as well — otherwise the first v2 export silently discards every existing
cache:

```python
def read(path: Path) -> tuple[dict, list[dict]]:
    """Parse a cache file. Accepts v1 and v2.

    v1 entries carry no provenance, so they are assigned the header's manifest
    hash and generation 0 -- 'older than anything tagged'. That is the correct
    reading: a v1 cache is exactly one generation and predates the concept, so
    any v2 entry for the same key should win.
    """


def merge(existing: list[dict], fresh: list[dict], *, keep: int = 3) -> list[dict]:
    """Accumulate generations per portable key, newest first, bounded.

    Bounded by *generation*, not by entry count: one generation contributes one
    entry per key, so 'keep 3' means three releases of history, which is what
    the operator is actually choosing. An unbounded cache is a file that grows
    every release forever and is never noticed until it is large.

    Same (key, generation) from a re-tune replaces rather than duplicates: the
    later run is the one taken on the more warmed-up device.
    """
    by_key: dict[bytes, dict[int, dict]] = collections.defaultdict(dict)
    for entry in itertools.chain(existing, fresh):
        by_key[entry["dispatch"]][entry["generation"]] = entry

    out = []
    for key in sorted(by_key):
        generations = sorted(by_key[key], reverse=True)[:keep]
        out.extend(by_key[key][g] for g in generations)
    return out                      # already (key, generation desc) ordered
```

The output ordering is exactly the invariant the loader's span index depends on,
so write it from `merge` and assert it in the writer rather than sorting again
somewhere else.

CLI:

```bash
python -m bigcherry replay-cache tune.measurements.jsonl \
    --manifest artifacts/<rev>/hip-autotune-manifest.json \
    --merge-into dispatch.cache \
    --keep-generations 3 \
    --output dispatch.cache
```

`--merge-into` and `--output` naming the same file is the normal case and must
be safe: read fully, build in memory, write to a temp path, rename. A crash
mid-write that leaves a truncated cache would take out the accumulated history
of every previous release, which is the one irreplaceable artifact here.

### Step 7 — `replay-slim` re-keys rather than copies

This is the bug the item was opened for. With the key already portable

## Validation

### Shipped, and must not regress

- Tune under `workload-max`, generate `replay-slim`, export, replay: the slim build resolves winners rather than missing all of them. This is what failed before the interim measure (81 misses, zero digest overlap) and it is the acceptance criterion for the key change.
- Re-run the matching-manifest replay: 25244/25244 dispatched, zero misses.
- A winner whose candidate no longer exists is dropped at load, not launched.

### v2 format and lookup

- Writer round-trip: v2 out, v2 in, byte-identical entries.
- **v1 is still readable.** A v1 cache merges into a v2 export with generation 0 and the header's manifest hash. If this is missed, the first v2 export silently discards every cache in existence — which is a data-loss bug wearing an upgrade's clothing.
- Merge preserves an older generation for a key the new run did not re-tune, and replaces rather than duplicates the same `(key, generation)`.
- Bounding is by generation: with `--keep-generations 2`, a key tuned on three releases retains the two newest, and a key tuned once retains one.
- **The ordering invariant holds after merge**: entries are `(dispatch_digest, generation descending)`, contiguous per key. Assert it in the writer — the loader's span index is silently wrong if it does not, and the symptom is an *older* winner being served in preference to a newer one, which no test that only checks "a winner resolved" would catch.
- The index is built after the registry filter: a key whose every generation names an absent candidate resolves to a miss, not to a dangling span.
- `--merge-into` and `--output` naming one file leaves that file intact when the process is killed mid-write.

### Freshness and provenance

- Tune, bump upstream, rebuild without re-tuning: winners still resolve, are reported **stale**, and the run is correct.
- Re-tune on the new release, merge: the same signatures now resolve **fresh**, and the previous generation is still present in the file.
- A cache holding both generations, loaded by the *older* build, resolves the older generation as fresh — not the newer one as stale. Newest-wins is only the fallback rule; an exact provenance match always wins, whichever direction it points.
- `fresh` is computed at load, not per lookup: assert no digest comparison on the resolution path beyond the map probe (standards 15.2).

### Counts

- Coverage reports `fresh + stale + misses == total_dispatched`. A per-signature number nobody reconciles is a number nobody trusts.
- With HI36 also landed, the counts are a 2x2 product plus misses, and a generalised stale hit is visible as its own cell rather than folded into either parent.
- The load-time summary line names the generations present and how many entries are fresh for this build.

## Effort & Risk

**L, and the risk is concentrated in one place:** loosening the key is exactly the guard standards 13.1 put there deliberately. The argument for doing it is that the guard is enforced twice — the cache header already carries the manifest hash and rejects a mismatch, and the loader already drops unknown candidate names — so removing it from the *key* loses no safety while turning a silent total miss into a labelled, counted condition.

Get the review of that reasoning before writing the C++; if the owner disagrees, the alternative is to keep the key as-is and have `replay-slim` inherit the parent manifest's hash, which is narrower but leaves upstream bumps still discarding everything.

Step 1 is independently worth doing whatever is decided, and carries no risk.

## Standards

13.1 (software namespace in the dispatch key) is the standard being revised, not ignored — propose amending it to "provenance is recorded and enforced at load, and reported per lookup" rather than "provenance is hashed into the key". 9.2 (miss falls back to native) is unchanged. 15.2 (process cache on the hot path) is unaffected: resolution happens once per signature on the cold path.

## Interim measure IMPLEMENTED and VERIFIED 2026-08-05

Steps 1 and a simplified form of 2/5 are done. Steps 3, 4, 6, 7, 8 (v2 format, per-entry provenance, generations, merge, coverage counts) remain.

**What changed**

1. **The tuner records the key's components.** `Result` carries `signature_digest` and `hardware_digest`, emitted as hex alongside `dispatch` in every result record. Previously only the composite was written, so nothing could compute an alternative key from a measurements file — not a re-key, not a migration, not an offline comparison. Verified: 1155 of 1155 result records carry both.
2. **The key is portable.** `ggml_hip_dispatch_digest` now hashes hardware, signature and objective only; `GGML_HIP_AUTOTUNE_MANIFEST_HASH_STR` and `GGML_HIP_AUTOTUNE_SOURCE_REVISION_STR` are out of it.
3. **The manifest check moved from the key to a flag.** A mismatch used to reject the cache; it now loads, uses the winners, and warns. Added `ggml_hip_replay_is_stale()` and `g_stale` so the coverage report can state it — a log line in a week-old server is not a usable answer to "is this build tuned".

**Why loosening the key was safe.** The guards that protect correctness are per entry, not per key, and both still run: the loader drops any entry naming a candidate this binary does not carry, and the resolver re-runs `can_execute` before launching a stored winner. An old winner is therefore still *valid*; it may merely no longer be *optimal*, having been chosen from a different option set. That is exactly what the staleness flag communicates, and it replaces a silent total miss with a labelled condition.

**Verification** — tune under `workload-max`, generate `replay-slim` (35 candidates, manifest `13fc4790`), export, rebuild, replay, on gfx1100:

| Case | Cache | Dispatched | Misses | Warning |
| --- | --- | --- | --- | --- |
| Before this change | 95 winners | 14476/14476 | **81**, zero digest overlap | none |
| Slim, matching cache | 1155 winners | 1188/1188 | **1** | none, correctly |
| Slim, **mismatched** cache (`d64e79c8` against build `13fc4790`) | 1155 winners | 1188/1188 | **1** | **fires, winners still used** |

Both halves of the request hold: the tune survives a rebuild that changes the candidate set, and an out-of-date tune is used *and* flagged.

**Consequence to be aware of:** changing the digest invalidated every measurement taken before it, including the 95-winner MTP run behind RV10 and RV11. Those conclusions stand as measurements; the cache built from them is keyed the old way and needs a re-tune to be usable.

**Still to do** — the parts that need the deeper design: per-entry provenance so a cache can hold winners from several builds at once, a monotonic generation so "newest wins" is well defined, merging in the writer, bounding retained generations, and fresh/stale/miss counts in the coverage report. Until those land, a cache holds exactly one generation and re-tuning replaces it wholesale.
