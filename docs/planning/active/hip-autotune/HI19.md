# Enforce the signature / context / candidate / observation separation

## Description

The offline namespace validator and source-level identity audit are now both present. The audit protects the current signature/candidate boundary before patching or release validation, while preserving the existing ABI.

## Steps

- Write the four-record model into HIP_AUTOTUNE_STANDARDS as a numbered section,
  with the table from [FAMILY_MODEL.md](FAMILY_MODEL.md)
- Add `numerical_class` to the candidate descriptor —
  `exact_baseline | equivalent_within_backend_tolerance | reduced_precision` —
  and have the objective admit or reject classes before performance ranking
- Split candidate status into two independent fields:

  ```text
  enumeration_status = implemented | partial | absent
  dispatch_status    = wired | unavailable
  ```

  A candidate with `dispatch_status = unavailable` is excluded from ranking and
  promotion outright
- Add the observation fields the opaque families need:
  `provider_requested`, `provider_effective`, `actual_api`,
  `actual_reduce_algorithm`, `fallback_depth`, `fallback_chain`,
  `library_backend`, `solution_id`, `kernel_name`, `conversion_kernels`,
  `temporary_bytes`, `workspace_bytes`
- Rename MMQ's `fallback` to `impl_fallback` in documentation, catalog field
  names and generated headers. **Keep the stable-name token `fb`** — renaming it
  would invalidate every recorded name (standards 2.1)
- Document why the per-type token in `mmq:q8_0:...` is legitimate: MMQ kernels
  are compile-time specialised per type, so `q8_0` names a compiled artifact,
  not the incoming tensor. Read the field as `kernel_type`
- Add a source-audit invariant that fails if a candidate identity field appears
  in the signature struct, or vice versa

## Detailed Solution & Technical Design

`dispatch_status` is the item with immediate consequences. MMVQ is enumerated
but its entry point is gated `return false`, so today a signature where MMVQ
would win records "MMQ won" — which reads as a measurement but is an artifact of
what was reachable. That is worse than a missing candidate, because it is
indistinguishable from a real result after the fact. Until HI09 wires the entry
point, MMVQ candidates must be visibly `unavailable` rather than silently
ineligible.

`numerical_class` generalises the MMVF accumulator rule that HI07 already
implements ad hoc. The rule is: a lower-precision candidate is a *different
operation* unless the request's precision class permits it, and the authority on
that class is the signature's `prec` field (from `dst->op_params[0]`), never an
inference from source type.

The `impl_fallback` rename is documentation-and-tooling only by design. Two
unrelated meanings currently share the word: MMQ's compile-time fallback
implementation inside a `CASE` row, and the dispatcher's permission to fall back
to another family. Only the first is candidate configuration; the second belongs
to the selection request or benchmark mode, and conflating them in a family that
also has a `fallback_policy` (HI18) would be actively confusing.

Fixtures cover the valid separation and both insertion directions. The vendored checkout at source revision `4801e3c567d5131dd41b387df5f2d4b1370d92be` passes 33/33 audit checks. The full offline suite passes 492 tests plus 4 subtests.

## Effort & Risk

Low implementation risk, moderate blast radius — it touches the ABI, the
catalog and the schema at once. Do it before HI17 and HI18 add fields, not
after: retrofitting the separation onto two new families costs more than
establishing it first.
