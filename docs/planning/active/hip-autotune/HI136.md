# Safe partial strengthened ingest -- per-row quarantine of unsupported-domain signatures during production tune-campaign

## Description

Real finding from HI129's live-hardware validation (2026-08-27/28): a real `bigcherry tune-campaign` run against a real model (Qwen0.8B) correctly reached the new HI125 production wiring (dedicated signature-verifier lane built, `require_strengthened_ingest=True` invoked) and correctly HARD-FAILED the whole load with `sc.UnsupportedSignatureDomain: op='ADD' has no audited capability-applicability rule` -- a genuine fused ADD-adjacent dispatch outside HI121's currently-audited domain (MUL_MAT, MUL_MAT_ID, simple/routed GLU only). This is NOT a bug -- it is the deliberately-designed fail-closed behavior working correctly (per the HI125 step-6 design negotiation's explicit policy: 'do not weaken #6 with graceful silent fallback'). But it revealed new operational evidence: a real inference graph routinely dispatches ops outside the audited domain, so today's WHOLE-ARTIFACT all-or-nothing `require_strengthened_ingest` policy may make a fully-successful strengthened production campaign difficult or impossible against many/most real models, since load_measurements() currently invokes the verifier on EVERY result row and aborts the entire transaction on the first unsupported one.

## Steps

1. Design (adversarial GPT negotiation required, per this project's established discipline) a per-row quarantine mechanism: an unsupported-domain signature should be quarantined/unattested for that ROW only, not abort the whole load.
2. Preserve every existing invariant while doing this -- per dev-gpt-agent's explicit verdict (2026-08-27):
   - build/header/manifest attestation failure -> whole-load HARD FAIL (unchanged)
   - supported-domain digest/canonical mismatch -> whole-load HARD FAIL (unchanged)
   - malformed/forged evidence -> HARD FAIL (unchanged)
   - UnsupportedSignatureDomain -> explicitly quarantined/unattested (NEW: per-row, not whole-load)
   - a quarantined/unattested winner MUST NOT become production replay-cache export input
   - supported, genuinely verified winners -> winner_verification written normally
3. The last invariant is the hard part: the CURRENT same-generation production path goes promotion -> replay.build() DIRECTLY, not through replay_projection.py's own omitted_unverified_source quarantine gate (that gate is currently M4/cross-generation-only). A same-generation replay.build() call today does NOT check winner_verification at all. Any partial-ingest design must close this gap too, or a same-generation quarantined row could still leak into what ships.
4. Real-hardware validation: re-run a live tune-campaign (ideally with the SAME real model that surfaced this gap, Qwen0.8B, plus ideally a real MoE model for MUL_MAT_ID/routed-GLU coverage too) and confirm: campaign completes successfully end-to-end, supported-domain winners get real winner_verification rows, the one or more unsupported-domain rows are honestly quarantined (not silently promoted, not aborting the campaign), and none of the quarantined rows appear in the exported replay cache.
