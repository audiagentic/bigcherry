# Replay hot-path instrumentation: L0/L1/L2 hit-rate and native-selector-call counters

## Description

Carved out of HI87 as an independently implementable first slice (RP1 in the source document's own staged breakdown -- 'BigCherry Replay and RCCL Tuning Architecture', assessed 2026-08-23). Pure diagnostic instrumentation, zero behavior change: add counters for dispatch calls, thread-local (L1) cache hits, process-global (L2) cache hits, replay-DB (L3) lookups/misses, native-selector invocations, and hardware/signature digest constructions.

This is the natural, low-risk first move because HI87 itself is explicitly blocked on real measurement: 'how expensive is native_select() actually? ... Profile before implementing, not just from claimed motivation.' This item answers that question directly, and can ship on its own regardless of whether HI87's reorder is ever pursued -- the counters are useful diagnostic infrastructure independent of any hot-path change.

## Steps

- Add opt-in counters (env-gated, matching this codebase's existing GGML_HIP_*_TRACE convention -- zero cost when disabled) at: dispatch entry, L1 TLS cache hit/miss (g_thread_bindings), L2 process-global cache hit/miss (g_bindings), replay-DB (L3) exact-match lookup/miss, native-selector (ggml_hip_native_select) invocation, hardware-key/hardware-digest construction, signature-digest construction.
- Emit a summary report (counts + rates) on process exit or on demand, matching the source document's example report shape (dispatches / L1 hits / L2 hits / L3 lookups / native selector calls / digest builds).
- Run on a real workload (the dual-XTX production recipe already used throughout HI14/HI64/HI90 this session) to get real numbers: what fraction of dispatches are warm L1/L2 hits, and what does native_select() actually cost relative to a warm lookup.
