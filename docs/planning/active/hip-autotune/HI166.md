# Ordered per-step speculative acceptance trace equality (aggregate counts are structurally insufficient)

## Description

The behavioural gate compares generated token IDs plus AGGREGATE (draft_n, draft_n_accepted) scalars. behavioral_gate.py's own docstring already flags this as a known limitation; dev-gpt-agent (req_bdb8d2b1) confirms it must be closed and that the need is STRUCTURAL -- it does not require waiting for an equal-aggregate/different-order failure to be observed first.

These two trajectories are indistinguishable to the current gate:

  [(4,4), (4,0), (4,4)]
  [(4,2), (4,2), (4,4)]

Both aggregate to 12 drafted / 8 accepted, while executing different work schedules. llama-server's n_accepted_per_pos does not solve it either: it is a cumulative histogram by draft position, so [1,3] and [3,1] still collide.

This matters now rather than theoretically. A promoted cache measured acceptance 0.94734 -> 0.86391, bit-identical across 16 cells, and that difference alone accounted for what looked like a 9% tg512 regression. Any comparison whose arms differ in acceptance is comparing different amounts of work, not different speeds.

## Steps

1. DONE: recorded, in order, per speculative step: draft_n and accepted_n, as (uint32_t, uint32_t) pairs on server_slot_stats.draft_trace (patches/0850_ordered_speculative_trace). Acceptance in this codebase's accept-and-verify design is always a prefix accept (both common_sampler_sample_and_accept_n and server_sample_and_accept_synth stop at the first rejected position -- confirmed by dev-gpt-agent review req_afbaf0f27c6d4511 against the actual sampler implementations, not assumed), so a bare (draft_n, accepted_n) pair per step is sufficient; no acceptance bitmap/accepted-indices needed for this pin.
2. DONE: emits ordered_trace_digest (tools/bigcherry/tuning/behavioral_gate.py's new ordered_trace_digest()) alongside total_drafted/total_accepted/step-count in the normal per-vector artifact (BehavioralGateReport.summary()); the FULL ordered trace is retained only on a non-exact_pass verdict, so the common case stays as small as before this patch.
3. DONE: the gate's equality condition (compare_traces()) is now generated output equal AND ordered draft_trace tuple equal -- replacing the old aggregate-scalar-only (draft_n, draft_n_accepted) comparison. Anything else is BEHAVIOR CHANGED, unchanged from before.
4. DONE: llama-server-side instrumentation implemented as patches/0850_ordered_speculative_trace, exposing timings.draft_trace in the /completion response. Recorded on server_slot_stats (the per-task-result struct, same place n_draft_tokens/n_draft_accepted/n_draft_verif_steps already live) rather than server_slot (where n_accepted_per_pos lives, deliberately excluded from task results per that struct's own comment). Recording point is immediately after `accepted` is computed, BEFORE the checkpoint-rollback early return, guarded by `!slot.spec_is_replay` -- this is the one point that captures each true logical verification decision exactly once, using the original draft width rather than a rollback-truncated replay width (a real bug in my first draft of this point, caught by dev-gpt-agent review before implementation, then verified directly against the checkpoint-rollback code path in server-context.cpp).
