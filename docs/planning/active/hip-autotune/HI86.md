# Topology-aware execution planner (candidate architecture, above per-op dispatch)

## Description

Candidate long-term architecture, NOT started, NOT source-verified -- captured from an ad-hoc exploratory conversation with dev-gpt-agent over the ag-agents-gateway (2026-08-22), not a structured GPT design review. Recording it because it converged on a coherent, self-consistent architecture across several rounds of pushback rather than a single unreviewed suggestion, and because it names a real, currently-missing generalization that several existing items are independently backing into piecemeal.

The core claim: BigCherry's current tuner answers `f(operation, hardware) -> implementation` -- a good abstraction for kernel autotuning, but not sufficient once decisions have consequences outside the local operation (transfer/sync cost, placement, prefill vs decode phase, cross-device reduction). Several existing items are already touching pieces of this from different angles without a shared abstraction: HI18/HI85's SPLIT_REDUCE provider selection, RDNA warp/kernel selection, MTP device embeddings, and prompt-cache/replay checkpoint selection. The proposal is to make 'choose an execution strategy given topology + model + phase' a first-class planning problem instead of accumulating per-feature ad-hoc branching (e.g. arch-conditional code paths).

## Steps

## Detailed Solution & Technical Design

Sketch from the conversation (unverified against source, offered as a shape rather than a spec):

- Local dispatch keeps doing kernel-level autotuning as today, but collapses near-equivalent candidates into a small number of 'strategy classes' with materially different external consequences (e.g. fastest-local / low-workspace / graph-safe) before anything above it ever sees them -- the planner should not enumerate raw kernel candidates.
- Planning happens over coarse execution regions (e.g. prefill region, decode region, an attention/FFN/MoE block), not per-operation, to keep the combinatorics bounded.
- Cached plans use dependency-based validity, not value-based cache keys: a small PlanKey (model/topology/workload class + objective) retrieves a candidate; separate revision tokens owned by each contributing subsystem (topology, model layout, cost model, strategy catalog) determine whether that candidate is still valid, so a cache key doesn't have to grow a field for every fact that could someday matter.
- Runtime state (free VRAM, current residency, etc.) should not be read directly by a plan's applicability check either -- a plan should declare resource *claims* (memory claim, communication requirement, capability requirement) and the owning subsystem (MemoryManager, Topology, Backend) answers whether the claim can be satisfied, rather than the plan embedding a boolean predicate over raw runtime fields. Both of these exist specifically to stop cache keys and precondition checks from re-accumulating the same kind of ad-hoc per-field growth the planner is meant to replace.
- Safety/admissibility (can this strategy be used at all here) is checked before cost (which admissible strategy is fastest), never the reverse -- see HI85's now-recorded SPLIT_REDUCE-specific version of this same idea.

The conversation's own suggested starting slice -- and the reason this item and HI85 should be read together -- is SPLIT_REDUCE: it already has a real per-call provider seam (patches/0830), real telemetry (topology, shape, provider, fallback), and, since HI85, a real confirmed hardware-safety finding (RCCL crashes for heterogeneous N>=3 groups) that needs exactly this kind of admissibility-before-cost handling. A first planner slice bounded to 2-GPU SPLIT_REDUCE with only RcclReduce/MetaReduce as strategy classes was the conversation's proposed 'smallest useful, non-throwaway' starting point.

## Effort & Risk

High risk of being architecture-for-its-own-sake if pursued top-down. The conversation itself flagged its own biggest weak point under pushback: exposing ranked/alternative candidates instead of a single winner risks just relocating combinatorial ugliness into the planner rather than eliminating it, and precondition/applicability checks are themselves a form of signature that can creep the same way cache keys do. Its answer (strategy-class collapsing at the dispatch boundary, coarse execution regions, and declarative resource claims routed to owning subsystems instead of predicates over shared state) held up under three rounds of that pushback, but none of it has been checked against BigCherry's actual code structure yet.

## Standards

Should be checked against HIP_AUTOTUNE_STANDARDS 10.2 (hardware key without device ordinal) and 12.4 (hard eligibility) if pursued -- this proposal's admissibility-before-cost ordering and topology-revision-token idea are close cousins of both, and should be reconciled rather than duplicated.
