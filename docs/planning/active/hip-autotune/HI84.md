# SPLIT_REDUCE N>2 device correctness campaign (D=3/D=4)

## Description

Extends HI18's SPLIT_REDUCE correctness comparison (tools/bigcherry/reduce_correctness.py, patches/1224's D=2 test-hip-reduce probe) to D=3 and D=4 device counts. GPT-designed (2026-08-22), not yet source-verified for its D>2-specific claims (the D=2 comm_ctx-driven construction and the real META split-state/PARTIAL/MIRRORED mechanics ARE independently verified against vendor source -- see HI18.md notes; this item's N>2-specific additions on top of that -- the K=1 MUL_MAT encoding, campaign driver, permutation matrix, provenance state-machine overhaul -- have not been).

**BLOCKED on a fleet question, not a design question:** hardware closure for this item requires 3 and 4 distinct real HIP devices. If the fleet only has the dual-XTX pair on Brutus (D=2), this item cannot produce hardware evidence no matter how complete the code is -- confirm 3+ GPU hardware exists/is planned before starting implementation.

Rationale for creating this as a separate item rather than folding into HI18: HI18's own acceptance criteria are scoped to the validated n2:peer1001 topology; N>2 is templated as future work there already ('Extend the hardware key so a 2-device topology and a 4-device topology do not share a winner'). Keeping this separate avoids blocking HI18's D=2 closure on N>2 hardware availability.

## Detailed Solution & Technical Design

Key mechanics (GPT-designed, only the D=2 subset independently source-verified so far):

- Split-state callback only needs to describe the 2 static leaf tensors (A, B) as GGML_BACKEND_SPLIT_AXIS_0 with 1 element per rank; META derives the compute tensor (MUL_MAT output)'s PARTIAL/MIRRORED state itself from the real handle_mul_mat() rule (verified: ggml-backend-meta.cpp:578-594, axis0+axis0 -> PARTIAL pre-sync / MIRRORED post-sync) and the subgraph partitioner terminates on PARTIAL (verified: line 1962). Do NOT hand-encode PARTIAL in the callback -- that would manufacture the answer instead of exercising production partitioning.
- Static tensors go through ggml_backend_meta_alloc_ctx_tensors_from_buft with USAGE_WEIGHTS; compute tensors (partial, out) get scheduler-allocated with USAGE_COMPUTE via ggml_backend_sched -- NOT the same buffer, because META's callback-invocation decision depends on buffer usage state at tensor-init time.
- Per-rank readback for a MIRRORED tensor via the ordinary ggml_backend_tensor_get only returns simple-backend-0's copy (verified pattern at ggml-backend-meta.cpp's MIRRORED case, 'TODO other simple backend may be better') -- this is why per-device output must come from the existing HI58 nodes-capture telemetry hook (the tensor array 0830 already keeps alive across the provider/fallback boundary), not a new generic accessor.
- device_ids[] / devices[] pairing with rank position is part of the evidence contract -- for permutation testing, rank-N.f32 input files stay attached to logical rank position while physical device assignment varies across the run (device order (2,0,1) means rank-0.f32 -> physical device 2, etc), specifically to catch rank/device-mapping bugs.
- Analytical error bound (gamma=(D-1)*u/(1-(D-1)*u)) is already D-generic in reduce_correctness.py and deliberately conservative enough to tolerate different valid reduction-tree rounding orders at D=3/D=4 (sequential vs pairwise summation can legitimately differ bitwise) -- do not tighten it or promote bitwise agreement to a hard gate for D>2; record cross_device_digest_equal as a diagnostic signal only.
- D=3 is higher priority than D=4: it is the only device count that exercises allreduce_fallback's non-power-of-two fold-excess-ranks-then-copy-back logic (ggml-backend-meta.cpp ~2146-2198); D=2 and D=4 (a pure power of 2) cannot reach that branch at all.

## Notes

Do not start implementation until 3+ GPU hardware availability is confirmed -- this is a fleet/infrastructure question for the user, not something resolvable by more source-reading or design work. If confirmed unavailable, keep this item pending/backlogged rather than superseded (the design remains valid for whenever such hardware exists).

2026-08-22: hardware confirmed by user -- Brutus has 4 physical GPUs: devices 0/1 = RX 7900 XTX (gfx1100, RDNA3, the validated production dual-XTX pair used throughout HI18's D=2 work), device 2 = R9700 (gfx1201, RDNA4), device 3 = RX 6900 XT (gfx1030, RDNA2). So D=3/D=4 hardware closure IS reachable on this box -- the earlier blocker (no 3+ GPU hardware) is resolved.

Important wrinkle this introduces, not present in GPT's design as written: a D=4 run across devices 0-3 is NOT 4 identical GPUs -- it's 3 different architecture generations (RDNA2/3/4) sharing one reduction. That changes what the evidence proves:

- Peer-access topology across generations may differ substantially from the validated n2:peer1001 (partial) case -- device 2/3 may have no direct PCIe peer access to 0/1 or each other, forcing host-staged copies inside META's fallback path that the dual-XTX pair never exercises. This is likely to actually be MORE valuable evidence (exercises code paths D=2 can't reach at all), not less -- but it means 'D=4 correctness' here is heterogeneous-topology correctness, not a stand-in for some future identical-4x-XTX production fleet that doesn't exist.
- RCCL/NCCL cross-architecture collective support should be verified before assuming the RCCL arm is even a valid candidate on this mix -- it may only be exercisable via META on some device pairs.
- The reduction/dispatch hardware-key philosophy (standards 10.2, identical GPUs share a winner) does not straightforwardly apply to a heterogeneous 4-device topology -- this campaign's job is correctness evidence, not a promotable dispatch winner, so this is fine, but worth stating explicitly so nobody later mistakes a passing heterogeneous D=4 run for 'a 4x-XTX winner is safe.'

D=3 options on this hardware: {0,1,2} (dual-XTX + R9700, 2 RDNA3-family + 1 RDNA4) or {0,1,3} (dual-XTX + 6900XT, 2 RDNA3-family + 1 RDNA2) or {1,2,3} / {0,2,3} (single-XTX + the other two). Any 3-of-4 subset is still heterogeneous; there is no homogeneous D=3 subset available. Worth deciding with GPT whether to test multiple D=3 subsets or pick one representative set first.

Next step once implementation starts: re-confirm with GPT whether the split-state/META design changes at all for a heterogeneous topology (it shouldn't structurally -- META's partitioner doesn't care about architecture -- but peer-access-driven code paths and RCCL cross-arch support are real open questions worth raising before writing patches/1224's D>2 support).
