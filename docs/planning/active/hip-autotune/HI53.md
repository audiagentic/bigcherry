# MMVQ native-wrapper eligibility crash on MoE MUL_MAT_ID (ne12 > MMVQ_MAX_BATCH_SIZE)

## Description

Discovered while hardware-validating [[HI52]] (HI54 MMQ workspace fix) on a MoE model (gpt-oss-20B). Server crashes with `GGML_ASSERT(!ids || ne12 <= MMVQ_MAX_BATCH_SIZE) failed` in vendor/llama.cpp/ggml/src/ggml-cuda/mmvq.cu:1337 on the very first completion request under GGML_HIP_DISPATCH_MODE=tune.

Root cause (found by inspection): ggml_hip_mmvq_can_execute in hip-autotune-dispatch.cu has an explicit guard for the FORCED-candidate path -- `if ((sig.flags & GGML_HIP_SIG_HAS_IDS) != 0 && sig.ned[1] > 1) return false;` (blocks multi-token MUL_MAT_ID from a forced MMVQ candidate, with a comment explaining exactly this abort is what it exists to prevent) -- but the NATIVE-WRAPPER branch a few lines above it (`if (self->source_class == GGML_HIP_SOURCE_NATIVE_WRAPPER) return true;`) returns eligible unconditionally, before that check runs. So native selection itself can pick MMVQ for a MoE signature whose actual ne12 exceeds MMVQ_MAX_BATCH_SIZE, and the launch aborts.

## Detailed Solution & Technical Design

Not yet investigated in depth -- this item exists to capture the crash and root-cause hypothesis before the trail goes cold, not as a finished diagnosis. Open questions: (1) is `sig.ned[1] > 1` actually the same condition as `ne12 > MMVQ_MAX_BATCH_SIZE`, or are these two different dimensions that happen to usually correlate -- if they're not equivalent, the forced-candidate guard itself may be insufficient for some shapes even where it does run; (2) why does the native-wrapper branch skip this check entirely -- was it ever meant to (native selection is supposed to mirror upstream's own choice, which presumably wouldn't select an out-of-bounds MMVQ path, so maybe the actual bug is upstream's own native-selection heuristic disagreeing with what mmvq.cu will accept, in a shape bigcherry's dispatch layer is exposing rather than causing); (3) whether this is a bigcherry-only regression or reproduces on a stock/native build too (would clarify whether this is bigcherry's dispatch-layer bug or an upstream one bigcherry merely surfaces by routing through tune mode).

## Validation

Offline validation must prove the source contract against the pinned upstream tree before hardware work is accepted. Hardware evidence must cover each architecture independently, with at least these shape classes for quantized MUL_MAT_ID: ne12=1, the architecture/type-specific native limit, the global MMVQ_MAX_BATCH_SIZE boundary, and one value above that boundary. Each row must record architecture, source type, ne12, selected family, native/forced eligibility result, and whether execution completed without an upstream assertion.

The required architecture set is gfx1030, gfx1100, and gfx1201; missing architecture or boundary-shape evidence is a failed validation, not an implicit pass. A MoE model (gpt-oss-20B or similar) must complete a full tuning pass under GGML_HIP_DISPATCH_MODE=tune without crashing. Reproduce first against a stock/native (non-tune) build to determine whether this is bigcherry-introduced or upstream-inherited.

Current evidence: offline parity remains green (HI53 focused contract suite: 5 passed; broader bounded review: 36 passed). Brutus stock/native q8_0 MUL_MAT_ID passed 75/75 on each required architecture: gfx1030, gfx1100, gfx1201. Brutus tune-mode q8_0 MUL_MAT_ID also passed 75/75 on each, with no assertion, ROCm error, illegal-memory error, or measurement failure; the matrix includes ne12=1 and values below and above that boundary. The exact ne12=8 row and architecture/type-specific native-limit row remain outstanding.

A real gpt-oss-20B Q6 completion was run with GGML_HIP_DISPATCH_MODE=tune, GGML_HIP_TUNE_SCREEN_SAMPLES=1, GGML_HIP_TUNE_FINAL_SAMPLES=2, and graphs disabled, independently on gfx1030 (device 3), gfx1100 (device 0), and gfx1201 (device 2). Each produced 25 result records, including six op=30 MUL_MAT_ID records at ne12=2/4/12. The ne12=12 records are above MMVQ_MAX_BATCH_SIZE=8 and selected mmq:native:v1 with eligible=1 and measured=1; all three architectures reported zero measurement failures and zero launch_failed rejects. The exact ne12=8 boundary and architecture/type-specific native-limit row are still absent, so this item remains in_progress.
