# Illegal HIP memory access under tune-mode dispatch + MTP speculative decoding

## Description

GGML_HIP_DISPATCH_MODE=tune crashes (SIGABRT/illegal HIP memory access) when llama-server runs with --spec-type draft-mtp speculative decoding and a real completion request is served. Crash is in a different code path than HI70's earlier small-ubatch crash (already fixed via GGML_CUDA_DISABLE_GRAPHS=1) -- this one aborts inside ggml_hip_mmvq_can_execute() calling ggml_cuda_get_device(), which itself reports a deferred/async ROCm 'illegal memory access' error, meaning the actual bad access happened earlier in an async HIP call and is only surfaced at this later synchronization point.

## Steps



## Detailed Solution & Technical Design

PRECISELY DIAGNOSED (2026-08-18, per user tip to isolate tune-mode-specific behavior and use serialized kernel launches):

1. Confirmed with GGML_HIP_DISPATCH_MODE=native (dispatch hook active, no candidate rotation) + the SAME MTP speculative-decoding request (Qwen3.5-4B-UD-Q4_K_XL self-speculating MTP, --spec-type draft-mtp --spec-draft-n-max 4, -c 4096 -ctk/-ctv/-ctkd/-ctvd q8_0): completion succeeds end to end, no crash. This rules out MTP/speculative decoding itself, the model, context size, and KV cache configuration as causes -- matches the user's own working production experience (base llama.cpp + MTP + tensor-split dual XTX + Qwen3.8-27B). The bug is specific to GGML_HIP_DISPATCH_MODE=tune's candidate-rotation/measurement path.

2. Reran under GGML_HIP_DISPATCH_MODE=tune with AMD_SERIALIZE_KERNEL=3 (forces synchronous kernel launches, so a deferred/async HIP error surfaces at the actual faulting launch instead of an unrelated later API call). New, more precise stack:
```
ggml_hip_mmq_launch -> ggml_cuda_mul_mat_q -> ggml_cuda_get_device() [reports "illegal memory access"]
  called from (anonymous namespace)::time_candidate(...)
  called from ggml_hip_tuner_resolve(...)
```
The fault is a real MMQ candidate KERNEL LAUNCH going bad while being timed by the tuner's own measurement harness (time_candidate/ggml_hip_tuner_resolve in hip-autotune-tuner.cu), when the dispatch signature carries MTP's small batch width (a handful of draft tokens verified together in one MUL_MAT call -- exactly the src1_ncols in [2,16] range HI70 identified as needed for MMF but which apparently ALSO exercises previously-untested MMQ territory).

3. Checked for an existing precedent: hip-autotune-dispatch.cu's ggml_hip_mmvq_can_execute() (~L1144-1151) already has exactly this class of guard for MMVQ -- get_mmvq_mmid_max_batch(type, cc), added per its own comment to fix 'HI53's first-request crash' where 'tune-mode measurement admitted a native MMVQ launch that native execution would avoid' for MoE expert-token batches. mmvq.cuh declares get_mmvq_mmid_max_batch; there is no equivalent get_mmq_..._max_batch for MMQ. This strongly suggests the SAME class of bug HI53 already fixed for MMVQ exists, unfixed, for MMQ: the tuner's measurement path can select/launch an MMQ candidate at a batch width real native dispatch would never choose (or would route to a different kernel for), and MMQ's own launcher/config path has no equivalent bound to prevent it.

Not yet confirmed which exact MMQ candidate/kernel this is (needs one more level of tracing -- e.g. temporary logging of self->variant fields and sig.ned[] in ggml_hip_mmq_launch just before the crash, or re-running under rocgdb/a HIP memory checker for a precise faulting address) or whether the true fix is a bound analogous to get_mmvq_mmid_max_batch, or a real out-of-bounds workspace/shared-memory sizing bug inside the MMQ kernel itself for very small ncols_dst. Both are plausible; the HI53 precedent makes the batch-bound-guard theory the stronger lead to check first.

## Notes

Found as a side effect of HI70's MMF f16 coverage investigation (RE15 stage F) -- multi-token-batch (src1_ncols 2-16) dispatch is required to ever exercise MMF, and MTP speculative decoding is the natural way to produce that shape from a real workload. This crash blocks that path. Device 2/gfx1201 only tested; not yet tried on gfx1100/gfx1030.

USER GUIDANCE APPLIED (2026-08-18): user correctly predicted 'base llamacpp should work' -- confirmed: native-mode dispatch (equivalent to base llama.cpp's own routing, just going through our thin pass-through hook) handles the exact same MTP request without issue. Kept context conservative (-c 4096, down from the default 262144) and tried q8_0 KV cache on both target and MTP draft model per the user's suggestion -- neither changed the crash (ruling out VRAM/context-size as the cause, which is useful negative information: this is a real dispatch-layer bug, not a resource-limit issue). AMD_SERIALIZE_KERNEL=3 (forces synchronous launches to get a precise fault location instead of a deferred async report) was the key diagnostic step that pinpointed the real crash site to MMQ's tuner-timed launch path, distinct from the eligibility-check-only crash signature seen in the first repro.
