# Investigate whether the HI141 w4:nw8:rpb1:sk0 defect corrupts shared MTP trunk state (draft AND target)

## Description

HI141's remaining root-cause work (why a candidate with 5e-15 NMSE causes such an outsized MTP acceptance collapse) has an architectural angle not yet investigated. This Qwen3.8-27B MTP setup builds its draft context from the SAME model file as the target (server log: "creating MTP draft context against the target model '...Qwen3.8-27B-Q8_0.gguf'") -- consistent with DeepSeek/Qwen-style MTP, where extra prediction head(s) are attached to a shared base-model transformer trunk, not a fully independent smaller draft model (unlike classic speculative decoding).

BigCherry's dispatch/replay cache is signature-keyed (op+shape+dtype) and PROCESS-GLOBAL -- it has no concept of which llama_context (draft vs target) issued a given MUL_MAT_VEC_Q call. Any call from the draft computation and the target computation that happens to share an identical dispatch signature will unavoidably route to the SAME tuned candidate from the SAME cache; there is no mechanism by which they could independently receive different candidates for an identical signature.

Open question: does mmvq:q8_0:w4:nw8:rpb1:sk0:v1 get exercised in a SHARED trunk layer that both the draft proposal and the target verification pass through? If so, a numeric defect there doesn't just corrupt one side of the native-vs-candidate comparison -- it distorts the hidden states feeding BOTH what the draft proposes AND what the target checks it against. That is a structurally different (and plausibly much more consequential) failure mode than "only the target's own decode is slightly off": errors correlated between proposer and verifier do not necessarily cancel the way independent per-side noise would, which could help explain why a numerically tiny (near machine-epsilon) defect produced such a large real acceptance-rate collapse (93.5%->62.1%).

Determine exactly which layers/tensors are shared trunk vs. MTP-head-specific in this model's real graph (Qwen3.8-27B MTP variant) -- read the model's actual tensor names/graph construction in llama.cpp's MTP support code, or inspect the real dispatch signatures the draft context vs target context each issue during a real run.
2. Cross-reference against the real dispatch signature that triggers mmvq:q8_0:w4:nw8:rpb1:sk0:v1 (already known from HI141: ne1=[5120,4,1,1], hidden dim 5120) -- does this shape correspond to a shared-trunk layer, or a head-specific one?
3. If shared: this reframes HI141's remaining root-cause work (the mul_mat_vec_q rows_per_block=1 source read) with a sharper hypothesis -- the defect's real-world severity may be explained by proposer/verifier correlation, not just isolated target-side numeric drift, and this same correlation risk should inform HI143's behavioral-gate design (e.g. whether corpus vectors need to specifically stress shared-trunk-heavy generation patterns).
4. If independent/head-specific: this rules out the correlation hypothesis and the investigation should focus purely on the isolated numeric defect itself.
