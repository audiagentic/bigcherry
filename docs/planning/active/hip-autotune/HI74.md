# Replay v5 foundation — route-aware cache format with match-kind extension point

## Description

Cross-cutting foundation for the routing-transform replay contract (HI30/HI31) and any future generalised entries (HI36b). Per the 2026-08-21 GPT adjudication (req_09656b782a5d449a) and the HI30/31 verdict: a fresh-process transformed route requires a NEW binary replay format, not just an SQL field. The current v4 layout has no transform field, and a transformed winner must be validated against the TRANSFORMED signature before becoming a binding — a lookup contract change, not a byte addition.

## Detailed Solution & Technical Design

Wire contract:
- v5 entry adds uint16 transform_id (0 == GGML_HIP_TRANSFORM_NONE).
- v5 entry adds an explicit match/key-kind discriminator: match_kind = EXACT | MMQ_KM | MMVQ_NE0 | ... — an extension point so generalised entries (HI36b) do not force v6. Sufficient versioning/length that future key forms are rejectable rather than misparsed.
- transform_id is the STORED DECISION; it does not join the dispatch digest (which identifies the operation being decided).
- ABI pinning: until transforms carry an implementation_version, transformed entries REQUIRE exact manifest/source provenance (no relaxed revision mode). Ordinary candidate-only replay keeps today's rules.
- v4 input: production replay rejects with rerun_required (consistent with fail-closed policy). Python offline legacy reader retained for historical campaign artifacts only.
- Loader split: 'parse/select cached entry' (persistence layer) vs 'validate route against this invocation' (resolver: transform exists && equivalence_verified && can_apply(original_sig) && candidate.family == target_family && can_execute(candidate, transformed_sig, hw) && variant compatible). Unknown/missing/inapplicable transform → native.

### 2026-08-21 pin-specific kernel identity — a format fact from the S1b equivalence trace

The 22dc605→0adcc3bb window renamed the non-fusion small_k mmvq kernel instantiation: `mul_mat_vec_q` gained a 7th template parameter (`halve_iters`, added upstream in `25ae3a9b` #26843 alongside the GB10 nwarps table) (6-param mangled name at 22dc605, 7-param at b10502). Behaviour is unchanged (identical dispatch count, busy share to 0.02pp, byte-identical dominant geometries; ceiling 73.224%→73.243%) but the KERNEL-NAME identity changed. Consequences for the v5 format:

1. Mangled kernel names are pin-specific identifiers. A cache or provenance record that keys on them must carry the source revision (the dispatch digest already does — keep it that way, never relax).
2. The `match_kind` discriminator and any future kernel-identity field must be treated as schema-versioned, not free-form: a pin move can silently change every name in a family.
3. This is concrete evidence for the rebase A-list item (A6 or wherever it lands): pin moves invalidate name-keyed caches by construction; the v4→v5 `rerun_required` path is the correct production behaviour for cross-pin caches.

Source: docs/reference/h36-campaign-27b-r9700/README.md, S1b section.
