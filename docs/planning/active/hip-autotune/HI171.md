# Existing-cache execution audit is P0, before any further tuning campaign

## Description

Owner-directed correction to the tuning runbook (C:\Users\mgs\Downloads\BigCherry_HIP_Tuning_Improvement_and_Candidate_Completeness_Runbook.md) after reviewing HI168's production-shaped baseline (docs/evidence/hi168-baseline-20260906.md). The runbook's original sequencing put HI166 (ordered speculative trace equality) and candidate-completeness auditing first, then execution/accounting. That is right for NEW campaigns, but it skips a cheaper, higher-value question for the FIVE caches HI168 already produced: did the winners we already promoted even launch as intended, and if so, did they help? Answering that needs no new GPU tuning time, only joining artifacts already on disk.

HI168's concrete findings that motivate this: GPU0, GPU1 and gfx1030 replay generally failed to improve on BC native end-to-end (dominant metrics near parity or negative). The dual-XTX 27B and gfx1201 results remain exploratory -- every row across all five caches is performance_admitted=false. The gfx1201 prompt-processing deltas (+15-24%) are an EXECUTION-IDENTITY WARNING, not a performance claim: their magnitude is inconsistent with the XTX/gfx1030 results and must not be treated as real until physical-device evidence rules out CPU fallback or a topology mismatch.

Given that, widening the candidate search (more MMQ variants, BLAS completion, etc.) before knowing whether existing promoted keys even execute as tuned risks the same failure class HI166 exists to prevent: a larger search space finds more apparent winners for reasons unrelated to being faster. Poor replay results must not be read as 'we need more candidates' until execution is audited -- they may equally mean the winners we have never launch, or launch and lose.

## Detailed Solution & Technical Design

Deliberately NOT attempted: per-key production GPU-time. Nothing in this project's current artifacts measures how long an individual promoted candidate runs inside the real serving graph -- that needs rocprofv3 kernel-fraction data joined per dispatch digest (runbook section 16), which is a separate, larger piece of work. execution_audit.py's DIFFERENT_FASTER/DIFFERENT_SLOWER split is therefore driven by an optional, CALLER-SUPPLIED --e2e-verdicts mapping (dispatch digest -> 'improved'|'regressed'), never invented from the isolated tuner measurement. Absent that input, a genuinely-different, genuinely-launched candidate defaults to DIFFERENT_FASTER with e2e_verdict='not_measured' recorded explicitly in the row -- an isolated win, not a production claim.
