### gpt scoping verdict (2026-08-29): mixed-provider dispatch is NOT currently feasible -- real architectural gap, not just missing tuning

Confirmed via real source inspection (ggml-backend-meta.cpp): META builds exactly ONE comm_ctx from ALL participating simple_backends (comm_init(simple_backends.data(), simple_backends.size())), and every reduction collects one terminal tensor from every backend and calls ONE comm_allreduce(comm_ctx, nodes.data()) against that whole set. BigCherry's GGML_HIP_REDUCE_PLAN selects a provider PER CALL but always against that same whole-cohort comm_ctx; forced rccl only activates when comms.size() == backends.size() (i.e. ALL participants, no subset). Patch 1225 likewise evaluates the COMPLETE device set before ncclCommInitAll -- no participant-mask or subcommunicator concept exists anywhere in this architecture.

**Consequence**: 'RCCL for devices {0,1,2}, META for device 3, combined into one correct 4-GPU tensor-split result' is not just unimplemented -- it isn't even mathematically well-formed under the current single-comm_ctx model. Naively running RCCL over {0,1,2} while device 3 independently reduces via META would produce a WRONG result (RCCL yields S0+S1+S2; device 3's real contribution S3 is never combined in). A correct implementation would need genuine hierarchical/composite reduction (subgroup reduce -> cross-group combine -> dissemination) -- a new collective-composition architecture, not Phase 2 tuning work.

**Recommended scope (gpt, adopted)**: HI142 does NOT attempt mixed-provider 4-GPU composition. Two-part plan:

1. **RQ00 (short, first)**: formal design-gate closure confirming (a) participant-set construction path (tensor-split devices -> META simple_backends -> comm_ctx), (b) the one-provider-covers-all-participants invariant as a recorded architectural fact, (c) explicit disposition that hierarchical mixed-provider execution is out of HI142's scope (a new composition architecture, deferred to a future separate item, not silently absorbed here).
2. **P2.1-P2.11 (main body)**: qualify and tune RCCL for the PURE 3-GPU-eligible cohort -- specifically {0,1,2} (2x XTX + R9700), where device 3 is simply not present in that server process / not a tensor-split participant at all (not 'excluded from the communicator while still contributing a shard' -- genuinely absent from that deployment). This is a real, immediately deployable, distinct server configuration from the current dual-XTX production baseline -- not a variant of the 4-GPU case.

TopologyIdentityV1 design: {XTX,R9700} pairs canonicalize to ONE identity when topology-relevant facts match (architecture classes, PCIe-AtomicOps eligibility, transport class, peer-access capability) -- do NOT encode 'device 3 excluded' or physical ordinals as negative topology facts; an idle/uninvolved GPU is irrelevant, but a GPU that DOES own a tensor-split shard is a real participant, not a spectator. For any future 4-GPU work, keep TopologyIdentityV1 (hardware graph) strictly separate from a new CollectiveExecutionPlanIdentityV1 (participant partition + subgroup provider(s) + combine/dissemination stage) -- do not overload topology identity with provider-selection/exclusion facts.

**Bottom line for the user**: near-term real, deployable value is a genuine 3-GPU-only (2x XTX + R9700, no 6900XT in that process) server configuration with RCCL instead of META for its reduction -- expected to inherit HI18's ~40x speedup. True 4-GPU-with-6900XT-present configurations remain META-only for the foreseeable future; making RCCL+META coexist correctly in one 4-GPU communicator is real, separate, nontrivial future engineering work, not a tuning task.
