# BLAS-family kernel tuning: authorize and build candidate search for the rocBLAS/Tensile path HI17 made observable

## Description

HI17 (completed) decomposed the opaque BLAS candidate into a controlled, observable execution plan -- the catalog retains blas:native:v1 as the correctness fallback, runtime native-only resolve/apply/execute is implemented, and record-mode telemetry captures effective API/provider/backend, conversions, temporary bytes, calculated workspace, and execution-options state. Critically, HI17's own closure notes are explicit that this was foundational only: "no provider/API alternative or performance promotion was authorized." Today, every BLAS-family dispatch (the Cijk_Alik_Bljk_... rocBLAS/Tensile GEMM kernels visible in real kernel traces) runs through the identical forced-native path regardless of GGML_HIP_DISPATCH_MODE=native vs replay -- BigCherry's tuning/candidate-promotion system has never searched or promoted an alternative BLAS kernel, provider, or compute-type.

This surfaced concretely during HI172's real kernel-trace investigation (2026-09-09): the two largest single-kernel time deltas in an early GPU0 native-vs-replay trace were BOTH rocBLAS/Tensile kernels, present at IDENTICAL call counts in both arms (proving they cannot be a tuning-candidate effect, since BLAS isn't tuned) -- which is exactly the evidence that led to identifying a real measurement-order confound (fixed native-then-replay ordering within each pass, without HI171/TEST.md's own required arm-order rotation) rather than a genuine dispatch-mode effect. That investigation is what prompted this item: BLAS is currently BigCherry's single largest unexplored optimization surface, already has the necessary observability/candidate-identity foundation (HI17), but has zero live candidate search.

Scope for this item: design (and, once designed, implement) an actual BLAS-family candidate search -- alternative rocBLAS/Tensile solution selection, compute_type variants (the existing opt-in GGML_HIP_BLAS_EXPERIMENT=f16_temp per-call route is a precedent, currently manual/experimental only, never evaluated by the tuner), or provider alternatives -- integrated into the SAME promotion/correctness-evidence/behavioral-gate pipeline every other tuning family already goes through (HI67 correctness evidence, HI143 behavioral gate, HTR01 recovery), not a separate ad-hoc mechanism. Given HI17's own explicit warning that this needs "the required same-representative native-versus-forced execution, complete effective telemetry, and quantitative timing-parity gate" before any promotion, and BLAS kernels (rocBLAS/Tensile-generated) are a fundamentally different code surface than BigCherry's own hand-written MMVQ/MMQ candidates (no source-level control over the kernel implementation itself -- candidate selection here means choosing AMONG existing library-provided solutions/algorithms, not authoring new kernel variants), this is architecturally a different kind of tuning problem and should not assume the existing MMVQ/MMQ tuner machinery transfers directly.

## Steps

1. Add `solution_selection` as an eighth field on the BLAS candidate identity (extends HI17's seven-field plan: operand_type, accumulation_type, output_type, source_a/b_conversion, output_conversion, numerical_class) -- shape `(provider, library_version_triple, solution_index)`. Runtime-id side table extension, not a change to `ggml_hip_blas_plan_v1`'s existing fields.
2. Build an offline solution-discovery pass (extends RD87's `tools/lab/rd87-hipblaslt-oracle/` methodology into a maintained tuning-campaign lane): for each real captured signature that resolves to the `blas:native` family, enumerate real rocBLAS solutions for the currently-active provider, time each, persist the winning `solution_index` keyed by (signature, exact rocBLAS/hipBLAS/hipBLASLt version triple).
3. Implement resolve/apply/execute for the new candidate: resolve checks for an exact signature + exact-version-triple match in the persisted table; apply requests that specific `solution_index` via the library's explicit solution-selection API (rocBLAS: `rocblas_gemm_ex` with explicit `solution_index`); execute reuses HI17's shared vendor forwarder. No match -> unchanged forced-native fallback.
4. Add per-solution workspace/resource measurement to the offline discovery pass (do not inherit BLAS-1's existing pool-size assumptions).
5. Add the version-triple invalidation check as a hard, fail-closed gate: any rocBLAS/hipBLAS/hipBLASLt version mismatch between discovery-time and apply-time makes the persisted selection unusable, forcing fallback to forced-native (never interpolated/reused across versions).
6. Wire the new candidate family into the existing promotion/correctness-evidence/behavioral-gate pipeline (HI67 correctness evidence, HI143 behavioral gate, HTR01 recovery) -- no separate ad-hoc promotion mechanism.
7. Offline regression tests: candidate-identity contract, version-triple gating (positive + mismatch-invalidation), resolve/apply/execute seam, workspace accounting, fail-closed missing-provenance cases.
8. Real-hardware validation: rerun RD87's own shape set (`tools/lab/rd87-hipblaslt-oracle/rd87_comparison.csv`) as the first real discovery-campaign input on Brutus, since it's already known-real, deduped, and has an established native-timing baseline to gate against.

## Detailed Solution & Technical Design

**Mechanically, a BLAS-family candidate is a persisted rocBLAS/hipBLASLt solution_index selection, bound to an exact library-version triple** -- not a new hand-written kernel (rocBLAS/Tensile kernels are vendor-generated; BigCherry has no source-level control over them). This extends HI17's existing stable candidate identity (operand/accumulation/output type, conversion routes, numerical_class) with an eighth field: `solution_selection = (provider, library_version_triple, solution_index)`. Runtime behavior: resolve -> if a matching persisted solution_selection exists for this exact signature + exact installed rocBLAS/hipBLAS/hipBLASLt version triple, request that specific solution via the library's solution-selection API (rocBLAS: `rocblas_gemm_ex` with an explicit `solution_index`; hipBLASLt: `hipblasLtMatmulAlgoGetHeuristic`/explicit algo selection) instead of letting the library's own heuristic pick -- otherwise fall back to today's forced-native path unchanged.

**This is offline-tuned, not online-searched at runtime** -- mirrors llama.cpp's own MMVQ/MMQ approach and RD87's own oracle methodology: solution discovery (enumerate every real solution for a shape, time each, per RD87's `hipblaslt-bench --algo_method all` precedent, generalized to rocBLAS's own solution enumeration for the currently-active provider) happens offline during a tuning campaign, producing a small persisted table of (signature, library_version_triple) -> winning solution_index. Runtime never enumerates or searches; it only ever requests one specific pre-selected solution_index. This avoids RD87's own risk item #4 (runtime enumeration cost) entirely by construction.

**Scope boundary, driven directly by RD87's real data**: eligibility for a BLAS-family solution-selection candidate is gated on the signature ALREADY resolving to the `blas:native` family at native dispatch time (HI17's existing family-membership boundary) -- not on raw shape heuristics (small-K/large-N). This naturally excludes every MMVQ/MMQ-eligible signature (RD87's negative-finding population, tiny-N N<=5 decode) without needing a separate exclusion rule, since those signatures never reach the BLAS family's candidate set in the first place. RD87's CSV (`tools/lab/rd87-hipblaslt-oracle/rd87_comparison.csv`) is real prior evidence that real headroom exists specifically in this already-BLAS-native population (up to 2.74x on K=256,M=256,N=24).

**MVP slice, first thing to implement**: solution_index selection only, for the CURRENTLY ACTIVE provider (rocBLAS, since that's what forced-native already uses) -- do not attempt rocBLAS-vs-hipBLASLt provider switching in the same slice; that's a separate follow-on candidate dimension once solution_index selection itself is proven. Readiness gate (following HI17/HI25's fail-closed pattern) requires, before any promotion: (a) exact rocBLAS/hipBLAS/hipBLASLt version-triple match between the version solution_index was discovered under and the version it's being applied under -- mismatch invalidates the persisted selection outright, no fallback interpolation; (b) architecture match; (c) CPU-reference correctness pass for the exact signature; (d) resource/workspace evidence -- solution_index selection can change required workspace size, so this must be measured per-solution, not assumed from BLAS-1's existing pool sizing; (e) benchmark evidence vs current forced-native under the SAME quantitative noise-tolerance gate HI17's parity evidence used (`abs(delta) <= max(5%, native repeatability spread)`).

**Real risks specific to this candidate family** (distinct from BigCherry's existing MMVQ/MMQ tuner assumptions, which assume BigCherry controls kernel source): (1) solution_index numbering is not guaranteed stable across ROCm/rocBLAS/hipBLASLt releases -- the version-triple binding above is a hard correctness requirement, not an optimization; a version bump must invalidate every persisted selection until rediscovered, exactly like HI17's own build-namespace-extension item flagged. (2) workspace/temp-buffer sizing varies per solution -- must be queried and accounted per-candidate, not inherited from BLAS-1's existing pool assumptions. (3) Runtime solution enumeration must never happen in the hot path -- discovery is strictly offline (an extension of RD87's oracle methodology, generalized from hipBLASLt's external bench tool to a proper offline tuning-campaign pass that can also drive rocBLAS's own internal solution enumeration).

### Cross-link: RD87's hipBLASLt oracle (2026-09-09) -- real prior data point for this item's scope

RD87 ran `hipblaslt-bench` (external AMD offline-tuning client, not BigCherry's own dispatch path) against 55 real GEMM/MMVQ shapes captured from a live dual-gfx1100 27B tuning campaign, comparing native BigCherry dispatch vs hipBLASLt heuristic vs hipBLASLt's best-of-every-real-solution run (`--algo_method all`). See `tools/lab/rd87-hipblaslt-oracle/` (script + `rd87_comparison.csv`, corrected 2026-09-09 after an earlier analysis bug hid the real all-solutions numbers -- see RD87's own notes for the correction detail) and `docs/planning/completed/rdna-boost-experiments/RD87.md`.

**Relevant to this item's scoping**: the wins and losses split cleanly by which native code path the shape already uses.

- Shapes already on `blas:native:v1` (small-K K=64/256, larger-N N>=8 -- i.e. real BLAS-family dispatch, the exact surface this item targets) show hipBLASLt's best-of-all-solutions run 1.2x-2.7x FASTER than native rocBLAS in several real cases (best: K=256,M=256,N=24, 18.02us native vs 6.58us hipBLASLt-tuned). This is real, external, corroborating evidence that BLAS-family solution search (this item's scope) has genuine headroom for at least some shapes -- not just a theoretical opportunity.
- Shapes on `mmvq:native:v1` (tiny-N N<=5 decode, BigCherry's own hand-written kernel family, NOT the BLAS family) are a bad fit for hipBLASLt -- up to 10x slower in heuristic mode, at best noise-level parity even with exhaustive search. This is out of this item's scope anyway (MMVQ is a different candidate family, already tuned by the existing tuner) but is useful negative evidence against ever routing tiny-N decode dispatch through a generic BLAS library, external or internal.

Recommend treating RD87's CSV as a real starting shape-list when scoping this item's initial search space: prioritize small-K/larger-N BLAS-native shapes, and do not expect wins on tiny-N decode shapes even if they showed up in a BLAS-family trace (per HI172's kernel-trace finding that motivated filing this item).
