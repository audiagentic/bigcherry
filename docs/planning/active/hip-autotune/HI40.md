# Fix pool workspace metrics to track requested size, not actual pool size

## Description

patches/0900_pool_workspace_metrics.py's original accounting used the pool's actual_size (which on a best-fit reuse hit can reflect a stranger's leftover cached buffer, the exact contamination HI56's cache-clear call worked around) rather than what the candidate genuinely requested. This item corrects it to track requested size.

### 2026-08-12: bc_requested_size fix re-applied to patches/0900_pool_workspace_metrics.py

Added `bc_requested_size` member to `ggml_cuda_pool_alloc<T>`, set it at `alloc()` time to `size * sizeof(T)`, switched both `note_alloc`/`note_free` accounting calls to read it instead of `actual_size` (the real `pool->free(ptr, actual_size)` call is untouched). Verified all four patch anchors match the current pinned vendor tree.

**Discovered while landing this: the patch has never actually been applied to any build.** `patches/0900_pool_workspace_metrics.py` declares no `STATE` constant, so `patchset.module_state()` defaults it to `"untested"` -- and `bigcherry apply --recipe bigcherry --force` (this project's normal apply invocation) filters to `states=validated` by default. Confirmed via a real apply run: `common.cuh` does not appear in the patch report at all, while every `STATE = "validated"` patch does. This is consistent with, and likely why, the tuner-side wiring gap exists (see below) -- nothing has ever exercised these counters end to end, including the pre-reset run this fix's own history describes as "verified against a synthetic pristine base," which was never a real build/run.

Deliberately leaving `STATE` unset rather than flipping to `"validated"` now: doing so would apply the patch (correct in isolation) into a tree where the counters it adds are still completely unread (see below), which is exactly the "do not enable workspace-based ranking until HI40+HI54 land together" gate [[HI54]] already calls for. Flip to `validated` only once the tuner wiring (below) exists and the combined chain has been run against real hardware.

**New gap found while wiring this up:** `bc_workspace_peak_bytes()`/`bc_workspace_clear_cache()` are entirely unreferenced anywhere in `hip-autotune-tuner.cu`, `hip-autotune-dispatch.cu`, or `hip-autotune-record.cpp` (confirmed via grep, zero matches outside `common.cuh`/`ggml-cuda.cu`). No isolated-vs-interleaved measurement-site distinction exists in the tuner to hang HI54's clear/rebase protocol on -- that structure itself is unbuilt.

Remaining scope, in order: (1) DONE -- requested-size accounting is correct in the patch, gated by design pending (2). (2) wire `bc_workspace_peak_bytes()` into the tuner's per-candidate result and JSON emission (`measurement.pool_peak_bytes`), including introducing an isolated-vs-interleaved measurement-site distinction -- currently entirely absent, this is [[HI54]]'s larger, previously-untracked half. (3) HI54's clear-before-warmup/rebase-after-warmup protocol at the isolated sites (2) introduces. (4) flip `STATE = "validated"` on this patch once (1)-(3) are proven against real hardware, and only then run the corpus-wide identical-pool_peak_bytes-across-siblings check and decide whether `bc_workspace_clear_cache()`'s overhead is safe to drop.
