## Notes

Formerly tracked as HI64.

### 2026-08-11: requested-size fix implemented and verified against a synthetic pristine base -- deliberately NOT applied to the live vendor tree

The fix is not a one-line swap. ggml_cuda_pool_alloc<T>::alloc()'s note_alloc call and its destructor's note_free call must stay paired on the same quantity, or the running bc_workspace_in_use counter drifts on every alloc/free cycle and corrupts every later peak reading (pool->free(ptr, actual_size) -- the real pool operation -- correctly keeps using actual_size; only the accounting side-channel calls change). Implemented correctly: added a new bc_requested_size member to ggml_cuda_pool_alloc<T>, set once at alloc() time (size * sizeof(T)), and both note_alloc/note_free now read from it instead of actual_size.

A second, more serious hazard found: patches are additive (insert_after), and the live vendor tree already had the OLD version of this same patch's output baked in from a prior apply. Re-running bigcherry apply against that tree would not replace the old inserted lines -- it would insert the new ones alongside them. Verified concretely via an isolated synthetic "already old-patched" snippet: confirmed 2 note_alloc/2 note_free calls resulted (the double-counting bug predicted, reproduced offline). Verified the fix IS correct against a genuinely pristine synthetic base: single note_alloc/note_free pair each, correctly reading bc_requested_size.

Deliberately not applied to the real vendor tree in that pass -- needed a from-scratch re-clone + full re-apply to land safely.

### 2026-08-12: confirmed the fix did NOT survive into the recovered/committed patch file

Checked patches/0900_pool_workspace_metrics.py as recovered and committed today (2026-08-12, commit 46f3594, itself reconstructed from an earlier session transcript after the 2026-08-11 external git-reset incident): `grep -n "bc_requested_size\|actual_size" patches/0900_pool_workspace_metrics.py` shows note_alloc/note_free still read `actual_size` (lines 130-140), not `bc_requested_size`. The fix described above was never committed anywhere and is not present in the current tree -- this is real remaining work, not already-done work with a stale tracking record. The transcript's own "deliberately not applied to the live tree" note is the likely explanation: the fix existed only as an uncommitted edit in a session that was itself wiped by the same incident, one layer removed from what SE01-03/EX01/EX02 recovered.

Remaining scope: (1) re-apply the bc_requested_size fix to patches/0900_pool_workspace_metrics.py, (2) the corpus-wide identical-pool_peak_bytes-across-siblings check against real tune data, (3) decide whether bc_workspace_clear_cache()'s overhead is now safe to drop -- all three need real work, none are done.
