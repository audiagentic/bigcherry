# pin-bump orchestrator: design only (split into HI151/HI152/HI153 for implementation)

## Description

Design-phase item capturing gpt's proposed `bigcherry pin-bump <target>` orchestrator (from req_57759a6f9bbb43ef, prompted by the real b10502->b10680 bump-process test) plus my rebuttal points still being debated with gpt (req pending). Goal: automate the common case of PIN_BUMP.md's manual procedure while stopping cleanly and precisely on anything genuinely uncertain -- not a survey, a target design to implement.

gpt's initial proposal (accepted parts):
- New orchestrating command `bigcherry pin-bump <target> [--recipe] [--trees] [--resume] [--report-dir]`, not a shell wrapper -- existing verbs (repin/pull/audit/patch-rebase-check/apply/pin-status) already return structured results a wrapper would have to re-parse from prose.
- Global preflight (resolve ref->SHA, clean controller checkout, probe every required tree reachable) before any mutation.
- One committed transition (config/recipes.toml + releases/pin-transition.json together), remote trees consume that SAME declaring commit rather than independently repinning.
- Per-tree: sync to declaring commit (dirty/non-FF => STOP) -> pull -> audit -> patch-lint -> patch-rebase-check --all (coverage report) -> patch-rebase-check --recipe (build-selection report) -> apply --known-good on the RECIPE report only (never --all) -> re-audit -> rebuild campaign surfaces -> record invalidation dispositions.
- Completion requires pin-status --complete --all-remotes PASS, verbatim output captured in release notes, transition marker cleared in the same commit as invalidation-list dispositions.
- Stop/auto-proceed table: auto-proceed only past CLEAN/CLEAN_NOOP/NOT_APPLICABLE_BY_DESIGN and expected transient old->new divergence; STOP on FAILED_NEEDS_RECONCILIATION, BLOCKED_BY_DEPENDENCY, QUARANTINED, non-FF/unreachable trees, general audit failure.
- One narrow, provably-safe auto-repair carve-out: overlay drift where every drifted path is (a) not upstream-tracked, (b) overlay-owned, (c) differs from current overlay ONLY by newline encoding -- exactly the bug fixed live this session -- otherwise STOP, never blind --force.
- A `coverage.complete` invariant (discovered_patch_ids == checked_patch_ids UNION explicit rejected exclusions) using the real, already-existing `patch-rebase-check --all`, as a completion gate independent of recipe selection -- meant to close the class of gap where a non-recipe patch (like 1206, though that specific instance turned out NOT to be broken -- see HI149's correction) could silently go unchecked forever.
- Structured JSON failure envelope per STOP: schema_version, operation, run_id, target{from/to ref+sha}, transition_commit, phase, tree{name,role,path}, failure{code,human_required,retryable,summary,evidence,recommended_actions}, resume{completed_phases,next_phase}, artifacts[]. Orchestration state itself lives under artifacts/pin-bump/<run>/, never dumped into releases/*.json (avoids the exact class of bug fixed today in records.py).

Verified against real source before accepting (gpt has fabricated verbatim claims before this session): `patch-rebase-check --all` and `patch-lint` both really exist with the described flags; audit.py's check_overlay_sync really does raw `read_bytes() != read_bytes()` comparison (audit.py:526), matching the newline-only auto-repair precondition.

Open rebuttal points sent back to gpt (see follow-up request) -- do not treat these as settled until gpt's second-round response is triaged:
1. The overlay auto-repair precondition 'matches the previous BigCherry overlay materialization' has no real backing mechanism -- nothing today records a history of past overlay writes to compare against. Pushed gpt to either drop that clause (rely only on the newline-only-diff check, which IS mechanically checkable) or specify exactly what would store/provide that history.
2. gpt's per-tree sync step only checks git-dirty/non-fast-forward before touching a remote tree. That's necessary but not sufficient -- today's real run found a tree (Brutus's configured campaign path) with a clean-enough-looking git state but active concurrent-session evidence (running experiment log tails) that made it unsafe to touch. Asked gpt for a concrete liveness/lock signal beyond git status.
3. Questioned whether the coverage.complete gate (100% of --all patches clean before ANY bump can complete) is too strict for a real repo with routinely-churning experimental/rdna-boosts patches -- asked whether an explicit per-patch triage disposition (clean, or knowingly-broken-with-owner-and-reason) should satisfy the gate instead of requiring literal 100% clean, so unrelated production bumps aren't chronically blocked by known experimental breakage.
4. Asked gpt to justify the full multi-tree SSH-orchestrating state-machine's complexity against actual bump frequency -- proposed a staged rollout (Phase 1: single-tree orchestrator + coverage gate + failure envelope; Phase 2: multi-tree SSH sequencing) rather than building the whole thing at once, and asked gpt to argue for or against that split.

Next step: incorporate gpt's second-round response, resolve the four points above, then split into concrete implementation sub-items (schema/state-machine skeleton, coverage gate, narrow overlay auto-repair, multi-tree sequencing) the way HI145 was split into HI146/147/148.

### Round 2 (gpt rebuttal response, req_2a88067289ea4015) -- verified and largely converged

Verified real before accepting: ResourceLock class really exists (tools/bigcherry/core/resources.py:17), ProjectContext.work_root really exists and is used exactly as claimed (build/builds.py, campaign/build.py, campaign/lane.py), and patch lifecycle really has a `STATE = "rejected"` value in use (patches/1003, patches/1004) alongside 'validated'/'untested' seen elsewhere -- all real, not fabricated.

**One caught fabrication**: gpt's cadence argument cited "b10362 -> b10502 on 20 Aug 2026; b10502 -> b10680 on 29 Aug 2026" as evidence of ~weekly cadence. Checked releases/*.json directly: b10502.json's first_seen is 2026-08-20T03:16:47Z, but b10362.json's first_seen is 2026-08-25T09:31:50Z -- FIVE DAYS LATER than b10502, the reverse of the chronology gpt described. The release-record history is not a clean monotonic bump timeline (there's out-of-order/experimental pin activity, consistent with this being a fast-moving multi-agent research repo, not a simple linear release cadence). This doesn't overturn gpt's underlying conclusion (too little/too messy history to justify a distributed state machine yet) -- if anything it strengthens it -- but the specific evidence cited was wrong and should not be repeated as fact.

**Resolution on the four points -- all four accepted as the target design:**

1. **Overlay auto-repair**: gpt retracted the unfalsifiable "previous materialization" clause outright, agreeing it isn't checkable and shouldn't be invented. Final precondition, all must hold: overlay-owned path, not upstream-tracked, raw bytes differ, both sides decode as UTF-8, and content is exactly equal after CRLF/CR->LF normalization. Otherwise STOP. Matches exactly the newline-only fix already shipped today in _write_overlay_snapshot/_copy_overlay -- no new mechanism needed, just gating apply's existing normalized-equality check behind "was this the ONLY thing that differed" before allowing an unattended rewrite.

2. **Liveness beyond git-dirty**: gpt agrees git status alone is insufficient (concedes the real Brutus incident this session would not have been caught by it) and proposes a new tree-activity protocol under ProjectContext.work_root (real, existing canonical host-local state): `<work_root>/tree-activity/<hash(project_root)>/maintenance.lock` + `leases/<uuid>.json` (pid, hostname, command, run_id, project_root, started_at). Long-running runners (build/campaign-build/tune-campaign/profile-campaign/experiment) create/remove a lease; pin-bump acquires the maintenance lock only if no live leases exist; new work refuses to start while the maintenance lock is held; staleness is decided by real PID liveness on that host, never silently overridden. Explicitly flags this needs a transition period (not every runner is lease-aware yet) with a Linux /proc/*/cwd + /proc/*/cmdline scan as a diagnostic-only fallback, never authoritative. This is new infrastructure to build, not something that already exists -- correctly labeled as such.

3. **Coverage-gate strictness**: gpt retracted the literal-100%-clean requirement AND rejected my suggested `STATE="known_broken"` lifecycle addition (correctly -- lifecycle states are patch identity, rebase failures are revision-specific, conflating them would be wrong). Instead: a separate revision-bound disposition record `{patch_id, target_revision, patch_digest, disposition: "known_broken", failure_status, reason, owner, tracking_item}`, invalidated the moment target_revision or patch_digest changes. Completion policy: a RECIPE-selected patch must be clean (no escape hatch, ever); a non-selected patch may be clean OR carry a matching known_broken disposition; a rejected patch is excluded-but-reported; anything undiscovered/untriaged STOPs. This satisfies my original concern (production bumps aren't hostage to experimental churn) without silently hiding anything -- HI149 (the RD13 false alarm) would have been exactly this kind of disposition IF 1206 had actually been broken, which it wasn't.

4. **Complexity vs cadence**: gpt reversed its original position and now argues AGAINST building multi-tree SSH orchestration yet, explicitly on cost/evidence grounds -- current bump history is too sparse and too irregular (see the corrected chronology above) to justify a distributed state machine, and this very bump surfaced multiple never-before-seen edge cases in the single-tree case alone. Proposes exactly the staged split I suggested: Phase 1 ships a single-tree `bigcherry pin-bump <target>` (lease/liveness gate, transition detection, pull/audit/newline-self-heal/patch-lint/patch-rebase-check --all with triage-gated coverage/recipe-apply/rebuild/structured-JSON-result), human still invokes it once per required tree by hand, `pin-status --complete --all-remotes` remains the real cross-tree authority (already real, already sufficient for this). Phase 2 (controller-driven SSH sequencing over the same per-tree worker) only after Phase 1 has survived roughly 3 real bumps.

**Converged target design** (supersedes the round-1 description above where they conflict): single-tree first-class CLI orchestrator (`bigcherry pin-bump <target>`) + new tree-activity lease/maintenance-lock protocol under work_root + all-patch coverage accounting with revision-bound `known_broken` dispositions (not a lifecycle-state change) + the existing multi-tree `pin-status --complete --all-remotes` gate, used as-is. Multi-tree SSH orchestration explicitly deferred to a later Phase 2, not part of this item's implementation scope.
