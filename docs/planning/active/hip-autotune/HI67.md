# CPU-reference correctness contract: headroom rule, deterministic seeds, tune mode stays native

## Description

CPU-reference correctness contract for tuner acceptance and promotion evidence (F1, P0): the tuner's native-relative acceptance does not bound end-to-end error, so marginal signatures can intermittently pass tuning yet fail the project's own gate (RV08). Replace the production correctness contract with CPU-reference-based evidence.

## Steps



## Detailed Solution & Technical Design

CONTRACT (GPT-adjudicated in RV49): CPU/reference correctness is the canonical production correctness oracle; native-relative correctness is only a cheap tuner screening invariant. For a candidate to become dispatchable in replay, with R = CPU reference semantics used by test-backend-ops, N = native GPU result, C = candidate GPU result, T = upstream correctness threshold for that operation (5e-4 NMSE for the relevant MUL_MAT cases at b10362): require E_N = NMSE(R,N) <= T AND E_C = NMSE(R,C) <= E_N + 0.5 * (T - E_N). A candidate may consume at most half of native's remaining CPU-reference NMSE budget; if native itself fails, the signature produces no non-native winner; a more-accurate candidate naturally passes. 0.5 becomes a named/versioned correctness_headroom_fraction (default 0.5) recorded in evidence - deliberately stricter than E_C <= T because sitting on the project cliff edge is exactly what failed intermittently on q4_1 k=32 (RV08). Use the WORST result across >=3 deterministic input seeds, not an average; the evidence records the seeds (upstream test init itself uses random inputs, so marginal implementations can cross the boundary between invocations). max_abs_error = 1e-2 is replaced for reference-grade evidence by max_abs(C,R) <= max_abs(N,R) across the same trials - deliberately conservative, no new fixed absolute tolerance; record full distributions and relax only with evidence. The existing 1e-6 candidate-vs-native check stays as an additional local screening check but is renamed/described accurately as delta_nmse_vs_native - it is NOT production correctness evidence.

VERIFIED PYTHON LEAK (must change with the C++ semantics, or F1 is not closed): autotune_catalog.py read_correctness_evidence() currently builds production evidence from native-relative metrics and hardcodes tolerances {nmse: 1e-6, max_abs: 1e-2} (line ~651), and production manifest generation (line ~775) accepts it. It must stop treating ordinary tuner-native deltas as production proof.

MODE CONSEQUENCE: until reference-grade correctness exists, tune mode = measure/select/record with ACTUAL WORKLOAD DISPATCH REMAINING NATIVE. Today tune installs the candidate returned by ggml_hip_tuner_resolve() into the normal dispatch binding so subsequent execution uses it - that must stop. Replay = execute only externally validated/promoted winners (already true). Promotion pipeline requires CPU-reference evidence keyed by at least source/manifest + architecture + signature + candidate.

## Validation

Contract tests: a candidate within 1e-6 of native but pushing E_C past E_N + 0.5*(T-E_N) is rejected; a more-accurate-than-native candidate passes; a signature whose native fails E_N <= T yields no non-native winner; evidence records the deterministic seeds and the headroom fraction name/version; tune mode leaves the real workload dispatch on native (verified by an actual run where a faster candidate is selected but the binding stays native); replay refuses a winner lacking CPU-reference evidence keyed correctly; read_correctness_evidence() rejects legacy native-delta evidence as production proof; marginal q4_1 k=32 RDNA2 case no longer intermittently trips the 5e-4 gate on repeated sweeps.
