# Replay benchmarks must prove tuned kernels actually launched, not merely that a cache loaded

## Description

Every replay benchmark run to date is uninterpretable: arms were torn down with kill -9, which destroys the shutdown-emitted replay report, so there is no evidence the cache ever resolved a lookup. 'The winners are neutral' and 'the cache never hit' are the same data.

dev-gpt-agent (req_6075d7c2055c4aa2) makes a sharper point that survives even after the teardown fix: EXACT > 0 is NOT sufficient evidence that a tuned kernel ran. The resolver revalidates a cached candidate after an exact hit -- can_execute, blacklist, transform applicability -- and can replace the binding with native. So a run can report exact hits and still launch native for every one of them.

The counter that actually answers the question does not exist yet: a count incremented at the real executor/launch point, AFTER final validation, keyed by stable candidate+variant.

## Steps

1. Add final_tuned_launches, incremented at the launch point after all revalidation, keyed by stable candidate name + variant.
2. Add per-winner launch counts.
3. Add fallback_after_exact -- exact hits that were subsequently replaced by native. This is the number that makes an exact-hit count trustworthy or exposes it as hollow.
4. Emit the full evidence set into the benchmark artifact, not only a log line: cache_entries_loaded, eligible_dispatches, exact_replay_resolutions, final_tuned_bindings, final_tuned_launches, fallback_after_exact, miss/unavailable/incompatible, per-winner launches.
5. Enforce the invariant in analysis: loaded > 0, exact > 0, final_tuned_launches > 0, sum(per_winner_launches) == final_tuned_launches, fallback_after_exact reported. Any violation invalidates the run.
6. Compute the predicted E2E gain and compare it to the measured one (see HI161's arithmetic note).

## Detailed Solution & Technical Design

gpt's decision rule for the neutral result, once tuned launches are proven:

  predicted_E2E_gain = SUM over winning signatures of
      (native_time_per_signature * real_launch_count * kernel_time_reduction)
      / decode_wall_time

where kernel_time_reduction = g/(1+g) for a throughput speedup g. For the measured winners that is: 6.05%->5.70%, 9.80%->8.93%, 12.74%->11.30%, 18.28%->15.45%, 22.89%->18.63%.

The corresponding maximum share of decode wall time consistent with <0.2% E2E movement is 3.51%, 2.24%, 1.77%, 1.29%, 1.07% respectively. So neutral is entirely plausible if the 19 winning signatures collectively occupy only ~1-3% of decode critical path.

If predicted < 0.2%: the kernel gains are real and E2E-irrelevant, and microbenchmark-driven promotion is measuring something that cannot move the metric we care about.
If predicted > 0.5-1% and replay still measures ~0%: the microbench gain is not reproducing on the real critical path, or is being offset by graph-level effects.

Do NOT infer from 'MMVQ is the decode family' that these 19 signatures dominate decode. That inference is the error to avoid.
