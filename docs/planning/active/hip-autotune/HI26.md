# Q8_1 activation reuse, K-tile tuning, and fused gate+up prefill for gfx1100 dense models

## Description

The public evidence shows three genuinely novel projects that together could compound:

1. **Q8_1 activation reuse across prefill graph nodes** — mainline llama.cpp quantizes the same F32 activation independently inside each MMQ call (gate, up, down). hipEngine demonstrated Q8_0 prefill fusion but not via llama.cpp's integer-MMQ path, and mainline gate/up fusion is restricted to N=1 (decode only).

2. **K-tile / barrier-schedule tuning** — the existing RDNA3 MMQ uses two K=128 halves within a K=256 iteration inherited across shape regimes, not selected per signature. No public RDNA3 experiment has systematically compared K tile 128 vs 256 vs 384 vs 512 for Q8_0/Q8_1.

3. **Fused gate+up prefill via integer-MMQ** — hipEngine implemented fused gate+up with FP16 WMMA (dequantizes to FP16 fragments), not the integer-MMQ path. Mainline llama.cpp fusion is decode-only (N=1). A fused integer-MMQ gate+up for N=512 prefill is genuinely unexplored.

These compound: activation reuse avoids quantization overhead, K-tile tuning reduces barrier stalls, and fused gate+up eliminates a second activation traversal entirely.

## Steps

- Phase 0: Instrumentation — Q8_1 quantisation launch counters, source tensor identity tracing, MMQ consumer grouping report, weighted timing by graph node
- Phase 1: Prepacked native entry point — refactor ggml_cuda_mul_mat_q into inline quantisation wrapper + prepacked MMQ executor
- Phase 2: Execution-scoped pack planner — compatibility key, graph grouping, arena lifetime, prepare-before-first-consumer, release-after-last-consumer
- Phase 3: gfx1100 exact native clones — K5120/N512 J48/J64/J128 and K3072/N512 J64, separate translation unit, same LDS layout, same WMMA calls
- Phase 4: Low-risk configuration variants — occupancy 1, alternative I, alternative thread count, full-tile compile-time paths
- Phase 5: LDS variants — full K=256 activation staging, double buffering, K=384/K=512 where applicable, each independently measured
- Phase 6: Optional fused gate/up prefill — after shared packing and specialised MMQ are stable, multi-output candidate behind tuner
- Phase 7: Split/reduce optimisation — profile separately: compute, copy, RCCL, internal reduction, stream waits, host staging

Complexity: Medium for Approach A (cache), High for Approaches B/C (graph fusion, GGUF changes).

Key risks:

2. Memory pressure — Q8_1 buffers are ~2.8 MiB for the hot signature. A cache of 4-8 entries is ~22 MiB, which is manageable but needs monitoring.
3. Graph restructuring (Approach B/C) changes the dispatch path and could interact with the tuner's measurement infrastructure.

### Eligibility Check
```cpp
bool is_reusable_mmq_node(const ggml_tensor * node) {
    return node->op == GGML_OP_MUL_MAT
        && node->src[0]->type == GGML_TYPE_Q8_0
        && node->src[1]->type == GGML_TYPE_F32
        && node->type         == GGML_TYPE_F32
        && node->src[1]->ne[1] > 1  // prefill, not decode
        && !node_has_ids(node)
        && !has_broadcast(node)

}
```

### Grouping
Group eligible nodes by `mmq_pack_key`. Groups with only one consumer use existing inline quantisation.

## Component 2: Reusable Q8_1 Pack

### Allocation
```cpp
size_t calculate_q8_1_pack_bytes(const mmq_pack_key & key) {
    const size_t matrix_bytes =
        key.ne13 * key.ne12 * key.ne11 * key.ne10_padded
        * sizeof(block_q8_1_mmq) / QK8_1_MMQ;
    const size_t guard_bytes = key.j_max * sizeof(block_q8_1_mmq);
    return align_up(matrix_bytes + guard_bytes, 256);
}
```
For K=5120, N=512: approximately 2.8 MiB.

### Lifetime
Buffer begins before first consumer, ends after last consumer. Arena reuses memory after final consumer.

### Baseline Kernel
Retains current kernel's functions where possible:
- Same LDS layout (Q8_0 weight tile + Q8_1 activation tile)
- Same WMMA calls (__builtin_amdgcn_wmma_i32_16x16x16_iu8_w32)
- Same accumulator mapping and writeback
- Hardcoded K, N; M can remain runtime-defined (multiple of TILE_M)

### Kernel Variants (Each Isolated as Distinct Candidate)

**Occupancy variant**: __launch_bounds__(256, 2) vs __launch_bounds__(256, 1). No other code changes.

**Full K=256 activation staging**: load full B tile, one barrier per K tile instead of two halves with four barriers.

**Double-buffered LDS**: prefetch next B tile while computing current. Based on rocWMMA perf_i8gemm pattern.

**K-tile candidates**: TILE_K=128/256/384/512 as separate compile-time candidates. Not runtime-variable inside one kernel.

### Eligibility

## Project 1: Q8_1 Activation Reuse Across Prefill Graph Nodes

### The Problem
Current `ggml_cuda_mul_mat_q()` does this for every individual MMQ operation:
```
allocate src1_q8_1
quantize_mmq_q8_1_cuda(src1, src1_q8_1)
launch MMQ operation
release temporary storage
```

The quantization and allocation occur inside `ggml_cuda_mul_mat_q()`, so separate graph nodes consuming the same F32 source (e.g., gate and up both reading the same hidden state) do not share the packed activation.

Existing deduplication only covers one case:
```cpp
const bool dedup_bcast = ne11 == 1 && n_expert_used > 1;
```
This quantizes a broadcast activation once within a single MoE MUL_MAT_ID and scatters to expert slots. It does not cache Q8_1 across distinct gate, up, QKV or other matmul nodes.

### For Qwen3.5/3.6 Dense Models
The current model loader defines separate:
```
ffn_gate  [K=5120, M=6144]  Q8_0
ffn_up    [K=5120, M=6144]  Q8_0
ffn_down  [K=1536, M=5120]  Q8_0
```
So the same F32 activation [N=512, K=5120] is quantized to Q8_1 twice — once for gate, once for up.

### What to Avoid (One Time)
- A second activation quantization kernel launch
- A second temporary allocation (~2.8 MiB for Q8_1 [K=5120, N=512])
- Repeated reading of the F32 activation from VRAM
- Launch overhead (two separate MMQ dispatches)
- Potentially repeated activation LDS staging if the same K tile is loaded twice

### Implementation: Graph-Scoped Q8_1 Cache

**Approach A: Backend-level activation cache**
Add a small LRU or generation-scoped cache to the CUDA backend that stores recently quantized Q8_1 activations. When `ggml_cuda_mul_mat_q()` needs src1_q8_1, it checks the cache first:
```
hash = (src1_device_ptr, src1_ne0, src1_ne1, src1_ne2, src1_ne3)
cached = q8_1_cache.lookup(hash)
if cached.valid and cached.generation == current_graph_generation:
    use cached.buffer
else:
    allocate, quantize, cache.insert(hash -> buffer)
```
The cache is invalidated at the start of each graph evaluation (generation counter increment) since activations change between forward passes.

**Approach B: Graph-scoped fusion pass**
Before building the computation graph, identify adjacent MUL_MAT nodes sharing the same src1 and fuse them into a single operation that quantizes once and dispatches twice. This is more invasive but avoids cache misses entirely.

**Approach C: GGUF-level physical fusion**
Store gate+up weights as a physically fused tensor [K=5120, M_gate+M_up] and dispatch a single MMQ call that writes to a concatenated output buffer. This requires changes to the model loader and GGUF format.

Approach A is the lowest-risk starting point — it requires no graph restructuring and works with the existing dispatch infrastructure.

### Validation
- Count Q8_1 quantization kernel launches before/after (should be roughly halved for dense gate+up pairs)
- Measure total quantization time saved (quantize_mmq_q8_1_cuda is fast but not free)
- End-to-end prefill time with replay cache
- Memory allocation count reduction
- Correctness: identical output to unoptimized path

## Project 2: K-Tile and Barrier-Schedule Tuning for gfx1100

### The Problem
The existing RDNA3 MMQ uses two K=128 activation halves within a K=256 iteration. That design is inherited across shape regimes rather than selected per complete signature. No public experiment has systematically compared K tile 128 vs 256 vs 384 vs 512 for Q8_0/Q8_1.

### Why It Matters for Our Signatures
For K=5120:
- K tile 128: 40 K tiles, 8 barriers per tile (A + B0 + B1 + compute each) = 320 barriers
- K tile 256: 20 K tiles, 4 barriers per tile = 80 barriers (current)
- K tile 384: 14 K tiles + tail, 4 barriers per tile = ~56 barriers
- K tile 512: 10 K tiles, 4 barriers per tile = 40 barriers

For K=3072:
- K tile 256: 12 K tiles, 48 barriers
- K tile 512: 6 K tiles + tail, ~24 barriers

Each barrier costs approximately 200-400 ns on gfx1100 depending on occupancy. Reducing barriers from 80 to 40 saves ~8-16 ms for the K=5120 signature alone.

### Constraints
The K tile must fit within LDS:
```
A tile: I * sram_stride * sizeof(int)
B half-tile: J * padded_q8_1_row * sizeof(int) / 2
metadata: J * sizeof(float)
```
With I=128, J=128, the current ~57 KiB per block fits two blocks under 128 KiB. Doubling K to 512 requires staging both halves simultaneously — which is exactly what HI25's Phase 4 does for the exact-shape kernel.

### Implementation
For the generic MMQ path, this means:
1. Add K-tile as a candidate variant (similar to J already being a variant)
2. Generate candidates for K tile 128, 256, 384, 512 on gfx1100 Q8_0
3. Let the tuner measure which fits and wins per signature
4. For K > 256, the kernel must stage both halves simultaneously (HI25 Phase 4)

### Validation
- Each K tile must fit within LDS (compile-time check)
- Bit-identical output to current K=256 path
- Barrier count reduction measured via rocprofv3
- End-to-end prefill improvement ≥2% to justify the complexity

## Project 3: Fused Gate+Up Prefill via Integer-MMQ (Genuinely Novel)

### The Gap
Mainline llama.cpp PR #16715 merged GEMV fusion for decode but intentionally restricted to `ncols_dst == 1` due to binary-size, compilation and register-pressure concerns. hipEngine implemented fused gate+up prefill with FP16 WMMA (dequantizes Q8_0 weights into FP16 fragments). Neither covers the integer-MMQ path for N=512 prefill.

### The Opportunity
For dense models:
```
gate:  [K=5120, M=6144] × [K=5120, N=512] → [M=6144, N=512]
silogm: elementwise
down:  [K=5120, M=1536] × [K=5120, N=512] → [M=1536, N=512]
```
Gate and up read the same F32 activation [N=512, K=5120]. A fused kernel that quantizes once and dispatches both would save:
- One Q8_1 quantization (~2.8 MiB activation)
- One temporary allocation
- One MMQ kernel launch
- Potentially one activation LDS staging sequence if the same K tiles are loaded twice

### Implementation: Dual-Weight Integer-MMQ Kernel

Build a kernel that takes two weight tensors and one activation:
1. Quantize activation once to Q8_1
2. For each K tile, load B (shared) into LDS once
3. Load A_gate or A_up from their respective global addresses
4. Issue WMMA for the current weight tensor
5. Accumulate into the appropriate output buffer

This preserves the integer-MMQ path — no FP16 dequantization — while sharing the activation quantization and LDS staging.

### Key Design Decisions
- **Same or different K tiles?** Gate and up have the same K=5120, so the same K tile schedule applies to both. This means B (activation) can be staged once per K tile and reused for both gate and up WMMA operations.
- **Output accumulation:** Gate output goes to buffer 0, up output goes to buffer 1. The kernel writes two separate F32 outputs without interference because the M dimensions differ (6144 vs 6144, but different output buffers).
- **Activation reuse:** B is loaded from LDS once per K tile, then used for both gate and up WMMA calls. This is the biggest saving — activation LDS staging is roughly half the LDS budget.

### Validation
- Bit-identical output to separate gate+up MMQ calls
- One Q8_1 quantization instead of two (verified by kernel launch count)
- One B LDS staging per K tile instead of two
- End-to-end prefill improvement ≥2% to justify the complexity
