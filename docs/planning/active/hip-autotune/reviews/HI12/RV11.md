# Aggregate matmul saving is 7.6%, and the benchmark noise floor is three times larger

## Notes

Computed from /tmp/tune-mtp-server.jsonl.measurements.jsonl on brutus. The native baseline per signature is the fastest `*:native:*` candidate with status ok in that signature's own measurement set, so the comparison is against what upstream would have run on that exact shape rather than against a global default.

## Findings

Answers the question RV09 left open: the tuned build showed no end-to-end throughput change despite RV10 measuring 14–20% improvements on individual signatures. Computed from the real MTP tuning run's measurements (95 signatures), comparing each winner's median against the best native candidate for the same signature.

| Family | Signatures | Native µs | Tuned µs | Saved |
| --- | --- | --- | --- | --- |
| mmvq | 58 | 5773.8 | 5238.1 | **9.3%** |
| mmq | 11 | 4058.1 | 3824.1 | 5.8% |
| mmvf | 5 | 56.1 | 54.4 | 3.0% |
| blas | 21 | 350.6 | 348.8 | 0.5% |
| **total** | **95** | **10238.6** | **9465.4** | **7.6%** |

**The 14–20% figures are the top winners, not the aggregate.** Those are a minority of signatures; averaged across everything actually dispatched the saving is 7.6%.

Weighting by real execution counts changes almost nothing. The replay run's coverage gives mmvq 12246 dispatches, mmq 3612, blas 172, mmvf 52. Combining each family's mean per-call cost (mmvq 99.5 µs, mmq 369 µs, blas 16.7 µs, mmvf 11.2 µs) with its saving gives **~7.5% weighted**, because mmq's high per-call cost and smaller saving offsets mmvq's larger one. Assumes executions distribute evenly across a family's signatures, which is approximate but adequate at this precision.

**Why nothing showed end to end.** Three multiplications, each shrinking the effect:

1. Matmul time falls by ~7.5%, not 14–20%.
2. Matmul is only a fraction of decode wall time. If it is roughly half, the end-to-end effect is ~3–4%.
3. **The benchmark's own noise is ±10%** — tg128 measured 67.99 ± 6.92 native and 65.69 ± 7.74 replayed. The expected effect is about a third of one standard deviation.

So the null result is exactly what this measurement setup would produce whether the gain existed or not. It is not evidence the tuning does nothing, and it is not evidence it works either. The benchmark as run cannot answer the question.

## Conclusion

The per-signature measurements in RV10 stand. The end-to-end claim remains unproven in both directions, and the reason is now quantified rather than speculated.

To actually resolve it:

1. **Measure matmul time directly, not tokens per second.** A ~7.5% change in a component is straightforward to observe with the tuner's own timing harness and impossible to observe through a ±10% end-to-end benchmark. The measurements JSONL already contains everything needed.
2. **If an end-to-end number is wanted, budget for the noise.** Resolving a 3% effect against ±10% spread needs on the order of 50+ repetitions, not the 5 the harness defaults to. Worth deciding whether that is a good use of GPU time before running it.
3. **Establish what fraction of decode time is matmul at all.** Nothing in this project has measured it, and it is the multiplier that determines whether any of this work can matter. If attention or sampling dominates at 16k context, a matmul win is capped regardless of how good the kernels get.
4. **BLAS is worth 0.5% across 21 signatures.** Forced BLAS wins often (RV07 counted 24 wins on RDNA3) but the wins are tiny. This weakens the case for HI17's decomposition work relative to how the win *count* made it look — a reminder that counting wins and measuring value are different things.

The honest summary for anyone reading the plan: the dispatch layer demonstrably picks faster kernels, the aggregate effect on matmul is single-digit percent, and whether that reaches the user has not been measured.
