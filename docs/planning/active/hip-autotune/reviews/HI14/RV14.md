# Multi-GPU and graph-capture validation: most of the matrix passes; mixed-architecture tensor split is an upstream limitation

## Notes

Mixed-topology logs on brutus: /tmp/mix.log (replay, segfault) and /tmp/mixnat.log (native, identical segfault). Reproduce with `-dev ROCm0,ROCm2 -sm tensor -ts 1,1`.

## Findings

Working through HI14's validation matrix with the evidence gathered across this session, plus the two gaps that had not been attempted.

**Passing, measured 2026-08-05:**

| Row | Result |
| --- | --- |
| Single XTX (gfx1100) | full `MUL_MAT` sweep, 1155 signatures, 0 failures; plus the real MTP workload |
| Single R9700 (gfx1201) | full sweep, 1157 signatures, 0 failures, no aborts |
| gfx1030 (RDNA2) | full sweep, 0 failures (not in the original matrix; the catalog supports it and nothing had ever run on it) |
| Multiple XTX, tensor split | real MTP workload, `-sm tensor -ts 1,1`, replay 17500/17500 dispatched, 0 misses |
| **HIP graphs enabled** | every replay run had graphs on — no `GGML_CUDA_DISABLE_GRAPHS` — and reported 100% dispatched, so **nothing bypasses the dispatch layer under capture** |
| MTP widths from inventory | widths 1,2,4,5,6,8,10,12,16 observed and tuned |
| pp512 / tg128 | run throughout |

**Mixed XTX + R9700 tensor split segfaults, and it is not ours.** `-dev ROCm0,ROCm2 -sm tensor` crashes during model load. Attributed by the same method that corrected RV08: **native mode segfaults identically**. No bigcherry frame appears in either trace, and the dispatch layer is not reached — the crash is in model loading, before any matmul. Also visible on that path: `internal AllReduce init failed (n_devices != 2?); falling back to meta-backend butterfly`, and the earlier `llama_params_fit is not implemented for SPLIT_MODE_TENSOR`.

So mixed-architecture tensor split is an upstream limitation. Worth knowing because HI14 lists it as a row to validate and it cannot be validated until upstream supports it.

**Hardware separation is correct by construction.** `ggml_hip_make_hardware_key(ctx.device)` builds the key from the *context's* device, and the key includes `architecture_code` and `compute_units`. So heterogeneous devices produce distinct keys and cannot share winners. This is what would have made the mixed run interesting — the XTX half hitting the cache and the R9700 half missing would have been the correct outcome — and it remains unexercised.

**One real defect found and fixed.** `GGML_HIP_DISPATCH_MODE=native` was not accepted by `ggml_hip_parse_mode`, which warned "unknown GGML_HIP_DISPATCH_MODE=native; using native" and fell through. Harmless in effect, since the fallback is native either way, but it teaches anyone reading the log to distrust the mode they asked for, and it makes a deliberate native baseline look like a typo. Baselines are not incidental here: comparing against native is exactly how RV08 was correctly re-attributed and how this segfault was pinned on upstream. Fixed and verified: zero unknown-mode warnings.

## Conclusion

HI14 is substantially satisfied for the topologies that work. Remaining, in rough order of value:

1. **Long-context server workload** — the largest untested row and the one closest to production. Everything so far ran at `-c 8192` or `-c 16384` against a target of 245,760. Hot-signature ranking at 200k will not resemble what has been measured, and the attention shapes that dominate late in a sequence are entirely unrepresented.
2. **pp256 / pp1024 / pp4096 and tg512** — cheap to add to an existing bench invocation.
3. **Mixed XTX/R9700** — blocked upstream. Recheck after a `bigcherry pull`; it needs no work on our side, and hardware separation is already correct by construction.
4. **RCCL and the production PCIe topology** — untouched. Note the mixed run fell back to "meta-backend butterfly" for AllReduce, so the RCCL path has not been exercised by anything in this session.

Also still open from RV05 and unchanged by this: tuning is *skipped* under graph capture, so a signature first seen inside a captured graph is never measured. Replay is unaffected — it looks up rather than measures, which is why the graph rows above pass — but a tuning run should keep using `GGML_CUDA_DISABLE_GRAPHS=1` until that is closed.
