# OPEN, correctness: tuner intermittently selects a candidate that fails the project's own error threshold

## Notes

Logs on brutus, preserved under artifacts/tuning-logs/: gfx1030-rdna2-s1f1.log (the failing run), gfx1030-rdna2-native.log (passes), gfx1030-rdna2-s1f1-nograph.log (passes). Repeats at /tmp/rv08-rep1.log and /tmp/rv08-rep2.log, both passing, and /tmp/tune-gfx1030-s3f15.log at 3/15, passing.

Reproduce with ~/bc-build-multi/bin, HIP_VISIBLE_DEVICES=3. Expect to need several attempts.

## Findings

**Corrected 2026-08-05. The first version of this review blamed HIP graph capture. That was wrong, and the error is instructive enough to leave on the record.**

Found on gfx1030 (RDNA2), the first time anything ran on that card. A full `test-backend-ops -o MUL_MAT` sweep under `GGML_HIP_DISPATCH_MODE=tune` failed one case:

```
[MUL_MAT] ERR = 0.000520917 > 0.000500000
  MUL_MAT(type_a=q4_1,type_b=f32,m=16,n=1,k=32,bs=[1,1],nr=[1,1],per=[0,1,2,3],k_v=0,o=1): FAIL
```

4% over the threshold, while native mode on the same card passed cleanly.

The full evidence, gathered in the order taken:

| Run | Samples | Graphs | Result |
| --- | --- | --- | --- |
| native | -- | on | PASS |
| tune | 1/1 | on | **FAIL** |
| tune | 1/1 | **off** | PASS |
| tune | 3/15 | on | PASS |
| tune | 1/1 | on (repeat 1) | PASS |
| tune | 1/1 | on (repeat 2) | PASS |

**The failure is intermittent.** Two repeats of the exact configuration that failed both passed. It is not a graph bug: disabling graphs was one run against one run, and I read a difference between two single-sample runs as signal when single-sample winner selection is noisy — the precise caution I had written into `CANDIDATES.md` an hour earlier and then failed to apply to my own experiment.

**What it actually is.** The tuner accepts a candidate by comparing it against *native* with `max_nmse = 1e-6` (and `max_abs_error = 1e-2`). `test-backend-ops` compares the GPU result against a *CPU reference* at 5e-4. Those are different measurements against different baselines. A candidate can sit comfortably within 1e-6 of native and still push the total deviation from the CPU reference past 5e-4, whenever native is itself already close to that threshold — which for `q4_1` at `k=32` it evidently is.

At one sample per candidate the winner for a marginal signature varies run to run, so whether a run trips the threshold is luck. That is why it is intermittent, and why more samples made it disappear: better sampling picks the genuinely faster candidate more consistently, and here that happened to be an accurate one.

**Why this matters more than a flaky test.** The tuner's acceptance criterion does not bound end-to-end error. It bounds *divergence from native*, which is not the same thing and does not compose. A tuning run can therefore produce a winner set that fails the project's own correctness gate, intermittently, with nothing in the tuner reporting a problem — every candidate it accepted was within its stated tolerance.

RDNA2 exposed it first, but nothing about the mechanism is RDNA2-specific. It needs a signature where native already sits near the tolerance, which is a property of the shape and quantisation, not the architecture.

## Conclusion

Not fixed. This is a design question about what the tuner's correctness contract should be.

1. **Decide what the tolerance is protecting.** Comparing against native answers "is this candidate equivalent to what upstream would have done", which is the right question for *attribution* but the wrong one for *correctness*. If the guarantee is meant to be "a tuned build is as correct as an untuned one", the check has to bound error against the same reference the project's correctness gate uses, or be tight enough that composition cannot exceed it.
2. **Consider a headroom rule instead of a fixed epsilon.** Reject a candidate whose deviation is large relative to native's own remaining margin, rather than against a flat 1e-6. That directly targets the marginal-signature case.
3. **`max_abs_error = 1e-2` deserves separate scrutiny.** It is not what failed here, but it is permissive for small-magnitude outputs and nothing in this session exercised it.
4. **Do not tune at one sample.** Beyond the noise in winner selection, it makes this failure mode reachable. RV07 already established 1/1 runs cannot support timing claims; this adds a correctness reason.
5. Re-run the RDNA2 sweep several times at 1/1 to estimate how often it trips, before deciding how urgent this is.

The graph-capture question raised in the first version of this review is *not* answered and should not be considered closed — it simply has no evidence behind it. RV05's separate finding stands: tuning is skipped under capture, so signatures first seen inside a captured graph go unmeasured. That remains a coverage gap worth closing under HI14.
