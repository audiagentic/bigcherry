# replay-slim implemented, but the manifest hash is in the lookup key so every winner is orphaned

## Notes

Reproduce:

```bash
python3 -m bigcherry generate --variant-set replay-slim \
  --inventory artifacts/mtp-inventory.json \
  --winners <db>.measurements.jsonl
python3 -m bigcherry.replay_cache <db>.measurements.jsonl \
  --manifest artifacts/<rev>/hip-autotune-manifest.json --output dispatch-slim.cache
cmake -B build-slim -DGGML_HIP_DISPATCH_REPLAY=ON \
  -DGGML_HIP_AUTOTUNE_VARIANT_SET=replay-slim -DGGML_HIP_AUTOTUNE_SIGNATURE_FILE=…
```

Note CMake does not invoke the generator — it requires the registry to be in the tree already and fails configure if it is not — so the generate step must come first and the two must agree on the variant set.

## Findings

`replay-slim` and `replay-full` had been declared in `VARIANT_SETS` since the schema was written and implemented nowhere; `build_manifest` handled only `inventory`, `workload-max` and `full-max`. Slimming a production build down to the variants a tuning run actually chose was the last structurally missing piece of the production path.

Implemented in `autotune_catalog.py`: `read_winners()` parses the same measurements JSONL the replay-cache writer reads, so a slim build and the cache it loads derive from one set of measurements rather than two readings of it. `build_manifest` gained a `winners` parameter and filters the enumerated catalog to those names. `--winners` is wired through both the standalone parser and the `bigcherry generate` subcommand.

**Native wrappers always survive the filter**, and that is correctness rather than caution: a replay miss falls back to native (standards 9.2), so a build without them has nothing to serve a signature the cache does not cover, and `validate_manifest` rejects a family that has candidates but no `native_wrapper`. A winner naming a candidate absent from the generated catalog is a hard error, not a skip — it means the measurements came from a different inventory or architecture set.

Result on the real MTP winners: **270 candidates to 50** (37 mmvq, 6 mmq, 4 mmvf, 2 blas, 1 mmf), an 81% reduction. 45 winning variants plus the 5 native wrappers.

**The manifest-hash coupling question is answered, and it needs no format change.** The loader rejects a cache whose manifest hash differs from the build's, and a slim build necessarily has a different manifest from the tuning build (`3126b3aa` against `d64e79c8`). The order that works is: generate slim first, then export the cache against the *slim* manifest. The writer's existing "refuse if a winner is absent from the manifest" check is what makes this safe — it is precisely the guarantee that slimming dropped nothing the cache needs. Verified: all 95 winners resolved against the slim manifest and the cache stamped `3126b3aa`.

**The stated rationale for slimming does not survive measurement.** `libggml-hip.so` is **67 MiB slim against 68 MiB full** for the same single architecture — about 1.5%. The library is dominated by upstream's own kernel instantiations across every type and op; the generated MMVQ variants are a small slice of it. (The 164 MiB `bc-build-multi` is three architectures and not a comparison.) If `replay-slim` is to be justified it has to be on compile time, or on not shipping unmeasured code into production, not on binary size.

## Conclusion

**Corrected 2026-08-05. The first version of this review claimed the manifest-hash coupling was "answered and needs no format change". That was wrong, and it was wrong in a way that would have shipped a production build silently running untuned.**

What is implemented and does work: winner filtering (270 candidates to 50), native wrappers surviving the filter, the hard error on a winner absent from the catalog, cache export stamping the slim manifest hash, and compilation.

**What does not work: the cache is unusable in a slim build.** `ggml_hip_dispatch_digest` (hip-autotune-signature.cpp:165) builds the lookup key from hardware digest, signature digest, objective, **manifest hash** and **source revision**. Slimming changes the candidate set, so the manifest hash changes, so **every key changes**. Not one of the 95 winners can be looked up.

Measured on the real MTP workload, both runs on the same free XTXs:

| Build | Manifest | Dispatched | Misses |
| --- | --- | --- | --- |
| full replay (`workload-max`) | `d64e79c8` = tuning | 25244/25244 | **0** |
| slim replay (`replay-slim`) | `3126b3aa` ≠ tuning | 14476/14476 | **81** |

The 81 missed digests are **entirely disjoint** from the 95 tuned digests — zero overlap — which is the signature of a changed key rather than a changed workload.

**It fails silently, and that is the worst part.** The cache header carries its own manifest hash, I stamped the slim one, so the header check passes and the loader reports "95 winner(s) loaded". Every lookup then misses and falls back to native. Nothing distinguishes "cache orphaned" from "workload has new signatures". A production deployment would look correct, log nothing unusual, and be entirely untuned.

**A second correction, on how the earlier result was verified.** RV09 reported the full replay chain at "100% coverage, zero misses". The coverage figure was real; **the zero-misses figure was not evidence of anything** — `ggml_hip_replay_record_miss` returns early unless `GGML_HIP_DISPATCH_MISS=native-record`, which that run did not set. Misses were simply not being recorded. Re-run since with recording enabled: the matching-manifest build genuinely has **zero misses across 25244 dispatches**, so the conclusion survives, but it had not actually been tested when it was claimed. Coverage counts dispatches through the layer; a miss is still a dispatch. The two numbers answer different questions and only one of them was being asked.

**The fix is a design change, recorded as HI23** — make the key portable (hardware, signature, objective) and carry manifest hash, source revision and a release generation as per-entry provenance, preferring an exact match and falling back to the newest with a staleness flag. That also fixes the larger problem this exposed: **every upstream bump currently discards all tuning**, silently, at a cost of roughly 20 minutes of exclusive GPU time per run.

Step 1 of HI23 is already done and is independently correct whichever way the design review goes: the tuner now emits `signature` and `hardware` digest hex alongside `dispatch` in each result record. Previously only the composite was recorded, so **no tool could compute any other key from a measurements file** — not a re-keyed cache, not a migration, not even an offline comparison of which signatures two runs share. Verified: builds clean, tests 12/12, audit 32/32.

The binary-size finding stands unchanged: 67 MiB slim against 68 MiB full, about 1.5%, so `replay-slim` must be justified on compile time or on not shipping unmeasured code.
