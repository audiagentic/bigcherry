# Steps 4 and 6 are mutually exclusive -- the L1-hit shadow assertion cannot produce evidence while the guard stays

## Notes



## Findings

Step 4 requires the `!native.valid` guard to stay above the L1 lookup. Step 6 requires a shadow assertion on the L1-hit path: `if (l1_hit) { auto shadow = native_select(...); assert(shadow.valid); }`, whose purpose is to gather empirical support for the claim that an L1 hit implies native validity.

These cannot both hold. With the guard in place, every dispatch with an invalid native selection has already returned before the L1 lookup is reached. So at the l1_found branch `native.valid` is unconditionally true, and `native_select` is a deterministic function of inputs that have not changed. The shadow recompute must therefore agree, always. The counter reports 'N checked, 0 invalid' regardless of whether the underlying claim is true or false.

That is worse than not having it: it looks like accumulated evidence, and the whole reason the guard move was deferred is that the original validity claim was asserted without proof and then corrected. Shipping a vacuous counter risks that same claim being re-accepted later on the strength of a number that could never have come out any other way.

Second, smaller finding: the entry point `ggml_hip_dispatch_try` has its OWN `if (!native.valid) return false;` before the signature is even built. HI158's design text discusses only the guard inside `ggml_hip_dispatch_resolve`. There are two guards, and BOTH must move for deferral to save anything. The item should name both.

## Conclusion

Implemented steps 1, 2, 3 and 5 (zero-allocation memoized provider, resolver takes the provider, force-once, per-site force counters) plus a pre-resolved provider form the family collection points need, since standards 11.1 forbids consulting native selection there. Deliberately did NOT implement step 6, and recorded why in the code at the point where it would have gone.

This leaves the patch perf-neutral by construction, which is the correct and intended outcome of keeping step 4 -- it lands the mechanism with no behavior change so the later guard move is a small, attributable diff. It must not be presented as a performance patch, and must not be gated on an end-to-end improvement it cannot produce.

To make step 6 real, the guard move needs to be reachable in a build: e.g. an explicit experiment mode that moves both guards and enables the shadow recompute, so the counter can actually observe a disagreement. Proposed as follow-up work, not as part of this item.
