## Findings

P0-1 per-row source-build proof incomplete: _require_row_belongs_to_build() only proves a measurement exists for (source_build_id, dispatch_digest, signature_digest) -- it does NOT prove the JSONL row's winner/native/hardware match what that build actually recorded. Concrete attack: DB row has winner=generated-X/native=native-X, edited artifact row claims winner=native-Y/native=native-Y (native-Y exists in both manifests) -- row-membership and candidate-equivalence both pass, and replay's promotion gate treats winner==native as safe, skipping non-native gates. Fix: bind every projected row against winner JOIN hardware JOIN signature JOIN candidate requiring exact build_id/dispatch/signature/hardware/winner stable_name/native stable_name (+ any trusted safety state); better: persist an ingest-time artifact digest binding the whole measurements artifact to its DB ingestion.

P0-2 --source-manifest is required but never verified as the actual source build's manifest: project_measurements() loads the JSON and builds source_candidates_by_name without first proving recomputed source manifest hash == source manifest.manifest_hash == DB build.manifest_hash, source_revision match, build_descriptor hash match, and producer_capabilities match against DB/header attestation. Fix: add _load_source_manifest() with the same fail-closed rigor as _load_target_capabilities(), bound to source_build_id and the current measurements header; no projection should read candidates until those proofs pass.

P0-3 candidate descriptor equality is not implementation equality (the deeper issue behind P0-2's check): descriptor fields (stable_name/family/source_class/implementation_version/architectures/config/graph_safe/deterministic) contain NO digest of actual kernel/dispatch implementation source -- implementation_version is manually maintained at 1. Two builds with byte-identical descriptors but genuinely different kernel source both pass source_candidate==target_candidate even though the target implementation was never measured. The existing cross-revision test only changes MARKER.txt and deliberately leaves candidate semantics unchanged, so it never exercises this. Needs a real candidate implementation identity -- a source/implementation digest mechanically tied to the actual code, not a manually-bumped :v1 label. Reviewer calls this 'the largest design checkpoint.'

P0-4 canonical signature digest -> canonical content still unproven (NOT actually closed despite round-3's repeat-sighting check): inventory now detects a digest later reappearing with a DIFFERENT canonical JSON (useful corruption detection), but the FIRST stored canonical for a digest is still accepted on faith -- no proof the real C++ signature hash actually produces that digest. Tests still explicitly pair arbitrary '11'*16/'22'*16 digests with invented canonical dicts and accept them. A poisoned first record establishes digest D -> harmless-looking canonical C, and C becomes semantic authority for all future compatibility decisions built on it. Reviewer reaffirms not reimplementing the C++ canonical serializer in Python is correct; the real fix is a production C++ signature-digest helper/verifier that canonical JSON must be proven to hash to, before a row is marked verified/reusable.

P0-5 multi-generation non-native replay conflicts with the existing correctness resolver: schema 7 intentionally allows the same portable dispatch to have measurements across multiple builds (central to HI121), but promotion_gate.resolve_promotion_identity() does `SELECT DISTINCT build_id FROM measurement WHERE signature_id=? AND hardware_id=? AND dispatch_digest=?` and requires exactly one result -- once two builds (A, B) both have D/S/H measurements, correctness-gate export refuses with ambiguity, even though the projected header already carries the missing authority in hi121_source_provenance.source_build_id. replay's correctness resolver doesn't consume it. Fix: projected artifacts should pass their explicit verified source_build_id into correctness binding; non-projected measurements keep today's unique-resolution behavior. Test scenario given: build A and B share D/S/H, project A->C, non-native promoted winner on A, valid RV49 evidence for A, replay.build(dispatch_db=multi-build DB) must resolve A explicitly rather than report ambiguity.

P1-1 build descriptor provenance still nullable/weaker than HI121 needs: descriptor mismatch is only rejected when BOTH stored DB descriptor and incoming descriptor are non-null; _load_source_capabilities() requires the artifact header descriptor but if the DB build's descriptor is NULL there's nothing to compare against. For an HI121-projectable build all three (DB build_descriptor_hash, header descriptor, source manifest recomputed descriptor) must exist and be exactly equal; old descriptor-less builds should be capability-unknown/not-projectable, not silently passed.

P1-2 manifest's embedded build_descriptor isn't independently recomputed: _verify_and_persist_hip_capabilities() checks header descriptor against manifest['build_descriptor']['descriptor_hash'] and independently recomputes manifest_hash, but manifest_hash() deliberately EXCLUDES build_descriptor -- so the descriptor object itself is never independently recomputed and cross-checked (catalog.build_descriptor(manifest_without_descriptor_authority) should be recomputed and exact-compared against the embedded descriptor). Otherwise the manifest is partially self-attesting.
