# Generate-stage manifest/source_revision provenance mismatch in campaign builds

## Description

A tune-lane campaign build's compiled binary embedded a candidate-catalog manifest whose recorded source_revision (4801e3c567d5131dd41b387df5f2d4b1370d92be, an old pin) did not match the git tree it was actually compiled from (6ea215d171fd / tag b10362, the current pin). Discovered on real Brutus hardware (2026-08-19) while trying to export a replay cache from a fresh tune run's promoted winners: `bigcherry.replay_cache` correctly refused with 'measurements producer source_revision does not match the supplied manifest's source_revision', and a manually-substituted older cached manifest (matching source_revision by search) then failed with 'winner ... is not in hip-autotune-manifest.json' (wrong candidate set entirely). This means the campaign build pipeline's `generate` step, at least via `legacy-build`, is not reliably regenerating the manifest fresh against the tree it is about to compile -- something is reusing or mislabeling a stale content-addressed cache entry from an earlier session's different pin.
