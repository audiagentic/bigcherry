# Stage advisories: surface prior findings at the moment a result appears

## Description

Over one session an agent independently rediscovered three things this repository already knew, each time after reporting a conclusion that had to be retracted:

1. HI130 records: 'Any FUTURE benchmark ... with speculative decoding MUST verify draft_acceptance is IDENTICAL across compared configs before trusting tg128/tg512 deltas -- this was the root cause of every false conclusion in this investigation.' A benchmark was run and reported without that check anyway, and the resulting 'winners regress tg512 by 9%' was in fact a change in work done (acceptance 0.94734 -> 0.86391, bit-identical across 16 cells).
2. `bigcherry ab-benchmark` already provides paired, interleaved A/B with build-composition verification via --stock-cmake-cache/--patched-cmake-cache. A worse harness was written from scratch in bash; its first result was retracted for an arm-order confound ab-benchmark already handles.
3. The behavioural corpus qwen38-production-v1 held a single vector at n_predict=128, so a gate built specifically to catch MTP acceptance regressions certified a cache that regressed acceptance at every longer generation length -- and 128 was the only metric that improved.

None of this was hidden. It was in plan items, module docstrings and a CLI that was not read. Knowledge only discoverable by already knowing where to look does not get looked at.

Implemented: tools/bigcherry/tuning/advisories.py, emitted at the end of tune-campaign.

## Steps

1. DONE: advisories.py plus wiring into cli/tuning.py's campaign result path.
2. Extend to the other stages where an agent forms a conclusion: build (what the lane does and does not contain), ab-benchmark (activation and work-equivalence preconditions), recovery, and patch promotion.
3. Add a test asserting each advisory fires on its condition and stays silent otherwise -- an advisory that fires unconditionally is the failure mode to guard against.
4. Consider a machine-readable form in the receipt alongside the human text, so a supervising agent can act on tags rather than parse prose.

## Detailed Solution & Technical Design

DESIGN CONSTRAINTS, each learned in the same session:

1. NOT the C++ runtime. llama-server installs a log callback that swallows the library's GGML_LOG_INFO lines entirely -- the dispatch counter reports were invisible for hours because of it, and were wrongly read as 'the dispatch layer never ran'. An advisory emitted from the dispatch layer would go nowhere.
2. Therefore the campaign tooling, which never ships. The owner's requirement that these be absent from production builds is then satisfied STRUCTURALLY rather than by a compile flag that could be got wrong -- a strictly stronger guarantee than #ifdef.
3. Conditional, never blanket. An advisory that always prints is banner text and banner text is not read. Each is gated on a condition actually present in the receipt, so seeing one means it applies to the run in front of you.
4. stderr, not stdout, and suppressed entirely under --json, so machine consumers are unaffected.
5. Best-effort: every input read is guarded. A campaign that has already spent real GPU hours must never fail at its last line because an advisory input was missing or malformed.

Advisories implemented, each firing on a real condition observed in campaign 27e45ae32ec4:

- activation-evidence: exact > 0 does NOT prove tuned kernels ran; the resolver revalidates cached candidates and can substitute native. Only final_tuned_launches > 0 is sufficient, and it needs a diagnostics-ON build plus the coverage JSON because the log channel is swallowed.
- mtp-acceptance: HI130's rule, with the concrete 0.94734 -> 0.86391 case.
- corpus-coverage: names the generation lengths the gate actually certified and states that anything else is uncertified.
- alternatives-exhausted: HTR04's rule that recovery failure != retune, with the full correct chain.
- untuned-families: names families executing real work with no tuned candidates, and points at kernel-fraction/impact to size them before optimising anything else.
- use-the-harness: ab-benchmark exists; do not write another one.
