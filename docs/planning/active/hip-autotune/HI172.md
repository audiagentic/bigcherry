# Critical-path/slack vs contention hypothesis for isolated-vs-e2e tuning divergence

## Description

HI171's real e2e matrix (2026-09-08, current source, all 5 HI168 caches) found that isolated per-dispatch-key tuner speedups (5.7%-35% across the five caches, all execution-audit-confirmed as genuinely launching from cache) do NOT reliably translate into real end-to-end serving performance on ANY topology tested: GPU0 shows a real regression (-1.3% pp512, -1.8% pp2048 replay vs native), GPU1 is mixed, GPU2/GPU3/27B are flat/no-measurable-effect despite real isolated wins.

HYPOTHESIS: the isolated per-dispatch tuner measurement and the aggregate e2e tokens/sec measurement are two ends of a spectrum that structurally cannot distinguish between three different causal explanations for this divergence:

1. DILUTION -- the isolated win is real, but the tuned dispatch is a small fraction of total GPU time in real serving (attention, KV-cache ops, other kernels dominate); a genuine 10% kernel-level win nets out to well under 1% overall, invisible against measurement noise. The isolated number never lied; it just never mattered much.

2. OFF-CRITICAL-PATH -- the kernel genuinely got faster, but it was never gating the next pipeline step in real serving (it overlaps with or is hidden behind other work), so shortening it doesn't shorten wall-clock at all. The isolated microbenchmark cannot see this because in isolation EVERYTHING is trivially on the critical path (it's the only thing running).

3. CONTENTION-DEPENDENT REGRESSION -- the kernel is only faster when it is the ONLY thing running on the GPU. In real serving it shares occupancy/register/shared-memory pressure with many concurrently-scheduled kernels, and its real per-invocation duration under that contention is actually WORSE than native's, even though the isolated, uncontended measurement was honest. This is the most concerning explanation, since it means the tuner's whole methodology (measure each dispatch alone, pick the fastest) is measuring the wrong thing entirely for a decode-heavy real workload.

A fourth, related possibility raised in conversation: the REVERSE of (3) -- a candidate that measures WORSE in isolation could in principle be BETTER in real serving if it exploits GPU slack differently (e.g. trades a bit of own-kernel latency for lower resource pressure that lets NEIGHBORING kernels run faster, netting positive on wall-clock even though its own isolated number looks like a loss). Today's per-dispatch-isolated-measurement tuning methodology is structurally blind to this class entirely -- it would never even be tried as a candidate, let alone promoted.

Why this matters beyond just explaining GPU0's regression: if (3)/(4) are real and general (not GPU0-specific), it implies BigCherry's entire tuning methodology -- optimize each dispatch independently via isolated microbenchmark, promote whichever measures fastest alone -- may be structurally the wrong approach for a decode-heavy real workload where many kernels are densely scheduled back-to-back. That is a much bigger finding than "GPU0's cache needs demotion" and would motivate a genuinely different tuning architecture (critical-path-aware, or real-trace-scored) rather than a lifecycle fix to one cache.

PROPOSED METHOD TO DISTINGUISH THESE: run rocprofv3 kernel tracing on real native and real replay llama-server processes (same production binaries already used for HI171's e2e comparison) serving the SAME workload, on GPU0 (cleanest real regression to explain). Use the EXISTING `bigcherry kernel-fraction` tool (tools/bigcherry/analysis/kernel_fraction.py, HI35 Part 2 -- already built, aggregates rocprofv3 kernel-trace CSVs by kernel family, reports both time-share and a wall-clock ceiling: "a 10% matmul saving is at most matmul_fraction x 10% end to end") to get:
(a) what fraction of total GPU time the tuned dispatch family actually occupies during real serving -- tests hypothesis 1 directly (if fraction is small, dilution alone explains the flat/no-effect results, though GPU0's finding is a REGRESSION not merely flat, which dilution alone does not explain -- a diluted-but-still-positive effect cannot become net negative from dilution alone, so GPU0 specifically needs hypothesis 2 or 3);
(b) real per-kernel duration native vs replay AS MEASURED IN THE ACTUAL PIPELINED CONTEXT (not the isolated tuner's number) -- tests hypothesis 3 directly: if the real in-context duration for replay's kernel is genuinely longer than native's despite the isolated tuner claiming replay is faster, that is direct proof of contention-dependent regression;
(c) kernel start/end timestamps reconstructed into a GPU-busy/idle timeline -- tests hypothesis 2 (critical-path membership) and reveals whether real slack exists in the request's critical path at all.

Also relevant: HI132 (pending, hip-autotune plan) already scopes 'bigcherry profile-campaign: rocprofv3-based repeatable GPU/runtime deep-profiling command' -- check whether HI172's needs are already covered by HI132's planned scope, or are a distinct, narrower analysis that can proceed independently of HI132's own implementation timeline.

BEFORE running real GPU/profiling time on this: consulting dev-gpt-agent to sanity-check the hypothesis framing (is the 3-way + reverse-4th taxonomy sound / complete / correctly falsifiable given the available tooling) and the proposed kernel-fraction-based method, per this session's established practice of review-before-spend on nontrivial real-hardware work.
