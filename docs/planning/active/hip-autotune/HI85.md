# AUTO reduction plan crashes instead of falling back on RCCL hard failure

## Description

Discovered as a side effect of HI84's Stage 2 heterogeneous-pair characterization on Brutus (2026-08-22), not something deliberately investigated -- flagging as its own item because it's a real production robustness gap, distinct from HI18/HI84's correctness-evidence scope.

When SPLIT_REDUCE's RCCL provider hits certain real hardware failures, it does not fail gracefully (return false, letting the caller fall through to META's generic butterfly reduction, exactly as patches/0830's telemetry contract assumes). Instead it aborts the entire process with SIGABRT. AUTO mode (the actual production default -- GGML_HIP_REDUCE_PLAN unset or 'auto') does not catch this: it attempts RCCL first, RCCL aborts hard, and the whole inference process dies instead of transparently falling back to META the way the fallback_depth/handoff telemetry contract implies it always would.

Concretely reproduced via HI18's test-hip-reduce probe (patches/1224) on Brutus: any allreduce whose participant set includes device 3 (RX 6900 XT, gfx1030/RDNA2) alongside any other GPU on this box crashes under GGML_HIP_REDUCE_PLAN=rccl AND under the default auto -- exit 134, real stack ggml_backend_cuda_comm_allreduce_nccl -> ncclGroupEnd() -> 'ROCm error: unhandled cuda error' / 'HIP failure: the operation cannot be performed in the present state'. Forced GGML_HIP_REDUCE_PLAN=meta works correctly and is numerically verified correct for the same device pairs (see HI84's Stage 2 notes).

DISCREPANCY RESOLVED (2026-08-22): user recalled successfully running all 4 GPUs together previously (DeepSeek, with some layers offloaded to CPU since the model didn't fit in VRAM) -- initially appeared to contradict the RCCL crash findings above. Root cause of the apparent conflict: that prior run used layer/pipeline-split distribution (llama.cpp's default multi-GPU mode, `-sm layer` or unspecified, with CPU offload for whatever doesn't fit), NOT tensor-split (`-sm tensor`, what production's dual-XTX profile actually uses and what every crash test in this item used). Layer-split partitions MODEL LAYERS across GPUs sequentially -- each GPU runs its own layers and passes activations to the next via simple point-to-point copies -- and never constructs the comm_ctx/META reduction machinery or calls RCCL at all. Only tensor-split needs a cross-device allreduce (splitting matrices WITHIN a layer, requiring partial results to be summed back together), which is the only reason device 3's RCCL incompatibility can surface.

Confirmed directly: `-sm layer -ngl 99` across HIP_VISIBLE_DEVICES=0,1,2,3 (all 4 heterogeneous GPUs, real ROCm-7.14-multiarch RCCL-enabled build) loads cleanly and completes a real inference request successfully, no crash, no RCCL/allreduce code path touched at all. This is NOT new counter-evidence against the RCCL finding -- it's a different code path that was never expected to be affected.

Also directly confirmed device ordering does not matter for the crash: tested HIP_VISIBLE_DEVICES permutations (3,0 / 0,3 / 0,1,3 / 3,0,1) via the raw stock reproducer -- device 3 triggers the identical crash regardless of its position in the list or which logical rank index it lands on ('current device: N' in the error always just reflects whichever rank device 3 happened to map to that run, not a different root cause). The 3-device set excluding device 3 (0,1,2 -- both RDNA3 XTXs + the RDNA4 R9700) works cleanly with no crash, reinforcing that device 3 itself, not group size or ordering, is the actual trigger.

Final state unchanged in substance: RCCL/tensor-split with device 3 in the participant set crashes reliably and reproducibly across ROCm 7.2.4 and 7.14 (genuinely RCCL-enabled builds), independent of device order or group size; layer-split and GGML_CUDA_ALLREDUCE=internal (falls back to META) both work reliably as alternatives. No further action planned on this item unless device 3's participation in a real tensor-split deployment becomes an actual requirement.

CORRECTION (2026-08-22): my initial explanation for the 'user ran all 4 GPUs successfully before' discrepancy was wrong on one point -- I conflated 'CPU layer-offload' with '-sm layer split mode' and tested only the latter. These are orthogonal: -ngl controls how many layers reach GPU at all (rest stay on CPU); -sm controls how the GPU-resident layers get split across GPUs. -sm tensor + partial -ngl (CPU offload) is a valid, real combination, correctly pointed out by the user.

Tested directly: `-sm tensor -ngl 20` (partial offload, most of Qwen3.5-9B-Q8_0 on CPU) across HIP_VISIBLE_DEVICES=0,1,2,3 on the real RCCL-enabled ROCm-7.14-multiarch build -- CRASHES, identical signature ('invalid device function' at ggml_backend_cuda_comm_allreduce_nccl, current device 3). CPU layer-offload does NOT avoid the issue: whatever fraction of the model IS resident on GPU still gets tensor-split across the participating devices and still requires the same cross-device allreduce for that portion, so device 3's RCCL incompatibility still triggers.

So the corrected, precise statement is: it is specifically `-sm layer` (or default/no -sm, i.e. pipeline distribution) that avoids RCCL entirely, NOT 'CPU offload' as a general concept -- CPU offload is orthogonal and does not help when -sm tensor is what's actually selected. If the user's prior successful 4-GPU DeepSeek run used -sm tensor with CPU offload rather than -sm layer, that would NOT be explained by this reasoning and would be genuinely new counter-evidence worth investigating further (different model architecture/MoE routing possibly avoiding the reduction in some cases, different -sm value entirely, or a different point in time/driver state). Only -sm layer has been directly confirmed clean; -sm tensor has been confirmed to crash with device 3 in every configuration tested (full GPU-resident, partial GPU-resident via -ngl, different HIP_VISIBLE_DEVICES orderings, 2/3/4-device groups, two ROCm versions).

MAJOR CORRECTION (2026-08-22): the earlier conclusion 'devices {0,1,2} (RDNA3+RDNA3+RDNA4, no device 3) work cleanly' was WRONG -- it was based only on the raw synthetic reproducer's tiny 64-element tensor, which is far below ggml-cuda.cu's small-vs-large-tensor threshold (n_backends==3: ne<131072 is 'small'). Tested with the REAL production model (Qwen3.8-27B-Q8_0, real llama-server, -sm tensor -ngl 99, real tensor shapes/sizes across dozens of real layers) on HIP_VISIBLE_DEVICES=0,1,2: CRASHES. Same call site (ggml_backend_cuda_comm_try_allreduce_nccl), same 'invalid device function' error as the device-3 cases, but this time at 'current device: 2' -- the R9700 (gfx1201/RDNA4), with device 3 (gfx1030/RDNA2) not even present in this run.

So the issue is NOT narrowly 'device 3 / gfx1030 specifically' as concluded earlier -- it is broader: this box's RCCL has a real problem with heterogeneous multi-architecture 3+ device groups under realistic (large/many) tensor workloads, not tied to one specific card. The earlier small-tensor synthetic tests gave a false-negative for the {0,1,2} case specifically because the test tensors were too small to reach the code path/threshold where the real failure occurs.

REVISED UNDERSTANDING: RCCL heterogeneous multi-arch group collectives (N>=3 devices spanning more than one GPU architecture) are unreliable on this box under real workload tensor sizes, independent of which specific card combination is used -- this looks more like a genuine RCCL bug/limitation with heterogeneous >=3-way groups on this hardware/ROCm stack in general, not a single-card compatibility issue. Confirmed reproducing across: {0,3} pair, {1,3} pair, {2,3} pair, {0,1,3} triple, {3,0,1} triple (all synthetic-tensor, all include device 3), AND NOW {0,1,2} triple with a REAL model and NO device 3 present. Worth testing {0,2}/{1,2} with the REAL model too before trusting the 'pairs are fine' conclusion the same way {0,1,2} synthetic testing turned out not to be trustworthy.

Practical conclusion strengthens rather than weakens: this remains a real hardware/RCCL-stack limitation for N>=3-device heterogeneous groups on this box, not a BigCherry defect (still confirmed via the stock-code reproducer for the device-3 cases), and does not affect the actual production {0,1} topology. HI84's D=3/D=4 correctness work (if pursued) should treat 'RCCL any N>=3 heterogeneous group' as expected-to-fail and plan to use forced META for those groups from the start, rather than treating device 3 as the sole exclusion.

FINAL, DEFINITIVE CONCLUSION (2026-08-22): tested every remaining 2-device pair with the real production model (Qwen3.8-27B-Q8_0, real llama-server, -sm tensor -ngl 99, ROCm-7.14-multiarch genuinely-RCCL-enabled build) to settle whether the crash is about device 3, group size, or something else. Result is completely clean and simple:

- {0,1} (RDNA3 + RDNA3, the actual production pair): WORKS. Real inference completes correctly.
- {0,2} (RDNA3 + RDNA4): CRASHES. 'invalid device function' at ggml_backend_cuda_comm_allreduce_nccl.
- {1,2} (RDNA3 + RDNA4): CRASHES. Same signature.
- {0,1,2} (RDNA3+RDNA3+RDNA4): CRASHES. Same signature (reported earlier this item).
- Every combination including device 3 (RDNA2): CRASHES, both ROCm 7.2.4 and 7.14.

So the rule is exactly: RCCL works ONLY when every participating device shares the same GPU architecture (gfx target). ANY architecture mismatch -- even a single pair, even RDNA3+RDNA4 which are architecturally adjacent/recent -- crashes reliably under real production tensor sizes. This is NOT about device count (N=2 crashes exactly like N=3), NOT about device 3/RDNA2 specifically (RDNA3+RDNA4 crashes too), and NOT a small-vs-large-tensor threshold artifact on its own (though tensor size does matter for WHETHER a given test catches it -- tiny synthetic tensors can mask the bug entirely, as the earlier misleading '0,1,2 is clean' and '0,2/1,2 pairs are clean' conclusions from synthetic-tensor testing demonstrated).

This reframes the whole investigation: this is not a 'one bad card' problem, it is 'this box's RCCL/ROCm stack cannot do heterogeneous-architecture GPU collectives at all under real workloads,' confirmed across two ROCm versions with the real production server and real production-shaped tensors. The only combination that has ever produced a real, successful, real-model inference response via RCCL/tensor-split on this box is the actual production topology {0,1} (same architecture).

PRACTICAL CONCLUSION (final): -sm tensor is safe ONLY on same-architecture GPU subsets. On this box that means {0,1} only. Any tensor-split deployment spanning devices of different architectures (0/1 with 2, or with 3, in any combination) requires GGML_HIP_REDUCE_PLAN=meta forced explicitly, or GGML_CUDA_ALLREDUCE=internal for exactly 2 devices (which also just falls back to META), since AUTO's RCCL-first default will crash the process rather than gracefully falling back to META, for ANY heterogeneous-architecture participant set. -sm layer (pipeline/layer split) remains unaffected regardless of architecture mix, since it never invokes RCCL at all. This should be treated as a documented hardware/RCCL-stack limitation for this specific box, not something to fix at the BigCherry code layer -- confirmed not a BigCherry defect via the stock-code (zero BigCherry code) reproducer in this item's first triage round.

FIX IMPLEMENTED (2026-08-22): patches/1225_hi85_nccl_heterogeneous_arch_guard.py. Root-cause diagnosed via NCCL_DEBUG=INFO tracing against the genuinely RCCL-enabled ROCm-7.14-multiarch build: per-rank topology/tuning setup IS correctly architecture-aware (RCCL assigns a distinct 'Tuning index' per rank matching each device's real GPU model, and ncclCommInitAll_impl completes cleanly for every rank), but the crash happens later, inside ncclGroupEnd() when the actual collective kernel is launched -- 'HIP failure: invalid device function' on the non-matching rank. This is a HIP-level hard abort (SIGABRT), NOT a catchable ncclResult_t error code, so the existing 'NCCL init failed (...); falling back to internal AllReduce' warning path (which only triggers on a bad return code from ncclCommInitAll itself) never has a chance to run -- init succeeds, the crash happens on the next call.

Fix: added a guard in ggml_backend_cuda_comm_init_nccl(), placed immediately after (same function, same pattern as) the existing virtual-device decline check. Compares every participating device's ggml_cuda_device_info::cc (already tracked, populated from real prop.gcnArchName at ggml-cuda.cu:349) before ever calling ncclCommInitAll; any mismatch logs a clear GGML_LOG_WARN naming the reason (per explicit user requirement -- must be visible, not a silent behavior change) and falls back to the existing ggml_backend_cuda_comm_init_internal(ret) path, exactly mirroring the pre-existing virtual-device guard. This makes AUTO's RCCL-first default safe for a heterogeneous participant set instead of crashing the whole process; forced GGML_HIP_REDUCE_PLAN=meta already worked correctly for these cases and is unaffected.

7 new source-contract tests (patch applies cleanly/idempotently against the real vendored source, guard runs before the real ncclCommInitAll call site -- verified against the actual patched file content, not just the patch's own prose, since the patch's docstring/comments also mention ncclCommInitAll and could produce a false match -- decline reuses the existing internal-AllReduce fallback rather than a new path, warning is logged before declining, and the check covers every device in the participant set via a loop, not just a single pair). Full offline suite: 1650 passed, 3 skipped.

One real implementation wrinkle worth recording: the anchor had to be built to survive the bigcherry patcher's noise-stripping pass, which blanks string literals (including their quotes) to same-length spaces before anchor matching -- the same technique patches/1222 already established for blanked comments, applied here to the two GGML_LOG_WARN string-literal arguments in the anchor block.

This is the concrete next step before calling this fix closed.
