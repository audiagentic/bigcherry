# AUTO reduction plan crashes instead of falling back on RCCL hard failure

## Description

Discovered as a side effect of HI84's Stage 2 heterogeneous-pair characterization on Brutus (2026-08-22), not something deliberately investigated -- flagging as its own item because it's a real production robustness gap, distinct from HI18/HI84's correctness-evidence scope.

When SPLIT_REDUCE's RCCL provider hits certain real hardware failures, it does not fail gracefully (return false, letting the caller fall through to META's generic butterfly reduction, exactly as patches/0830's telemetry contract assumes). Instead it aborts the entire process with SIGABRT. AUTO mode (the actual production default -- GGML_HIP_REDUCE_PLAN unset or 'auto') does not catch this: it attempts RCCL first, RCCL aborts hard, and the whole inference process dies instead of transparently falling back to META the way the fallback_depth/handoff telemetry contract implies it always would.

Concretely reproduced via HI18's test-hip-reduce probe (patches/1224) on Brutus: any allreduce whose participant set includes device 3 (RX 6900 XT, gfx1030/RDNA2) alongside any other GPU on this box crashes under GGML_HIP_REDUCE_PLAN=rccl AND under the default auto -- exit 134, real stack ggml_backend_cuda_comm_allreduce_nccl -> ncclGroupEnd() -> 'ROCm error: unhandled cuda error' / 'HIP failure: the operation cannot be performed in the present state'. Forced GGML_HIP_REDUCE_PLAN=meta works correctly and is numerically verified correct for the same device pairs (see HI84's Stage 2 notes).

## Notes

Not yet triaged for root cause (is this RCCL/ROCm's own limitation with this GPU/driver/codeobject combination, or something BigCherry's provider-selection code could detect and avoid before calling into RCCL) or severity (does this affect any currently-supported/documented production hardware configuration, or only this specific heterogeneous mix that isn't a real deployment target). Whoever picks this up should first determine: (1) does GGML_CUDA_ALLREDUCE (the pre-existing, unrelated env var controlling backend construction time provider selection: nccl/internal/none) offer any way to avoid RCCL for a known-bad device combination at initialization instead of discovering the failure at every call, (2) can ncclCommInitAll/ncclGroupEnd's failure mode be probed/caught before it aborts the process (may not be possible if it's a hard HIP-level fault rather than a catchable NCCL error code), (3) whether this is specific to gfx1030 (RDNA2) or a broader multi-generation RCCL limitation worth documenting as a hardware compatibility boundary regardless of a code fix.

ROOT-CAUSE TRIAGE (2026-08-22): confirmed this is a pure upstream/RCCL bug, not anything BigCherry's overlay/patches introduced.

Wrote a minimal, BigCherry-free reproducer (no telemetry, no META backend, no dispatch layer -- just ggml_backend_load_all -> enumerate GPU devices -> ggml_backend_dev_init x2 -> resolve ggml_backend_comm_init/ggml_backend_comm_allreduce_tensor via the plain backend registry -> comm_init -> allocate 2 tiny COMPUTE-flagged F32 tensors -> comm_allreduce_tensor) and compiled/linked it directly against Brutus's existing STOCK (unpatched, separate vendor/llama.cpp-stock checkout, no GGML_HIP_AUTOTUNE, no BigCherry code at all) build at ~/bc-build-stock-rccl.

Ran with HIP_VISIBLE_DEVICES=0,3 (device 0 = RX 7900 XTX/RDNA3, device 3 = RX 6900 XT/RDNA2 -- the exact pairing that crashed HI18's probe): identical crash. Same signature exactly: SIGABRT (exit 134), 'ROCm error: unhandled cuda error', 'HIP failure: the operation cannot be performed in the present state', in ggml_backend_cuda_comm_try_allreduce_nccl -> ncclGroupEnd(). This is upstream ggml-cuda.cu's own RCCL allreduce path, reached with zero BigCherry involvement (this stock checkout predates and has none of BigCherry's dispatch/telemetry/META instrumentation).

CONCLUSION: this is an RCCL/ROCm-level incompatibility specific to combining this particular RDNA2 card (gfx1030, RX 6900 XT) with other GPU architectures via NCCL's collective init/allreduce on this system -- a real hardware/driver/RCCL-library boundary, not a BigCherry defect, and not something HI18/HI84's correctness-evidence work could have caused or needs to work around at the BigCherry layer. Options going forward, none started: (1) report/check known RCCL issues for mixed RDNA2+RDNA3/4 topologies upstream, (2) treat 'device 3 excluded from RCCL, META-only' as a documented hardware boundary for this box rather than a bug to fix, (3) investigate whether GGML_CUDA_ALLREDUCE=internal or =none avoids the crash for this specific device combination at backend-construction time (init-time provider selection, distinct from BigCherry's per-call GGML_HIP_REDUCE_PLAN seam) as a possible production mitigation if this hardware combination is ever actually deployed.

Downgrading practical urgency: since this reproduces identically on stock, unmodified upstream code, it is arguably not a BigCherry bug to fix at all -- it's either an upstream llama.cpp/RCCL issue worth reporting, or simply a known hardware limitation of this specific heterogeneous combination that doesn't need code changes on BigCherry's side. Keep pending; do not prioritize a BigCherry-side fix without first confirming this combination is an actual deployment target.
