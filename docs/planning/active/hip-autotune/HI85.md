# AUTO reduction plan crashes instead of falling back on RCCL hard failure

## Description

Discovered as a side effect of HI84's Stage 2 heterogeneous-pair characterization on Brutus (2026-08-22), not something deliberately investigated -- flagging as its own item because it's a real production robustness gap, distinct from HI18/HI84's correctness-evidence scope.

When SPLIT_REDUCE's RCCL provider hits certain real hardware failures, it does not fail gracefully (return false, letting the caller fall through to META's generic butterfly reduction, exactly as patches/0830's telemetry contract assumes). Instead it aborts the entire process with SIGABRT. AUTO mode (the actual production default -- GGML_HIP_REDUCE_PLAN unset or 'auto') does not catch this: it attempts RCCL first, RCCL aborts hard, and the whole inference process dies instead of transparently falling back to META the way the fallback_depth/handoff telemetry contract implies it always would.

Concretely reproduced via HI18's test-hip-reduce probe (patches/1224) on Brutus: any allreduce whose participant set includes device 3 (RX 6900 XT, gfx1030/RDNA2) alongside any other GPU on this box crashes under GGML_HIP_REDUCE_PLAN=rccl AND under the default auto -- exit 134, real stack ggml_backend_cuda_comm_allreduce_nccl -> ncclGroupEnd() -> 'ROCm error: unhandled cuda error' / 'HIP failure: the operation cannot be performed in the present state'. Forced GGML_HIP_REDUCE_PLAN=meta works correctly and is numerically verified correct for the same device pairs (see HI84's Stage 2 notes).

ROOT-CAUSE TRIAGE (2026-08-22): confirmed this is a pure upstream/RCCL bug, not anything BigCherry's overlay/patches introduced.

Wrote a minimal, BigCherry-free reproducer (no telemetry, no META backend, no dispatch layer -- just ggml_backend_load_all -> enumerate GPU devices -> ggml_backend_dev_init x2 -> resolve ggml_backend_comm_init/ggml_backend_comm_allreduce_tensor via the plain backend registry -> comm_init -> allocate 2 tiny COMPUTE-flagged F32 tensors -> comm_allreduce_tensor) and compiled/linked it directly against Brutus's existing STOCK (unpatched, separate vendor/llama.cpp-stock checkout, no GGML_HIP_AUTOTUNE, no BigCherry code at all) build at ~/bc-build-stock-rccl.

Ran with HIP_VISIBLE_DEVICES=0,3 (device 0 = RX 7900 XTX/RDNA3, device 3 = RX 6900 XT/RDNA2 -- the exact pairing that crashed HI18's probe): identical crash. Same signature exactly: SIGABRT (exit 134), 'ROCm error: unhandled cuda error', 'HIP failure: the operation cannot be performed in the present state', in ggml_backend_cuda_comm_try_allreduce_nccl -> ncclGroupEnd(). This is upstream ggml-cuda.cu's own RCCL allreduce path, reached with zero BigCherry involvement (this stock checkout predates and has none of BigCherry's dispatch/telemetry/META instrumentation).

CONCLUSION: this is an RCCL/ROCm-level incompatibility specific to combining this particular RDNA2 card (gfx1030, RX 6900 XT) with other GPU architectures via NCCL's collective init/allreduce on this system -- a real hardware/driver/RCCL-library boundary, not a BigCherry defect, and not something HI18/HI84's correctness-evidence work could have caused or needs to work around at the BigCherry layer. Options going forward, none started: (1) report/check known RCCL issues for mixed RDNA2+RDNA3/4 topologies upstream, (2) treat 'device 3 excluded from RCCL, META-only' as a documented hardware boundary for this box rather than a bug to fix, (3) investigate whether GGML_CUDA_ALLREDUCE=internal or =none avoids the crash for this specific device combination at backend-construction time (init-time provider selection, distinct from BigCherry's per-call GGML_HIP_REDUCE_PLAN seam) as a possible production mitigation if this hardware combination is ever actually deployed.

Downgrading practical urgency: since this reproduces identically on stock, unmodified upstream code, it is arguably not a BigCherry bug to fix at all -- it's either an upstream llama.cpp/RCCL issue worth reporting, or simply a known hardware limitation of this specific heterogeneous combination that doesn't need code changes on BigCherry's side. Keep pending; do not prioritize a BigCherry-side fix without first confirming this combination is an actual deployment target.

ROOT-CAUSE TRIAGE, ROUND 2 (2026-08-22) -- tested across two independent ROCm versions with real production llama-server + real models, per user request (they recalled a prior successful 4-GPU RCCL run and wanted this checked properly rather than accepted on a single data point).

Built ROCm 7.14.0 side-by-side with the existing production 7.2.4 install using BigCherry's OWN existing toolchain-selection mechanism (tools/rocm-env.sh + vendor/rocm/<version>/ convention, previously undocumented as usable for this but exactly designed for it) -- no system-wide change, /opt/rocm untouched throughout. Downloaded AMD's 7.14 tarballs to ~/rocm-7.14(-multiarch) on Brutus, symlinked into vendor/rocm/, selected via `source tools/rocm-env.sh 7.14-multiarch`, built with `-DGGML_HIP_RCCL=ON -DAMDGPU_TARGETS='gfx1100;gfx1201;gfx1030'` (matching bc-build-hi64hi14's real production cmake flags).

First attempt used AMD's single-architecture 'gfx110X' tarball without -DGGML_HIP_RCCL=ON -- silently built WITHOUT RCCL at all (GGML_HIP_RCCL gates find_package(rccl)/GGML_USE_NCCL in ggml/src/ggml-hip/CMakeLists.txt, confirmed by zero NCCL/RCCL mentions in the configure log even with NCCL_DEBUG=INFO set at runtime). That first 'success' was invalid evidence -- it never reached the RCCL code path at all, just fell through the same internal->meta chain as the explicit GGML_CUDA_ALLREDUCE=internal test. Caught and corrected: downloaded AMD's true multi-arch tarball (therock-dist-linux-multiarch-7.14.0.tar.gz, 20GB extracted, genuinely covers gfx1030/gfx1100/gfx1201 together -- verified gfx1030 code-object strings present in the resulting librccl.so.1.0 via `strings`), reconfigured with GGML_HIP_RCCL=ON explicitly, rebuilt clean.

Re-ran the identical real-production test (llama-server, Qwen3.5-2B-IQ4_XS, -sm tensor -ngl 99, HIP_VISIBLE_DEVICES=0,1,2,3, default GGML_CUDA_ALLREDUCE i.e. RCCL attempted first) against this genuinely RCCL-enabled 7.14 build: CRASHES, same as 7.2.4, but with a DIFFERENT specific error -- 'HIP failure: invalid device function' at ggml_backend_cuda_comm_allreduce_nccl's ncclGroupEnd(), vs 7.2.4's 'the operation cannot be performed in the present state'. Both happen at the identical call site, both specifically when device 3 (RX 6900 XT, gfx1030/RDNA2) participates in the RCCL group.

UPDATED CONCLUSION: this is not a ROCm-7.2.4-specific regression -- reproduces on two independent ROCm versions (7.2.4 and 7.14.0) with genuinely RCCL-enabled builds, with real production llama-server and real models both times, and with the raw BigCherry-free stock-code reproducer from the first triage round. The different error signature per ROCm version ('operation cannot be performed in present state' vs 'invalid device function') suggests the underlying issue may be RCCL's kernel/code-object selection logic for a HETEROGENEOUS multi-architecture group specifically (gfx1030 code objects ARE present in RCCL's own binary per the strings check, ruling out simple missing-architecture packaging) rather than a single fixed bug -- but confirming the precise root cause inside RCCL itself is beyond what's practical to keep chasing from the BigCherry side without RCCL's own source/debug tooling.

STILL WORKS RELIABLY on every version tested: GGML_CUDA_ALLREDUCE=internal (declines cleanly for n_devices!=2, falls back to META's butterfly reduction) -- real inference completes successfully every time this was tried, including the full 4-device heterogeneous set.

Test infrastructure state: ~/bc-build-rocm714-multiarch (real RCCL-enabled 7.14 build) and vendor/rocm/7.14, vendor/rocm/7.14-multiarch (symlinks to ~/rocm-7.14/install and ~/rocm-7.14-multiarch/install, ~30GB combined) left in place on Brutus for any follow-up testing -- not cleaned up, since they may be useful for further RCCL-version comparison work. The single-arch (non-multiarch) 7.14 build (~/bc-build-rocm714) is stale/invalid (no RCCL) and could be removed or reconfigured.

Practical recommendation unchanged in substance, strengthened by the multi-version evidence: treat 'device 3 (gfx1030) excluded from RCCL, META-only' as a real hardware/RCCL-library boundary for this box across ROCm versions, not a bug to fix at the BigCherry layer. If this combination becomes an actual deployment target, GGML_CUDA_ALLREDUCE=internal is a viable, already-verified-working mitigation (falls back to META automatically) -- though internal AR itself only supports exactly 2 devices, so for the D=3/D=4 heterogeneous case specifically the effective production-safe path is forcing META directly (GGML_HIP_REDUCE_PLAN=meta, already verified correct by HI18/HI84's own probe work) rather than relying on AUTO's RCCL-first default at all when device 3 is in the participant set.

DISCREPANCY RESOLVED (2026-08-22): user recalled successfully running all 4 GPUs together previously (DeepSeek, with some layers offloaded to CPU since the model didn't fit in VRAM) -- initially appeared to contradict the RCCL crash findings above. Root cause of the apparent conflict: that prior run used layer/pipeline-split distribution (llama.cpp's default multi-GPU mode, `-sm layer` or unspecified, with CPU offload for whatever doesn't fit), NOT tensor-split (`-sm tensor`, what production's dual-XTX profile actually uses and what every crash test in this item used). Layer-split partitions MODEL LAYERS across GPUs sequentially -- each GPU runs its own layers and passes activations to the next via simple point-to-point copies -- and never constructs the comm_ctx/META reduction machinery or calls RCCL at all. Only tensor-split needs a cross-device allreduce (splitting matrices WITHIN a layer, requiring partial results to be summed back together), which is the only reason device 3's RCCL incompatibility can surface.

Confirmed directly: `-sm layer -ngl 99` across HIP_VISIBLE_DEVICES=0,1,2,3 (all 4 heterogeneous GPUs, real ROCm-7.14-multiarch RCCL-enabled build) loads cleanly and completes a real inference request successfully, no crash, no RCCL/allreduce code path touched at all. This is NOT new counter-evidence against the RCCL finding -- it's a different code path that was never expected to be affected.

Also directly confirmed device ordering does not matter for the crash: tested HIP_VISIBLE_DEVICES permutations (3,0 / 0,3 / 0,1,3 / 3,0,1) via the raw stock reproducer -- device 3 triggers the identical crash regardless of its position in the list or which logical rank index it lands on ('current device: N' in the error always just reflects whichever rank device 3 happened to map to that run, not a different root cause). The 3-device set excluding device 3 (0,1,2 -- both RDNA3 XTXs + the RDNA4 R9700) works cleanly with no crash, reinforcing that device 3 itself, not group size or ordering, is the actual trigger.

Final state unchanged in substance: RCCL/tensor-split with device 3 in the participant set crashes reliably and reproducibly across ROCm 7.2.4 and 7.14 (genuinely RCCL-enabled builds), independent of device order or group size; layer-split and GGML_CUDA_ALLREDUCE=internal (falls back to META) both work reliably as alternatives. No further action planned on this item unless device 3's participation in a real tensor-split deployment becomes an actual requirement.

CORRECTION (2026-08-22): my initial explanation for the 'user ran all 4 GPUs successfully before' discrepancy was wrong on one point -- I conflated 'CPU layer-offload' with '-sm layer split mode' and tested only the latter. These are orthogonal: -ngl controls how many layers reach GPU at all (rest stay on CPU); -sm controls how the GPU-resident layers get split across GPUs. -sm tensor + partial -ngl (CPU offload) is a valid, real combination, correctly pointed out by the user.

Tested directly: `-sm tensor -ngl 20` (partial offload, most of Qwen3.5-9B-Q8_0 on CPU) across HIP_VISIBLE_DEVICES=0,1,2,3 on the real RCCL-enabled ROCm-7.14-multiarch build -- CRASHES, identical signature ('invalid device function' at ggml_backend_cuda_comm_allreduce_nccl, current device 3). CPU layer-offload does NOT avoid the issue: whatever fraction of the model IS resident on GPU still gets tensor-split across the participating devices and still requires the same cross-device allreduce for that portion, so device 3's RCCL incompatibility still triggers.

So the corrected, precise statement is: it is specifically `-sm layer` (or default/no -sm, i.e. pipeline distribution) that avoids RCCL entirely, NOT 'CPU offload' as a general concept -- CPU offload is orthogonal and does not help when -sm tensor is what's actually selected. If the user's prior successful 4-GPU DeepSeek run used -sm tensor with CPU offload rather than -sm layer, that would NOT be explained by this reasoning and would be genuinely new counter-evidence worth investigating further (different model architecture/MoE routing possibly avoiding the reduction in some cases, different -sm value entirely, or a different point in time/driver state). Only -sm layer has been directly confirmed clean; -sm tensor has been confirmed to crash with device 3 in every configuration tested (full GPU-resident, partial GPU-resident via -ngl, different HIP_VISIBLE_DEVICES orderings, 2/3/4-device groups, two ROCm versions).

MAJOR CORRECTION (2026-08-22): the earlier conclusion 'devices {0,1,2} (RDNA3+RDNA3+RDNA4, no device 3) work cleanly' was WRONG -- it was based only on the raw synthetic reproducer's tiny 64-element tensor, which is far below ggml-cuda.cu's small-vs-large-tensor threshold (n_backends==3: ne<131072 is 'small'). Tested with the REAL production model (Qwen3.8-27B-Q8_0, real llama-server, -sm tensor -ngl 99, real tensor shapes/sizes across dozens of real layers) on HIP_VISIBLE_DEVICES=0,1,2: CRASHES. Same call site (ggml_backend_cuda_comm_try_allreduce_nccl), same 'invalid device function' error as the device-3 cases, but this time at 'current device: 2' -- the R9700 (gfx1201/RDNA4), with device 3 (gfx1030/RDNA2) not even present in this run.

So the issue is NOT narrowly 'device 3 / gfx1030 specifically' as concluded earlier -- it is broader: this box's RCCL has a real problem with heterogeneous multi-architecture 3+ device groups under realistic (large/many) tensor workloads, not tied to one specific card. The earlier small-tensor synthetic tests gave a false-negative for the {0,1,2} case specifically because the test tensors were too small to reach the code path/threshold where the real failure occurs.

CRITICAL SANITY CHECK, CONFIRMED CLEAN: the actual real production pair -- devices {0,1} (both RX 7900 XTX / RDNA3, the ONLY topology actually used in production today) -- loads the real 27B model successfully and completes a real inference request correctly under the same ROCm-7.14-multiarch RCCL-enabled build. Production is NOT at risk; this entire investigation has been exclusively about topologies (3-device and 4-device heterogeneous groups) that are not currently deployed.

REVISED UNDERSTANDING: RCCL heterogeneous multi-arch group collectives (N>=3 devices spanning more than one GPU architecture) are unreliable on this box under real workload tensor sizes, independent of which specific card combination is used -- this looks more like a genuine RCCL bug/limitation with heterogeneous >=3-way groups on this hardware/ROCm stack in general, not a single-card compatibility issue. Confirmed reproducing across: {0,3} pair, {1,3} pair, {2,3} pair, {0,1,3} triple, {3,0,1} triple (all synthetic-tensor, all include device 3), AND NOW {0,1,2} triple with a REAL model and NO device 3 present. The one combination NOT yet shown to crash is exactly N=2 (any pair not involving unusual VRAM/topology constraints) -- {0,2} and {1,2} synthetic-tensor pairs were clean, and {0,1} is clean with the real model. Worth testing {0,2}/{1,2} with the REAL model too before trusting the 'pairs are fine' conclusion the same way {0,1,2} synthetic testing turned out not to be trustworthy.

Practical conclusion strengthens rather than weakens: this remains a real hardware/RCCL-stack limitation for N>=3-device heterogeneous groups on this box, not a BigCherry defect (still confirmed via the stock-code reproducer for the device-3 cases), and does not affect the actual production {0,1} topology. HI84's D=3/D=4 correctness work (if pursued) should treat 'RCCL any N>=3 heterogeneous group' as expected-to-fail and plan to use forced META for those groups from the start, rather than treating device 3 as the sole exclusion.
