# Replay fallback paths under graph capture (hardware separation, cache corruption, process-cache hit)

## Description

Split off from HI16 (2026-08-23) so HI16's genuinely-completed scope (catalog/registry agreement, cross-language digest agreement, forced-native bitwise parity across all five kernel families) can close honestly. This item is HI16's one remaining substantial gap: replay-mode fallback behavior under graph capture has no dedicated test coverage -- hardware separation (a cache built for one GPU class must not silently serve another), refined-to-base fallback, missing-candidate fallback, corrupted-cache handling, incompatible-manifest-hash handling, process cache hit after first lookup (no recurring hashing), and graph capture recording the selected launch rather than the dispatcher lookup.

## Steps

1. Determine what test infrastructure already exists for replay-mode testing (hip-autotune-inspect's cache-loading half is the closest existing tool -- check whether it can drive these scenarios or whether new infrastructure is needed).
2. Construct or acquire test caches exhibiting each fallback condition: wrong-hardware-class, missing candidate, corrupted bytes, incompatible manifest hash.
3. Verify graph capture specifically: with GGML_HIP_AUTOTUNE off / replay mode + graph capture on, confirm the CAPTURED launch is the resolved candidate's actual launch, not a re-run of the dispatcher's lookup logic on every replay (which would defeat the point of graph capture).
4. Verify process cache hit: after the first resolution for a given portable dispatch key, confirm no repeated hashing/lookup work occurs on subsequent calls within the same process.
