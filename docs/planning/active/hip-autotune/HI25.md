# Custom gfx1100 Q8_0 × Q8_1 WMMA kernel for K=5120, M=6144, N=512 (cherrypips family)

## Description

Bounded offline readiness gate for future custom MMQ/MMVQ kernels. No speculative GPU kernel implementation is included. An explicitly enabled custom candidate must prove architecture coverage, stable identity, correctness reference, compiler resource evidence, and benchmark evidence before catalog validation and registry generation can accept it.

## Steps

- Represent custom-kernel enablement evidence in the candidate config.
- Validate architecture mask and stable candidate identity against the manifest candidate.
- Require a distinct correctness/reference candidate and evidence path.
- Require architecture-matched resource-report evidence with SHA-256 identity.
- Require passed benchmark evidence with metric and baseline identity.
- Add offline regression tests and keep ordinary native/existing candidates compatible.

## Detailed Solution & Technical Design

The schema validator treats config.custom_kernel=true as an explicit opt-in. It requires architecture_mask to equal the canonical mask derived from architectures, candidate_identity to equal stable_name, a distinct correctness_reference record, a resource_report covering exactly the candidate architectures, and passed benchmark_evidence. Resource and benchmark links carry SHA-256 digests. Validation runs from validate_candidate, so malformed custom candidates cannot reach manifest validation, catalog rendering, or generated registry output.

## Stage 1: Exact-Shape Clone (Measure Genericity Overhead)

Clone the current native RDNA3 Q8_0 MMQ kernel into a separate translation unit and hard-code:
- gfx1100, Q8_0 × Q8_1
- K=5120, M=6144, N=512, I=128, J=128
- threads=256, no fallback, no tails, no batching, no experts, no stream-K

**Preserve exactly:**
- LDS layout (A tile ≈39 KiB + B half-tile ≈18 KiB, ~57 KiB total)
- Weight and activation loading (76-word SRAM stride pattern)
- Two K=128 halves per K=256 iteration
- RDNA3 WMMA calls (__builtin_amdgcn_wmma_i32_16x16x16_iu8_w32)
- Accumulator mapping and writeback

**Remove only generic machinery:**
- ggml_type template parameter and type switch
- Runtime I/J/K dimensions → constexpr
- Stride parameters → fixed indexing with shift/mask:
  ```
  tile_n = blockIdx.x & 3u; tile_m = blockIdx.x >> 2;
  m0 = tile_m << 7; n0 = tile_n << 7;
  tid = threadIdx.x; wave = tid >> 5; lane = tid & 31u;
  lane16 = lane & 15u; half = lane >> 4;
  ```
- Fallback path, tail handling, channel/sample ratios, expert IDs, fixup state, runtime J selection

**This answers: How much does genericity itself cost?**
- 0–1%: generic template overhead is compiled away → specialization alone isn't enough
- 2–3%: specialization is already worthwhile → proceed to Stage 2
- Regression: generated code changed unfavourably → inspect ISA, stop or adjust

**Stop rule:** At least parity with native. If slower, investigate before continuing.

## Stage 2: Occupancy Variants (Cheapest Meaningful Test)

Compile identical variants of the Stage 1 clone:
- __launch_bounds__(256, 2) — current two-block target
- __launch_bounds__(256, 1) — allow more VGPRs per thread

The kernel carries 64 FP32 accumulators per thread. Occupancy-two may be constraining VGPR allocation or causing extra movement.

**Measure:**
- VGPRs, SGPRs, spills and scratch (hard: private = 0, VGPR spills = 0)
- Active workgroups per CU
- Instruction count from ISA inspection
- Kernel median with p10/p90

**Stop rule:** Continue when better median with no problematic tails.

## Stage 3: Dead Branch Removal (Low-Risk Cleanup)

From the Stage 2 winner, compile out:
- Tile limit checks and bounds clamping
- Tail handling for non-multiple-of-tile dimensions
- Fallback clamps
- Runtime tensor dimensions and strides (contiguous is known)
- Channel and sample ratios
- Expert IDs and fixup state
- Runtime J selection

These are low-risk because the signature is exactly divisible in every dimension.

**Stop rule:** Repeatable gain above ~1%.

## Stage 4: Full K=256 Activation Tile in LDS (Halve Barriers)

The generic kernel processes K=256 as two K=128 halves with synchronization around each half. A specialized variant can stage both halves simultaneously.

**Current sequence:**
```
load A + B0 → barrier → compute B0 → barrier → load B1 → barrier → compute B1 → barrier
```
4 barriers per K tile × 20 tiles = 80 barriers total.

**With full K=256 B staging and A removed from LDS:**
```
load full B0+B1 → barrier → compute all K=256 → barrier
```
2 barriers per K tile × 20 tiles = 40 barriers total.

LDS budget: 36,864 bytes per B tile × 2 resident workgroups = 73,728 bytes (well under 128 KiB).

**Crucially preserves llama.cpp's proven tiled MMQ organization** — unlike the failed direct-WMMA experiment.

**Stop rule:** At least ~2% improvement.

## Stage 5: LDS Double Buffering (Prefetch Pipeline)

AMD's official perf_i8gemm example uses global prefetch, two LDS buffers, and compute/load overlap:
```
prefetch K tile 0 → write LDS buffer 0 → sync
current = 0
for each subsequent tile:
    prefetch next tile from global
    compute current tile from LDS[current]
    publish next tile to LDS[next]
    sync
    swap current and next
```

This is more promising than replacing LDS with direct global loads.

**Stop rule:** Gain survives end-to-end replay (not just microbenchmark).

## Stage 6: Preconverted Scale Storage (FP32 Sidecar)

The Q8_0 scale is static with the model. A packed sidecar stores it in FP32 or directly in the kernel's consumed arrangement.

**Potential benefit:**
- Remove repeated FP16-to-FP32 conversions per K=32 fragment
- Reduce scale-address calculations
- Possibly improve vector loading

**Potential cost:**
- Additional model memory (FP16 → FP32 doubles scale storage from 2 to 4 bytes per block)
- Duplicate packed weights for this signature
- Cache impact

**Stop rule:** At least ~3–5% kernel improvement.

## What Is Probably Not Worth Trying First

Do NOT initially build:
- Direct-global-load integer-WMMA kernel (hipEngine proved 44.7% regression)
- Completely new packed-weight format
- No-LDS implementation
- Fully handwritten assembly kernel
- Large generalized RDNA3 kernel framework

These are deferred until after Stages 1–6 have established a baseline and the incremental gains have been measured.

## Phase 1: Extract and Specialize (Correctness Baseline)

Extract llama.cpp's existing Q8_0/Q8_1 MMQ kernel into a standalone gfx1100-only file. Preserve its exact LDS layout, K decomposition, and WMMA fragment mapping. The goal is bit-identical output with native MMQ for this shape.

### What to preserve exactly
- **LDS layout:** Current A tile (≈39 KiB) + B half-tile (≈18 KiB) in LDS — the same ~57 KiB per block that fits two blocks under 128 KiB
- **K decomposition:** Two K=128 halves within each K=256 iteration, with four barriers per K tile
- **Q8_0 weight tile transformation:** The exact dequantize-and-stage pattern from mmq-load-tiles.cuh
- **Q8_1 LDS row:** 36-word padded row stride (avoids bank conflicts on RDNA2+
64-bank LDS)
- **WMMA fragment mapping:** Exact RDNA3 mirrored input layout from vecdotq.cuh — lanes 0–15 and 16–31 must have identical A/B fragments
- **Accumulator and writeback mapping:** Same output-lane ownership as native
- **Scale contract:** Q8_0 d × Q8_1 d scale multiplication every K=32, applied the same way as vecdotq.cuh

### What to remove in Phase 2
- ggml_type template parameter and type switch
- Runtime I/J/K dimensions — hardcoded to this exact shape
- Stride parameters — use fixed indexing
- Fallback path selection
- Tail handling for non-multiple-of-tile dimensions
- MoE expert bounds and ids support
- Channel/sample ratio broadcast logic
- Stream-K fixup buffers
- Generic tile descriptor objects
- Function pointers / dispatch indirection
- int64_t indexing — uint32_t suffices (M=6144, N=512, K=5120)
- Dynamic shared memory offsets

### Phase 2: Remove generic machinery
Replace all runtime-computed values with compile-time constexpr. Use shift/mask decomposition:
```
tile_n = blockIdx.x & 3u; tile_m = blockIdx.x >> 2;
m0 = tile_m << 7; n0 = tile_n << 7;
tid = threadIdx.x; wave = tid >> 5; lane = tid & 31u;
lane16 = lane & 15u; half = lane >> 4;
```

### Phase 3: Confirm baseline
The specialized clone must be bit-identical to native for this shape. If it is not, something about the LDS layout or WMMA fragment mapping diverged.

### Phase 4: Test Individual Optimizations (Each Must Beat Baseline)

**Optimization A: Occupancy 1 vs 2**
- Build __launch_bounds__(256, 1) allowing more VGPRs
- Build __launch_bounds__(256, 2) preserving two-block target
- Measure both; keep the faster one as new baseline
- Inspect hipcc --resource-usage: VGPR, SGPR, private bytes, spills
- Hard requirement: private segment = 0, VGPR spills = 0

**Optimization B: Full K=256 B staging (remove A from LDS)**
- Prepack A into tile-major order; load directly into VGPR fragments
- Stage full 36,864-byte B tile in LDS (two resident workgroups = 73,728 bytes)
- Reduce barriers from 4 to 2 per K tile (80 → 40 total for K=5120)
- This is the strongest concrete improvement

**Optimization C: FP32-preconverted A scales**
- Convert Q8_0 FP16 scale to FP32 once at model load
- Removes one half-to-float conversion per weight block per execution
- Increases scale storage from 2 to 4 bytes per 32 weights (only for hot signature)

**Optimization D: Double-buffered LDS**
- Two LDS buffers; prefetch next K tile while computing current
- Based on rocWMMA perf_i8gemm pattern:
  ```
  prefetch A/B → write LDS buffer 0 → sync → compute → prefetch → write LDS buffer 1 → sync → swap
  ```

**Optimization E: 512-thread alternative**
- 16 waves, each wave computes 16×64 output (half the columns)
- 32 FP32 accumulators per thread instead of 64
- One resident workgroup per CU; 192 workgroups in two scheduling rounds

**Optimization F: Independent-wave no-LDS**
- Each wave loads A and B directly from global memory
- Zero LDS, zero block barriers
- Relies on 2.8 MiB B operand fitting in L2 cache
- Most experimental — only after other optimizations are stable

## Critical lesson from hipEngine

hipEngine's rejected Q8T16 × Q8_1 experiment proved that a straightforward integer WMMA kernel with prequantized activations and direct global loads is 44.66% slower than the existing FP16 WMMA kernel on gfx1100. The bottleneck was not activation quantization (only +0.016 ms) — it was the fundamental difference between llama.cpp's shared-memory decomposition and a clean WMMA design.

**We must start from llama.cpp's MMQ LDS layout, not from a green-field WMMA kernel.** The advantage is in:
1. How Q8_0 weights are staged into LDS (the 76-word SRAM stride pattern)
2. How Q8_1 activations are tiled with 36-word padding for bank-conflict avoidance
3. The two K=128 half-tile decomposition that fits under the 128 KiB LDS limit
4. The WMMA fragment mapping that reuses staged data across multiple dot products

## Why cherrypips is a separate family, not an MMQ candidate

MMQ varies J over the same kernel body with the same data layout. Cherrypips:
- Requires entirely different prepack buffers (tile-major A, tiled B)
- Has a completely different launch contract (four typed pointers, no strides)
- Uses FP32 scale plane instead of FP16 inline scales
- Would need threading repacked pointers through mul_mat_q — architecturally wrong

Separate family keeps experimental kernels isolated. If something breaks, it's contained. The tuner doesn't have to deal with a candidate that requires prepack infrastructure no other candidate uses.

## Why not extend the generic RDNA3 path

The generic RDNA3 kernel (I=128, J=128, K=256) is already good — it uses WMMA. But it:
- Stages both A and B in LDS, leaving only half of B's K=256 resident at once (4 barriers per K tile)
- Converts FP16 scales to FP32 on every K=32 fragment
- Carries all generic machinery: type dispatch, shape parameters, stride calculations, bounds checks
- Uses dynamically indexed local arrays that risk register spills
- Loads A from row-major layout with full-K-stride loads across 16 rows

Each optimization compounds: removing A from LDS enables full-B staging, which halves barriers. Preconverting scales removes per-block FP16→FP32. Tile-major A eliminates strided loads. The exact-shape kernel eliminates all generic overhead.

## Phase discipline

Do NOT skip Phase 1-3 and go straight to the optimized design. hipEngine did exactly that and got a 44% regression. Each Phase 4 optimization is independently tested and discarded if it doesn't beat baseline. The first concrete kernel to ship is whichever combination of optimizations actually won.

## Kernel Architecture

### Target
- gfx1100 only (RX 7900 XTX — 96 CUs, wave32, 128 KiB LDS/CU, 6 MiB L2)
- --offload-arch=gfx1100 with compile-time architecture guard:
  ```cpp
  #if !defined(__gfx1100__)
  #error "This kernel is only valid for gfx1100"
  #endif
  ```

### Work Decomposition
- 256-thread workgroup = 8 wave32s
- Each workgroup computes one 128×128 output tile
- Each wave computes 16 rows × 128 columns = eight independent 16×16 WMMA fragments
- Launch: M tiles = 6144/128 = 48, N tiles = 512/128 = 4 → 192 workgroups
- 1D grid with shift/mask decomposition:
  ```cpp
  tile_n = blockIdx.x & 3u; tile_m = blockIdx.x >> 2;
  m0 = tile_m << 7; n0 = tile_n << 7;
  tid = threadIdx.x; wave = tid >> 5; lane = tid & 31u;
  lane16 = lane & 15u; half = lane >> 4;
  ```

### Data Representation
- **A (weights):** Separate quant/scale planes in tile-major order:
  ```cpp
  struct alignas(16) Gfx1100Q8Fragment {
      i32x4 k0_15;   // 16 packed signed int8
      i32x4 k16_31;  // 16 packed signed int8
  };
  ```
  Layout: [m_tile][k_tile][k32][wave][row16]
  FP16 scales preconverted to FP32 at model load.

- **B (activations):** Tile-major Q8_1 with N=128, K=256:
  Each tile = 32,768 bytes (quants) + 4,096 bytes (FP32 scales) = 36,864 bytes
  Total B = 4 N tiles × 20 K tiles × 36,864 bytes = ~2.8 MiB (fits in L2)

### LDS Design
- **Remove A from LDS** — load directly into VGPR fragments
- **Full B K=256 tile in LDS** — 36,864 bytes per tile
- Two resident workgroups consume only 73,728 bytes of LDS (well under 128 KiB)
- Reduces barriers from 4 to 2 per K=256 (80 → 40 total for K=5120)
- Cooperative B loading: exactly 9 aligned 16-byte vectors per thread

### WMMA Execution
- Direct __builtin_amdgcn_wmma_i32_16x16x16_iu8_w32 — two calls per K=32
- Mirrored RDNA3 input fragments (Candidate A: load twice, or B: half-wave + shuffle)
- Eight named f32x8 accumulator vectors (not dynamically indexed arrays)
- WMMA result converted once: __builtin_convertvector(ci, f32x8)

### Scale Handling
- B scale vector loaded in WMMA accumulator order: one A scale × eight B scales per fragment
- Preloaded in FP32; no FP16-to-FP32 conversion in hot loop

### Register Strategy
- __launch_bounds__(256, 2) for two-block occupancy (primary)
- __launch_bounds__(256, 1) and __launch_bounds__(512, 1) as variants
- Hard requirement: private segment = 0, VGPR spills = 0, SGPR spills = 0

### Kernel Arguments (four pointers only)
```
cost AFragment * __restrict__ a_quants;
const float     * __restrict__ a_scales;
const u32x4     * __restrict__ b_tiles;
float           * __restrict__ dst;
```

## Why a new family, not another MMQ candidate

MMQ varies one dimension (J) over the same kernel body. Cherrypips is an entirely different kernel with:
- Different data layout (tile-major prepacked vs row-major interleaved)
- Different memory access pattern (direct VGPR loads vs LDS staging)
- Different scale representation (FP32 plane vs FP16 inline)
- Different activation quantization path (prepacked B tiles vs on-the-fly)

Adding this as another J value in the MMQ config table would mean threading prepack buffers, repacked pointers, and entirely new launch logic through mul_mat_q — which is architecturally wrong. The kernel does not share its body, its data movement, or its contract with any other MMQ candidate.
