# Root-cause and fix: mmvq:q8_0:w4:nw8:rpb1:sk0:v1 degrades MTP draft acceptance after long prefill (93.5%->62%)

## Description

Real HI136/HI121 real-hardware validation (2026-08-29, dual RX 7900 XTX, Qwen3.8-27B-Q8_0) found a genuine, deterministic, reproducible performance regression: under production MTP speculative decoding (--spec-type draft-mtp), the decode segment immediately following a 4096-token prefill shows MTP draft acceptance dropping from 93.5% (native dispatch) to 62.1% (tuned/replay dispatch) -- confirmed with temperature=0/seed=42 (bit-identical accept/generate counts across 5 reps both legs, so not sampling noise), and confirmed as NEW relative to a prior clean 4-way baseline (vanilla llama.cpp / bc-native / bc-replay-native / bc-replay-tuned, all matching within noise, draft_acceptance=0.9346 identical across all four, documented in HI130.md 2026-08-27) that used a smaller/different promoted-candidate set. Every OTHER benchmark scenario (pp256/pp1024/pp4096 prefill throughput, tg512/tg2048 steady-state decode) shows tuned dispatch equal-to-or-better than native -- this is narrowly scoped to decode-right-after-a-large-prefill.

Binary-search candidate ablation (real hardware, real GGML_HIP_DISPATCH cache rebuilds, real mtp-dual server-bench runs) fully localized the cause to the `mmvq:q8_0:w4:*` candidate family (3 variants: nw4:rpb4:sk1, nw8:rpb1:sk0, nw8:rpb2:sk0). The w1/w2 mmvq family, the w5 mmvq family, and the one mmvf candidate were all independently confirmed clean.

## Steps

1. Identify the ROOT CAUSE, not just correlation: read the actual kernel source for the mmvq w4 candidate variant (warp/workgroup-size parameter w=4) and determine what is numerically different from native and from the clean w1/w2/w5 variants at this warp-size configuration -- candidates: warp-size-dependent reduction/accumulation order causing larger floating-point summation error, an edge case when input dimensions do not evenly divide by w=4, or a gap in HI67's correctness-evidence seed sampling not exercising this real long-context/post-prefill numerical regime.
2. Narrow within the w4 family if useful: ablate each of the 3 w4 variants (nw4:rpb4:sk1, nw8:rpb1:sk0, nw8:rpb2:sk0) individually to see if all three are implicated or only a subset.
3. Decide and implement the fix: (a) real numerical fix to the implicated kernel if a genuine bug is found, (b) exclude the implicated w4 candidate(s) from promotion/dispatch for this op/shape via the existing candidate-exclusion mechanism (made durable), or (c) tighten HI67's correctness-evidence gate if a real coverage gap is revealed.
4. Re-run the full mtp-dual benchmark (raw llama-bench + run_bench.py server-bench, 5+ reps) after the fix to confirm tg128 recovers to native-parity with no new regression.
5. Archive the full investigation as an evidence bundle under docs/evidence/2026-08-29-hi136-mtp-acceptance-regression/ (raw receipt JSONs, ablation cache manifests, bench logs, candidate lists) per the existing docs/evidence/2026-08-27-dual-xtx-tune-run/README.md convention, and record the final root-cause explanation and fix in this item's notes -- both WHAT was wrong and WHY it happened.

MAJOR ROOT-CAUSE LEAD (2026-08-29, immediately after w4/w5 localization): read the actual mmvq.cu/mmvq-autotune.cuh source. The candidate name's `w<N>` is NOT warp-related at all -- it is the `width` template parameter, which IS `ncols_dst` (confirmed via mmvq.cu:559's static_assert message "bigcherry: MMVQ width out of bounds" bounding it against MMVQ_MAX_BATCH_SIZE, and mmvq-autotune.cuh's own template signature `template <ggml_type type, int width, int nwarps, int rows_per_block, bool small_k>`). ncols_dst is the BATCH WIDTH -- how many destination columns (real-world: how many tokens' worth of matvec work) one kernel launch processes together.

This is a structural, not coincidental, match to the production launch flags: `--spec-draft-n-max 4` means MTP speculative decoding naturally submits verification batches of up to 4 draft tokens (plus the real token being verified against = up to 5 total) per decode step. The w4/w5 candidates are EXACTLY the batch-width kernels MTP's own draft/verify mechanism would predominantly dispatch through -- not an arbitrary unlucky pair out of 5 width buckets (w1/w2/w4/w5 were the widths present in this campaign's promoted set). w1/w2 (clean) correspond to batch widths MTP essentially never produces (single-token steady decode uses width=1, matching tg512/tg2048's own clean steady-state result, which is consistent: those tests are NOT under MTP verification batching pressure the way the pp4096-then-decode segment is, since draft acceptance/rejection patterns and batch composition differ there too).

Working hypothesis, NOT yet verified: a real indexing/correctness bug in the batched MUL_MAT_VEC_Q kernel specific to ncols_dst=4 or 5 (off-by-one, incorrect column-stride, shared-memory sizing, or similar), that HI67's correctness-evidence gate's per-signature seed-sampling harness never exercised at these exact multi-column batch shapes in a way that surfaces the bug (isolated microbenchmark correctness tests may not replicate the real ids/fusion/stride shapes a live MTP verify call passes). This would mean the bug is NOT a subtle floating-point tolerance issue as originally hypothesized (teacher-forced test showed ordinary decode logits tracking closely) but a real, width-specific batched-kernel defect that only manifests under the exact batch shape MTP produces -- worth checking whether HI67's correctness-evidence generation ever tests ncols_dst>1 batched dispatch shapes at all, or only ncols_dst=1 single-token correctness, which would be a real, structural gap in the correctness-evidence methodology, not just a bug in one candidate.

Next concrete step: read get_vec_dot_q_cuda / the actual per-thread column-indexing logic in mul_mat_vec_q's body (mmvq.cu, the loop after line ~570) for how row/column indices are computed as a function of ncols_dst, and check HI67's correctness-evidence generation code (hi80_generate_correctness_evidence.py or equivalent, referenced elsewhere in this session) for what ncols_dst value(s) its test vectors actually use.

CORRECTION to the earlier "correctness gate never tested this width" hypothesis (2026-08-29, immediately after posting it): checked directly via SQL against tune.sqlite. The actual w4-winning signature's recorded canonical_json is real: `ne1: [5120, 4, 1, 1]` -- a genuine, real batch-width-4 MUL_MAT (5120 = hidden dim / k, 4 = the real ncols_dst / MTP batch width). Since HI67's correctness-evidence mapper (signature_to_test_file_line in tools/bigcherry/tuning/signature_mapping.py) derives its test-file shape directly from this same signature record's own ne0/ne1/ned fields, it DID test the real width=4 shape when certifying this candidate, and it PASSED (promotion_status="promoted", real NMSE-bounded correctness evidence, not a coverage gap). So the earlier "correctness gate skipped batch>1" theory is ruled out.

Revised working hypothesis: a small, real, WITHIN-NMSE-TOLERANCE numeric difference in the w4 kernel (larger or differently distributed than in the unused-by-MTP w1/w2 variants) that is legitimate by HI67's own correctness contract, but occasionally flips a close top-1/top-2 argmax decision during MTP's real verify step -- consistent with the earlier teacher-forced logit-divergence test (separate diagnostic, same investigation) which found real but small (~0.01-0.03 logprob) native-vs-tuned differences, not gross errors. Also worth reframing: w1/w2 being "clean" under ablation may not mean they are MORE correct -- MTP's own verify mechanism always submits multi-token batches (matching w4/w5's width), so w1/w2 (width=1) may simply be barely EXERCISED by real MTP decode regardless of their own correctness, making their ablation a near-no-op rather than positive evidence of their own numeric quality.

GPT ROOT-CAUSE VERDICT (2026-08-29, fresh session req_c380583d0eb64284 after the prior session stalled/failed):

**Mechanism (plausible, not yet fully proven)**: at temp=0, MTP speculative verification effectively requires exact target-argmax==drafted-token agreement along the speculative prefix -- the first changed greedy top-1 terminates the accepted prefix, and every later drafted token in that batch loses its compute-saving value. Ordinary greedy decoding has no equivalent multiplier (an argmax flip just changes the output sequence, it doesn't collapse a whole batch's acceptance). So a small ~0.01-0.03 logit perturbation (the scale found in this investigation's earlier teacher-forced diagnostic) can plausibly produce the observed ~25% tg loss if enough decode positions carry a small top1/top2 margin. Still needs direct confirmation via an accepted-tokens/draft histogram (llama.cpp's speculative machinery already tracks this) comparing native vs w4.

**Remediation, explicit order**:
1. Immediate containment: quarantine mmvq:q8_0:w4:* promotion. Do NOT touch w5 -- confirmed clean and load-bearing (real production traffic uses it too).
2. Split the 3 individual w4 variants (nw8:rpb1:sk0, nw8:rpb2:sk0, nw4:rpb4:sk1) -- required before any permanent decision, cheap relative to the information gained. NOT YET DONE.
3. Run a small MTP diagnostic recording tg128 AND accepted-tokens/draft + accepted-prefix histogram (not just aggregate throughput).
4. Differential-test whichever variant(s) reproduce the regression against __bigcherry_native__ on the EXACT width=4 input, reporting PER-COLUMN error, not aggregate NMSE (aggregate NMSE cannot catch one bad column).
5. Decide fix from that: geometry-specific kernel bug (if isolated to one variant) vs. a real gap in HI67's correctness contract for batched (ncols_dst>1) MMVQ (if all three show similarly small, smooth errors concentrated around close decisions) -- in the latter case HI67 should eventually gain worst-column NMSE, per-column max-abs/normalized error, and a speculative-acceptance/performance gate for MTP-relevant widths, IN ADDITION to today's aggregate NMSE (not a replacement).

**Explicitly rejected as the fix**: tightening aggregate NMSE tolerance as the primary remediation -- gpt was clear this cannot protect against a single bad column/decision-critical localized error.

Interpretation guide for the individual-variant split (not yet run): one candidate bad -> geometry-specific defect; both nw8:* bad, nw4:* clean -> nwarps=8/reduction-partition suspect; only nw4:rpb4:sk1 bad -> rpb/small-k path suspect; all three bad with similarly small/smooth errors -> HI67 contract gap, not a kernel bug.

Next concrete step (about to execute): individual ablation of the 3 w4 variants via the same real-hardware cache-rebuild + mtp-dual methodology already used for the family-level localization.

Only ONE of the 3 w4 candidates is responsible. Per gpt's own interpretation guide ("one candidate bad -> geometry-specific defect"), this rules out a systemic width=4/ncols_dst=4 numerical-drift explanation and points to a genuine, narrow kernel defect specific to the exact geometry combination width=4, nwarps=8, rows_per_block=1, small_k=0 -- notably the ONLY difference from the clean nw8:rpb2:sk0 sibling is rows_per_block (1 vs 2), which narrows the suspect surface considerably: whatever this kernel does differently when handling exactly 1 output row per CUDA block (vs 2) at nwarps=8/width=4 is the immediate area to inspect (mul_mat_vec_q's body in ggml/src/ggml-cuda/mmvq.cu, the row-indexing/reduction logic parameterized by rows_per_cuda_block).

Updated remediation per this sharper localization: immediate containment should now be scoped to excluding ONLY mmvq:q8_0:w4:nw8:rpb1:sk0:v1 from promotion (not the whole w4 family) -- the sibling nw8:rpb2:sk0 and nw4:rpb4:sk1 are confirmed clean and should NOT be penalized by an overly-broad exclusion. Root-cause reading of mul_mat_vec_q's rows_per_cuda_block-parameterized logic (mmvq.cu) for what specifically breaks at rows_per_block=1 (vs 2) is the concrete next step, not yet done. WHY THIS CANDIDATE WAS PROMOTED (2026-08-29, direct answer to user question): checked the actual tune-time measurement for mmvq:q8_0:w4:nw8:rpb1:sk0:v1 from promoted.jsonl. It measured genuinely faster than native (7.976us vs 10.344us effective, ~23% real latency win) AND essentially numerically perfect for the tested inputs: nmse=5.4723e-15 (machine-epsilon level), max_abs=9.53674e-07 (float32 rounding noise). This was not a borderline promotion -- by every metric the tuning pipeline checks, this candidate looked like a clean, safe win. Native's own comparison entry in the same row: nmse=0, effective_us=10.344 (15 real samples, tight distribution).

DIRECT ANSWER: no, today's tuning methodology could not have caught this at tune time, and this is a real, structural gap rather than a process failure by any one step. The correctness-evidence check only exercises a handful of seeded/synthetic reference inputs per signature (HI67's contract) -- it does not, and structurally cannot, cover the full space of real activation values a live model produces during actual generation. This candidate's apparent defect (not yet proven to be a bug vs. rare legitimate numeric edge case -- see the still-pending per-column differential test) is consistent with being triggered by specific real data patterns that simply never appeared among the correctness-evidence's small sample set, not a general/average correctness problem the aggregate NMSE metric is built to catch. A candidate can be genuinely, measurably perfect against every input the tuner tried and still be wrong on inputs it never tried.

Structural fix implications (do not attempt as an ad-hoc patch to this one candidate -- these are real HI67/tuning-pipeline design questions, consistent with gpt's own remediation guidance above): (a) an end-to-end speculative-decoding acceptance-rate regression check as part of promotion for MTP-relevant candidates -- i.e., actually exercising the real generation pipeline's behavior, not just isolated per-dispatch kernel numerics, before promoting; and/or (b) correctness-evidence generation against real captured production activation values (from an actual model forward pass) rather than purely synthetic/seeded reference inputs, so rare real-world data patterns have a chance of being exercised. Both are substantial additions to the tuning pipeline's design, not quick fixes, and should be scoped as their own follow-up item(s) once this specific candidate's root cause is confirmed (still pending: per-column differential test against native at the real width=4 input, and the accepted-tokens/draft histogram gpt specified).
