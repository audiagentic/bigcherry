# Root-cause mmq_types=[] while MMQ carries 27% of real dispatches

## Description

The tuning inventory for campaign 27e45ae32ec4 records mmvq_types=['q8_0'], mmvf_types=['f32'], mmq_types=[] and mmf_types=[]. The real benchmark workload on the same profile executes 51,456 MMQ dispatches -- 27% of 190,950 total matmul dispatches, all of them reaching the dispatch layer (dispatched == executed for the family).

So a quarter of the workload has no tuned candidates, and no amount of dispatch-path optimisation can improve it.

WHAT THE INVENTORY ACTUALLY MEANS. catalog.py's Inventory docstring is explicit: these are 'Observed types and paths from a RECORD-MODE run', and the float_types property records the same phenomenon on this exact profile -- 'On the 27B MTP profile mmf_types came back empty -- native never chose MMF'. So mmq_types=[] is not an exclusion or a filter; it is a statement that the RECORD run never executed an MMQ operation.

That points at a workload mismatch between the record stage and the workload being served, rather than at a missing candidate family. The two runs are not the same shape mix:
  - production-dual-xtx sets tune-context=4096, --ubatch-size 512, --batch-size 2048.
  - The benchmark (mtp-dual) runs pp256/pp1024/pp4096 as well as tg128/512/2048. Prefill at ubatch 512 gives large ne11, which is where native selects MMQ; decode at ne11~1-16 is where it selects MMVQ.

If the record stage is decode-dominated, MMQ signatures never enter the inventory, so no MMQ signature is ever tuned -- regardless of whether MMQ candidates could be generated. Note quant_types deliberately unions mmq_types|mmvq_types so MMQ CANDIDATES may still exist; what is missing is observed MMQ SIGNATURES to tune them against.

## Detailed Solution & Technical Design

ROOT CAUSE (confirmed): `_stage_record` in tools/bigcherry/tuning/workflow.py drove the record-mode server with a single short (~15-token) decode-shaped smoke prompt. Native dispatch selects MMQ only for large-ne11 (prefill-shaped) work and MMVQ for small ne11 (decode, ne11~1-16) -- a short prompt with n_predict=96 never produces a prefill dispatch large enough to cross that threshold, so MMQ signatures never entered the record run's raw observation data, and therefore never entered the inventory, regardless of whether MMQ candidates could be generated for them.

FIX IMPLEMENTED (dev-gpt-agent review req_bcf8417d476b435f, then implemented and validated on real hardware): `_stage_record` now issues the original short smoke prompt (kept -- still the right shape for decode/mmvq signature discovery) PLUS a discovery sweep of three synthetic, deterministic prefill-shaped prompts (~256/~1024/~4096 words, `_RECORD_DISCOVERY_WORD_COUNTS` / `_synthetic_prefill_prompt()`), each with small n_predict=8 (this is about exercising the prefill dispatch, not generation length). Deterministic repeated-word construction, not natural-language approximation, per GPT's recommendation -- exact token count isn't achievable without a tokenizer at this call site, so this is a deliberately generous envelope, verified empirically (not assumed from length alone).

SCOPE, deliberately narrow per GPT review (confidence 0.99 on this specific point): `_stage_tune` (the tune-mode stage that MEASURES candidates, distinct from record's job of DISCOVERING signatures) was deliberately left UNCHANGED. HI166 (ordered per-step acceptance trace equality) explicitly gates broadening what gets TUNED/measured -- fixing record-only DISCOVERY does not activate new MMQ tuning by itself (no MMQ candidate was measured, promoted, or otherwise entered the tuning/promotion pipeline by this change), but widening tune's own measurement workload to actually exercise MMQ candidates would be exactly the kind of tuning-coverage expansion HI166 must land before. That is explicitly NOT done here and is follow-up work gated behind HI166, not part of this item's fix.
