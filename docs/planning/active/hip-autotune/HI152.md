# revision-bound patch coverage/disposition schema + gate

## Description

Second HI150 sub-item. A `patch-rebase-check --all` report today has no notion of an accepted, revision-bound reason a non-recipe patch is allowed to stay broken -- HI149 (the RD13 false alarm) showed the gap this closes, even though that specific instance wasn't actually broken.

Design (converged with gpt, see HI150 notes):
- A disposition record per (patch_id, target_revision, patch_digest): {patch_id, target_revision, patch_digest, disposition: "known_broken", failure_status, reason, owner, tracking_item}. Stored where release-record-adjacent-but-not-a-ReleaseRecord artifacts live (artifacts/pin-bump/... per HI150, NOT releases/*.json -- avoids the exact class of bug fixed in records.py this session).
- Disposition is invalidated the instant target_revision or patch_digest changes -- it is never a standing waiver.
- Do NOT add a new patch lifecycle STATE (gpt's correction, accepted) -- lifecycle states (validated/untested/rejected) are patch identity; rebase failures are revision-specific facts, kept separate.
- Coverage completion policy: recipe-selected patch -> must be CLEAN/CLEAN_NOOP/NOT_APPLICABLE_BY_DESIGN, no escape hatch; non-selected patch -> clean OR a matching known_broken disposition; rejected patch -> excluded but reported; anything undiscovered/untriaged -> STOP.
- Coverage invariant: discovered_patch_ids (from --all) == checked_patch_ids UNION explicit rejected exclusions UNION known_broken-dispositioned ids.

## Steps

1. Add a small schema/module (e.g. tools/bigcherry/patch/disposition.py): load/save/validate disposition records, a function computing coverage.complete against a patch-rebase-check --all report + a disposition set.
2. Extend patch-rebase-check's --json output (or a wrapping report) with the `coverage` block (discovered_patch_ids, checked_patch_ids, excluded, uncovered_patch_ids, complete) as gpt proposed.
3. CLI surface: a way to record a disposition (e.g. `bigcherry patch-disposition set --patch-id ... --revision ... --reason ... --owner ... --tracking-item ...`), and a way to list/clear them.
4. Unit tests: coverage.complete true/false cases, disposition invalidated by revision or digest change, recipe-selected patch never gets an escape hatch even with a matching disposition record.
