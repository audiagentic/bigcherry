# Windows/WDDM measurement hardening — unblocked sweeps poison on transient fatal failures

## Description

On the local Windows workstation (WDDM), full unblocked HIP tuning sweeps hit transient fatal measurement failures that poison the whole experiment: both an ON and a matched OFF run of Slice A died at different random stages with identical failure modes, proving the flake is environmental, not caused by the double-native twin. Evidence collection therefore had to use HIP_LAUNCH_BLOCKING=1, which serializes launches and makes blocked-run timings non-authoritative (accepted for Slice A's local gate; production-architecture validation on Brutus/Linux remains the unblocked evidence gate).

The failure is a SUSPECTED transient WDDM/TDR-class measurement error inside hipEvent timing — classification against the actual driver error code is step 1 of this item, not an assumption. The current policy treats any launch/timing failure as global poison, which is correct in principle but means one transient driver hiccup discards an entire multi-hour sweep with no retry or quarantine of the affected signature.

## Steps

- Reproduce unblocked: run a full sweep without HIP_LAUNCH_BLOCKING=1 on the workstation and capture the fatal-failure class (TDR/event error code) from the log.
- Classify transient vs permanent failure modes at the hipEvent/launch layer.
- Add bounded retry with backoff for the transient class only; permanent failures keep poisoning (standards: a wrong measurement is worse than no measurement).
- Record the retry/recovery in the journal JSONL so poisoned-vs-recovered runs are distinguishable in artifacts.
- Verify: an unblocked sweep completes on the workstation, or fails with a classified permanent error, and the OFF/ON parity still holds under verify_slice_a.py.

### 2026-08-22: item (4) generation-keyed recovery -- resolved as not implementable today, by design, not a gap

Investigated whether a genuine "HIP context/device execution generation was recreated" signal exists anywhere in the real backend, per GPT's own instruction (req_559bb03e75494a74): "If the current llama.cpp backend cannot genuinely recreate that state within one process, do not fake this test. Leave that acceptance point open until there is a real lifecycle seam."

Finding, conclusive: **`hipDeviceReset()`/`cudaDeviceReset()` is called nowhere in the entire vendored ggml-cuda backend -- not in bigcherry's own additions, and not in upstream llama.cpp's own code either** (grepped every .cu/.cuh/.cpp/.h under ggml/src/ggml-cuda/; the only hit is hip-autotune-tuner.cu's own comment documenting its absence). `ggml_backend_cuda_init(device)`/`ggml_backend_cuda_free()` (ggml-cuda.cu:5903-5922, :2679-2691) create/destroy a `ggml_backend_cuda_context` C++ wrapper object, but that constructor does nothing to the underlying HIP driver-level primary context for the device -- no reset, no explicit context creation. A HIP/CUDA primary context is a process-wide singleton, lazily created on first use and torn down only by `hipDeviceReset()` or process exit; nothing in this backend, upstream or bigcherry, ever calls the former.

Consequence: a genuinely faulted/poisoned device's underlying driver state cannot be proven recreated within a running process by ANY observable signal this backend exposes today -- not because bigcherry hasn't wired one up yet, but because the signal itself does not exist anywhere in llama.cpp's HIP backend architecture. Inventing one would mean either (a) calling `hipDeviceReset()` from the tuner, which GPT's requirement (3) and this item's own tests explicitly forbid (would invalidate llama.cpp's own live allocations on that device), or (b) adding new lifecycle machinery to ggml-cuda.cu itself that upstream does not have and has given no indication it wants -- out of scope for a bigcherry hardening patch.

**Resolution: item (4) is closed as "not implementable given the real backend architecture", not left open as a TODO.** Poison-until-process-exit (per-device, scoped by the 2026-08-21 fix) is therefore not a stopgap awaiting a follow-up -- it is the correct, final design given that no safe in-process recovery boundary exists. Revisit ONLY if upstream llama.cpp's HIP backend itself ever gains genuine context-recreation semantics (e.g. a real per-device teardown/recreate lifecycle exposed to backends) -- there is no such proposal upstream as of this writing.

### 2026-08-22: REAL HARDWARE FINDING -- per-device scoping alone was not sufficient, second defect found and fixed

Real dual-XTX fault-injection validation (per GPT's design, req_559bb03e75494a74) found that a fault injected on the FIRST-processed device also silently poisoned the SECOND device's tuning, even though PerDeviceState's own storage was correctly per-device. Root cause (GPT's diagnosis, req_c6a1d50e4f8b4d20, confirmed against real source line-by-line before implementing): NOT a PerDeviceState bug. hip-autotune-dispatch.cu's `g_bindings` (process-global, keyed only by the portable, device-ordinal-free dispatch_digest -- deliberately shared so identical GPUs can reuse a winner, standards 10.2) and hip-autotune-tuner.cu's `g_results` (same portable key) both let a device-local FAILURE masquerade as a portable resolution: the first device's poisoned attempt got cached in both maps via blind emplace() BEFORE the tune-mode branch / before the per-device poison check, so a second device hitting the same key never even reached its own g_tuner_poisoned check -- it short-circuited on the first device's failure.

Fix (GPT's design, req_a83f4d26c42e492a, one commit): `ggml_hip_tuner_resolve()`'s public contract changed from a bare `const ggml_hip_candidate_descriptor *` to a new `ggml_hip_tuner_resolution { winner; measurement_failure; }` struct (implemented via a thin wrapper around a renamed `ggml_hip_tuner_resolve_impl()`, avoiding touching ~25 scattered exit sites while preserving the exact same external contract). `record_result()` now does failure->success replacement (a failed g_results entry is retained only as fallback evidence until a healthy device's real measurement replaces it; a success is never replaced by a later failure). The impl's g_results cache-hit check now excludes failed entries. dispatch.cu gates the process-global g_bindings.emplace() on a new `process_binding_cacheable` flag (false for both a tuner measurement_failure AND a capture-time tuning skip -- a related pre-existing leak fixed in the same change); the per-device/thread g_thread_bindings.insert() stays completely unconditional, matching the intended split (device-local failure evidence stays local; only genuinely portable results become process-global). No change to hardware/dispatch identity (still correctly device-ordinal-free) -- the fix is about WHAT gets cached, not WHERE.

Verified: 9 new source-contract tests, full offline suite 1555 passed. Real compiler build on Brutus, zero errors. Re-ran the exact fault-injection test that exposed the bug (12 MUL_MAT q4_0 shapes, dual real XTX, GGML_HIP_TUNE_TEST_FAIL_CANDIDATE/STAGE) both device orders (0,1 and 1,0): canonical measurements.jsonl now shows all 12 shapes measurement_failure=false (identical to the clean baseline) on BOTH runs; the journal correctly preserves 12 real failure rows (device 0's poisoned attempts, historical evidence, not erased) PLUS 12 real success rows (device 1's actual measurements) -- exactly the intended state machine. This is genuinely hardware-validated now, not merely structurally sound.

### 2026-08-22: REAL HARDWARE FINDING + FIX -- cross-device poison leak via shared portable caches (commits 2c32c7d, follow-up below)

Real dual-XTX fault-injection validation found that per-device PerDeviceState scoping (5e03cb4) alone was not sufficient: a fault on the first-processed device also silently poisoned the second device's tuning. Root cause (GPT-diagnosed, confirmed against real source line-by-line): dispatch.cu's process-global `g_bindings` and tuner.cu's process-global `g_results` -- both deliberately keyed WITHOUT a device dimension so identical GPUs can share a winner, standards 10.2 -- let a device-local FAILURE masquerade as a portable resolution, short-circuiting a second device before it ever reached its own poison check.

Fix: `ggml_hip_tuner_resolve()` now returns `ggml_hip_tuner_resolution { winner; measurement_failure }` (via a thin wrapper around a renamed `ggml_hip_tuner_resolve_impl()`, avoiding touching ~25 scattered exit sites). `record_result()` only lets a non-failed result replace a failed one for the same portable key, never the reverse. The impl's g_results cache-hit check excludes failed entries. dispatch.cu gates the process-global `g_bindings.emplace()` on a new `process_binding_cacheable` flag (false for both a tuner failure and a capture-time skip); `g_thread_bindings.insert()` stays unconditional for a failure (still useful locally) but is now ALSO gated by a separate `thread_binding_cacheable` flag for the capture-skip case specifically (GPT follow-up review caught that unconditionally caching native during a capture-time skip would permanently starve that (thread,device,signature) triple even after capture ends, since capture -- unlike a fatal failure -- is not a permanent condition).

GPT follow-up review also caught a real concurrency race in the first version of the fix: the single-flight lock was acquired inside the impl and released before the wrapper's own g_results re-check, leaving a window where a second thread's failure->success replacement could land in between, making the wrapper report a stale measurement_failure value for an invocation that actually failed. Fixed by moving g_single_flight_mutex acquisition to the wrapper, held across both the impl call and the re-check.

Verified: 13 new/updated source-contract tests (9 initial + 4 follow-up), full offline suite 1558 passed. Real compiler builds on Brutus, zero errors, twice (initial fix + follow-up fixes). Re-ran the exact fault-injection test that exposed the bug three times total (initial fix, both device orders; follow-up fixes, re-confirmation): canonical measurements.jsonl always shows all 12 shapes clean (measurement_failure=false, matching the no-injection baseline); the journal always correctly preserves 12 real failure rows (historical evidence) + 12 real success rows (the eventual healthy measurement) -- the intended state machine, confirmed stable across both the original fix and the concurrency/capture-skip follow-up.
