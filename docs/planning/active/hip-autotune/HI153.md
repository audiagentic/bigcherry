# bigcherry pin-bump: single-tree orchestrator command

## Description

Third HI150 sub-item, depends on HI151 (lease/lock) and HI152 (coverage/disposition). The actual `bigcherry pin-bump <target>` command: a single-tree state machine over the existing verbs (repin/pull/audit/patch-lint/patch-rebase-check/apply/pin-status), stopping cleanly with a structured JSON failure envelope on anything not provably safe to auto-proceed past, per the converged HI150 design. Multi-tree SSH sequencing is explicitly OUT of scope here (deferred to a later Phase 2 item, not created yet).

## Steps

1. Acquire the HI151 maintenance lock (refuse if a live lease exists) before any mutation.
2. Preflight: resolve target ref -> exact SHA, require clean controller checkout, detect/refuse an incompatible existing transition marker.
3. Declare: call repin, verify only intended pin/marker state changed, commit config/recipes.toml + releases/pin-transition.json together.
4. Pipeline: pull -> audit -> (if audit fails ONLY on overlay.vendor_sync with every drifted file overlay-owned/not-upstream-tracked/UTF-8/newline-only-different per HI150's narrow rule, self-heal via the existing overlay-copy path and re-audit; otherwise STOP) -> patch-lint -> patch-rebase-check --all (coverage report, gated by HI152's coverage.complete) -> patch-rebase-check --recipe (build-selection report) -> apply --rebase-report <recipe-report> --known-good (never apply the --all report) -> re-audit.
5. Structured failure envelope on every STOP (schema_version, operation, run_id, target, transition_commit, phase, tree, failure{code,human_required,retryable,summary,evidence,recommended_actions}, resume{completed_phases,next_phase}, artifacts[]) written under artifacts/pin-bump/<run_id>/.
6. --resume support: read back the run's state file and continue from next_phase rather than restarting.
7. On success: print a clear PASS summary; multi-tree completion still requires a human to run `bigcherry pin-status --complete --all-remotes` afterward (that gate already exists and is sufficient, no change needed there).

LIVE FIRE-TEST SUCCEEDED 2026-08-30: bigcherry pin-bump b10687 (from b10680) completed end to end for the first time, independently reverified via `bigcherry pin-status` (consistent, patched) and `bigcherry audit` (34/34).

Three real bugs found and fixed by this one live run, in order encountered:
1. acquire_maintenance_lock() called .acquire() itself AND was used as `with acquire_maintenance_lock(...)`, whose __enter__ also acquires -- guaranteed double-acquire, tripped its own lock before any real work. Fixed: helper now returns an unacquired lock.
2. patch-rebase-check --all crashed uncaught (bigcherry.patch.rebase.RebaseCheckError, unhandled) the instant the registry contained two intentional alternative candidates (1205 vs 1207) -- a permanent, by-design registry feature, not a transient state. Real, deeper fix in rebase.py: `--all` now partitions non-rejected patches into conflict-free groups (_partition_conflict_free), probes each group in its own isolated worktree via the existing quarantine_fixed_point, and merges results; cross-group REQUIRES satisfied via resolve_exact's existing context_ids. Two real coverage findings surfaced once this worked: 1201 (RD20, already confirmed superseded) and 1215/1216/1217 (RD39-44, a real anchor break in common.cuh's cublas_handle signature) -- both handled via real `patch-disposition set` records, not silently waived.
3. The audit phase computed its result purely in-memory and never persisted it to the ReleaseRecord (record.audit) the way cli/source.py's cmd_audit does -- so apply_known_good's own admission gate (which reads the PERSISTED record, not this run's in-memory report) never saw a pass and refused every real run. Fixed: audit phase now updates+saves the ReleaseRecord itself.

Also observed (not fixed, self-inflicted by iterating on the tool mid-run rather than a design flaw needing action now): apply's stale-report guard correctly fired when my own commits between the coverage and apply phases moved the bound bigcherry_revision -- correct fail-closed behavistribution, not a bug, but confirms `apply` currently trusts a possibly-stale `coverage`-phase artifact without re-checking freshness itself; worth a note for anyone hitting it in real (not self-inflicted) usage: roll state.json's next_phase back to 'coverage' and --resume.

HI153 is now genuinely proven, not just unit-tested. Full end-to-end integration test coverage (a synthetic-fixture test of run() itself) is still not written -- this live run is real evidence the composition works, but doesn't replace an automated regression test for it.
