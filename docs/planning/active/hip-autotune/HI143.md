# Detect real-data-triggered candidate defects during tuning, not post-hoc (HI141 methodology gap)

## Description

HI141 found a real production regression (mmvq:q8_0:w4:nw8:rpb1:sk0:v1 collapsing MTP draft acceptance from 93.5% to 62.1%) caused by a candidate that measured as essentially numerically perfect (nmse=5.47e-15, machine-epsilon) against HI67's correctness-evidence gate at tune time, and was a genuine, real 23% latency win (7.976us vs native's 10.344us) -- by every metric the tuning pipeline checks today, this was a clean, safe promotion. The defect only manifested against real production data during actual MTP decoding, discovered only via a full end-to-end real-hardware regression hunt after the fact, not by the tuning/correctness pipeline itself.

Root structural gap (confirmed via direct source read, tools/bigcherry/tuning/correctness_evidence.py's collect_seed_evidence()): correctness evidence is generated by running test-backend-ops with an integer --seed that fills test tensors with SYNTHETIC RANDOM DATA (test-backend-ops' own RNG-seeded fill), not real captured model weights or real activations from an actual forward pass. Only 3 seeds are checked per candidate. This proves 'correct for 3 random draws of synthetic noise,' not 'correct for the data this model will actually produce.' Real quantized weights have specific statistical structure (block-wise quantization scales, particular value distributions) that uniform random fill does not replicate -- a candidate defect triggered by a real-data-specific pattern (a dequantization edge case, a boundary condition, a specific bit pattern) has no particular reason to ever be hit by random seeds, no matter how many tuning runs are repeated. There is also no feedback loop today from real end-to-end generation behavior (e.g. MTP speculative-decoding acceptance rate) back into what gets promoted -- promotion is decided entirely from isolated per-op latency + synthetic-seed NMSE.

Goal: detect this CLASS of failure (a candidate that is fast and passes synthetic correctness evidence but degrades real model behavior) DURING the tuning/promotion pipeline itself, as a first-class gate, not as a post-hoc discovery requiring a full manual real-hardware investigation like HI141's.

## Mandatory promotion path

synthetic correctness (existing HI67) -> local latency promotion (existing) -> multi-vector real-workload behavioral gate (NEW, this item)

No provisional winner reaches production promotion without passing all three.

## Behavioral gate mechanism

For each provisional (non-native) winner relevant to a real corpus vector:
- Run native and candidate (via provisional replay cache) through the SAME deterministic (temp=0, fixed seed) real generation request.
- **Different generated token sequence => HARD FAIL, reject promotion.** Model-visible output changed -- never acceptable regardless of throughput.
- **Same generated tokens + identical MTP acceptance trace => exact PASS**, cheap path.
- **Same generated tokens + DIFFERENT acceptance trace (but same output) => "behavior changed", not an automatic reject.** Requires production-parity E2E throughput adjudication: candidate must be non-inferior (margin derived from calibrated native<->native throughput repeatability noise floor, not an invented percentage) or it is rejected.

This replaces the earlier-rejected ideas of (a) an arbitrary pp-based tolerance band on acceptance rate (dropped -- no measurement noise exists under a deterministic reproducer, so any real generated-output divergence should hard-fail, not get a tolerance band) and (b) a strict per-step accepted-prefix-must-never-decrease rule (dropped -- would false-positive-reject genuinely good candidates with harmless FP-reassociation-driven local reordering that nets out fine or better in real throughput).

## Corpus construction

- HI141's own known-bad reproducer is PERMANENTLY pinned as one corpus vector (regression witness).
- Remaining vectors are REAL production/production-parity requests (prompt_token_ids, n_predict, MTP args, model identity captured verbatim from real workload traffic, not synthetic filler) -- stratified across the observed real workload's output-length quartiles (e.g. 2 vectors/quartile for 8 total), not an arbitrary fixed decode length. Decode length for each vector = that vector's own real original request horizon, not a value invented for the gate or derived from a known candidate's divergence point.
- Rotating vectors (beyond the permanent HI141 + a few permanent production-like ones) are deterministically reselected from a larger versioned real-workload pool, keyed by model/build identity, so campaigns progressively exercise more real activation diversity without becoming irreproducible.
- Per-vector candidate/signature dispatch-hit counts are mandatory: a provisional candidate never exercised by ANY corpus vector is "behavior_uncovered", not silently PASS.
- Before a real workload vector enters the gate corpus, its native-vs-native self-replay determinism must be certified once for its exact (model, build/runtime, hardware, args) identity -- if native vs itself ever diverges, that workload cannot be used under the exact-comparison contract.

## Cost control

- Mandatory passing-path cost is O(1) per campaign (one native behavioral leg + one provisional-cache behavioral leg, all corpus vectors run sequentially under the same model load each -- 2 model loads maximum, not per-candidate), NOT O(candidates). Native leg result cacheable when native_behavior_identity is unchanged across campaigns.
- Do NOT scope the gate to only "suspicious" candidates (e.g. by NMSE) -- explicitly rejected, since HI141's own NMSE (5.47e-15) gave zero indication of risk; that heuristic is proven backwards by this exact case.
- Do NOT make the gate periodic-only -- a new candidate can introduce a real regression on the very first campaign that promotes it; the gate belongs on every promotion transaction.
- Empirical acceptance criterion for the implementation: gate_overhead / existing_campaign_time <= 15% for the real production 27B campaign. If exceeded, reduce corpus decode budget or eliminate redundant native loads -- do not weaken the exact-comparison contract to hit the budget.

## Isolation (which candidate caused a HARD FAIL) is explicitly OUT OF SCOPE for this item (deferred as v2)

On a behavioral HARD FAIL, v1's contract is simply: reject promotion for every non-native winner implicated by that failing run, persist the failing vector + first-divergence step + native/candidate trace + candidate dispatch-hit set, and exit the campaign as rejected_behavioral_regression. That alone is sufficient to prevent another HI141 reaching production -- it does not require automatically isolating the single guilty candidate (which is real, separate engineering: a deterministic subset-cache constructor, replay-cache rebuild API, server lifecycle management, exact behavioral runner/comparator, candidate-hit-aware binary partition, resumable state, final single-candidate confirmation -- essentially hardening today's manual ablate_group.py-style workflow into a production primitive). Track that as a separate follow-up item once v1 is implemented and proven; do not conflate the two.
