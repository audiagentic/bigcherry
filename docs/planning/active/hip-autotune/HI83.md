# Validated-state evidence contract: tie STATE="validated" to real HI82 evidence

## Description

GPT review (gpt-auto-agent, req_6b1466ee8369406c) of the completed HI82 body of work (patch source isolation, activation evidence, build-configuration identity, campaign-identity-gated resume, per-bench-arm build identity -- all implemented and verified on real gfx1100 hardware this session) found the most consequential remaining gap: BigCherry can now produce strong, real evidence that a patch was genuinely built, activated, and tested -- but the repository's authoritative patch lifecycle state (a patch module's own `STATE = "validated" | "untested" | "rejected"`, cross-checked against the TOML catalog by patch_catalog.py) is NOT mechanically tied to that evidence. A developer can still hand-edit a patch module's STATE to "validated" with no machine check that matching evidence exists, or that it still matches the CURRENT patch implementation/source/build. Editing a validated patch today does not automatically invalidate its validated status.

GPT's recommended contract (a validation record binding, at minimum): patch ID; patch_implementation_digest; base/source revision or patched source-tree identity; relevant runtime GPU architecture; activation disposition (executed, or legitimately gate-verified-blocked); correctness disposition (passed, or an explicitly admissible N/A with eligibility-gate proof); campaign identity digest; the relevant completed-build identities (compile_verification_id, runtime_bundle_hash); evidence/artifact references. For performance patches, GPT recommends also binding benchmark evidence, but keeping "performance claim proven" conceptually distinct from "correctness/activation validated".

Governance check to add (conceptually): STATE != validated -> no evidence requirement. STATE == validated -> current patch digest must have matching evidence, current source/base identity must match, required architecture/gate conditions must be covered, activation must be proven or gate-verified-blocked, correctness must be proven. The key property this closes: staleness -- editing patches/1204_rd08_q6k_mmvq_vdr2.py (or any validated patch) after a successful validation run should invalidate STATE="validated" until revalidated, since we already have the exact patch/source/build identities needed to detect that.

GPT explicitly ranked this as the single highest-value next piece of work in this whole area (above the deferred campaign_workers.py production-worker compile-verification migration, and above running a validation sweep over the untested rdna-boosts patch backlog) -- "the repository does not yet require that evidence before allowing the authoritative word validated to be asserted... closing that boundary is what I would do next."
