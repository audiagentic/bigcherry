# Make campaign workflows unattended across models and GPU topologies

## Description

Follow-up to HI168. Add one thin validated matrix entrypoint over existing BigCherry campaign workflows so selectable registered models, GPU sets/topologies and runtime configurations can run unattended with reproducible provenance. tune-campaign, ab-benchmark, ServerRunner and existing admission/evidence machinery remain authoritative; this item covers outer resolution, serialization, delegation and aggregation only.

## Steps

## Detailed Solution & Technical Design

Expose exactly one matrix runner over existing campaign configuration (for example, bigcherry campaign-run --matrix <name>). Resolve and validate every cell before hardware execution. Reject unresolved models, unavailable or duplicate GPUs, topology mismatch, invalid profiles, missing build identities, incompatible caches or required evidence failures. Never auto-select, regenerate, retune or silently fall back from a rejected replay cache. Keep production replay timing and diagnostic evidence separate; the matrix layer cannot upgrade admission. Use write-once cell artifacts and deterministic ordering.

ARCHITECTURE DECISION (2026-09-08, dev-gpt-agent req_0fe4b5d23fd049f6, consulted BEFORE writing any code, per real precedent below):

Real precedent that made this consultation necessary: commit 2feb858a -- another session started writing a parallel orchestrator for a 4-arm x N-architecture build matrix; the owner stopped it ("I thought this was what campaigns were for") because tools/bigcherry/campaign/planner.py's CampaignLaneSelector/CampaignRequest already orchestrate multi-lane builds (source x build-variant x patch-composition x compile-architecture, plus EC03 contract-expansion). The module was deleted before it went anywhere.

Verdict on whether HI170 repeats that mistake: NO, but the boundary must be kept explicit. Confirmed by grep (zero references to ROCR_VISIBLE_DEVICES/HIP_VISIBLE_DEVICES/gpu_set/device/topology anywhere in campaign/{planner,execution,resolution}.py or core/config.py) that GPU physical-placement/visibility is a genuinely different, currently-unaddressed axis from what CampaignLane resolves (BUILD identity: source/patch/compile-architecture). CampaignLane.architectures means COMPILE targets, not "run on physical GPU 2" -- do not conflate them.

The general test for future cases like this: does varying the axis require a different intended build artifact/build_plan_id, or can the same resolved binary run unchanged with a different runtime placement? Build-affecting -> extend campaign machinery. Runtime-placement-only (device selection/visibility/topology/model execution against an already-resolved artifact) -> belongs in a layer ABOVE campaign/planner.py. An axis affecting both must have its build-affecting projection and its runtime projection split, not owned by one overloaded lane concept.

PLACEMENT: new module tools/bigcherry/campaign/runtime_matrix.py (sibling to planner.py/execution.py, NOT under tuning/ -- it orchestrates both tune-campaign and ab-benchmark/ServerRunner, so tuning/ would give it the wrong ownership). planner.py stays unchanged and must never import runtime_matrix or environment.Device -- the dependency direction is one-way (runtime_matrix consumes planner/build results).

SHAPE: two functions, per GPT's recommendation --
  resolve_matrix(...) -> tuple[ResolvedCell, ...]   # no GPU execution, preflight only
  run_matrix(resolved_cells) -> RunSummary          # serial delegation only, reuses tune-campaign/ab-benchmark/ServerRunner unchanged
ResolvedCell may reference canonical campaign/build identities but must never independently choose patch composition or reinterpret/upgrade a child's verdict.

PRIOR ART TO COMPOSE, NOT REDESIGN (per GPT, all confirmed present in this codebase):
  - config/recipes.toml's [campaign.e2e-build-matrix] -- already owns the BUILD side of the model/topology campaign; HI170 consumes this, does not reproduce its lanes.
  - campaign/plan.py -- establishes the identity-resolution-boundary philosophy this needs: never create a downstream descriptor with a guessed identity before its real prerequisites resolve.
  - tuning/workflow.py -- already composes a canonical campaign build with model/device/runtime execution and emits an identity-bearing receipt; closest existing seam to imitate.
  - campaign/benchmark.py::run_server_comparison_capture() -- closest existing execution SHAPE: validates config/arms/device selectors first, prepares all arms, executes serially, writes cell.json + run.json, distinguishes production/diagnostic evidence roles, requires clean server shutdown, keeps capture explicitly unadmitted.
  - ServerRunner -- canonical process lifecycle/clean-teardown primitive.
  - e2e_smoke_campaign.py -- has the intended status.json + append-only events.jsonl progress shape already (step 8); reuse that SHAPE later, not its orchestration engine.

CONCRETE BLOCKER, must be resolved as an explicit design choice before/during implementation, NOT silently picked: the stated "resolve the WHOLE matrix before touching any GPU" preflight contract cannot be literally true for tune cells as tune-campaign currently works -- build.tune requires an inventory, and tune-campaign currently OBTAINS that inventory by running the record stage on a real GPU first. Two options, per GPT: (a) require pre-existing, identity-bound cached inventory/evidence for every tune cell up front; missing/stale cache fails the ENTIRE preflight closed, or (b) explicitly weaken "whole matrix resolved before any GPU" to allow staged identity resolution after the record stage runs. Do NOT invent/provisionally hash a tune build identity before its inventory exists -- campaign/plan.py's own philosophy explicitly rejects that. Leaning toward (a) for the initial cut (matches this project's fail-closed default), but this must be a recorded decision when implementation starts, not an assumption.

OTHER BLOCKERS SURFACED, to settle during implementation:
  - GPU visibility needs ONE canonical resolver -- DONE this session (2026-09-08, ahead of runtime_matrix.py itself): core.environment.gpu_visibility_pair()/Host.gpu_visibility_env() now compute the correct ROCR_VISIBLE_DEVICES/HIP_VISIBLE_DEVICES PAIR (VA22, "the two-selector trap" -- ROCR filters physical devices first, HIP then indexes by POSITION into that filtered list, so a selection not starting at physical index 0 needs HIP reindexed from 0, e.g. physical device 2 alone needs ROCR="2"/HIP="0", never HIP="2"). Found dead/unused code (Host.visible_devices(), called nowhere) that returned ONE string for both selectors -- exactly the bug shape, just never yet exercised. Replaced outright (no legacy shim, per project doctrine). Wired into tuning/workflow.py's four ServerRunner env_overrides sites, which previously set ONLY HIP_VISIBLE_DEVICES (worked by accident today because ROCR is left ambiently unset in the common case, but fragile the moment this runs in a context with inherited ROCR state, and the wrong pattern for runtime_matrix.py to copy). New tests: tools/tests/core/test_environment.py (GpuVisibilityPairTests, 6 tests + Host-method agreement test) and tools/tests/tuning/test_workflow.py (GpuVisibilityEnvTests, 3 tests). runtime_matrix.py should call environment.gpu_visibility_pair()/Host.gpu_visibility_env() directly -- do not reimplement this math a third time.
  - Do not duplicate topology in two argv authorities: runtime profiles already carry -sm tensor/-ts etc; a topology selector should validate/describe compatibility with the requested device set, not independently emit a possibly-contradictory split-mode argument.
  - Separate orchestration status from evidence verdict: a cell needs e.g. matrix_status=executed|infrastructure_failed|skipped distinct from the child's verdict, copied verbatim. A run being "complete" must never imply performance_admitted=true.
  - Do not let ab-benchmark --server-config's explicitly-unadmitted diagnostic capture become production admission by virtue of being wrapped in a matrix run.
  - run_campaign()'s failure semantics (catch a failed lane, continue siblings) are NOT HI170's semantics: an ordinary clean child rejection may continue to the next cell, but residual process/GPU state must abort the WHOLE matrix, not just skip one cell.
  - Clean process shutdown (ServerRunner.last_shutdown.clean) is necessary but not sufficient for HI170's stronger "no residual process/device state" rule -- needs a parent-level quiescence check before the first cell AND after every cell. Fail closed; never auto-kill unrelated production processes to force quiescence.
  - TOCTOU: after whole-matrix preflight, bind each cell to config/tooling revision + runtime-profile digest + model registry identity + build IDs/binary hashes + cache evidence, then RE-CHECK those exact bindings immediately before executing that child -- campaign/benchmark.py already re-verifies source attestation immediately before execution; follow that pattern.

Recommended boundary for implementation start: campaign/runtime_matrix.py consuming e2e-build-matrix, core.environment (now including the fixed GPU-visibility resolver), the model registry (config/models.toml), and runtime profiles; reuse tune-campaign/ab-benchmark and their receipts completely unchanged.
