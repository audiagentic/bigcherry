# Extend HI80 correctness-evidence generation to GLU (op=100) signatures, including MoE-routed GLU

## Description

HI105 extended HI80's correctness-evidence generation from MUL_MAT-only to also cover MUL_MAT_ID, but explicitly left GLU (op=100) out of scope -- deliberately, per HI80's own doctrine of deriving each op's mapping from its own real test_case subclass (test_glu) rather than assuming shared semantics from overlapping canonical fields (has_ids/n_expert appear on GLU rows too, since some GLU nodes are MoE-routed, but that does not make them MUL_MAT_ID).

During HI105's broader real MoE tune campaign on Qwen3.6-35B-A3B (2026-08-24), two real GLU candidates were found with genuine isolated kernel wins -- both currently stuck at rejected_no_correctness_evidence purely because the GLU mapper doesn't exist, the exact same tooling-gap shape HI105 fixed for MUL_MAT_ID:
- dispatch=7ef2471585a5aa6fbb49384efe566ac5: MoE-routed GLU (has_ids=true), ne0=[2048,256,256,1] ne1=[2048,1,1,1] ned=[256,8,1,1] -- candidate mmvq:q8_0:w1:nw1:rpb1:sk0:v1 found 14.1% isolated improvement.
- dispatch=d816ffce280de2a7ce2292c6406da23d: non-routed GLU (has_ids=false), ne0=[2048,512,1,1] ne1=[2048,1,1,1] ned=[512,1,1,1] -- candidate mmvq:q8_0:w1:nw4:rpb1:sk0:v1 found 4.3% isolated improvement.

A dev-gpt-agent deep-dive (2026-08-24) independently flagged this same gap, and separately noted (worth verifying against real source before acting): mainline llama.cpp already has CUDA-graph fusion recognizing {MUL_MAT_ID, MUL_MAT_ID, GLU} sequences (from merged upstream PR #16715, restricted to ncols_dst==1/decode per HI26's own notes) -- meaning the routed GLU signature above may already be running through a FUSED epilogue in production, which would change what 'the candidate' for that dispatch even means and needs to be understood before writing a mapper.

## Steps

1. Read test-backend-ops' real test_glu case (mirror HI105's own process for test_mul_mat_id) to derive the real op_filter/target_tensor/shape semantics for GLU -- do not assume MUL_MAT_ID's conventions transfer.
2. Verify GPT's PR #16715 CUDA-graph-fusion claim against real source (ggml-cuda's graph fusion code) before assuming it's accurate or relevant -- if the routed GLU signature is already running fused in production, the correctness-evidence generator needs to evidence the FUSED path, not GLU in isolation, or the evidence would be for an op that never actually executes standalone.
3. Add signature_to_glu_test_file_line() (or equivalent) to signature_correctness_mapping.py and route it through signature_to_any_test_file_line()'s dispatcher, following HI105's exact pattern.
4. Validate on real hardware against the two real dispatches above; confirm via HI80 CLI + tune-promote whether they actually reach promoted status.
5. If promoted, consider whether a real end-to-end A/B is warranted given HI105's finding that MoE-routed candidate wins of this size (4-14%) did not move full-model throughput for the MUL_MAT_ID case -- do not assume this one will either without measuring.
