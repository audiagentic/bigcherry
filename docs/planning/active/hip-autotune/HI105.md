# Extend HI80 correctness-evidence generation to MUL_MAT_ID (MoE-routed) signatures

## Description

HI80's correctness-evidence tool (hi80_generate_correctness_evidence.py) is deliberately MUL_MAT-only: any non-MUL_MAT row is reported and skipped, since MUL_MAT_ID needs its own op_filter/target_tensor derivation rather than reusing MUL_MAT's mapping assumptions (per signature_correctness_mapping.py's own docstring). This blocks real per-signature promoted-winner replay for any MoE-routed (has_ids) result -- including RD54's two validated MMVQ nwarps candidates for Qwen-class MoE decode, which are statistically airtight (p=0.0, tight 95% CIs, nmse~0 vs native) but cannot pass tune-promote's correctness gate (promotion_status=rejected_no_correctness_evidence) purely because of this tooling gap, not a correctness concern.

## Detailed Solution & Technical Design

Derive a MUL_MAT_ID-specific op_filter/target_tensor mapping (signature_to_op_filter's MUL_MAT-only assumptions do not transfer directly -- MUL_MAT_ID's ids/expert-routing shape and memory layout differ from plain MUL_MAT, as documented in the pinned mmvq.cu: ncols_dst = ids ? ne2 : ne1, and a dedicated mul_mat_vec_q_moe_launch kernel exists for the multi-token MoE case that plain MUL_MAT never touches). Extend correctness_evidence.generate_correctness_evidence() and write_correctness_evidence() to accept and route MUL_MAT_ID signatures against a patched test-backend-ops binary the same way MUL_MAT already works, verified against a real MoE model's real recorded signatures (RD54's Qwen3.6-35B-A3B Q8_0 K=256/K=2048 signatures are ready-made real test cases).

### Real scope correction found during implementation
Only one of RD54's two signatures is actually MUL_MAT_ID. K=256 (down projection) is op=30=MUL_MAT_ID, confirmed via load_ggml_op_names against the real vendored source. K=2048 (RD54's other real signature) is op=100=GLU -- a real, distinct fused activation node with its own test-backend-ops class (test_glu), not MUL_MAT_ID, despite carrying the same has_ids/n_expert canonical fields. This HI105 slice correctly, deliberately does NOT cover it (matches HI80's own doctrine: derive from that op's own test_case subclass first, never assume from shared flags). GLU-fused MUL_MAT_ID correctness evidence is a real, separate future item.

### Implementation (5 commits: f78eb2d, 8265ba4, 7f2e04c, df211d0, 5dcd6d7)
1. Fixed a real, independent safety-gate bug found along the way: correctness_evidence.py's run_test_backend_ops() set GGML_HIP_FORCE_CANDIDATE for the candidate run but never GGML_HIP_FORCE_CANDIDATE_STRICT (dispatch.cu's own comment names this exact file as the reason STRICT exists).
2. New patch 1236: test_generic_op's GGML_OP_MUL_MAT_ID initializer gets a deterministic, FULL-expert-range shuffle under BIGCHERRY_TEST_DETERMINISTIC_SEED (the pre-existing code was both non-deterministic across processes -- random_device, not seeded -- AND confined to a {0..n_expert_used-1} range, never the real full expert pool). Emits its own BIGCHERRY_REF_DIGEST for the ids tensor.
3. New signature_to_mul_mat_id_test_file_line() in signature_correctness_mapping.py: shape identity derived from src/llama-graph.cpp's build_moe_ffn (real production MoE code), verified against RD54's real signature. as/b taken literally from the recorded ne0/ne1 (no broadcast-flag branching needed), ids=(n_expert_used,ned[2],1,1) type I32 (resolved from the parsed type table, not hardcoded), nb=[0,0,0,0] on every source (ggml's own 'default contiguous strides' convention -- no Q8_0 block-layout math needed in Python).
4. New signature_to_any_test_file_line() dispatcher: hi80_generate_correctness_evidence.py was found (dev-gpt-agent review) to still call the MUL_MAT-only mapper unconditionally, silently SKIPPING every real MUL_MAT_ID row without incrementing the failure count -- a run could exit 0 having generated no evidence at all. Fixed by routing through the dispatcher.
5. Fixed a second real gap (dev-gpt-agent review): the MUL_MAT_ID mapper originally reused 'leaf_0' (weights) as its digest tensor, same as plain MUL_MAT -- but weights/activations already have a proven deterministic guarantee from patch 1222; the NEW risk MUL_MAT_ID introduces is expert routing. Changed to 'leaf_2' (the ids tensor). This was flagged as an extrapolation needing real-hardware confirmation (HI80's own leaf_0 convention was verified only for the 2-source MUL_MAT case) -- confirmed directly below.
