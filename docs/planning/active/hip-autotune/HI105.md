# Extend HI80 correctness-evidence generation to MUL_MAT_ID (MoE-routed) signatures

## Description

HI80's correctness-evidence tool (hi80_generate_correctness_evidence.py) is deliberately MUL_MAT-only: any non-MUL_MAT row is reported and skipped, since MUL_MAT_ID needs its own op_filter/target_tensor derivation rather than reusing MUL_MAT's mapping assumptions (per signature_correctness_mapping.py's own docstring). This blocks real per-signature promoted-winner replay for any MoE-routed (has_ids) result -- including RD54's two validated MMVQ nwarps candidates for Qwen-class MoE decode, which are statistically airtight (p=0.0, tight 95% CIs, nmse~0 vs native) but cannot pass tune-promote's correctness gate (promotion_status=rejected_no_correctness_evidence) purely because of this tooling gap, not a correctness concern.

## Detailed Solution & Technical Design

Derive a MUL_MAT_ID-specific op_filter/target_tensor mapping (signature_to_op_filter's MUL_MAT-only assumptions do not transfer directly -- MUL_MAT_ID's ids/expert-routing shape and memory layout differ from plain MUL_MAT, as documented in the pinned mmvq.cu: ncols_dst = ids ? ne2 : ne1, and a dedicated mul_mat_vec_q_moe_launch kernel exists for the multi-token MoE case that plain MUL_MAT never touches). Extend correctness_evidence.generate_correctness_evidence() and write_correctness_evidence() to accept and route MUL_MAT_ID signatures against a patched test-backend-ops binary the same way MUL_MAT already works, verified against a real MoE model's real recorded signatures (RD54's Qwen3.6-35B-A3B Q8_0 K=256/K=2048 signatures are ready-made real test cases).
