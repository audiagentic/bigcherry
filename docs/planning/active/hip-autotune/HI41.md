# Ranking-policy table abstraction (HI50) — plural, offline-replayable winner-selection policies

## Description

Before the external git-reset incident (2026-08-11/12), `hip-autotune-tuner.cu` had a compiled-in **policy table** abstraction that let multiple named winner-selection algorithms shadow-evaluate on every tuning pass, with exactly one nominated as `production_policy` (default `latency-v1`) actually driving dispatch/confirmation/promotion. Every other active policy's pick was recorded as an unconfirmed prediction for offline comparison, never touching a GPU launch of its own beyond what the production policy already measured.

Current `hip-autotune-tuner.cu` (post-recovery) has none of this: a single hardcoded selection path, no policy registry, no per-policy ranking-decision JSON. This item captures the exact pre-reset design and source so it can be re-implemented faithfully without re-deriving it, deferred until there is time to do it properly (it is not required for the P0 promotion/confirmation gate, which can be grafted onto the current single-path selection directly).

## Detailed Solution & Technical Design

**Architecture** (mirrors the existing HI50 comments in the recovered source verbatim):

- `PolicyCandidateVerdict { Measurement* m; std::string verdict; std::string rejection_reason; }` — one per finalist a policy considered (winner/qualified/near_tie_below_threshold/outside_tie_band/not_attempted/rejected), so a rejected or near-tie candidate stays visible in the report, not just the pick.
- `PolicySelection { std::vector<Measurement*> qualified; bool any_short_rounds; std::vector<PolicyCandidateVerdict> ranked; }` — `qualified.front()` is the pick if non-empty; nullptr-pick (native retained) is represented by an empty `qualified`, matching the pre-HI50 call site's own convention.
- `PolicyTableEntry { const char* name; int version; PolicySelection (*fn)(...); }` and `const PolicyTableEntry g_policy_table[] = {{"latency-v1", 1, select_latency_v1}};` — adding a policy is adding one table entry; nothing else in the resolve()/flush() pipeline changes.
- `resolve_production_policy_index(config)` — maps `config.production_policy` (default `"latency-v1"`) to a table index, falling back to index 0 on an unrecognized name so a typo can only mis-scope which policy's *name* is reported as production, never silently stop promotion.
- `policy_name_is_active(name, config.active_policies)` — comma-separated allow-list, `"all"` (the default) means every compiled-in policy shadow-evaluates.
- `select_latency_v1(...)` — pure extraction of the tie-break/qualify algorithm that is the ONLY algorithm current code runs today (rank by `effective_us`, near-tie band by `tie_pct`, require `replacement_threshold_pct` + paired sign test to qualify, break ties by p95/workspace/native-preference/name). No behavior change versus current single-path logic — this is the reference policy current code already implements, just not yet named/registered/replayable.
- At resolve time: every entry in `config.active_policies` (or just the production entry if narrower) is evaluated against the same already-measured finalists — pure CPU-side ranking, zero extra GPU launches. Only the production policy's pick continues into the determinism recheck and confirmation holdout. `result.ranking_decisions_json` records every policy's full verdict list per signature; `result.production_policy_name`/`production_policy_version` record which one was authoritative.
- Depends on fields not yet in current `Measurement`/`Result` structs: `is_native_twin` (bool, marks the double-native measurement used when no MMQ J-best twin exists — HI24 step 4), `canary_state` (`ggml_hip_canary_state_v1` enum: NOT_AVAILABLE/PASS/RETRIED_PASS/UNRESOLVED, replaces current's bare `canary_pct` float-only signal).
- Python-side counterpart is `ranking_policy.py` (doc section 8 of the recovery handover) — `CandidateMetrics`/`PolicyDecision`/`POLICY_REGISTRY`/`latency-v1`, which offline-replays `ranking_decisions_json` against persisted evidence via `rank_replay.py` / `bigcherry rank-replay --verify-parity`. That Python side is tracked separately (not blocked on this C++ work landing first, since `ranking_decisions_json`/`provisional_winner` are what it consumes).
