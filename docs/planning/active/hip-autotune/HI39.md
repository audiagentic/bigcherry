### 2026-08-11: deep re-verification of the "remaining proof" list -- no guesswork, no implementation this pass

Read tools/bigcherry/experiment_bundle.py in full (the item's own Files section had named a nonexistent experiment.py; the real, working module is experiment_bundle.py, 255 lines -- name drift worth fixing). The core contract is genuinely solid: intent written before child launch, model/artifact BLAKE2b hashing, relative path-escape rejection, a strict environment allow-list with regex-based secret refusal, atomic document writes via tune_journal.atomic_write, lifecycle-state validation, and a parent-experiment-graph cycle detector. All read and confirmed directly, not assumed.

Four "remaining proof" gaps checked one at a time:

1. Workload/seed/timing-policy fields -- confirmed absent from intent/final in run_managed(). Genuinely not started.
2. OS/compiler/ROCm/driver/library version fingerprint -- confirmed absent. Genuinely not started; deciding exactly what to capture and how to query it portably (Windows vs Linux) is real design work.
3. Device/topology descriptor -- partially wrong as originally framed. HI52 already built and shipped exactly this primitive: src/ggml/src/ggml-cuda/hip-autotune-smi.h -- ggml_hip_query_device_state(), dlopen-based against librocm_smi64, degrades to valid=false on Windows/library-absent. Already wired in and proven -- verified at hip-autotune-tuner.cu:1640/1711/1787/2116/2682-2683: every tuned signature already carries device_state_pre/device_state_post in its result JSON, gated behind GGML_HIP_TUNE_SMI=1. So per-signature device telemetry is NOT missing -- what HI47 still lacks is a host-level (bundle-boundary) snapshot taken by experiment_bundle.py's run_managed() before/after the whole managed subprocess. Python has no HIP device access of its own; needs either (a) shelling out to rocm-smi/amd-smi CLI and parsing output (format varies by ROCm version, real guesswork risk unless verified against a real CLI run first), or (b) a small new C++ executable target wrapping the already-proven ggml_hip_query_device_state() that the Python host runner shells out to. (b) is lower-risk (reuses tested code) but needs a new CMake executable target -- not attempted without an actual build+run available. No CLI wrapper exists yet.
4. Typed runtime artifact schemas / downstream bundle adapters -- confirmed absent; open-ended integration work across every consumer (impact, kernel-fraction, report, tune-freshness, release validation, A/B reporting).

Deliberately not implemented this pass, per the same staging principle applied to HI38/HI48 (land self-contained, independently verifiable units; do not bundle build-system or hot-path changes into a pass with no hardware validation available).

Recommended next action, cheapest first: build the small SMI-query CLI wrapper around ggml_hip_query_device_state() (reuses proven code, no new device-state logic to design) as its own separately-landed change with a real CMake target -- closes gap 3 fully and is the only one of the four that doesn't also require an open design decision.
