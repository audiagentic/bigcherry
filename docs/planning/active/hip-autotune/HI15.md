# Production hardening — replay-full binary, cache export, and corruption handling

## Description

Phase 9 — production hardening. Export validated winners to compact immutable cache. Build replay-full binary with no SQLite/tuner. Implement candidate blacklist, bounded miss logs, metrics/coverage reporting, and replay-slim generator.

## Steps

- Export validated SQLite winners to compact immutable binary cache
- Build replay-full production binary — confirm no SQLite/tuner linked
- Implement corruption handling: incompatible/corrupted cache falls back safely
- Unknown signatures use native and record misses via `GGML_HIP_DISPATCH_MISS=native-record`
- Cache loaded from `GGML_HIP_DISPATCH_CACHE=path/to/replay.bin`
- Candidate blacklist mechanism for invalid/high-spill geometries
- Bounded miss logging in production
- Metrics and coverage reporting
- Replay-slim generator: compile only selected winners plus native fallbacks

## Notes

### Review update

**`GGML_HIP_EXPORT_METRICS` already exists upstream** (`ggml/CMakeLists.txt`, and it already sets `-Rpass-analysis=kernel-resource-usage --save-temps`). No patch needed — consume its output rather than adding the flag. (A4)

**The blacklist belongs before tuning, not in production hardening.** Plan 17.2 is explicit: compile full-max as an audit, inspect compiler resource output, and blacklist high-spill geometries *before* runtime tuning. A spilling MMVQ geometry that reaches the tuner wastes measurement time on a candidate that was never viable. Moved to a new item after HI09 (PACK_REVIEW B6); what remains here is the runtime blacklist consumption.

**Two tools the plans dropped** (PATCH_MAP patches 10 and 11, PACK_REVIEW B7):

- `hip-autotune-export` — SQLite winners to compact binary cache. Not optional: it is the only bridge from tune builds to production. May be Python, since it runs offline.
- `hip-autotune-inspect` — inspect a cache or registry. Should be **C++**, so it links the real registry and validates with the same loader production uses. A Python re-implementation could disagree with the loader, which is the one thing it exists to check.

**Restart-only cache reload is a deliberate non-goal** (plan 12.5, PACK_REVIEW B8). Captured HIP graphs hold the resolved candidate, so live reload requires graph and binding invalidation that has not been proven.
