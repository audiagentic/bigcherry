# Decompose the opaque BLAS candidate into a controlled execution plan

## Description

Today BLAS is one candidate, `blas:hipblas-auto:v1`, standing in for what the
source shows to be a three-stage plan with at least four independent choices.
On the 27B MTP profile **19 of 92 signatures** resolve to BLAS, so a fifth of
the workload's distinct operations currently have exactly one thing the tuner
can say about them: "hipBLAS did something".

`ggml_cuda_mul_mat_cublas_impl` performs input conversion, the GEMM, and output
conversion. Each stage has a decision upstream makes by heuristic and never
measures. See [FAMILY_MODEL.md](FAMILY_MODEL.md) for the verification behind
each item below.

## Steps

- **`compute_type` as a forced variant.** `ggml_cuda_mul_mat_cublas` already
  selects F32/F16/BF16 through a template `switch`, and upstream already ships a
  global `GGML_CUDA_CUBLAS_COMPUTE_TYPE` override. Add a defaulted parameter
  (the Option C pattern used by HI06–HI08) so the choice can be made per
  signature instead of per process.
- **Precision-class gating.** `dst->op_params[0] == GGML_PREC_F32` is the
  request's precision class, and the signature already carries it as `prec`
  ([hip-autotune-types.h:135](../../../../src/ggml/src/ggml-cuda/hip-autotune-types.h#L135)).
  Gate `compute_type` on it; no ABI change needed. Never infer the class from
  source type — a quantised source does not make every accumulation mode
  equivalent.
- **`numerical_class` on every candidate** — `exact_baseline`,
  `equivalent_within_backend_tolerance`, `reduced_precision`. The objective
  admits or rejects classes *before* performance ranking, so a reduced-precision
  candidate cannot win by default against a strict request.
- **`conversion_route` as an explicit field.** `convert` (contiguous) and
  `convert_nc` (strided) are already two routes for one type pair, so a
  `convert_type` field would be wrong even today.
- **`output_conversion_route`.** `prefer_f32_output`
  ([ggml-cuda.cu:1515-1520](../../../../vendor/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu#L1515-L1520))
  gives RDNA4/CDNA/Volta direct F32 output and denies it to RDNA3. The 2× XTX
  rig is gfx1100, so every F16-compute BLAS call there allocates an F16 temp and
  runs a full extra pass. This is a same-hardware A/B, not a hypothetical.
- **`api_strategy`, not `api`.** The API is chosen by a hard if/else chain over
  signature properties, so exactly one is reachable per shape by default.
  `native-auto | prefer-strided | prefer-pointer-batched | force-gemmex`; the
  API actually called is an observation. Upstream's own comment at
  [ggml-cuda.cu:1545](../../../../vendor/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu#L1545)
  ("Theoretically … would always work … probably because the internal kernel
  selection logic is suboptimal") is the documented reason `prefer-strided`
  exists as a candidate.
- **`provider_policy`** — `hipblas-auto | hipblas-force-tensile |
  hipblas-prefer-hipblaslt`, driven by `ROCBLAS_USE_HIPBLASLT`. Policies under
  one family, not three families.
- **Effective-path telemetry** — `provider_requested`, `provider_effective`,
  `observed.api`, `library_backend`, `solution_id`, `kernel_name`,
  `conversion_kernels`, `temporary_bytes`, `workspace_bytes`. A winner without
  it is marked unverified and excluded from promotion: reporting
  `winner = hipblas-prefer-hipblaslt` without establishing that hipBLASLt
  handled the call is not a measurement.
- **Build namespace extension** — ROCm, hipBLAS, rocBLAS and hipBLASLt versions
  plus `ROCBLAS_USE_HIPBLASLT`, since internal selection changes across
  releases.

## Detailed Solution & Technical Design

DQ_BLAS and BLAS are **not two entry points**. There is one
`ggml_cuda_mul_mat_cublas`, and whether a call dequantises is decided by
`src0->type == compute_type` — where `compute_type` is the candidate's own
choice. The same candidate is therefore DQ_BLAS against a q8_0 signature and
plain BLAS against an f16 one.

So this implements **one `BLAS` family** with `conversion_route = none` meaning
no dequantisation, and reports `actual_family = dq_blas | blas` as a derived
observation. Splitting the family by source type would re-import a request
attribute into family membership, which is the thing the taxonomy exists to
avoid. Grouping and cost attribution work identically either way.

Sequencing: `compute_type` first. It is the cheapest (the template switch and
the env override already exist), it is the choice that determines whether
conversion happens at all, and it validates the precision-class machinery that
everything else depends on.

No BLAS candidate should be promoted from the telemetry-only proof alone.

## Effort & Risk

Medium risk. The conversion temporaries come from the pool allocator, so
workspace accounting must be attributed to the candidate rather than lost in the
pool — otherwise a candidate that allocates two large temps looks free.
`GGML_PREC_F32` gating is the correctness-critical part: getting it wrong lets a
reduced-precision candidate win a strict-precision signature.

 provider, api_strategy, provider_policy)
