# Patch-validation campaign: content-addressed source isolation + activation-evidence gate (GPT design, req_51838ef1ea5f4086)

## Description

GPT review (2026-08-21/22, gpt-auto-agent request req_51838ef1ea5f4086) of tools/bigcherry/patch_validation_campaign.py found a real, hit-this-session contamination risk: --build-root reuses ONE mutable vendor/llama.cpp checkout across sequential patch applications with no isolation or provenance check, so applying patch A then patch B to the same build-root silently composes both patches into one build rather than testing B in isolation. This session applied 1204_rd08_q6k_mmvq_vdr2 then later 1002_hip_unsafe_math_opt_in to the SAME tree -- the two don't share touched files (CUDA kernel files vs ggml-hip/CMakeLists.txt) so the specific findings this session recorded are not invalidated, but the pattern is unsound for unattended multi-patch scaling.

Full design (GPT, verbatim structure):
1. SOURCE ISOLATION: replace the single mutable vendor tree with content-addressed, git-worktree-per-source-identity storage. source_key = hash(base_revision, patch_name, patch_implementation_digest). After patching, record git_worktree_tree() (a real git tree hash computed via a temporary index, capturing tracked mods/deletions/untracked adds without touching the operator's real index) into a manifest; every reuse re-verifies HEAD + worktree tree hash against the manifest and fails closed on any mismatch. Patch identity must include a content digest of the patch module (not just its name) -- this session literally changed 1204's own edit script mid-session while keeping the same name.
2. ACTIVATION EVIDENCE as a first-class campaign gate, not just build+correctness+bench: introduce ActivationEvidence{status: executed|not_executed|not_applicable|unobservable, mechanism, detail}, written to activation.json next to bench.json. Campaign verdict must depend on it: not_applicable -> 'gate-verified-blocked', unobservable -> 'unobservable', executed-but-correctness-failed -> 'failed-correctness', executed+correctness -> 'validated'. A green build + plausible bench numbers must never alone imply 'validated' -- this exact failure mode was found live: 1221_rd50_gdn_chunked_recurrence is arch-gated to RDNA3.5 and would produce a normal-looking flat-bench 'pass' on our gfx1100/gfx1201 hardware despite the new kernel never executing.
3. Six-state disposition (not just untested/validated): validated, gate-verified-blocked (eligibility/fallback verified, positive path hardware-unavailable), model-blocked (selection logic unit-tested, model integration unavailable), unobservable (campaign cannot prove the new path executed), failed, untested.
4. RD12/RD13-class silent graph-fusion patches: add ONE shared env-gated hit marker (BIGCHERRY_PATCH_TRACE=1, not per-patch vars) emitted once (std::atomic_flag-guarded) at the actual fusion COMMIT point (after all eligibility checks pass, not inside can_fuse() alone) via GGML_LOG_INFO('BIGCHERRY_PATCH_HIT patch=<id> path=<name>'). Campaign runs two probes before benchmarking: BIGCHERRY_PATCH_TRACE=1 must show the marker; BIGCHERRY_PATCH_TRACE=1 + GGML_CUDA_DISABLE_FUSION=1 must NOT show it (negative control proving the marker identifies the fusion path, not something else). Diagnostic instrumentation stripped/unset for the real benchmark run.
5. RD50/RD21-class arch-gated patches: unit-test the patch's COMPLETE eligibility predicate (not just the upstream arch macro) with the real dispatch condition; verify the current-hardware FALLBACK path still produces correct output on gfx1100/gfx1201 knowing the predicate returns false there; compile (not run) the positive path for the target arch to catch codegen-only errors even without hardware.
6. 1005-class model-unavailable patches: extract/unit-test the pure checkpoint-selection function with synthetic checkpoint metadata (recurrent-state-compatible / ordinary-transformer / stale / post-divergence candidates) rather than requiring a live model integration test.
7. Build-configuration identity (separate from source identity) must include: source tree fingerprint, arch, build mode, generator, compiler identity, ROCm/toolchain identity, CMake options, environment-derived flags -- the Windows CMAKE_HIP_FLAGS-doesn't-propagate discovery (HI81) is cited as proof that 'configured intent' and 'actual compiled command' are not synonymous and must both be checked (post_build_verify hook, generalizing the ninja-t-commands check already done ad hoc for 1002).
8. bench.json's stock/native/replay entries should each carry their own source_tree/build_identity, not just a bare binary path.
9. status.json/resume must include a campaign identity (patch digest, patched source tree, model identity, GPU arch, build identities, campaign-script version) and refuse to resume stale stage artifacts on any mismatch rather than silently treating stages as done.

Priority order GPT recommended: (1) source/build isolation first (measurement-integrity blocker for any further unattended multi-patch runs), (2) activation.json/verdict gate, (3) RD12/RD13 markers, (4) reclassify RD50/RD21 as gate-verified-blocked, (5) reclassify 1005 as model-blocked with a pure-function test, (6) generalize post_build_verify for future compile-flag-class patches.
