# Implement family-level tuning engine with complete-path timing and correctness validation

## Description

Patch 9 — implement the full tuning engine (hip-autotune-tuner.cu, hip-autotune-metrics.cpp). Complete-path event timing, native reference output, hard eligibility screening, warmup/screen/finalist stages, measurement persistence, and winner selection with replacement threshold.

**B2: Screening retention policy** — retain the native candidate (always) + top 3 by median + every candidate within 10% of best median. Parameterised as `screen_keep_top = 3`, `screen_keep_within_pct = 10`.

## Steps

The engine runs. E1..E6 are implemented per the Detailed Solution and Code
Samples sections below. Original completed steps are retained at the bottom
for provenance.

### E1..E6 (implemented 2026-08-07)

- **E1 — paired sign test.** `binomial_tail_ge` and `paired_sign_test` implemented; final-stage rounds are stored per-Measurement in `final_gpu_us`/`final_host_us`, NaN-padded so index r always means round r; `median_of`/`percentile_of`/`mad_of` filter NaN internally. ## Detailed Solution & Technical Design

All six changes live in `hip-autotune-tuner.cu` / `.cuh` plus a matching field
in `tools/bigcherry/inventory.py`. None of them changes a hashed struct, so no
ABI version moves and no existing cache is invalidated.

### E1 — the pairing is already there; stop discarding it

#### What the code does now

`hip-autotune-tuner.cu:467-489` measures round-major:

```
for round in 0 .. final_samples:
    for i in finalists:
        one sample
```

That is a randomised-block design. Finalist *i*'s sample in round *r* and
finalist *j*'s sample in round *r* were taken microseconds apart on the same
clock state, the same thermal state and the same queue depth. The common-mode
noise that makes GPU timing hard is very nearly *shared* between them.

The code then computes `median_of(gpu[i])` per finalist and compares medians.
That throws the pairing away: two medians drawn from 15 samples each are
compared as if the samples were independent, which is exactly the comparison
RV21 showed to be worth ~14% at three samples.

#### What to do instead

Compare **round by round**. For each round where both the candidate and native
produced a sample, ask only which was faster. Count the rounds. Under the null
hypothesis "these two are the same kernel speed", each round is a fair coin, so
the count of candidate wins is `Binomial(n, 0.5)` and the one-sided tail is an
exact p-value with no distributional assumption at all.

#### Why the sign test and not a t-test or a bootstrap

The file already argues the case in its own comments. `mad_of` at
`hip-autotune-tuner.cu:112-123` exists because "a single preemption or clock
excursion makes stddev meaningless while MAD barely moves -- and GPU timings are
full of both". A t-test on paired differences is a statement about a *mean*
difference and inherits precisely the fragility MAD was chosen to avoid: one
preempted round with a 10x reading dominates it.

The sign test uses only the direction of each paired difference. A 10x outlier
round costs one vote, the same as a 0.1% round. It is the natural companion to a
median-and-MAD summary, and it is about twenty lines of code.

It is deliberately *conservative*: it will refuse to confirm a real 1% win that
is smaller than the round-to-round noise. That is the correct failure direction
here — the cost of a false positive is a permanent wrong winner in a shipped
cache, and the cost of a false negative is retaining native, which is the status
quo.

#### The decision rule

A non-native candidate replaces native only when **both** hold:

1. `improvement_pct >= replacement_threshold_pct` (1%, unchanged) — effect size
2. `sign_test_p <= confidence_alpha` (0.025, new) — consistency

Effect size without consistency is RV21. Consistency without effect size is a
reproducible 0.05% win that is not worth a cache entry.

Applied to the tie set rather than only to the provisional best: filter the tie
set to members that pass (1) and (2) against native, *then* run the existing
`(p95, workspace, not_native, name)` sort over what survives. Empty set means
native is retained with `reason = "no candidate beat native with confidence"`.

#### Sample alignment — the detail that silently breaks this

`time_candidate` can fail mid-run, and the current loop simply does not append
for that finalist that round (`:474-478`). Index *r* in `gpu[i]` therefore stops
meaning "round r" as soon as any candidate has failed once, and every subsequent
pair is mismatched — comparing round 7 of one candidate against round 8 of
another. Medians do not care. A paired test does.

Fix: on failure push `NaN` so position always equals round, and skip NaN pairs
when testing. `median_of` and `mad_of` must then filter NaN before sorting
(`std::sort` with NaN present is undefined behaviour, not merely wrong).

#### Reference values for validation

At `final_samples = 15`, the smallest win count with one-sided p <= 0.025 is
**12 of 15** (p = 576/32768 = 0.0176; 11 of 15 gives p = 0.0592, which fails).
At `final_samples = 3` no outcome can reach 0.025 — the best possible is
p = 0.125. That is not a defect: a three-sample run genuinely cannot establish a
1% difference, and the engine should now say so instead of asserting a winner.
Runs at `FINAL_SAMPLES=3` will therefore retain native far more often, and that
change in behaviour is the point.

### E2 — raw samples, so a decision can be re-audited without a GPU

`measurement.samples_json` exists at `sql/dispatch-db.sql:161` and nothing
writes it. Keeping the raw finalist samples makes every winner recomputable
offline: a different alpha, a different statistic, a different tie policy can all
be tried against a completed run rather than by re-tuning on hardware for ten
minutes per sweep. It is also what HI35's impact model and HI34's fidelity
experiment both consume.

Scope it to finalists. Screened-only candidates get 3-20 samples and are not
decision-relevant; finalists are at most ~6 per signature. At 1151 signatures x
6 finalists x 100 samples x ~8 bytes the file grows by roughly 5.5 MB, which is
acceptable for an artifact already written once per sweep. Gate on
`GGML_HIP_TUNE_EMIT_SAMPLES` (default 1) for the case where it is not.

### E3 — rank on whichever resource is actually binding

#### The subtlety worth getting right

The naive reading of "GPU time vs host time" is wrong in this harness. Both
events are recorded on the same stream around the same launch batch, so a host
stall *between* the two records still appears inside the GPU elapsed time — the
timestamps are taken when the stream reaches each event. For most candidates,
therefore, `host_median ~= gpu_median + sync_overhead`, and the difference
carries no information.

The case where they genuinely diverge is the one B3 named: the host cost of
*submitting* the work exceeds the GPU cost of *executing* it. `TUNING-DETAIL.md`
has the signatures — `f099775dd9793993` picks a winner at **12.36 us** and ranks
its neighbours 1.6% and 2.9% behind. At that scale launch submission is a
material fraction of the call, and in a decode loop issuing hundreds of such ops
the CPU, not the GPU, is the limiter. A candidate that submits more work per call
looks free on the GPU clock and is not free in production.

#### The rule

Calibrate the harness's own sync cost once per process, then rank on

```
effective_us = max(gpu_median_us, host_median_us - host_sync_overhead_us)
```

The `max` is self-correcting and needs no mode switch: when the host runs ahead
of the GPU (large kernels, deep queue) the second term is smaller and the GPU
number wins, which is right. When submission dominates (tiny kernels) the host
term wins, which is also right.

`median_us` stays the recorded and reported figure; `effective_us` is what the
comparison and the sign test use. Record both, plus `host_sync_overhead_us` in
the header, so the adjustment is auditable rather than invisible.

#### Expected effect, as a falsifiable prediction

`effective_us` must differ from `median_us` on `f099775dd9793993` (12.36 us) and
`7bedae49d322d5d7` (12.56 us), and must not differ measurably on
`615f6214f9597bef` (766 us) or `20a1ffdbaedfc690` (686 us). If it moves the big
signatures, the calibration is wrong.

### E4 — two distinct failures, two distinct reasons

`GGML_HIP_REJECT_UNSTABLE` is declared, named and mapped in Python, and nothing
ever assigns it. Both things it might mean are real, and they are not the same
thing, so they get separate enumerators.

#### `GGML_HIP_REJECT_NOISY` — timing dispersion (new enumerator)

A candidate whose own dispersion exceeds the margin being decided cannot be
ranked, however good its median looks. After the final stage, if
`mad_us / median_us > noisy_mad_ratio` (default 0.25) mark it NOISY and exclude
it from selection while keeping it in the output.

The data already computed pays for this: `mad_us` is calculated at `:484` and
read by nothing.

If *native* is NOISY, reject the signature exactly as an unmeasurable native is
rejected today (`:338-346`) — a baseline that cannot be pinned down is not a
baseline. Record `reason = "native timing unstable; run rejected"`.

#### `GGML_HIP_REJECT_UNSTABLE` — numerical non-determinism

The descriptor carries `deterministic` (`hip-autotune-types.h:255`) and nothing
checks it. Verify it for the **winner only**, after selection: launch it twice
more into scratch with a device-to-host copy after each, and `memcmp`. Differ,
while the descriptor claims determinism, means the candidate is not what it says
it is — mark UNSTABLE, drop it from the tie set, and re-select.

Winner-only bounds the cost at two launches and two copies per signature
regardless of catalog size, and it is the only candidate whose determinism ends
up asserted in a shipped cache.

### E5 — give `gen/elig/meas` a denominator that varies

`result.generated` counts every registry entry that passed the fused-family
filter, so it is the registry size. `TUNING-DETAIL.md` shows the consequence on
every one of its fifteen hot signatures: `270/11/9` for MMQ, `270/26/24` for
MMVQ, `270/22/20`, `270/7/5`. The first number never moves.

`COVERAGE_AUDIT.md:120-131` defines the diagnostic as

> `generated` high, `eligible` low -> an eligibility predicate is too strict

which cannot fire against a constant. Four of the five defects in the RV01-RV05
table were exactly that class of predicate error, so this is the counter that
was meant to catch them and cannot.

Add `applicable`, counted between the two:

```
applicable = supports_arch(candidate, hw)
          && (candidate->variant.src0_type == 0                    // native wrapper
              || candidate->variant.src0_type == sig.src0_type)
```

`variant.src0_type` exists precisely for this and is documented at
`hip-autotune-types.h:177-200` as the field whose absence caused RV01. A native
wrapper leaves it 0 and is admitted unconditionally, matching the existing rule.

Report `gen/appl/elig/meas`. On `4dc5d20446ffea2f` (q8_0) the triple stops being
`270/11/9` and becomes something like `270/60/11/9`, where `11/60` is a ratio
that means something and can be watched across architectures.

Also aggregate rejection reasons into the per-signature log line and the JSONL
result record. The per-candidate array already carries them, but nothing
summarises them, so a sweep of 1151 signatures cannot be read during the run —
only post-processed after it.

### E1 — exact binomial tail and the paired test

```cpp
// P(X >= k) for X ~ Binomial(n, 0.5), exact.
//
// Summed downward from i = n with a running ratio, so no binomial coefficient
// is ever materialised and nothing overflows for any n the tuner can produce.
//   C(n, i-1) = C(n, i) * i / (n - i + 1)
double binomial_tail_ge(int k, int n) {
    if (k <= 0) return 1.0;
    if (k >  n) return 0.0;
    double term = std::exp(-(double) n * std::log(2.0));   // C(n,n) / 2^n
    double sum  = term;
    for (int i = n; i > k; --i) {
        term *= (double) i / (double) (n - i + 1);
        sum  += term;
    }
    return std::min(sum, 1.0);
}

// Paired sign test over the interleaved final rounds.
//
// Only the direction of each paired difference is used, so one preempted round
// costs a single vote instead of dominating a mean -- the same reasoning that
// put MAD in this file rather than stddev.
//
// Returns the one-sided p-value for "candidate is faster than baseline", and
// 1.0 when too few usable rounds survive to say anything.
double paired_sign_test(const std::vector<double> & baseline,
                        const std::vector<double> & candidate,
                        int min_rounds, int & wins_out, int & rounds_out) {
    wins_out = rounds_out = 0;
    const size_t rounds = std::min(baseline.size(), candidate.size());
    int wins = 0;
    int n    = 0;
    for (size_t r = 0; r < rounds; ++r) {
        // NaN marks a round where that candidate failed to launch; the pairing
        // is only meaningful when both sides produced a sample in the *same*
        // round, which is why failures pad rather than shorten the vector.
        if (std::isnan(baseline[r]) || std::isnan(candidate[r])) continue;
        if (candidate[r] == baseline[r]) continue;   // tie: excluded, standard
        if (candidate[r] < baseline[r]) ++wins;
        ++n;
    }
    wins_out = wins; rounds_out = n;
    return n < min_rounds ? 1.0 : binomial_tail_ge(wins, n);
}
```

#### Keeping the rounds aligned

In the final stage, replace the conditional append with an unconditional one:

```cpp
for (int round = 0; round < config.final_samples; ++round) {
    for (size_t i = 0; i < finalists.size(); ++i) {
        std::vector<double> g1, h1;
        if (time_candidate(finalists[i]->candidate, lc, 0, 1,
```

#### The replacement decision

```cpp
// Effect size and consistency are different questions and both must answer yes.
// Effect without consistency is RV21: a 14% "win" between two runs of the same
// kernel. Consistency without effect is a reproducible 0.05% that is not worth
// a cache entry.
std::vector<Measurement *> qualified;
for (Measurement * m : tied) {
    if (m == native_m) { qualified.push_back(m); continue; }
    int wins = 0, rounds = 0;
    m->sign_p = paired_sign_test(native_m->final_gpu_us, m->final_gpu_us,
                                 config.min_paired_rounds, wins, rounds);
    m->sign_wins   = wins;
    m->sign_rounds = rounds;
    const double impr = 100.0 * (native_m->effective_us - m->effective_us)
                        / native_m->effective_us;
    if (impr >= config.replacement_threshold_pct &&
            m->sign_p <= config.confidence_alpha) {
        qualified.push_back(m);
    }
}

if (qualified.empty() || qualified.front() == native_m) {
    result.winner = native.candidate;
    result.reason = rounds_were_short
        ? "native retained (too few paired rounds to confirm any challenger)"
        : "native retained";
} else {
    std::sort(qualified.begin(), qualified.end(), tie_order);  // existing sort
    result.winner     = qualified.front()->candidate;
    result.confidence = 1.0 - qualified.front()->sign_p;
    result.reason     = "measured winner, " +
        std::to_string(qualified.front()->sign_wins) + "/" +
        std::to_string(qualified.front()->sign_rounds) + " paired rounds";
}
```

### E3 — calibrating the harness's own sync cost

```cpp
// The floor cost of one timed sample with no work in it: two event records, a
// synchronize, and the two host clock reads. Subtracting it is what makes a
// host-side number comparable with a GPU-side one.
//
// Measured once per process on the tuning stream. Cheap, and constant enough
// that a per-signature recalibration would only add noise.
double ggml_hip_tuner_host_sync_overhead_us(cudaStream_t stream) {
    static double cached = -1.0;
    if (cached >= 0.0) return cached;

    hipEvent_t a, b;
    hipEventCreate(&a); hipEventCreate(&b);
    std::vector<double> samples;
    for (int i = 0; i < 20; ++i) {
        const int64_t t0 = ggml_time_us();
        hipEventRecord(a, stream);
        hipEventRecord(b, stream);
        hipEventSynchronize(b);
        samples.push_back((double) (ggml_time_us() - t0));
    }
    hipEventDestroy(a); hipEventDestroy(b);
    cached = median_of(samples);
    return cached;
}

// max(), not a mode switch: whichever resource is binding is the one that
// bounds the call, and the other term is smaller by construction.
inline double effective_us(const Measurement & m, double sync_overhead_us) {
    return std::max(m.median_us, m.host_median_us - sync_overhead_us);
}
```

## Validation

Each check is written so that failing it points at one change.

### E1 — paired sign test

- **Unit, offline.** `binomial_tail_ge(12, 15) == 0.017578125` exactly
  (576/32768), `binomial_tail_ge(11, 15) == 0.059204...`, `binomial_tail_ge(0, n) == 1.0`,
  `binomial_tail_ge(n, n) == 2^-n`. These are the values the 15-sample default
  turns on, so they are worth pinning rather than eyeballing.
- **Behavioural.** A run at `GGML_HIP_TUNE_FINAL_SAMPLES=3` must produce **zero**
  non-native winners, because no 3-round outcome can reach p <= 0.025. If any
  signature still reports a forced winner, the test is not gating the decision.
- **Regression against a known-good result.** Re-tune the RV19 production
  configuration. `4dc5d20446ffea2f` (+44.35%) and `d4d829f52511ebc2` (+69.76%)
  must keep their winners at 15/15 or 14/15 rounds. `035282e415599068` (+2.68%,
  native 4th at +2.8%) is the interesting one: it either passes with a
  respectable round count or it is revealed as noise, and both outcomes are
  informative.
- **Alignment.** With a candidate forced to fail every third round (test hook),
  the paired test must report `rounds` equal to the number of successful pairs,
  and medians must be unchanged from a NaN-free run.

### E2 — raw samples

- `samples_us` length equals `final_samples` for every finalist, NaN included.
- A Python re-run of winner selection over the JSONL alone reproduces every
  `winner` field in that same file. This is the real test: it proves the decision
  is reconstructible without hardware.

### E3 — effective_us

- `host_sync_overhead_us` is stable within 20% across three consecutive process
  starts on an idle GPU.
- `effective_us != median_us` on `f099775dd9793993` (12.36 us) and
  `7bedae49d322d5d7` (12.56 us).
- `effective_us == median_us` to within 0.5% on `615f6214f9597bef` (766.85 us)
  and `20a1ffdbaedfc690` (685.85 us). Movement on the large signatures means the
  calibration is wrong, not that a discovery was made.

### E4 — NOISY / UNSTABLE

- Tuning while a second process loads the GPU produces NOISY rejections; the
  same sweep on an idle GPU produces none. This is the same discriminator HI24's
  canary uses, and the two must agree on which runs were contaminated.
- A candidate stubbed to return a counter in its output is rejected UNSTABLE and
  the next qualified candidate is selected instead.
- `deterministic == 0` candidates are never subjected to the check.

### E5 — coverage denominator

- `applicable` varies across signatures within one sweep. If it is constant, it
  has been computed wrong — that is the whole defect being fixed.
- On a q8_0 MMQ signature, `applicable` excludes every `mmvq:q4_0:*` and
  `mmf:f32:*` candidate, and `applicable >= eligible` always holds.
- Reproduce RV01 deliberately (revert `variant.src0_type` population): the
  eligible/applicable ratio must collapse visibly in the log **before** the sweep
  reaches signature 198 and aborts. This is the check that would have turned a
  four-defect archaeology into one log line.

### E6 — compiler

- `SELECT compiler FROM build` is non-null after `python -m bigcherry.inventory`.
- Two builds from different ROCm versions produce two `build` rows, not one.

### Cross-cutting

- `test-backend-ops -o MUL_MAT` still reports 0 failures and `2/2 backends
  passed` on gfx1100 and gfx1201.
- Tune wall time per sweep grows by less than 5% — E1/E3/E5 are arithmetic over
  data already collected, and only E4's determinism check adds launches (two per
  signature).

## Effort & Risk

**M on top of a working engine, not L.** Five of the six changes are arithmetic
over values the tuner already computes and then discards: the paired rounds
(E1), the host medians (E3), the MADs (E4-NOISY), the registry walk (E5). Only
E4's determinism recheck adds device work, and it is bounded at two launches per
signature.

**The one behavioural risk is E1, and it is deliberate.** Requiring statistical
confidence will reduce the count of non-native winners, possibly sharply at low
sample counts — by construction, `FINAL_SAMPLES=3` will produce none at all.
That will look like a regression against the "75 forced winners out of 95"
headline in HANDOFF. It is not: those winners were selected by median comparison
at sample counts RV21 showed carry ~14% error, and the honest reading is that an
unknown fraction of them were noise. Re-tune at `FINAL_SAMPLES=15` before
comparing counts, and compare *call-weighted saving* rather than win counts —
the RV19 10.2% figure is the number that should not move.

**Sequencing.** E5 and E6 are independent and can land first; they change no
decision. E1 depends on E3 only in that both feed the same comparison, so land
E3 first and E1 against `effective_us` rather than retrofitting. E4's NOISY
interacts with HI24's canary — both detect a contaminated run — so land HI24's
canary first (it is already implemented) and treat disagreement between them as
a bug in one of the two.

**Ordering against HI34.** HI34 changes `launches_per_sample`, which changes
every timing this item compares. Land HI12's E-series first so there is a stable
decision rule to evaluate HI34 against; otherwise both change at once and
neither can be attributed.
