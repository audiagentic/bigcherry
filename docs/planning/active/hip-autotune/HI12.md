# Implement family-level tuning engine with complete-path timing and correctness validation

## Description

Patch 9 — implement the full tuning engine (hip-autotune-tuner.cu, hip-autotune-metrics.cpp). Complete-path event timing, native reference output, hard eligibility screening, warmup/screen/finalist stages, measurement persistence, and winner selection with replacement threshold.

**B2: Screening retention policy** — retain the native candidate (always) + top 3 by median + every candidate within 10% of best median. Parameterised as `screen_keep_top = 3`, `screen_keep_within_pct = 10`.

## Steps

- Implement scratch destination and workspace allocation for each candidate
- Native reference output generation using native candidate
- Complete-path HIP event timing including activation quant/setup (not just terminal kernel)
- **Host-side timing** — record `host_median_us` alongside GPU time; a tiny kernel can win on GPU time and lose on wall clock, which is precisely the case for MMVQ geometry variants (B3)
- **Median absolute deviation** — record `gpu_mad_us` (not only stddev); GPU timings are right-skewed and a single preemption makes stddev useless (B3)
- Warmup launches (10-20), screening samples (15-30), final samples (100)
- Candidate order randomization/interleaving in final measurement
- Correctness validation: NMSE, max absolute error, NaN/Inf detection
- Measurement persistence to SQLite with raw sample data
- Winner selection: lowest median GPU time, 1% replacement threshold, workspace_bytes filtering, near-tie tiebreaker
- Near-tie resolution: collect candidates within `tie_pct` (default 0.5%) of best; sort by `(p95, workspace_bytes, not_native, name)`
- **Winner reason** — record `winner.reason` (text explanation of why the candidate won) for each winner (HANDOFF + B3)
- **Build compiler** — record `build.compiler` (compiler version/identifier) in build table (HANDOFF + B3)
- **Build dispatch ABI** — record `build.dispatch_abi` (dispatch ABI version) in build table (HANDOFF + B3)
- Native must be measured — reject tuning run for that signature if native is absent from valid measurements
- Hot-signature-first priority by call frequency

### Schema prework (before first tune)

The following fields are missing from `sql/dispatch-db.sql` and must be added before the first tuning run writes measurements:

- `winner.reason` — text explanation of why the candidate won (HANDOFF + B3)
- `build.compiler` — compiler version/identifier (HANDOFF + B3)
- `build.dispatch_abi` — dispatch ABI version (HANDOFF + B3)
- `measurement.gpu_mad_us` — median absolute deviation for GPU timings (B3)
- `measurement.host_median_us` — host-side median time per sample (B3)

Final state on brutus (gfx1100, ROCm 7.2, `workload-max` from `artifacts/mtp-inventory.json`), driving `test-backend-ops -o MUL_MAT` under `GGML_HIP_DISPATCH_MODE=tune`:

Getting there took five defects, each found only by running on hardware, each masked by the one before it. The progression is worth keeping because it shows the engine was never the problem — eligibility was:

| Fix | Sweep reached |
| --- | --- |
| (start) | immediate abort |
| RV01 — candidate src0 type absent from the descriptor | 198 |
| RV02 — MMQ predicate broader than upstream's tables | 243 |
| RV03 — MMF eligibility ignoring type and arch | 366 |
| RV04 — src1 F32 precondition unchecked in all four families | 810 |
| RV05 — tuner measuring inside HIP graph capture | **1151, complete** |

**The pattern matters more than any single fix.** Four of the five are the same defect class: an eligibility predicate that approximates what the build actually instantiated, wrong in a different direction each time — type absent entirely, predicate broader than the tables, type and arch unchecked, a documented precondition never read. Two of them did not abort cleanly; RV03 faulted as an HSA hardware exception that took the queue down and read as a driver fault.

The structural fix is recorded in RV03's conclusion: derive eligibility from the instantiation set the build already knows (`template-instances/*.cu`, the config tables the catalog already parses) instead of hand-maintaining predicates alongside it. Worth pairing with an HI16 test that launches every registered candidate against a signature it claims to serve — that finds this whole class offline, in seconds, instead of as a device fault after 800 signatures.

**The engine itself is behaving.** `gen/elig/meas` is reported per signature and is what made each defect visible as a number before it became a crash — keep it prominent. Forced MMVQ geometries beat native on real signatures (see HI09), so the tuner measures and prefers non-native candidates rather than always falling back.

**Still open:**

- Cross-architecture validation on gfx1201 (RDNA4) and gfx1030 (RDNA2) — in progress. Four of the fixes give architecture-dependent answers and have only ever been exercised on one architecture, so a predicate that is accidentally right on RDNA3 is currently unproven. RDNA2 is the sharpest test (no WMMA at all, so every MMF float type should be ineligible, and it exercises `ggml_cuda_mmq_get_config_rdna2`, a table nothing has touched). RDNA4 is where RV03's ncols 9..16 trade-off is falsifiable.
- Tuning is **skipped**, not deferred, under graph capture (RV05). A signature only ever seen inside a captured graph is never tuned. See HI14.
- Schema fields still missing before a real tune (B3): `winner.reason`, `build.compiler`, `build.dispatch_abi`.
- Any tuning output produced before RV01 is invalid — winners may have been measured on a different type than they name.

Earlier planning notes retained:
