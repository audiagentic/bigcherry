# Real production signature time-share audit -- distinguish 'native won because searched' from 'native because never searched'

## Description

A dev-gpt-agent deep-dive (2026-08-24, session ses_05a713a4e4e44b2d, prompted after HI105's null result on MoE candidate tuning) raised a real, unverified assumption this project has been implicitly making: that the large non-MoE ops recorded during real campaigns (e.g. the lm_head/vocab-projection matmul with ne1[1]=124160, or attention ops at ne1[1]=16384/4096) are correctly resolving to native/blas:native because that IS optimal, rather than because they were never seriously searched. GPT's specific claim (NOT YET VERIFIED against real source -- must be checked before acting on it): enumerate_blas() only provides the first forced-native structured plan; provider/API alternatives are deferred rather than exhaustively searched, unlike MMQ/MMVQ which really does enumerate J/config/geometry candidates.

This matters because HI105's real campaign showed MoE-routed matmuls (MUL_MAT_ID) are too small a compute share to matter for full-model throughput, even with real, correctness-verified, promoted candidates. If the large non-MoE ops are ALSO under-searched, that's a much bigger, more promising target than anything MoE-related -- but if they're already properly searched and native genuinely wins, that's worth knowing too, so effort isn't wasted chasing a dead end a second time.

## Steps

1. Verify GPT's enumerate_blas() claim directly against real source (tools/bigcherry or ggml/src/ggml-cuda's blas enumeration code) -- do not take it on faith, same discipline as the rest of this session.
2. For the real signatures already captured in a campaign (e.g. HI105's moe_tune.jsonl.measurements.jsonl, or a fresh capture), classify every signature by: aggregate production GPU time share (not just isolated candidate microbenchmark time -- use real profiler/critical-path data if available, not FLOPs or calls x isolated_us alone, especially relevant on dual-GPU tensor-split), call count, candidate_count actually measured, best measured delta, and promotion/gate status.
3. Separate this classification for pp512 (prefill) and tg128 (decode) -- the dominant signatures differ between the two (confirmed empirically in HI105/RD54: MoE decode vs prefill candidates are structurally different signatures).
4. Identify which large-time-share signatures have candidate_count=0 or 1 (never meaningfully searched) vs candidate_count>1 with native winning (genuinely evaluated, native is the real winner).
5. Report findings; file follow-up RD/HI items only for signatures found to be under-searched with real time-share evidence, not speculation.
