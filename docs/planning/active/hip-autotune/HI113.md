# tune/control-mode live dispatch resolution needs more VRAM headroom than production KV-cache settings leave -- real reproducible ROCm OOM

## Description

HI109 (real dense Qwen3.8-27B/Q8_0 production campaign, 2026-08-24 Brutus): both `GGML_HIP_DISPATCH_MODE=tune` and a plain `control`-lane build (GGML_HIP_AUTOTUNE=ON, no replay) crashed with a real, reproducible `cudaMalloc failed: out of memory` at model load, at full real production KV-cache settings (n_slots=4, n_ctx_slot=8192, i.e. no -c/--parallel override -- the actual production launch flags). The error is in `ggml_backend_meta_buffer_type_alloc_buffer`/`ggml_gallocr_reserve_n_impl`, hit during `llama_context::graph_reserve()` while `common_speculative_init_result` sets up the MTP draft context.

GPUs were confirmed free before each attempt (rocm-smi showed 0 KFD processes, ~28MB baseline usage on both real cards). Reproduced 3 times for the control build (2 back-to-back retries, same exact 1360.28 MiB allocation failing both times) and once for tune mode.

Root cause hypothesis (not yet confirmed by reading source): both `tune` and `control` modes perform LIVE dispatch resolution against the compiled native-candidate registry at graph-reserve time (tune benchmarks candidates; control still resolves/searches among native candidates even though it never replaces the winner), which needs scratch workspace on top of whatever the model + KV cache already use. `record` mode does not hit this -- it only logs signature shapes, never touches the resolve/search path -- and loaded fine with the identical real production flags in the same session. `replay` mode's actual VRAM behavior at full production settings was never independently tested this session (the A/B always ran it at the same reduced -c 8192 --parallel 4 as the native comparison side, for a fair comparison -- so replay's real per-production-flags VRAM footprint is still unconfirmed).

Workaround used this session: reduce to `-c 8192 --parallel 4` for both tune-mode and any control/native-comparison server. This is a real deviation from production flags and was applied to BOTH sides of the A/B for fairness, but it means HI109's A/B numbers were not measured at actual production KV-cache settings.

## Steps

1. Read the tune/control dispatch-resolve path (hip-autotune-tuner.cu / hip-autotune-dispatch.cu) to find what workspace it allocates at graph-reserve time and whether it scales with candidate-registry size, batch width, or something else.
2. Confirm whether `replay` mode has the same VRAM headroom requirement at full production settings (untested this session) -- if replay is fine at full settings, the workaround only matters for tune/control, which is lower-stakes (rerunning a tuning session vs. a real user-facing OOM in production).
2b. If replay ALSO needs headroom beyond production defaults, this is a release-blocking finding, not just a tuning-workflow inconvenience -- escalate.
3. Either reduce/bound the workspace tune/control allocate at graph-reserve, or document the required KV-cache headroom formula so a tune-mode campaign against a near-VRAM-limit production config can size -c/--parallel correctly up front instead of hitting a live-hardware crash.
