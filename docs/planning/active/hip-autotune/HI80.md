# Correctness-evidence generation CLI (op_filter/target_tensor derivation from a promoted row's signature)

## Description

HI67 slice 3's correctness GATE (tools/bigcherry/promotion_correctness_gate.py, called automatically inside tune_promotion.promote()) is real and enforced -- confirmed this session when two genuine routing-transform winners (batch_for_mmvf, +49.5%/+18.3%, both passing full statistical confirmation) correctly hit `rejected_no_correctness_evidence` because no evidence exists yet. The GENERATION side (tools/bigcherry/correctness_evidence.py: collect_seed_evidence/generate_correctness_evidence/write_correctness_evidence) is implemented as a library but has NO CLI entrypoint and no orchestration loop -- nothing calls it for a batch of promotable rows today. generate_correctness_evidence() requires the caller to supply `op_filter` (a `-p` regex matching test-backend-ops' own generated test-case description string, e.g. "MUL_MAT(type_a=f32,...,m=128,n=1,k=1057,...)") and `target_tensor` directly -- there is no existing helper mapping a promoted row's canonical/signature JSON into that exact regex+tensor-name pair, and getting this wrong would silently produce evidence for the WRONG signature (a correctness-of-the-safety-gate risk, not just a usability gap). Needs: (1) a signature->op_filter/target_tensor mapping helper, verified against real test-backend-ops output for known signatures; (2) a CLI (e.g. `bigcherry generate-correctness-evidence <measurements.jsonl> --dispatch-db <db> --binary <patched-test-backend-ops>`) that loops over pending_bh rows, runs generate_correctness_evidence per row with a versioned seed set, and calls write_correctness_evidence; (3) wiring into e2e_smoke_campaign.py as an optional stage between promote and export, so real transform/candidate winners can actually reach promoted status end-to-end.

## Detailed Solution & Technical Design

New module tools/bigcherry/signature_correctness_mapping.py implements the first concrete gap HI80 identified: mapping a real BigCherry dispatch signature JSON into the exact op_filter regex and target_tensor name generate_correctness_evidence() needs.

load_ggml_type_names(vendor_root) and load_ggml_op_names(vendor_root) parse the real vendored source directly (ggml/include/ggml.h's enum ggml_type / enum ggml_op declarations, ggml/src/ggml.c's type_traits table and GGML_OP_NAME array) rather than hand-transcribing a lookup table -- this eliminates the drift risk a hardcoded dict would carry if the vendor pin moves and an enum gets reordered or a type gets renamed.

signature_to_op_filter(signature, vendor_root) is MUL_MAT-only this slice (the op actually blocking HI80's own referenced blocked wins). It derives type_a/type_b from src0_type/src1_type via the parsed type-name table, and m/n/k from the signature's ne0/ne1 4-element arrays (m=ne0[1], n=ne1[1], k=ne0[0]==ne1[0], verified against test-backend-ops.cpp's struct test_mul_mat build_graph()).

Corrected mid-implementation against the REAL caller: run_test_backend_ops() in correctness_evidence.py already hardcodes -o MUL_MAT and passes op_filter straight through as -p's value, and test-backend-ops' own -p matching (std::regex_search against test_case::vars() alone, main(), ~line 10602) does NOT include the op name or parentheses -- only the comma-joined vars() string. An earlier draft of this function built an op_filter shaped like 'MUL_MAT(type_a=...)' before this was caught and fixed by reading the actual caller and confirming on real Brutus hardware.

Also hardware-discovered and fixed: bs/nr/per/k_v/o cannot be reconstructed from a BigCherry signature (ne0[2]/ne0[3] carry the PRODUCT bs[i]*nr[i] with no way to recover the factors). Wildcarding them was tried first and found, on real hardware, to match 13 DISTINCT registered test cases for one (type_a,type_b,m,n,k) tuple -- all producing a tensor named 'out', which find_digest_for_tensor()/find_metric_for_tensor() match by name alone, so an unpinned filter could silently take evidence from the wrong one of the 13. Fixed by fully anchoring the filter (^...$) to the expected non-batched default (bs=[1,1], nr=[1,1], per=[0,1,2,3], k_v=0, o=1), confirmed by hardware to collapse the same query to exactly 1 match.

### 2026-08-23: real Brutus run attempted -- found a genuine, deeper coverage gap, not a bug in the CLI

Built a fresh test-backend-ops with patches 1222+1223 applied (`~/bc-build-hi64hi14`, GGML_HIP_AUTOTUNE_RECORD=ON), located the real campaign artifacts on Brutus (`/home/audumla/e2e-smoke-gptoss20b/`: real dispatch.sqlite + tune.jsonl.measurements.jsonl, containing the real a8ef5ddb... dispatch), and ran `python3 -m bigcherry.hi80_generate_correctness_evidence` against them for real.

First sanity-checked the binary/patches themselves work correctly: ran a synthetic registered shape (`m=16,n=1,k=256`) directly and confirmed both BIGCHERRY_REF_DIGEST and BIGCHERRY_CORRECTNESS_METRIC markers fire exactly as designed. The mechanism itself is sound.

The real CLI run against the 8 promotable rows in that measurements file: 7 MUL_MAT rows FAILED with 'missing BIGCHERRY_REF_DIGEST for tensor out' (1 non-MUL_MAT row correctly SKIPPED, matching the item's own documented MUL_MAT-only scope). Investigated dispatch a8ef5ddb's real canonical signature: `ne0=[2880,32,1,1], ne1=[2880,21,1,1]` -- m=32, n=21, k=2880, f32/f32. This is a genuine real gpt-oss-20B model dimension (k=2880 is a real hidden-dim-adjacent size for that model), and it is NOT one of test-backend-ops' own fixed synthetic test-case shapes (which use round numbers like 256/2048, not 2880) -- so `signature_to_op_filter()`'s derived regex correctly describes the real signature, but matches ZERO registered test-backend-ops cases, so the binary runs 0 tests for it and emits no BIGCHERRY_REF_DIGEST/BIGCHERRY_CORRECTNESS_METRIC output at all.

**This is the real, previously-undiscovered limitation of HI80's current design: it can only generate correctness evidence for a promoted-row signature that HAPPENS to coincide with one of test-backend-ops' own fixed synthetic shapes.** Real production dispatch shapes (derived from an actual model's real tensor dimensions during real inference) generally do NOT coincide with that fixed corpus -- confirmed directly for this exact blocked win. The op_filter/target_tensor mapping machinery (signature_correctness_mapping.py) is correct and does what it claims; the gap is one level up, in test-backend-ops' own test-case generation never producing a case for an arbitrary real shape.

**Consequence:** HI80's stated real-hardware acceptance criterion ('generate real evidence for the 2 blocked routing-transform wins, reach promoted status') is NOT achievable with the CLI as currently designed, for THIS pair of dispatches, without one of:
1. Extending test-backend-ops itself (a real patch, new scope) to accept an arbitrary custom shape via a CLI flag or env var, rather than only filtering its own fixed generated corpus -- the natural fix, but nontrivial: test-backend-ops' test-case generation is upstream code, and adding a 'test exactly this m/n/k/type' escape hatch needs careful design (see patches/1222/1223's own precedent for how this codebase adds narrow, additive hooks to vendored test infra).
2. Finding a DIFFERENT promotable win whose real dispatch shape happens to already coincide with a registered test-backend-ops case (unreliable, not a real solution, just luck).

Not attempted this session -- extending test-backend-ops' shape coverage is a real, separate engineering task with its own design questions (how to specify an arbitrary shape safely, whether it needs its own patch number, whether it conflicts with 1222/1223's existing hooks), not a quick follow-up. Filing this finding here rather than a new item since it's a refinement of HI80's own scope, not a separate concern -- whoever picks up HI80 next needs this as the actual next blocker, not the CLI-doesn't-exist gap the item was originally filed for (that gap is now closed; this is the next one).

### 2026-08-23: RESOLVED -- test-backend-ops --test-file escape hatch + a second real fix (digest tensor decoupling)

**Finding 1 (corpus mismatch, no new patch needed):** signature_to_op_filter() only ever produces evidence when a real dispatch signature coincides with one of test-backend-ops' own fixed synthetic corpus shapes -- confirmed on Brutus that a real gpt-oss-20B MUL_MAT (m=32,n=21,k=2880) matches none of them. test-backend-ops already has a general escape hatch for exactly this: `--test-file <path>`, read by `make_test_cases_from_file()` into one `test_generic_op` per line, which builds a graph directly from the given op/type/ne/sources instead of the fixed generator -- works for ANY signature, no new patch to test-backend-ops itself. Added `signature_correctness_mapping.signature_to_test_file_line()` (MUL_MAT-only, F32/F16/BF16 only -- quantized types need block-size-aware byte-stride math not attempted this slice) and threaded an optional `test_file` parameter through `correctness_evidence.py`'s `run_test_backend_ops()`/`collect_seed_evidence()`/`generate_correctness_evidence()`, with `hi80_generate_correctness_evidence.py`'s `generate_for_row()` switched to use it as the primary path.

**Finding 2 (found while validating Finding 1 on real hardware):** the first real end-to-end CLI run against the exact blocked dispatch STILL failed -- 'missing BIGCHERRY_REF_DIGEST for tensor out' -- even though a manual replica of the exact same subprocess call succeeded. Root-caused by comparing full real stderr: `test_generic_op`'s destination tensor is NEVER pre-filled with random data before the op runs (a registered test case like `test_mul_mat` apparently does this, incidentally giving its named destination a BIGCHERRY_REF_DIGEST line too; `test_generic_op` does not), so 'out' never gets a REF_DIGEST line at all -- even though its BIGCHERRY_CORRECTNESS_METRIC line (the actual correctness comparison) fires correctly regardless. The REF_DIGEST check's real purpose (proving native and candidate runs saw the SAME reference input) doesn't actually need the destination tensor's digest -- a genuine input/leaf tensor works just as well and is always present. Fix: `collect_seed_evidence()`/`generate_correctness_evidence()` gained a separate `digest_tensor` parameter (defaults to `target_tensor` if omitted, exactly preserving the old op_filter-path behavior), and `signature_to_test_file_line()` now returns a 3-tuple `(line, target_tensor='out', digest_tensor='leaf_0')` -- 'leaf_0' is ggml's own auto-assigned name for the first unnamed source tensor (verified directly against real stderr: nels=92160 matches src0's real element count for this signature).
