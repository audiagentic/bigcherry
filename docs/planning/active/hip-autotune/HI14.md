### 2026-08-22: real capture-lifecycle instrumentation landed (patch 1231)

Per GPT's priority ranking (req_559bb03e75494a74, HI14 ranked #2 after HI67): the headline gap above -- no runtime producer for capture_begin/capture_end/instantiate/replay evidence -- is now closed at the instrumentation level. New patches/1231_hi14_graph_capture_lifecycle_evidence.py instruments the four real HIP graph API call sites in ggml-cuda.cu's ggml_backend_cuda_graph_compute()/ggml_cuda_graph_evaluate_and_capture() (cudaStreamBeginCapture, cudaStreamEndCapture, cudaGraphInstantiate, cudaGraphLaunch -- confirmed against the real vendored file), each immediately after its CUDA_CHECK() succeeds, with a once-per-process BIGCHERRY_GRAPH_LIFECYCLE stage=<name> marker gated behind BIGCHERRY_GRAPH_LIFECYCLE_TRACE (zero-cost by default). ### 2026-08-23: REAL HARDWARE CLOSURE of the headline capture-lifecycle gap

Ran the dual-XTX graph-on workload the 2026-08-22 instrumentation (patch 1231) needed but had never been exercised against, on real Brutus hardware: `~/bc-build-hi64hi14/bin/llama-server` (built 2026-08-23 03:29, GGML_HIP_RCCL=ON, AMDGPU_TARGETS=gfx1100;gfx1201;gfx1030 -- production-matching, and carries the HI64 per-device poison-scoping fix too), HIP_VISIBLE_DEVICES=0,1 / ROCR_VISIBLE_DEVICES=0,1 (both real RX 7900 XTX, gfx1100, confirmed via server log 'ROCm0'/'ROCm1'), real production launch flags from the dual-xtx-27b bench profile (-sm tensor --tensor-split 1,1, --flash-attn on, --ubatch-size 512 --batch-size 2048, -ngl 99, --spec-type draft-mtp --spec-draft-n-max 4, -ctkd/-ctvd q8_0, -c 64000), real production model (/mnt/vault/llm-models/qwen3.8-27b/gguf/mtp/Qwen3.8-27B-Q8_0.gguf), BIGCHERRY_GRAPH_LIFECYCLE_TRACE=1, default GGML_HIP_DISPATCH_MODE (AUTO/native -- no forced replay needed for this evidence).

REAL FINDING along the way, worth recording: the first attempt at default server verbosity (-lv unset, i.e. verbosity=3) produced ZERO BIGCHERRY_GRAPH_LIFECYCLE log lines despite the server log's own 'graphs reused = 27/47' counters proving graphs WERE genuinely captured and replayed. Root-caused by reading vendor/llama.cpp/common/log.cpp: raw ggml GGML_LOG_INFO calls (as opposed to llama-server's own tagged LOG_INF macro) are mapped by common_get_verbosity() to LOG_LEVEL_TRACE=4, which the default verbosity threshold (3) silently drops before they ever reach the log sink -- confirmed the compiled binary genuinely contains the instrumentation (`strings libggml-hip.so | grep BIGCHERRY_GRAPH_LIFECYCLE` found all 4 stage strings) and the running process's real /proc/<pid>/environ had the trace var set, ruling out both an unbuilt-patch and an unset-env-var explanation. This means patch 1231's markers are silently invisible at any llama-server verbosity below `-lv 4` in production -- a real, previously-undocumented visibility gap in the instrumentation itself, distinct from whether graphs work (they do). Re-ran with `-lv 4` and got clean, real markers.

Sent 3 real completion requests (varying prompt/length) through the running server via curl; server log shows graphs reused=27/57/88 across the run (monotonically increasing, confirming genuine reuse, not just capture). grep of the real server log found exactly one occurrence each of BIGCHERRY_GRAPH_LIFECYCLE stage=capture_begin/capture_end/instantiate/replay (matching the once-per-process atomic_flag guard in the instrumentation). Pulled the log locally and ran it through the real `graph_lifecycle_evidence.capture_lifecycle_from_log()` (tools/bigcherry/graph_lifecycle_evidence.py, unmodified, offline-verified code from 2026-08-22): result `{'capture_begin': True, 'capture_end': True, 'instantiate': True, 'replay': True}` -- exactly the shape `validate_multi_gpu_evidence()`'s `graph.capture_lifecycle` requires.

This closes the item's own headline gap, repeated verbatim across the PH01 scan and RV60 notes below: 'no real-run capture-lifecycle evidence (capture_begin/instantiate/replay) exists anywhere.' It now does, from real dual-gfx1100 hardware running the actual production topology, flags, and model.

**NOT YET DONE (stays open, narrower than before):** a full `validate_multi_gpu_evidence()` pass also needs `per_device` dispatch/replay_dispatches/signatures/winners counts, which need per-dispatch telemetry (RECORD mode or a dispatch DB), not just the graph-lifecycle log markers gathered here. `bc-build-hi64hi14` was NOT built with `GGML_HIP_AUTOTUNE_RECORD=ON` (confirmed via hip-autotune-dispatch.cu's own `#ifndef GGML_HIP_AUTOTUNE_RECORD` guard, which downgrades RECORD mode to native with a warning if the symbol is absent), so this same run's telemetry can't retroactively supply that half -- it needs a separate build+run. The remaining matrix rows (mixed gfx1100/gfx1201 tensor split, multiple-XTX-only beyond this pair, long-context server-workload qualification) are also still open, unchanged from the PH01 scan.
