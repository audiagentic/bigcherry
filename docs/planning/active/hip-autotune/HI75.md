# HI36b — generalised dispatch runtime: two-level lookup and generalised cache entries on replay v5

## Description

Runtime/cache implementation of winner generalisation, GO'd by the 27B R9700 verdict (docs/reference/HI36A_VERDICT_27B_R9700.md) for mmq and mmvq. HI36a is closed; this is the deferred half per the 2026-08-21 adjudication, and it lands on replay v5 (HI74), not v4.

## Steps

- 1. Wait for HI74 (v5 foundation, match_kind discriminator) to land — the generalised route is a new match_kind value, not a v4 cache-format change. The ENT_SIGNATURE[0]=1 marker design in HI36's stale code samples is INVALIDATED (v4 writes the real signature digest there); do not implement from it.
- 2. Implement the generalised digest: reuse the canonical signature JSON with the frozen key mask (mmq: family+src0_type+K+M; mmvq: family+src0_type+full ne0), distinct personalisation prefix, C++ and Python byte-identical, pinned by cross-language test vectors.
- 3. Export: generalised entries are ordinary entries under the generalised dispatch digest, one per group, representative = highest-call-count promoted winner per the frozen rule; assert on exact/generalised digest collision at export.
- 4. Dispatch: two-level lookup (exact v5 match first, generalised second, native third) with the standard runtime guards — the generalised key yields a recommendation, can_execute against the real target signature is the authorization.
- 5. Provenance: separate exact/generalised/miss counters in coverage; a generalised hit is never reported as an exact hit; generalised entries carry their own match_kind so replay format version + route schema version are self-describing (HI37).
- 6. Re-run promotion on HI67-final tooling (the S6 evidence used pre-slice-3 tooling) and re-apply the verdict gates to the new miss log before shipping.
- 7. Re-run the S7 same-workload replay and both holdouts (12k + parallel-2) against the shipped cache: exact counts unchanged on the tuned workload, generalised conversions match the what-if prediction (49/49 on this evidence).

## Detailed Solution & Technical Design

The HI36 item's Step 4-5 design (two-level lookup, provenance counters, exporter, cross-language vectors) still stands as the implementation blueprint EXCEPT the 'Two findings' code-sample section, which the 2026-08-20 PH01 audit invalidated against the v4 wire format. On v5 the correct hook is the match_kind discriminator: EXACT entries keep today's semantics, GENERALISED entries carry the generalised route id + the representative's provenance. Safety argument unchanged: per-entry guards (loader drops unknown candidates; can_execute re-run before launch) make the worst case an eligible-but-suboptimal candidate, bounded by the measured regret (≤1.10% on 27B evidence).
