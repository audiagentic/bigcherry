# Fix real correctness failure in mmvf:f32 w8:bs32 and w1:bs160 candidates

## Description

During a broader real MoE tune campaign on Qwen3.6-35B-A3B (built on top of HI105's now-working MUL_MAT_ID correctness-evidence path), hi80_generate_correctness_evidence.py caught two real, non-MoE candidates that fail CPU-reference correctness on all 3 deterministic seeds while native succeeds cleanly on the same seeds -- a genuine dispatch/kernel bug, not a tooling gap. Both are plain MUL_MAT (op=29, no HAS_IDS flag), F32 source type, mmvf family:

- dispatch=5e47944021eb0874c452b3f9d5e7a11b: ne0=[256,256,1,1], ne1=[256,8,1,1], winner candidate `mmvf:f32:w8:bs32:accf32:v1` -- FAILED: seed=1 native=ok candidate=failed, seed=2 native=ok candidate=failed, seed=3 native=ok candidate=failed.
- dispatch=ec467f813954eb15319491db6abd47ca: ne0=[2048,512,1,1], ne1=[2048,1,1,1], winner candidate `mmvf:f32:w1:bs160:accf32:v1` -- same failure pattern (all 3 seeds candidate=failed, native=ok).

tune-promote correctly rejected both (promotion_status=rejected_no_correctness_evidence), so this never reached production replay -- the correctness gate did exactly its job. But the underlying mmvf F32 candidates themselves (w8:bs32:accf32 and w1:bs160:accf32 configurations specifically) appear to be genuinely broken on real hardware (RDNA3, dual RX 7900 XTX) and need root-causing: is it a real numerical/launch bug in those specific warp-count/block-size mmvf variants, or a test-harness issue specific to F32 MUL_MAT under BIGCHERRY_TEST_DETERMINISTIC_SEED? Either way it needs investigation, not just silent rejection.

## Steps

1. Reproduce standalone: extract the exact test-file line hi80 generated for these two dispatches/candidates and run test-backend-ops directly with GGML_HIP_FORCE_CANDIDATE forcing each of the two failing candidate names, under BIGCHERRY_TEST_DETERMINISTIC_SEED, to see the actual failure mode (crash? wrong values? NaN/Inf?) rather than the aggregated CLI's terse FAILED line.
2. Determine whether the failure is specific to accf32 accumulation, the w8:bs32 / w1:bs160 warp/block-size combination, or F32 MUL_MAT generally in mmvf.
3. Check whether this candidate is ever actually selected as a winner in a real production-scale tune run (i.e. does it matter), separately from whether it's simply broken.
4. Root-cause and fix the underlying mmvf kernel/launch-policy bug if real, or fix the test harness if the failure is a harness artifact -- do not close this by just leaving the correctness gate to reject it forever without understanding why.
