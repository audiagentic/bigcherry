# Build-plan-id content addressing doesn't account for the requested binary target -- rebuilds into a shared directory with a new target produce byte-mismatched artifacts

## Description

Reproducible (not flaky -- confirmed across 3 separate attempts with different run-ids) build failure found while working HI109: requesting `bigcherry build --lane bigcherry:record:linux-multi --binary-relative-path bin/llama-server` against a build_plan_id/source_slice directory that had already published a llama-bench binary (same lane, same config, no --experiment difference) fails with:

`bigcherry.artifacts.ArtifactError: immutable artifact already exists with different bytes: builds/<source_slice>/<build_plan_id>/libggml-hip.so.0.20.2`

campaign_workers.py's own comment states the design intent explicitly: 'a shared configure cache across targets is legitimate' -- i.e. building a second binary target (llama-server) into the same build_plan_id directory that already has a first target (llama-bench) built is supposed to work, reusing the shared configure/object cache. In practice it does not: ninja relinks libggml-hip.so.0.20.2 with different bytes purely because a different top-level target was requested, even though build_plan_id (content-derived from source+patches+config, NOT from binary_relative_path) claims this is the identical build. A second, unrelated failure was also hit at the generate stage when reusing the same run-id (`immutable artifact already exists with different bytes: runs/<run-id>/generate/hip-autotune-manifest.json`), suggesting the generate stage may also be non-reproducible across invocations that differ only in requested binary target.

Workaround used to unblock HI109: added the (functionally irrelevant to llama-server/llama-bench, since it only touches tests/test-backend-ops.cpp) hi105-correctness experiment patches to force a genuinely different build_plan_id/fresh directory. This works but is a hack, not a real fix, and won't be available/appropriate for every future case that hits this.

## Steps

1. Reproduce minimally: build bigcherry:record:linux-multi with --binary-relative-path bin/llama-bench, then in the SAME source_slice/build_plan_id directory (same lane, same run-id or fresh run-id, no experiment/config change) request --binary-relative-path bin/llama-server. Confirm the exact byte diff in libggml-hip.so.0.20.2 between the two builds (diff the actual .so files, not just the failure message) to determine whether it's genuinely nondeterministic linking (symbol ordering, parallel-build races) or a real semantic difference (different compile definitions leaking in based on which top-level ninja target is requested).
2. Check the generate stage's hip-autotune-manifest.json non-reproducibility too -- is it timestamped, or does it also vary by requested target?
3. Fix the root cause: either make the shared build artifacts genuinely deterministic regardless of which additional target is requested (matching the code's own stated design intent), or make build_plan_id/artifact identity account for the full requested target set so two different target requests never collide in the same content-addressed slot.
