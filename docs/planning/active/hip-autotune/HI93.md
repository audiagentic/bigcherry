# Cache per-device hardware key/digest once per process (RP4 slice)

## Description

Carved out of HI87 as an independently implementable slice (RP4 in the source document's own staged breakdown -- 'BigCherry Replay and RCCL Tuning Architecture', assessed 2026-08-23). The cold-path resolver currently derives the hardware key (architecture, wave size, compute units, feature flags, shared memory per block) and its digest fresh on every cold signature encounter, even though these properties never change for a given device within a process. Cache them once per device, keyed by hipGetDevice()'s current value (same pattern this session's HI64 work already used for PerDeviceState<T>).

Deliberately independent of HI87's native-selector reorder question: this only removes redundant reconstruction work on the cold path (the path that already runs native_select() and full resolution), not the warm-hit fast path HI87/RP2-RP3 target. It can ship on its own, is low-risk (pure caching of an already-deterministic value, no semantic change), and does not need HI92's profiling data to justify -- the redundancy itself is the justification, independent of how large or small its measured cost turns out to be.

## Steps

- Add a DeviceDispatchProfile-style cache (hardware key + hardware digest) keyed by device, constructed once on first use per device and reused for the life of the process.
- Wire the cold-path resolver to consult this cache instead of reconstructing the hardware key/digest on every cold signature.
- Verify identical dispatch decisions before/after (pure caching, no behavior change) via existing replay/telemetry evidence.
