# Does tuned dispatch actually improve end-to-end throughput? -- the open question, its failed attempts, and what is still needed

## Description

THE QUESTION: does applying tuned kernel winners make production faster, end to end, on a real serving workload? It is still unanswered. This item exists because it had no home: eleven plan items (HI158-HI167, HTR07) cover pieces of the machinery, and none owns the question itself, so the same ground kept being re-derived and the same mistakes repeated.

CURRENT STATUS: unanswered. The most recent measurement was VOID for a reason that is itself a finding -- the tuned winners change MTP draft acceptance from 0.94734 to 0.86391, bit-identical across all 16 cells, so the arms did different amounts of WORK and a throughput comparison between them is meaningless however clean the numbers look.

WHY IT MATTERS: the tuner promotes winners on isolated kernel measurements showing 6-23% improvements. Whether any of that reaches production throughput has never been established. HI130 already reached the same impasse and recorded 'no evidence of a real tuning-driven performance improvement over either vanilla upstream llama.cpp or bigcherry's own untuned dispatch currently exists, on this workload/candidate set/hardware'.

## Steps

1. IN FLIGHT: run the same comparison with speculative decode DISABLED (SPEC_ARGS empty, BENCH_CONFIGS=full). Without drafts there is no acceptance to vary, so a throughput delta is a real speed difference. This is the cleanest available answer to the question and does not depend on HI166 landing first.
2. Confirm activation in the same run: final_tuned_launches > 0 from a diagnostics-ON build of the same revision, since the production binary now carries no instrumentation.
3. Compute predicted vs measured with `bigcherry impact --observations <record jsonl> --measurements <promoted.jsonl>`, and `bigcherry kernel-fraction` over a rocprofv3 trace for the time share. If predicted gain is below the noise floor, 'no measurable improvement' is the correct and final answer for this workload rather than a measurement failure.
4. Only then, with HI166 landed, revisit the MTP lane -- where the question is genuinely harder because the winners change how much work is done.

## Detailed Solution & Technical Design

ATTEMPTS, AND WHY EACH FAILED. Recorded in full because every one produced a reported conclusion that had to be retracted, and the failure modes recur.

1. replay vs control, 1 sample per arm, fixed order, replay last. VOID: arm confounded with position. Thermal drift over a ~10 minute run produces exactly the clean monotone pattern observed. Reported as a result before the confound was noticed.

2. Balanced rerun, 6 rounds. Showed replay worse on 5 metrics with complete separation -- but the arms differed by RD73, the REPLAY build flag AND the cache, three variables described as one. Attribution withdrawn.

3. Winner isolation, same binary, cache on/off. VOID: both arms torn down with kill -9, which destroys the shutdown-emitted replay report, so there was no evidence the cache was ever consulted. 'Winners are neutral' and 'the cache never hit' were the same data.

4. Everything before the mode fix. VOID: GGML_HIP_DISPATCH_MODE defaults to NATIVE and no script set it, so ggml_hip_dispatch_mul_mat returned false immediately -- the dispatch layer never ran, and no cache was ever loaded.

5. Counter runs that looked silent. NOT void, but misread: llama-server installs a log callback that swallows GGML_LOG_INFO, so the reports were invisible. Conclusion 'the layer never ran' was wrong; the evidence channel is the GGML_HIP_DISPATCH_COVERAGE JSON.

6. Tuned vs untuned on the MTP lane, 16 cells, order-balanced, same production binary, cache the only variable. Methodologically sound and still VOID as a throughput comparison: draft acceptance differs, so the arms did different work. tg128 +2.30%, tg512 -8.98%, tg2048 -5.54% describe two different workloads, not two speeds.

WHAT IS ESTABLISHED. The cache resolves on the model it was tuned for (exact 45 of 86 distinct signatures). L1 hit rate is 31.9%, not the 99.8% every prior estimate assumed. Calling native first costs 38.6ms per run, ~0.01% of wall time. Warm CUDA-graph replay bypasses the CPU dispatch path entirely, so dispatch-overhead work has a far smaller ceiling than assumed.

## Notes

CAVEATS THAT MUST TRAVEL WITH ANY ANSWER.

- A non-speculative answer does not transfer to the MTP lane. It isolates speed from work, which is what makes it interpretable, but production serves MTP.
- The cache under test was tuned on tierL-qwen27b-q8. Q6_K is the dominant quantisation (tierA-qwen4b-q6k is the default lane for 12 of 19 contracts), so an answer here describes one lane.
- Winners are hardware-keyed and signature-keyed; this result covers dual gfx1100 only.
- The tuned cache was produced on a build that INCLUDES RD73, which independently measures as a ~2% regression (HI162). If RD73 is demoted the composition changes and the cache may need retuning.
- 'No improvement' is a legitimate outcome. HI130 already reached it once and offered two live hypotheses that remain open: MTP's CPU-side sampling and RCCL tensor-split communication may dominate the critical path, or the candidate/promotion criteria may not be finding meaningfully different-performing candidates for this shape mix.
