# Profile and tune META butterfly allreduce for Brutus heterogeneous tensor-split

## Description

Establish the real cost structure of the existing, correctness-proven META reduction on Brutus's real heterogeneous tensor-split topologies ({0,1,2} and {0,1,2,3}), then make only evidence-driven optimizations inside that existing path. Reached via adversarial gpt-dev-agent design negotiation (2026-08-28, session ses_217212336c92455d) after explicitly rejecting a broader 'build a new heterogeneous collective backend / RCCL replacement' scope: no concrete evidence exists that META's butterfly has an intrinsic (not implementation-level) performance ceiling on this hardware, so a second algorithm is not justified before measuring the first. HI85 (closed) established RCCL cannot support any heterogeneous-architecture participant set on this box (hard ISA-level kernel-dispatch fault in ncclGroupEnd(), not a packaging or tuning issue) and patch 1225 now fails closed (hard abort) rather than silently substituting a different reduction when tensor-split is explicitly requested across mismatched architectures -- META is the only proven-correct path for these topologies and stays that way for this item.

## Steps

1. Freeze the target topology matrix: primary {0,1,2} and {0,1,2,3} (real heterogeneous hardware on Brutus); {0,1} dual-XTX may be recorded only as a same-architecture reference. Do not expand to arbitrary heterogeneous hardware.
2. Re-establish isolated META correctness/cost baselines: reuse HI18's test-hip-reduce probe (patch 1224) and HI84's real-hardware heterogeneous topology + numerical-correctness methodology; exercise representative reduction sizes/shapes from real tensor-split inference with META explicitly selected (GGML_HIP_REDUCE_PLAN=meta). Profiling must use an explicit test/experiment path -- do not weaken patch 1225's fail-closed guard to do this.
3. Make HI132's profile-campaign tool META-aware (minimal change): it currently marks any multi-GPU pass without RCCL activity as incomplete_multi_gpu_capture, which is wrong for an intentional META run. Require all expected GPU agents always; require RCCL activity only when RCCL is the expected provider for that run.
4. Profile the existing META path on the real workload via bigcherry profile-campaign (rocprofv3 --sys-trace, interleaved unprofiled controls, multi-GPU agent validation) -- capture META reduction kernels, HIP/HSA calls, memory/copy activity, synchronization, per-GPU dispatch counts/timings, and resource usage.
5. Produce a cost decomposition BEFORE changing any code: bytes transferred per reduction, number of transfer/reduction stages, P2P vs staged copies, kernel execution vs synchronization/wait time, per-device/rank imbalance, small- vs large-message behavior, launch/event/copy counts. Identify whether the dominant cost is algorithmic bandwidth, current scheduling, chunk sizing, unnecessary synchronization/copies, or kernel execution itself.
6. Tune only demonstrated bottlenecks inside the existing META implementation (chunk sizing, device/rank ordering, stream/event scheduling, redundant sync/copy removal, existing reduction-kernel tuning). No speculative rewrite; no new algorithm.
