# Winner/tuning persistence across llama.cpp revision bumps -- retain-by-default, retune-as-overlay

## Description

Explicit user requirement (2026-08-27): retuning every model after every llama.cpp pin bump is unreasonable. Tuned winners must be retained by default across a revision bump, not wiped/invalidated wholesale. A retune after a bump must overlay/update only the entries actually affected (ops whose kernel candidates changed), leaving everything else's existing winner intact and usable.

GPT design-validation (2026-08-27, req_fa592b0e623847d3) delivered the real scope after reviewing the actual current code (including tools/bigcherry/tuning/replay_projection.py, which neither prior investigation pass in this session had read): this is NOT primarily a C++ runtime freshness-check problem, and GGML_HIP_DISPATCH_REPLAY_REVISION_MATCH=OFF should NOT become the default -- it treats implementation_version as the cross-revision safety proof, which is weaker than the source-derived candidate-identity model BigCherry already has, and it does nothing for whether an old measurement's producer understood every capability dimension the new build cares about (HI121's capability-provenance concept).

The right foundation already exists: replay_projection.py implements durable multi-generation history -> target-specific projection, with source/target capability checks and candidate implementation-equivalence proof, rewriting projected winners to the target's own provenance so ordinary strict replay.build() can consume them with NO runtime/format change. This is currently an expert/manual path (standalone project-replay CLI), not wired into the default tune-campaign workflow.

## Steps

Per GPT's recommended acceptance boundaries (not yet broken into sub-steps/estimated):
1. Durable historical tuning authority -- persist promoted winners beyond one campaign run's workdir/tune.sqlite so a new campaign for the same workload+hardware can find prior generations.
2. Automatic source->target compatibility projection using the existing replay_projection.py/HI121 machinery: for each dispatch, produce a structured report state -- RETAINED, RETUNE_REQUIRED_CANDIDATE_CHANGED, RETUNE_REQUIRED_CANDIDATE_REMOVED, RETUNE_REQUIRED_CAPABILITY, NEW_DISPATCH, and ideally RETAINED_RETUNE_RECOMMENDED_CANDIDATE_SET_CHANGED (safe to keep using, but the search universe changed so it may no longer be optimal).
3. Immediately build a target-bound replay cache from the RETAINED set -- production gets its prior known-good winners back with NO retune required.
4. Delta tuning: a NEW missing piece (_stage_tune() currently always benchmarks the whole workload with no way to restrict to an uncovered/changed dispatch subset) -- needs either a signature/dispatch filter into tune mode or an equivalent mechanism to drive only the delta set.
5. Generate correctness evidence only for newly selected/changed winners (not the whole set).
6. Overlay the new generation over the retained target cache via replay.py's EXISTING build(..., merge_into=..., generation=...) mechanics (already correct, per GPT: portable keys exclude build identity, select_newest_winners() is generation-based, newer generations replace only matching dispatches) -- no new mechanism needed here.
7. Verify the combined target cache on the workload: zero stale/rerun-required entries, both retained and new winners producing real exact hits.
8. Wire all of the above into tune-campaign (HI130's orchestrator) as the DEFAULT path, with an explicit full-retune escape hatch for when an operator wants to force it.
