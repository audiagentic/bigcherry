# Winner/tuning persistence across llama.cpp revision bumps -- retain-by-default, retune-as-overlay

## Description

Explicit user requirement (2026-08-27): retuning every model after every llama.cpp pin bump is unreasonable. Tuned winners must be retained by default across a revision bump, not wiped/invalidated wholesale. A retune after a bump must overlay/update only the entries actually affected (ops whose kernel candidates changed), leaving everything else's existing winner intact and usable.

Investigation (forked agent, 2026-08-27) found the identity model ALREADY supports this at the Python layer: catalog.py's candidate_implementation_digest() is deliberately revision-independent (hashes an explicit source-file slice, not a git revision); dispatch_abi.py/promotion_gate.py gate purely on signature/hardware schema + candidate identity, never revision; replay.py's select_newest_winners()/portable_tuning_key() already supports multiple provenance identities coexisting within one generation -- this overlay/retention model was already built for exactly this scenario.

Follow-up investigation found the C++ runtime side ALSO already exists and is real-hardware-validated (see notes) -- this is not a missing mechanism, it's an existing mechanism blocked by one specific, already-root-caused bug tracked under HI130.

The actual blocker (root-caused by a GPT review in HI130's own session, req_12ba9a471b824e10): replay's freshness check compares a WHOLE-MANIFEST hash (catalog.py's manifest_hash(), which bakes in variant_set) rather than PER-CANDIDATE identity -- so even byte-identical candidates fail to match after any rebuild, and every dispatch falls back to native regardless of the revision-match flag. The real fix (not yet implemented per HI130.md as of this writing): make the freshness check verify per-candidate identity (implementation digest/config/ABI/capability) instead of requiring whole-manifest equality.
