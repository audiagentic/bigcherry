# Winner/tuning persistence across llama.cpp revision bumps -- retain-by-default, retune-as-overlay

## Description

Explicit user requirement (2026-08-27): retuning every model after every llama.cpp pin bump is unreasonable. Tuned winners must be retained by default across a revision bump; a retune must only touch the ops actually affected, not the whole model.

FINAL DESIGN after 3 rounds of adversarial GPT design discussion (2026-08-27, requests req_fa592b0e623847d3, req_e4b7e368b6ac435c, req_87f7321b2b3e4db9 -- full history in change-log if needed, this description/steps/notes reflect only the settled conclusion, not the path there).

The right foundation already exists and must not be reinvented: tools/bigcherry/tuning/replay_projection.py (HI121 M4) proves offline that a historical measurement is safe to reuse against a new target build (capability compatibility both directions + candidate implementation-equivalence, rewriting output to the target's own provenance so ordinary replay.build() consumes it unmodified). It is currently a manual/expert CLI path, not wired into tune-campaign.

Explicitly REJECTED approaches, with reasons: (a) GGML_HIP_DISPATCH_REPLAY_REVISION_MATCH=OFF as the default -- weaker than the source-derived identity model already available, and blind to capability-provenance gaps. (b) A global cross-model historical database + index + GC -- unverified cross-model signature-overlap assumption (different model architectures produce different matmul shapes), and GC is solving a fleet-scale problem this solo-operator, ~1-8GB/year-of-evidence tool doesn't have. (c) Production inference misses as the PRIMARY delta-discovery mechanism -- pushes a real performance-regression window onto production traffic; a cheap pre-deploy record-only pass (no benchmarking) is strictly better and costs little. (d) A new parallel build orchestrator for "target refresh" -- should reuse tune-campaign's (HI130) existing workflow.py stage helpers via a new run_tune_refresh(), not duplicate campaign/build plumbing.

## Steps

HARD SEQUENCING (frozen 2026-08-27): HI125 (C++-authoritative signature verifier -- currently a real gap; project_measurements() relies on DB canonical_json without independent C++ proof) -> HI127 (schema-7 verification/attestation state tracking, so projection can tell which historical rows passed strengthened verification) -> HI128 (retroactive re-attestation of EXISTING historical data; anything that fails re-attestation must be quarantined, never grandfathered) -> HI129 GO (the real Brutus A->B cross-generation validation run -- this is the foundational proof that cross-generation projection is trustworthy end-to-end; HI131 must not duplicate this experiment, only consume its result) -> HI131 V1A (below). V1A may be DESIGNED and tested synthetically in parallel with the HI121 chain, but must not ship for automatic production retention before HI129 returns GO.

V1A -- operational cross-generation retention (the actual deliverable, scoped small on purpose):
1. Operator names one explicit prior tune-campaign generation for this model/runtime-profile/hardware (e.g. --retain-from <receipt>) -- no global store, no index, no cross-model sharing assumption for V1.
2. Run a cheap, tuning-free RECORD-ONLY pass on the new target build under the real runtime profile (workflow.py's existing _stage_record, no benchmarking) to discover today's exact signature/hardware set.
3. Build the new target replay-full lane through NORMAL campaign planner/admission (workflow.py's existing stages) -- never generate an out-of-band source/build that could bypass HI102's patch-admission gate.
4. Project the prior generation's promoted measurements (+ its own tune.sqlite + source manifest) onto the new target manifest/root via the EXISTING replay_projection.project_measurements() -- no new compatibility definition invented here.
5. Additional correctness-portability checks project_measurements() does NOT yet do, needed before a retained winner can be trusted without a fresh correctness pass: (a) the NATIVE baseline candidate must ALSO be proven equivalent between source and target, not just the winner -- RV49's correctness threshold is native-error-relative, so a changed native implementation invalidates the old threshold even if the challenger is untouched; (b) same toolchain/compiler/ROCm epoch, or require fresh correctness revalidation -- candidate implementation_digest deliberately does not cover compiler flags/vendor libs/GPU behavior.
6. Diff today's recorded signature set against the successfully-projected set. If the delta is empty: export the target-bound cache, run strict replay verification, done -- zero tuning. If non-empty: report the exact RETUNE_REQUIRED delta and stop (V1A does not need to also perform the retune).

V1B -- conditional phase 2, build ONLY if V1A's real usage shows a recurring non-trivial delta pattern that makes it worthwhile (do not build pre-emptively):
7. A narrow, additive C++ tune-mode primitive: skip a supplied set of already-proven-retained (hardware_digest, signature_digest) pairs during benchmarking, tune everything else. Prefer skip-list over include-list semantics -- a missed exclusion just wastes GPU time re-tuning something already known-good (safe); a missed inclusion in an include-list would silently fail to tune something genuinely new (unsafe).
8. New winners get fresh promotion/correctness evidence as normal, then merge with the retained set via replay.py's EXISTING generation/merge_into mechanics (already correct and sufficient -- portable keys already exclude build identity, select_newest_winners() is already generation-based) -- no new overlay mechanism needed.
