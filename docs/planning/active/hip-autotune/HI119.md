# Fused MUL_MAT(_ID)+GLU correctness-evidence harness (real two-op graph, not the single-op --test-file mapper)

## Description

Follow-up to HI118 (which captures real gate-tensor geometry in the signature schema -- a hard prerequisite for this item). test-backend-ops' --test-file/test_generic_op escape hatch (the mechanism HI80/HI105's mapper pattern relies on) can only build ONE op per test case (confirmed via make_test_cases_from_file(), vendor/llama.cpp/tests/test-backend-ops.cpp ~line 10528) -- it cannot represent the real fused MUL_MAT(_ID)+GLU compound HI108's investigation found every recorded GLU signature actually is. This item builds a bespoke small harness that constructs the REAL two-tensor-input fused computation (the real x/gate mul_mat_id calls with HI118's captured real gate geometry, followed by the real GLU op) via the ggml C API directly, runs native vs candidate, and produces evidence in the same digest/metric format tools/bigcherry/correctness_evidence.py's write_correctness_evidence() already expects -- so it plugs into the existing hi80_generate_correctness_evidence.py CLI / e2e_smoke_campaign.py S3b stage without changing their own orchestration logic, only the evidence-GENERATION step for this one op shape.

## Steps

Once HI118 lands and a real campaign has captured real gate-tensor geometry for a fused-GLU dispatch, read the exact fused kernel's real numeric semantics (which projection is native vs candidate, whether the fused kernel differs in more than just the underlying MUL_MAT_ID choice) before writing the harness -- do not assume the GLU epilogue itself is bit-identical between native and candidate paths without checking.
2. Build the harness: construct the real x + gate mul_mat_id graph nodes (or the dense equivalent) plus the GLU epilogue via ggml's own C API, run it under both the native and candidate dispatch resolutions, and compute the same BIGCHERRY_REF_DIGEST/BIGCHERRY_CORRECTNESS_METRIC-equivalent evidence correctness_evidence.py's generate_correctness_evidence() expects to consume.

## Detailed Solution & Technical Design

REAL DESIGN, confirmed against source 2026-08-25 (step 1 of this item's own steps): ggml-cuda's own graph-level fusion optimizer (ggml-cuda.cu, ggml_cuda_can_fuse() ~line 3352-3396, and the scale-variant matcher ~line 3800-3930) scans for an exact ADJACENT node pattern in the compute graph and fuses it automatically -- this is the real trigger, not something BigCherry's dispatch hook does on its own:

  simple:  [MUL_MAT_ID(gate), MUL_MAT_ID(up), GLU]                         (mul_mat_id_glu_ops, ~line 3369)
  biased:  [MUL_MAT_ID(gate), ADD_ID, MUL_MAT_ID(up), ADD_ID, GLU]         (mul_mat_id_bias_glu_ops, ~line 3367)
  scaled:  [...MUL, ...MUL_ID, MUL_ID, MUL, (ADD_ID), GLU]                 (~line 3870-3881, RD17's x_scale_channel_dst territory)

Confirmed exact tensor identities at the real fusion construction site (~line 3914-3927): `src0 = up_n->src[0]` (up/x weight), `src1 = up_n->src[1]` (activations), `ids = up_n->src[2]`; `fusion_data.gate = gate_n->src[0]` (the GATE MUL_MAT_ID node's OWN weight tensor -- a separate real tensor, same shape/type/stride as up's weight because both are independent MUL_MAT_ID nodes built from identically-shaped model weights, which is WHY ggml_cuda_should_fuse_mul_mat's ggml_are_same_shape/stride check on ffn_up->src[0] vs ffn_gate->src[0] always passes for a real model); the dispatch call passes `cgraph->nodes[glu_idx]` (the GLU node itself) as `dst`. This exactly matches what HI108/HI118 already found by reading the consumer side (mmvq.cu) and the signature builder.

CONSEQUENCE for the harness design: rather than a fully bespoke standalone evidence producer (this item's original framing), the more consistent, doctrine-aligned design is a NEW registered test_case subclass in test-backend-ops.cpp (a new/extended BigCherry patch, following test_mul_mat_id's own precedent) that builds this EXACT adjacent 3-node (or 5-node biased) subgraph -- two MUL_MAT_ID nodes with identically-shaped weight tensors feeding a GLU node via ggml_glu_split. Running that graph through ggml_backend_cuda_graph_compute() naturally triggers ggml-cuda's own existing fusion detector, which then calls BigCherry's ggml_hip_dispatch_mul_mat() with a REAL, correctly-populated fusion struct -- indistinguishable from a real production fused dispatch. This reuses ALL of HI80's existing deterministic-seed (patch 1222) and BIGCHERRY_REF_DIGEST/CORRECTNESS_METRIC (patch 1223) infrastructure for free, since that infrastructure lives in test-backend-ops' own eval loop and works for any registered test_case, not just the ones HI80/HI105 already handle. Do NOT attempt this via test-backend-ops' --test-file/test_generic_op escape hatch -- confirmed unusable for a multi-node fused graph (single op per line only); this needs a genuine new C++ test_case class, compiled into a real patched test-backend-ops binary, not a runtime-file-driven case.

OPEN DESIGN QUESTION RESOLVED (partially, needs runtime confirmation before committing to it): checked Qwen3.6-35B-A3B's real MoE FFN construction (vendor/llama.cpp/src/models/qwen3moe.cpp ~line 137) -- it calls build_moe_ffn with NO bias tensors (nullptr for gate_inp_b and the up/gate/down bias params), and passes ffn_up_exps_s/ffn_gate_exps_s (real fields, but declared TENSOR_NOT_REQUIRED, per-expert-shaped, in llama-model.cpp ~line 1452-1453 -- an OPTIONAL scale tensor typically absent for a standard Q8_0 GGUF, since Q8_0's own scale is baked into its quant blocks rather than stored as a separate top-level tensor). This strongly suggests HI108's two real blocked dispatches (both q8_0 candidates) use the SIMPLE 3-node fusion pattern (no bias, no scale) -- but this is inference from model-construction code, not a runtime observation of the actual fusion struct for those two specific dispatches. Confirm for certain before building the harness: e.g. by adding a one-line debug print of fusion.gate_scale/x_bias/gate_bias nullness at the real ggml_hip_make_signature() call site and re-running the real campaign, or by checking the real GGUF's tensor list for a 'ffn_up_exps.scale' tensor. Build the simple 3-node case first regardless (it is the most likely to be real AND the smallest to implement), and only add the biased/scaled variants if runtime evidence shows they're actually needed.
