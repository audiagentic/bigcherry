# Fused MUL_MAT(_ID)+GLU correctness-evidence harness (real two-op graph, not the single-op --test-file mapper)

## Description

Follow-up to HI118 (which captures real gate-tensor geometry in the signature schema -- a hard prerequisite for this item). test-backend-ops' --test-file/test_generic_op escape hatch (the mechanism HI80/HI105's mapper pattern relies on) can only build ONE op per test case (confirmed via make_test_cases_from_file(), vendor/llama.cpp/tests/test-backend-ops.cpp ~line 10528) -- it cannot represent the real fused MUL_MAT(_ID)+GLU compound HI108's investigation found every recorded GLU signature actually is. This item builds a bespoke small harness that constructs the REAL two-tensor-input fused computation (the real x/gate mul_mat_id calls with HI118's captured real gate geometry, followed by the real GLU op) via the ggml C API directly, runs native vs candidate, and produces evidence in the same digest/metric format tools/bigcherry/correctness_evidence.py's write_correctness_evidence() already expects -- so it plugs into the existing hi80_generate_correctness_evidence.py CLI / e2e_smoke_campaign.py S3b stage without changing their own orchestration logic, only the evidence-GENERATION step for this one op shape.

## Steps

1. Once HI118 lands and a real campaign has captured real gate-tensor geometry for a fused-GLU dispatch, read the exact fused kernel's real numeric semantics (which projection is native vs candidate, whether the fused kernel differs in more than just the underlying MUL_MAT_ID choice) before writing the harness -- do not assume the GLU epilogue itself is bit-identical between native and candidate paths without checking.
2. Build the harness: construct the real x + gate mul_mat_id graph nodes (or the dense equivalent) plus the GLU epilogue via ggml's own C API, run it under both the native and candidate dispatch resolutions, and compute the same BIGCHERRY_REF_DIGEST/BIGCHERRY_CORRECTNESS_METRIC-equivalent evidence correctness_evidence.py's generate_correctness_evidence() expects to consume.
3. Wire it into hi80_generate_correctness_evidence.py's generate_for_row() as a new branch (gated on the recorded signature's op==GLU and fusion != NONE), following the existing MUL_MAT/MUL_MAT_ID branch pattern.
4. Real-hardware validation against the two real HI108 dispatches (7ef2471585a5aa6fbb49384efe566ac5, d816ffce280de2a7ce2292c6406da23d); confirm via the real e2e_smoke_campaign S3b stage + tune-promote whether they reach promoted status.
5. Per HI108's own original step 5: if promoted, do not assume the isolated 4-14% kernel win moves full-model throughput -- measure a real end-to-end A/B before claiming a production win, matching HI105's own finding that a MoE-routed candidate win of similar size did not move throughput for the MUL_MAT_ID case.
6. (dev-gpt-agent review of HI118, 2026-08-25) Add a behavioral signature/digest test: toggling each HI118 fusion presence flag (X_BIAS/GATE_BIAS/X_SCALE/GATE_SCALE) must change the resulting signature digest, exercised against a real fused dispatch, not just a source-text wiring check.
7. (same review) Fail closed on legacy v1 fusion records that predate HI118's flags -- a zero flag bit on an old artifact means 'written before this schema addition,' not 'genuinely absent,' and generate_for_row()'s new branch must not silently treat the two the same way.
