# Fused MUL_MAT(_ID)+GLU correctness-evidence harness (real two-op graph, not the single-op --test-file mapper)

## Description

Follow-up to HI118 (which captures real gate-tensor geometry in the signature schema -- a hard prerequisite for this item). test-backend-ops' --test-file/test_generic_op escape hatch (the mechanism HI80/HI105's mapper pattern relies on) can only build ONE op per test case (confirmed via make_test_cases_from_file(), vendor/llama.cpp/tests/test-backend-ops.cpp ~line 10528) -- it cannot represent the real fused MUL_MAT(_ID)+GLU compound HI108's investigation found every recorded GLU signature actually is. This item builds a bespoke small harness that constructs the REAL two-tensor-input fused computation (the real x/gate mul_mat_id calls with HI118's captured real gate geometry, followed by the real GLU op) via the ggml C API directly, runs native vs candidate, and produces evidence in the same digest/metric format tools/bigcherry/correctness_evidence.py's write_correctness_evidence() already expects -- so it plugs into the existing hi80_generate_correctness_evidence.py CLI / e2e_smoke_campaign.py S3b stage without changing their own orchestration logic, only the evidence-GENERATION step for this one op shape.

## Detailed Solution & Technical Design

OPEN DESIGN QUESTION NOW DEFINITIVELY RESOLVED (2026-08-25, real GGUF inspection, not inference): read the real tensor list directly from /mnt/vault/llm-models/qwen3.6-35B-A3B/gguf/Qwen3.6-35B-A3B-Revised-q8_0.gguf on Brutus (raw GGUF header parse, no llama.cpp needed) -- only `blk.N.ffn_gate_exps.weight` / `blk.N.ffn_up_exps.weight` exist for every layer; there is NO `.bias` or `.scale` variant anywhere in the file for either tensor. This is direct, definitive confirmation (not inference from model-construction code) that BOTH of HI108's real blocked dispatches use the SIMPLE 3-node fusion pattern `[MUL_MAT_ID(gate), MUL_MAT_ID(up), GLU]` -- no bias/scale variant needed. (Also noted: the model has a separate `ffn_gate_shexp`/`ffn_up_shexp` shared-expert path, distinct from the routed `_exps` path -- HI108's second, has_ids=false dispatch is most likely this shared-expert branch, still MUL_MAT-based not MUL_MAT_ID, same no-bias/no-scale conclusion applies.)

Build the simple 3-node case ONLY for the first implementation pass -- biased/scaled variants are confirmed not needed for either of the two real dispatches this item exists to fix, and should not be built speculatively.

--- (older investigation below, retained for the full trail) ---

REAL DESIGN, confirmed against source 2026-08-25 (step 1 of this item's own steps): ggml-cuda's own graph-level fusion optimizer (ggml-cuda.cu, ggml_cuda_can_fuse() ~line 3352-3396, and the scale-variant matcher ~line 3800-3930) scans for an exact ADJACENT node pattern in the compute graph and fuses it automatically -- this is the real trigger, not something BigCherry's dispatch hook does on its own:

  simple:  [MUL_MAT_ID(gate), MUL_MAT_ID(up), GLU]                         (mul_mat_id_glu_ops, ~line 3369)
  biased:  [MUL_MAT_ID(gate), ADD_ID, MUL_MAT_ID(up), ADD_ID, GLU]         (mul_mat_id_bias_glu_ops, ~line 3367)
  scaled:  [...MUL, ...MUL_ID, MUL_ID, MUL, (ADD_ID), GLU]                 (~line 3870-3881, RD17's x_scale_channel_dst territory)

Confirmed exact tensor identities at the real fusion construction site (~line 3914-3927): `src0 = up_n->src[0]` (up/x weight), `src1 = up_n->src[1]` (activations), `ids = up_n->src[2]`; `fusion_data.gate = gate_n->src[0]` (the GATE MUL_MAT_ID node's OWN weight tensor -- a separate real tensor, same shape/type/stride as up's weight because both are independent MUL_MAT_ID nodes built from identically-shaped model weights); the dispatch call passes `cgraph->nodes[glu_idx]` (the GLU node itself) as `dst`.

CONSEQUENCE for the harness design: rather than a fully bespoke standalone evidence producer (this item's original framing), the more consistent, doctrine-aligned design is a NEW registered test_case subclass in test-backend-ops.cpp (a new/extended BigCherry patch, following test_mul_mat_id's own precedent) that builds this EXACT adjacent 3-node subgraph. Running that graph through ggml_backend_cuda_graph_compute() naturally triggers ggml-cuda's own existing fusion detector, which then calls BigCherry's ggml_hip_dispatch_mul_mat() with a REAL, correctly-populated fusion struct. This reuses ALL of HI80's existing deterministic-seed (patch 1222) and BIGCHERRY_REF_DIGEST/CORRECTNESS_METRIC (patch 1223) infrastructure for free. Do NOT attempt this via test-backend-ops' --test-file/test_generic_op escape hatch -- confirmed unusable for a multi-node fused graph (single op per line only); this needs a genuine new C++ test_case class.
