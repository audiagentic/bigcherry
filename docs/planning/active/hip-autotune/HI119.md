## Detailed Solution & Technical Design

dev-gpt-agent deep design review (2026-08-25) -- GO verdict with two major corrections, both independently verified against real source before being recorded here:

VERIFIED CLAIM 1 -- test_mul_mat_vec_fusion already exists (vendor/llama.cpp/tests/test-backend-ops.cpp, struct at line 6389, use_id=true graph-building branch at line 6507-6554): confirmed real. Its use_id path builds `ggml_mul_mat_id(ctx, ups, cur, ids)` and `ggml_mul_mat_id(ctx, gates, cur, ids)` sharing the exact same `cur`/`ids` tensor objects, then combines via build_gate() (ggml_glu_split or ggml_swiglu_oai for the SWIGLU_OAI case) -- almost exactly HI119's needed shape. BUT confirmed real gap: line 6548-6550 shows an unconditional `ggml_mul(ctx, out, scale)` AFTER build_gate()'s GLU output, so the GLU there is never the terminal graph output -- must be fixed (make GLU terminal) for HI119's own use, not reused unmodified.

VERIFIED CLAIM 2 -- init_mul_mat_id_tensors() (test-backend-ops.cpp line 4717) is genuinely non-deterministic: confirmed real, exact code is `std::random_device rd; std::default_random_engine rng(rd());` seeding the expert-ID shuffle. Confirmed patch 1222 (patches/1222_hi67_deterministic_test_backend_ops_seed.py) only covers float tensor init. Confirmed patch 1236's own docstring (patches/1236_hi105_deterministic_mul_mat_id_ids.py) explicitly scopes itself ONLY to test_generic_op's own SEPARATE std::random_device, and explicitly distinguishes 'the registered test_mul_mat_id class's own init_mul_mat_id_tensors()' as out of scope for that patch. So ANY registered test_case using init_mul_mat_id_tensors() (test_mul_mat_id, test_mul_mat_vec_fusion, and HI119's planned new class if it reused this initializer unmodified) gets non-deterministic expert routing today -- native and candidate forced-runs could route to different experts despite identical deterministic float inputs, silently invalidating any correctness comparison. This is a real, load-bearing blocker for HI119's evidence integrity, not a style nit -- must be fixed (extend deterministic-seed coverage to this initializer, or an equivalent) before HI119's evidence can be trusted.

Other source-verified corrections from the review (see revised Steps for the full list): ggml_cuda_should_fuse_mul_mat/ggml_can_fuse_subgraph require gate/up to share the exact same activation/ids TENSOR POINTERS (not merely same-shape separate tensors) and each MM result to have exactly one consumer; supported glu_op is SWIGLU/GEGLU/SWIGLU_OAI only (swapped rejected); the real dispatch construction site's tensor identities (up_n->src[0/1/2] as src0/src1/ids, gate_n->src[0] as fusion.gate, the GLU node itself as dst) match what HI108/HI118 already found from the consumer side.

MOST IMPORTANT NEW REQUIREMENT (not something I had planned for): correctness PASS must require proof the fused signature was ACTUALLY executed (observed dispatch signature digest == requested digest, observed candidate resolution == expected), not just that CPU-vs-GPU numerics matched -- otherwise a future fusion-detection regression (CUDA silently falling back to unfused execution) could make CPU comparison still pass while HI119 wrongly certifies correctness for a candidate that was never actually exercised as fused. This closes a real gap in what 'correctness evidence' would otherwise mean for this specific harness.
