# Split replay-full correctness evidence into workload evidence + candidate-qualification evidence

## Description

autotune_catalog.build_manifest()'s correctness gate for PRODUCTION_VARIANT_SETS (replay-full/replay-slim with correctness_source set) requires every non-native candidate the compile-time enumerators produce (enumerate_mmq/enumerate_mmvf/etc, the full type/width/block-size/nwarps/CASE-row cartesian product) to have positive correctness evidence in the SAME artifact that supplied the winners. That equivalence is correct for replay-slim (a non-native candidate cannot be a winner without having been exercised by the tune run that selected it), but wrong for replay-full, whose whole documented purpose is to retain the full candidate set beyond what any one workload happened to exercise.

Discovered during RE20's real-hardware standard-profile proof (2026-08-17): 5 different real production-shaped workloads on Brutus (Qwen3.5-0.8B, Qwen3.5-9B, Qwen3.6-35B-A3B, Qwen3.8-27B with MTP speculative drafting, and the last again with q8_0-quantized KV cache matching the actual production server's config) raised correctness-evidence coverage for gfx1201's replay-full candidate set from 55 to 131 entries but never closed the last one: `mmq:q8_0:j16:fb1:t128:o2:i64:sram-q8_0:k256:sk0:v1`. GPT-auto-agent root-caused this by reading the runtime eligibility code directly: MMQ's `fb1` (fallback) variant only becomes eligible when the q8_0 weight matrix's `ne0[1] % 128 != 0` -- a narrow, shape-derived condition no realistic LLM's matmul dimensions are likely to hit by chance. This is 'legal but workload-unobserved', not dead/unreachable code (the CASE row exists in the architecture table and can_execute() explicitly admits it under that condition) -- so it should NOT be pruned from the catalog on this evidence alone.

## Steps

1. Add a synthetic candidate-qualification path: construct one valid q8_0 MUL_MAT signature (q8_0 src0, F32 src1/activation, a legal shared dimension, src0/ne0[1] deliberately NOT divisible by 128, otherwise ordinary MMQ-compatible tensors) targeting gfx1201, via test-backend-ops if its existing generator can express the shape cleanly, else a small dedicated BigCherry candidate-qualification test.
2. Run that synthetic operation through a tune-capable build in tune mode (not GGML_HIP_FORCE_CANDIDATE alone -- forcing proves can_execute()/launch only, since a successfully forced candidate returns from resolution before the tuner runs and never populates real correctness evidence). Confirm the tuner measures it and read_correctness_evidence() picks up NMSE/max-abs for the mmq:q8_0:j16:fb1:... row.
3. Design and implement the API split in autotune_catalog.py: build_manifest()'s correctness_source parameter becomes two provenance-bearing inputs (e.g. tuning_correctness_source + candidate_qualification_source, or a single structured CorrectnessEvidenceBundle) -- replay-full evidence = workload evidence UNION candidate-qualification evidence, both tied to the same source/build/architecture namespace; replay-slim keeps requiring only the winner-producing tune artifact (unchanged semantics).
4. Update campaign_workers.py's make_generate_worker() and any other caller of build_manifest()/read_correctness_evidence() for the new bundle shape.
5. Do NOT prune the mmq:q8_0:j16 candidate and do NOT switch the standard profile's `replay` build from replay-full to replay-slim as a workaround -- both were explicitly rejected by GPT's review as hiding the evidence-model gap rather than fixing it. Only reconsider pruning if a bounded synthetic witness search proves no valid dispatch signature exists on the architecture for which the candidate's can_execute() can return true.

## Detailed Solution & Technical Design

Full GPT-auto-agent diagnosis (2026-08-17 check-in, session ses_bd735a6bb2d1462c/req_59517278bada4d44), recorded verbatim for implementation fidelity:

"My read is: do not change the standard replay lane to replay-slim, and stop trying more real models for this candidate. You have found a mismatch between the right safety invariant and the wrong evidence source. The invariant is good: every non-native candidate that can ship in a production replay-full binary should have positive correctness evidence. What is not sound is the stronger current assumption: every replay-full candidate must have obtained that evidence incidentally from the same end-to-end tuning workload. Those are not equivalent.

The current catalog does restrict replay-full using the inventory, but MMQ restriction is only at the quantization-type level. Once q8_0 occurs, every applicable q8_0 CASE row from the architecture table enters the candidate set. It is not restricted by the actual shapes that occurred. The runtime eligibility code explains why model hunting stalls: for MMQ, fallback is shape-derived (`const bool shape_fallback = (sig.ne0[1] % 128) != 0; if ((self->variant.fallback != 0) != shape_fallback) return false;`). So the fb1 candidate can only participate when the q8_0 weight matrix has ne0[1] not divisible by 128 -- much narrower than 'run a model containing q8_0'. Five workloads can contain thousands of q8_0 matmuls and still never give this row one eligible signature. This is deliberate upstream design (MMQ fallback derived from row divisibility), not a BigCherry bug.

Option (b) is the correct immediate solution: targeted synthetic backend-op exercising. Construct one valid q8_0 MUL_MAT signature (q8_0 src0, F32 activation/src1, a legal shared dimension, src0/ne0[1] deliberately not divisible by 128, otherwise ordinary MMQ-compatible tensors, gfx1201). MMQ's family-level predicate only requires a supported quantized type plus F32 activation; it deliberately does not import upstream's performance heuristics. Run that operation through a tune-capable build; the normal tuner should see the q8_0 fb1 CASE rows including j16 as eligible and produce the correctness metrics read_correctness_evidence() wants. GGML_HIP_FORCE_CANDIDATE is a preliminary diagnostic only -- in tune/replay modes a successfully forced candidate returns from resolution before the tuner runs, proving can_execute()+launch work but NOT populating real tuner correctness evidence. So: optionally force the candidate once on an odd-row synthetic MUL_MAT to prove the witness shape, then run the SAME synthetic operation normally in tune mode so the tuner measures it and emits NMSE/max-abs evidence. test-backend-ops is a sensible home if its generator can express the shape; otherwise add a tiny BigCherry candidate-qualification test rather than distort a real GGUF model to generate it.

But there is still a catalog-design change to make: split the semantics of replay-full and replay-slim correctness sources. Today build_manifest() applies the same rule to both: every emitted non-native candidate must occur successfully in correctness_source, described as coming from the tune artifact. That's coherent for replay-slim (candidates = native wrappers + actual winners; a non-native candidate cannot be a winner without having been exercised by that tune run). For replay-full, the stated purpose is explicitly different: it retains the whole tuned candidate set so another workload can use it without rebuilding/re-tuning -- it is therefore logically expected to contain candidates not reachable from the workload that happened to produce today's winners. I would make replay-full require: correctness evidence = workload evidence UNION candidate-qualification evidence, both tied to the same source/build/architecture namespace. I'd make that explicit rather than overload correctness_source -- e.g. tuning_correctness_source + candidate_qualification_source, or a single structured CorrectnessEvidenceBundle containing multiple provenance-bearing inputs. Then: tune evidence proves candidates encountered naturally; the synthetic qualification suite fills the catalog-wide holes; replay-full still fails closed if any production candidate has neither; replay-slim continues requiring the winner-producing tune artifact itself. That preserves the safety gate instead of weakening it.

I would NOT prune this specific candidate. 'Never seen in realistic current LLM inference' is not the same as unreachable. The code tells us an apparent witness class: q8_0 MMQ with ne0[1] % 128 != 0. The architecture table has the CASE row, and runtime can_execute() explicitly admits fb1 when that condition is true, subject to the ordinary shared-memory check. Classify it as 'legal but workload-unobserved', not dead. Pruning should be reserved for a stronger result: there exists no valid dispatch signature on this architecture for which candidate->can_execute() can return true. If a bounded synthetic witness search establishes that, THEN the catalog is wrong to carry the candidate for that target and it should be removed or architecture-masked before the production evidence gate -- precedent already exists for architecture-specific exclusion via resource-blacklisted candidates being removed only from affected targets rather than globally.

I would NOT switch campaign.standard to replay-slim. That would make RE20 easier by changing what production means. recipes.toml's build.replay ('Applies stored winners without measuring. What ships.', variant-set = replay-full) is in campaign.standard, and the catalog explicitly distinguishes replay-full's 'keep the whole tuned set' semantics from replay-slim's winner-only semantics. Changing the canonical profile to slim merely because one candidate cannot be reached by today's models would hide the evidence-model bug by shrinking the product, and would undo the semantic parity RE19 established. Only change production to replay-slim if that's an independent product/build-policy decision that winner-only binaries are what BigCherry should ship -- not an RE20 workaround.

For RE20: keep the acceptance condition that all five canonical lanes including replay must execute successfully, but refine what the replay acceptance condition MEANS. It should mean: the canonical replay-full lane must succeed when supplied with its complete declared production evidence dependencies. It should NOT mean: one realistic end-to-end model workload must incidentally exercise every replay-full catalog candidate. Record the RE20 decision as: RE20 does not switch replay to replay-slim; replay remains replay-full; candidate-complete correctness remains mandatory, but catalog-wide correctness qualification is separated from workload coverage; the immediate gfx1201 hole is closed with a targeted synthetic MMQ fallback-shape operation; subsequent work formalizes candidate-qualification evidence as an input to replay-full generation. Smallest path to unstick RE20: do the synthetic q8_0 odd-row test before modifying the catalog API -- if it produces the j16/fb1 correctness row as expected, the diagnosis is proven (candidate is reachable, model zoo isn't an adequate qualification mechanism, replay-full itself is not what needs abandoning). Also keep running varying-model tests in the background on free GPUs to opportunistically flush out more tunable results while this lands."
