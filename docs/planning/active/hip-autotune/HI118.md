# Capture fused MUL_MAT(_ID)+GLU gate-tensor geometry in the dispatch signature schema

## Description

HI108's investigation (2026-08-25, confirmed by dev-gpt-agent) found that every GLU-op signature this tuner ever records is a fused MUL_MAT(_ID)+GLU epilogue: ggml_hip_dispatch_mul_mat() and ggml_hip_dispatch_family() both call the same ggml_hip_make_signature(src0, src1, ids, dst, fusion) (src/ggml/src/ggml-cuda/hip-autotune-signature.cpp ~line 270), which records only a coarse fusion-kind byte (sig.fusion, from ggml_hip_fusion_kind()) -- it does NOT capture the real gate tensor's shape/type at all. `fusion->gate` is a genuinely separate ggml_tensor* (vendor/llama.cpp/ggml/src/ggml-cuda/common.cuh ~line 1591, struct ggml_cuda_mm_fusion_args_host), so a fused GLU dispatch's recorded ne0/ne1/ned describe only ONE of the two underlying mul_mat_id projections (the x/up side) -- the gate side's geometry is irretrievably absent from every artifact this tuner has ever written for such a dispatch. dev-gpt-agent's explicit warning: do not infer the gate shape from the x side even where models happen to make them equal -- capture it for real.

## Steps

1. Extend ggml_hip_dispatch_signature_v1 (hip-autotune-types.h) with real gate-tensor geometry fields (at minimum gate ne/type; check whether gate_bias/x_bias/x_scale/gate_scale also need capturing for a faithful replay -- read ggml_cuda_mm_fusion_args_host's full field list before deciding scope).
2. Update ggml_hip_make_signature() (hip-autotune-signature.cpp) to populate the new fields from `fusion->gate` (and any other fusion fields decided in step 1) when fusion != nullptr.
3. Bump the signature schema version; update every schema-version-aware consumer (dispatch_db ingestion, replay, etc.) to handle the new field additively -- do not break existing artifacts written under the old schema.
4. Offline tests: a synthetic fused-GLU signature round-trips the new fields correctly; an old-schema artifact still loads (backward compat).
5. Real-hardware validation: rebuild, run a real GLU-fusing MoE campaign (Qwen3.6-35B-A3B, matching HI105/HI108's own real workload), confirm the new fields populate with real, sane gate-tensor geometry for the two dispatches HI108 already found (7ef2471585a5aa6fbb49384efe566ac5, d816ffce280de2a7ce2292c6406da23d).
