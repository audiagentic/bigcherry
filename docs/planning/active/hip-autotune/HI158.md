# Lazy native_select on the dispatch hot path (reopens HI87 under the sub-1% policy)

## Description

On 99.8% of dispatches the hook computes a native fallback it immediately throws away.

    native = ggml_hip_native_select(...)          ~193.6 ns   ALWAYS
    sig    = ggml_hip_make_signature(...)
    bound  = ggml_hip_dispatch_resolve(ctx, sig, native, lc)

Inside resolve:

    resolved.candidate = native.candidate;      // seeded from native
    if (mode == NATIVE || !native.valid) return resolved;
    ...
    if (l1_found) {
        resolved.candidate = thread_binding.candidate;   // OVERWRITTEN
        return resolved;
    }

Measured on real gfx1100 (110,020-dispatch repeated-shape sweep, 99.8% L1 hit rate): native_select mean 193.6 ns (n=860), L1-hit lookup mean 52.6 ns (n=860).

WHY REOPENED. HI87 measured exactly this and closed WITHOUT action: the saving scaled to ~0.1-0.3% of decode latency, below the then-current intervention threshold. Its stated reopen condition was 'a future workload where this path measurably exceeds ~1% of real end-to-end decode wall time'. Two things changed: owner policy is now explicit that sub-1% wins are worth taking if nothing regresses, and we now benchmark MTP speculative decode, which issues far more, smaller dispatches per token than the workload HI87 scaled against.

Filed as a NEW item rather than editing HI87: that closure was correct on its own terms and stays as recorded history.

## Steps

1. Zero-allocation memoized native provider (tensor pointers + ctx, computed
   flag, cached selection). No std::function, no allocation.
2. ggml_hip_dispatch_resolve takes the provider instead of a computed value.
3. Force-once semantics per mode as above; the L1-hit path must never force.
4. Do NOT move the !native.valid guard in this patch.
5. Structural counters: dispatches, L1_hits, L1_misses, native_select_calls,
   native_select_ns, native_forced_native_mode, native_forced_tune,
   native_forced_record, native_forced_miss.
6. Temporary shadow assertion for the LATER guard-move work (not shipped):
   if (l1_hit) { auto shadow = native_select(...); assert(shadow.valid); }
   Broad shape/type/path coverage. Empirical zero failures SUPPORTS the proof;
   it does not replace key analysis.

## Detailed Solution & Technical Design

Design from adversarial review (dev-gpt-agent, req_035ff85a4a88456d).

TWO OPTIONS. The owner proposed the second; it dominates.

  A. Cache the native selection in L1 so a hit needs no native_select.
     REJECTED for now: requires proving native_select is a pure function of
     (signature, device). It reads cc/warp_size, tensor types/shapes incl.
     ne11/ne12/dst->ne[2], contiguity, a padding condition. If the signature
     fails to capture ANY of those, two different native selections collide on
     one key and the cache returns the WRONG kernel -- a correctness fault.
     Review: 'creates a new cache-correctness invariant for negligible
     additional upside at 99.8% L1 hits'.

  B. Pass native as a LAZY, MEMOIZED provider. Same function, same inputs,
     deferred until actually needed. No cache, no purity obligation, no
     stale-key hazard. IMPLEMENT THIS.

Zero-allocation memoized provider, NOT std::function. force-once semantics,
one provider per resolver invocation. No provider reuse across invocations in
this patch.

A CLAIM OF MINE THAT WAS WRONG. I argued an L1 hit implies native validity, so
the !native.valid guard could move after the lookup. Corrected:

    'L1 hit => native was valid PREVIOUSLY. It does not prove:
     L1 hit => native would be valid FOR THIS INVOCATION.'

Moving the guard is therefore a SEPARATE, LATER step needing proof that every
input capable of changing native.valid is either encoded in the L1
identity/device or immutable for that binding's lifetime. If that cannot be
proven, the better fallback is to SPLIT native_select into a cheap
validity/eligibility predicate plus the expensive selector, leaving only the
cheap predicate ahead of L1.

FORCE-ONCE SEMANTICS PER MODE:

    NATIVE mode        force immediately
    TUNE               force once at first real need, not at generic entry
    RECORD             L1 bypassed; force only where record consumes native
    normal L1 miss     force once
    normal L1 hit      NEVER force
    fused/MoE/split    re-entry needs no eagerness; per-invocation provider,
                       force at first real use

OUT OF SCOPE: make_signature (measured separately -- also runs every dispatch
and is unmeasured; see the parallel review req_250d70fcb13042b1), and any
pointer-keyed or two-tier L1 key, which adds pointer-lifetime, omitted-field
and collision hazards plus a second cache-identity proof.

## Validation

FALSIFIABLE STRUCTURAL PREDICTION -- proves the mechanism fired:

    baseline: native_select_calls ~= dispatches
    patched:  native_select_calls ~= L1_misses + explicit-force paths

Theoretical avoided work: 0.998 * 193.6 ns = ~193.2 ns per dispatch.

PRIMARY GATE IS END-TO-END, NOT THE MICROBENCHMARK. Gate on decode performance
-- latency per accepted token / accepted tok/s under MTP -- never on resolver
microbenchmarks. A resolver that gets faster while decode does not move is not
a win.

Paired A/B MTP decode on real gfx1100, identical model/config/prompt/
speculation settings, interleaved and randomised sessions. Record: end-to-end
decode, accepted tokens / MTP acceptance, dispatches per token, L1 hit rate,
native_select calls per token, resolver time, correctness/output equivalence.

Regression-test every resolver path: ordinary decode, NATIVE, TUNE, RECORD,
fused, MoE, tensor-split.

## Effort & Risk

Medium. The change is small and semantics-preserving -- same function, same inputs, merely deferred -- which is why it was chosen over caching.

Risks: (1) a missed force site leaves a path reading an uncomputed selection; the counters catch it. (2) Re-entrant paths forcing eagerly and quietly erasing the saving; per-path force counters make that visible. (3) Being tempted into the guard move without the proof -- explicitly deferred.

## Notes

The win is real but small. The honest framing is that it is worth taking BECAUSE small wins accumulate, not because this one is significant alone. If the end-to-end gate shows no movement, that is a legitimate negative result: the patch must not ship on the counter delta alone, which proves only that the mechanism fired, not that anyone benefited.
