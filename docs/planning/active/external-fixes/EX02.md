# MMQ q6_K/J=112 illegal-memory-access incident on gfx1100 -- quarantined, root cause open

## Description

The historical incident involved a specific generated MMQ kernel candidate -- `mmq:q6_k:j112:fb0:t256:o2:i128:sram-q6_k:k256:sk0:v1` (Q6_K quantized input, J-tile size 112, thread config t256/o2/i128, shared-memory q6_k SRAM path) -- and recorded `ROCm error: an illegal memory access was encountered` on AMD RX 7900 XTX (gfx1100), reproduced deterministically 3 times across two independent instrumentation approaches. Only reachable under bigcherry's own exhaustive tuning sweep: native dispatch's own J-selection (`ggml_cuda_mmq_native_j_best` in mmq.cu) always picks the smallest J that covers a batch in one tile, so it never forces J=112 onto MTP speculative-decoding's narrow draft-decode batch widths (3-16) the way an exhaustive sweep does -- a genuinely new code path, not a previously-known-bad one.

Environment: AMD RX 7900 XTX (gfx1100), ROCm 7.2.4, Clang 22.0.0 (roc-7.2.4 26084), llama.cpp 4801e3c567d5 (tag b10362), Qwen3.5-9B MTP variant Q6_K, `--spec-type draft-mtp --spec-draft-n-max 5`.

Checked whether already reported upstream: no. Nearby-but-different issues found (#21140 device -1 in recurrent-state restore, #22052 RX 7900 XTX memory fault via Oculink, #20839 invalid-device-function from architecture spoofing) -- none match this trigger combination (WMMA q6_K MMQ + J=112 + MTP-narrow batch widths).

Two hypotheses formed and ruled out with real numbers/source, not guesses:
1. Shared-memory overflow via HIP's no-op `CUDA_SET_SHARED_MEMORY_LIMIT` (confirmed real platform gap, but this GPU's sharedMemPerBlock==sharedMemPerBlockOptin==65536, and the crashing config's real requirement computed by hand is 55,744 bytes -- 9.75KB of headroom, not an overflow).
2. Y-tile global-memory over-read of the src1_q8_1 staging buffer for narrow batches -- ruled out, mmq.cu's own allocation already pads by `ggml_cuda_mmq_get_J_max(...) * sizeof(block_q8_1_mmq)` specifically to make this safe (the same J_max term bigcherry's own ggml_hip_mmq_workspace mirrors, HI54).

Current mitigation (already implemented and live in `src/ggml/src/ggml-cuda/hip-autotune-dispatch.cu`, inside `ggml_hip_mmq_can_execute`, immediately before its final `return ggml_cuda_mmq_variant_is_eligible(...)`): a narrow, reversible, gfx1100-scoped quarantine of exactly this candidate identity (src0_type==GGML_TYPE_Q6_K && primary==112 && fallback==0 && architecture_code==GGML_HIP_ARCH_GFX1100). Explicitly NOT a broad disable of the candidate elsewhere -- this config row is shared with other architectures' own tables that were never proven to crash, and a blanket exclusion would quarantine hardware unnecessarily. Verified fix (not a guess): rebuilt with the block compiled in, reran the exact MTP-9B reproduction twice; `grep -c "mmq:q6_k:j112" journal.jsonl` = 0 and `tune-journal status` reported `complete: true, interrupted: false` -- first fully completed run of that workload in four attempts.

Diagnostic status, 2026-08-14: the quarantine was bypassed only through the opt-in `GGML_HIP_TUNE_TEST_DISABLE_EX02_QUARANTINE=1` switch on Brutus gfx1100. With the exact shared Qwen3.5-9B MTP Q6_K model, `HIP_LAUNCH_BLOCKING=1`, graphs disabled, the `full-max` manifest, and the standard `server-bench` pp512/tg128 workload, the tuner measured the exact J=112/fallback=0 candidate 39 times and all Q6_K MMQ candidates 526 times. The run completed with 89 result records and zero measurement failures, HIP errors, or assertions. A second run under `rocgdb` measured J=112/fallback=0 39 times again and also completed without a fault; the debugger was stopped only by a deliberate SIGTERM after the bench completed. This is clean non-reproduction evidence, not a root-cause capture and not sufficient to remove the quarantine.

GPT-auto review, 2026-08-14: the candidate stable name is coarser than the complete dispatch identity, so these counts do not prove that the historical failing shape was exercised. The separate `/tmp/bc-tune-*` artifact is a Qwen3.5-0.8B run and contains no EX02 fault. The opt-in `GGML_HIP_TUNE_TRACE_ATTEMPTS` record now includes the complete canonical signature JSON beside its digest, so a future killed measurement can be replayed exactly; normal production tracing remains off. The next step remains recovery of the historical digest/full signature and exact tuner-path replay under `HIP_LAUNCH_BLOCKING=1`, graphs disabled, tracing, and `rocgdb`.

Trace implementation validation, 2026-08-14: after applying the pushed overlay to the Brutus vendor checkout and rebuilding the HIP tuner from `15cc257`, one real Qwen3.5-0.8B completion under `HIP_LAUNCH_BLOCKING=1` produced 1,395 durable attempt events. Offline parsing found 1,395/1,395 object-valued `signature_json` payloads, including the complete `ne0`/`ne1`/`ned`, stride, type, flags, op, and refinement fields. Journal SHA-256: `d0eb2dc70bbe2ac1d0de1627ae09755d06fd05b749704d98ec80dcf0079ef9d3`. This validates the diagnostic mechanism only; it is not the historical EX02 reproduction.

Trace integrity validation, 2026-08-14: independently reconstructing the canonical JSON for every one of those 1,395 attempts and applying the production BLAKE2b-128 digest algorithm yielded `digest_matches=1395`, `mismatches=0`. This proves that the emitted signature digest and complete JSON agree for that run; it does not identify the historical failing signature.

Historical-artifact audit, 2026-08-14: the retained `/tmp/ex02-*` journals, logs, measurement exports, `/tmp/bc-tune.sqlite`, repository incident records, and llamacpp raw-log tree were searched for the exact candidate and a complete signature. The exact candidate is present in the clean `ex02-gdb`/`ex02-sweep` diagnostic journals, but those pre-existing attempt records contain no `signature_json` and both runs completed without a fault. The other candidate hits are measurement/catalog records or ineligible forced-probe warnings. No historical fault journal, complete canonical signature, or historical signature digest survived. EX02 therefore remains pending and quarantined; no exact replay or kernel change is justified until that identity is recovered.

The earlier synthetic probe was not an EX02 reproduction: `MUL_MAT(type_a=q6_K,type_b=f32,m=16,n=1,k=256)` requires fallback=1 because the runtime derives `shape_fallback` from `sig.ne0[1] % 128`, so it cannot exercise the `fb0` candidate. Direct `GGML_HIP_FORCE_CANDIDATE` mode is also not a tuner reproduction because an eligible forced candidate returns before the normal measurement path. The next diagnosis must preserve the original failing signature/shape and run through the exhaustive measurement path.

Root cause is still open -- both hypotheses above were real platform/behavior facts but not the actual cause. A live faulting instruction/address inside `ggml_cuda_mmq_vec_dot_q6_K_q8_1_mma` (mmq-vec-dot.cuh) is still required before proposing a kernel or quarantine change; clean generic runs and the new diagnostic bypass do not satisfy that gate.

## Steps

1. Recover the original failing signature digest and full canonical signature/shape from the historical exhaustive-sweep or crash artifact. The opt-in attempt trace now stores `signature_json` beside `signature`, so future faults are directly replayable. Then attach rocgdb to that exact measurement path (Qwen3.5-9B MTP, same args as above, quarantine disabled only in a throwaway diagnostic process) and capture the faulting instruction, address, candidate identity, signature digest, and measurement stage. A generic clean server-bench run is a non-reproduction only.
2. If the historical trigger no longer reproduces, preserve the clean-run evidence and inspect the old artifact/build/source revision for a changed signature, candidate-set, allocator, or measurement-workspace condition. Do not infer a kernel fix from clean runs.
3. Once a root cause is identified, implement a real fix (either in bigcherry's own generated candidate code, or as an upstream-fixes patch if the bug is in llama.cpp's own kernel), then rerun the exact trigger and a clean native control.
4. Remove the quarantine block in hip-autotune-dispatch.cu only after the exact trigger passes under the fixed build on gfx1100 and the evidence identifies why the old fault is prevented.
5. Do not widen the quarantine's scope while root cause is open.
