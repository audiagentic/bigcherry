# Root-cause XTX 0's host-read contention (it halves every other CPU-attached card's GPU transfers)

## Description

RAD40 measured: while XTX 0 (03:00.0, root port 00:01.0, Gen4 x8) pulls host memory at full rate, every GPU-initiated transfer of the other CPU-attached cards halves (XTX 1 13.3 -> 6.8 GB/s, R9700 6.7 -> 3.4), including SDMA copies and GPU writes; CPU BAR pushes keep full rate. XTX 0 wins whichever starts first. A configuration cause (MaxReadReq/MaxPayload, relaxed ordering, extended tags, root-port arbitration, the x8/x8 bifurcation) would be fixable for every layout at no code cost.

## Steps

1. Record lspci -vv for 03:00.0, 06:00.0, 09:00.0, 17:00.0 and root ports 00:01.0, 00:01.1, 00:06.0, 00:1d.0 (needs root on the host): DevCtl MaxPayload/MaxReadReq, RlxdOrd, ExtTag, LnkSta.
2. Re-run RAD40's host-link-bw.hip contention arm, then swap the roles (XTX 1 reading first) and, if possible, the physical slots of XTX 0/1 to separate slot from card.
3. If a setting differs: test matching settings (setpci) under contention.

GPT seed (gateway reviewer, 2026-11-10; full text runs/rad49-gpt-review/seed/):

- Assessment: High-priority diagnosis; root cause not established. RAD40 demonstrates an asymmetric interaction: XTX 0 reading host memory at approximately 13.4 GB/s reduces XTX 1's measured GPU-initiated transfer rate from approximately 13.3 to 6.8 GB/s and the R9700's from 6.7 to 3.4 GB/s. This affects GPU writes as well as reads, so describing it simply as host-memory read-bandwidth saturation is incomplete. CPU BAR writes remain near their uncontended rates. A root-port, requester-credit, platform-fabric or ordering interaction is plausible, but no specific PCIe configuration defect is verified.
- References: [pciutils `lspci` manual, verbose topology/configuration output](https://github.com/pciutils/pciutils/blob/master/lspci.man); [pciutils `setpci` manual, configuration-space access and dry-run mode](https://github.com/pciutils/pciutils/blob/master/setpci.man); [HIP host memory documentation, mapped and NUMA-aware allocations](https://rocmdocs.amd.com/projects/HIP/en/develop/how-to/hip_runtime_api/memory_management/host_memory.html). - Dependencies / ordering: First in the host-link sequence. Its observations should accompany HL02 and HL05, but HL02 need not wait for a configuration fix. Physical card swapping is a later optional experiment, not a prerequisite.

PROGRESS 2026-11-10: negotiated links read from sysfs (XTX0/XTX1 Gen4 x8 on CPU root ports, R9700 Gen4 x4, 6900 XT tail Gen3 x4 via the chipset root port). New tool tools/lab/radiance/host-link-duplex.hip (PR #795). Tail, 5 MiB in/10 MiB out: pull 3.6 GB/s, push 3.55 GB/s (equal to the HL04 act/write stage times, so link-bound); copy-engine duplex 1.06x the slower direction, no slowdown of a concurrent compute kernel; kernel transfers add ~0.5 ms contention. FINDING 2026-11-13 (step 1 done; full `lspci -vv` captured on the host by the user, root):

| | XTX 0 (03:00.0) | XTX 1 (06:00.0) | R9700 (09:00.0) |
|---|---|---|---|
| CPU root port | 00:01.0, PEG x16 controller, first x8 half | 00:01.1, same PEG controller, second x8 half | 00:06.0, separate CPU x4 controller |
| Link | Gen4 x8 (card behind its own Navi switch, internal x16) | Gen4 x8 | Gen4 x4 |
| Endpoint DevCtl | MPS 256, MRRS 512, RlxdOrd+, ExtTag+, NoSnoop+ | identical | identical |
| Endpoint DevCtl2 | 10BitTagReq- (capable +) | identical | identical |
| Switch up/down ports | MPS 256, MRRS 512, RlxdOrd+, ExtTag+ | identical | identical |
| Root port | MPS 256, MRRS 128, RlxdOrd-, ExtTag-, 10BitTagComp+, ASPM disabled | identical | identical |
| AER | clean | clean | clean |

IOMMU: kernel `intel_iommu=on iommu=pt`; the GPU IOMMU groups (20, 24, 28, 43) are all `identity`, so GPU DMA is not translated (IOTLB contention ruled out).

Conclusion: no PCIe configuration difference between the three CPU-attached cards; every setting this item suspected (MaxPayload, MaxReadReq, relaxed ordering, extended/10-bit tags, ASPM) is identical, and the IOMMU is in passthrough. The only asymmetry is position: XTX 0 is the first half of the bifurcated PEG x16 controller. Since the R9700 on a separate controller is also slowed, the shared point is inside the CPU (system agent / IO fabric to memory), which PCI config space does not control. A `setpci` experiment has no target. Remaining optional test: physically swap XTX 0 and XTX 1 to separate slot from card. Mitigation moves to software: HL02 (CPU push under contention) and VTP38 (host-reduced all-reduce).

In-engine evidence the effect is live (VTP36 rad0031 two-shot timeline, int8 TP3, 2048-token prompt, ~10 MB per all-reduce, weights 4,4,1): the XTX ranks do identical reduce work (read 8/9 of the message) yet XTX 0 takes 889 us (~10 GB/s) and XTX 1 1301 us (~6.8 GB/s, the contended rate above); XTX 0 and the R9700 then wait ~400 us at the second barrier, about 10% of each ~4 ms prefill all-reduce. Decode shows the same skew in microseconds (8 streams: 23 vs 39 us). Unrelated: the chipset-attached 6900 XT (00:1d.0, Gen3 x4) has a logged correctable error source 15:00.0.

RESULT 2026-11-13 (slot swap, step 2 done): the two XTX cards were physically swapped between the PEG halves (card A: VBIOS 113-EXT95848-001; card B: VBIOS 113-EXT89622-001). Contention matrix (tools: a kernel reading or writing pinned mapped host memory; background card reads 256 MiB for 12 s, measured card runs 5 s from +3 s), before and after:

| | before: card A at 00:01.0 | after: card B at 00:01.0 |
|---|---|---|
| solo read / write, each XTX | 13.4 / 14.2 GB/s | 13.4 / 14.3 GB/s |
| solo read / write, R9700 | 6.7 / 7.1 GB/s | 6.7 / 7.1 GB/s |
| 00:01.0 card reading: other XTX read / write | 6.7 / 6.7 | 6.7 / 6.7 |
| 00:01.0 card reading: R9700 read / write | 3.4 / 3.5 | 3.4 / 3.4 |
| 00:01.1 card or R9700 reading: anyone else | unaffected | unaffected |
| 00:01.0 card starting 3 s after another reader | still wins (others drop to half) | still wins |

The halving follows the slot (root port 00:01.0, first half of the bifurcated PEG x16 controller), not the card or its VBIOS. With identical PCIe settings and IOMMU passthrough (finding above), the cause is CPU-internal arbitration that favours that port; there is no configuration fix. During the swap, a reboot with card B alone at 00:01.0 already showed it halving the R9700 (3.4 GB/s), where in the second slot before the swap it had not. This item's question is answered: no fix is available, and the mitigation is in software (HL02, VTP38; in VTP36, a smaller reduce share for the rank on 00:01.1, or keeping the 00:01.0 rank's pulls off the critical path).
