# Cross-GPU contention and transfer-method laboratory gates (TP3, TP2 and MoE)

## Description

**Single laboratory owner** for cross-GPU contention and transfer method comparisons: GPU pull, SDMA, GPU writes, coherent/non-coherent host memory, and true CPU BAR/DMA-BUF push. HL01 completed the 2026-11-13 root-port diagnosis. The slowdown follows the first PEG x8 half, not a GPU/VBIOS; while that rank pulls host memory, the other XTX falls to ~6.7 GB/s and R9700 to ~3.4 GB/s for GPU-initiated transfers. CPU BAR push is unaffected. The exact internal CPU arbitration stage remains inferred.

Test actual TP3 all-reduce messages (320 KiB–10 MiB) with simultaneous GPU partial producers and CPU push. Produce a reusable measured host profile. RAD40 is superseded historical evidence; RAD50 owns DMA-BUF mapping/live/fault safety proof. VTP38 alone owns production TP3 host transport; HL03, HL05 and RAD42/RAD51 own distinct MoE and TP2 consumers.

## Steps

1. **Gate A (~5-minute probe):** matched coherent versus genuinely non-coherent/write-combined mapped-host mailbox reads/writes under ongoing first-PEG GPU host reads. Validate payload, explicit ordering and allocation/PCIe attributes where measurable. If contention disappears without failure, test this cheaper mitigation first.
2. **Gate B (concurrent CPU push):** at 320 KiB–10 MiB, compare GPU pull/SDMA, CPU push to the contention-driving rank only, and CPU push to **all three** ranks while GPU producers write partials. Start one P-core-pinned CPU thread per card; try two for x8 only if measured. Record per-card push GB/s, CPU time/memory bandwidth, GPU producer progress, and slowest completion. All-rank results are provisional until Gate C.
3. **Gate C (R9700 qualification):** extend the later positive RAD50 R9700 DMA-BUF mapping/4 KiB–4 MiB verification to full 10 MiB, repeated generations, GPU-already-waiting consumer, posted-write readiness, faults and reuse. Distinguish the original inconclusive HSA-pool canary from the working DMA-BUF API.
4. **Matched controls:** A idle victim GPU pull, B victim GPU pull under primary pull, C primary CPU-fed/no primary GPU pull with victim GPU-pull *recovery*, D victim CPU BAR push while primary GPU pull continues, E primary GPU write-only trigger and victim read/write, F measured primary duty-cycle 0/25/50/75/100%, including reversed starting order. Never count `hipMemcpyAsync` as CPU BAR push.
5. **Piece pipeline:** GPU write k+1 / CPU work k / CPU push k-1, with RAD50 generation/ready/ACK and no stale buffer reuse; measure complete critical path rather than only nominal link rates.
6. **Handoff:** compare matched prefill/decode shapes, fit method/shape crossover with uncertainty, and give VTP38 a topology-calibrated host profile without model, BDF or device-order runtime constants.

## Detailed Solution & Technical Design

**Different questions require different gates.** Arm C asks whether a *victim GPU pull* recovers to >=90% of its own idle GPU-pull rate when the primary no longer pulls. Arm D asks whether *victim CPU BAR push* under ongoing primary GPU reads reduces actual producer-to-consumer makespan. The >=90% GPU-pull metric must not be applied to CPU BAR push (whose idle throughput is already lower). Arm E checks whether primary GPU writes alone create the same arbitration; F measures duty-cycle/onset and start-order effects.

Use RAD50's ROCr VMM DMA-BUF export, `SCM_RIGHTS` to a CPU-only process, persistent `mmap`, `DMA_BUF_IOCTL_SYNC START/END`, corrected gfx11 device-rate-scaled `wall_clock64()` waiter, full-word GPU verifier and generation-bound ready/consumed tickets. A CPU fence or host-ready flag alone is not evidence of completed posted BAR writes. Preserve direct and parent-coherent-relay controls and fail closed on timeout, early publication or stale generation.

Run paired interleaved sessions under the GPU lease. Record physical topology *as run metadata*, GPU/ROCm/kernel/build, exact bytes/stride, RAM/coherence attributes, CPU affinity/power, real competing GB/s and active time, producer CPU/GPU work, first piece, last arrival, CPU memory bandwidth and p50/p95 (p99 only with enough samples). For S=10 MiB, three producer GPU writes contribute 3S bytes, a CPU sum reads 3S, and all-three CPU pushes write 3S to BAR targets, plus potential S intermediate; count measured RAM, cache and BAR traffic independently.

Performance decision: >=15% realistic affected transfer-makespan improvement or >=0.3 ms representative layer critical-path saving without >5% repeatable p99 regression. Numerical/correctness and all-rank life/fault requirements precede any VTP38 production change.
