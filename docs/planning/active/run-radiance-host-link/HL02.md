# Contention A/B: GPU pull vs CPU BAR push for the consumer card while XTX 0 reads

## Description

All RAD50 push gains so far are on idle links (R9700 combine 1.25x serial at 768 rows, ~1.0x at 1-16). Under XTX 0 read contention the pull halves while the push does not, so the system-level gain may be much larger. RAD50's S6 contention gate is still open.

## Steps

1. Add a background-load arm to rad50-tester (or reuse RAD40 host-pull.hip): steady host reads on XTX 0.
2. Measure the R9700 (and XTX 1) consuming 256-2048-row planes by GPU pull vs DMA-BUF CPU push, with and without the background load; record the other cards' throughput too.
3. Report transfer makespan and the background card's rate for each arm.

**Required matched contention matrix (each victim XTX 1 and R9700):**

| Arm | Primary-slot GPU / primary target | Victim action | Deciding question |
|---|---|---|---|
| A | Idle | GPU pull pinned host payload | Uncontended reference |
| B | GPU continuously pulls host payload | GPU pull pinned host payload | Reproduce the ~half-rate victim |
| C | CPU BAR/DMA-BUF pushes payload into primary GPU VRAM; **no primary GPU host pull** | GPU pulls host payload | Does the victim's original pull rate recover? |
| D | Primary GPU continuously pulls host payload | **CPU BAR/DMA-BUF pushes into victim VRAM** | Does CPU push bypass contention even while it persists? |
| E | Primary GPU writes (not reads) pinned host payload | Victim GPU pulls, then writes host (separate arms) | Is the trigger specifically primary GPU host *reads*? |
| F | Primary GPU pulls host at 0/25/50/75/100% measured duty cycle | Victim GPU reads/writes host | Priority-onset vs proportional arbitration; reverse start order |

Record primary-reader actual GB/s and active interval, not just commanded duty cycle. C's >=90% recovery test compares the victim's **GPU pull** with its own A baseline, not CPU-push bandwidth. D instead compares real producer-to-consumer time: RAD40's CPU BAR writes to XTX 1/R9700 (~10.3/~5.6 GB/s) remain below idle GPU pulls (~13.3/~6.7) but exceed contended GPU pulls (~6.8/~3.4). HIP H2D asynchronous memcpy is GPU/SDMA-initiated on the measured path and **is not CPU BAR push**.

**Shapes and experiment controls.** Include the existing 1/16/64/256/768/2048-row MoE shapes and TP3 all-reduce sizes ~320 KiB to ~10 MiB, with actual byte counts, strides and pinned allocations recorded. Test whole-plane and realistic pipelined 256-row consumption. Fix clock/power states, CPU affinity/thread count, BDF-to-rank mapping, ROCm/BIOS/build, source data, warmup and verification overhead. Capture source write/publish, DMA-BUF SYNC, CPU reduction/copy, GPU first-read, generation-ready/ACK and completion; collect p50/p95 (p99 only with adequate repeats), per-device bandwidth and makespan. Run >=3 interleaved ABBA sessions under the GPU lease, including background-only and no-background CPU load controls. Check full payload content, delayed writes, missed readiness, already-running GPU verifier, buffer recycle, fault and timeout cases.

**Coherence diagnosis is separate.** RAD40 already observed *equal idle* GPU host-read bandwidth for coherent, non-coherent and write-combined buffers. That does not establish contended equivalence. HIP coarse-/fine-grained or mapped-host flags do not by themselves prove a changed PCIe No Snoop attribute or elimination of CPU snooping; a valid A/B must establish equivalent PCIe traffic and working set, correct explicit synchronization, and transaction cacheability/attributes where measurable. Never promote non-coherent mailboxes to production on a bandwidth result alone.

**Stop/go by question.** Diagnosis passes C only if the victim's GPU pull recovers >=90% of A without new correctness defects. CPU push passes D for an application only if actual contended transfer-path makespan improves >=15% or a representative layer critical path saves >=0.3 ms, with no p99 regression >5%. Neither test alone approves a production path. Recheck current R9700 full-size, cross-process and *GPU-live* DMA-BUF receipts: an older serial canary or idle-only pass does not validate all requirements.
