# Concurrent-agent shared-checkout coordination (source-control, not toolchain)

## Description

Split out of TO01 (2026-08-23, plan-hygiene, audit §7.2 concern C). This is a SOURCE-CONTROL / concurrent-agent operational concern, NOT a toolchain concern -- filed separately so it stops being buried inside a dependency-management item.

Confirmed this session on Brutus: multiple agent sessions run against the SAME ~/bigcherry git checkout concurrently, with no lock file or coordination mechanism. Two agents' uncommitted work landed in the same working tree at different points (HI64/HI67/HI89/HI90 from a concurrent session vs. this session's HI80/HI24/HI37/HI16/RD87), and releases/*.json bookkeeping files were independently regenerated by at least two different agents' `bigcherry apply`/`audit` runs on the same checkout without any coordination -- each session just reverts the other's incidental side effects rather than anything being actually locked. This same class of problem already caused real planning-tool data loss (the RD69-76 concurrent-write race, root-caused and handed to AUDiaGentic).

Scope: this is a source-control coordination problem, not a build-isolation problem -- build OUTPUT dirs (vendor/rocm-libraries/, ~/bc-build-*) are self-contained and gitignored and NOT a collision risk. The real risk is entirely in the shared git checkout and its generated-but-tracked bookkeeping files (releases/*.json).

## Steps

- At minimum: document the informal protocol every session has been improvising as an explicit written convention -- check git status before committing, stage only your own files, never touch a file another session has uncommitted changes in, revert releases/*.json regeneration noise before committing.
- At most: a real lock file or session-registration mechanism (e.g. .agentic/active-sessions/<pid>.json heartbeat) that lets a session see what another is currently touching before it starts.
- Coordinate with AUDiaGentic (audiagentic.components.planning) where the same cross-process concurrency root cause applies to the planning tool itself.
