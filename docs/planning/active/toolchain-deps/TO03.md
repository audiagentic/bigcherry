# Concurrent-agent shared-checkout coordination (source-control, not toolchain)

## Description

Current-source review at BigCherry `7e690088df137321b00d92e7f1b2bb6142081133` confirms the risk is shared-checkout source-control ownership, not build/campaign isolation.

Existing safeguards already cover part of the requirement:

- `AGENTS.md` forbids `git stash`, `git reset`, and `git rebase` in the shared tree.
- `docs/reference/tooling/TOOLING.md` requires preserving unrelated shared-worktree edits and not staging another actor's work.
- build/source tooling uses isolated/generated work roots and detached source worktrees; `.gitignore` already excludes `artifacts/`, `vendor/`, and build outputs.

The bounded missing piece was an explicit operational staging/ownership protocol. It is now documented in `docs/reference/tooling/SHARED_WORKTREE.md`. No lock/session registry is justified without a reproducible collision that survives the documented protocol.

## Current-source disposition

- **Written protocol: DONE.** It requires pre/post `git status`, explicit-path staging, staged-diff inspection, ownership of generated tracked files, no broad staging/commit-a, no destructive git commands, and no force push.
- **Stale instruction corrected:** the old step to "revert releases/*.json regeneration noise" is unsafe when provenance is unknown. The correct rule is leave unrelated generated changes unstaged; restore only changes known to be yours.
- **Lock/session registry: NOT REQUIRED YET.** Existing ignored build/artifact/vendor roots are not evidence of a checkout collision requiring global locking.
- **Concurrent exercise: BLOCKED.** GitHub-only review cannot run two live sessions against the same checkout.
