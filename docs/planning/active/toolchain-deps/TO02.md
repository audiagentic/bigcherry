# Structured evidence capture for ad-hoc real-hardware verification runs (non-patch)

## Description

Split out of TO01 (2026-08-23, plan-hygiene, audit §7.2 concern B). TO01 mixes three independent concerns; this is the toolchain/hardware EVIDENCE-CAPTURE half.

Problem: this session's real-hardware verification runs (HI16 forced-native parity, HI24 hot-list smoke test, HI37 cross-language digest check, RD87's build attempts) were captured only as prose in each plan item's own notes field -- not indexed, not structured, not reusable the way docs/reference/patch-validation-evidence/*.json + patch_validation_campaign.py is for PATCH acceptance specifically. There is no equivalent structured evidence store for feature-level real-hardware verification runs that aren't patch-acceptance campaigns.

Reuse-first: reuse existing provenance/environment-input systems where possible. Do not invent a third parallel mechanism without first checking whether patch_validation_evidence.py's mechanism can be generalized to non-patch verification runs.

## Steps

- Decide whether ad hoc real-hardware feature-verification runs (distinct from patch-acceptance campaigns) deserve their own structured evidence store, or whether generalizing the existing patch-validation-evidence mechanism to cover non-patch verification runs is the better fit -- don't invent a third parallel mechanism.
- If a new/extended mechanism is built, retrofit this session's own real-hardware runs (HI16 forced-native parity, HI24 hot-list, HI37 workload digest cross-check, RD87's build attempts) as its first real entries, so the mechanism is validated against real prior evidence rather than only future runs.
