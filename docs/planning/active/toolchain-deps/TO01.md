# Formalize external dependency/toolchain management (ROCm, Vulkan, llama.cpp pin, multi-version)

## Description

This session found real gaps in how BigCherry tracks and documents its external dependencies: (1) a working vendored ROCm 7.1 HIP toolchain plus a real local GPU were available on this workstation the whole time, but that wasn't obvious/discoverable without already knowing to check vendor/rocm/ and BUILD.md's Windows section -- an agent (or a new contributor) starting cold could easily conclude 'no compiler/hardware available' incorrectly, as happened this session. (2) hipBLASLt's offline-tuning client binaries are a real, confirmed, currently-unfilled dependency gap (RD87) with no documented acquisition path until this session. (3) More broadly: the project already vendors multiple ROCm versions side by side (vendor/rocm/7.1, 7.2.4, 7.14, 7.14-multiarch across Windows/Brutus per BUILD.md), tracks the llama.cpp upstream pin via recipes.toml's tree_state_key/repin mechanism, and may need to support multiple GPU backends (Vulkan is named by the owner as a concern, alongside HIP) -- but there is no single place that inventories 'what toolchains/backends/library versions does this project depend on, which are vendored where, which are missing, and how do you get the missing ones.'

## Steps

1. Audit what's actually vendored/available today across both known build hosts (this Windows workstation's vendor/rocm/<version>/, Brutus's vendor/rocm/<version>/ plus its system /opt/rocm*) and record it somewhere durable -- not just discovered ad hoc per session.
2. Decide the doc/tooling shape: extend BUILD.md's new 'Known dependency/toolchain gaps' section (this session, 2026-08-23) into a fuller dependency inventory, or a dedicated DEPENDENCIES.md, or a machine-readable manifest tools/bigcherry could read/validate against (e.g. a `bigcherry doctor`-style command that reports what's vendored/missing) -- pick one rather than letting documentation and reality drift independently.
3. Establish whether Vulkan is a real near-term backend concern for this project (grep for existing Vulkan references/plans) or a hypothetical the owner wants tracked preemptively -- scope this item's Vulkan half accordingly rather than assuming.
4. Cover multi-version handling explicitly: the project already has two versioning concerns that interact (ROCm toolchain version vendored under vendor/rocm/<version>/, and the llama.cpp upstream pin via recipes.toml) -- document how they compose (e.g. does a given recipe/pin combination require a specific ROCm version, and is that recorded/checked anywhere).
5. Close RD87's concrete sub-gap (hipBLASLt client build) as part of or alongside this, once scoped.
