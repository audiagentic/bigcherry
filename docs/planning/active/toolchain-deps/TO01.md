# Toolchain/dependency acquisition and version inventory (ROCm toolchains, llama.cpp pin, Vulkan backend)

## Description

NARROWED 2026-08-23 (plan-hygiene, audit §7.2): this card was a mega-item mixing three concerns; it now covers ONLY toolchain/dependency acquisition + version inventory (concern A). The evidence-capture half is TO02; the concurrent-agent coordination half is TO03. See the Split note in Notes for the migration record.

Problem: BigCherry vendors multiple ROCm toolchain versions side by side (vendor/rocm/7.1, 7.2.4, 7.14, 7.14-multiarch across the Windows workstation and Brutus per BUILD.md) and tracks the llama.cpp upstream pin via recipes.toml's tree_state_key/repin mechanism, but there is no single durable place that inventories: what toolchains/backends/library versions the project depends on, which are vendored where, which are missing, and how to obtain the missing ones. This has already caused a real session-level failure: a working vendored ROCm 7.1 HIP toolchain plus a real local GPU were available on this workstation the whole time, but that was not discoverable without already knowing to check vendor/rocm/ and BUILD.md's Windows section -- a cold agent/contributor could easily conclude 'no compiler/hardware available' incorrectly (as happened). And a real confirmed dependency gap (hipBLASLt offline-tuning client binaries, RD87) had no documented acquisition path until its fix escalated live from 'install a package' to 'sparse-clone a much larger monorepo (rocm-libraries)' -- evidence that acquisition paths need to be recorded BEFORE they're needed, not rediscovered per session.

## Steps

- 1. Audit what's actually vendored/available today across both known build hosts (this Windows workstation's vendor/rocm/<version>/ + local GPU; Brutus's vendor/rocm/<version>/ plus its system /opt/rocm*) and record it somewhere durable -- not just discovered ad hoc per session.
- 2. Decide the doc/tooling shape: extend BUILD.md's 'Known dependency/toolchain gaps' section (2026-08-23) into a fuller dependency inventory, or a dedicated DEPENDENCIES.md, or a machine-readable manifest tools/bigcherry could read/validate against (e.g. a `bigcherry doctor`-style command that reports what's vendored/missing) -- pick one rather than letting documentation and reality drift independently.
- 3. Establish whether Vulkan is a real near-term backend concern for this project (grep for existing Vulkan references/plans) or a hypothetical the owner wants tracked preemptively -- scope the Vulkan half accordingly rather than assuming. (Note: RE30's stock Vulkan lane now exists and is proven, which changes this question's answer -- re-verify against RE30's current state.)
- 4. Cover multi-version handling explicitly: the project has two interacting versioning concerns (ROCm toolchain version vendored under vendor/rocm/<version>/, and the llama.cpp upstream pin via recipes.toml) -- document how they compose (e.g. does a given recipe/pin combination require a specific ROCm version, and is that recorded/checked anywhere).
- 5. Close RD87's concrete sub-gap (hipBLASLt client build) as part of or alongside this, once scoped -- including recording its real acquisition path (ROCm/rocm-libraries monorepo, sparse-checked-out into vendor/rocm-libraries on Brutus, per RD87's 2026-08-23 notes) once RD87 settles.
