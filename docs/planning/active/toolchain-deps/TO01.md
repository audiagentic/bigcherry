# Formalize external dependency/toolchain management AND ad hoc test/evidence capture

## Description

This session found real gaps in how BigCherry tracks and documents its external dependencies AND how it captures the results of ad hoc real-hardware verification runs. (1) a working vendored ROCm 7.1 HIP toolchain plus a real local GPU were available on this workstation the whole time, but that wasn't obvious/discoverable without already knowing to check vendor/rocm/ and BUILD.md's Windows section -- an agent (or a new contributor) starting cold could easily conclude 'no compiler/hardware available' incorrectly, as happened this session. (2) hipBLASLt's offline-tuning client binaries are a real, confirmed, currently-unfilled dependency gap (RD87) with no documented acquisition path until this session -- and RD87's own investigation escalated well past a simple missing-package problem into a structural one (the ROCm/hipBLASLt tag needs AMD's much larger rocm-libraries monorepo, not a standalone clone), which is itself evidence that dependency acquisition paths need to be recorded BEFORE they're needed, not rediscovered live each time. (3) More broadly: the project already vendors multiple ROCm versions side by side (vendor/rocm/7.1, 7.2.4, 7.14, 7.14-multiarch across Windows/Brutus per BUILD.md), tracks the llama.cpp upstream pin via recipes.toml's tree_state_key/repin mechanism, and may need to support multiple GPU backends (Vulkan is named by the owner as a concern, alongside HIP) -- but there is no single place that inventories 'what toolchains/backends/library versions does this project depend on, which are vendored where, which are missing, and how do you get the missing ones.' (4) Separately, this session ran several real-hardware verification passes (HI16's forced-native-parity check, HI24's hot-list smoke test, HI37's cross-language digest check) whose results were captured only as prose in each plan item's own notes field -- discoverable if you know which item to check, but not indexed, not structured, and not reusable the way docs/reference/patch-validation-evidence/*.json + patch_validation_campaign.py already is for PATCH acceptance specifically. There is no equivalent structured evidence store for feature-level real-hardware verification runs that aren't patch-acceptance campaigns.

## Steps

### Toolchain/dependency half
1. Audit what's actually vendored/available today across both known build hosts (this Windows workstation's vendor/rocm/<version>/, Brutus's vendor/rocm/<version>/ plus its system /opt/rocm*) and record it somewhere durable -- not just discovered ad hoc per session.
2. Decide the doc/tooling shape: extend BUILD.md's 'Known dependency/toolchain gaps' section (2026-08-23) into a fuller dependency inventory, or a dedicated DEPENDENCIES.md, or a machine-readable manifest tools/bigcherry could read/validate against (e.g. a `bigcherry doctor`-style command that reports what's vendored/missing) -- pick one rather than letting documentation and reality drift independently.
3. Establish whether Vulkan is a real near-term backend concern for this project (grep for existing Vulkan references/plans) or a hypothetical the owner wants tracked preemptively -- scope this item's Vulkan half accordingly rather than assuming.
4. Cover multi-version handling explicitly: the project already has two versioning concerns that interact (ROCm toolchain version vendored under vendor/rocm/<version>/, and the llama.cpp upstream pin via recipes.toml) -- document how they compose (e.g. does a given recipe/pin combination require a specific ROCm version, and is that recorded/checked anywhere).
5. Close RD87's concrete sub-gap (hipBLASLt client build) as part of or alongside this, once scoped -- including recording its real acquisition path (rocm-libraries monorepo vs. an older standalone-buildable tag) once RD87 settles which one actually works.

### Test/evidence-capture half (owner request, 2026-08-23, folded in)
6. Decide whether ad hoc real-hardware feature-verification runs (distinct from patch-acceptance campaigns, which already have patch_validation_campaign.py) deserve their own structured evidence store, or whether extending the existing patch-validation-evidence mechanism to cover non-patch verification runs is the better fit -- don't invent a third parallel mechanism without checking whether the existing one can just be generalized.
7. If a new/extended mechanism is built, retrofit this session's own real-hardware runs (HI16 forced-native parity, HI24 hot-list, HI37 workload digest cross-check, RD87's build attempts) as its first real entries, so the new mechanism is validated against real prior evidence rather than only future runs.
