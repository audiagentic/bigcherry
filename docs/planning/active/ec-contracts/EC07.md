# Correctness gates: parity/reference/bit-identity per contract

## Description

Wire parity/reference/bit-identity requirements declared by the contract's `correctness` section (e.g. `backend_reference: required`, `greedy_parity: required`) into the actual gate that must pass before a contract's evidence is considered complete.

Full source: docs/reference/BigCherry_Experiment_Contract_Implementation_Guide.md (§7 EC07 row, §12 step 8, Appendix A correctness notes).

## Detailed Solution & Technical Design

## Correctness requirements observed per-patch (guide Appendix A, the concrete cases this gate must support)
- 1002 (hip_unsafe_math_opt_in): MTP contracts must record unsafe-math build state and require bit-identical acceptance -- a correctness requirement tied to a BUILD OPTION, not just a kernel candidate.
- 1201 (RD20 attn_gate_tp_split): correctness-first contract; reproduce the pre-fix failure where possible, prove 1/2/3+ GPU equality.
- 1204 (RD08 Q6_K MMVQ VDR2): gate on bit-identity vs VDR1.
- 1205 (RD12 paired MMVQ dual output): gate on bit-identity.
- 1207 (RD17 MoE top-k down fold): gate on PPL/output equality.
- 1209 (RD22 iGPU host-buffer backout): promote only with integrated-GPU output/PPL evidence -- correctness evidence must be architecture-scoped, not assumed to generalize from a different GPU class.
- 1210 (RD26a): partial cluster -- correctness claim must stay incomplete until the composition-gated FA/MMVQ pieces are validated together, not claim RD26 complete from the standalone subset alone.

Guide §12 step 8: "Run correctness/parity/bit-identity checks appropriate to the optimization." Reuses `parity.py`/`parity_loaders.py`/existing HI correctness tests per guide §3 -- this item is the WIRING (contract declares which checks are required, gate enforces they ran and passed) not a new correctness-checking engine.

## Validation

A contract declaring `greedy_parity: required` cannot reach promotion (EC09) without a passing parity result attached to its evidence bundle (EC05); a contract declaring no correctness requirements is still valid (guide Appendix B: "a correctness patch may have no expected throughput gain" implies the inverse is also true -- a pure-performance contract may legitimately declare minimal correctness scope, but the declaration must be explicit, never silently absent).
