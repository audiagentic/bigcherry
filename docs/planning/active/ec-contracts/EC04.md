# Lane metadata: contract/optimization ID, role, workload, model reference

## Description

`campaign_lane.py` carries contract ID, optimization ID, role (positive/control/boundary/holdout), workload tag and model/recipe reference through the lane execution spec/result, so downstream evidence binding (EC05) and reporting (EC10) can attribute a lane's outcome back to exactly which part of the contract it was proving.

Full source: docs/reference/BigCherry_Experiment_Contract_Implementation_Guide.md (§7 EC04 row).

## Steps



## Detailed Solution & Technical Design

Extends `CampaignLaneExecutionSpec` (see `experiment: str | None` already added this session for the `--experiment` isolated-patch-bench mechanism) with contract-aware fields: `contract_id`, `optimization_id` (the atomic_part from the contract's source section), `role` (one of positive/control/boundary/holdout), `workload_tag`, and `model_ref`. This is metadata carried alongside the lane, not new identity -- per guide §2's non-negotiable architecture, workload labels are experiment metadata, not kernel-family identity, and must not perturb build_plan_id/effective_build_id/source_slice_id.
