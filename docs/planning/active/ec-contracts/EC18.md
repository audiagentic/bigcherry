# Mandatory trigger-proof requirement for performance contracts

## Description

External review (2026-08-20) found that a performance contract can pass merely because a benchmark completed, without proving the candidate code path was actually exercised. A benchmark run against a model/workload that never triggers the target signature can look like legitimate neutral (or even passing) evidence, when it's actually meaningless -- especially dangerous for narrow-eligibility optimizations (tiny-M Q8, specific head sizes, specific MoE density, BF16 KV, gfx1151-only, hybrid/GDN graph shapes).

## Steps

Every performance contract needs a machine-checkable 'this code path was actually exercised' assertion (e.g. candidate kernel launches > 0, expected route selected > 0, mean-occupancy selector selected > 0), consumed from BigCherry's existing coverage/telemetry instrumentation (0700 coverage_counters, 0810 replay_hit_diagnostics, 0820 measurement_signature_shapes, 0830 split_reduce_telemetry -- all already built and validated, per this project's own framework patch series). Missing trigger evidence should make a contract report INVALID, a third state distinct from pass/fail, not silently treated as a neutral/passing result.

## Detailed Solution & Technical Design

Adds a new evaluation layer to tools/bigcherry/experiment_contract.py, consumed by EC09's evaluate_promotion_gate() as a mandatory-if-supplied precondition:

- TriggerEvidence (frozen dataclass): one lane's proof that the target code path actually ran -- role, lane_id, candidate_launches (int|None), expected_route_selected (int|None). Requires at least one of the two count fields (raises ExperimentContractError otherwise, since a lane with neither is unfalsifiable); both fields must be non-negative integers when present.

- evaluate_trigger_proof(trigger_evidence: list[TriggerEvidence]) -> dict: fails closed unless every POSITIVE-role lane has candidate_launches > 0 or expected_route_selected > 0. Scoped to positive-role lanes only (mirrors aggregate_contract_effects/EC06's own precedent) -- control lanes deliberately should NOT trigger the candidate in most contracts, and boundary lanes explore the edge of eligibility and may legitimately sit on the non-triggering side, so neither is checked here. An empty evidence list fails closed (not vacuously true). Returns {passed, reasons, checked_lanes, untriggered_lanes}.

- evaluate_promotion_gate() gains an optional trigger_proof parameter, checked FIRST: when supplied and trigger_proof['passed'] is False, the function returns immediately with {status: 'invalid', passed: False, reasons: [...]} -- never falling through to correctness/effects/regression checks, since those numbers are meaningless if the candidate path never ran. When trigger_proof passes or is None (backward compatibility for existing/EC18-unaware callers), the existing pass/fail logic runs unchanged, now also returning a status field ('pass' or 'fail') alongside the pre-existing passed boolean for callers that want the three-way distinction without a breaking key removal.

- render_report() surfaces the status field explicitly when present, with a dedicated INVALID callout distinct from the existing 'blocked by:' fail rendering, so a rejected-for-real-reasons contract and an unfalsifiable-measurement contract read differently in the human-facing report.

Who produces TriggerEvidence: out of scope for this slice -- this item implements the evaluation gate only, per EC07's own precedent (the gate consumes facts, it does not measure them). A future integration slice would read candidate-launch/route-selection counts out of the existing 0700/0810/0820/0830 telemetry artifacts referenced in this item's original notes and construct TriggerEvidence instances from them; no such reader was written this session, and none of those telemetry artifacts were inspected for exact field names -- that remains open (see Notes).

## Validation

Full offline suite: 1670 passed, 3 skipped (up from 1653 before this change). New tests: TriggerEvidenceTests (5 cases: requires-one-field, launches-only, route-only, rejects-negative, rejects-bool-as-int), TriggerProofTests (6 cases: all-lanes-triggered via launches, via route-selected, one-untriggered-lane-fails, empty-evidence-fails-closed, control-role-not-checked, boundary-role-not-checked), plus 5 new cases folded into PromotionGateTests (status='pass'/'fail' on the existing paths, missing-trigger-proof short-circuits to invalid even with perfect effects, passing trigger-proof does not block a real pass, trigger_proof=None preserves old behavior) and 1 into RenderReportTests (invalid status renders distinctly). No hardware validation performed or needed for this slice -- pure evaluation logic over already-produced telemetry counts, no new instrumentation site was added.

## Effort & Risk

Low implementation risk (pure Python, additive, backward-compatible via the optional trigger_proof parameter). The real risk is scope: this closes the EVALUATION half of EC18 (given trigger evidence, correctly gate on it) but not the PRODUCTION half (actually extracting candidate_launches/expected_route_selected from real 0700/0810/0820/0830 telemetry for a real contract run) -- a contract author today still has to hand-construct TriggerEvidence; nothing wires it up automatically yet. Do not consider EC18 fully closed on the strength of this slice alone.

## Acceptance Criteria

- [x] A machine-checkable trigger-proof evaluation exists (evaluate_trigger_proof), independent of correctness/performance evaluation.
- [x] A contract whose positive-role lane(s) never exercised the candidate (zero launches AND zero route selections) reports a distinct INVALID status, not pass or fail.
- [x] Trigger-proof failure short-circuits before correctness/effects/regression checks run -- an invalid measurement never gets a chance to look like a real pass.
- [x] Backward compatible: omitting trigger_proof (existing/pre-EC18 callers) preserves exactly the prior pass/fail behavior.
- [x] render_report() distinguishes INVALID from a normal fail in the human-readable output.
- [ ] TriggerEvidence is actually populated from real BigCherry telemetry (0700/0810/0820/0830) for at least one real contract run -- not done this session; the evaluation gate exists and is tested, but nothing in the repo yet constructs TriggerEvidence from a real telemetry artifact.
