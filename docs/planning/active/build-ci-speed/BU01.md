# Cut radiance build time: docs-only PRs skip the engine build, CI-seeded compiler cache for the lab, prebuilt release bundle, smaller kernel recompiles

## Description

Radiance builds are slow when they are cold. CI (radiance-build.yml) already uses a prebuilt ROCm 7.2.4 image, a ccache keyed per run with restore-keys, and a cached bare upstream clone; warm runs on main take about 2 minutes. Any change that touches the radiance sources or the libr3 GPU kernels recompiles the big device-code units: 28 to 73 minutes in CI (runs 41763998632, 41750493766, 41719889181, 41687743079) and about 25 minutes in the lab for a branch build (RAD46, RHP11 F/G). Two further costs: (a) the radiance-build job runs on docs-only PRs, because its path filter 'engines/radiance/**' matches READMEs and plan files (PR 559 changed only markdown and still queued the full build); (b) the lab cannot reuse CI's compiler cache, and every released pin is rebuilt locally because the GitHub release carries no binary (MEN27). This item is the umbrella for four independent speed-ups; each is a separate slice.

## Steps

1. SLICE 1 - skip the engine build for docs-only changes. In radiance-build.yml (and the caller decision in pr-ci.yml) exclude markdown, docs/** and docs/planning/** from the path filter, keeping engines/radiance/** code, patches, component.toml, CMake and test files. Prefer a paths-ignore list over enumerating includes, so a new source directory cannot silently be skipped. Make sure the required check 'ci-pass' still passes when the job is skipped (the 'skipping' result is already accepted for other jobs).
2. SLICE 2 - seed the lab compiler cache from CI. Measure first: in a branch build, how many translation units miss, and what is the hit rate with the CI cache imported. Then publish main's ccache directory as a downloadable artifact (or restore it from the Actions cache with gh cache / actions-cache tooling) and add a lab step that imports it into BC_WORK_ROOT's ccache, with CCACHE_BASEDIR and CCACHE_NOHASHDIR set the same way as CI so keys match. The lab compiler version, flags and ROCm version must equal the image's, or no entry will hit: record both and fail loudly on a mismatch.
3. SLICE 3 - prebuilt runtime bundle on each release (this is MEN27; either implement it here and close MEN27 into this item, or make this slice depend on it). pin-release attaches the lane build's runtime bundle (engine, libr3, libr3moe, libr4d, radiance_home, libs) plus a SHA-256 file to the GitHub release, and records the digests in releases/<pin>.json. Add a lab command that, for the stock pin, downloads and verifies the bundle into the build store under the same plan-id key lab-build.sh uses, so rad_build finds it and does not compile. Branch builds (patches, component changes) still compile.
4. SLICE 4 - smaller recompiles for kernel edits. Using the compile logs and ninja -d stats from a RAD46/F-G-style edit, list the units that rebuilt and why. Split the large kernel translation units so an edit to one kernel does not rebuild unrelated ones, and move rarely-changing kernels into their own library targets. Keep each split behaviour-neutral: same kernels, same code-object hashes where the compiler is deterministic, and the component tests unchanged.
5. Re-measure after each slice and write the numbers (cold, warm, docs-only, kernel-edit) into this item's notes.

## Detailed Solution & Technical Design

WHY EACH LEVER: the cold time is dominated by hipcc device-code compilation of a few very large units, so the levers are (1) do not build when nothing buildable changed, (2) turn a lab cold build into a mostly-warm one by sharing the cache CI already fills, (3) skip the build completely when the source is the stock pin, (4) reduce the size of the unit that must rebuild when someone edits one kernel.

SLICE 1 DESIGN: pr-ci.yml decides which jobs run from a 'changes' job; the radiance build is a reusable workflow with its own on.pull_request.paths. A docs-only PR therefore either never starts the workflow (then the required 'radiance / build' check is absent, which a branch ruleset may treat as missing) or starts it and skips. Verify how the ruleset treats a missing check before choosing; the existing 'skipping' conclusions for compile-only and offline-patch show the accepted pattern. Do not drop the component tests for changes under engines/radiance/components/** or patches/**.

SLICE 2 DESIGN: ccache keys depend on the compiler binary and mtime-independent content hashes of preprocessed source plus flags; with CCACHE_BASEDIR=/src and CCACHE_NOHASHDIR=true the build tree path no longer matters (already done for CI). The lab builds in a different path and possibly a different ROCm; prove equality by compiling one unit in both places and comparing ccache's hash inputs (ccache --print-stats and CCACHE_DEBUG=1). If the compilers differ, the lab should compile inside the same build image (docker) rather than on the host, which also removes drift.

SLICE 3 DESIGN: the bundle is already a build output keyed by plan id (work/builds/<store>/<plan>). A release asset is that directory tarred deterministically (sorted names, fixed mtime and owner) with a SHA-256 list. The consumer re-derives the plan id from the pinned source and the stock patch set, downloads the asset whose release record names that plan id, verifies the digest, and unpacks it into the store. A mismatch or missing asset falls back to compiling, never to an unverified binary. No P2P, no machine names in the asset or record.

SLICE 4 DESIGN: do not guess; start from evidence (which units rebuilt for the RAD46 and RHP11 edits). Typical wins are header include fan-out (a widely included header edited by a small change) and monolithic .hip files holding many kernels. Prefer moving a kernel into its own unit over template tricks.

## Validation

Measure before and after on the same inputs and record all four numbers in notes: (a) a docs-only PR: the radiance build is skipped and ci-pass is green; (b) a cold CI build and a warm one; (c) a lab branch build after a one-kernel edit, with and without the imported CI cache (report ccache hit rate and wall time); (d) a lab stock-pin start from a downloaded bundle that does not invoke the compiler (check the log for zero compile steps and that the binary's SHA matches the release record). Negative tests: a corrupted bundle or digest mismatch is rejected and the lab falls back to compiling; a PR touching engines/radiance/components/** or patches/** still runs the full build and component tests; a mismatched compiler between lab and CI cache is reported, not silently used. Run tools/tests/release and tools/tests/campaign suites and the workflow lint.

## Effort & Risk

Slice 1 is small and low risk; the one trap is a required check that goes missing instead of skipping. Slice 2 is medium: it only pays if the lab and CI compiler and flags are identical, and a wrong match would fail quietly into a cold build, so detect and report it. Slice 3 is medium and touches the release process, so it needs the release-line owner's review; a bad asset must never be trusted (verify digest, fall back to compiling). Slice 4 is the largest and riskiest because it edits GPU kernel sources: split behaviour-neutrally and guard with the existing component tests and a code-object comparison. Do slices 1 and 3 first; they give the most for the least risk.

## Standards

Managed changes only (no ad hoc scripts outside the repo); no compatibility shims; no machine names, local paths or tokens in workflows, assets or release records; fail closed on any digest or compiler mismatch; the primary checkout stays untouched (slice worktree and PR); CI and release workflow edits follow the bigcherry-slice-workflow skill; document any new lab command in tools/lab/radiance/README.md.

## Acceptance Criteria

1. A PR that changes only markdown or docs/** does not start the radiance build, and ci-pass is green. 2. A lab branch build after a single-kernel edit reuses the CI cache and finishes in under 10 minutes (target; record the measured number), with the hit rate reported. 3. Each engine release carries a runtime bundle asset with SHA-256 that matches the lane build in the release record, and the lab can start the stock pin from it without compiling. 4. The recompile set for a single-kernel edit shrinks measurably, with the before and after unit lists recorded. 5. No behaviour change: component tests and the existing KLD or hash checks are unchanged.
