# Bound HIP compilation parallelism in CI

## Baseline

GitHub Radiance build 41801034883 (2026-11-04): the build-image step took **45m 53s** despite a restored 2.0 GiB ccache. Compiler calls: 610 hits, 118 misses (83.79% hits). The cache occupied 2.0 / 5.0 GiB, so a larger cache is not the immediate answer.

Run 41811030819: same step took **44s** with 728 / 728 cache hits. The avoidable long tail is **uncached HIP compilation**, not image download or upstream cloning.

## Trial

A bare `cmake --build ... -j` masks `CMAKE_BUILD_PARALLEL_LEVEL` for Ninja (verified with an executable trace of a local Ninja build). The campaign builder now omits that flag when CMake's standard limit is set; otherwise the existing default is preserved.

Normal Radiance CI keeps its existing Ninja default, while manual dispatch can trial `CMAKE_BUILD_PARALLEL_LEVEL=2` or `6`. Every run reports per-HIP-object elapsed time from Ninja logs. Manually dispatch **2** and **6** compilation jobs with **cold=true**, same branch and source commit, to measure comparable cold builds without ccache. No GPU runtime work is required.

## Acceptance

- Both cold trials compile and pass component tests.
- Compare the Build-in-image step duration, resource behaviour, and top slow HIP commands at the **same source SHA**.
- Introduce the two-job cap as a follow-up only if it materially reduces wall time without sacrificing compile coverage or stability; the default stays unchanged until then.
- Record the measured pair here before considering BU02 complete.

The trial does not change optimisations, target architectures, release binaries, or the tests run.
