# Reuse verified Radiance engine and component build layers in CI

## What changes

Radiance PR CI can restore a verified, **prebuilt engine** and six separately
versioned component build trees from a previous successful **main** build:
`libr3`, `libr2`, `moe-remote`, `ngram-helper`, `bc-gfx12` and `serving`.
Layer keys fingerprint the pinned engine, patch set, toolchain, build logic,
and exact component inputs (including shared headers). Documentation is not a
compile input. These are build outputs, **not** the existing ROCm Docker image
or release runtime bundle.

On a complete hit, the production build worker still checks its
source-slice/build-plan identity, toolchain and binary/runtime SHA-256 metadata.
On a partial hit, cache restore removes the build metadata and **forces the
real CMake build**; an edited or unavailable component cannot silently reuse a
previous component's plugin. All component tests run in either case. A corrupt
or misattributed archive fails closed. The cache remains optional: missing
layers simply compile normally.

Only a successful push to `main` **after component tests** writes immutable
build layers. PRs can restore but never seed the shared cache. The existing
compiler cache remains a fallback when a component changes or a layer misses.
Images/paths are stable at `/src` inside the build container.

## Evidence and limits

- Unit tests exercise production export/restore, all-layer and partial reuse,
  corrupt archives, wrong fingerprints, and archive traversal rejection.
- GitHub PR CI must verify the first cache-miss build; its merge to main then
  seeds layers. A subsequent matching PR must confirm actual cache-hit,
  component-test success and measured wall time before claiming a speedup.
- The previous 2-job/6-job ccache-disabled experiment (77m38s/73m28s) is **not**
  a performance result for these layers. It measures the cold compile path.
- New upstream pin, SDK, engine build configuration or component dependencies
  legitimately cause cache misses. First builds still compile; no GPU work is
  required in CI, and acceptance benchmarks remain in the lab.
- Cache upload/download size, GitHub's storage limits and eviction need
  measurement from real Actions runs. If layers prove too large, replace the
  archive transport without weakening validation.
