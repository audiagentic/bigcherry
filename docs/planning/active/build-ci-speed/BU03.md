# CI speed watch: radiance build on kernel changes, ccache misses, and run-time trend

## Description

Watch CI run times and find build improvements. Measured 2026-11-25 over the last 31 radiance-build runs: mean 25 min, 10 runs over 30 min, max 49 min, min under a minute (docs-only). The 14 min runs have a 96% ccache hit rate (905 of 938 calls); the slow runs are exactly the PRs that change libr3 kernel source (each IQR/K-parallel/head change took 37 to 49 min), because the large libr3 HIP units for gfx1100 miss the cache and recompile. Offline suites are short: core about 2.7 min, patch about 3.2 min, pr-ci gating 25 s typical.

## Steps

1. A recorder (watch.sh, kept outside the repository) appends every finished workflow run's duration, event and conclusion to a table; extend the check-in to read it and report trend, not point values. 2. Kernel-change PRs: use the family compile targets (RCS20) and the discrete unit harness (RCS25) to prove a kernel change at PR level on the changed unit only, and build the full plugin on main and at release (the release build already runs after merge). 3. ccache: check why the large libr3 units are the late misses (restored cache starts full; the build already runs unbounded and trims after); measure the hit rate on a rebase-only PR against a kernel PR. 4. Concurrency: the build is a single docker step; check CMake parallelism against the runner's cores and the HIP unit order (longest units first). 5. Do not run the radiance build twice for one PR (PR check and push-on-main both build the same tree): confirm whether the main push build can reuse the PR's result.

## Notes

Created from the owner's request to monitor build improvements. Data: ci-watch table.

2026-11-25 finding (unit harness work): a real cold lane build of main with ccache disabled gives, for five IQR plane-prefill forms, 240 VGPR with 2 to 3 spills, while the shipped 2020.11.4 and 2020.12.0 libr3 carries 236 with none for the same forms; every other one of the 7,802 kernel records equals the release. Same compiler build, flags and cuid, so the shipped objects most likely came from a ccache entry made from an earlier source state (the CI restore key or the release job's cache). Measured effect: none (replay of the plane route, 80 points: 79 same, 1 within noise, hashes unchanged). Decision: no guard; the cold-build records become the baseline and the unit harness compares against a cold build. Follow-up for this item: the release job should build the bundle without trusting a restored object whose inputs it did not hash (or record the ccache hit rate per unit in the release metadata), so a release is reproducible from its source; check how the restore key and the content-hashed compiler check admit an object made from earlier text.
