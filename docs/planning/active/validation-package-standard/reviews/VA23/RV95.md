# eligible_for_validated_state fails open: campaign reports validated-eligible for a record verify_validated_patch() rejects

## Notes



## Findings

Found during RD73's clean re-qualification (real dual-gfx1100 run, contract hash de6e54ff, 10 paired rounds, campaign identity adecd397cacf).

The contract gate PASSED on real hardware: end_to_end_gain_pct +1.717% (ci95_low +1.385%), max_control_regression_pct 0.0%, correctness bit_identical PASS, resource graph_cache_entries PASS, trigger proof PASS.

The campaign then printed:

    [patch-campaign] validation verdict: eligible (0 blocking reasons)
    [patch-campaign] STATE='validated' eligible: yes

and wrote a record with eligible_for_validated_state=True, final_eligibility=True, validation_disposition='validated', blockers=[].

But setting state="validated" and running patch-verify-evidence REJECTS that same record, under both the default and --no-legacy-grandfather:

    status: missing-or-stale
    no current qualifying HI83 validation record
    missing architecture(s): gfx1100
    adecd397cacf: activation is not executed+activation-verified; correctness did not pass

Root cause, confirmed in the record itself: the contract path proves correctness and activation, but never writes them into the structured generic fields verify_validated_patch() reads.

    check_results._contract_correctness_gate.passed = true
    record['activation']   = {'status': 'unknown', 'disposition': 'unknown'}
    record['correctness']  = {'disposition': 'unknown'}

TWO DISTINCT DEFECTS:

(1) FAIL-OPEN INCONSISTENCY (the serious one). eligible_for_validated_state and verify_validated_patch() disagree about the same record, and the flag is the OPTIMISTIC side. A fail-closed system must never have its convenience flag report eligible where its authoritative verifier reports missing-or-stale. Anyone trusting the campaign's own printed verdict would promote a patch the verifier rejects.

(2) STALE DOCUMENTATION, IN THE WRONG DIRECTION. validation_campaign.py:3287, patches/1233.../README.md, and docs/reference/patches/PATCH_VALIDATION.md all state that eligible_for_validated_state 'cannot become True' from --run-rd73-contract alone. That is now false: it DOES become True. The docs describe a fail-closed gap; the actual behaviour is a fail-open one. The documentation is not merely out of date, it describes the safer of the two behaviours.

NOT A SCIENCE PROBLEM. RD73's contract result is real and auditable; all 10 recorded artifacts verify byte-for-byte against their sha256s. The patch was left at state='untested' (the attempted promotion was reverted) and holds ported-benched-evidence cleanly with problems: []. What blocks promotion is adapter plumbing, not evidence.

## Conclusion

Fix (1) first and treat it as a correctness bug in the validation framework, not an enhancement: either make eligible_for_validated_state consult the same predicate as verify_validated_patch(), or stop emitting a 'STATE=validated eligible' verdict from a path that cannot populate the fields the verifier requires. The two must not be able to disagree, and where they do, the verifier wins.

Then complete the VA23 rebinding so --run-rd73-contract writes its proven activation and correctness results into the structured activation/correctness dispositions instead of leaving them 'unknown'. That single change converts a proven +1.717% end-to-end win into a promotable one.

Update the three stale doc sites once behaviour is fixed, so they describe the real (fixed) behaviour rather than the historical fail-closed claim.
