# Execution attestation: no measurement is evidence unless the observed environment matches its resolved identity

## Description

A benchmark that silently falls back to CPU still prints a well-formed results table labelled backend "ROCm", with plausible numbers and TIGHTER variance than the real GPU run. Observed on real hardware 2026-09-05, same binary/model/command, differing only in device-selection env:

    failed to initialize ROCm: no ROCm-capable device is detected
    | qwen35 9B Q6_K | ROCm | pp512 |   43.70 +/- 0.06 |
    | qwen35 9B Q6_K | ROCm | tg128 |   10.46 +/- 0.00 |

    found 1 ROCm devices ... gfx1201, VRAM 32624 MiB
    | qwen35 9B Q6_K | ROCm | pp512 | 3160.50 +/- 31.80 |
    | qwen35 9B Q6_K | ROCm | tg128 |   69.57 +/- 0.07  |

72x and 6.7x wrong. The only signal was one stderr line above the table.

WHY THIS IS DANGEROUS HERE. Promotion runs a paired A/B with a block bootstrap and a pre-registered confidence rule. If ONE ARM silently falls back to CPU we get an enormous, perfectly plausible effect with tight CIs. The outlier policy is frozen as 'keep every valid pair, never trim, never use a statistical test to discard' -- so such an arm would be KEPT unless caught as a VALIDITY FAILURE. The frozen doctrine already names this category ('required telemetry is missing or corrupt'), defined independently of expected benefit. It is upstream of statistics, not a statistical problem.

THIS HAS ALREADY COST US TWICE. (1) _require_real_gpu_execution()'s own comment records RD08's false subject_hit=false on 2026-09-01, when gfx1030's HIP runtime failed to detect the device and a trigger check quietly ran CPU-only. (2) VA22 records the gfx1201 double-env-selector bug -- ROCR_VISIBLE_DEVICES filters the device list and HIP_VISIBLE_DEVICES then indexes INTO the filtered set, so setting both selects nothing. That exact bug recurred on 2026-09-05 despite being documented, which is the argument for enforcement in code rather than docs.

COVERAGE GAP, the reason this is P0. A guard exists but does not cover the path that produced our only promoted result:

    _run_one_trace_probe              guarded
    llama-bench runners (RD08/RD04)   guarded
    run_rd73_mtp_server_lane          NOT guarded
    run_rd73_decode_control_lane      NOT guarded
    run_rd73_resource_burst_session   NOT guarded

RD73's lanes drive llama-server rather than llama-bench and never inherited the guard. RD73 is promoted and SHIPPED on 6 sessions, none carrying GPU-execution attestation. The archived server logs contain no ggml_cuda_init line, so it cannot be verified retroactively. Magnitude rules out CPU fallback (a 27B Q8_0 at ~50 tps cannot be CPU), so the result is almost certainly sound -- but it is formally unattested.

## Detailed Solution & Technical Design

Design from adversarial review (dev-gpt-agent, req_7bd183755a0643e7).

INVARIANT: no measurement is valid unless the environment actually OBSERVED BY THAT MEASURED PROCESS positively matches its immutable resolved MeasurementIdentity. Missing or unknown attestation is invalid, not neutral. The results table's 'ROCm' label is never proof of execution backend.

MINIMUM ATTESTATION -- identity (must match) vs telemetry (record only):

    actual backend used (not requested)            IDENTITY
    accelerator device count                       IDENTITY
    per-device gfx architecture                    IDENTITY
    stable device locator (UUID, else PCI BDF)     IDENTITY, frozen per session
    VRAM                                           telemetry
    ROCm/driver versions                           telemetry unless contract-pinned
    device marketing name / serial                 telemetry

Positive proof: backend=ROCm, device_count=N, devices=[{arch, id}]. Catches CPU fallback, wrong arch, wrong cardinality, AND swapping between two same-arch cards (we have 2x gfx1100).

Attestation MUST come from the measured process's own backend-init path. rocminfo, env vars, build targets and the table label prove intent or capability, never actual execution.

ENFORCEMENT -- all three layers, ONE canonical comparator:

    compare_execution_identity(expected, observed) -> PASS | reason_codes

    1. runner          after EVERY measured subprocess, before accepting
                       parsed metrics. Not a single preflight -- one preflight
                       cannot prove later processes.
    2. evidence writer authoritative choke point; cannot persist valid=true
                       without attestation bound to the measurement identity hash.
    3. promotion gate  defence in depth.

FAILURE SEMANTICS: record AND abort, classified ERROR (identity/harness malfunction), never scientific FAIL. Persist the invalid attempt with its attestation, abort the lane, accept zero subsequent measurements from it. A rerun gets a new attempt identity. If discovered after the fact, those measurements are invalid EVIDENCE excluded by validity rules -- not trimmed as outliers.

ARCHITECTURE AUTHORITY -- resolves the four existing declarations without a fifth axis:

    patch.toml validation-architectures  = RELEASE/SHIP coverage requirement
    contract scope.architectures         = SCIENTIFIC scope of one measurement
    platform targets                     = capability inventory
    campaign --amdgpu-targets            = execution selector only

    contract scope + campaign selection + platform resolution
        -> immutable resolved MeasurementIdentity
        -> runtime attestation must equal it

    CLI target not in contract scope        -> configuration ERROR
    contract target unavailable on platform -> BLOCKED
    observed arch != resolved lane arch     -> validity ERROR
    missing required patch architecture     -> not promotable

Do NOT derive patch.toml coverage from a single contract; that erases its separate release-coverage meaning.

    valid_measurement = correctness_valid
                        AND attestation == PASS
                        AND attestation.measurement_identity_hash matches

## Validation

Required tests:

    parseable CPU-fallback table          -> ERROR
    ROCm present but wrong gfx arch       -> ERROR
    wrong device count                    -> ERROR
    same arch, different UUID/BDF         -> ERROR
    correct backend/count/arch/device     -> PASS
    missing attestation                   -> ERROR
    VRAM or driver version differs        -> PASS (telemetry)
    CLI arch outside contract scope       -> configuration ERROR

Plus a golden-thread test proving the guard cannot be bypassed by adding a new
lane: every measured-subprocess path reaches the same comparator.

Explicitly OUT of scope: do not change bootstrap, CI, outlier or
effect-estimation code. This is an evidence-validity gate upstream of statistics.

## Effort & Risk

Medium. The comparator and reason codes are small and pure. The real risk is COVERAGE: the existing guard was correct and still missed the lanes that mattered, so this is only done when EVERY measured-subprocess path reaches one comparator, proven by test rather than inspection.

Second risk: RD73's server lanes may not currently capture the backend-init line at all. If so, log capture must be fixed first.
