# Wire patch-validation-campaign as a real ValidationPlan/Experiment-Contract executor

## Description

GPT round 4 code-grounded review (req_82dc1c3dcc744fb2) found the principal remaining blocker: the real validation executor is NOT actually wired to satisfy the ValidationPlan checks it claims to require. Today patch-validation-campaign creates ValidationContext with trace_evidence={}, no performance_evidence, and package_root=None -- but RD08's real adapter requires trace-marker and autotune-campaign validators that explicitly need bound trace/performance artifacts, and custom validators need package_root. Additionally, bind_contract() currently collapses any number of required correctness checks into ONE generic correctness capability (RD04 requires both backend_reference and ppl_equality, but one arbitrary correctness producer can currently satisfy static build_validation_plan() -- existing EC07 already correctly requires every named check independently, and final qualification must use that named-check gate, not a generic capability PASS). The same collapse problem exists for performance/controls: the generic autotune-campaign validator only checks a bound artifact has campaign_id and passed=true -- it does NOT evaluate the Experiment Contract's actual workload/scope/thresholds. Existing Experiment Contract code already owns proper effect aggregation/control-regression semantics; reuse that authority instead of letting a generic PASS constitute scientific validation.
