# Document the RD-patch validation methodology and folder standard

## Description

Write the canonical per-patch validation package standard (README.md + validation.toml + optional validation/ + evidence/validation.json in the current canonical evidence schema -- do not hardcode 'schema v2': VA07 established this will likely become schema v3, and the doc must name it generically enough to survive that), building on RD08's existing pattern as the real precedent rather than inventing a new one. Document the 8 real tracked-status values (planned, ported-untested, ported-benched, ported-validated, deferred-hardware, superseded, excluded, evidence-only) and exactly what evidence each one requires before patch-status may claim it. Clarify the storage rule: validation authority stays co-located under patches/<id>/ (not docs/evidence/, which is reserved for cross-cutting incident narratives like HI141/HTR01). MUST document the distinction between tracked-status (a historical lifecycle level, not revision-bound) and evidence-verifier qualification (whether that level is CURRENTLY qualified for the active pin, by resolved commit SHA) -- these are two different questions and patch-lint/patch-verify-evidence must not conflate them. MUST document the one-time structural-grandfather migration mechanism: existing nonconforming packages get a single baseline exemption bound to (patch implementation digest + patch.toml digest + policy/version identifier + normalized tracked-status set); ANY change to any of these invalidates the exemption. No hardcoded per-patch exceptions. MUST state plainly that this exemption protects lint SHAPE only and never authorizes starting a NEW validation run (see VA02's execution-side guard). MUST document multi-contract patches (e.g. 1203_rd050607, binding three distinct RD05/RD06/RD07 hypotheses) as UNSUPPORTED/fail-closed until VA09 lands.
