# Document the RD-patch validation methodology and folder standard

## Description

Write the canonical per-patch validation package standard (README.md + validation.toml + optional validation/ + evidence/validation.json schema v2), building on RD08's existing pattern as the real precedent rather than inventing a new one. Document the 8 real tracked-status values (planned, ported-untested, ported-benched, ported-validated, deferred-hardware, superseded, excluded, evidence-only) and exactly what evidence each one requires before patch-status may claim it. Clarify the storage rule: validation authority stays co-located under patches/<id>/ (not docs/evidence/, which is reserved for cross-cutting incident narratives like HI141/HTR01). MUST also document the distinction (GPT review round 2, req_ca5dcb978aac467d) between tracked-status (a historical lifecycle level, not revision-bound -- e.g. 'ported-benched' can be true forever even if stale) and evidence-verifier qualification (whether that level is CURRENTLY qualified for the active pin) -- these are two different questions and patch-lint/patch-verify-evidence must not conflate them. MUST document the one-time structural-grandfather migration mechanism: existing nonconforming packages get a single baseline exemption bound to (patch implementation digest + tracked status); ANY change to either invalidates the exemption. No hardcoded per-patch exceptions (e.g. no special-casing RD04/RD58/RD73 by name).
