# Qualify and selectively promote RDNA CM1 winners

## Description

Qualify PR #27952's CM1 candidate on real RDNA3, RDNA3.5, and RDNA4 Vulkan stacks, then promote only exact device/driver/signature winners into replay; keep default enablement off unless evidence supports it.

## Steps

1. Record native and CM1 signatures on gfx1100, gfx115x, and gfx120x; test RADV and proprietary AMD stacks separately.
2. Run correctness across all supported quant types for MUL_MAT and MUL_MAT_ID, including tails, split-K, batched shapes, and expert routing.
3. Measure forced candidates using repository statistical/effect-evidence policy, with warm-up excluded and full recipe timing.
4. Tune by exact signature/device/driver rather than architecture-wide aggregate.
5. Seed RDNA4 upstream exclusions as negative controls: q4_1, q5_1, q4_k, q5_k, nvfp4 for MUL_MAT, and nvfp4 for MUL_MAT_ID.
6. Promote only replay-safe winners with complete identity; demonstrate stale driver/device/shader/candidate misses fall back to native.
7. Reassess upstream merge/pin status and retire redundant downstream implementation when the pin contains an equivalent upstream change.

Use the existing workflow/evidence/promotion machinery after RE30 becomes backend-aware: Vulkan stock -> record -> candidate -> tune -> correctness -> promote -> replay -> replay diagnostics. Do not claim the existing HIP-oriented tune campaign is reusable unchanged. Capture source/build manifests, shader audit, correctness, route telemetry, measurements, promotion, and replay diagnostics under one RO22 run.

## Detailed Solution & Technical Design

Treat the PR's RDNA3/3.5 gains and RDNA4 mixed results as hypotheses, not policy. RDNA3 is the first target, RDNA3.5 is a separate hardware class despite shared upstream labels, and RDNA4 must be tuned independently because operator regressions can coexist with MoE end-to-end gains. Compare per recorded signature first; use operator aggregates and llama-bench PP/TG only as secondary evidence. Do not promote a global RDNA3/RDNA4 winner.

Promotion key is exact physical device + Vulkan driver identity/version + shader/SPIR-V digest + BigCherry/vendor build identity + dispatch signature + candidate recipe. Test gfx1100 first, then gfx115x, then gfx120x; keep RADV and proprietary stacks separate. RDNA4 upstream exclusions are negative controls, not universal policy. Operator timing and end-to-end MoE results may diverge, so per-signature evidence precedes aggregate PP/TG.

RO22 is a qualification campaign and promotion decision, not a fourth source patch. Its subject/control builds must follow the validation-domain roles, while tune/replay/stock remain campaign roles. The CM1 Experiment Contract is the scientific authority; the patch adapter only wires execution. If both 1246 and 1247 are needed in the subject composition, keep their patch identities separate and do not pretend this is a multi-contract validation of one descriptor.
