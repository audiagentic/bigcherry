# Split validation_campaign.py monolith: per-patch producer code lives under patches/<id>/

## Description

`tools/bigcherry/patch/validation_campaign.py` has grown to 8,357 lines with 28 patch-specific `run_rdXX_*`/`run_patch*` functions bolted on (RD04, RD08, RD12, RD58, RD73, RD1000/PA35, and counting), each carrying its own bespoke correctness/perf/CLI-wiring logic mixed into one shared file. Flagged directly by the user (2026-09-13): "we should split into per patch - code and scripts for patches should be stored under the patch folder - we need to standardize folder names for these and any other patch specific code/config/artifacts/etc - we should not be creating monoliths."

Every new patch's validation work currently extends this single file rather than plugging into a shared, generic campaign engine via config/contracts. This is the same anti-pattern the project's own `bigcherry-patch-author` skill warns against at the patch-definition level ("Do not create a new production `patches/<id>.py` flat module") -- but validation_campaign.py itself has become exactly that kind of flat, ever-growing module at the tooling layer.

Do not refactor this incidentally while doing unrelated work (per patching-patch-system's own convention) -- track as its own effort.

## Detailed Solution & Technical Design

GPT design (req_0fb717b910e145b2, 2026-09-13), verified structurally sound against real source names this session. End-state principle: validation_campaign.py knows how to EXECUTE a selected validation producer but never knows WHICH patch/RD it is executing -- patch identity, producer entrypoint, policy, inputs, and allowed artifacts are all owned by patches/<id>/validation/; reusable build/run/evidence machinery stays shared.

1. STANDARD PATCH-LOCAL LAYOUT (validation/ is the only home for patch-specific executable validation material):
patches/<id>/validation/
  producer.toml   -- declarative producer dispatch/policy/artifact allowlist (separate from validation.toml, which defines validation OBLIGATIONS/checks, a different schema)
  producer.py     -- thin implementation of the generic producer protocol, orchestration only
  correctness.py, benchmark.py, state_restore.py, etc. -- substantial patch-specific logic split by concern only when warranted
  scripts/run_real.py -- human/lab driver, must invoke the SAME generic producer path as normal tooling (not a second implementation)
  config/, fixtures/ -- created only when actually needed; fixtures/ holds immutable golden data, never generated evidence
Do not create empty directories. No __init__.py (numeric dir names make package imports undesirable; keep path-based spec_from_file_location loading, RD43's existing pattern is the precedent).

2. GENERIC PRODUCER DISPATCH replaces all dedicated flags:
--patch <id> --validation-producer <producer-name> --producer-input KEY=VALUE (repeatable, patch-specific inputs like RD73's corpus become --producer-input corpus=... instead of a dedicated --rd73-corpus flag)
producer.toml schema (example shape, exact policy values must be transcribed from each patch's REAL current gating code, never assumed):
  [producer.correctness]
  entrypoint = "producer.py"
  callable = "run_correctness"
  trace_probe = "skip"|"run"
  standard_campaign = "skip"|"run"
  correctness_evidence_cli = "forbid"|"allow"
  performance_benchmark_cli = "forbid"|"allow"
  artifacts = ["correctness.json"]
One generic validate_producer_cli_compatibility() replaces every repeated exclusion tuple currently hand-copied per flag.

Shared protocol module: tools/bigcherry/patch/validation_producer.py -- ProducerSpec (patch_id, producer_id, entrypoint, callable_name, policy enums, artifact_names, declared inputs), ProducerContext (repo_root, patch_dir, workdir, campaign_id, base_revision, hip_path, fat_targets: FatTargetPlan, model, corpus, build_env, inputs, validation_build_identities), ProducerResult (correctness, named_correctness_results, validation_build_identities, activation_evidence, performance_evidence, trace_evidence, check_results, lane_effects, emitted_artifacts). Protocol: `class ValidationProducer(Protocol): def __call__(self, ctx: ProducerContext) -> ProducerResult`.
Constraints: never pass argparse.Namespace into patch code (decouples patch modules from CLI structure); no generic record_kwargs escape hatch (would recreate the monolith through untyped fields); reconcile ProducerResult's exact fields against the CURRENT make_record() call before freezing the protocol -- don't silently drop an existing evidence field; reuse BigCherry's existing build-identity type if one is already public rather than inventing a parallel BuildIdentityMap alias.

Loader: resolve_producer(*, patch_dir, producer_id) -> (ProducerSpec, ValidationProducer) reads patch_dir/validation/producer.toml, validates entrypoint stays inside patch_dir/validation/ (reject absolute paths, ../ traversal), spec_from_file_location, resolves the callable. No central `{"rd12": load_rd12, ...}` map -- that would just be a different registry monolith. Reject: unknown producer, missing callable, duplicate/invalid artifact names, unknown policy enum, undeclared/missing-required producer-input.

run() end-state shape: resolve_selected_producer -> validate_producer_cli_compatibility -> conditionally run_generic_trace_probe/run_standard_campaign per policy -> call the resolved producer -> validate_producer_result -> make_record() using result.validation_build_identities. No `if args.run_rd12_contract: elif args.run_rd73_contract: ...` chain.

3. FAT-BUILD RULE MADE STRUCTURAL (not producer-author discipline): shared FatTargetPlan(targets, cmake_value) + build_validation_pair_once(...) -> ValidationBuildPair + run_validation_pair_per_device(builds, devices, ...) -- a producer can physically only write `for device in devices: run_only(builds, env={HIP_VISIBLE_DEVICES: device.index})`, never `for device in devices: build_tree(...)`. Mandatory hardware-free regression test: N devices => exactly 1 control build + 1 subject build, both with the identical fat ";"-joined target string, build count does not scale with N, run count does scale with N, each run has the expected HIP_VISIBLE_DEVICES. This directly targets the exact bug class that recurred twice this session (RD04's fat-build fix, commits cacc0b98/b65071d1) for different patches.

4. ARTIFACT ALLOWLIST: no import-time registration (avoids global mutable state / import-order dependence / test-order dependence). Static declarative producer.toml artifact_names instead: `_CORE_ARTIFACT_NAMES` (truly generic only) | `producer_artifact_names` passed into `_artifact_refs()`/`make_record(..., producer_artifact_names=selected_spec.artifact_names)`. Validate names: basename only, no absolute path, no `/`/`\`, no `..`, no glob, non-empty, unique. Require `result.emitted_artifacts <= spec.artifact_names`. As each patch migrates, remove its filenames from evidence.py's central `_artifact_refs()` enumeration in the SAME commit.

5. MIGRATION ORDER (GPT's reasoning, may be revised if a real callgraph shows otherwise): foundation (validation_producer.py + shared primitives) -> RD12 (best pilot: single top-level producer, already tests the hard case of a producer owning its own separate control/subject builds and returning validation_build_identities) -> RD58 (small, proves the mechanism isn't contract-specific, producer ID "state-restore") -> RD73 (more complex multi-function/typed-input case, e.g. --rd73-corpus becomes --producer-input corpus=...) -> RD08 -> RD04 (two producer IDs under one patch: "contract-correctness" and "benchmark") -> RD1203/RD05-06-07 (migrate together since they share one backend producer -- do not triplicate backend_correctness.py) -> RD1000 (last, audit-closing/evidence path needs careful inventory first) -> final sweep removing the remaining `_load_rdXX_correctness_module()`-class hardcoded loaders (RD08/RD17/RD13/RD43/RD19/RD26).
Final grep acceptance: validation_campaign.py contains no `run_rdXX_*`, `run_patchXXXX_*`, `_load_rdXX_*`, `--run-rdXX-*`, patch-specific artifact names, or patch-ID-specific execution branches.

6. ATOMIC MIGRATION RULE per patch, no compatibility layer (matches this project's CLAUDE.md "no legacy, no backward compatibility" rule explicitly): (1) capture current hardware-free test baseline, (2) add patch-local producer.py+producer.toml, (3) add/update generic dispatcher tests, (4) convert tests/callers to --validation-producer, (5) move the real-hardware driver script if one exists, (6) delete the old producer function(s), (7) delete the old argparse flag(s), (8) delete every old skip/exclusion/ambiguity condition, (9) delete the migrated central artifact names, (10) run the full relevant hardware-free suite, (11) grep shared modules for the migrated RD/patch ID -- zero execution-plumbing hits required, (12) commit that ONE patch's migration atomically. Explicitly do NOT add: old-flag aliases, deprecated argparse options, re-export wrappers, old-function forwarding wrappers, tools/lab symlinks, or dual old/new evidence paths.

7. REQUIRED GENERIC TESTS (minimum set, hardware-free): producer manifest parses/fails closed; unknown producer rejected; unknown/missing-required producer-input rejected; entrypoint traversal rejected; generic loader invokes exactly the selected producer; no two producers permitted simultaneously; every former CLI conflict now driven from ProducerSpec; ProducerResult validation identities are exactly {control, subject}; generic campaign identities remain exactly {tune, replay, stock}; the two identity domains cannot be substituted for each other; undeclared emitted artifact rejected; unlisted workdir file excluded from evidence; a producer's declared artifact IS accepted; fat-target build occurs once per control/subject regardless of device count; the run loop sets HIP_VISIBLE_DEVICES per device; a producer exception fails the campaign rather than yielding partial evidence; the result payload reaches make_record() with no patch-specific branch. Consider a structural test that scans validation_campaign.py for forbidden patch-specific producer conventions, to prevent the monolith regrowing.

If any of these currently live inside validation_campaign.py, extract to an appropriately named shared runtime module when actually needed for the dependency direction below -- don't churn files just to satisfy the layout. Required dependency direction: validation_campaign -> validation_producer/shared validation runtime/evidence; patches/<id>/validation/producer.py -> validation_producer types/shared validation runtime/shared activation+evidence helpers. NEVER: a patch producer importing validation_campaign.py.
