# Split validation_campaign.py monolith: per-patch producer code lives under patches/<id>/

## Description

`tools/bigcherry/patch/validation_campaign.py` has grown to 8,357 lines with 28 patch-specific `run_rdXX_*`/`run_patch*` functions bolted on (RD04, RD08, RD12, RD58, RD73, RD1000/PA35, and counting), each carrying its own bespoke correctness/perf/CLI-wiring logic mixed into one shared file. Flagged directly by the user (2026-09-13): "we should split into per patch - code and scripts for patches should be stored under the patch folder - we need to standardize folder names for these and any other patch specific code/config/artifacts/etc - we should not be creating monoliths."

Every new patch's validation work currently extends this single file rather than plugging into a shared, generic campaign engine via config/contracts. This is the same anti-pattern the project's own `bigcherry-patch-author` skill warns against at the patch-definition level ("Do not create a new production `patches/<id>.py` flat module") -- but validation_campaign.py itself has become exactly that kind of flat, ever-growing module at the tooling layer.

Do not refactor this incidentally while doing unrelated work (per patching-patch-system's own convention) -- track as its own effort.

## Steps

1. Design a standard folder/file naming convention for patch-specific validation code, scripts, config, and artifacts under patches/<id>/ (e.g. patches/<id>/validation/producer.py, patches/<id>/validation/README.md) -- extending the existing validation/ subfolder convention already used by some patches (e.g. RD08's validation/rd08_correctness.py) to be the mandatory, universal shape.
2. Define the shared/generic engine surface each per-patch producer plugs into (contract loading, build_tree(), run_paired_lane(), evidence make_record()/write_record()) so validation_campaign.py becomes a thin dispatcher + shared primitives library, not a growing pile of per-patch functions.
3. Migrate existing per-patch functions (RD04, RD08, RD12, RD58, RD73, RD1000, and RD05/06/07's shared 1203 function) out of validation_campaign.py into their own patches/<id>/validation/ modules, preserving all existing tests and behavior -- verify via the existing hardware-free test suite before/after each migration.
4. Update the ad-hoc tools/lab/<label>-correctness/run_real.py driver scripts to match the new per-patch code location convention, or fold their logic into the same per-patch validation module.
5. Document the new convention in docs/reference/patches/PATCH_AUTHORING.md and PATCH_VALIDATION.md so future patches follow it from the start rather than adding another function to the shared file.
