# Finish validation-producer architecture and migrate patch-specific code out of validation_campaign.py

## Description

`validation_campaign.py` is still a ~427 KB patch-specific monolith. PA36 foundation commit `41f80820` has landed `tools/bigcherry/patch/validation_producer.py` with `ProducerSpec`, `ProducerContext`, `ProducerResult`, `ValidationProducer`, `FatTargetPlan`, manifest loading, input validation, CLI compatibility policy, artifact allowlisting, and result validation. No real patch producer has migrated yet.

The old plan overstated foundation completion: the module does not yet provide the shared control/subject build-pair executor, per-device run helper, generic dispatch into evidence, producer artifact wiring, or a fully plural-contract validation runtime. Those are the next slice before moving patch code.

## Benefit target

This is the highest-return complexity reduction in the patch-system refactor. The current campaign CLI has at least nine patch/RD-specific execution modes (`rd08-lanes`, `rd08-contract`, `rd04-benchmark`, `rd58`, `rd73`, `rd12`, `rd04-contract`, `rd13`, `rd26`) plus dedicated producer inputs and matching execution/evidence branches.

The end-state targets are structural and testable:

- zero `--run-rd*`, patch-ID-specific, or contract-ID-specific execution modes in shared campaign/validation CLI code;
- zero `run_rd*`, `run_patch*`, `_load_rd*`, patch-ID dispatch branches, or patch-specific artifact names in shared execution modules;
- adding a normal patch-local producer requires zero edits to shared dispatcher/CLI/evidence code;
- one generic control/subject build-pair path and one generic per-device execution path;
- one typed producer/check result path into the existing evidence writer;
- zero shared-runtime dependence on the singular `ValidationPlan.contract` compatibility accessor.

Do not set an arbitrary final LOC limit for `validation_campaign.py`; removing patch knowledge and repeated change points is the benefit target. Generic orchestration may remain substantial if it has one owner and one extension path.

## End-state rule

`validation_campaign.py` may know how to execute a selected producer, but never which RD/patch it is. Patch identity, producer entrypoint, declared inputs/policy/artifacts, and patch-specific orchestration live under `patches/<id>/validation/`. Patch-local producer modules may import shared validation/build/evidence helpers, but must never import `validation_campaign.py`.

Standard layout when needed:

`patches/<id>/validation/producer.toml`
`patches/<id>/validation/producer.py`
`patches/<id>/validation/scripts/run_real.py`

Additional modules/fixtures only when real complexity requires them; do not create empty scaffolding.

## Remaining foundation slice

This foundation slice is the schedulable dependency checkpoint **PA36-F** ("generic runtime foundation complete"). PA33, PA37, and PA39 depend on PA36-F, not on completion of all PA36 migrations. The atomic migration sequence below runs after PA36-F and may interleave with other items per its recommended order.

1. Extract or expose a shared build/run runtime below `validation_campaign.py` for materialize/build pair once, `FatTargetPlan`, per-device execution, completed-build evidence, and common correctness/performance helpers. Keep generic implementation in the existing appropriate campaign/validation owner rather than moving it into patch packages.
2. Make plural contracts first-class before the first real producer migration:
   - replace shared-runtime `ValidationPlan.contract` use with `plan.contracts`/explicit check scope;
   - evolve `ValidationContext` to expose the complete immutable contract set plus contract-hash mapping and helpers that resolve the contracts applicable to a `CheckSpec`;
   - single-contract validators may explicitly require exactly one scoped contract, but shared orchestration must never silently collapse a plural plan;
   - because no real patch producer has migrated to the new API yet, replace/strengthen opaque `ProducerResult.named_correctness_results: Mapping[str, object]` before adoption with typed per-check result records carrying check ID, contract scope, existing `ValidationResult`/disposition data, and bound artifacts rather than adding a 1203-specific aggregate shape.
3. Add a generic producer execution function that: resolves manifest -> validates inputs/CLI policy -> constructs typed context -> executes -> validates typed results -> passes them to the existing validation/evidence authorities.
4. Extend evidence artifact collection to accept only the selected producer's declarative artifact allowlist in addition to core artifacts.
5. Add CLI presentation for `--validation-producer` and repeatable `--producer-input` through the existing campaign entrypoint, with no RD-specific flags in the new path.
6. Add structural tests that fail if new `run_rdXX_*`, `run_patchXXXX_*`, `_load_rdXX_*`, `--run-rdXX-*`, shared `ValidationPlan.contract` access, or consumer-specific producer-result decoding is added to shared execution code.
7. Add a synthetic producer fixture proving that a new producer can be declared, selected, executed, validated, and evidence-bound without modifying shared implementation code.

## Atomic migration sequence

Each producer migration is its own commit and deletes its old flag/branch/function/artifact names in that same commit; no aliases or wrappers.

Recommended current order:

1. RD12 (1205) pilot.
2. RD04 (1202).
3. RD13 (1206) and RD26 (1210), whose dedicated flags landed after PA36 was first written.
4. RD58 (1234).
5. RD73 (1233), including typed corpus input.
6. RD08 (1204).
7. RD05/RD06/RD07 (atomic patch 1203) are implemented and registered by PA37 (sole owner) against the PA36-F generic plural-contract runtime. PA36 performs no 1203 producer work; it merely counts that migration toward its structural end-state (zero shared patch-specific branches). This remains the proof case for the already-generic plural-contract runtime, not the place to introduce a 1203 exception; one shared producer implementation, not three builds.
8. Patch 1000 verification producer from PA35.
9. Remaining hard-coded loaders/branches discovered by structural scan (including RD17/RD43/RD19 and any later additions).

Re-evaluate order if a real call graph shows a smaller safe pilot, but never batch unrelated patch migrations.

## Migration checklist

Capture baseline; add patch-local manifest/producer; convert tests/callers; move any lab driver to `validation/scripts/`; delete old producer function, flag, exclusion guards, loader, and central artifact names; run focused/full hardware-free tests; structurally scan shared modules for the migrated ID; then perform real-hardware equivalence where the producer previously had accepted hardware evidence.

## Validation

Generic tests: manifest/path traversal/policy/input failure; exact `{control,subject}` validation identities; artifact allowlist; producer exception fails closed; build count fixed at one control+one subject regardless of device count; run count scales with devices and uses the intended `HIP_VISIBLE_DEVICES`; no ROCR double-filter; typed per-check results reach the existing evidence writer; single- and multi-contract plans retain explicit contract scope; a plural plan cannot pass through a singular compatibility accessor; synthetic producer requires zero shared implementation change; no patch-specific branch.

Per migration: prove semantic equivalence to the prior accepted producer output, including contract gate and build identities, before deleting the old path in the same commit.

## Acceptance Criteria

All patch-specific producers execute from patch-local manifests through one generic dispatcher; shared campaign/validation code contains no patch/RD-specific execution flags/functions/loaders/artifact names; adding a normal producer requires no shared implementation edit; build-once fat-multiarch is structural; artifact ownership is declarative; producer/check results are typed; shared execution is natively plural-contract and never reads `ValidationPlan.contract`; generic shared helpers have one owner; and real producer migrations preserve accepted evidence semantics without compatibility layers.
