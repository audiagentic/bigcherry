# Unified patch validation gate orchestration (gates.py + patch-gates CLI)

## Description

User-directed design review (2026-09-11): "Do we have a patch workflow that we can use to ensure we have covered all that's needed... standard gates and then gates that they need based on the type of patch they are". Motivated by a real incident the same session: three patches (1225, 0840, 1224, and historically 1200/1001) were promoted to state="validated" with real hardware evidence, correct README/SUMMARY.md/patch.toml sync, and (for 3) explicit GPT solution-approval -- by every check documented in docs/reference/testing/PATCH_VALIDATION.md, that should have been sufficient. But attempting to actually build 1200 (RD19) and 1001 via `bigcherry build --experiment <name>` failed at `patch_admission.admit()` with "no current qualifying HI83 validation record; missing architecture(s): ..." -- a real, separate, stricter gate the documented promotion workflow never surfaced, discovered only by hitting it directly.

GPT design verdict (dev-gpt-agent, session ses_6f4dfb6b87034bbb, req_d00af5d188984a3b), asked to confirm/design after independently reading the real code: **no unified workflow exists today.** Individual gates are each independently correct (check_validation_packages, require_execution_package, patch_admission.admit/HI83 evidence, check_performance_evidence, disposition), but there is no single policy evaluator answering "is this patch ready for THIS operation" -- applicability and sequencing are fragmented across ~7 separate modules/checks with no orchestration layer connecting them. This is exactly what let 1200/1001 pass every check that was actually run while still failing a real one nobody ran until build time.

## Acceptance Criteria

gates.py exists and composes (does not reimplement) validation_policy.check_validation_packages/require_execution_package, evidence.py's HI83 record verification, patch_admission.admit, check_performance_evidence, and disposition lookups behind one evaluate_patch_gates(descriptor, intent, context) entrypoint. `bigcherry patch-gates <id> --intent {validate,promote,build,rebase}` exists and returns per-gate PASS/FAIL/BLOCKED/NA with --json support. patch-lint consumes the same gate registry rather than a separate parallel check list. docs/reference/testing/PATCH_VALIDATION.md reorganized around the G0-G7 sequence with a gate matrix near the top; no second canonical doc created. Running --intent build against 1225/0840/1224/1200/1001/1002/1232 surfaces their real current G4/G7 status (expected: several will show BLOCKED/FAIL given tonight's 1200/1001 discovery, which is the point -- this closes that visibility gap).

## Notes

GPT's full proposed gate taxonomy (verbatim, do not re-derive):

G0 Identity/registry (every patch): valid package/schema, ID/order/kind/origin/backend/tags, safe paths, dependency/conflict graph.
G1 Documentation/lifecycle (every patch): SUMMARY.md synced with patch.toml, lifecycle metadata internally consistent.
G2 Apply/revision (every patch targeting a source revision): anchors/apply valid on target pin, idempotent/already-applied behavior, rebase status known.
G3 Validation definition (before any validation execution): README + validation.toml, resolvable ValidationPlan, required contract(s) except an explicit profile exemption -- wraps require_execution_package().
G4 Evidence qualification (promotion/build requiring qualification): structured evidence exists and matches exact pin, patch subject digest, validation identity, declared architectures/contracts, required checks passed -- HI83 is authoritative here.
G5 Lifecycle promotion (untested->validated): G0-G4 pass AND evidence says eligible_for_validated_state=true, metadata sync/review complete.
G6 Disposition (rebase/build/release): current revision+digest known_broken disposition handled correctly, never used to excuse a recipe-selected patch.
G7 Production admission (actual production build/composition): run the existing post-composition patch_admission gate over the COMPLETE resolved patch set, not merely the focal patch.

Applicability must compose as: standard gates + operation/lifecycle gates + kind gates + tag gates + origin/scope gates. The operation should be explicit: author, validate, promote, build, rebase.

Kind-specific additions:
- framework: preserve the existing narrow local-framework exemption (packaged+local+non-external+non-RD+no contract); any RD/contract/external/runtime-scientific framework patch loses the exemption and follows normal scientific qualification.
- diagnostic: must prove it builds/runs and its declared check mechanism works; a diagnostic PASS must never imply production correctness/performance.
- upstream-backport: require upstream provenance/source identity, current-pin rebase/apply proof, external-source metadata coherence, qualification of the LOCALLY adapted result (not trusting upstream's own numbers) -- directly closes tonight's patch-1000 gap (its perf claim rested entirely on the upstream PR's own numbers).
- enhancement: for validated, require a bound Experiment Contract; activation + correctness appropriate to the claimed effect; performance obligations come from contract/tag -- closes the exact hole that let 1200/1001 (non-RD validated enhancements) escape check_validation_packages() coverage.

Tag policy: do NOT invent bespoke gates per subsystem tag (allreduce/mmq/mtp/etc stay classification-only). `optimization` is the deliberate exception and should be STRENGTHENED beyond tonight's README-marker-substring check (which GPT notes "explicitly admits it cannot verify the comparison is real") into a structured requirement: native llama.cpp -> BigCherry baseline -> BigCherry+patch, with identities/workload/repetitions/statistics/contract threshold recorded in EVIDENCE, with README becoming the human-readable summary rather than the proof itself. `tuning` is the only other tag worth policy-bearing status later (selector/dispatch activation + fallback correctness) -- do not silently add semantics to it in this item.

Concrete implementation GPT recommends:
- New tools/bigcherry/patch/gates.py orchestration layer -- does NOT move/reimplement existing checks, only sequences/composes them. GateResult(id, status=PASS|FAIL|BLOCKED|NA, phase, authority, detail); evaluate_patch_gates(descriptor, intent, context).
- New CLI: `bigcherry patch-gates <patch-id> --intent {validate|promote|build|rebase}` (+ --source for build/rebase), with --json.
- patch-lint should consume the SAME gate registry for every repository-resolvable/static gate (not stay a separate parallel implementation).
- Transition safety: run --intent promote specifically whenever patch.toml's state field changes to "validated" (e.g. as a pre-commit-style check for that specific diff), rather than making ordinary lint fail every already-validated patch the instant a pin bump makes its hardware evidence stale -- that's a deliberately different, narrower trigger than blanket lint enforcement.
- Do NOT create a second canonical doc: reorganize docs/reference/testing/PATCH_VALIDATION.md around this gate sequence, add a compact "gate matrix" near the top; PATCH_AUTHORING.md points to it, doesn't duplicate it.

GPT's own summary of the payoff: "one machine-readable applicability engine used by docs, lint, promotion review, and build admission... would have made the 1200/1001 situation visible at promote time rather than first appearing during bigcherry build."

Direct consequence for tonight's already-promoted patches (1225, 0840, 1224, 1200, 1001, 1002, 1232): none of these have a real G4 (HI83 evidence-record) check confirmed passing -- only G0/G1/G5-adjacent (state+README+SUMMARY sync) were verified. A --intent build (G7) run against each, once this exists, is the real remaining verification step for all of them, not just 1200/1001 (which are merely the two that happened to get hit first).
