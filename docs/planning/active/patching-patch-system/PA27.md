# Mechanically split 0100 into serving dispatch/replay and campaign tune/record build plumbing

## Description

First implementation step of PA20. Split `patches/0100_cmake_options` by runtime ownership while preserving the current aggregate behavior and patch ordering.

The previous plan's "autotune/SQLite half" is stale. Current 0100 explicitly has no SQLite link edit and says record mode writes JSONL with offline stdlib SQLite processing. `GGML_HIP_AUTOTUNE_SQLITE` still appears as an option declaration in 0100, so this item must first determine whether it has any live consumer; if not, remove that dead option instead of creating a new patch around it.

## Steps

1. Inventory every 0100 edit and every live reference to each introduced CMake option/compile definition. Classify each symbol as serving dispatch/replay, campaign tune/record/diagnostic, shared validation, or dead.
2. Prove whether `GGML_HIP_AUTOTUNE_SQLITE` has a live consumer. Delete it if declaration-only; do not preserve a compatibility option without a consumer.
3. Keep the serving half responsible only for what a replay/serving build needs: dispatch/replay enablement, generated registry inclusion, production source list, and validation that makes invalid replay builds fail closed.
4. Move tune/record-only options, tuner source inclusion, workload/record routing, and campaign-only diagnostics to a separately selectable package. Shared definitions must have one owner; avoid two patches editing the same semantic block in incompatible ways.
5. Preserve the old aggregate behavior by composing both halves in the transitional framework set. Add exact apply/idempotence and composition tests before changing any source recipe.
6. Build at least: stock/no-dispatch, replay serving, record, and tune. Use the normal generate/build path; dispatch-enabled builds require generated `hip-autotune-registry.inc`.
7. Verify a serving build has no tuner/record-only symbols or dependencies while still resolving and replaying winners.

## Files

`patches/0100_cmake_options/**`; one new packaged patch allocated through the normal patch-authoring rules; `config/recipes.toml` only for transitional aggregate composition; focused patch/apply/build tests.

## Validation

Patch apply and idempotence on the pinned base; aggregate tree equivalence for all behavior intentionally preserved; source/symbol inspection of replay vs tune builds; generated-input identity; focused CMake negative tests for mutually exclusive/invalid option combinations.

## Acceptance Criteria

Two independently selectable packages exist; composing them reproduces the current intended 0100 behavior; serving replay builds contain no tune/record-only code; dead SQLite compatibility is either proven live and correctly owned or removed; no source taxonomy is cut over until PA26 passes.

## Notes

Do not add aliases, forwarding patches, or an opt-out switch that leaves the monolith intact. Git history is the compatibility record.
