# Make the production patches cheaper to carry across pin bumps

## Description

Goal: fewer and smaller breakages when the llama.cpp pin moves, without changing what any patch does.

Evidence (b11402 -> b11474 bump, 2026-10-08, 72 upstream commits): the production set is 48 patches with 326 anchored edits. 13 patches edit ggml/src/ggml-cuda/ggml-cuda.cu, 7 edit mmvq.cu, 6 edit ggml-backend-meta.cpp, 5 edit src/models/qwen4exp.cpp. 8 production patches broke. Every one broke because upstream changed the exact lines it anchors on; none broke because it was a separate package (being separate is why the eight fixes took 18 minutes). 3 of the 8 broke because upstream had absorbed the same change (1343 = upstream 1a3011cc0, 1335 = #29901, 1336 = #29943). The worst anchors were long function-body anchors: 1346 had one of about 100 lines, and 1326 broke only because upstream moved a loop body into a function and re-indented it. 15 production patches require another production patch, and a few (1334, 1294, 1332) apply only in composition because they anchor on text an earlier patch inserts. One failure was invisible to every offline check: 1347 called ggml_cuda_should_use_mmvf with the old argument list (upstream added warp_size in 9d3aba6b5); composition and tests were green and the first hardware build failed.

Conclusion: what breaks at a bump is the number of exact-text anchors into upstream's hot files. Merging packages does not reduce that number, so it is the weakest lever; moving our code out of upstream files and anchoring on stable text are the strong ones.

## Steps

Five workstreams, in this order. Each step changes packaging only - mechanism and output stay the same.

A. Compile step in the bump (small, do first).
  1. Add a compile-only build of the production set to the pin-bump procedure, after the composition check and before any hardware run: every translation unit a production patch touches must compile for the HIP targets (gfx1100, gfx1201, gfx1030). No link or model needed.
  2. Wire it into `bigcherry pin-bump` as its own phase with a failure envelope naming the file, line and patch that owns the line; document it in docs/reference/build/PIN_BUMP.md and the bump-llamacpp skill.
  3. Brutus: install pytest for the Python the lab uses (three patch tests cannot be imported there today).

B. Our code in our own files, one-line hooks in upstream's (largest payoff).
  1. Pattern: a patch that adds a kernel or helper creates it in a BigCherry-owned file (FilePatch(create=True), e.g. ggml/src/ggml-cuda/bc-<topic>.cu/.cuh, picked up by the existing ggml-cuda glob) and leaves in the upstream file only the include and the call. The only thing a bump can then break is the hook.
  2. Apply first to the three newest kernel patches as the reference implementation: 1344_dsv4_hc_grid_index (two kernels pasted into dsv4-hc.cu + two launch edits), 1345_moe_ids_multiwarp (kernel + launcher pasted into mmid.cu + switch edit), 1347_f32_thin_transposed_mmvf (helper kernel + dispatch block in ggml-cuda.cu).
  3. Then the patches with the most edits in hot files: 1281_moe_mul_mat_id_range (30 edits), 0200_dispatch_hook (30), 1340_meta_per_device_arena (20), 1341_meta_subset_mirrored (16), and the remaining patches in ggml-cuda.cu and mmvq.cu.
  4. Where a kernel needs file-local upstream helpers (static functions, templates), say so per patch: either the hook passes what is needed or the helper stays in the upstream file with a signature anchor.

C. Anchor on stable text.
  1. Rule for PATCH_AUTHORING.md: anchor on a function signature, a case label or a unique one-line statement; never on a multi-line body when a signature is available; max_span_lines above about 6 needs a written reason.
  2. Audit the 326 edits: list every anchor longer than 6 lines or inside a function body that a signature would serve, by patch; fix as each patch is touched for B.
  3. Add a patch-lint warning for anchors over the limit without the reason.

D. Upstream the generic patches.
  1. Candidates: 1344 (division-free hyper-connection kernels), 1345 (multi-warp mm_ids helper), 1347 (thin F32 matmul through mul_mat_vec_f), 1294 (deterministic and ordered top-k), 1292 (k-pool tail truncate), 1340/1341 (per-device compute arena and subset-mirrored inputs for -sm tensor).
  2. Per candidate: check upstream master for an equivalent, prepare the change against master with the measurements we have, record it in config/external-sources.toml so `bigcherry sources check` reports when it merges. Opening PRs is the owner's decision - prepare, do not submit.

E. Merge only the families that are one mechanism.
  1. Q8_1 activation chain into one package: 1235_rd09_q81_activation_cache_foundation (registry), 1307_q81_activation_cache_mmvq (consumer), 1309_rms_norm_mul_q81, 1310_act_q81, 1311_hc_pre_q81, 1312_mul_q81 (producers). Same data structure, same files, same rules. Every existing flag stays as its own off switch.
  2. 1339_meta_memory_report into 1340_meta_per_device_arena (1340 is written on top of 1339's hooks). 1341 stays separate (different mechanism, different files).
  3. Not merged: 1281 + 1283 (a new op and the policy that uses it; no shared anchors, small gain - revisit after B), 1294 + 1295 (a general top-k kernel change and a Qwen4Exp attention path; the link is functional, not textual).
  4. Net effect on the production set: 48 -> about 42 packages.

## Detailed Solution & Technical Design

Equivalence proof for every refactored or merged patch (packaging change only): materialise the production source tree before and after from the same pinned base and compare. For B the trees differ by construction (code moves between files), so the proof is (1) the moved kernel/helper text is byte-identical apart from its location, checked by the patch test, (2) the build compiles, (3) on hardware: greedy text identical to the pre-refactor build with GGML_CUDA_DISABLE_FUSION=1 on both, probes TV 0.0000, and one ABBA at 24K showing no speed change. For E (merges) the before/after production trees must be byte-identical (same edits, one package): compare source-tree hashes; no hardware run needed beyond the next routine build.

A merged package carries the union of the merged patches' evidence in its README (the old READMEs are kept verbatim as sections) and one state. Owner rule (CLAUDE.local.md): a default or wiring change does not invalidate a patch's proof; the same applies to a packaging change that leaves the mechanism and output unchanged - no demotion, no re-validation campaign, only the checks above.

Retired patch ids are not reused. Experiments in config/recipes.toml that name a merged patch are updated in the same change. No compatibility aliases for old package names.

## Validation

A: a deliberately wrong argument list in a production patch is caught by the compile phase before any hardware run. B: per patch, the moved-text test, a clean build, identical greedy text with fusion off, probes TV 0.0000, ABBA neutral. C: lint reports zero unexplained long anchors in the production set. D: each candidate has an entry in external-sources.toml and a prepared change against upstream master. E: before/after production source-tree hashes identical. Overall measure at the next pin bump: number of production patches that need a manual fix, against 8 of 48 at b11474.

## Effort & Risk

A: S, low risk. B: L - 3 patches as the pattern, then about 15 more; medium risk per patch (kernels that use file-local upstream helpers; CMake pickup of new files; each needs a build and an identity run). C: M, low risk, mostly done while doing B. D: M of preparation, no project risk; outcome depends on upstream. E: M, low risk when the tree hashes match. Main risk overall: changing 20 validated patches at once - mitigate by doing one patch per commit with its own identity check and never batching refactors with behaviour changes.

## Standards

No legacy or back-compat shims: a moved kernel leaves no copy behind, a merged patch leaves no alias. Packaging changes do not invalidate proofs. One mechanism per patch remains the rule; merging is only for packages that are one mechanism. Bug fixes and improvements go inside the patch they belong to.
