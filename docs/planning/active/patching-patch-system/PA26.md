# Prove serving replay equivalence after the PA27 mechanical split

## Description

Evidence gate between PA27 and PA28. PA27 is allowed to mechanically split 0100 while preserving the aggregate composition; PA26 then proves that the candidate `serving-core` composition produces the same replay decisions and outputs as the current framework for a fixed promoted-winner database.

This is not a source-inspection proof and not a prerequisite to creating the split. It is the behavioral gate that decides which 0100 functionality is truly serving-critical.

## Steps

1. Select a known-real promoted winners/replay database and record hashes for winners, model, generated registry, source ref, BigCherry revision, build profile, GPU identity, and relevant environment.
2. Build the current aggregate arm and the PA27 serving-core candidate from the same resolved source/ref and generated inputs.
3. Replay every winner dimension exercised by 0300/0400/0500/0600/0650 and compare resolved signature, chosen candidate/configuration, dispatch outcome, and output/correctness artifact.
4. Include negative fixtures that intentionally remove or alter one serving dependency and prove the equivalence test detects the divergence.
5. If a real dimension diverges, reclassify the responsible functionality into serving-core before PA28. Do not waive the difference because throughput is similar.

(req_a4974e46d4d643e0) before commit, all four blocking findings applied:

- `tools/bigcherry/campaign/replay_equivalence_hardware.py`: materializes
  and builds BOTH arms through the REAL production pipeline
  (`campaign.lane.execute_campaign_lane`, never reimplemented) behind an
  injectable `lane_executor` (defaults to the real function; tests inject a
  fake returning hand-built real `CampaignLaneResult`/`BuildPlan`/
  `ArtifactRef` objects -- the real execute_campaign_lane is never invoked
  by any test, since that would require a real HIP compile).
- Build-identity fairness (GPT finding): compares a `BuildPlan` PROJECTION
  EXCLUDING `source_slice_id` (which legitimately differs -- composition is
  the variable under test) plus `CampaignLaneResult.effective_build_id`
  equality (the actual resolved configure/toolchain identity, not just the
  requested plan). `source_slice_id`/`build_plan_id` themselves are
  deliberately NOT required to match.
- Diagnostic-observability fix (GPT finding, blocking): the PRODUCTION pair
  (exact control vs exact serving-core candidate) is intentionally
  diagnostics-free on both arms and cannot emit a per-dispatch hit log. Added
  a separate DIAGNOSTIC companion pair -- candidate = serving-core +
  0810_replay_hit_diagnostics re-added as an ephemeral PA26-only probe
  (`replay_equivalence.build_serving_core_diagnostic_config`), explicitly
  bound back to the production candidate's composition via
  `require_diagnostic_matches_production` (diagnostic == production + 0810,
  nothing else) before any diagnostic result is trusted.
- Runtime comparison (GPT finding, blocking -- coverage gap): arm-level
  fields (process success, clean shutdown, output digest, correctness,
  model/GPU/runtime-args identity) separated from per-dispatch fields
  (dispatch, signature, winner, config_binding digest, transform_id,
  match_kind, call_count, outcome). Compares BOTH exactly, AND requires each
  arm's observed dispatch set exactly equal the frozen corpus's expected set
  -- closes the gap where two EMPTY per-dispatch result sets could otherwise
  read as spuriously equivalent.
- Failure-handling boundary (GPT finding, blocking): introduced
  `RuntimeNotEvaluated`, a specific exception distinct from
  `NotImplementedError`. The default `real_hardware_runtime_runner` stub
  raises it; `build_hardware_receipt` catches ONLY this exception to emit a
  `NOT_EVALUATED` receipt. Any other exception (a parser bug, an SSH/process
  error after execution starts, a malformed log, a real runner defect)
  propagates as a genuine failure -- never silently downgraded to
  "not evaluated".
- 47 tests in `tools/tests/campaign/test_replay_equivalence_hardware.py`
  (plus the unchanged 14 offline tests), all offline; full
  `tools/tests/campaign` suite: 730 tests, same 2 pre-existing unrelated
  failures as every prior PA26 commit (contract-registry count, migration
