# PA20 step 2: prove replay-winner equivalence before any patch reclassification

## Description

Prove replay-winner equivalence for the proposed PA20 core-serving composition, after a mechanical PA27 extraction has produced the candidate split. PA26 is an equivalence gate, not a prerequisite to creating the mechanical split.

## Steps

1. Use a known-real promoted winners.jsonl/replay database and record its hashes and source/build identity.
2. Compare current full-framework composition with the mechanically extracted core-serving candidate from PA27.
3. Replay every winner dimension across 0300, 0400, 0500, 0600 and 0650; compare dispatch decisions, resolved configuration and outputs.
4. If any dimension diverges, keep the responsible patch in core-serving or amend PA27/PA20 classification with evidence.
5. Publish a reproducible equivalence receipt and only then expose new taxonomy in PA28.

## Detailed Solution & Technical Design

The cycle is intentionally removed: PA27 first performs a mechanical extraction while preserving the existing aggregate composition; PA26 then proves replay-winner equivalence against that candidate. Use BuildPlan/effective identity and existing replay/campaign primitives; do not rely on source inspection alone.
