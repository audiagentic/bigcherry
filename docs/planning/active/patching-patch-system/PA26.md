# Prove serving replay equivalence after the PA27 mechanical split

## Description

Evidence gate between PA27 and PA28. PA27 is allowed to mechanically split 0100 while preserving the aggregate composition; PA26 then proves that the candidate `serving-core` composition produces the same replay decisions and outputs as the current framework for a fixed promoted-winner database.

This is not a source-inspection proof and not a prerequisite to creating the split. It is the behavioral gate that decides which 0100 functionality is truly serving-critical.

## Steps

1. Select a known-real promoted winners/replay database and record hashes for winners, model, generated registry, source ref, BigCherry revision, build profile, GPU identity, and relevant environment.
2. Build the current aggregate arm and the PA27 serving-core candidate from the same resolved source/ref and generated inputs.
3. Replay every winner dimension exercised by 0300/0400/0500/0600/0650 and compare resolved signature, chosen candidate/configuration, dispatch outcome, and output/correctness artifact.
4. Include negative fixtures that intentionally remove or alter one serving dependency and prove the equivalence test detects the divergence.
5. If a real dimension diverges, reclassify the responsible functionality into serving-core before PA28. Do not waive the difference because throughput is similar.

## 2026-09-14: offline oracle implemented (design reviewed by GPT)

Brutus was busy serving production when this work started, so the offline
(no-GPU) half of PA26 was implemented first, per GPT design guidance
(dev-gpt-agent session ses_c2892cdae7f14feb, req_accf444d1eaa4537):

- `tools/bigcherry/campaign/replay_equivalence.py`: resolves control
  (`bigcherry-native` = framework + upstream-fixes, via the normal
  `campaign.resolution` path) and an EPHEMERAL PA26 serving-core candidate
  (framework minus the 8-module PA20 serving boundary: 0110, 0700, 0800,
  0810, 0820, 0830, 0900, 1100) -- constructed in-memory only, never written
  to `config/recipes.toml` (PA28 owns any real public serving-core
  taxonomy). Fails closed if `config/recipes.toml`'s `framework` set drifts
  from the hardcoded expected-removed list.
- Asserts the exact ordered composition delta AND shared-module content-hash
  equality between arms (catches a same-ID-different-hash divergence, not
  just membership).
- Binds a fixed v5 winners corpus via `tuning.replay.read_cache(...,
  enforce_schema=True)` only -- GPT flagged that the historical
  `dispatch-27b-v5.cache` reference artifact is schema-1 and must be
  re-exported under current gates before use here, never read via the
  `enforce_schema=False` historical-inspection escape hatch.
- Emits a receipt (`build_offline_receipt`) with `runtime.status =
  "NOT_EVALUATED"` -- this proves composition + corpus identity only, NOT
  behavioral replay equivalence.
- 12 tests in `tools/tests/campaign/test_replay_equivalence.py`, including
  the negative fixtures GPT called out as most important: dropping a real
  serving module (0650) from the candidate must fail the oracle; an
  unexpected extra module must fail; an empty/wrong-version cache must fail.
  All pass; ran full `tools/tests/campaign` suite (695 tests) -- only 2
  pre-existing unrelated failures (contract-registry count, migration lint),
  confirmed unrelated via `git status` (only the 2 new PA26 files untracked).

GPT's scope correction (important): PA26 is NOT "does 0100 vs 0100+0110
change 0300-0650's presence" (they're identical in both arms by
construction) -- it is "is removing 0110 + the other 7 campaign/qualification
modules behaviorally inert for production replay." Any hardware divergence
found later reclassifies that module into serving-core before PA28, per the
plan item's own acceptance criteria.

**Still required to close PA26** (explicitly NOT done): the real two-arm
