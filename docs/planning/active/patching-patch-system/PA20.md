# Refactor framework composition into serving, campaign, and qualification patch surfaces

## Description

Architecture parent for splitting the current monolithic `[patch-set.framework]` without changing patch-system policy or inventing compatibility aliases. Review against current main corrected two stale premises in the older plan: current `0100_cmake_options` no longer links SQLite (it explicitly states "No SQLite anywhere"), and patches 0800/1100 cannot simply be excluded because they have real campaign/qualification ownership.

The purpose is patch-surface isolation, rebase attribution, and independently testable compositions. It is not a fix for a demonstrated serving-runtime overhead regression; current build profiles already compile dispatch/tuner machinery out when disabled.

## Benefit target

The benefit is reduced production patch surface and clearer ownership, not fewer recipe objects. At current main, `[patch-set.framework]` contains 14 patches; `source.bigcherry` therefore carries 15 modules with the one current upstream-fix and empty validated-enhancement set. The proposed serving surface contains seven framework responsibilities, so the same current snapshot would resolve to eight release modules: 15 -> 8, about a 47% reduction in production patch modules.

Treat those counts as a measured baseline, not a frozen acceptance number. If patch inventory changes before implementation, recompute the before/after count. The durable targets are:

- release/control compositions contain zero `campaign-support` or `qualification-support` modules;
- a campaign/qualification-only patch change cannot alter the serving source identity;
- serving rebase/apply failures are attributable only to serving-core plus independent policy sets;
- no patch from the old framework becomes ownerless merely to improve the count.

A small increase in explicit recipe objects is acceptable because each object has one semantic responsibility.

## Target architecture

- `serving-core`: the PA27 dispatch/replay half of 0100, 0200, 0300, 0400, 0500, 0600, 0650.
- `campaign-support`: the PA27 tune/record build plumbing plus 0700, 0800, 0810, 0820, 0900. 0800 belongs here because graceful `/shutdown` exists specifically to flush automation/tuning state.
- `qualification-support`: 0830 and 1100. Both are evidence/telemetry surfaces, not serving requirements.
- `upstream-fixes` and `validated-enhancements` remain independent policy sets; do not merge them into framework taxonomy.

Keep `source.bigcherry` as the canonical release source, but change its framework dependency to `serving-core` after migration. Replace the ambiguous control source `bigcherry-native` with an explicit serving baseline (provisional name `bigcherry-serving-base`) that is `serving-core + upstream-fixes` and has no validated enhancements. Add `bigcherry-tuning` and `bigcherry-qualification` for their named purposes. Experiments remain overlays through `campaign.resolution`; do not bake experiment patches into these sources.

## Ordered implementation

1. PA27 mechanically split 0100 and prove both halves compose back to the current aggregate behavior.
2. PA26 prove replay/winner behavior of the serving-core candidate against the current framework composition.
3. PA28 add the new patch-sets/sources alongside the old names; no live consumer moves yet.
4. PA34 must land before migration-dependent gate/rebase work so exact source/experiment/focal-overlay identity is authoritative.
5. PA29 atomically migrate live consumers. Production `source.bigcherry` stays production; `bigcherry-native` control consumers move to the explicit serving baseline; tuning/qualification consumers move to their semantic sources.
6. PA30 run semantic/evidence/performance equivalence gates against the migrated compositions.
7. PA31 delete `[patch-set.framework]` and `source.bigcherry-native`; no alias/shim.

PA33 is related but not on the taxonomy critical path until validation execution is used for PA30. PA36 owns validation-producer decoupling and must not be conflated with this source/patch-set split.

## Files

`config/recipes.toml`; `patches/0100_cmake_options/**`; campaign/source resolution consumers; tests that assert patch-set/source identity; current docs that describe framework/native compositions.

## Validation

For every transitional and final source, record ordered patch IDs, module hashes, `patch_set_id`, resolved source ref, build profile, and generated-input identity. Prove that no patch from the old framework is orphaned: every old member is either assigned to one new set or explicitly retired by a separately justified change. Record before/after module counts at the migration revision, but judge success by semantic ownership and source isolation rather than an exact historical count.

## Acceptance Criteria

Complete only when PA27, PA26, PA28, PA29, PA30, and PA31 are complete; `source.bigcherry` is the serving release composition; the serving baseline contains no campaign/qualification patch surface; tuning and qualification surfaces are independently selectable; all fourteen former framework patches (or the then-current inventory) have an explicit disposition; campaign/qualification-only changes do not perturb serving selector identity; and no compatibility alias preserves the old framework/native names.

## Notes

This review supersedes the older "core-serving/tuning-scaffolding/qualification-observability" classification where it omitted 0800/1100 and repeatedly treated SQLite as a current linked dependency. Git history preserves that design provenance; it is no longer implementation guidance.

Do not expand this refactor into automatic recipe derivation from patch metadata or split otherwise-cohesive 0200/0300/etc packages merely for symmetry. Those changes add abstraction without improving the measured production surface goal.
