# Replace patch-validate evidence alias with the canonical validation execution facade

## Description

Current `cmd_patch_validate()` is only an alias to `cmd_patch_verify_evidence()` and explicitly says hardware campaigns remain separate. Build one execution facade that resolves an exact selector, requires the existing validation package/Experiment Contract, invokes the PA36 generic patch-local producer path, and writes the existing durable validation evidence. Keep `patch-verify-evidence` as the read-only verifier.

This item is not a new gate evaluator, benchmark engine, scheduler, lifecycle/promotion engine, or generic resume framework.

## Benefit target

`patch-validate` should become presentation only. Its implementation may parse generic selector/producer inputs, construct the request, invoke PA34/PA36 authorities, and render/write the existing result; it must not acquire patch-specific orchestration.

Measurable targets:

- adding a normal patch-local producer requires zero edits to `tools/bigcherry/cli/patch.py` or CLI parser code;
- the command exposes zero `--run-rd*`, patch-ID-specific, or contract-ID-specific arguments;
- selector identity is serialized only by PA34's canonical identity type, not rebuilt by this command;
- producer/check/evidence interpretation remains in PA36/current validation authorities, so the facade contains zero switches on patch ID, RD ID, producer name, or check capability;
- `patch-verify-evidence` remains read-only and no second durable evidence schema is introduced.

## Dependencies

- PA34 selector identity must land first so validation receipts bind source/experiment/focal-overlay composition and matching G2 identity.
- PA36 must land the generic producer execution seam (manifest -> context -> build/run -> typed producer/check result -> evidence) before this CLI presents it. PA33 does not need every historical producer migrated before implementation, but it must not add new RD-specific branches to `validation_campaign.py`.
- `CatalogSnapshot` already exists in current base and should be reused; do not introduce a second registry scan/identity type.

## Steps

1. Replace the alias semantics with a real `patch-validate` handler using PA34's canonical selector resolver and exact `SelectorIdentity` object.
2. Resolve one immutable catalog snapshot, focal descriptor, validation plan via `validation_policy.require_execution_package()`, bound contracts, platform/device identity, model/fixture inputs, and PA36 `validation/producer.toml` producer selection before doing expensive work.
3. Fail fast if selector, pin, package, producer inputs, required architecture/device, model/corpus, generated registry, or build prerequisites are wrong.
4. Execute through PA36 shared primitives. Dispatch-enabled builds use the normal generate/build pipeline; never call a bare build path that can silently compile the feature inert.
5. Reuse existing correctness/performance/activation validators and performance-matrix/paired benchmark machinery. The facade consumes PA36's typed producer result and does not interpret patch-specific fields.
6. Bind the canonical selector identity object, control/subject build identities, device mapping, model/corpus hashes, commands/env, artifacts, check results, and contract gates into the existing `patches/<id>/evidence/validation.json` schema.
7. Emit only a compact generated run-summary projection for human consumption; do not create a competing durable evidence schema.
8. If durable run-directory/status primitives already exist in campaign runtime, reuse them. If a minimal execution receipt is missing, add it under that owner; never use `pgrep` liveness heuristics or build a second resume state machine in this command.
9. Migrate 2-3 real validations to the facade and reproduce their existing evidence semantics before calling PA33 complete.
10. Add a synthetic test producer and prove registering/executing it requires no CLI implementation change; this is the regression test for the extension boundary.

## CLI contract

The final CLI should express the same selector and producer vocabulary as the underlying system, e.g. focal patch + `--source`, optional PA34 `--experiment`/`--focal-overlay`, `--validation-producer`, and repeatable `--producer-input key=value`. Model/platform convenience arguments may resolve config values, but they must not become a second validation-plan language.

## Files

`tools/bigcherry/cli/main.py`; `tools/bigcherry/cli/patch.py`; PA36 shared execution modules; existing campaign build/run/fixture owners; docs/reference/testing/PATCH_VALIDATION.md; focused CLI/execution tests.

## Validation

Hardware-free: selector/package/producer fail-fast, one catalog snapshot, input validation, generated-build prerequisite, artifact allowlist, typed result threading, no lifecycle mutation, no duplicate report schema, no consumer-owned selector serialization, and synthetic-producer registration with zero CLI code changes. Hardware: 2-3 representative migrated producers reproduce accepted correctness/performance evidence and hashes/identity fields on real devices.

## Acceptance Criteria

`patch-validate` executes declared validation through PA34+PA36 authorities; `patch-verify-evidence` remains read-only; the CLI has no patch/RD-specific execution argument or dispatch branch; a new normal producer requires no CLI implementation edit; selector serialization has one owner; no second gate/benchmark/evidence framework is added; receipts are self-describing and selector/build/device/fixture bound; and real pilot validations reproduce established evidence semantics.
