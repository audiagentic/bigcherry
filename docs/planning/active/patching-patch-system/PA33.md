## Description

A thin CLI orchestrator (tools/bigcherry/patch/, not tools/lab/) that resolves composition -> materializes -> builds control/subject -> invokes a declared correctness-producer adapter -> invokes the existing generic performance executor (PVPS02's run_performance_benchmark/performance-matrix.json) -> binds artifacts into the existing evidence machinery (patches/<id>/evidence/validation.json) -> emits a compact run-summary.json/md. Consolidates infrastructure BigCherry already has (validation_campaign.py, PVPS02, config/recipes.toml platforms, validation.toml/Experiment Contracts, patch-verify-evidence) instead of adding a parallel layer.

## Notes

Filed 2026-09-12 after a session of repeated manual, ad-hoc per-patch validation (hand-written materialize/build scripts, hand-typed llama-bench/perplexity invocations, hand-computed paired-A/B statistics, freehand README writeups) surfaced the same mechanical steps re-derived from scratch for nearly every patch, plus recurring low-level mistakes (a pgrep-self-matching-via-ssh-command-line bug hit twice, re-deriving AMDGPU_TARGETS and the wikitext2 corpus path each time).

GPT's design (req_6cd6ba90c95f4a8e), concrete and prioritized:

Target CLI: `bigcherry patch-validate --patch <id> [--patch <id> ...] --model-tier <tier> --platform <platform> --mode correctness|performance|both --validation-tier <tier>`. --experiment <name> as an explicit composition override; patch ID normally auto-resolves its [experiment.*] recipes.toml entry. --mode is an execution filter only, not a new definition of correctness.

Do NOT encode patch-specific test logic in the orchestrator. Add a small oracle-adapter registry for the recurring real shapes: backend_ops, ppl_equality, completion_diff, trace_marker, custom_contract. validation.toml/the Experiment Contract selects the adapter + params; the orchestrator only executes it.

Stop hand-writing paired A/B loops -- PVPS02 already solved that (generic paired/rotated run_performance_benchmark, --run-performance-benchmark, performance-matrix.json). The missing piece is orchestration/adaptation, not another benchmark framework.

Stop hand-deriving build targets -- config/recipes.toml's [platform.linux-multi] already declares gfx1100/gfx1201/gfx1030/RCCL/tests/tools/server.

Flow: validation.toml -> adapter registry -> existing validation_campaign primitives (materialize/build, performance-matrix, correctness producers, activation) -> existing evidence/verdict machinery. Do NOT fold GPT solution-approval into this tool -- measurement terminates in deterministic evidence; disposition/review consumes that evidence separately, as a distinct step.

Do NOT invent a second full report schema -- patches/<id>/evidence/validation.json remains the durable record. Add only a compact generated run-summary.json projection (schema below) plus a mechanically-rendered run-summary.md (paste-ready README/plan evidence block; do not auto-edit README in v1).

Minimum run-summary.json projection: {schema, run_id, patches[], base_revision, subject_composition_digest, platform, gpu_architectures[], model:{tier,sha256}, workload:{kind,corpus_sha256}, checks:{build,activation,correctness,performance:{status,pairs,mean_delta_pct,stdev_delta_pct,artifact}}, verdict, blockers[], evidence:<path>}.

P0.5 (fold into the same change, these are the recurring operational mistakes to eliminate):
- Never use pgrep for remote-run liveness/ownership (self-matches its own ssh command line). Every run gets a directory, run.pid (the real $!), run.log, and an atomically-written status.json; test liveness via `kill -0 $(cat run.pid)`; completion means a terminal status.json, not a grep heuristic.
- Use platform.linux-multi (and sibling platform entries) instead of hand-entering AMDGPU_TARGETS; add a separate small runtime/device profile only for what recipes don't express (HIP_VISIBLE_DEVICES, canonical -sm tensor -ngl 99).
- A fixture registry/ensure-helper for corpora/models -- wikitext2 gets one symbolic ID with a cache path, source, and SHA256; patch-validate asks for "wikitext2", nobody re-derives the download path.
- Every run self-describing: save resolved commands, effective env, composition IDs, binary hashes, model/corpus hashes, device visibility, repetition count, and A/B ordering BEFORE execution.
- Preflight once, fail fast before a multi-hour run if model/corpus/binaries/device-count/required-architecture/composition are wrong.
- Atomic phase status: materialize -> control-build -> subject-build -> correctness -> performance -> evidence -> complete (enables safe polling and a future --resume without a complex resume state machine yet).

Build-next scope, explicitly bounded: one patch-validate command + oracle adapter registry + runtime/fixture resolution + summary renderer, reusing validation_campaign/PVPS02/recipes/platforms/validation.toml/Experiment Contracts/patch-verify-evidence. Then migrate the next 2-3 real patch validations onto it before generalizing further -- do not build ahead of that.
