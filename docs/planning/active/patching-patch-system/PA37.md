# Make atomic patch 1203 an executable, truthful multi-contract validation package

## Description

Patch 1203 already binds the three real contracts RD05/RD06/RD07 and has real backend-reference correctness producers in the shared campaign code. It still lacks an executable validation package because RD06/RD07 carry performance effects whose contract binding requires activation capability, while the 1203 patch currently has no confirmed real `BIGCHERRY_PATCH_TRACE` activation marker. Do not bypass `require_execution_package()` and do not invent a regex for a marker that source does not emit.

This item owns the complete 1203 implementation/package slice: truthful activation/claims, `validation.toml`, patch-local producer, contract/check routing, and hardware-free end-to-end execution through PA36's generic plural-contract path. PA39 owns only the subsequent real-hardware acceptance/evidence receipt. Do not split producer registration/evidence plumbing between PA37 and PA39.

## Benefit target

1203 must be a proof that the shared PA36 design handles a real plural-contract patch without a special case. Success means:

- zero 1203/RD05/RD06/RD07 branches in shared dispatcher, CLI, validator orchestration, or evidence writer;
- zero use of `ValidationPlan.contract` in the implementation path;
- one atomic control/subject build pair supplies all three contracts;
- contract/check/architecture routing is represented by generic typed per-check results, not a 1203-specific aggregate schema;
- after PA37, PA39 can execute hardware acceptance without designing or registering new implementation machinery.

## Steps

1. Re-read all three bound Experiment Contracts and derive required capabilities/check scopes from `bind_contract()` and the current plural `ValidationPlan` semantics.
2. Decide activation truthfully:
   - preferred: add a minimal `BIGCHERRY_PATCH_TRACE`-gated production-path marker in 1203's source transform that proves the atomic patch's relevant dispatch path executed, with zero behavior when tracing is off; or
   - if no truthful marker can represent the claim, revise the affected contract claim/policy through the Experiment Contract owner rather than fabricating activation evidence.
3. Author `patches/1203_rd050607_rdna4_wmma_fa_q6k_mmq/validation.toml` only after required capabilities have real producers. On a >1-contract plan, explicitly scope checks with `contracts=[...]`; unscoped checks do not satisfy plural contract-derived requirements.
4. Implement/migrate one patch-local 1203 producer under `patches/1203.../validation/` using PA36's generic manifest/context/build/run/result seam. Registration, typed result production, artifact declaration, and evidence handoff are all part of this item; do not defer them to PA39.
5. Correctness: one atomic control/subject pair, built once as fat `gfx1100;gfx1201;gfx1030`, then run per real-device slot when hardware is supplied. RD05/RD06 consume their gfx1201 result; RD07 requires all three architectures. Never rebuild per architecture and never claim causal isolation among co-tenanted RD05/06/07 changes.
6. Performance/controls: encode each contract's actual policy. In particular RD06's confidence/round requirements must come from its contract, not a copied RD04 benchmark configuration.
7. Route check outputs through PA36's generic typed per-check result contract and existing evidence validators. No raw producer JSON may masquerade as canonical correctness evidence, and no correctness-only result may set promotion eligibility.
8. Add hardware-free end-to-end tests using controlled/fake execution results for all required architectures, missing architecture, failed architecture, scoped contract routing, artifact binding, build identity, activation evidence, plural gate serialization, and promotion fail-closed behavior.
9. Run package lint/plan resolution and prove the producer can be selected/executed through the generic dispatcher with no new dedicated flag or shared patch-specific branch.
