# Promote-and-release: one command from a validated patch to a versioned BigCherry release

## Description

Owner request 2026-10-08: when a patch is promoted, one process should commit the promotion and cut a release, bumping the version automatically.

What exists: `bigcherry pin-release <llama tag>` releases a pin (gate, record, notes, main, release-please PR, tag, sync) and already supports further releases on the same pin with `--bump minor|patch` (bc-<build>.<minor>.<patch>). Promotion itself is still done by hand each time: patch.toml / patch.py STATE / SUMMARY status to validated, README promotion record, the patch into [patch-set.validated-enhancements] and out of its [experiment.*], default flip, catalog and lint checks, composition check, commit, ledger event, plan state.

Wanted: `bigcherry patch-promote <patch id> --evidence @<file> [--default-on] [--release]`.

## Steps

1. patch-promote: refuse unless the evidence file is given and the patch applies in the production composition; set state validated in patch.toml, patch.py and SUMMARY.md; write or extend README.md with the evidence verbatim under a 'Promotion record' heading; add the patch to validated-enhancements and remove it from experiment sets that would then repeat a base patch; run the patch's tests, the catalog/governance tests, patch-lint for that patch and patch-rebase-check for the production set; commit with a conventional subject (`feat(patch): promote <id> - <one line>` for an enhancement, `fix(patch): ...` for a fix) so release-please sees it. Any failed check leaves the tree untouched.
2. --default-on: flip the flag's default in the patch (the on-by-default / off-switch form), update EnvDoc and docs in the same commit; only with evidence on more than one model named in the evidence file (owner rule).
3. --release: after the promotion commit, run pin-release for the current pin with --bump minor for an enhancement or --bump patch for a fix, passing the same evidence; several promotions can be batched by promoting each and releasing once.
4. Ledger: the command prints the record_change_event payload (class, files, summaries, plan-item-ids from patch.toml) for the agent to submit - the ledger MCP tool is not callable from the CLI.
5. Tests on a scratch repository as for pin-release; document in PATCH_VALIDATION.md, the patch-lifecycle skill and PIN_BUMP.md.

## PRBE policy transfer (PRBE71/72/73)

This section is **policy/automation backlog**, not a claim that new qualification tooling is implemented.

1. **Ablation (PRBE71):** when evaluating coupled stream/GDN bundles, create separately composed, source-level or compile-time qualification variants; do not treat runtime env flags as independent ablation of `1215` RD39-42's coupled scratch/overlap edit or `1221` RD50-53's DPP/exp2/launch-bounds kernel decisions. `1215` is rejected; `1221` is untested/gfx1151-only. A variant must first pass backend correctness and have independently attributable kernel/PP/TG evidence. Never inject temporary qualifier flags into the promoted production default.
2. **Hardware eligibility (PRBE72):** a contract must specify the real hardware **traits** (integrated, UMA, peer access, GPU count, driver), not architecture alone when the mechanism depends on them. `tools/bigcherry/experiment/contract.py::Scope` already exposes the fields; `evaluate_scope_eligibility` fails closed on missing observations. The RD22 declaration in `config/experiment-contracts.toml` still needs a separate source-verified migration: do not blindly change gfx1201 to gfx1151 without checking patch 1209 and PRBE17. PA45 implementer should open a distinct config/test slice rather than calling the migration complete.
3. **Hardware-blocked retirement (PRBE73):** document blocker device/backend/topology, the concrete patch ID/state or missing-evidence reason, date blocked, last source/equivalence review and next review (suggest 90 days). On review, either revalidate, keep deferred with fresh explanation, or deprecate if obsolete; never delete/auto-promote. Confirm whether `docs/planning` frontmatter schema is owned by this repo or the external planning tool BEFORE building a field validator. Missing matching hardware is not a failed performance experiment.
4. **Lightweight promotion (QFP18):** retain fast mechanics + patch-lint + activation + independent measured ABBA evidence as an accepted path for eligible local enhancements. The minimum remains source/digest/architecture identity, unchanged-output or declared numeric contract and explicit baseline; hardware absence cannot be waved away by the lightweight tier. Use full validation/contract campaigns when high-risk, broadly default-on or weak evidence requires it.

No patches, config or CLI changes are part of this docs slice.
