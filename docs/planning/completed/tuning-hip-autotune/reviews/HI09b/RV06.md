# OPEN: architecture_mask does not encode capability, so 80 CDNA-only MMF candidates are evaluated on every RDNA signature

## Notes

Verified on gfx1100 (both the server XTX under Linux and the local GRE under Windows) and gfx1201. RDNA2 (gfx1030) remains unrun — measured peak VRAM for the sweep is 568 MiB against only 443 MiB free on that card, so it would OOM and disturb the job already running there.

Incidental finding from the same JSONL, worth its own look: candidate status counts were ineligible 193,657 / architecture 113,190 / ok 3,512 / **tolerance 1,491**. The tolerance rejections include `blas:hipblas-auto:v1` at nmse 1.5e-06 and max_abs 0.029 — the tuner correctly refusing a faster but numerically divergent candidate. That is the correctness validation doing its job, but the volume is worth understanding before a real tuning run, since a family rejected on tolerance is silently absent from the winner set.

## Findings

Found 2026-08-05 during cross-architecture validation on gfx1100 (RDNA3) and gfx1201 (RDNA4). Revised after checking precisely what these candidates require — the first framing ("candidates that cannot run") was too strong.

The `workload-max` catalog contains 81 MMF candidates: 80 generated `mmf:f32:*` variants and one native wrapper. **They are CDNA-only.** Upstream's `ggml_cuda_should_use_mmf` routes F32 through `ampere_mma_available(cc) || amd_mfma_available(cc)`, and:

- `amd_mfma_available(cc)` is `GGML_CUDA_CC_IS_CDNA(cc)` — MI100, MI210/MI250 (CDNA2), MI300 (CDNA3)
- `ampere_mma_available(cc)` is NVIDIA ≥ SM80, which a HIP overlay never sees

So the candidates are legitimate and correctly generated — on an MI300 they are exactly the right candidates, and the catalog is right to enumerate CDNA among its 26 architectures. **They are simply unrunnable on every GPU this project has**: 2× gfx1100 (RDNA3), gfx1201 (RDNA4), gfx1030 (RDNA2). RDNA3/4 have WMMA, which MMF uses only for F16/BF16; RDNA2 has neither.

The real defect is that `architecture_mask` does not encode capability. The mechanism to exclude them exists and is enforced — `ggml_hip_tuner_resolve` checks `ggml_hip_candidate_supports_arch` first and has a `GGML_HIP_REJECT_ARCHITECTURE` reason code for exactly this. But `mmf:f32:w10:nw1:v1` carries `UINT64_C(134217726)`, covering essentially every architecture the catalog knows, because `schema.architecture_mask` is built from the enumerated architecture *list* rather than from what the family can do per architecture. So 80 of 270 candidates — 30% of the space — fall through to `can_execute` and are rejected as `INELIGIBLE` on every signature, when they should have been excluded up front as `ARCHITECTURE`.

Evidence across full sweeps on both RDNA3 and RDNA4: every MMF winner was `mmf:native:v1`, not one generated MMF variant won or could have, and the eligible-count distributions for float src0 at ncols 9..16 are identical between the two architectures (59/58 cases with 2 eligible, then 6/6, 2/2, 7/7).

Not a correctness bug — RV03's `should_use_mmf` gate rejects them safely and `can_execute` is cheap. It is a clarity problem: it inflates `gen` in every coverage report, so a reader comparing generated against measured finds a third of the space unaccounted for and must know the reason. Miscategorising them as `INELIGIBLE` rather than `ARCHITECTURE` is precisely the kind of ambiguity HI12's coverage report exists to remove.

Secondary consequence, worth stating because it invalidates a planned test: RV03 noted that gating MMF on `should_use_mmf` whole costs exploring ncols 9..16 on RDNA3.0, and that RDNA4 would falsify it. **It cannot** — with no non-F32 MMF variants in the catalog, the only MMF candidate that can ever be eligible on RDNA is the native wrapper, so the width cap is unobservable. RV03's trade-off currently costs nothing and becomes real only once an inventory generates F16/BF16 MMF variants.

Also worth recording: **bigcherry has no CDNA hardware**, so these 80 candidates cannot be validated by this project at all. Anything asserting they work is unverified.

## Conclusion

**Fixed and verified on gfx1100, 2026-08-05.**

`architecture_mask` now encodes capability rather than the catalog's architecture list. Added to `autotune_schema.py`:

- `MFMA_ARCHITECTURES` — the four CDNA parts (gfx908/90a/942/950)
- `WMMA_ARCHITECTURES` — the ten RDNA3/RDNA3.5/RDNA4 parts. Note gfx115x is included: `AMD_WMMA_AVAILABLE` is `RDNA4 || RDNA3`, and `RDNA3` is `__GFX11__`, which covers RDNA3.5 as well as gfx110x.
- `mmf_architectures(source_type, architectures)` — F32 needs MFMA, F16/BF16 need WMMA or MFMA, mirroring the type switch at the end of `ggml_cuda_should_use_mmf`.

`enumerate_mmf` now passes the narrowed list, and skips the candidate entirely if nothing is left.

**Deliberately coarse.** `should_use_mmf` also excludes BF16 on CDNA3 and F16/BF16 on CDNA1/CDNA2, and remains the precise authority at dispatch time via RV03's gate. The mask narrows only where a candidate can *never* run, because a mask that is too narrow silently drops a workable candidate while one slightly too wide merely defers to a runtime check that already exists.

Verified end to end on the local idle gfx1100 (7900 GRE, Windows ROCm 7.1 build):

- `mmf:f32:w10:nw1:v1` mask went from `UINT64_C(134217726)` to `UINT64_C(240)` — bits 4..7, the CDNA parts, exactly.
- In the tuner's measurement JSONL that candidate now reports `"status":"architecture"` where it previously fell through to `ineligible`.
- **113,190 architecture rejections** across the run — 80 MMF f32 candidates × ~1,415 signatures = 113,200, matching to within rounding.
- Sweep still passes: 1,155 signatures, 0 failures, exit 0.

No behavioural change to winners, as expected: these candidates were already being rejected, just later and under a misleading reason.
