# MMF eligibility ignored type and arch, launching uninstantiated kernels

## Notes

Two further defects were found downstream of this one and are recorded as RV04 (src1 F32 precondition) and RV05 (tuning under graph capture). With all five fixed, the full MUL_MAT sweep completes on gfx1100: 1151 signatures tuned, 0 failures, exit 0, 2/2 backends passed.

## Findings

Still open. Found on gfx1100 2026-08-05 after RV02, on the float half of the MUL_MAT sweep. The third distinct instance of one underlying pattern — see the note at the end, which is the part worth acting on.

`ggml_cuda_mmf_variant_is_eligible` explicitly discards the type (`GGML_UNUSED(type)`) and validates only geometry: nwarps within 1..8, nwarps within `mmf_get_max_block_size(cc)/warp_size`, and a shared-memory bound. Nothing asks whether MMF has device code for this (type, arch) at all.

Result under tune mode:

```
mmf.cuh:60: ERROR: HIP kernel mul_mat_f has no device code compatible with HIP arch 1300.
Kernel Name: _ZL9mul_mat_fIfLi32ELi1ELi1ELb0EEvPKT_PKfPKiPfiiiiiiiiiiiiiiii
  -> mul_mat_f<float, 32, 1, 1, false>
HSA_STATUS_ERROR_EXCEPTION: An HSAIL operation resulted in a hardware exception
ggml-cuda.cu:114: ROCm error: unspecified launch failure
```

The kernel body compiled to a `NO_DEVICE_CODE` stub for this architecture, so the launch is a hardware exception rather than a clean abort — it takes the HIP queue down with it and the process dies with a device in an unusable state (`current device: -1` in the follow-on error). That is worse than the MMQ and MMVQ failures: no bigcherry frame appears, and the first-glance reading is a driver fault, exactly the misdiagnosis HANDOFF already records for the HI12/HI13 recursion bug.

Upstream's guard is `ggml_cuda_should_use_mmf(type, cc, warp_size, src0_ne, src0_nb, src1_ncols, mul_mat_id)`, which our predicate never consults.

Reached 243 tuned signatures with 0 test failures before this; the entire quantised half of the sweep now passes.

**The pattern, which matters more than this one bug.** Three families have now failed the same way: an eligibility predicate that approximates what the build actually instantiated, and is wrong in a different direction each time. RV01 — type absent from the descriptor entirely. RV02 — `ggml_is_quantized` broader than MMQ's config tables. RV03 — geometry checked, type and arch not checked at all. Each was found only by running it on hardware, and each looked like something else first.

## Conclusion

**Fixed and verified on gfx1100, 2026-08-05.**

`ggml_hip_mmf_can_execute` now calls upstream's own `ggml_cuda_should_use_mmf(type, cc, warp_size, ne, nb, src1_ncols, mul_mat_id)`, placed **before** the native-wrapper short-circuit — the native wrapper is as capable of naming an uncompiled kernel as any forced variant.

Root cause was sharper than first written: MMF's F32 path requires `ampere_mma_available || amd_mfma_available`, and RDNA3 has neither (it has WMMA). So *every* `mmf:f32` candidate is unrunnable on gfx1100 while looking perfectly eligible — 81 of them in the `workload-max` set.

The signature stores strides normalised to elements (`ggml_hip_fill_strides`), so they are converted back to bytes (`nb0[i] * ts / blck`) for the call.

**Called whole rather than split into a capability half, deliberately.** The alignment and contiguity checks inside it are crash-prevention (upstream's own comment says "would result in a crash"), and the ncols bounds track which instances upstream compiles. The one cost is exploring ncols 9..16 on RDNA3.0, where upstream caps at 8. Those candidates now report ineligible — a category HI12's coverage report distinguishes rather than hides. **This trade-off is falsifiable on RDNA4**, which is not RDNA3_0 and so should make 9..16 eligible; if it does not, the gate is over-restrictive. Cross-arch validation is running.

Sweep went 243 → 366 signatures after this fix.
