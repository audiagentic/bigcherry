# Illegal HIP memory access under tune-mode dispatch + MTP speculative decoding

## Description

GGML_HIP_DISPATCH_MODE=tune crashes (SIGABRT/illegal HIP memory access) when llama-server runs with --spec-type draft-mtp speculative decoding and a real completion request is served. Crash is in a different code path than HI70's earlier small-ubatch crash (already fixed via GGML_CUDA_DISABLE_GRAPHS=1) -- this one aborts inside ggml_hip_mmvq_can_execute() calling ggml_cuda_get_device(), which itself reports a deferred/async ROCm 'illegal memory access' error, meaning the actual bad access happened earlier in an async HIP call and is only surfaced at this later synchronization point.

## Steps



## Detailed Solution & Technical Design

GPT-AUTO DEEP-DIVE VERDICT (2026-08-18, session ses_91cabca918c2421f, resumed from the earlier RE12 review thread): do NOT copy get_mmvq_mmid_max_batch() into MMQ -- that guard solves a narrower MoE-specific (MUL_MAT_ID expert-batch) problem and our repro is dense MUL_MAT (Qwen3.5-4B, not MoE). The MMVQ precedent's real lesson to reuse is structural, not numeric: 'family-native does not exempt you from family launchability constraints' -- ggml_hip_mmq_can_execute()'s native-wrapper early return (`if (self->source_class == GGML_HIP_SOURCE_NATIVE_WRAPPER) return true;`) is the same class of mistake HI53 already fixed for MMVQ, just not yet applied to MMQ.

STRONGEST ROOT-CAUSE LEAD: a real out-of-bounds READ, not a missing simple gate. Upstream's dense ggml_cuda_mul_mat_q() quantizes src1 into src1_q8_1 and pads the allocation with `ggml_cuda_mmq_get_J_max(type, fallback, cc, ne11) * sizeof(block_q8_1_mmq)` as a safety tail -- BUT that tail is sized for upstream's NATURAL J-selection envelope for the REAL N (ne11/ncols_max), not for an arbitrarily FORCED J the tuner might choose to measure. mul_mat_q_process_tile<...,J,...>()'s Y-staging loop reads a full compile-time J-wide tile unconditionally (no tile_y_max_j bound on the READ, only on the output WRITE), and the launch grid does `ntx = ceil(ncols_max / J)` so N smaller than J still launches one full J-wide tile. The hard safety condition should be `required_tail_columns = (J - (N % J)) % J <= available_tail_columns = ggml_cuda_mmq_get_J_max(type, fallback, cc, N)` -- NOT a plain N-vs-batch-limit bound. For N=4 forced J=8 (needs 4 padding columns J_max's real-N search never allocates), or N=16 forced J=112 (needs 96 padding columns), this inequality plausibly fails badly.

CONCRETE CODE SMELL CONFIRMING THIS: bigcherry's OWN ggml_cuda_mmq_variant_is_eligible() (patches/0300_mmq_forced_j.py, _MMQ_SOURCE) already takes `ncols_max` as a parameter -- and immediately does `GGML_UNUSED(ncols_max);`, discarding it. The hard-eligibility API was clearly designed with the right shape-awareness in mind and never finished.

THIS MAY BE THE SAME BUG AS EX02 (see that item -- 'MMQ q6_K/J=112 illegal-memory-access incident on gfx1100', root cause still formally open, currently mitigated only by a narrow gfx1100-scoped quarantine). EX02's own investigation notes recorded ruling out exactly this Y-tile-overread hypothesis with the reasoning 'mmq.cu's own allocation already pads by ggml_cuda_mmq_get_J_max(...) ... to make this safe' -- but that reasoning only checked THAT the padding term exists, never whether it is SIZED CORRECTLY for an arbitrarily forced J far outside what J_max's own search over the real N would produce. GPT's assessment: that EX02 conclusion is 'demonstrably incomplete' and the Y-staging-overread hypothesis should be reopened for EX02 too, though EX02's exact historical signature was never recovered so it cannot be closed by this reasoning alone -- only reopened as the leading theory.

RECOMMENDED FIX (launch-envelope correctness at the MMQ boundary, NOT a batch-width cap and NOT an architecture blacklist):
1. One more diagnostic step BEFORE writing any fix: capture the exact failing candidate/signature (stable name, N/ncols_dst, J, fallback, type) via host-side logging immediately before the crashing launch (not device printf) with HIP_LAUNCH_BLOCKING=1 + GGML_CUDA_DISABLE_GRAPHS=1 (project's existing EX02 diagnostic protocol -- do not add a second serialization mechanism alongside AMD_SERIALIZE_KERNEL=3 already used). Compute required_tail = (J - N%J) % J vs available_tail = ggml_cuda_mmq_get_J_max(type, fallback, cc, N). If required_tail > available_tail, the mechanism is established -- proceed to the fix below without rocgdb. If the inequality holds (padding was sufficient), this hypothesis is wrong and the next step is rocgdb for the actual faulting instruction/address.
2. Make ggml_cuda_mmq_variant_is_eligible() genuinely shape-aware for dense MMQ: split into ggml_cuda_mmq_config_is_eligible() (existing type/J/fallback/config-table/shared-memory check, unchanged) + a new ggml_cuda_mmq_dense_variant_is_eligible(..., ncols_max) that ALSO enforces the tail-padding inequality above. Keep ggml_cuda_mmq_type_is_supported() calling only the config-only check (it currently passes ncols_max=0 as a sentinel to the combined function -- once the function is genuinely shape-aware, that sentinel call becomes wrong and must be redirected to the config-only variant, not special-cased).
3. Move MMQ's native-wrapper acceptance in ggml_hip_mmq_can_execute() (hip-autotune-dispatch.cu) below the same hard launchability check -- determine the family-native J via the already-existing ggml_cuda_mmq_native_j_best(type, fallback, ncols_max) and apply the SAME dense-safety predicate to it, so a native MMQ challenger at N=4 correctly gets rejected before measurement if its own natural J isn't safe at that N (mirrors HI53's fix for MMVQ exactly).
4. Do NOT generalize the dense tail-padding formula to the MUL_MAT_ID/MoE path in this fix -- MoE's allocation/launch geometry is different (flattened token/expert rows, per-expert col_diff depends on runtime expert distribution). Scope this fix to dense MMQ only.
5. Do NOT expand MMQ's workspace/padding to make huge forced-J-on-tiny-N safe as an alternative -- that would silently widen the kernel's valid input domain beyond what upstream ever exercises, risking a DIFFERENT narrow-N assumption producing quietly wrong output instead of an obvious crash. RE15 doesn't need that capability; reject unsafe shapes rather than trying to accommodate them.

DECOUPLING MMF EVIDENCE FROM THIS FIX (also recommended, addresses HI70's remaining MMF gap): use vendor/llama.cpp's own test-backend-ops.cpp test_mul_mat harness directly (CPU-referenced correctness, arbitrary m/n/k, already supports `-o MUL_MAT -p <regex>` filtering) instead of MTP/llama-server entirely -- construct M=32/K=256/N=<missing candidate's width> for each missing mmf:f16 candidate (satisfies RDNA4 wave32 F16 alignment + MMF_ROWS_PER_BLOCK=32), and separately M=127 (or any %128!=0)/K=256/N=128 for the remaining q5_k fb1 candidates (deterministically triggers fallback=1 without needing to find another real model with a lucky irregular shape). This is a smaller, deterministic, CPU-referenceable correctness corpus that removes model/workload luck from candidate correctness coverage entirely -- recommended as RE15's actual evidence-generation path going forward, decoupled from fixing HI71.

EXPLICITLY NOT RECOMMENDED: an MMQ batch-width cap mirroring get_mmvq_mmid_max_batch numerically; a gfx1201/gfx1100 architecture blacklist; weakening RE15's replay-full correctness gate to accept fewer than all reachable candidates as evidence.
