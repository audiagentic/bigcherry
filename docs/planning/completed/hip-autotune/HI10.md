# Implement signature collection (record mode) and SQLite persistence

## Description

Patch 8 — implement hip-autotune-record.cpp for record mode that captures signatures, native candidates, call counts, and deduplication. Implement hip-autotune-db.cpp with SQLite schema from dispatch-db.sql: build, hardware, signature, candidate, observation, measurement, winner, replay_miss tables.

## Steps

- Implement record mode in hip-autotune-record.cpp
- Construct signatures after device-local shape is known
- Observation merging on duplicate signature: increment `calls`, append new site to `sites_json` (deduplicated), merge diagnostics into `diagnostics_json` (later values override earlier for same key)
- Process dedup map for identical signatures at different call sites
- Implement SQLite persistence in hip-autotune-db.cpp using dispatch-db.sql schema
- Batched DB writes — not per-call
- 128-bit digest via `blake2b(digest_size=16)` with per-component `person=` prefixes: `llama-hip-tune` (signature), `llama-hardware` (hardware key), `llama-dispatch` (dispatch key)
- Full-key collision check on canonical JSON
- Coverage report: signature set, native candidates, frequency ranking
- Export inventory JSON for WORKLOAD_MAX candidate generation

## Notes

Major deviation from plan: **JSONL output, not SQLite at runtime.** Record mode writes JSON Lines from C++ (`hip-autotune-record.cpp`) and `python -m bigcherry.inventory` builds the SQLite database offline with the stdlib sqlite3 module. `sql/dispatch-db.sql` is unchanged and remains the schema of record — only *who* writes it moved.

Three benefits: killed tuning run keeps everything flushed; truncated final line recoverable by construction; standards 9.1 (production links no SQLite) true by construction rather than by remembering to gate it.

Dead `find_package(SQLite3)` / link logic removed from CMake patch rather than left as phantom requirement.
