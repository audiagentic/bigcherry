# Extend the HIP autotune dispatch/candidate system beyond matmul: non-matmul op-class scope and foundational infra

## Description

**A real, previously-unflagged scope boundary, confirmed by direct code audit (2026-09-09, forked investigation of HI173's own "is this covered" question)**: BigCherry's entire HIP autotune candidate/dispatch/tuning system -- the dispatch hook, the candidate registry (`tools/bigcherry/tuning/schema.py`'s `FAMILIES = ("mmvq", "mmq", "mmvf", "mmf", "blas")`), correctness evidence (HI67), behavioral gates (HI143), and promotion/recovery (HTR01) -- is wired exclusively into `ggml_cuda_mul_mat_cublas`/`ggml_cuda_mul_mat_cublas_dispatch` (`patches/0200_dispatch_hook/patch.py`). `hip-autotune-dispatch.cu` has zero `GGML_OP_*` branching outside that one hook.

**Every non-matmul GGML op runs unmodified upstream llama.cpp code with no BigCherry candidate wrapper, no observability, and no plan item claiming it**: flash-attention, RoPE, rmsnorm/norm, quantize/dequantize, softmax, GLU/activation kernels, and any other op class. This is structurally different from the BLAS gap HI17/HI173 address -- BLAS already has a candidate family (single-candidate, unsearched); these op classes have ZERO candidate-system presence of any kind, not even observation.

This item is the HI17-equivalent foundational step for that entire scope: establish observability + a stable candidate identity for one or more non-matmul op classes, WITHOUT authorizing any candidate search or promotion yet (same discipline HI17 applied to BLAS) -- proving the dispatch-hook pattern generalizes before committing to per-op-class tuning work. Concrete per-op-class candidate-search items (RoPE, flash-attention, rmsnorm, quantize/dequantize, softmax) are filed as separate follow-on items once this foundation exists, mirroring HI17 -> HI173's relationship, rather than being bundled here.

## Steps

1. Pick the FIRST op class to extend (do not attempt all at once): recommend RoPE or rmsnorm as the pilot -- both are simpler dispatch shapes than flash-attention (single-tensor elementwise/reduction-style ops, no KV-cache/mask/causal-structure complexity), so they de-risk the dispatch-hook generalization itself before tackling flash-attention's much larger candidate surface.
2. Locate the pilot op's real dispatch entry point in vendor/llama.cpp/ggml/src/ggml-cuda/ (e.g. rope.cu, norm.cu) and determine whether it already has more than one internal implementation variant (block-size/vectorization choices) that a candidate identity could name, or whether variants would need to be authored (would make this item's scope closer to HI25's custom-kernel precedent than HI17's decomposition-of-existing-choice precedent -- confirm which case applies before estimating effort).
3. Design a stable candidate identity for the pilot op class, following HI17's exact discipline: identity carries RESOLVED CONFIG (the actual choice made), not request attributes (shape/type stay in the signature, matching HIP_AUTOTUNE_STANDARDS 2.1/2.2).
4. Extend the dispatch hook mechanism to a second op (`patches/0200_dispatch_hook/patch.py` and `hip-autotune-dispatch.cu`) -- this is the actual proof-of-generalization step. Confirm the existing signature/manifest/replay infrastructure (hip-autotune-types.h, replay v3) either already generalizes or needs an explicit, scoped extension -- do not assume it transfers silently.
5. Add record-mode telemetry for the pilot op class (effective execution path, timing, any conversion/temp-buffer facts analogous to HI17's BLAS telemetry).
6. Offline regression tests: candidate-identity contract, dispatch-hook multi-op-class behavior (prove the matmul hook's existing behavior is unchanged), record-mode telemetry.
7. Real-hardware validation: correctness pass (CPU-reference or existing test-backend-ops harness) for the pilot op's native-vs-observed-native path (no forced/alternative candidate yet -- this step proves observability, not a performance claim).
8. Explicitly do NOT add a second candidate variant, search, or promotion for the pilot op in this item -- that is deliberately deferred to a follow-on item (mirroring HI17 -> THA17), once this item proves the dispatch-hook pattern generalizes safely.
9. Write up the generalization findings (what transferred cleanly from the matmul hook, what needed real rework) as the reusable template for the remaining op classes -- flash-attention, quantize/dequantize, softmax, and any others -- so each can be filed as its own scoped follow-on item (per-op-class candidate search) without repeating this item's foundational discovery work.

## Detailed Solution & Technical Design

**Why this must be scoped as infra-first, not a jump straight to candidate search**: HI17's own history is the direct precedent and warning here -- BLAS already HAD a stable, existing multi-provider/API surface (rocBLAS/hipBLAS/hipBLASLt), and even so HI17 took a full dedicated item just to build observability and a stable candidate identity, explicitly withholding any promotion. Non-matmul ops are architecturally further from BigCherry's existing tuner assumptions than BLAS was: BLAS is a library-solution-selection problem (HI173's scope); MMVQ/MMQ/MMVF/MMF are BigCherry's own hand-written kernel variants; a new op class starts from neither position -- it may have zero internal variant choice at all today (a single upstream kernel per shape, e.g. RoPE), meaning any 'candidate' would need genuinely new kernel authoring (HI25's cherrypips precedent, not HI17's decomposition precedent). This item's first real deliverable is determining, per pilot op, which of those two shapes the work actually is -- that determination changes the follow-on item's effort/risk profile substantially and must not be assumed.

**Dispatch-hook generalization is the load-bearing technical question**: the hook currently lives ONLY in `ggml_cuda_mul_mat_cublas`/`_dispatch`. Extending it to a second op means either (a) a second, parallel hook insertion point per op class (safer, more isolated, more patches to maintain), or (b) a genuinely generic hook mechanism keyed on `GGML_OP_*` (more reusable, more invasive to shared dispatch code, higher regression risk to the existing matmul path). This item must make and justify that architectural choice for the FIRST pilot op before any later op class reuses it -- do not let the second op class silently pick a different pattern than the first.

**Candidate-identity discipline carries over unchanged from HI17**: resolved config in the name, request attributes stay in the signature, no `applies_if`-as-best-effort, fail-closed on ambiguous/incomplete config. HIP_AUTOTUNE_STANDARDS apply identically regardless of op class.

## Effort & Risk

Large, high uncertainty until the pilot op's variant-shape question (decomposition vs authoring) is answered -- this is explicitly why the item is scoped as foundational/single-pilot-op rather than all five op classes at once. Primary risks: (1) the dispatch-hook generalization touches shared upstream-adjacent code (`hip-autotune-dispatch.cu`) that every existing matmul candidate depends on -- a regression here is high-blast-radius, not contained to the new op class; (2) if the pilot op has no existing internal variant choice, this item's scope silently becomes kernel-authoring-adjacent (HI25's risk profile), which is materially larger than HI17's was; (3) flash-attention specifically (not the recommended pilot, but the largest eventual op class in this scope) has KV-cache/causal-mask/mixed-precision structure that may not fit the matmul candidate-identity pattern at all -- do not assume it will generalize even if RoPE/rmsnorm do.

## Standards

HIP_AUTOTUNE_STANDARDS 2.1 (stable name is durable identity), 2.2 (name carries resolved config), 12.4 (hard eligibility), 13.1 (build namespace). Same fail-closed, no-applies_if-as-best-effort, no-fabricated-provenance discipline as every other HI-series item -- op-class scope does not relax any of this project's standing patch-lifecycle or tuning-evidence rules.

- [ ] Dispatch-hook generalization approach (per-op parallel hooks vs generic GGML_OP_*-keyed hook) chosen and justified, with the existing matmul path's behavior proven unchanged (regression tests pass).

RD73 (real precedent: a tuned matmul candidate broke CUDA/HIP graph-capture-identity assumptions in downstream MTP speculative-decode code, invisible to per-call numeric correctness) is written up as a durable architecture note: docs/reference/architecture/DESIGN_DECISIONS.md, "A tuned candidate can break code that never runs it".
