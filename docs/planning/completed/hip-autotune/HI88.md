# RCCL same-architecture algorithm/protocol tuning (realistic scope only)

## Description

Captured from critical assessment of an external design document ("BigCherry Replay and RCCL Tuning Architecture", pasted into chat 2026-08-23, not independently authored) against real hardware evidence and real RCCL/RCCL-plugin availability, per explicit user request to determine what's realistic and file it as backlog. Two verification checks were run before filing this item, both of which materially narrow the document's original scope -- see Notes.

The document's central premise for RCCL tuning was: qualify RCCL execution plans (algorithm/protocol/channel/chunk choices) to find a SAFE, working configuration even for heterogeneous-GPU-architecture participant groups, going further than HI85's current shipped mitigation (which declines cleanly to META for any heterogeneous group rather than trying to make RCCL itself work there). That premise is FALSIFIED by direct hardware testing (see Notes) -- forcing NCCL_ALGO/NCCL_PROTO does not avoid the crash under any of 6 combinations tested. What remains realistic and worth keeping as backlog: algorithm/protocol/channel tuning for the SAME-architecture case (the real production {0,1} dual-XTX topology, and any future same-architecture N-GPU deployment), purely as a PERFORMANCE optimization over RCCL's own default algorithm selection -- not as a correctness/safety mechanism.

## Steps



## Detailed Solution & Technical Design

Two concrete integration mechanisms exist, with different real availability:

1. Environment-variable overrides (NCCL_ALGO, NCCL_PROTO, and others in RCCL's standard runtime vocabulary -- Ring/Tree algorithms, Simple/LL/LL128 protocols, independently confirmed real via this session's own NCCL_DEBUG=INFO tracing during HI85's investigation). These work today, need no plugin, and could be swept empirically (via the existing telemetry/replay infrastructure, e.g. HI18's reduce_correctness.py harness) against the real {0,1} production pair to see whether any combination beats RCCL's own default choice for BigCherry's actual tensor shapes. This is the low-risk, immediately-actionable slice.

2. The document's proposed libnccl-tuner-bigcherry.so (NCCL/RCCL tuner plugin API, ncclTuner_v6, getCollInfo()/getChunkSize() callbacks) for programmatic per-call algorithm selection integrated with BigCherry's own signature/telemetry system. VERIFIED NOT PRESENT: searched the installed ROCm-7.14-multiarch runtime tarball's headers and found no tuner.h and no ncclTuner/tuner_v6/NCCL_TUNER symbols in nccl.h -- only a pre-built cost table (share/rccl/tuner/rccl_tuner_gfx950.csv), not an SDK. This plugin SDK, if it exists at all for RCCL (vs. NCCL proper), would have to come from RCCL's own GitHub source tree and has NOT been confirmed to exist or build against this project's pinned RCCL version. Treat this as a real, unresolved gap -- do not assume the plugin path is available without first checking RCCL's actual upstream source for this ABI.

The document also proposed splitting HI18's current combined reduction_signature_key (tools/bigcherry/telemetry.py: `split_reduce:v1:{element_type}:{element_count}:{slice_shape}:{topology_key}`) into three separate concepts -- a ReduceOperationSignature (op/dtype/shape only), a ReduceCommunicatorIdentity (rank count, ordered rank architectures, peer-access matrix, topology class), and a ReduceCompatibilityRevision (RCCL build/ABI identity). This is a reasonable normalization IF algorithm/protocol tuning is pursued (different signatures should be cacheable independent of which specific communicator identity produced them), but is pure refactoring risk with no benefit until (1) above actually produces a reason to cache algorithm/protocol choices per signature. Do not do this refactor speculatively.

Only proceed to plugin-based integration if (a) the env-var sweep shows a real, worthwhile performance delta and (b) RCCL's tuner plugin SDK is confirmed to actually exist and build against this project's pinned RCCL source.

## Effort & Risk

High risk of chasing a small or nonexistent performance win: RCCL's own built-in tuner (confirmed real -- the per-rank 'RCCL Tuning index' seen in this session's own NCCL_DEBUG=INFO traces) already selects algorithm/protocol per topology/message-size; BigCherry-side overriding it may just be worse than RCCL's own heuristic unless a specific, measured gap is found first. Do not schedule build-out effort before the env-var sweep produces a real measured number.
