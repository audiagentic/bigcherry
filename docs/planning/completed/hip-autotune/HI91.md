# Patch RD17 (paired-mmvq gated struct fields) anchor no longer matches current source

## Description

Discovered as a side effect of a real-hardware build verification pass (2026-08-23), not something deliberately investigated. `python -m bigcherry apply --force` (full-catalog apply, all groups/states) fails to apply patches/1207_rd17_moe_topk_down_fold.py's two struct-field edits (`rd17-struct-host`, `rd17-struct-device`) against the current vendor/llama.cpp pin (0adcc3bb5710): both anchors match 0 times, expected 1.

Anchors:
- `rd17-struct-host`: `    const ggml_tensor * gate_scale = nullptr;\n    ggml_glu_op glu_op;` (attaches to `ggml_cuda_mm_fusion_args_host`)
- `rd17-struct-device`: `    const void * gate_scale = nullptr;\n    ggml_glu_op glu_op;` (attaches to `ggml_cuda_mm_fusion_args_device`)

Every other patch in the full catalog applied cleanly in the same run (or was already applied) -- this is an isolated anchor drift on these two struct edits specifically, not a broader patcher/tree problem. Consistent with the same failure class HI35's S1b equivalence trace already documented for a different struct (mmvq's template parameter gaining `halve_iters` between pins) -- an upstream pin move can reorder/rename struct fields the anchor was written against.

## Steps

1. Diff the current vendor/llama.cpp ggml-cuda/common.cuh (or wherever ggml_cuda_mm_fusion_args_host/device now live) against what the RD17 patch's anchor expects -- confirm whether gate_scale/glu_op were reordered, renamed, or a field was inserted between them.
2. Determine RD17's own patch state (validated/untested/rejected) and whether it's selected by any default recipe -- if it's untested/rejected and not in a default recipe's groups, this may not be blocking anything today, only surfacing on a full --force apply.
3. Update the anchor to match current source, or mark the patch's state/group appropriately if RD17 itself is stale/superseded.
4. Confirm `python -m bigcherry apply` (recipe-scoped, not --force) still succeeds for every default recipe regardless of RD17's state -- the finding this item exists to close is specifically about the full-catalog --force path used for verification, not necessarily a production-blocking regression.

### 2026-08-23 (later, different session): MISDIAGNOSED -- not an anchor drift bug, resolved as no-op

This is NOT a real anchor-drift regression. patches/1207_rd17_moe_topk_down_fold.py's own header and its patch-catalog CONFLICTS declaration (`CONFLICTS = ("1205_rd12_paired_mmvq_dual_output",)`, confirmed via `bigcherry patch-explain 1207_rd17_moe_topk_down_fold` -> `conflicts: 1205_rd12_paired_mmvq_dual_output`) already document exactly this: 1207's struct anchor is the SAME 2-line `gate_scale` -> `glu_op` span that 1205 inserts its own `dst_gate` field between. Both patches are `group=rdna-boosts, state=untested` (confirmed via `patch-explain` on both). `apply --force` (or bare `apply` with no `--groups`/`--states` filter) selects the ENTIRE catalog including both mutually-exclusive experimental patches together, and 1205 (applied first) consumes the anchor 1207 then fails to find -- exactly the documented, intentional incompatibility, not upstream pin drift. No production recipe selects both together (every `[experiment.*]` entry in recipes.toml names exactly one 12xx patch by design), so this never affects a real build.

This item's own step 4 was already correct and is the actual resolution: `python -m bigcherry apply` (recipe-scoped, e.g. `--recipe bigcherry`, or `--groups core --states validated,untested` to include other untested-but-non-conflicting patches) succeeds cleanly -- verified directly, RESULT: PASS on both this workstation and a separately-checked Brutus checkout. Steps 1-3 (diff the source, update the anchor, retire RD17) are moot -- there is no drift to diff, no anchor to fix, and no reason to retire a patch whose only 'failure' is being force-selected alongside its own documented conflict partner. Closing as resolved-by-explanation, no code change needed.
