# Extend HI80 correctness-evidence generation to MUL_MAT_ID (MoE-routed) signatures

## Description

HI80's correctness-evidence tool (hi80_generate_correctness_evidence.py) is deliberately MUL_MAT-only: any non-MUL_MAT row is reported and skipped, since MUL_MAT_ID needs its own op_filter/target_tensor derivation rather than reusing MUL_MAT's mapping assumptions (per signature_correctness_mapping.py's own docstring). This blocks real per-signature promoted-winner replay for any MoE-routed (has_ids) result -- including RD54's two validated MMVQ nwarps candidates for Qwen-class MoE decode, which are statistically airtight (p=0.0, tight 95% CIs, nmse~0 vs native) but cannot pass tune-promote's correctness gate (promotion_status=rejected_no_correctness_evidence) purely because of this tooling gap, not a correctness concern.

## Steps



## Detailed Solution & Technical Design

Derive a MUL_MAT_ID-specific op_filter/target_tensor mapping (signature_to_op_filter's MUL_MAT-only assumptions do not transfer directly -- MUL_MAT_ID's ids/expert-routing shape and memory layout differ from plain MUL_MAT, as documented in the pinned mmvq.cu: ncols_dst = ids ? ne2 : ne1, and a dedicated mul_mat_vec_q_moe_launch kernel exists for the multi-token MoE case that plain MUL_MAT never touches). Extend correctness_evidence.generate_correctness_evidence() and write_correctness_evidence() to accept and route MUL_MAT_ID signatures against a patched test-backend-ops binary the same way MUL_MAT already works, verified against a real MoE model's real recorded signatures (RD54's Qwen3.6-35B-A3B Q8_0 K=256/K=2048 signatures are ready-made real test cases).

## BROADER CAMPAIGN CONFIRMATION (2026-08-24, same day, real hardware, Brutus)

Ran a full, real record -> tune -> correctness-evidence -> promote -> replay campaign on Qwen3.6-35B-A3B, not just the single K=256 signature from before, to test whether HI105 unlocking MUL_MAT_ID promotion generally produces measurable production gains.

**Record**: pp512+tg256, real workload, 29 real signatures captured (widths 1/4/8, mmq/mmvq/mmvf/blas families).

**Tune**: measured all 29 signatures, 95 candidates total, on real hardware.

**Correctness evidence**: ran the (now MUL_MAT_ID-aware) HI80 CLI against all 15 candidate (non-native-winner) rows. 3 evidence entries written, all MUL_MAT_ID: the original K=256/width-1 decode candidate (64e9cd56..., 55.86% isolated), plus two NEW real candidates this broader campaign found -- K=256 down-projection at 512-token batch/prefill (3c30c5f6..., 23.4% isolated) and K=2048 up/gate at 512-token batch/prefill (dc0d7f84..., 46.4% isolated). 2 candidates (unrelated mmvf:f32 family, not MoE) genuinely FAILED correctness on all 3 seeds -- filed separately as HI106, since that's a real kernel bug the gate correctly caught, not a HI105 scope item.

**Promote**: 3/15 promoted (all three MUL_MAT_ID candidates above); everything else correctly rejected or already-native.

**Replay build + real A/B** (build_plan_id=9251189577cc39b85d44d353c44535d6 vs the same native control as before): 8-round interleaved, BOTH pp512 (prefill -- exercises the two new batched candidates) and tg128 (decode -- exercises the original candidate). Result: pp512 native 1974.32 t/s vs replay 1972.99 t/s (-0.07%), tg128 native 72.620 t/s vs replay 72.620 t/s (+0.0008%). Both indistinguishable from zero.

**Conclusion**: this is not a fluke of one candidate. Even with 3 independently real, CPU-reference-verified, promoted MoE candidates covering both decode and prefill MoE-routing paths, full-model production throughput does not move. MoE-routed matmuls (MUL_MAT_ID) are consistently too small a fraction of total per-token/per-batch compute in this model's architecture for kernel-level tuning gains on them to matter at the production level -- a real, now well-evidenced structural finding, not a single-measurement anomaly.

## DECISIVE EXPERIMENT RESULT (2026-08-24, real hardware, Brutus)

Ran the real per-signature replay A/B this item existed to unblock. VRAM was previously fully consumed by an unrelated live production llama-server (PID 882093, ~50.7GB across both XTX GPUs) -- confirmed via rocm-smi that both GPUs are free before proceeding.

**Binaries**: native = fresh bigcherry-native:control:linux-multi build (build_plan_id=61c343efa39bdbe814bbe0d0a9902b23, GGML_HIP_AUTOTUNE=ON, GGML_HIP_DISPATCH_REPLAY=OFF -- confirmed mutually exclusive at compile time via patches/0100_cmake_options.py, so native/replay can never be runtime-switched on one binary). replay = the existing HI105 replay build (build_plan_id=15405d4069a475d2809ae5982b531cb9, GGML_HIP_DISPATCH_REPLAY=ON, winners baked in from the post-HI105 promoted-winners file containing RD54's K=256 dispatch 64e9cd56... at promotion_status=promoted, confirmed by grepping the exact input file used at build time).

**Method**: 8-round interleaved (native, replay) pairs, Qwen3.6-35B-A3B-Revised-q8_0, real production split config (-sm tensor, HIP_VISIBLE_DEVICES=0,1, -ngl 99, -ub 512 -b 2048, -ctk/-ctv q8_0, tg128, 1 rep/round to preserve interleaving against system-state drift -- the same paired-interleaved discipline RD54's own correction established as necessary).

**Result**: native mean 72.511 t/s, replay mean 72.598 t/s -- net +0.12%, indistinguishable from noise (per-round deltas: +0.03%, +0.51%, +0.51%, -0.11%, -0.20%, -0.11%, +0.14%, +0.20%, alternating sign, no trend).

**Conclusion**: RD54's K=256 candidate's 60.7% isolated-kernel speedup is real (HI105 already confirmed this via CPU-reference correctness) but the down-projection MUL_MAT_ID op it targets is a small enough fraction of total per-token decode compute that the end-to-end production effect is negligible -- not a regression, not a meaningful win. This is the correct, methodologically clean closing answer for RD54 at the full-model level: the tooling gap HI105 fixed was real and worth fixing (it unblocks correctness-gated promotion for every future MUL_MAT_ID candidate), but this particular candidate does not move production throughput.

## RESULT (2026-08-24, dev-gpt-agent session ses_05a713a4e4e44b2d + independent implementation and real-hardware verification)

**Disposition: IMPLEMENTED AND VALIDATED on real hardware. RD54's K=256 candidate is now PROMOTED.**

### Real scope correction found during implementation
Only one of RD54's two signatures is actually MUL_MAT_ID. K=256 (down projection) is op=30=MUL_MAT_ID, confirmed via load_ggml_op_names against the real vendored source. K=2048 (RD54's other real signature) is op=100=GLU -- a real, distinct fused activation node with its own test-backend-ops class (test_glu), not MUL_MAT_ID, despite carrying the same has_ids/n_expert canonical fields. This HI105 slice correctly, deliberately does NOT cover it (matches HI80's own doctrine: derive from that op's own test_case subclass first, never assume from shared flags). GLU-fused MUL_MAT_ID correctness evidence is a real, separate future item.

### Implementation (5 commits: f78eb2d, 8265ba4, 7f2e04c, df211d0, 5dcd6d7)
1. Fixed a real, independent safety-gate bug found along the way: correctness_evidence.py's run_test_backend_ops() set GGML_HIP_FORCE_CANDIDATE for the candidate run but never GGML_HIP_FORCE_CANDIDATE_STRICT (dispatch.cu's own comment names this exact file as the reason STRICT exists).
2. New patch 1236: test_generic_op's GGML_OP_MUL_MAT_ID initializer gets a deterministic, FULL-expert-range shuffle under BIGCHERRY_TEST_DETERMINISTIC_SEED (the pre-existing code was both non-deterministic across processes -- random_device, not seeded -- AND confined to a {0..n_expert_used-1} range, never the real full expert pool). Emits its own BIGCHERRY_REF_DIGEST for the ids tensor.
3. New signature_to_mul_mat_id_test_file_line() in signature_correctness_mapping.py: shape identity derived from src/llama-graph.cpp's build_moe_ffn (real production MoE code), verified against RD54's real signature. as/b taken literally from the recorded ne0/ne1 (no broadcast-flag branching needed), ids=(n_expert_used,ned[2],1,1) type I32 (resolved from the parsed type table, not hardcoded), nb=[0,0,0,0] on every source (ggml's own 'default contiguous strides' convention -- no Q8_0 block-layout math needed in Python).
4. New signature_to_any_test_file_line() dispatcher: hi80_generate_correctness_evidence.py was found (dev-gpt-agent review) to still call the MUL_MAT-only mapper unconditionally, silently SKIPPING every real MUL_MAT_ID row without incrementing the failure count -- a run could exit 0 having generated no evidence at all. Fixed by routing through the dispatcher.
5. Fixed a second real gap (dev-gpt-agent review): the MUL_MAT_ID mapper originally reused 'leaf_0' (weights) as its digest tensor, same as plain MUL_MAT -- but weights/activations already have a proven deterministic guarantee from patch 1222; the NEW risk MUL_MAT_ID introduces is expert routing. Changed to 'leaf_2' (the ids tensor). This was flagged as an extrapolation needing real-hardware confirmation (HI80's own leaf_0 convention was verified only for the 2-source MUL_MAT case) -- confirmed directly below.

### Real-hardware verification (Brutus, build_plan_id=288f2e79cd2ab3ed91c559eba73e3772, experiment.hi105-correctness = patches 1222+1223+1236)

**leaf_2 assumption confirmed empirically, not just extrapolated**: ran the real generated test-file line for RD54's K=256 signature directly. BIGCHERRY_REF_DIGEST lines: leaf_0 nels=134217728 (matches as: 256*2048*256), leaf_1 nels=2048 (matches b), leaf_2 nels=8 (matches ids: n_expert_used=8) -- leaf_2 is genuinely the ids tensor, confirmed by its element count alone, no guessing required.

**Real CPU-reference correctness test passed on real hardware**: MUL_MAT_ID(type=f32,ne=[2048,8,1,1],...,sources=q8_0[256,2048,256,1],f32[256,8,1,1],i32[8,1,1,1]) -- both ROCm0 and ROCm1 backends: OK, err=9.4e-15 / 9.3e-15 (both wells under threshold=5e-4), 3/3 backends passed.

**Real HI80 CLI run** against RD54's actual measurements.jsonl: K=256's row (dispatch=64e9cd56cca4afbadd254ace2640b595) -> `wrote evidence_id=1 (dispatchable, e_c=9.87848e-15)`. K=2048/GLU and the plain-quantized-MUL_MAT rows correctly SKIPPED (out of scope, as designed).

**Real tune-promote rerun**: promoted=1 (up from 0/5 before this item). K=256's row: `promotion_status=promoted`, winner=mmvq:q8_0:w1:nw1:rpb2:sk0:v1 (same candidate RD54 measured), statistics unchanged and still airtight (bh_accepted=True, p_value=0.0, 95% CI 60.68-60.88%). K=2048/GLU correctly remains `rejected_no_correctness_evidence` (out of scope, needs its own future item).
