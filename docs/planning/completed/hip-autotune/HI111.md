# Correctness-evidence MUL_MAT mapper rejected all quantized types (Q8_0/Q4_K/Q6_K/...) -- fixed via zero-strides sentinel

## Description

HI109 (real dense Qwen3.8-27B/Q8_0 production tune campaign, 2026-08-24 Brutus): `signature_to_test_file_line()` in tools/bigcherry/signature_correctness_mapping.py hand-computed test-backend-ops' `nb` byte strides from a `{F32, F16, BF16}`-only type-size whitelist, raising SignatureMappingError for every quantized signature. On this real Q8_0-quantized production model that meant almost none of the 113 real tuning hypotheses could get correctness evidence (only 4/113 before the fix -- everything else non-quantized/incidental).

Root cause was fixable, not fundamental: `signature_to_mul_mat_id_test_file_line()` (the HI105 MUL_MAT_ID sibling) had already solved the identical problem by serializing src0/src1 with `nb=[0,0,0,0]` -- test-backend-ops' own "use default contiguous strides" sentinel (`is_non_contiguous()`'s `nb[0]==0` check) -- letting ggml itself derive the correct block-aware layout for any type, quantized or not. That trick was never carried back to the plain-MUL_MAT mapper.

## Steps

1. Remove `_TEST_FILE_TYPE_SIZES` whitelist and `_contiguous_byte_strides()` from signature_to_test_file_line().
2. Always emit `nb=[0,0,0,0]` for src0/src1, matching the MUL_MAT_ID path.
3. Update/replace the unit test that asserted quantized types raise (`test_test_file_line_rejects_a_quantized_type`) with one confirming Q8_0 now maps cleanly.
4. Verify end-to-end on real Brutus hardware against the HI109 campaign's real measurements (105/113 hypotheses got evidence after the fix, up from 4/113; tune-promote went from 1 to 70 promoted candidates).
