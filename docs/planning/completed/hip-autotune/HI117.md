# Production critical-path attribution: why do real kernel-level wins vanish end-to-end (rocprofv3 campaign)

## Description

dev-gpt-agent prioritization review (2026-08-24/25, req_b851acae89e64e78), given four independent real null end-to-end results today (HI105 MoE dispatch tuning, HI109 Q8_0 dispatch tuning, HI114 RD07/RD08 Q6_K kernel patches, HI116 Q6_K dispatch tuning): the open question is no longer 'can BigCherry find faster kernels' (yes, up to 65% in isolation, correctness-verified) but 'where does the measured saving disappear between isolated candidate timing and real serving wall time'. Recommendation: stop starting new kernel/candidate tuning work; run a bounded real-hardware profiling campaign to attribute this before choosing the next lever.

GPT's framing: HI35's impact.py computes call-count x isolated-median-time per signature (a compositional model); kernel_fraction.py measures actual production GPU time from rocprof traces with correct cross-device/queue overlap handling, but its published ceiling is from dense 27B Q8_0 on R9700, not the dual-XTX configs tested today. That gap between the compositional model and real profiled time is exactly what today's null results exposed -- do not repeat HI107's calls x isolated-time audit pattern; measure the real delta inside actual production execution instead.

## Steps

1. Use the existing RD07 Q6_K stock-vs-patched pair (HI114, both legs bypass BigCherry's dispatch layer entirely -- cleanest isolation, since the externally-verified kernel win still vanished end-to-end even without any dispatch-layer involvement) as the primary profiling target. Run the exact same production server-bench workload under rocprofv3 for both legs.
2. Compare, for both legs: E2E wall/throughput; GPU-busy union over both XTXs; aggregate MMQ/MMVQ/BLAS/attention/copy/reduction kernel time; specifically the affected Q6_K MMQ kernels (calls, total time, median/distribution, launch geometry); per-GPU busy time/imbalance/overlap; impact.py's predicted saving vs the actual observed production-family reduction.
3. Secondarily, profile the HI116 Q6_K replay/native pair the same way -- useful because that A/B already ran at full real production settings (-c 256316, prompt cache, MTP) with a null result, ruling out HI113's (now-closed, corrected) VRAM-workaround story as an explanation.
4. The result forks decisively into one of five diagnoses (per GPT): (a) Q6_K MMQ production time doesn't actually fall -- isolated/tune microbench timing isn't representative of live serving, fix measurement fidelity first; (b) MMQ time falls but GPU busy/wall doesn't -- kernel isn't on the critical path, overlap hides the saving; (c) GPU busy falls but wall doesn't -- CPU/sync/scheduling/MTP-orchestration/request-handling/communication dominates; (d) wall falls under the profiler but tokens/sec stays noisy -- the effect is real but the current E2E harness lacks statistical resolution; (e) MMQ is genuinely a large critical-path fraction and still doesn't compose -- investigate graph-capture/cache-state/launch-sequencing specifically.
5. Do NOT modify tuner behavior as part of this item -- attribution only. The diagnosis determines which item to pick up next (RD30 if MoE empty-work is material, HI26 if dense-prefill repeated packing is material, HI18/HI88 only if communication/sync dominates, or a measurement-fidelity fix to the tuning harness itself).
