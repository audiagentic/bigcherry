# HI54: restore the exact MMQ workspace declaration (J_max + MoE routing buffers)

## Description

Real code regression, confirmed by direct comparison (not assumed from the addendum doc). Current ggml_hip_mmq_workspace() in hip-autotune-dispatch.cu is the known-incomplete formula: `k_padded` activation term only, missing the J_max activation-padding term and, on the MUL_MAT_ID/MoE path, three id-routing buffers entirely (zero MoE workspace accounting at all). The pre-reset version at commit 2c2fe7c has the exact fix, with its own comment documenting the corpus evidence that matches the addendum's numbers exactly: 269/310 cases under-declared, median 1.11x, worst 554x gap. Rederived directly from mmq.cu's real allocations (dense: lines 158-159; MUL_MAT_ID: lines 209-228), not fitted to ratios.

## Detailed Solution & Technical Design

Exact recovery, all dependencies confirmed present in current tree: ggml_cuda_mmq_get_J_max exists at vendor/llama.cpp/ggml/src/ggml-cuda/mmq.cuh:360 and is called from mmq.cu:159/228 with the same signature the recovered function expects; n_expert/n_expert_used/GGML_HIP_SIG_HAS_IDS all already exist in current hip-autotune-types.h. This is a pure drop-in of the 2c2fe7c function body -- no reconciliation needed, current dispatch.cu's surrounding code (ggml_hip_mmf_can_execute etc, the device-cc-read pattern) is unchanged since 2c2fe7c.

Deliberately NOT adding: the stream-k fixup buffer term. 2c2fe7c's own comment (preserved above the function) explains why -- every row in RDNA2/RDNA3/RDNA3.5/RDNA4 MMQ config tables has stream_k=false and the launcher gates that path NVIDIA-only, so it is unreachable dead code on this project's AMD targets. Do not "improve" the recovered fix by adding it.
