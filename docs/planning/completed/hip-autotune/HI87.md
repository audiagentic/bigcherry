# Warm-cache-first dispatch: skip native_select() on guaranteed cache hits

## Description

Captured from critical assessment of an external design document ("BigCherry Replay and RCCL Tuning Architecture", pasted into chat 2026-08-23, not independently authored -- treated as an idea source, not a spec) against BigCherry's real current dispatch code. This is the one part of that document verified directly against source before writing this item (see Detailed Solution) -- explicitly NOT yet implemented, backlog only.

Current confirmed behavior (src/ggml/src/ggml-cuda/hip-autotune-dispatch.cu): ggml_hip_dispatch_mul_mat() calls ggml_hip_native_select() unconditionally at line ~900-901, BEFORE ggml_hip_dispatch_resolve() is ever invoked (line ~925-926). Inside resolve(), the thread-local 8-entry cache check (g_thread_bindings.find, line ~495-496) and the process-global g_bindings cache check (line ~590-593) both run strictly AFTER native_select() has already executed and its result was passed in as a parameter. So on every single dispatch -- including a guaranteed warm-cache hit that will just return the cached binding -- native_select() still runs first and its result is thrown away. The document's proposed fix: add a cheap warm-cache lookup (by signature+hardware digest) BEFORE calling native_select() at all, and only fall through to native_select() on an actual cache miss.

## Detailed Solution & Technical Design

Document's proposed shape (unverified beyond the ordering claim above, which IS verified): an L0/L1/L2 hierarchy -- L0 a thread_local last-binding single-comparison fast path, L1 the existing 8-entry TLS ThreadBindingCache, L2 the existing process-global g_bindings map -- checked in that cheap-to-expensive order BEFORE native_select() runs, with native_select() only invoked on a genuine miss through all three. This is a re-ordering / early-exit optimization on top of caches that already exist (g_thread_bindings, g_bindings) -- it does not require new cache structures for L1/L2, only restructuring ggml_hip_dispatch_mul_mat()'s call order so the cheap lookup happens first. An L0 single-slot fast path would be new.

Open question needing real measurement before committing to this: how expensive is native_select() actually? If it's a handful of cheap comparisons against tensor metadata already in hand, this reorder may save little; if it does real work (shape analysis, capability probing), the saving could be meaningful on the hot decode-loop path where the same signature repeats every token. Profile before implementing, not just from claimed motivation.

**Design conversation**: per explicit user direction, this item's design was worked through with dev-gpt-agent via the agents gateway before any code was written (requests req_9d78359cc3ed4f14 and req_07fe302621724ea6, session ses_55680d7c75d7483c then ses_9395e0cfd4ad4b54 -- the gateway session silently rotated mid-investigation, each request was self-contained enough that this didn't lose context). GPT independently proposed the same two-gate measurement plan I had already started forming from source reading: (1) confirm L1 dominance in a real repeated-dispatch scenario via HI92's counters, (2) if that clears, get sampled cycle-level cost data (not per-call chrono, which would dominate what it measures) comparing native_select() against the L1 lookup it runs ahead of, and only prototype if the estimated per-token cost exceeds ~1% of real decode latency.

**Gate 1 -- real measurement**: `test-backend-ops perf -o MUL_MAT` on real gfx1100 hardware (184 distinct shapes, each run thousands of times -- one shape 9918 runs, another 7011, etc; 110,020 total dispatches). `GGML_HIP_DISPATCH_COUNTERS=1`: `entries=110020 native_select=110020 L1 hit=109836 miss=184 (99.8%)`. native_select() ran unconditionally on every one of 110,020 dispatches; 109,836 of those results were guaranteed-thrown-away L1 hits. Gate 1 clears cleanly -- the reorder's premise (native_select() runs before a warm cache is even checked) is real.

**Gate 2 -- sampled timing**: added `GGML_HIP_NATIVE_SELECT_TIMING=1`, an opt-in sampled diagnostic (1-in-128 calls, independent std::chrono::steady_clock samples) comparing native_select()'s cost against the L1 lookup's. First attempt had a real, self-caught bug: both call sites shared ONE sample-tick counter; since the two sites are always visited in the same relative order within a dispatch, the shared counter's parity locked one site to even ticks and the other to odd ticks -- an even modulus check (`tick % 128 == 0`) could then mathematically never fire for the odd-parity site, and L1 silently sampled n=0 (not "rare" -- provably impossible). Fixed with two independent atomic tick counters, reran. Real corrected result over the same 110,020-dispatch sweep: **native_select() mean=193.6ns (n=860) vs L1-hit-lookup mean=52.6ns (n=860)** -- native_select() really is ~3.7x costlier than the L1 lookup, confirming the reorder's premise is directionally true, just at a tiny absolute scale.

**Decision**: avoidable time per guaranteed-skippable dispatch is native_select()'s own 193.6ns. Using a generous 150-dispatches/token estimate (upper bound for a real dense/MoE decode step): 150 x 193.6ns = 29.0us/token, against this project's own measured production baseline (~93-109 t/s steady-state decode, ~9.2-10.8ms/token) = **~0.29% of token time**; a more realistic 50-dispatch estimate gives ~0.10%. Both land at or below the agreed <0.25-1% "close it" threshold, and real factors push the true number lower still: (1) this is CPU-side dispatch overhead in an async GPU launch pipeline -- plausibly partly hidden behind GPU kernel execution rather than sitting on the wall-clock critical path at all; (2) the 193.6ns sample already includes some steady_clock call overhead, so it's closer to a conservative ceiling than an exact intrinsic cost; (3) HI93 (already landed) eliminated the one other per-dispatch cost that WAS meaningfully expensive (hardware key/digest rebuild), so native_select()+L1 scan is close to the floor of what this hot path can cost now.

**Correctness/complexity argument (found independently, not from the design doc)**: `native.candidate` is a REQUIRED fallback in the replay-mode (L3) revalidation path -- both the exact-match-but-transform-invalid case and the can_execute/arch-eligibility revalidation case fall back to `native.candidate`/`native.variant` even after a lookup already ran. "Skip native_select() on any cache hit" is therefore only safe for L1/L2, never uniformly across all three cache levels -- real branching complexity added to a hot path every dense matmul dispatch goes through, for a sub-0.3% theoretical ceiling.

**Kept, not discarded**: the sampled timing diagnostic was initially written as throwaway scratch code, but per explicit user direction not to dismiss real working measurement tooling just because an LLM (gpt-dev-agent) agreed with closing the item, it was kept as a permanent, opt-in, zero-cost-when-disabled diagnostic (renamed from the throwaway `Hi87Timing`/`GGML_HIP_HI87_TIMING` naming to a permanent `NativeSelectTiming`/`GGML_HIP_NATIVE_SELECT_TIMING` convention, matching HI92's `GGML_HIP_DISPATCH_COUNTERS` pattern) rather than reverted. This directly serves the reopen condition below without needing to be rebuilt from scratch. 9 new source-contract tests (tools/tests/test_native_select_timing.py), including one that mechanically catches the exact shared-counter parity bug this investigation hit. Full offline suite: 1785 passed (up from 1776), 3 skipped, 61 subtests.

**Reopen condition** (agreed with gpt-dev-agent, not an arbitrary cutoff): a future workload where real end-to-end profiling -- not theoretical CPU-time arithmetic -- shows this dispatch path consuming >=1% of actual decode wall time. `GGML_HIP_NATIVE_SELECT_TIMING=1` plus `GGML_HIP_DISPATCH_COUNTERS=1` together are the tool to re-run that check.
