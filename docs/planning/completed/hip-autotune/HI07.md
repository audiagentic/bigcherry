# Implement MMVF forced block-size variant dispatch

## Description

Patch 5 — extract the existing MMVF block-size switch (32..256 in steps of 32) into a forced block-size launcher. Native path computes block_size_best; tune/replay passes a forced value. Eligibility checks: block size multiple of wave size, shared memory fits, precision semantics unchanged.

For F16 source type, accumulator mode (F32 vs F16) is a valid performance variant dimension — each candidate encodes its accumulator mode. Other types use F32 only.

## Steps

- Extract block-size switch into template `launch_mmvf_block(..., int block_size)` — valid values are exactly `range(32, 257, 32)`: 32, 64, 96, ..., 256
- Implement ggml_cuda_mmvf_variant_is_eligible() with block size, wave size, shared memory, width, fusion checks
- Native path computes block_size_best then calls same launcher
- For F16: enumerate both F32 and F16 accumulator modes as separate candidates
- For other types (F32, BF16): F32 accumulator only

## Notes

### Design revision -- explicit parameter, not a hidden override

An earlier implementation passed the forced value through a file-scope
thread-local, because threading a parameter through the dispatcher chain looked
like the larger diff. That was wrong, and the reason only shows up in
production.

A `replay-full` binary would read that override on **every** launch of the
family, and in production it is always the "no override" value. The native path
would be paying, on the hottest path in the system, for a feature only the tuner
uses. Since tuning and production are separate binaries by design (standards
9.1), production should carry none of it.

The forced value is therefore an **explicit, appended, defaulted parameter**:

```cpp
void launch_...(..., cudaStream_t stream, int forced_value = 0);
```

Appending and defaulting is what keeps the diff small -- every call site not on
the forced path compiles unchanged. Only the calls a forced value actually
travels through are updated, and repetitive forwarding is done with a single
`replace_all` edit whose match count is asserted, so upstream adding a case
fails loudly rather than leaving the patch half-applied.

**Consequence for testing.** With a hidden override, native and forced were
literally the same code, so "forced with the native value gives identical
output" was structurally guaranteed. With an explicit parameter the forced path
is separate code, and that property becomes something HI16 must actually check.
It was always a specified test; it is now load-bearing.


### Review update

Follow the HI06 shape exactly -- it is proven:

1. lift the switch into `launch_mmvf_forced_block<T, type_acc, ncols_dst>(..., int block_size)`;
2. lift `block_size_best` into a pure function;
3. reduce the original to those two calls.

Do **not** write a parallel forced path. One launcher is what makes forced
equal to native by construction.

**Accumulator mode is a template parameter, not an argument.** `type_acc` is
`half` or `float` at `mul_mat_vec_f_cuda` level, above the block-size switch.
Forcing it means selecting the branch that calls
`mul_mat_vec_f_cuda_switch_ncols_dst<T, half>` versus `<T, float>` -- so the
forced entry point takes `forced_acc_f16` and applies it at that outer level,
not inside the block-size launcher. Standards 3.1 still applies: an F16
accumulator against a request that did not ask for reduced precision is a
different operation and must be rejected by `can_execute`, which is already
implemented in `ggml_hip_mmvf_can_execute`.

**Block sizes are wave-size relative.** Upstream iterates
`block_size = 2*warp_size; block_size <= max_block_size; block_size += warp_size`
and caps at 128 for pre-RDNA1 AMD. The switch cases (32..256 step 32) assume
wave32. On CDNA (wave64) the reachable set differs, so eligibility must check
`block_size % warp_size == 0`, not merely membership of the switch.
