# CMAKE_HIP_FLAGS does not propagate to compile commands on Windows Ninja+Clang HIP builds

## Description

Found while validating patch 1002_hip_unsafe_math_opt_in: CMAKE_HIP_FLAGS-based options (GGML_HIP_UNSAFE_MATH, and the pre-existing GGML_HIP_EXPORT_METRICS -- same mechanism, same gap) set the CMake cache variable correctly but the flag never reaches the actual per-file compile command on Windows (`ninja -t commands` shows no trace of it, tested both -funsafe-math-optimizations and -Rpass-analysis=kernel-resource-usage). Confirmed working correctly on Linux/Brutus (same cmake invocation, same patch, flag present in the real compile command when ON). Likely a Windows-Ninja-generator-specific CMake HIP-language quirk (CMAKE_HIP_FLAGS may need to route through CMAKE_HIP_FLAGS_INIT or a per-target COMPILE_OPTIONS on this generator instead). Low urgency (Windows is a dev workstation platform, not where BigCherry ships) but means any CMAKE_HIP_FLAGS-gated option is silently a no-op on Windows today.

## Notes

Filed 2026-08-21/22 during patch-validation campaign work (see ledger). Verified via direct `ninja -t commands` inspection, not just CMakeCache.txt (which shows the variable correctly, masking the real gap).

CLOSED 2026-08-23. Root cause found by reading the actual source (not guessed), independently cross-checked against dev-gpt-agent (gateway request req_8acb7c7f51384d64, session ses_55680d7c75d7483c) which converged on the same mechanism from first principles: `vendor/llama.cpp/ggml/src/ggml-hip/CMakeLists.txt` forces `CXX_IS_HIPCC TRUE` unconditionally on Windows (its own comment: "CMake on Windows doesn't support the HIP language yet"), so `enable_language(HIP)` is NEVER called on Windows. Every ROCm source file's LANGUAGE property is then set to CXX, not HIP -- the `LANGUAGE HIP` branch only runs on Linux. `CMAKE_HIP_FLAGS` only feeds CMake's HIP-*language* compile rule, so on Windows it is a complete no-op: correctly cached in CMakeCache.txt, never consulted by the CXX rule that actually compiles these files. This is a straightforward "flag set on the wrong CMake language variable for the language actually in effect" bug, not an exotic Ninja/response-file/generator quirk.

Fix: patches/1232_hi81_windows_cxx_hipcc_flags_reach_compile.py, inserted into the CXX_IS_HIPCC branch right after the existing Windows-Debug COMPILE_FLAGS workaround. Appends the same two flags (GGML_HIP_EXPORT_METRICS's -Rpass-analysis=..., GGML_HIP_UNSAFE_MATH's -funsafe-math-optimizations) to the ROCm sources' real CXX COMPILE_FLAGS via `set_property(... APPEND_STRING ...)`, which composes with (rather than clobbers) the pre-existing Debug-only `PROPERTIES COMPILE_FLAGS "-O2 -g"` line immediately above. On Linux CXX_IS_HIPCC is false, so this block is inert there and the existing CMAKE_HIP_FLAGS path -- already confirmed working on Linux/Brutus -- remains the only one that fires.

Real hardware validation on gfx1100 (ROCm 7.1, Ninja, clang.exe/clang++.exe): fresh cmake configure + `ninja -t commands ggml-hip`, ON vs OFF:
- `-DGGML_HIP_UNSAFE_MATH=ON`: `-funsafe-math-optimizations` now present in the real per-file HIP compile line (was absent before this patch, confirmed both ways).
- default (OFF): flag correctly absent -- proves the gate itself works, not just "always append".
- `cmake --build ... --target ggml-hip` succeeds cleanly with the flag ON (only pre-existing unrelated sign-compare warnings; ggml-hip.dll links).

Side finding folded into TO01: `bigcherry apply --force`'s two-pass writer (patcher.apply_all) only commits ANY anchored patch to disk if EVERY selected patch's in-memory trial succeeds -- a single failing patch anywhere in the selection blocks the whole selection's disk write, not just its own file. A full unscoped --force run currently always includes patches/1207 (RD17) failing against patches/1205 (RD12) by documented, intentional design (HI91: two mutually-exclusive rdna-boosts experiments, never selected together by any real recipe) -- so a full-catalog --force apply silently writes NOTHING for any anchored patch, including this one, unless scoped with --groups/--states/--recipe to exclude the conflicting pair. This session's own validation only landed on disk via `apply --force --groups core`. Previous sessions' "my target file synced despite the FAIL" observations were only ever true for src/-overlay-copied files (unconditional copy, not gated by the patch trial pass) -- anchored patches to existing upstream files were never actually verified landing under a failing full-catalog apply. Not a new bug to fix (the all-or-nothing write is a deliberate atomicity property, and RD17/RD12's conflict is intentional per HI91) -- just an important operational fact: always scope apply --force when validating an anchored patch against a catalog with a known intentional conflict in it.
