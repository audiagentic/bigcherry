# Resolve bindings at graph-node lifetime -- the dispatch lookup may not need to run at all

## Description

dev-gpt-agent (req_7bd85f40d3334469) names this the point it would investigate hardest, and it challenges the premise of every other optimisation in this area: 'if bindings are actually invariant over a reusable graph variant, optimizing an 8-entry per-dispatch lookup is optimizing machinery that should not execute at all.'

For a reusable graph node whose types, extents, strides, fusion semantics, device and replay generation are all fixed, the resolved Binding is invariant across launches. The evidence that this is the common case is already in hand: a single 27B MTP bench run logs graphs reused = 3086, and presents only 86 distinct signatures across 199,242 dispatches -- roughly 2,300 dispatches per distinct signature.

If the binding were resolved once per graph node and stored in execution metadata, then every launch would skip native_select, make_signature, the L1 lookup, the L2 lookup and the persistent digest entirely.

That is a different order of saving from anything else under consideration. HI158's deferral removes ~38.6 ms per run; this removes the entire lookup path from ~199,000 of ~199,242 dispatches.

## Steps

1. Confirm the invariance conditions hold for the graph-node lifetime actually used here, including how replay generation changes and when the cache is reloaded.
2. Identify where a resolved Binding can be stored in graph/node execution metadata with explicit invalidation.
3. Prototype for one family, measured against the current path.
4. Only then consider widening.
