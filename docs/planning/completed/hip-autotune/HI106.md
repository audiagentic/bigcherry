# Correctness-evidence CLI must use a test-backend-ops binary built from the SAME inventory as the tune run

## Description

During a broader real MoE tune campaign on Qwen3.6-35B-A3B (built on top of HI105's now-working MUL_MAT_ID correctness-evidence path), hi80_generate_correctness_evidence.py caught two real, non-MoE candidates that fail CPU-reference correctness on all 3 deterministic seeds while native succeeds cleanly on the same seeds -- a genuine dispatch/kernel bug, not a tooling gap. Both are plain MUL_MAT (op=29, no HAS_IDS flag), F32 source type, mmvf family:

- dispatch=5e47944021eb0874c452b3f9d5e7a11b: ne0=[256,256,1,1], ne1=[256,8,1,1], winner candidate `mmvf:f32:w8:bs32:accf32:v1` -- FAILED: seed=1 native=ok candidate=failed, seed=2 native=ok candidate=failed, seed=3 native=ok candidate=failed.
- dispatch=ec467f813954eb15319491db6abd47ca: ne0=[2048,512,1,1], ne1=[2048,1,1,1], winner candidate `mmvf:f32:w1:bs160:accf32:v1` -- same failure pattern (all 3 seeds candidate=failed, native=ok).

tune-promote correctly rejected both (promotion_status=rejected_no_correctness_evidence), so this never reached production replay -- the correctness gate did exactly its job. But the underlying mmvf F32 candidates themselves (w8:bs32:accf32 and w1:bs160:accf32 configurations specifically) appear to be genuinely broken on real hardware (RDNA3, dual RX 7900 XTX) and need root-causing: is it a real numerical/launch bug in those specific warp-count/block-size mmvf variants, or a test-harness issue specific to F32 MUL_MAT under BIGCHERRY_TEST_DETERMINISTIC_SEED? Either way it needs investigation, not just silent rejection.

## CORRECTION (2026-08-24, same day): not a real kernel/correctness bug -- a stale-binary process gap in my own harness

Reproduced both failures standalone (direct run_test_backend_ops calls, full stdout/stderr captured, not just the aggregated CLI's terse FAILED line). Real root cause, from the actual candidate-run stderr:

```
hip-autotune-dispatch.cu:531: bigcherry: GGML_HIP_FORCE_CANDIDATE=mmvf:f32:w8:bs32:accf32:v1 not found in registry (GGML_HIP_FORCE_CANDIDATE_STRICT=1 -- failing closed instead of silently falling back to normal resolution)
```

The test-backend-ops binary I originally used for correctness-evidence generation (build_plan_id=288f2e79cd2ab3ed91c559eba73e3772) was built for the ORIGINAL RD54/HI105 K=256 correctness experiment, with its own narrower compiled candidate registry. It never had `mmvf:f32:w8:bs32:accf32:v1` or `mmvf:f32:w1:bs160:accf32:v1` in its registry at all -- those candidates only exist in the NEW campaign's inventory-scoped tune build. GGML_HIP_FORCE_CANDIDATE_STRICT correctly aborted (SIGABRT, exit -6) rather than silently falling back -- this is the safety mechanism working exactly as designed (see correctness_evidence.py's own HI105 comment on why STRICT exists). The 'FAILED: one or more seeds did not execute cleanly' aggregation message was accurate but the underlying cause was never a numerical/kernel bug -- it was reusing a stale, mis-scoped binary.

**Fix applied and verified**: rebuilt test-backend-ops via `bigcherry build --lane bigcherry:tune:linux-multi --experiment hi105-correctness --inventory <the campaign's own moe_inventory.json>` (build_plan_id=64360c9672de2750cbaea477e6e92a28) -- this compiles in BOTH the HI105 correctness-harness patches (1222+1223+1236) AND the full candidate registry matching the actual tune run's inventory. Re-ran both previously-failing candidates directly against this binary: both now return exit 0, 3/3 backends OK, real low correctness error (same order of magnitude as the other passing MUL_MAT_ID rows). No candidate/kernel bug exists.

**Real, generalizable finding for HI80/hi80_generate_correctness_evidence.py**: the CLI's `--binary` must always be built from the SAME `--inventory` file as the tune run being evidenced, not an arbitrary previously-built test-backend-ops binary. There is currently no validation of this -- a caller (like this session, the first time) can silently pass a binary whose candidate registry doesn't cover the measurements being evidenced, and every affected row will FAIL for a reason that looks like a real correctness bug but is actually a scope mismatch. Retitled this item to track that real, still-open tooling gap: either the CLI should verify the binary's compiled candidate registry covers every candidate name it's about to force (failing closed with a clear 'registry mismatch' error distinct from a real correctness FAILED), or the build step should be made an explicit, enforced part of the correctness-evidence workflow rather than left to the caller to get right by convention.

No real kernel bug found. HI105's broader-campaign promoted-winners result stands unaffected -- those 3 promotions used a correctly-scoped binary from the start (the original 288f2e79 binary's registry did happen to cover the MUL_MAT_ID candidates, since that's what it was built for).
