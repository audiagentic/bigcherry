# Replay hot-path instrumentation: L0/L1/L2 hit-rate and native-selector-call counters

## Description

Carved out of HI87 as an independently implementable first slice (RP1 in the source document's own staged breakdown -- 'BigCherry Replay and RCCL Tuning Architecture', assessed 2026-08-23). Pure diagnostic instrumentation, zero behavior change: add counters for dispatch calls, thread-local (L1) cache hits, process-global (L2) cache hits, replay-DB (L3) lookups/misses, native-selector invocations, and hardware/signature digest constructions.

This is the natural, low-risk first move because HI87 itself is explicitly blocked on real measurement: 'how expensive is native_select() actually? ... Profile before implementing, not just from claimed motivation.' This item answers that question directly, and can ship on its own regardless of whether HI87's reorder is ever pursued -- the counters are useful diagnostic infrastructure independent of any hot-path change.

## Steps

- Add opt-in counters (env-gated, matching this codebase's existing GGML_HIP_*_TRACE convention -- zero cost when disabled) at: dispatch entry, L1 TLS cache hit/miss (g_thread_bindings), L2 process-global cache hit/miss (g_bindings), replay-DB (L3) exact-match lookup/miss, native-selector (ggml_hip_native_select) invocation, hardware-key/hardware-digest construction, signature-digest construction.
- Emit a summary report (counts + rates) on process exit or on demand, matching the source document's example report shape (dispatches / L1 hits / L2 hits / L3 lookups / native selector calls / digest builds).
- Run on a real workload (the dual-XTX production recipe already used throughout HI14/HI64/HI90 this session) to get real numbers: what fraction of dispatches are warm L1/L2 hits, and what does native_select() actually cost relative to a warm lookup.

CLOSED 2026-08-23. Implemented opt-in counters (GGML_HIP_DISPATCH_COUNTERS=1, zero-cost when unset -- every fetch_add is guarded by a check-once atomic-bool enabled flag, matching GGML_HIP_TUNE_TRACE_ATTEMPTS' existing pattern) at every site the item's own steps named: dispatch entry, native-selector invocation (instrumented once inside ggml_hip_native_select() itself, capturing every call regardless of which of the three public dispatch entry points reached it), hardware-key/signature-digest construction, L1 (thread-local) hit/miss, L2 (process-global) hit/miss, L3 (replay-DB) lookup/hit.

**Real bug found and fixed during real-hardware validation**: the report was originally wired via `std::atexit()`, which does not reliably fire in this codebase's real shutdown path -- a real GGML_HIP_DISPATCH_COUNTERS=1 run produced no report at all. Found the actual working pattern by tracing how the existing 'dispatch coverage' report (which DOES print reliably) triggers: an explicit call inside `ggml_hip_autotune_flush()`, not atexit. Switched to the same explicit hook; confirmed firing on the next real run.

**Real hardware validation** (local AMD Radeon RX 7900 GRE, gfx1100, vendor/rocm/7.1): a native-mode run correctly showed all-zero counters (matching the existing 'dispatch coverage -- 0 dispatched' line for the same run -- native mode bypasses the resolver entirely, so zero is the CORRECT answer, not a bug). A tune-mode run showed sensible, internally-consistent numbers: `entries=2 native_select=2 hw_key_builds=1 sig_digest_builds=1 L1 hit=1 miss=1 (50.0%) L2 hit=0 miss=1 (0.0%) L3 lookups=0 hits=0 (0.0%)` -- exactly the expected shape (hardware key/signature digest built once and reused via the L1 cache on the second dispatch; L1 cold-then-warm; L2/L3 untouched since tune mode never reaches them).

13 new source-contract tests, including one that mechanically scans every `fetch_add` call site and asserts a `dispatch_counters_enabled()` guard precedes it within 200 chars -- catches an unguarded increment class of bug directly rather than trusting a manual review. Full offline suite: 1769 passed (up from 1756 at session point).

This is now the real measurement HI87 needs before its native-selector reorder can be justified -- HI87 should consult a real production workload run through these counters rather than re-deriving the question from scratch.
