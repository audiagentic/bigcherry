**Real, verified blocker on Brutus today**: `perf --version` fails -- "perf not found for kernel 7.0.13-070013" -- the installed /usr/bin/perf wrapper has no matching /usr/lib/linux-tools/<kernel>/perf. Brutus runs a non-distro-standard kernel string, so `apt install linux-tools-generic` will NOT fix this (gpt's assessment: no archive candidate likely exists for this exact kernel version).

**Real fix options** (either closes this item):
1. Build perf from source matching the exact running kernel: clone linux kernel source at the matching tag/version, `make -C tools/perf`, install the built binary as e.g. `/usr/local/bin/perf-<kernel-version>`, point profile-campaign's `[profiling.cpu] perf = "..."` config at it.
2. Move Brutus to a distro-supported kernel with a real matching `linux-tools-$(uname -r)` package -- cleaner long-term but a real infra change outside this plan's scope.

**perf_event_paranoid correction (important, verified via gpt pushback)**: do NOT lower `/proc/sys/kernel/perf_event_paranoid` (currently 2) as a blanket fix -- gpt corrected an initial overcautious assumption here. Per kernel docs, paranoid>=2 already permits per-process, user-space-only monitoring (`perf record -e cpu-clock:u -- <our-process>`), which is exactly what profile-campaign needs. Preflight should PROBE capability directly (`perf record -q -e cpu-clock:u -o /tmp/probe.data -- sleep 0.1`) rather than infer failure from the sysctl value alone. Only reach for CAP_PERFMON or a lower sysctl if kernel-level/system-wide counters are needed later -- not for this use case.

**Design once perf is available** (from the gpt negotiation, ready to implement without further design work):
- `perf record -F 199 -e cpu-clock:u --call-graph dwarf,16384 -o <dir>/perf.data -- <server invocation>` (199 Hz chosen over higher rates: a 60s active interval yields ~12k samples/thread, enough resolution without excessive DWARF-unwind overhead).
- `perf script` + `perf report --stdio --children` for normalized output; report as `symbol,dso,self_samples,inclusive_samples,self_pct,inclusive_pct,estimated_on_cpu_ms` -- explicitly NOT labeled as exact call counts (perf is sampling-based).
- `--profile-passes 2` (not statistical repetition) -- checks pass-to-pass call-stack-distribution reproducibility, not throughput power; profiled runs are diagnostic-only and never compared directly against unprofiled control throughput.
- Never run perf and rocprofv3 simultaneously -- their observer effects would become inseparable; profile-campaign already runs them as separate, interleaved-with-controls passes (see HI132).
- perf's default process/thread inheritance (no `--no-inherit`) correctly covers llama-server's worker/RCCL threads for our real dual-GPU tensor-split topology (one process, multiple HIP devices) -- confirmed sufficient, no extra flags needed for multi-GPU coverage on the CPU side (rocprofv3 remains solely authoritative for the GPU-agent/queue side).
- Escalation only, not default: Callgrind (Valgrind) for exact call counts on bounded CPU-only microbenchmarks when perf's sampling isn't precise enough -- never the normal server campaign (20-50x overhead).

**Acceptance**: profile-campaign's CPU stage currently reports `cpu_profile: unavailable` (HI132's real, honest degraded-mode behavthe today). Closing this item means: perf usable on Brutus (via either fix option above), `tools/bigcherry/profiling/perf.py` implemented per the design above, wired into workflow.py's existing (already-built) interleaved-control stage sequence, and validated against a real target question (the CPU-sampler-serialization gap) with real hardware evidence.
