## Validation

DONE (already implemented, found 2026-08-25, then corrected per dev-gpt-agent deep review): this item's real intent -- map a HIP device to a real GPU telemetry source and capture clock/temp/power with absent-not-zero semantics -- was already fully built under HI60 (src/ggml/src/ggml-cuda/hip-autotune-smi.cpp/.h, corrected citation -- HI52 is an unrelated MMQ workspace item), not under this item's own ID. Uses dlopen'd librocm_smi64.so.1 rather than raw /sys/bus/pci parsing (a deliberate, documented design deviation -- degrades cleanly to valid=false on Windows/library-absent hosts; if librocm_smi64 is genuinely unavailable on a Linux host that still has readable /sys/.../hwmon, telemetry is unavailable, a real but accepted narrower coverage envelope than literal sysfs parsing).

CORRECTION (2026-08-25, dev-gpt-agent deep review): the initial closure claim that absent-not-zero was fully satisfied was WRONG. The struct-level `valid` flag only proves device IDENTITY resolved -- it did not guarantee any individual metric (clock/temp/power/busy) was actually read; an RSMI call can fail independently per metric (e.g. power unsupported on this ASIC while clocks read fine) while `valid` stays true, and the old code serialized that failed metric as a plain numeric 0 -- indistinguishable from a genuine reading, exactly the ambiguity the struct's own header docstring claimed could not happen.

Fixed for real: added a `*_valid` bool per metric (sclk/mclk/edge_temp/junction_temp/power/busy) to ggml_hip_device_state, set independently from each RSMI call's real return code (hip-autotune-smi.cpp), and changed device_state_json() (hip-autotune-tuner.cu) to serialize an invalid metric as JSON `null` instead of a numeric default. Also hardened the two existing clock-drift-falsification `sclk_mhz==0` checks to require `sclk_valid`/`mclk_valid` too (defensive, keeps the old zero-check as a fallback). Added tools/tests/test_dispatch_safety.py::test_device_capture_does_not_emit_zero_for_a_single_failed_metric pinning the new fields/helpers/null behavior; full offline suite green (2061 passed, 2 pre-existing unrelated failures -- RA01 legacy-digest baseline + Windows symlink-privilege quirk -- both documented, neither touched by this change).

Real-hardware validation on Brutus (bc-build-hi64hi14, incremental ninja rebuild of ggml-hip succeeded cleanly): direct probes calling ggml_hip_query_device_state() and device_state_json() confirmed the EXACT real failure mode this fix targets -- on real hardware, socket_power_uw's RSMI call genuinely fails (power_valid=0) while sclk/mclk/edge_temp/busy all succeed independently (sclk_valid=1 sclk_mhz=1, mclk_valid=1 mclk_mhz=96, edge_temp_valid=1 edge_temp_mc=30000, busy_valid=1 busy_percent=0), and the JSON serializer correctly emits `"socket_power_uw":null` (previously would have been the indistinguishable-from-real `"socket_power_uw":0`).
