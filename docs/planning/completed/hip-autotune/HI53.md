# MMVQ native-wrapper eligibility crash on MoE MUL_MAT_ID (ne12 > MMVQ_MAX_BATCH_SIZE)

## Description

The root cause is now resolved. The pinned upstream MMVQ launch asserts `!ids || ne12 <= MMVQ_MAX_BATCH_SIZE`; for `MUL_MAT_ID`, the canonical expert-batch dimension is `sig.ned[2]`. Forced MMVQ rejects multi-token IDs when `sig.ned[2] > 1`, and native-wrapper eligibility applies the pinned architecture/type-specific `get_mmvq_mmid_max_batch(type, cc)` limit before returning the native wrapper. The prior `sig.ned[1]` wording was incorrect and has been removed.

- [x] Reproduce the q8_0 `MUL_MAT_ID` path against stock/native Brutus builds: 75/75 passed on gfx1030, gfx1100, and gfx1201.
- [x] Run the bounded tune matrix on gfx1030, gfx1100, and gfx1201: 75/75 passed on each with zero measurement failures.
- [x] Run the exact deduplicated boundary set `{ne12=1, L_arch, 8, 9}` for q8_0 `MUL_MAT_ID` on gfx1030, gfx1100, and gfx1201, reusing valid 8/9 artifacts where available.
- [x] Run one complete real gpt-oss-20B Q6 MoE tune request on each architecture through the formerly failing `MUL_MAT_ID` path.
- [x] Record selected family, native-MMVQ eligibility, forced-MMVQ eligibility contract, measurement status, and assertion-free completion for every boundary row.

## Detailed Solution & Technical Design

The diagnosis is resolved rather than hypothetical. `sig.ned[2]` is the expert batch for `MUL_MAT_ID`; `sig.ned[1]` is not the upstream `ne12` safety boundary. Native selection and native-wrapper eligibility now use the same pinned architecture/type-specific selector. The forced path remains fail-closed for multi-token IDs before geometry or launch. The runtime acceptance matrix is q8_0 with `ne12=1`, `L_arch`, `8`, and `9`, deduplicated when the limit equals a requested value. The global `MMVQ_MAX_BATCH_SIZE=8` is not the complete rule: q8_0 on gfx1201 has `L_arch=7`.
