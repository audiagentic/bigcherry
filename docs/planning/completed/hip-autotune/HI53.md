# MMVQ native-wrapper eligibility crash on MoE MUL_MAT_ID (ne12 > MMVQ_MAX_BATCH_SIZE)

## Description

Discovered while hardware-validating [[HI52]] (HI54 MMQ workspace fix) on a MoE model (gpt-oss-20B). Server crashes with `GGML_ASSERT(!ids || ne12 <= MMVQ_MAX_BATCH_SIZE) failed` in vendor/llama.cpp/ggml/src/ggml-cuda/mmvq.cu:1337 on the very first completion request under GGML_HIP_DISPATCH_MODE=tune.

Root cause (found by inspection): ggml_hip_mmvq_can_execute in hip-autotune-dispatch.cu has an explicit guard for the FORCED-candidate path -- `if ((sig.flags & GGML_HIP_SIG_HAS_IDS) != 0 && sig.ned[1] > 1) return false;` (blocks multi-token MUL_MAT_ID from a forced MMVQ candidate, with a comment explaining exactly this abort is what it exists to prevent) -- but the NATIVE-WRAPPER branch a few lines above it (`if (self->source_class == GGML_HIP_SOURCE_NATIVE_WRAPPER) return true;`) returns eligible unconditionally, before that check runs. So native selection itself can pick MMVQ for a MoE signature whose actual ne12 exceeds MMVQ_MAX_BATCH_SIZE, and the launch aborts.

## Detailed Solution & Technical Design

Not yet investigated in depth -- this item exists to capture the crash and root-cause hypothesis before the trail goes cold, not as a finished diagnosis. Open questions: (1) is `sig.ned[1] > 1` actually the same condition as `ne12 > MMVQ_MAX_BATCH_SIZE`, or are these two different dimensions that happen to usually correlate -- if they're not equivalent, the forced-candidate guard itself may be insufficient for some shapes even where it does run; (2) why does the native-wrapper branch skip this check entirely -- was it ever meant to (native selection is supposed to mirror upstream's own choice, which presumably wouldn't select an out-of-bounds MMVQ path, so maybe the actual bug is upstream's own native-selection heuristic disagreeing with what mmvq.cu will accept, in a shape bigcherry's dispatch layer is exposing rather than causing); (3) whether this is a bigcherry-only regression or reproduces on a stock/native build too (would clarify whether this is bigcherry's dispatch-layer bug or an upstream one bigcherry merely surfaces by routing through tune mode).

## Validation

HI53 is closed on fresh Brutus evidence from source/build revision `121c967`. The ignored vendor test matrix was temporarily extended with exact q8_0 MUL_MAT_ID rows `n=8` and `n=9` (canonical `ned[2]=8/9`), both `bigcherry-native` and `bigcherry-tune` were rebuilt, and the vendor test source was restored afterward. Native and tune runs each passed 2/2 on gfx1030 (HIP_VISIBLE_DEVICES=3), gfx1100 (device 0), and gfx1201 (device 2), with no assertion, ROCm/HSA, illegal-memory, launch, or measurement failure.

The durable tune records were written to the three Brutus measurement/journal pairs `/tmp/hi53-gfx1030-boundary.jsonl.measurements.jsonl`, `/tmp/hi53-gfx1100-boundary.jsonl.measurements.jsonl`, and `/tmp/hi53-gfx1201-boundary.jsonl.measurements.jsonl`, with parser-clean journals alongside them. Exact rows: gfx1030 q8_0 limit 8 — `ned[2]=8` native MMVQ eligible and winner (`eligible=2`, `measured=2`, `measurement_failure=false`), `ned[2]=9` native MMQ winner (`eligible=1`, `measured=1`); gfx1100 q8_0 limit 8 — the same results; gfx1201 q8_0 limit 7 — `ned[2]=8` and `ned[2]=9` native MMVQ ineligible and native MMQ winner (`eligible=1`, `measured=1` for each). The limits are the pinned upstream `get_mmvq_mmid_max_batch(q8_0, cc)` results from `mmvq.cu`; the global `MMVQ_MAX_BATCH_SIZE=8` is not sufficient for RDNA4 q8_0.

Forced MMVQ eligibility remains fail-closed for multi-token `MUL_MAT_ID` through the static contract `sig.ned[2] > 1`, and the focused HI53 source suite passes 5/5. The full offline suite passes 492 tests plus 4 subtests.
