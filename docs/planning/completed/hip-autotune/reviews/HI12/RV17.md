# GGML_CUDA_FORCE_MMQ is a no-op for q8_0 on RDNA3, and the tuner correctly subsumes it

## Notes

Both benchmark scripts wrote to the same log path, so the second run overwrote the first; the table above is reconstructed from the two runs' captured task output and was corrected after the overwrite was noticed. Builds: ~/bc-build-rccl (dispatch, RCCL) and ~/bc-build-forcemmq (plain, RCCL, FORCE_MMQ).

## Findings

Question raised by the owner: does compiling with MMQ improve short token generation, and is that something the tuner should uncover, since forcing MMQ only reassesses priority ordering?

**The reasoning is correct.** `GGML_CUDA_FORCE_MMQ` is a pure policy flag — a bare `return true` inside `ggml_cuda_should_use_mmq` (mmq.cu:403). It does not change what is compiled; MMQ instantiations come from the config tables. So it only re-prioritises families, which is exactly what measured dispatch does per signature rather than by a global compile-time switch. bigcherry's CMake already rejects the flag alongside measured dispatch (standards 4.3) on the grounds that it would *hide* the non-MMQ families and hand the tuner a truncated candidate set.

The obvious way the tuner could be cheating was checked and it is not: `ggml_hip_blas_launch` calls `ggml_cuda_mul_mat_cublas_dispatch`, upstream's whole dense path *including* dequantisation, and `ggml_hip_blas_workspace` accounts for dequantised src0 plus converted src1. MMQ and BLAS are compared like with like.

**Measured, and the flag does nothing here.** Plain RCCL build against plain RCCL plus `FORCE_MMQ`, identical settings (`-c 229376`, dual XTX `-sm tensor -ts 1,1`, draft-mtp n_max 5, q8_0 draft KV):

| | plain RCCL | + FORCE_MMQ |
| --- | --- | --- |
| pp256 | 693.7 | 692.3 |
| pp512 | 966.3 | 966.3 |
| pp1024 | 1031.7 | 1029.2 |
| pp2048 | 1180.7 | 1178.9 |
| pp4096 | 1254.8 | 1256.5 |
| tg128 | 89.5 | 88.5 |
| tg256 | 90.3 | 90.0 |
| tg512 | **89.8** | 82.6 |
| tg2048 | **91.2** | 81.0 |

Prefill and short generation are identical within noise. Long generation is *lower* with the flag, though tg512 and tg2048 carry standard deviations of 10 to 15, so that is suggestive rather than established.

**Why it is a no-op is the useful part.** Reading the AMD branch of `ggml_cuda_should_use_mmq`: the type switch caps MMQ only for Q2_K (`ne11 <= 128`), Q6_K (`<= 128` on RDNA3.0) and IQ2_XS/IQ2_S, and everything else hits `default: return true`. The target model is **q8_0**, which falls straight through. **MMQ is already the default choice for this type on this architecture**, so forcing it changes nothing. The flag exists for cases the RDNA3 q8_0 path never reaches — principally NVIDIA, where fp16 tensor cores make cuBLAS competitive and the function has a dedicated branch.

## Conclusion

`FORCE_MMQ` is not the explanation for the remaining tg128 gap against the production lane (89.5 here against 112.7 there). That residual must come from elsewhere — the lane's different upstream revision (b10227 against this tree's 22dc605) is the leading candidate, and the `hip-mmq` in its name evidently refers to something other than this flag.

Three things worth carrying forward:

1. **The tuner does subsume this class of decision**, and the premise behind that is sound: policy flags re-prioritise, measured dispatch re-prioritises from evidence per signature. Nothing here contradicts that.
2. **It also explains why `blas:native` wins signatures without that being a failure.** Where the tuner picks BLAS it has measured BLAS as faster on that shape, having timed the full dequantise-and-multiply path. Upstream would have picked MMQ for q8_0 by default, so those are cases where the tuner is *disagreeing with upstream on evidence* — which is the entire point of the layer.
3. **A negative result worth keeping.** Anyone reaching for `FORCE_MMQ` on RDNA3 with q8_0 should know it does nothing, and that it is forbidden with measured dispatch for a good reason.
