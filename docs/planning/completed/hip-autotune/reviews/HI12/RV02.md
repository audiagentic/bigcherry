# ggml_hip_family_can_serve admitted MMQ types upstream does not support

## Notes

Reproduce: build workload-max for gfx1100, then GGML_HIP_DISPATCH_MODE=tune GGML_HIP_TUNE_SCREEN_SAMPLES=1 GGML_HIP_TUNE_FINAL_SAMPLES=1 ./test-backend-ops test -o MUL_MAT. Aborts at mmq.cuh:98 after the iq1_s cases.

## Findings

Still open. Found on gfx1100 2026-08-05 after the RV01 (HI09) type-eligibility fix; it is a separate defect that the first fix uncovered rather than caused.

`ggml_hip_family_can_serve` gates MMQ with `ggml_is_quantized(src0)`. That is broader than the set MMQ actually implements. Upstream's `ggml_cuda_should_use_mmq` enumerates the supported types in a switch; quantised types **absent** from it include `IQ1_M`, `TQ1_0`, `TQ2_0`, `Q8_1` and `Q8_K`.

For such a type the family predicate returns true, and `ggml_hip_mmq_can_execute` returns true immediately for the native wrapper (it short-circuits before every other check). The launch then reaches `mmq_get_q8_1_ds_layout`, whose `default:` branch is `GGML_ABORT("fatal error")` — observed as `mmq.cuh:98: fatal error` under `GGML_HIP_DISPATCH_MODE=tune`, immediately after the last `iq1_s` case, i.e. on the first `iq1_m` case.

**Scope: this does not block the target workload.** The Q8_0 27B MTP configuration never produces these types. It blocks a full `test-backend-ops -o MUL_MAT` sweep under tune mode, which is the natural correctness gate for HI12. The run reached 198 tuned signatures with 0 test failures before aborting.

Root cause is the project's own documented anti-pattern: `ggml_is_quantized` is a *restatement* of upstream's support policy, and it has silently disagreed with it.

## Conclusion

**Fixed and verified on gfx1100, 2026-08-05.** Neither Option A nor B as written — a third approach is better than both and is what was implemented.

Rather than extracting or restating upstream's supported-type switch, MMQ support is now *derived by asking upstream's own per-architecture config tables*: `ggml_cuda_mmq_type_is_supported(type, cc, shared_mem_limit)` sweeps J over the same 8..128 bounds `ggml_cuda_mmq_config_is_eligible` uses and returns true if any (J, fallback) resolves to a real config row. Added to `patches/0300_mmq_forced_j.py`, declared in `hip-autotune-dispatch.cuh`, called from the MMQ arm of `ggml_hip_family_can_serve`.

Why this beats both original options: there is no type list anywhere to drift, so a type upstream adds or drops needs no change on our side; and it is architecture-aware, so a type present in upstream's switch but absent from *this* GPU's config table is correctly answered "no" — which the switch-extraction approach would have got wrong. It also sidesteps the trap noted below, since `should_use_mmq`'s performance heuristics are never consulted.

Verified: `iq1_m` now tunes cleanly (`gen/elig/meas 270/3/1, winner mmvq:native:v1`) where it previously aborted at `mmq.cuh:98`; MMQ is correctly excluded from its eligible set. The tune sweep advanced from 198 to 243 signatures with 0 test failures and now clears **every** quantised type — iq1_m, iq2_*, iq3_*, iq4_*, mxfp4, nvfp4, q1_0, q2_0, the K-quants and q8_0 — before reaching the float half. Audit 32/32, patcher tests 12/12.

Scope correction found while fixing: **MMVQ was not affected.** `ggml_cuda_should_use_mmvq` gates on `ggml_is_quantized` exactly as our predicate did, so any type that would abort in MMVQ aborts in upstream too. Only MMQ overreached.

Note for whoever touches `patches/0300`: the patch text changed, so `git checkout ggml/src/ggml-cuda/mmq.cu` is required before re-applying — the idempotence guard otherwise sees its own output and skips, exactly as HANDOFF warns.

The sweep still does not complete, but for an unrelated defect in MMF — see RV03.
