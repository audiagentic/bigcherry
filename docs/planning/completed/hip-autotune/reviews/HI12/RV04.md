# All four families require an F32 activation and none checked it

## Notes



## Findings

Found on gfx1100 2026-08-05, immediately after RV03. Fourth instance of the eligibility-overapproximation pattern.

Every matmul family asserts an F32 src1 on entry and none of the eligibility predicates encoded it:

- `mmvf.cu:673` and `:816` — `GGML_ASSERT(src1->type == GGML_TYPE_F32)`
- `mmf.cu:35`, `mmvq.cu:1320`, `mmq.cu:109` — the same assertion

`ggml_hip_family_can_serve` reasoned only about `src0` (`is_float`, `ggml_is_quantized`) and shape. Upstream never trips these assertions because it routes a non-F32 activation to the dense path long before reaching any family; the dispatch layer selects candidates itself, so it must encode the same precondition and did not.

Observed as `mmvf.cu:673: GGML_ASSERT(src1->type == GGML_TYPE_F32) failed` on an f16×f16 case, after 366 signatures had tuned cleanly.

This one is worth noting as the cheapest of the five to have prevented: it is a documented, hard, uniform precondition stated five times in upstream source, and the predicate simply never looked at `src1_type` — a field the signature has carried all along.

## Conclusion

**Fixed and verified.** One guard in `ggml_hip_family_can_serve`, ahead of the family switch: any family other than BLAS requires `sig.src1_type == GGML_TYPE_F32`. BLAS is exempt because it *is* the dense path that legitimately handles other activation types.

Sweep went 366 → 810 signatures after this fix — the largest single jump of the five, since it unblocked the whole f16/bf16 half of the matrix.
