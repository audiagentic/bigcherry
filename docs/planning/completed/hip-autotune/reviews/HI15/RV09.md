# Replay cache writer built; full tune-to-hot-path chain works end to end

## Notes

Reproduce the whole chain:

```bash
# tune (writes <db>.measurements.jsonl)
GGML_HIP_DISPATCH_MODE=tune GGML_HIP_DISPATCH_DB=/tmp/t.jsonl \
  GGML_HIP_TUNE_SCREEN_SAMPLES=3 GGML_HIP_TUNE_FINAL_SAMPLES=15 \
  GGML_CUDA_DISABLE_GRAPHS=1 <llama-server …>

# export
python3 -m bigcherry.replay_cache /tmp/t.jsonl.measurements.jsonl \
  --manifest artifacts/<rev>/hip-autotune-manifest.json --output dispatch.cache

# replay (needs a GGML_HIP_DISPATCH_REPLAY=ON build from the SAME manifest)
GGML_HIP_DISPATCH_MODE=replay GGML_HIP_DISPATCH_CACHE=dispatch.cache \
  GGML_HIP_DISPATCH_COVERAGE=cov.json GGML_HIP_DISPATCH_MISS_LOG=miss.jsonl \
  <llama-server …>
```

Still open, and unchanged by this work: `replay-full` and `replay-slim` appear in `VARIANT_SETS` and nowhere else, so there is no way to slim a production binary down to just the winning instances. The acceptance test above used a full `workload-max` build, which sidesteps the manifest-hash coupling question entirely — that question becomes live the moment the production build stops being generated from the same manifest as the tuning build.

## Findings

Confirmed by source search 2026-08-05 while trying to close the tune-to-replay loop end to end. Two separate gaps, and the second was found only by looking at the format byte by byte.

### 1. The replay cache has a reader and no writer

`GGML_HIP_REPLAY_MAGIC` (0x59484342) is defined in `hip-autotune-replay.h` and referenced in exactly one place: the validation branch of the loader. Nothing in `src/`, `tools/` or `patches/` ever emits it. The only thing the replay module writes is a miss log.

The pipeline has a hole in the middle:

```
record -> JSONL -> inventory -> generate -> build -> tune -> JSONL measurements
   -> ???  -> replay cache -> replay mode -> production
```

HANDOFF described HI11 as "mostly done -- loader, validation, corrupt-cache fallback verified", which is accurate and easy to misread. The *loader* is done and genuinely well tested: magic, container version, artifact version, both schema versions, manifest hash, truncation, content checksum and string-table bounds are eight distinct rejection paths. The *writer* does not exist, so replay mode has never been exercised against real tuned data, and RV10's 95 measured winners exist only as a JSONL in `/tmp`.

### 2. The entry format could not carry the winners even if a writer existed

A cache entry was laid out as dispatch digest, signature digest, name offset, `primary`, `secondary`, `width`, `acc_f16`, `fallback`, then two reserved bytes named `ENT_SEEDED` that nothing read. `ggml_hip_variant_params` has two further members, and **neither round-tripped**:

- **`small_k`** — every top winner on the real MTP workload is an `sk1` geometry (RV10: `w6:nw4:rpb4:sk1` at 19.65%, `w4` 17.09%, `w5` 19.12%, `w3` 14.18%). Replayed as `sk0` they name a *different compiled instance*, and `(w6,nw4,rpb4,sk0)` is not generated — so the launch would reach the HI09 missing-instance abort, not merely lose the gain.
- **`src0_type`** — added by RV01 this same session, and the serialisation was not extended with it. A replayed candidate would carry type 0 (`GGML_TYPE_F32`) and be rejected by its own family's `can_execute` on every quantised signature, silently falling back to native.

So replay would have failed on exactly the results worth replaying: the `sk1` geometries would abort, and everything else would quietly revert to native. Latent only because nothing has ever written a cache.

## Conclusion

**Both gaps closed, and the chain is verified end to end for the first time.**

### Gap 2 (entry format) — fixed

`ENT_SMALL_K` and `ENT_SRC0_TYPE` now occupy the previously unread reserved bytes and are read into the winner's variant params. `ENT_SIZE` unchanged; no version bump needed since nothing had ever written the format. The entry layout now has **no spare bytes**, so the next field addition needs a version bump and a coordinated writer change.

### Gap 1 (writer) — built

`tools/bigcherry/replay_cache.py` mirrors the loader byte for byte: magic, container/artifact/schema versions, manifest hash, blake2b-16 content checksum personalised `llama-dispatch`, string table, entries.

Three deliberate choices:

- **Python, not C++**, for the same reason record mode is: nothing in the production link path should be able to write this format, and a run killed at hour three still yields a usable cache from what its JSONL flushed. Truncated final lines are tolerated by construction.
- **Refuses rather than skips** a winner absent from the manifest. Skipping would produce a cache that loads cleanly and is quietly worse; a mismatch means the measurements and the manifest came from different generations, which is a build error, not a data quirk.
- **`ggml_type` values parsed from upstream's `ggml.h`**, not restated. The cache stores the type as a byte and a drifted table would repoint every entry at a different type with no error.

Also refactored `variant_fields()` out of `_variant_initialiser` so the writer packs the *same* numbers the registry emits rather than reproducing the mapping. Independent reproduction of that mapping is the root cause of four defects this session.

### Acceptance test — passes

Tuned the real MTP workload (RV10, 95 winners), exported a cache, built a separate `GGML_HIP_DISPATCH_REPLAY=ON` binary from the same manifest, and ran the same workload in replay mode:

```
cache:    6459 bytes, 95 winners, 49 distinct candidates, manifest d64e79c8
coverage: mmvq 12246/12246, mmq 3612/3612, mmvf 52/52, blas 172/172
          total 16082 dispatched / 16082 executed = 100%
misses:   0
```

This is the first time tuning output has ever reached a running inference server. Every prior "replay verified" claim meant the loader rejects bad input correctly.

### **No end-to-end throughput gain was demonstrated, and that matters**

| Mode | pp512 t/s | tg128 t/s |
| --- | --- | --- |
| native (record) | 553.16 ± 18.70 | 67.99 ± 6.92 |
| replay (tuned) | 571.03 ± 18.00 | 65.69 ± 7.74 |

Both differences are inside one standard deviation. The chain works; the benefit does not show at the application level. Do not report this as a speed-up.

RV10 measured 14–20% improvements on individual signatures and those measurements stand — but a per-signature matmul gain only moves tokens per second if the improved signatures are on the critical path and matmul dominates wall time. Neither is established. Three things would settle it:

1. **Repeat runs.** One repetition at ±3% variance cannot resolve a small gain either way.
2. **Hot-signature weighting (standards 7.4).** Weight each signature's improvement by its execution count. The coverage output already gives the counts — mmvq alone executed 12,246 times — so the data exists to compute an expected aggregate gain and compare it against what was observed.
3. **Check what else dominates.** If attention or sampling is the bottleneck at this context length, a matmul win cannot show up regardless.
