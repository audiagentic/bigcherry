## Findings

GPT (req_7310dd3953844f4a, gpt-auto-agent, 2026-08-20T23:01Z) adjudicated both questions. Full verdict text preserved in this review's notes below (too long to summarize losslessly).

Verdict 1 (R computation/keying): ACCEPT WITH REQUIRED HARDENING. test-backend-ops is the correct oracle; do not build a second one. Hard gates: (a) prove -- or patch -- that (source revision, exact test case, seed) produces identical input/reference data across independent processes before trusting two separate invocations as a joint R/N/C measurement; upstream test-backend-ops has history of std::random_device-based init and sporadic MUL_MAT test-data randomness, so this cannot be assumed. (b) emit a reference/input digest per seed so native and candidate rows can assert reference_digest_native == reference_digest_candidate. (c) capture raw NMSE/max-abs numbers, not upstream pass/fail booleans -- may need a small instrumentation patch to test-backend-ops to expose them in machine-readable form. (d) force GGML_HIP_FORCE_CANDIDATE=native explicitly for N, never 'unset'; verify the requested candidate actually dispatched (env var presence is not proof of execution). (e) match the exact signature's test-backend-ops case, not a broad -p corpus filter -- HI70's broad-filter tune-mode invocation is fine for screening, not for production proof.

Verdict 2 (storage shape): ACCEPT DEDICATED SQLITE, REVISE SCHEMA. Six required changes: (1) key on existing build_id/hardware_id/signature_id/candidate_id FKs, not a parallel source_slice_id/architecture/stable-name text-key namespace -- source_slice_id alone is insufficient since one slice can back multiple build plans/manifests; prefer hardware_id over bare architecture (stricter, already the DB's durable hardware-class identity). (2) store per-seed observations (seed, reference_digest, e_n_nmse, e_c_nmse, max_abs_native, max_abs_candidate, native/candidate execution_status) in a child table or canonical seed_results_json, with the parent row storing only derived worst-of-seeds aggregates -- a seeds_json array plus four aggregate numbers cannot prove every declared seed actually ran or that a failed seed wasn't silently dropped. (3) record native_candidate_id/native_stable_name explicitly -- the baseline must not be implicit. (4) contract_version/threshold_t/headroom_fraction on the row are producer-recorded metadata only; promotion must independently know the expected policy and reject evidence whose recorded parameters differ from the currently-required contract -- otherwise a buggy producer can self-authorize by writing a permissive threshold into its own evidence row. (5) adding this table is still schema 5 -> 6, not a free 'additive' change -- schema 5 itself is documented as an additive-table migration and this follows the same discipline. contract_version (not a new table) is the right mechanism for future semantic/policy revisions; a new table is only warranted if the stored STRUCTURE changes (e.g. adding ULP error, a new digest field). (6) promotion must not do 'any historical passing row' lookups (cherry-picking risk across repeated attempts) -- needs either one canonical deterministic seed-set policy per contract version, or the promoted-winner artifact must record which specific correctness-evidence id/digest it relied on, giving replay an auditable proof chain.

Also flagged a real current-code integration gap: execute_promotion_stage()/tune_promotion.promote() today reads ONLY the JSONL measurements artifact; it has no dispatch-DB input at all. HI67 slice 3 must grow the promotion stage boundary to accept a descriptor-verified dispatch_db input alongside measurements, and the promoted-winners artifact's provenance must include both parent artifacts -- tune_promotion.py must not implicitly discover a sqlite path on disk.
