# Candidate src0 type was never checked against the signature — two hardware aborts

## Notes

Files: src/ggml/src/ggml-cuda/hip-autotune-types.h, src/ggml/src/ggml-cuda/hip-autotune-dispatch.cu, tools/bigcherry/autotune_catalog.py.

## Findings

Found on gfx1100 (brutus) on 2026-08-05, the first time HI09's routing was ever compiled and run.

**Every generated candidate names itself for one src0 type in its stable name (`mmvq:q8_0:...`, `mmq:q8_0:...`, `mmf:f32:...`), that type never reached `ggml_hip_variant_params`, and so no `can_execute` could check it.** Every family's launch path dispatches on the *runtime* tensor type and applies the candidate's variant to whatever it finds, so candidates were being ruled eligible for, measured on, and declared winners of signatures of a completely different type.

The per-family `_is_eligible` helpers do not catch this. They are asked whether the *signature's* type is servable, never whether it is the type the candidate claims — so they answer truthfully and uselessly.

Two distinct hardware aborts, both from this one cause:

1. `mmvq.cu:972` — `no compiled MMVQ instance for type=q4_0 width=1 nwarps=1 rows_per_block=1 small_k=0`. MMVQ instances are generated per (type, geometry); the `workload-max` set built from a Q8_0 inventory contains only q8_0 instances, so a q8_0 candidate on a q4_0 matmul finds nothing compiled. This is the HI09 part-1 abort firing correctly — it caught a real registry/instance disagreement, exactly as designed.

2. `mmq.cuh:98` (`NO_DEVICE_CODE`) — an `mmq:q8_0:j16:fb1:t128:o2:i64:sram-q8_0:k256:sk0:v1` candidate **won an iq1_s signature**. MMQ's config table is per type, so `j16` names a different kernel configuration for iq1_s than for q8_0; forcing one type's J onto another asks for an instantiation the table never defined.

MMF/MMVF do not crash, because upstream instantiates every type — which is worse, not better: the winner is recorded under a stable name that misstates the type it ran on, and nothing signals it.

This is the same shape as the MMQ `fallback` bug already recorded in HANDOFF.md (eligibility checking one thing while the launch used another). That fix closed one dimension of a two-dimensional hole.

## Conclusion

Incorporated. `ggml_hip_variant_params` gains `uint8_t src0_type`, taking the last `reserved` byte so the struct size is unchanged (the same precedent `small_k` set). `_variant_initialiser` emits it as the enumerator (`GGML_TYPE_Q8_0`) rather than its value, so an upstream renumbering cannot silently repoint every candidate at a different type; BLAS stays 0 as it has no per-type identity. All four family `can_execute` predicates now reject a type mismatch, with the reasoning recorded at each site.

Verified on gfx1100: abort 1 is gone; forced MMVQ geometries now win real signatures (`mmvq:q8_0:w8:nw1:rpb1:sk0:v1` and five others beat native); the iq1_s signature that previously mis-selected a q8_0 MMQ candidate now correctly selects `mmq:native:v1`, and its eligible-candidate count fell from 7 to 3. 198 signatures tuned cleanly. Registry now types 128 Q8_0 + 136 F32 entries. Audit 32/32, patcher tests 12/12.

A consequence worth stating: an `mmvf:f32` candidate is no longer measured on f16/bf16 signatures, so those shapes now fall back to native unless the inventory generates those types. That is correct, and HI12's coverage report is what surfaces it rather than it being silently mismeasured.

Replay caches need no migration: they validate the manifest hash, which this change alters, so any pre-change cache is rejected rather than misread.
