# Measured on both architectures: MMVQ geometry is worth it on RDNA3 (median 16%) and near-worthless on RDNA4

## Notes

Logs: /tmp/tune-rdna4-samples.log on brutus; C:\bcw\tune-rdna3-samples.log locally. Both at SCREEN_SAMPLES=3 FINAL_SAMPLES=15 on idle GPUs.

The RDNA3 run used the local 7900 GRE (80 CU), not the server's XTX (96 CU). `ggml_hip_hardware_key_v1` includes `compute_units`, so these are different hardware keys and the GRE's winners will not be replayed onto an XTX — the comparison above is valid as evidence about the architecture, but the actual winners for the dual-XTX target still have to be tuned there.

Both runs predate nothing that affects winners: the RV06 mask fix only reclassifies MMF f32 candidates that were already rejected.

## Findings

First tuning run taken under conditions that can support a performance claim: **gfx1201 (RDNA4), idle GPU, `GGML_HIP_TUNE_SCREEN_SAMPLES=3 GGML_HIP_TUNE_FINAL_SAMPLES=15`**, full `test-backend-ops -o MUL_MAT`, 1155 signatures, 0 failures. Every earlier run this session used 1 sample on a contended machine and could not support any performance statement — including my own earlier claim that "the explicit geometry matrix earns its place", which was wrong to make.

1071 native, 83 forced (7.2%). Forced-winner improvements overall: min 1.01%, median 14.40%, p90 38.23%, max 70.39%.

**The result that matters for this item.** MMVQ explicit geometry — 98 generated instances, the great majority of the new compiled code HI09 added — wins **5 of 335 MMVQ signatures (1.5%)**:

Three of the five are ~1%, which 15 final samples can barely resolve from noise.

Meanwhile **MMVF wins 71 signatures at median 16.13% and max 70.39%** — and MMVF candidates are `existing_runtime`: block size and accumulator selection over kernels upstream already instantiates. They required no new compiled code whatsoever. MMQ forced-J wins 3; forced BLAS wins 4.

So on this workload and this architecture, essentially all the measured benefit of the dispatch layer comes from selecting among parameters upstream already compiles, and almost none from the explicit MMVQ geometry matrix.

## Conclusion

**Superseded by the RDNA3 run — the RDNA4-only conclusion below was wrong, and wrong in the direction that would have cost the most.**

The same measurement on the **target architecture** (local idle gfx1100 / 7900 GRE, Windows ROCm 7.1 build, `SCREEN_SAMPLES=3 FINAL_SAMPLES=15`, 1156 signatures, 0 failures):

| Winner | RDNA3 (gfx1100, target) | RDNA4 (gfx1201) |
| --- | --- | --- |
| `mmvq:native` | 326 | 330 |
| `blas:native` | 321 | 323 |
| `mmvf:native` | 184 | 210 |
| `mmq:native` | 176 | 191 |
| `mmvf:f32:*` | 79 | 71 |
| **`mmvq:q8_0:*`** | **24** | **5** |
| `blas:hipblas-auto` | 24 | 4 |
| `mmf:native` | 18 | 17 |
| `mmq:q8_0:*` | 3 | 3 |
| | 103 forced | 83 forced |

**MMVQ explicit geometry on RDNA3: 24 wins, min 1.12%, median 16.18%, max 25.32%, with 20 of the 24 above 10%.** That is not noise and it is not marginal — it is the same order of benefit as MMVF. On RDNA4 the identical code wins 5 times at ~1–5%. The caveat I attached to the RDNA4 result — wrong architecture — turned out to be the whole story, not a hedge.

**HI09 is justified on the hardware it targets.** The earlier reading, that essentially all benefit came from parameters upstream already compiles, holds only on RDNA4.

**The most valuable geometry is a `small_k` one.** `mmvq:q8_0:w1:nw4:rpb4:sk1:v1` alone takes 14 of the 24 wins. `small_k` is precisely the dimension that was present in the stable name and in the generated instances but silently dropped by `_variant_initialiser`, so the registry could name it and had no way to request it (recorded in HANDOFF and fixed before this session). **The single most valuable compiled geometry in the catalog was unreachable until that fix.** Anyone tempted to treat that as a tidy-up should read this line.

Revised priorities, replacing those below:

1. HI09 stays. Do not trim the MMVQ geometry matrix on the strength of RDNA4 numbers, and be wary of any future decision to prune generated instances that is not backed by per-architecture data.
2. MMVF remains strong and cheap (79 wins, median ~16%, no new compiled code).
3. HI17 gains support but less than it first appeared: forced BLAS wins 24 on RDNA3, but at median 1.88% — most are near-trivial, with one at 18.6%. Worth doing for the three hidden choices it exposes, not for the raw win count.
4. Still outstanding and still the real question: record → tune on the actual Q8_0 27B MTP configuration. Both runs here use `test-backend-ops`' synthetic shapes, and the four MTP-relevant facts in HANDOFF (draft widths 1..5, 245k context, tensor split, tight VRAM) are unrepresented. Note the dominant winner is a `w1` geometry, which is the draft-width regime — encouraging, but not evidence.

*Original RDNA4-only conclusion, retained for the record:*

Not a verdict on HI09 — wrong architecture, wrong shapes, margins near the noise floor. What it does establish is that the record → tune cycle on the actual configuration should precede further investment in geometry enumeration; if MMVQ geometry wins as little there as it does here, the 98 generated instances are a large amount of compiled code for very little.
