# Decisive: on the real MTP workload 79% of signatures prefer a forced candidate, dominated by small_k MMVQ at draft widths

## Notes

Measurements at /tmp/tune-mtp-server.jsonl.measurements.jsonl on brutus (4.6 MB). Note `llama-server` installs its own log callback, so `bigcherry: tuned` lines never reach its log — the JSONL is the only record. A grep of the server log shows zero tuning and is misleading.

Throughput during the tuned run: pp512 509.05 t/s, tg128 61.63 t/s, against 553.16 / 67.99 in record mode. The tuning overhead is expected and says nothing about the winners' value.

## Findings

**The measurement RV07 said was still owed.** Tuned the actual target configuration end to end on 2026-08-05: `llama-server` with `--spec-type draft-mtp --spec-draft-n-max 5`, Q8_0 27B MTP, 2× RX 7900 XTX with `-sm tensor -ts 1,1`, `-c 16384`, driven by the bench harness in `server-bench` mode, `SCREEN_SAMPLES=3 FINAL_SAMPLES=15`, `GGML_CUDA_DISABLE_GRAPHS=1` per RV05.

**95 signatures tuned. 75 forced winners against 20 native — 79%.**

For comparison, the same code on synthetic `test-backend-ops` shapes gave 103 forced of 1156 (8.9%) on RDNA3. **The real workload has roughly a nine-fold higher rate of preferring a tuned candidate.** The synthetic sweep did not merely fail to represent this workload; it understated the value of the whole dispatch layer by nearly an order of magnitude.

**Three things this establishes.**

1. **HI09's hypothesis is confirmed on its own terms.** The item was justified by MTP draft widths 1..8 on a 27B model. The dominant winners are `w3`, `w4`, `w5` and `w6` — the draft-width regime produced by `spec_draft_n_max 5` — at 14–20% median improvement. This is the workload it was designed for, and it is where it wins.

2. **`small_k` is the single most valuable dimension in the catalog.** The `nw4:rpb4:sk1` family takes the top three winner slots. Combined with the RDNA3 synthetic result, where `mmvq:q8_0:w1:nw4:rpb4:sk1:v1` alone took 14 of 24 MMVQ wins, `small_k` has now been the standout on two independent workloads. It is also the dimension that `_variant_initialiser` silently dropped, so the registry could name it but never request it. **The highest-value geometry in the project was unreachable until that was fixed** — recorded again because a one-line packing omission cost the best result in the catalog.

3. **Synthetic sweeps must not be used to judge candidate value.** RV07 drew a per-architecture conclusion from `test-backend-ops` and hedged that the real workload was untested. That hedge was load-bearing: the real answer is nine times more favourable and concentrated in a completely different part of the geometry space.

## Conclusion

HI09 is vindicated on the workload that matters. No trimming of the MMVQ geometry matrix should be considered on synthetic evidence.

Follow-ups this opens:

1. **The tuning output cannot be used yet.** There is no replay cache writer (RV09 against HI15), so these 95 winners exist only in `/tmp/tune-mtp-server.jsonl.measurements.jsonl`. Closing that gap is now the highest-value work in the project: the measurement says the winners are worth 14–20% on the hot path, and nothing can consume them.
2. **Re-run at representative context.** This was `-c 16384`, not 245,760. Standards 7.4 hot-signature ranking at 200k will differ, and the target config's attention shapes dominate late in a sequence.
3. **Widen the geometry matrix around `nw4:rpb4:sk1`.** The winners cluster tightly there; the catalog currently enumerates `small_k` only for `nwarps > 1` with `rows_per_block = nwarps`. Whether neighbouring points do better is untested.
4. **136 tolerance rejections** on this workload, against 1581 accepted. Given RV08, worth checking none of those are candidates that would have won.
5. Regenerating from `mtp-server-inventory.json` (240 candidates against the current 270) should be paired with this, since the width coverage differs.
