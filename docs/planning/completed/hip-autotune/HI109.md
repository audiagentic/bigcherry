# Real record->tune->promote->replay campaign on the dense Qwen3.8-27B production model

## Description

Everything measured today (HI105, RD54) used Qwen3.6-35B-A3B, a MoE model, as the investigation vehicle -- and found that MoE-routed matmul (MUL_MAT_ID) candidate tuning does not move production throughput, because MoE routing is too small a compute share to matter for that architecture. The actual production server (per project memory: dual-xtx-27b profile, coder-quality-high llama-swap alias) serves a DENSE model -- Qwen3.8-27B-Q8_0 with MTP speculative decode, dual RX 7900 XTX, -sm tensor -- which has no MoE routing at all. Every MUL_MAT in a dense model's FFN/attention runs on every token; there is no dilution effect. This means a real per-signature win here is far more likely to show up end-to-end than anything found in today's MoE work, and the now-fully-validated tooling chain (correctness-evidence generation, tune-promote, replay build, real interleaved A/B methodology -- all proven working today via HI105/HI106) has never been pointed at this model at all.

HI14 (multi-GPU/graph-capture release-gate item) separately notes it needs a real GGML_HIP_AUTOTUNE_RECORD=ON run against this exact model+flags for its own per-device telemetry evidence -- that record pass can double as this campaign's first stage; do not duplicate the record run if HI14's is still fresh and usable.

## Steps

1. Check HI14 for a usable recent record-mode capture against the real 27B/MTP/dual-XTX production workload before running a new one.
2. If needed, run record mode against the real production launch flags (memory: -sm tensor --tensor-split 1,1 --flash-attn on --ubatch-size 512 --batch-size 2048 -ngl 99 --spec-type draft-mtp --spec-draft-n-max 4 -ctkd/-ctvd q8_0 -c 64000 or the profile default -c 64000, model /mnt/vault/llm-models/qwen3.8-27b/gguf/mtp/Qwen3.8-27B-Q8_0.gguf) to capture the real dense-model signature set -- this will look very different from today's MoE signatures (no has_ids rows at all, likely fewer, larger, more repetitive MUL_MAT shapes given every token hits every FFN weight).
3. Tune-mode measure all real signatures on real hardware.
4. Generate correctness evidence (the now-working MUL_MAT-only path suffices here -- no MUL_MAT_ID exists in a dense model) and run tune-promote.
5. Build a real replay binary and run the SAME interleaved, paired A/B methodology validated today (>=5 rounds, matching production flags, both pp and tg, mtp-dual bench-runner config per project memory's own explicit warning that single-rep numbers are unreliable at this profile: tg512 ranged 61-105 t/s in one prior run) against the existing measured baseline (memory: pp4096 ~1249 t/s, tg2048 ~93-109 t/s with MTP).
6. Report real before/after numbers -- do not assume a win; today's session is exactly the cautionary tale for why this needs to be actually measured, not assumed from isolated kernel deltas.
