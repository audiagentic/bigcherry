# HI121 close-out step 3: mechanical candidate implementation identity (RV84 P0-3)

## Description

RV84 P0-3, confirmed real by dev-gpt-agent's independent investigation (2026-08-26): _candidate_implementation_is_equivalent() is effectively source_candidate == target_candidate on catalog.Candidate.to_dict() fields (stable_name/family/source_class/implementation_version/architectures/config/graph_safe/deterministic). implementation_version is manually maintained at 1 -- there is no mechanically source-derived implementation digest. Two builds with byte-identical descriptors but genuinely DIFFERENT kernel/dispatch implementation source both pass equivalence even though the target implementation was never measured. The existing cross-revision test only changes MARKER.txt and deliberately leaves candidate semantics unchanged, so it never exercises this. Reviewer (both RV84 and dev-gpt-agent) calls this the largest remaining design checkpoint.

## Steps

1. Design a deterministic implementation/source digest that changes when candidate implementation-affecting source/config changes -- likely a content hash over the actual kernel/dispatch source files a candidate's stable_name maps to (patches/rd/*, vendor kernel source, or generated dispatch code), not a manually-bumped :v1 label.
2. Require source/target winner implementation-digest equality (not dictionary equality on metadata fields) for _candidate_implementation_is_equivalent() to return True.
3. Add a real test where source and target candidates have byte-identical descriptors but different underlying kernel source, proving the current dictionary-equality check would have wrongly passed and the new digest-based check correctly rejects.
