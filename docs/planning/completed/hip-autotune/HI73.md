# Workload-shape-aware candidate catalog: skip evidence for candidates a real inventory can never reach

## Description

The candidate catalog (autotune_catalog.py) currently enumerates every candidate a config table structurally allows for a given type/architecture, then demands correctness evidence for all of them (RE15's replay-full gate) -- regardless of whether the specific workload being tuned could ever actually produce the tensor shape or batch width that candidate needs. This is why HI70 needed a separate direct-op corpus (patches/1100_hi70_direct_op_evidence.py): 24 candidates were structurally unreachable from any real single-stream model (MMQ fb1 needs a non-block-aligned dense dimension; MMF needs a [1,16] batch width only speculative decoding produces), and no amount of workload sweeping could ever produce evidence for them.

## Detailed Solution & Technical Design

Originally scoped inside HI70's detailed_solution (now closed) as the deferred, more architecturally complete alternative to the direct-op corpus:

autotune_catalog.py's Inventory class (~L215-263) only tracks observed quant TYPES and widths per family from record.jsonl -> inventory.json -- it discards the actual per-signature shape (ne0/ne1/etc, present in each raw record-mode observation) once it reduces record.jsonl into inventory.json.

To make the replay-full catalog gate only require correctness evidence for candidates a given workload could ever actually reach, generate_inventory/build_inventory (inventory.py) would need to also capture, per family: whether any observed signature had ne01 % 128 != 0 (MMQ fallback applicability, architecture-independent), and per architecture (warp_size varies -- 32 on RDNA4/gfx1201, 64 on older RDNA/CDNA), whether any observed src1_ncols fell in MMF's [1,16] eligibility window. autotune_catalog.py's enumerate_mmq()/enumerate_mmf() would then skip fb1/nwarps-family candidates the inventory proves unreachable, instead of enumerating a superset and later demanding evidence build_manifest() knows can never arrive.

This does NOT replace the direct-op corpus -- HI70's corpus stays as the deliberate, deterministic evidence source for candidates that ARE genuinely reachable in principle but rare in practice (RE15's own HI70 review explicitly recommended keeping it as a first-class evidence source, separate from workload-reachability). This item is about not demanding evidence for candidates that are provably unreachable for a GIVEN workload's own recorded shapes, which would let a workload-scoped replay-full build skip corpus cases it doesn't need, and would make new/unusual future models fail faster and more clearly (an inventory-level 'this candidate is unreachable' message) rather than only being discoverable via a multi-hour real-hardware investigation like HI70's.

### 2026-08-21 IMPLEMENTED — commit b2d2d75

Inventory now records per-type shape reachability from the raw record observations: MMQ fallback applicability from `ne0[1] % 128` (architecture-independent) and the MMF window from the float/f32/even-K/width<=16 eligibility conditions. The restricted catalog profiles skip candidate rows the inventory proves unreachable, with `generate` reporting each skipped row and its reason. Absent or null field means unknown: nothing is skipped (fail-open for reachability, fail-closed for evidence — an unproven-reachable candidate still needs its evidence). Per the item scope, this does NOT replace HI70's direct-op corpus (candidates reachable in principle but rare in practice keep the corpus as their evidence source); this is only the provably-unreachable-for-this-workload case.
