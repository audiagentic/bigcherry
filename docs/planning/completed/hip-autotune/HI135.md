# Unexplained intra-device Rect copy triggered by 6900XT presence in tensor-split topology

## Description

Real, reproducible finding from HI134's investigation (which was scoped to META's reduction path and explicitly excludes this): under -sm tensor with the RDNA2 6900XT (physical device 3) participating in the device group, a same-device (intra-GPU) __amd_rocclr_copyBufferRectAligned copy occurs on the OTHER devices (the RDNA3 XTX pair, ranks 0/1) -- NOT on the 6900XT itself. ~250-258 calls per profiled pass, 2.5-3.4ms mean duration each (up to ~9.5ms p95), ~650ms-860ms total per pass. Decisively established as unrelated to META's reduction transfers: real memory_copy_trace.csv analysis (hi134-stage-attribution-01) shows META's actual FOLD/BUTTERFLY/COPY_BACK transfers are all host-staged HOST_TO_DEVICE/DEVICE_TO_HOST copies (no P2P on this box, per HI84) in the thousands per pass, scaling linearly with the real reduction count -- entirely separate from the 250 DEVICE_TO_DEVICE same-agent (source==destination) copies that match the Rect count exactly.

## Steps

1. Confirmed present: -sm tensor + device 3 (6900XT) anywhere in the group, {0,1,3} and {0,1,2,3} (both HI134 profile-campaign runs).
2. Confirmed absent: {0,1,2} (no 6900XT), and {0,1,3} under -sm layer (never touches comm_ctx/META at all) -- so it requires BOTH tensor-split AND the 6900XT's presence, but the copy itself executes on the XTX devices, not the 6900XT.
3. DONE (2026-09-01, zero new GPU time -- reused hi134-meta-baseline-03's existing rocprofv3 CSVs): correlation-ID attribution. All 516 same-agent DEVICE_TO_DEVICE copies on gpu-1 (matching count on gpu-2) join to `hsa_amd_memory_async_copy_rect`, which joins by timestamp-containment to `hipMemcpy2DAsync`. Real cost: 424.9ms summed on one GPU (823.5us mean x 516 calls) -- ~850ms/pass combined, matching the original 650-860ms/pass estimate.
4. DONE: timing-distribution rules out startup/shard-repacking -- calls span 9.2%-100% of the trace, median 2.9ms gap, recur throughout the whole run.
5. DONE: source-level attribution to `ggml_cuda_cpy()` in ggml/src/ggml-cuda/cpy.cu (~line 460-479), servicing GGML_OP_CPY/GGML_OP_DUP graph nodes. Non-fully-contiguous same-type/same-shape copies take `ggml_cuda_cpy_as_memcpy_2d()`'s 2D-strided `cudaMemcpy2DAsync(..., cudaMemcpyDeviceToDevice, ...)` path -- matches the trace exactly.
6. DONE: ruled out `ggml_backend_cuda_buffer_cpy_tensor()` (ggml-cuda.cu ~862, the buffer-level cross-split relay) -- it uses a flat cudaMemcpyAsync, not 2D, so this is NOT scheduler split-boundary plumbing; it's a real GGML_OP_CPY/DUP node from the model's own compute graph.
7. DONE (2026-09-01): checked kernel_trace.csv for context around a sample copy event. No compute kernels appear on the same Stream_Id near these copies (that stream is copy-dedicated), and widening to ALL streams found the nearest kernels before/after (1.4-1.6ms away in both directions) are ALSO copyBufferRectAligned, not compute -- i.e. these copies cluster in isolated bursts with no concurrent compute activity nearby. Two real implications: (a) this cost is EXPOSED, not hidden under other GPU work -- it directly adds to wall-clock time, not free; (b) the isolated-burst pattern (unrelated to normal per-token kernel activity) suggests this is more likely periodic maintenance/bookkeeping (KV-cache paging, context-checkpoint compaction) than a per-token forward-pass graph op, though this is inference from the pattern, not yet confirmed against source.
8. NOT YET DONE: identify WHICH graph operation/maintenance path this is. Static source reading + trace correlation has reached its useful limit without op/tensor names -- next step needs either a graph dump (op names, not just shapes) or minimal targeted debug instrumentation (temporarily logging op name + contiguity flags at the ggml_cuda_cpy() call site), run against real {0,1,3} vs {0,1,2} configs for a clean A/B. Given finding (7) confirms this is athe periodic/bursty pattern, also worth checking whether it correlates with context-checkpoint/cache-eviction intervals (this project's own --ctx-checkpoints/--checkpoint-min-step flags) rather than every token.
9. Once (8) identifies the op, assess whether avoiding the non-contiguous split (or making backend-sched/graph-build prefer contiguous per-device layouts for heterogeneous groups) is feasible. Priority is now HIGHER given (7) confirmed the cost is fully exposed on the critical path, not hidden.
