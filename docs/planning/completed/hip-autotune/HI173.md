# BLAS-family kernel tuning: authorize and build candidate search for the rocBLAS/Tensile path HI17 made observable

## Description

HI17 (completed) decomposed the opaque BLAS candidate into a controlled, observable execution plan -- the catalog retains blas:native:v1 as the correctness fallback, runtime native-only resolve/apply/execute is implemented, and record-mode telemetry captures effective API/provider/backend, conversions, temporary bytes, calculated workspace, and execution-options state. Critically, HI17's own closure notes are explicit that this was foundational only: "no provider/API alternative or performance promotion was authorized." Today, every BLAS-family dispatch (the Cijk_Alik_Bljk_... rocBLAS/Tensile GEMM kernels visible in real kernel traces) runs through the identical forced-native path regardless of GGML_HIP_DISPATCH_MODE=native vs replay -- BigCherry's tuning/candidate-promotion system has never searched or promoted an alternative BLAS kernel, provider, or compute-type.

This surfaced concretely during HI172's real kernel-trace investigation (2026-09-09): the two largest single-kernel time deltas in an early GPU0 native-vs-replay trace were BOTH rocBLAS/Tensile kernels, present at IDENTICAL call counts in both arms (proving they cannot be a tuning-candidate effect, since BLAS isn't tuned) -- which is exactly the evidence that led to identifying a real measurement-order confound (fixed native-then-replay ordering within each pass, without HI171/TEST.md's own required arm-order rotation) rather than a genuine dispatch-mode effect. That investigation is what prompted this item: BLAS is currently BigCherry's single largest unexplored optimization surface, already has the necessary observability/candidate-identity foundation (HI17), but has zero live candidate search.

Scope for this item: design (and, once designed, implement) an actual BLAS-family candidate search -- alternative rocBLAS/Tensile solution selection, compute_type variants (the existing opt-in GGML_HIP_BLAS_EXPERIMENT=f16_temp per-call route is a precedent, currently manual/experimental only, never evaluated by the tuner), or provider alternatives -- integrated into the SAME promotion/correctness-evidence/behavioral-gate pipeline every other tuning family already goes through (HI67 correctness evidence, HI143 behavioral gate, HTR01 recovery), not a separate ad-hoc mechanism. Given HI17's own explicit warning that this needs "the required same-representative native-versus-forced execution, complete effective telemetry, and quantitative timing-parity gate" before any promotion, and BLAS kernels (rocBLAS/Tensile-generated) are a fundamentally different code surface than BigCherry's own hand-written MMVQ/MMQ candidates (no source-level control over the kernel implementation itself -- candidate selection here means choosing AMONG existing library-provided solutions/algorithms, not authoring new kernel variants), this is architecturally a different kind of tuning problem and should not assume the existing MMVQ/MMQ tuner machinery transfers directly.

## Steps

1. **Corrected 2026-09-09**: build the `vendor_selection` implementation-selector schema as a SEPARATE tagged object (`{backend, api_kind, algorithm_id, arch, vendor_artifact_identity}`) layered alongside HI17's existing seven-field semantic BLAS plan -- do NOT fold it into that plan as an eighth field. `vendor_artifact_identity` binds to the effective linked-library identity (e.g. a content hash), not a bare version string.
2. Build an offline solution-discovery pass that INGESTS rocBLAS's own `rocblas-gemm-tune` output (winning `solution_index` per captured GEMM problem, applied via `ROCBLAS_TENSILE_GEMM_OVERRIDE_PATH`) rather than inventing a parallel discovery/provenance format. Extend RD87's `tools/lab/rd87-hipblaslt-oracle/` methodology only as the shape-capture/dedup front end feeding real problems into `rocblas-gemm-tune` -- not as a replacement for the vendor tool's own tuning pass.
3. Restrict eligibility to signatures whose native EFFECTIVE API has an explicit-solution equivalent (`gemm_ex`/`gemm_batched_ex`/`gemm_strided_batched_ex`) -- "resolves to blas:native family" alone is necessary but not sufficient (see detailed_solution). Pin AND observe the effective backend (rocBLAS may internally dispatch to Tensile or hipBLASLt per `ROCBLAS_USE_HIPBLASLT`) rather than assuming it from provider name.
4. Implement resolve/apply/execute for the new candidate: resolve checks for an exact signature + exact vendor-artifact-identity match; apply dispatches through the MATCHING explicit-solution API for that signature's effective API family (not a single generic call for every eligible signature); execute reuses HI17's shared vendor forwarder. No match -> unchanged forced-native fallback.
5. Add per-solution workspace/resource measurement to the discovery pass, using rocBLAS's own memory-size query/workspace controls -- record allocation source/lifetime, not just byte count, and do not inherit BLAS-1's existing pool-size assumptions.
6. Add the vendor-artifact-identity invalidation check as a hard, fail-closed gate: any mismatch between discovery-time and apply-time effective artifact identity makes the persisted selection unusable, forcing fallback to forced-native (never interpolated/reused across versions or rebuilds).
7. **Corrected promotion gate**: reuse HI17's `abs(delta) <= max(5%, noise)` criterion ONLY as a seam/control gate (proves resolve/apply/execute doesn't perturb execution when no better solution exists). Actual candidate promotion requires positive e2e performance evidence through the SAME pipeline every other tuning family uses (HI67 correctness evidence, HI143 behavioral gate, HTR01 recovery) -- a candidate is promoted because it measurably wins, never merely because it doesn't measurably lose.
8. Re-run numeric/determinism evidence per selected algorithm specifically -- same compute type does not imply identical reduction ordering across different vendor solutions; do not assume HI17's original BLAS-1 correctness pass covers this.
9. Apply the full RD73-precedent downstream-assumption gate before promotion (see validation section): capture-lifecycle validation (cold/warm capture, capture success, replay success, cache-hit/recapture behavior), not just a graph-cache-key spot check, plus paired MTP e2e performance evidence.
10. Offline regression tests: candidate-identity contract (vendor_selection as a separate layer, not a plan-field addition), effective-API-eligibility gating (positive + explicit-solution-API-mismatch rejection), vendor-artifact-identity invalidation (positive + mismatch), resolve/apply/execute seam, workspace accounting.
11. Real-hardware validation: run `rocblas-gemm-tune` against RD87's own shape set (`tools/lab/rd87-hipblaslt-oracle/rd87_comparison.csv`) as the first real discovery-pass input on Brutus.
12. **Required follow-on, not optional**: file/scope a hipBLASLt algorithm-selection slice once the rocBLAS mechanism-proof lands -- rocBLAS-only does not capture RD87's own evidenced hipBLASLt-vs-native headroom (see acceptance_criteria).

## Detailed Solution & Technical Design

**CORRECTED 2026-09-09 after adversarial GPT review (req_1f043f8b4ca94575) found a P0 bug and real gaps in the first draft. This version supersedes the original text below in every particular the review flagged.**

**P0 fix -- the promotion gate was inverted.** The original draft reused HI17's `abs(delta) <= max(5%, native repeatability spread)` criterion as the promotion gate for a tuned candidate. That criterion proves a seam does NOT perturb execution (correct for validating the plumbing itself) -- used as a promotion gate it would REJECT a genuine improvement, including the >5% RD87 wins that motivate this item existing at all. Corrected: that parity criterion is a seam/control gate only (used to prove resolve/apply/execute doesn't silently break anything when no better solution exists). Actual candidate promotion uses the SAME positive-performance/e2e evidence policy every other tuning family already uses (HI67/HI143/HTR01) -- a candidate is promoted because it measurably wins, not merely because it doesn't measurably lose.

**Mechanism, corrected**: a BLAS-family tuned candidate is a persisted vendor-library algorithm/solution selection. Reuse rocBLAS's OWN offline-tuning artifact rather than inventing a parallel discovery/provenance format: `rocblas-gemm-tune` already consumes captured GEMM problems and emits winning `solution_index` values as a CSV, applied via `ROCBLAS_TENSILE_GEMM_OVERRIDE_PATH`. Ingest and preserve that vendor artifact as BigCherry's discovery-pass output instead of building a bespoke one. Direct `*_get_solutions` APIs exist but are current beta APIs in rocBLAS -- put them behind an adapter, don't make them BigCherry's persistent format directly.

**Candidate-identity shape, corrected**: do NOT add `(provider, library_version_triple, solution_index)` as an eighth field bolted onto HI17's seven-field semantic BLAS plan. Keep that seven-field plan intact (it describes WHAT is computed) and add a separate, explicitly-tagged implementation selector: `vendor_selection = {backend, api_kind, algorithm_id, arch, vendor_artifact_identity}`. A bare version-triple is both over-broad (an unrelated hipBLASLt version bump need not invalidate a forced-Tensile winner) and under-specific (a same-version custom rebuild of rocBLAS/Tensile can change the actual kernel library without changing the version string). Bind invalidation to the EFFECTIVE dependency/artifact identity (e.g. a hash of the actual linked library, not just its reported version), with version strings retained only as a diagnostic/cache namespace, not the correctness-binding key itself.

**rocBLAS-only MVP is a good mechanism-proof, but does NOT close the RD87 opportunity -- say so explicitly, do not imply otherwise.** RD87 demonstrated hipBLASLt-vs-native-rocBLAS headroom (up to 2.74x on several real shapes). It did NOT demonstrate comparable headroom AMONG rocBLAS/Tensile solution_index choices -- that's an unverified, separate hypothesis. Keep rocBLAS/Tensile first if the goal is the simplest seam proof, but this item's own acceptance criteria must state plainly that completing the rocBLAS-only slice does not, by itself, capture RD87's evidenced win. A hipBLASLt algorithm-selection slice is a REQUIRED follow-on (see acceptance_criteria), not an optional someday-item. Also: `provider=rocBLAS` is insufficient identity on its own -- current rocBLAS can internally dispatch to either Tensile or hipBLASLt depending on `ROCBLAS_USE_HIPBLASLT`, so a Tensile-solution_index experiment must pin AND observe the effective backend actually used per call, not assume it from the provider name. hipBLASLt has its own separate offline-tuning file/override mechanism (distinct from rocBLAS's), so the provider abstraction in `vendor_selection` must anticipate multiple different vendor artifact shapes, not assume every provider exposes rocBLAS-style solution indices.

**Eligibility boundary, corrected -- "already resolves to blas:native" is necessary but not sufficient.** HI17's BLAS family covers multiple distinct effective APIs (SGEMM, GemmEx, strided-batched, pointer-batched). Applying an explicit `solution_index` via `rocblas_gemm_ex(...)` to a signature whose native effective API is plain SGEMM (or another API without an explicit-solution equivalent) is actually an API-STRATEGY CHANGE, not a solution-selection-only change -- a materially bigger claim than this item's own stated scope. Corrected eligibility: restrict the MVP to calls whose exact effective native API has an explicit-solution equivalent, and dispatch through the MATCHING explicit-solution path (`gemm_ex`/`gemm_batched_ex`/`gemm_strided_batched_ex`) for that specific API family, not a single generic `rocblas_gemm_ex` call for every eligible signature. Persist and re-validate the COMPLETE vendor-call descriptor before every execution, not just the signature: effective backend/API, M/N/K, transposes, lda/ldb/ldc/ldd, batch count/strides, operand/output/compute types, any atomics-relevant flags, and architecture.

**Real risks specific to this candidate family** (distinct from BigCherry's existing MMVQ/MMQ tuner assumptions, which assume BigCherry controls kernel source): (1) solution identity is not guaranteed stable across ROCm/rocBLAS/hipBLASLt releases OR across same-version custom rebuilds -- bind to effective artifact identity, not just reported version, and fail closed (never interpolated/reused) on any mismatch. (2) workspace/temp-buffer sizing varies per solution and per whether rocBLAS is internally managing/reallocating handle workspace -- rocBLAS exposes memory-size query/workspace controls for this; use them rather than assuming BLAS-1's existing pool sizing. (3) Runtime solution enumeration must never happen in the hot path -- discovery is strictly offline, via the vendor's own `rocblas-gemm-tune` artifact ingestion. (4) Same compute type does not imply identical reduction ordering across different solutions -- numeric/determinism evidence must be re-run per selected algorithm, not assumed to carry over from HI17's original BLAS-1 correctness pass.
