# HI121 close-out step 5: source-build-aware multi-generation promotion resolution (RV84 P0-5)

## Description

RV84 P0-5, confirmed real by dev-gpt-agent's independent investigation (2026-08-26): schema 7 intentionally allows the same portable dispatch (D/S/H) to have measurements across MULTIPLE builds -- central to HI121's whole point. But promotion_gate.resolve_promotion_identity() does `SELECT DISTINCT build_id FROM measurement WHERE signature_id=? AND hardware_id=? AND dispatch_digest=?` and requires exactly ONE result -- once two builds (A, B) both have D/S/H measurements, correctness-gate export refuses with ambiguity. The projected artifact ALREADY carries the missing authority in hi121_source_provenance.source_build_id, but the resolver ignores it entirely. As HI121's own database becomes more useful (more history accumulated), this makes MORE builds fail, not fewer -- precisely the opposite of the intended effect.

## Steps

1. Read tools/bigcherry/tuning/promotion_gate.py's resolve_promotion_identity() and how replay.build() calls it.
2. Add an optional source_build_id parameter/input that, when the artifact being resolved carries hi121_source_provenance.source_build_id (i.e. it's a projected artifact), threads that exact build_id into the query (WHERE ... AND build_id = ?) instead of requiring global uniqueness.
3. Non-projected/ordinary measurements keep today's 'must resolve to exactly one build' behavior unchanged -- this is additive, not a relaxation of the existing safety property for the common case.
4. Test scenario (from RV84): build A and B both have measurements for the same D/S/H; project A's measurements into artifact C; A has a non-native promoted winner with valid RV49 evidence; replay.build() against the multi-build DB must resolve A explicitly via the projected artifact's source_build_id, not report ambiguity.
