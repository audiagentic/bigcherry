# Safe partial strengthened ingest -- per-row quarantine of unsupported-domain signatures during production tune-campaign

## Description

Real finding from HI129's live-hardware validation (2026-08-27/28): a real `bigcherry tune-campaign` run against a real model (Qwen0.8B) correctly reached the new HI125 production wiring (dedicated signature-verifier lane built, `require_strengthened_ingest=True` invoked) and correctly HARD-FAILED the whole load with `sc.UnsupportedSignatureDomain: op='ADD' has no audited capability-applicability rule` -- a genuine fused ADD-adjacent dispatch outside HI121's currently-audited domain (MUL_MAT, MUL_MAT_ID, simple/routed GLU only). This is NOT a bug -- it is the deliberately-designed fail-closed behavior working correctly (per the HI125 step-6 design negotiation's explicit policy: 'do not weaken #6 with graceful silent fallback'). But it revealed new operational evidence: a real inference graph routinely dispatches ops outside the audited domain, so today's WHOLE-ARTIFACT all-or-nothing `require_strengthened_ingest` policy may make a fully-successful strengthened production campaign difficult or impossible against many/most real models, since load_measurements() currently invokes the verifier on EVERY result row and aborts the entire transaction on the first unsupported one.

## Steps

1. Add `UnauditedSignatureDomain`/`InvalidSignatureDomain` exception classes; audit and update every current `raise UnsupportedSignatureDomain(...)` call site in signature_capabilities.py to raise the correct specific subtype (valid-but-uncovered ops like ADD/dense-GLU -> Unaudited; malformed/impossible/contradictory evidence -> Invalid).
2. Add `unsupported_signature_policy="error"` parameter to `inventory.load_measurements()`.
3. Update `_resolve_signature()` to catch only `UnauditedSignatureDomain` for quarantine handling (per point 3 above); every other failure mode remains fatal exactly as today.
4. Return per-load `winner_verifications`/`quarantined_unsupported_winners` counts from `load_measurements()`.
5. Wire production workflow.py to pass `unsupported_signature_policy="quarantine"` and enforce `verified_winners > 0` (hard TuneCampaignError otherwise).
6. Factor the exact winner-row-identity resolution logic out of replay_projection.py into a shared location so both projection and same-generation replay can use it.
7. Add `replay.build(require_winner_verification=False)`; wire production's `_stage_replay_export()` to pass `True`; unattested measured rows get omitted, identity mismatches still hard-fail.
8. Tighten replay_projection.py's exception handling per point 6 above (Invalid -> ProjectionError, Unaudited -> unchanged omission).
9. Offline adversarial test coverage required before this can be considered done: mixed audited+ADD load succeeds with one winner_verification row and one quarantined count under quarantine policy; the SAME mixed load still hard-aborts under the default "error" policy (no accidental behavior change for existing callers); a malformed/InvalidSignatureDomain canonical still hard-aborts even under quarantine policy; the existing same-digest/different-canonical disagreement check still fires even for a quarantined row; replay.build(require_winner_verification=True) correctly excludes an unattested winner from the exported cache; a forged/mismatched row passed to replay.build() with require_winner_verification=True still hard-fails; a workflow run that ends with zero verified winners raises TuneCampaignError; every existing caller's default-argument behavior is provably unchanged (regression tests on the pre-HI136 test suite must still pass unmodified).
10. Real-hardware validation: re-run the EXACT SAME Qwen0.8B Brutus campaign that originally surfaced this gap (this is the strongest possible regression witness since it reproduces the real dropout precisely) -- require: verified_winners > 0, quarantined_unsupported_winners > 0, no quarantined dispatch appears in the exported replay cache, a real replay completion succeeds, and the real replay coverage shows exact > 0 / stale=false / rerun_required=0. A second real-hardware run against a genuine MoE model is explicitly NOT required for HI136's own closure (HI125 already separately proved MUL_MAT_ID/routed-GLU verification on real MoE hardware this session) -- the Qwen0.8B mixed-domain run is the decisive one for HI136 specifically.

Converged design (investigation + adversarial GPT design negotiation, 2026-08-27/28):

1. Exception taxonomy split: `UnsupportedSignatureDomain` becomes a base class; add `UnauditedSignatureDomain` (a well-formed, reachable signature with simply no audited applicability rule yet -- e.g. ADD, dense/non-routed GLU) and `InvalidSignatureDomain` (malformed, contradictory, impossible, or stale semantic evidence -- e.g. bad field types, wrong schema epoch, unknown flag bits, impossible MUL_MAT+HAS_IDS combos, contradictory GLU bias/fusion state). Only `UnauditedSignatureDomain` is ever eligible for quarantine; `InvalidSignatureDomain` always remains a hard failure -- this taxonomy split is critical because today's single exception type conflates "legitimately uncovered" with "structurally broken," and blindly quarantining every UnsupportedSignatureDomain would be unsafe.

2. `inventory.load_measurements()` gains a new parameter `unsupported_signature_policy: Literal["error", "quarantine"] = "error"` (default preserves ALL existing behavior exactly -- manual/legacy/offline callers are unaffected). The production tune-campaign workflow explicitly opts into `"quarantine"`.

3. Inside `_resolve_signature()`, the verifier call site catches `UnauditedSignatureDomain` specifically -- if policy is `"error"`, raise `RecordError` as today; if `"quarantine"`, mark that row as quarantined (do NOT return early -- the row still goes through every existing integrity check: same-load `signature_seen_canonical` disagreement, DB canonical comparison, digest parsing, etc. all still apply to quarantined rows exactly as before). A quarantined row is still ingested into SQLite (measurement/winner rows preserved for diagnostics and future HI128 re-attestation once the domain widens) -- it just does not get a `winner_verification` row written.

4. `load_measurements()`'s return dict gains `winner_verifications` (rows that got real HI127 attestation) and `quarantined_unsupported_winners` (rows honestly quarantined). No DB schema migration needed -- absence of `winner_verification` already means "unattested," schema-8 semantics are unchanged.

5. Same-generation `replay.build()` gets `require_winner_verification: bool = False` (default preserves existing behavior for all non-production/manual/legacy callers). When `True`: requires `dispatch_db`; resolves every measured result to its exact winner row (reusing/generalizing the row-binding logic already in `replay_projection.py`'s `_require_row_belongs_to_build()`, moved into a shared location e.g. `verification_state.py`, accepting optional `source_build_id` -- projection supplies it explicitly, same-generation replay passes `None` and requires exactly one matching winner); forged/malformed/ambiguous rows are HARD FAILs; an exact winner lacking current `winner_verification` is simply omitted from export; an exact, verified winner is retained; existing promotion/correctness gates then run on the retained set exactly as today. Production's `_stage_replay_export()` passes `require_winner_verification=True`; all other callers keep the safe default.

6. `replay_projection.py` also uses the new taxonomy: `UnauditedSignatureDomain` still counts as `omitted_unsupported_domain` (unchanged behavior); `InvalidSignatureDomain` becomes a hard `ProjectionError` instead (an attested row that turns out structurally invalid must never be quietly miscategorized as ordinary unsupported coverage).

7. A production campaign ending with ZERO verified winners must NOT report success. `_stage_load_and_promote()` checks `load_measurements()`'s returned `winner_verifications` and raises `TuneCampaignError("strengthened ingest produced zero verified winners")` if it is 0. This belongs at the workflow layer, not inside the generic loader, since offline/import/remediation callers may legitimately want a DB containing only quarantined historical evidence. `WorkflowReceipt` gains `verified_winners`/`quarantined_unsupported_winners` fields (receipt schema bump) so this is durably recorded.
