# Implement MMQ forced-J variant enumeration and dispatch

## Notes

### Design revision -- explicit parameter, not a hidden override

An earlier implementation passed the forced value through a file-scope
thread-local, because threading a parameter through the dispatcher chain looked
like the larger diff. That was wrong, and the reason only shows up in
production.

A `replay-full` binary would read that override on **every** launch of the
family, and in production it is always the "no override" value. The native path
would be paying, on the hottest path in the system, for a feature only the tuner
uses. Since tuning and production are separate binaries by design (standards
9.1), production should carry none of it.

The forced value is therefore an **explicit, appended, defaulted parameter**:

```cpp
void launch_...(..., cudaStream_t stream, int forced_value = 0);
```

Appending and defaulting is what keeps the diff small -- every call site not on
the forced path compiles unchanged. Only the calls a forced value actually
travels through are updated, and repetitive forwarding is done with a single
`replace_all` edit whose match count is asserted, so upstream adding a case
fails loudly rather than leaving the patch half-applied.

**Consequence for testing.** With a hidden override, native and forced were
literally the same code, so "forced with the native value gives identical
output" was structurally guaranteed. With an explicit parameter the forced path
is separate code, and that property becomes something HI16 must actually check.
It was always a specified test; it is now load-bearing.


### Review update (prework pack + real-build findings)

**The J space is the config table, not `range(8, 129, 8)`.** The switch covers
all sixteen values, but `ggml_cuda_mmq_get_config` returns `GGML_TYPE_COUNT`
for combinations the architecture's `CASE` table does not define, and the
native scan skips them. CDNA defines 154 rows to RDNA3's 260, with `q8_0`
stopping at J=64. Enumerating the full range manufactures candidates that abort
inside `launch_mul_mat_q`. See PACK_REVIEW A2.

**`ggml_cuda_mmq_enumerate_variants` is not needed at runtime.** PATCH_MAP
proposes it returning a `std::vector`. The catalog enumerates offline instead,
so the runtime only needs the eligibility predicate -- no allocation on any
dispatch path.

### Implementation status: DONE

`patches/0300_mmq_forced_j.py` -- three anchored edits:

1. `mul_mat_q_launch_forced_J<type, fallback>(..., int J)` -- the switch, lifted.
2. `mul_mat_q_compute_J_best<type, fallback>(args)` -- upstream's scan, lifted.
3. `mul_mat_q_switch_J` becomes those two calls.

Native and forced share one launcher, so forced J = J_best is identical to
native *by construction*, not by testing. Verified: gfx1100 build clean,
1545/1545 `test-backend-ops` MUL_MAT cases pass.
