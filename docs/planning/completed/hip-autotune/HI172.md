# Critical-path/slack vs contention hypothesis for isolated-vs-e2e tuning divergence

## Description

HI171's real e2e matrix (2026-09-08, current source, all 5 HI168 caches) found that isolated per-dispatch-key tuner speedups (5.7%-35% across the five caches, all execution-audit-confirmed as genuinely launching from cache) do NOT reliably translate into real end-to-end serving performance on ANY topology tested: GPU0 shows a real regression (-1.3% pp512, -1.8% pp2048 replay vs native), GPU1 is mixed, GPU2/GPU3/27B are flat/no-measurable-effect despite real isolated wins.

REVISED TAXONOMY (dev-gpt-agent review, 2026-09-08, req_714d201cc4b64f87 -- corrects the original 3-way + inverse framing):

1. DILUTION -- isolated win real, tuned dispatch is a small fraction of total GPU time; nets out to well under 1% overall, invisible against noise. kernel-fraction's family share/wall-clock ceiling tests this directly.

2. OFF-CRITICAL-PATH -- kernel genuinely faster but doesn't gate the next pipeline step (hidden behind/overlapping other work), so wall-clock is unaffected. IMPORTANT CORRECTION (gpt): like dilution, this alone gives ~0 wall benefit, NOT a negative result -- it CANNOT by itself explain GPU0's real regression. GPU0 needs hypothesis 3 or 4 below, not 2.

3. IN-CONTEXT KERNEL REGRESSION (broadened from the original 'contention-dependent' framing -- gpt: proving the replay kernel is genuinely slower in real pipelined context proves isolated-to-in-context reversal, but does NOT by itself prove occupancy/register/LDS contention specifically; other real causes include cache/memory-state effects, DVFS/power-state differences, launch/queue differences, or changed surrounding activity. Must not claim 'contention' as the mechanism without direct concurrency evidence.)

4. SYSTEM/NEIGHBOR EXTERNALITY (NEW, added per gpt review -- the missing mechanism that can produce a negative e2e result while the tuned kernel ITSELF remains faster in context): the tuned kernel stays faster in-context, but its presence makes SURROUNDING kernels slower -- concurrent resource pressure, sequential cache pollution, memory-bandwidth contention, host launch/sync overhead shifts, etc. This is now believed to be the most likely explanation for a genuine negative wall-clock result where the kernel itself measures fine.

INVERSE CASE (kept, but gpt notes traces alone cannot establish it, since an isolated LOSER candidate was never selected/promoted and so never appears in a replay trace to compare): a candidate that measures worse in isolation but is better in real serving by exploiting GPU slack differently. Testing this requires an INTERVENTIONAL counterfactual -- force an isolated runner-up/loser candidate into the cache (GGML_HIP_FORCE_CANDIDATE) and measure real e2e, not passive tracing of what's already promoted. This is exactly the winner-vs-runner-up counterfactual design already discussed for the GPU0/GPU1 cross-swap test earlier in this session -- same mechanism, now formally the way to test hypothesis 4's inverse.

EXCLUDED as a tuning mechanism, kept as a null/confound: measurement/environment drift. HI132 already has interleaved unprofiled controls specifically to detect and flag this (environment_stable=false gate) rather than mistake it for a real effect.

METHOD, PER GPT'S REVIEW: reuse HI132 (bigcherry profile-campaign), which is FULLY IMPLEMENTED and already validated on real hardware (not merely 'pending' as its own plan-item state currently says -- see its own notes: full offline test suite green, a real dual-GPU rocprofv3 run succeeded 2026-08-27 with real kernel data, RCCL capture, and environment-drift detection all confirmed working). Do NOT build an independent profiler.

HOWEVER, gpt identified real gaps between HI132's current top-level `profile-campaign` orchestrator and HI171's exact setup that must be bridged: HI132 launches with runtime_profile.tune_context (not production context), uses its own fixed prompt/96-token completion (not HI171's server-bench pp512/pp2048/tg512 workload), builds its OWN lane rather than directly profiling HI171's already-proven native/replay arms, does not currently inject replay mode/cache into the profiled server, and sets only HIP_VISIBLE_DEVICES (not the newer canonical ROCR/HIP visibility pair, VA22's two-selector-trap fix HI171 itself had to work around earlier this session). CORRECT APPROACH: make HI172 a narrow extension/consumer of HI132's PRIMITIVES (ServerRunner.command_prefix, rocprofv3_command_prefix builder, capture validation, the raw CSV parser, interleaved controls) -- driving the EXACT HI171 native/replay binary+cache+environment+server-bench workload, not HI132's own top-level campaign shape.

GRANULARITY (gpt, corrects the original kernel-fraction-only proposal): family aggregation (kernel_fraction.py's own output) is sufficient ONLY for the dilution test. For causal diagnosis (hypotheses 2/3/4) it is insufficient -- need (a) exact-kernel-symbol statistics (calls/mean/p95/total duration, native vs replay, per exact kernel name -- HI132's own rocprof.py parser ALREADY aggregates per exact Kernel_Name including VGPR/SGPR/scratch, unlike kernel_fraction.py which collapses to family), and (b) raw dispatch rows/timestamps (Queue_Id, Stream_Id, Dispatch_Id, Correlation_Id, grid/workgroup) for overlap/queue/stream/critical-path analysis -- HI132's raw CSV has these columns but its current summary parser discards most of them; may need a thin additional aggregation step reading the raw per-kernel rows HI132's parser already retains.

IMPORTANT CAVEAT (gpt): do not assume a promoted candidate's stable name (e.g. 'mmvq:q8_0:w4:nw8:rpb1:sk0:v1') literally appears in rocprof's device-kernel symbol -- rocprof records the LAUNCHED device kernel, not necessarily the host wrapper name. Must build a VERIFIED promoted-candidate/config -> observed-kernel-symbol(s) mapping from each real trace, not assume a naming match. Also profile the COMPLETE candidate path (e.g. kernel_fraction deliberately includes MMQ activation quantization since the tuned matmul path includes it) -- comparing only one kernel could miss where cost actually moved.

PRIORITIZATION (gpt): profile GPU0's pp2048 workload first -- the largest, cleanest real regression (-1.81%), best signal-per-GPU-hour of anywhere in the whole matrix.

DISCRIMINATOR TABLE (gpt, final):
Exact candidate faster in replay + tiny wall share -> dilution
Exact candidate faster in replay + adequate share, but hidden behind independent gating work -> off-critical-path
Exact candidate SLOWER in replay in-context -> in-context regression
Exact candidate faster in replay but neighbors/system become slower -> externality
No stable repeatable trace/control difference -> unresolved/confounded
