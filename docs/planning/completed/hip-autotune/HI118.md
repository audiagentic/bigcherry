# Capture fused MUL_MAT(_ID)+GLU gate-tensor geometry in the dispatch signature schema

## Description

HI108's investigation (2026-08-25, confirmed by dev-gpt-agent) found that every GLU-op signature this tuner ever records is a fused MUL_MAT(_ID)+GLU epilogue: ggml_hip_dispatch_mul_mat() and ggml_hip_dispatch_family() both call the same ggml_hip_make_signature(src0, src1, ids, dst, fusion) (src/ggml/src/ggml-cuda/hip-autotune-signature.cpp ~line 270), which records only a coarse fusion-kind byte (sig.fusion, from ggml_hip_fusion_kind()) -- it does NOT capture the real gate tensor's shape/type at all. `fusion->gate` is a genuinely separate ggml_tensor* (vendor/llama.cpp/ggml/src/ggml-cuda/common.cuh ~line 1591, struct ggml_cuda_mm_fusion_args_host), so a fused GLU dispatch's recorded ne0/ne1/ned describe only ONE of the two underlying mul_mat_id projections (the x/up side) -- the gate side's geometry is irretrievably absent from every artifact this tuner has ever written for such a dispatch. dev-gpt-agent's explicit warning: do not infer the gate shape from the x side even where models happen to make them equal -- capture it for real.

## Steps

1. Extend ggml_hip_dispatch_signature_v1 (hip-autotune-types.h) with real gate-tensor geometry fields (at minimum gate ne/type; check whether gate_bias/x_bias/x_scale/gate_scale also need capturing for a faithful replay -- read ggml_cuda_mm_fusion_args_host's full field list before deciding scope).
2. Update ggml_hip_make_signature() (hip-autotune-signature.cpp) to populate the new fields from `fusion->gate` (and any other fusion fields decided in step 1) when fusion != nullptr.
3. Bump the signature schema version; update every schema-version-aware consumer (dispatch_db ingestion, replay, etc.) to handle the new field additively -- do not break existing artifacts written under the old schema.
4. Offline tests: a synthetic fused-GLU signature round-trips the new fields correctly; an old-schema artifact still loads (backward compat).
5. Real-hardware validation: rebuild, run a real GLU-fusing MoE campaign (Qwen3.6-35B-A3B, matching HI105/HI108's own real workload), confirm the new fields populate with real, sane gate-tensor geometry for the two dispatches HI108 already found (7ef2471585a5aa6fbb49384efe566ac5, d816ffce280de2a7ce2292c6406da23d).

## Validation

DONE 2026-08-25 -- REVISED SCOPE, much smaller than originally estimated. Investigation (reading mmvq.cu's real GGML_ASSERT calls ~line 1435-1462, where the struct's six fusion->* fields are used) found every fusion tensor's real geometry is already algebraically derivable from fields ggml_hip_dispatch_signature_v1 records today: fusion->gate must share src0's exact type and stride (`type == src0->type && ggml_are_same_stride(fusion->gate, src0)`, a hard runtime assertion, not an inferred model convention); fusion->x_bias/gate_bias must be F32 with `ne[0] == dst->ne[0]` and (if ids) `ne[1] == src0->ne[2]` (== this signature's own n_expert field). So NO new ne/type fields are needed for gate or the biases, and NO schema-version bump was needed -- this eliminates the original item's biggest assumed risk (artifact migration/backward-compat).

What WAS genuinely missing: ggml_hip_fusion_kind() (hip-autotune-signature.cpp) collapses fusion->x_bias and fusion->gate_bias into one coarse GGML_HIP_FUSION_BIAS/GATE_BIAS value, and never records fusion->x_scale/gate_scale presence at all (NVFP4-only, per mmvq.cu's own comment; never observed on the real q8_0 dispatches HI108 found, but a real future gap if a future model uses them). Fixed by adding 4 new additive flag bits to ggml_hip_signature_flag (GGML_HIP_SIG_FUSION_X_BIAS/GATE_BIAS/X_SCALE/GATE_SCALE, bits 7-10 of the existing `flags` field -- no struct layout change, no version bump), set independently in ggml_hip_make_signature() from each real fusion->* field.

Real build break found and fixed along the way: an initial attempt also tracked fusion->dst_gate (a 6th field visible in this session's LOCAL Windows vendor/llama.cpp checkout), which broke a real incremental rebuild on Brutus with 'no member named dst_gate'. Root cause: dst_gate only exists on ggml_cuda_mm_fusion_args_host under the experimental, non-default patch 1207_rd17_moe_topk_down_fold.py -- the local Windows vendor tree had it applied (git-dirty, from earlier session work), Brutus's did not. Dropped dst_gate entirely (also correctly out of scope per the struct's own comment: only meaningful when glu_op == GGML_GLU_OP_NONE, a different, non-GLU-combining fusion mode than HI108/HI119 care about).

Offline tests added (tools/tests/test_dispatch_safety.py::TestHi118FusionFieldPresenceFlags, 2 tests: new bits defined without collision + explicitly absent for dst_gate, and ggml_hip_make_signature sets each flag from its own independent fusion field with no dst_gate reference). Full offline suite green (2065 passed, only the known pre-existing Windows symlink-privilege test unrelated). Real-hardware validated: incremental ninja rebuild on Brutus (bc-build-hi64hi14) succeeds cleanly after the dst_gate fix, and a real test-backend-ops MUL_MAT dispatch run confirms the change is inert/safe for the ordinary non-fused path (no regression). Committed 2ef2dfa (tuning-code-rebase, pushed), Brutus vendor overlay synced to the corrected files. HI119 (the fused-graph correctness-evidence harness) can now proceed directly against the current schema -- ready to consume GGML_HIP_SIG_FUSION_X_BIAS/GATE_BIAS/X_SCALE/GATE_SCALE plus the existing sig.fusion/sig.glu_op/ne0/ned/n_expert fields, with no further schema work needed first.
