# Real production pp4096 throughput may have regressed ~2.4x since the recorded 2026-08-19 baseline -- suspected ROCm 7.1.4.0 -> 7.2.4 upgrade, unconfirmed

## Description

While investigating HI114's RD07/Q6_K A/B, the user asked why measured pp4096 (~503-521 t/s across every build tested today -- BigCherry control/stock, RD07-patched, and genuinely-stock upstream llama.cpp with zero BigCherry patches) is roughly 2.4x below the recorded project baseline (pp4096 ~1249 t/s, tg2048 ~93-109 t/s, [[project-dual-xtx-baseline]] memory, measured 2026-08-19 on real hardware).

Systematically ruled out today, real-hardware-verified: BigCherry code/patches (stock upstream shows the identical ~520 t/s), `-fa auto` vs `on` (both match the real bench harness's own defaults), `--load-mode mmap`, `--parallel 1` vs unset, `-c 64000` vs unset/huge-default, RCCL linkage (confirmed present and linked, `GGML_HIP_RCCL=ON`), concurrent GPU contention (no other process was using the GPUs during any test), and PCIe link width (initially misread from `rocm-smi`'s pcie-clock-level field, which reported GPU[0] stuck at 2.5GT/s x8 under load; retracted after the kernel's own authoritative /sys/bus/pci/devices/<bdf>/{current,max}_link_{speed,width} showed 16.0GT/s -- though the user confirmed the cards are physically wired x8, which is a static hardware characteristic that would apply equally to the historical baseline too, so it cannot explain a NEW gap).

**Real, unconfirmed lead:** `/opt/rocm-7.2.4` (currently active, `/etc/alternatives/rocm` points to it) was installed 2026-08-19 11:02:39 -- the SAME day the 1249 t/s baseline was recorded. `/opt/rocm7140` (a genuine, full 9.4GB alternate ROCm 7.1.4.0 install, not a stub) exists alongside it, created 11:20 the same day. Both installs landed within 18 minutes of each other, so install timestamps alone cannot establish which version was active during the historical measurement -- this needs a direct empirical test, not more timestamp archaeology.

## Steps

1. Build a llama-server binary with CMake pointed at /opt/rocm7140 instead of the currently-active /opt/rocm (7.2.4) -- check whether bigcherry's build tooling supports an alternate ROCm path via --c-compiler/--cxx-compiler or a CMAKE_PREFIX_PATH-style override; may need a direct cmake invocation outside bigcherry's own build pipeline for this one-off comparison.
2. Run the exact same real bench harness (`run_bench.py --bench-type server-bench --server-url ... --bench-configs mtp-dual --toggles '{"repetitions":5}'`) against it with identical launch flags to today's tests.
3. If pp4096 recovers to ~1249 t/s on ROCm 7.1.4.0: this is a confirmed real regression in ROCm/RCCL 7.2.4's tensor-split collective performance on RDNA3 -- escalate immediately, this affects real production traffic today, not just tuning experiments. File an upstream ROCm bug report with the isolated repro.
4. If pp4096 does NOT recover: the ROCm-version hypothesis is falsified: fall back to checking whether the historical 1249 t/s measurement's own raw log/methodology can be found and re-examined (was it genuinely the same model/flags/hardware, or is there a methodology difference not yet identified).
