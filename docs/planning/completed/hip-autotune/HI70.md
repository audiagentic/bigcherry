# gfx1201 replay-full catalog: 24 candidates never reach correctness evidence regardless of workload

## Description

RE15's real end-to-end acceptance run on Brutus (device 2/gfx1201) found that 24 of 100 non-native candidates in the restricted replay-full catalog (small-batch MMQ tile variants j16/j32/j64/j128 across q8_0/q4_k/q5_k/q6_k source types, plus mmf:f16 warp-count variants nw1-nw8) never reach status='ok' correctness evidence, blocking generate --variant-set replay-full's build_manifest() gate. Confirmed workload-independent: identical 24 missing across a llama-bench batch/ubatch sweep, a broad llama-server + Brutus bench-runner sweep (bench-configs=full, pp256..pp4096/tg128..tg2048), and a repeat with flash-attention + q8_0 KV-cache quantization explicitly enabled.

## Detailed Solution & Technical Design

ROOT CAUSE FOUND (2026-08-18, verified directly against vendor source, not the earlier gpt-auto hypothesis alone -- that hypothesis pointed the right direction; this confirms and sharpens it to two exact code-level conditions):

**MMQ fb1 candidates (16 of the 24: j16/j32/j64/j128 x q8_0/q4_k/q5_k/q6_k):**
vendor/llama.cpp/ggml/src/ggml-cuda/mmq.cu:151 -- `const bool fallback = ne01 % 128 != 0;`
Fallback mode ("fb1" in the candidate stable_name) is NOT a free choice the tuner or catalog can select -- it is determined entirely by whether src0's row count (ne01) is a multiple of 128. mmq-config-rdna4.cuh genuinely DOES define config rows for fallback=true at exactly J=16/32/64/128 for all four affected types (confirmed by direct read of mmq-config-rdna4.cuh lines ~79-153) -- the config table is not the problem. The problem is that Qwen3.5-0.8B (and, structurally, most well-formed production models, whose hidden/intermediate dimensions are deliberately chosen as multiples of 128 for exactly this GPU-efficiency reason) never produces a MUL_MAT with ne01 % 128 != 0 anywhere in its forward pass. fb1 is not unreachable on this hardware -- it is unreachable for THIS MODEL because the model's own dimensions are block-aligned.

**MMF f16 nw1-nw8 candidates (8 of the 24, missing as a complete group):**
vendor/llama.cpp/ggml/src/ggml-cuda/mmf.cu:164 -- `if (src0_ne[0] % (warp_size * (4/ts)) != 0) return false;`
This is MMF's hard applicability gate, checked before ANY nwarps variant is considered -- exactly matching the observed all-or-nothing pattern (every one of nw1..nw8 missing together, never a partial subset). warp_size is 32 on gfx1201 (RDNA4, confirmed via rocminfo earlier this session: "Wave Size: 32"), so for f16 (ts=2, 4/ts=2) the gate requires src0_ne[0] % 64 == 0. If this model's f16-typed tensors' leading dimension is not a multiple of 64 on this wave32 architecture, MMF disqualifies itself entirely -- again a real, model-dependent (and here also wave-size-dependent) applicability fact, not a dispatch or catalog bug.

**Conclusion:** these 24 candidates are not broken and not a coverage gap in the sense of "measure more." They require shapes this specific model/workload structurally never produces. No amount of additional benchmark sweeping (which is why every sweep attempted this session found the identical 24) will ever produce evidence for them from this model.

**What actually needs fixing (scoped, not yet implemented):** autotune_catalog.py's Inventory class (tools/bigcherry/autotune_catalog.py ~L215) only tracks observed TYPES and widths per family -- it discards the actual per-signature shape (ne0/ne1/etc, which IS present in each raw record-mode observation's "canonical" block, see RECORD_OBS-style fixtures and real observation rows captured this session) once it reduces record.jsonl into inventory.json. To make the replay-full catalog gate only require correctness evidence for candidates this workload could ever actually reach, generate_inventory/build_inventory (inventory.py) needs to also capture, per family: whether any observed signature had ne01 % 128 != 0 (for MMQ fallback applicability, architecture-independent) and, per architecture (warp_size varies -- 32 on RDNA4/gfx1201, 64 on older RDNA/CDNA -- so this fact is NOT single-valued across a multi-architecture build), whether any observed src0 leading dimension satisfied MMF's alignment gate. autotune_catalog.py's enumerate_mmq()/enumerate_mmf() would then skip fb1/nwarps-family candidates the inventory proves unreachable, instead of enumerating a superset and later demanding evidence build_manifest() knows can never arrive.

This is real new scope (record.jsonl -> inventory.json schema addition, per-architecture-aware catalog logic, tests, real-hardware re-verification) -- not a quick patch. Do not implement it inline without deciding this is worth doing; an alternative is to accept these 24 as a documented, workload-dependent exemption specific to variant sets generated FROM a model with these properties (block-aligned dims, wave32 f16 tensor width not a multiple of 64) -- but RE15's acceptance criterion (3) currently requires complete correctness evidence for the FULL replay-full catalog, which was written before this distinction was understood, so either the inventory-awareness fix or a deliberate re-scoping of that acceptance criterion is needed to unblock RE15 stage F.

MMF f16 ROOT CAUSE NOW FULLY IDENTIFIED (2026-08-18, corrects/completes the earlier retracted shape-based guess): re-read ggml_cuda_should_use_mmf() in mmf.cu directly. The real gate is NOT a tensor-shape/alignment condition at all -- it's a POLICY check: `else if (src1_ncols > 16) return false;` (non-mul_mat_id path). src1_ncols is the number of columns dispatched together in ONE MUL_MAT call -- i.e. the batch width of the CURRENT decode step, not anything about the weight tensor. A normal single-sequence llama-bench -p/-n benchmark dispatches batch=1 during token generation (decode) and large batches only during prompt processing (which routes to MMQ, not MMF/MMVF) -- there is NO normal single-stream workload shape that ever puts a MUL_MAT call in the 2-16-column range MMF requires. This fully explains why mmf:f16 nw1-8 never got evidence in ANY of this session's workload sweeps (batch/ubatch variation, flash-attention, KV quantization, different models) -- none of those change decode batch width. Confirmed hardware capability is NOT the blocker either: gfx1201 is RDNA4, and amd_wmma_available(cc) returns true for RDNA4, so F16 MMF is HW-capable on this GPU. The only way to reach src1_ncols in [2,16] from a real workload is multi-token batch verification -- i.e. speculative/MTP decoding (draft tokens verified together in one batch).
