# Profile-gated exact on-device correctness reduction for candidate screening

## Description

On-device exact correctness reduction for screening (F4, P2): replace the full device-to-host output copy + host NMSE compare per eligible candidate with an exact on-device scalar reduction, but only if profiling shows it material - and never by subsampling or deferring correctness.

## Steps



## Detailed Solution & Technical Design

DESIGN (GPT-adjudicated in RV49): profile first - if the screening copies are a material portion of tune time, implement an EXACT device-side reduction over the COMPLETE output that computes sum((C-N)^2), sum(N^2), max(abs(C-N)) and any_nan_or_inf, copying only those scalars to the host. DO NOT strided-subsample correctness and do NOT defer correctness until after finalist selection - both trade a hard correctness property for cold-path speed, and are rejected by design. Sequenced AFTER HI67 (F1) because F1 changes what the reference actually needs to be (CPU reference R, not just native N) - build the reduction against the final reference semantics in one pass rather than twice. Note the verified correction: the determinism recheck does the D2H copy only twice and only for the selected winner, not for all finalists - the bulk cost is the per-eligible-candidate screening pass.

**Design conversation**: per standing process, worked through the measurement plan with dev-gpt-agent via the agents gateway before implementing (session ses_3499284b9d3c4541, request req_5c8c2a476c2c4143). Agreed design: primary go/no-go metric is aggregate avoidable correctness wall time / aggregate cold tuner-resolution wall time (F_tune = sum(correctness)/sum(cold_tuner)), NOT a mean of per-candidate ratios -- averaging would let a handful of cheap candidates with proportionally large fixed overhead dominate the decision despite contributing negligible absolute wall time. Every correctness stage (D2H copy, sync, host compare_outputs, native-reference copy) timed in full, not sampled like HI87's dispatch-hot-path diagnostic, since each contains a real transfer/sync/O(N) traversal (timer overhead negligible by comparison). Pre-registered gate (agreed before seeing data): F_tune <2% close as not-worth-it; 2-5% gray zone; >=5% device-reduction prototype justified.

**Real hardware measurement** (gfx1100, ROCm 7.1, non-blocking -- no HIP_LAUNCH_BLOCKING, since blocking would inflate the denominator and bias against HI69 per gpt's warning): full `test-backend-ops test -o MUL_MAT` correctness+tune sweep, 1216/1216 tests passed (no regression from the instrumentation). Result: 1088 cold-path signature resolutions, 11,570 screening candidates, 228.320s total cold tuner wall time, of which only 1.228s (**F_tune=0.5379%**) was the D2H-copy+host-compare correctness machinery (copy_sync=1040ms dominates, compare_outputs() CPU loop itself only 71ms, native-reference copy 117ms). Clears the <2% close threshold cleanly -- confirmed reproducible on a smaller follow-up sweep (F_tune=0.5182%, d2h_bytes=563712). Per-candidate ratio median 2.08%/p95 4.07% is higher than the aggregate (expected: different, larger denominator including native measurement/finalist/confirmation work outside individual candidate slices, plus duration-weighting -- gpt's review explained this precisely, does not change the verdict).

**Why this is a stronger result than just "below 2%"**: the measured 1.228s is an upper bound on the possible saving, not the saving a real implementation could achieve -- the proposed on-device reduction would still need to launch a kernel, read both tensors, reduce, sync, and copy scalars back. Even a magically-free correctness check buys at most 0.54% of cold tuning time; a real implementation buys less, for real added complexity (GPU reduction kernel, NaN/Inf handling on-device, new tests, floating-point reduction-order questions).

**Bit-exact validation question**: HI69's own validation text called for "bit-exact agreement" between a GPU reduction and compare_outputs(). Left explicitly N/A/not adjudicated -- the implementation gate never opened, so this question (a parallel GPU reduction changes floating-point summation order vs. the host's sequential double accumulation, so literal bit-identity may conflict with the optimization's own point) was never resolved and shouldn't be treated as settled if this item is ever reopened.
