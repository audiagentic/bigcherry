# Separate fast runtime cache identity from the persistent cryptographic digest

## Description

dev-gpt-agent (req_7bd85f40d3334469) reviewed the dispatch algorithms and rates this the top design defect -- above the L1 memcmp I had been focused on, and far above HI158's native_select deferral.

Runtime cache identity and PERSISTENT cache identity are conflated. On every L1 miss the resolver computes ggml_hip_signature_digest(sig), which is:

  232-byte struct -> canonical JSON std::string (repeated snprintf per field)
                  -> BLAKE2b

and a second canonical string is built and hashed for the dispatch digest. That is a heap allocation, dozens of integer formatting calls and a cryptographic hash, on the cache-MISS path, purely to index a process-local hash map. The persistent digest exists so a cache can be written to disk and matched across runs; using it as the in-process L2 key charges every miss the full cost of persistence.

This interacts badly with the L1 sizing question. The measured workload presents 86 distinct signatures to an 8-slot round-robin L1. If L1 thrashes -- and gpt predicts real hit rates materially below the synthetic 99.8%, plausibly under 90% -- then JSON serialisation plus BLAKE2b runs on a large fraction of ~200,000 dispatches per bench run. That would dwarf every cost measured so far, including the 38.6 ms total attributed to native_select.

gpt's verdict on my proposed alternative -- hash once up front and key L1 on the digest -- is NO, with the current hash: it would move a major cost onto every dispatch rather than every miss.

## Steps

1. Introduce a cheap runtime tag (a few mixed high-discrimination fields, not a hash of the whole struct) and key BOTH L1 and L2 on it, with exact signature compare deciding equality.
2. Restrict the canonical JSON + BLAKE2b digest to replay/persistence only, computed on an L2 miss, never on an L1 miss that L2 can serve.
3. Verify the invariant that a runtime-tag collision can only cost an extra compare, never a wrong binding.

## Detailed Solution & Technical Design

gpt's recommended architecture:

  tensor metadata
    -> prepare_dispatch() ONCE: signature, cheap runtime tag, derived predicates
    -> TLS set-associative L1, keyed cheap tag + exact signature compare
    -> per-device/sharded runtime L2, same cheap key
    -> ONLY on L2 miss: canonical JSON + BLAKE2 persistent digest, replay lookup,
       native_select if required

On L1/L2 structure: prefer a split layout (compact hot tags[] array, signatures touched only on tag match) and set associativity -- 16 or 32 entries, 2- or 4-way -- so a normal lookup is 2-4 integer comparisons and usually zero full memcmps. Explicitly: do NOT use the persistent digest as the tag.

On replacement policy, gpt's ordering is capacity/reuse-distance >> associativity >> replacement policy. Round-robin has genuine pathological behaviour (a cyclic working set one larger than capacity gives ~100% misses, and RR evicts a hot entry that LRU would protect) but LRU cannot rescue undersizing, so do not build true LRU before measuring.

DO NOT pick a capacity from intuition. Record a per-thread signature sequence, compute reuse/stack distance, and simulate capacities 4/8/16/32/64 under RR/LRU/2-way/4-way offline. That yields the answer without fitting policy to benchmark noise.

Interpretation: this workload's steady-state decode almost certainly hits L1 (the thread-local cache) on nearly every dispatch once warmed up, so L2's key -- whether cheap fingerprint or expensive persistent digest -- rarely executes at all in this measurement window. HI163's diagnosed mechanism (digest computation gated behind an L2 miss) was real and worth fixing regardless (correctness/design quality, and it matters whenever L1 does miss, e.g. thrashing workloads with more than ~8 live signatures per thread), but it does NOT appear to be the dominant contributor to the +5-6% hipLaunchKernel host-side gap actually observed on GPU0. The real source of that gap remains unexplained and is NOT this item's mechanism -- do not close this investigation thread as solved. Candidates for further investigation (not yet explored): a genuine per-call constant-overhead difference between native's and replay's code paths elsewhere in ggml_hip_dispatch_resolve()/ggml_hip_dispatch_launch() unrelated to cache keying (e.g. an extra branch, an extra atomic, or replay-specific bookkeeping that runs unconditionally regardless of cache tier), or something in HIP's own runtime behavior when GGML_HIP_DISPATCH_REPLAY is compiled in at all (a compile-time flag difference between native and replay builds, not a cache-hit-path difference).

HI163 itself remains a real, implemented, tested, and merged correctness/design fix (see IMPLEMENTED note below) -- worth keeping regardless of this result -- but its promotion should NOT be described as having fixed GPU0's e2e regression. That regression's real cause is still open. Recommend re-scoping the search: instrument/measure WHERE inside dispatch_resolve/launch the extra ~0.6us/call actually goes (a finer-grained trace than whole-function hipLaunchKernel timing), rather than assuming it is the cache-tier mechanism this item targeted.
