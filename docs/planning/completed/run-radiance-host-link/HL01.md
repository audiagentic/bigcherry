# Root-port host-transfer contention: CPU arbitration diagnosed by physical XTX swap

## Description

**Completed 2026-11-13.** Identify why GPU-initiated host transfers from every other CPU-attached card slow when the GPU on the first bifurcated PEG x8 half reads host memory. Full `lspci -vv`/IOMMU inspection, before/after physical XTX swap, and a partial-population control show the asymmetry follows root port `00:01.0`, not the physical card, VBIOS or request start order. Other XTX host reads/writes fall to ~6.7 GB/s and R9700 reads/writes to ~3.4 GB/s, while the primary card retains ~13.4 GB/s host reads. SDMA is affected, CPU BAR writes are not.

**Supported diagnosis:** CPU-internal arbitration favours the first PEG half; the coherent-snoop inbound stage is a *hypothesis*, not a proved microarchitectural cause. PCIe settings match and GPU DMA uses IOMMU passthrough. No justified PCIe configuration fix was found. HL02 owns all remaining transfer-method/contention tests, and VTP38 owns the production TP3 transport.

## Steps

1. **Done:** Capture card/switch/root-port `lspci -vv`, link widths, MPS/MRRS, ordering, tag capability, AER and IOMMU identity mappings.
2. **Done:** Reproduce solo and contention host-read and host-write matrices; reverse start order and observe SDMA and CPU BAR controls.
3. **Done:** Physically swap the XTX cards between PEG halves and repeat the same matrix.
4. **Done:** With just the formerly non-contending XTX at the primary PEG half, reproduce the R9700 host-read slowdown.
5. **Closed:** No differing PCIe setting warrants `setpci` experimentation. Handoff software transfer tests to HL02 and implementation to VTP38.

## Detailed Solution & Technical Design

The XTXs negotiate separate Gen4 x8 links on the bifurcated PEG controller, and the R9700 is on a separate CPU Gen4 x4 root port. Endpoint and switch settings match; root ports likewise match. Root-port MPS 256, MRRS 128, relaxed ordering and extended tags disabled; endpoints MPS 256, MRRS 512, relaxed ordering and extended tags enabled. GPU IOMMU groups use identity mappings.

The halving follows the *slot* after exchanging the two physical XTX cards. Because a separate-controller R9700 is affected, the shared mechanism must lie upstream in CPU I/O/memory arbitration, not exclusively within the two PEG links. Victim GPU writes also halve, ruling out an explanation confined to host-read bandwidth. These tests do not isolate a specific internal CPU queue, snoop stage or firmware switch.

Any measured host-profile mitigation must be topology-calibrated; never encode the observed BDF/slot as a machine-independent constant.

IOMMU: kernel `intel_iommu=on iommu=pt`; the GPU IOMMU groups (20, 24, 28, 43) are all `identity`, so GPU DMA is not translated (IOTLB contention ruled out).

Conclusion: no PCIe configuration difference between the three CPU-attached cards; every setting this item suspected (MaxPayload, MaxReadReq, relaxed ordering, extended/10-bit tags, ASPM) is identical, and the IOMMU is in passthrough. The only asymmetry is position: XTX 0 is the first half of the bifurcated PEG x16 controller. Since the R9700 on a separate controller is also slowed, the shared point is inside the CPU (system agent / IO fabric to memory), which PCI config space does not control. A `setpci` experiment has no target. Remaining optional test: physically swap XTX 0 and XTX 1 to separate slot from card. Mitigation moves to software: HL02 (CPU push under contention) and VTP38 (host-reduced all-reduce).

In-engine evidence the effect is live (VTP36 rad0031 two-shot timeline, int8 TP3, 2048-token prompt, ~10 MB per all-reduce, weights 4,4,1): the XTX ranks do identical reduce work (read 8/9 of the message) yet XTX 0 takes 889 us (~10 GB/s) and XTX 1 1301 us (~6.8 GB/s, the contended rate above); XTX 0 and the R9700 then wait ~400 us at the second barrier, about 10% of each ~4 ms prefill all-reduce. Decode shows the same skew in microseconds (8 streams: 23 vs 39 us). Unrelated: the chipset-attached 6900 XT (00:1d.0, Gen3 x4) has a logged correctable error source 15:00.0.

The halving follows the slot (root port 00:01.0, first half of the bifurcated PEG x16 controller), not the card or its VBIOS. With identical PCIe settings and IOMMU passthrough (finding above), the cause is CPU-internal arbitration that favours that port; there is no configuration fix.
