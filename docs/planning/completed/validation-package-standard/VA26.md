# PQM-v1: standard Patch Qualification Matrix (4 arms x N architectures, isolated + in-situ)

## Description

Owner spec: every patch validation should measure llama.cpp native, bigcherry-native, bigcherry-native + the patch alone, and the full bigcherry release set -- across all three cards for single-card-applicable patches, with multi-GPU and heterogeneous topologies added later.

All four arms are ALREADY expressible with existing primitives; nothing new is needed to compose them:

    1  llama-native        patch-sets = []
    2  bigcherry-native    patch-sets = ["framework"]
    3  bigcherry-native + --experiment <patch>-only     (additive experiment mechanism)
    4  bigcherry           patch-sets = ["framework", "validated-enhancements"]

WHY THIS MATTERS NOW. RD73 was promoted and shipped on evidence from ONE contrast (3 vs 2) on ONE architecture (gfx1100). Nothing measured whether it still helps IN COMBINATION with the rest of the release set, and nothing measured the other two cards at all. The 27B model it was qualified on (29GB) cannot even load on gfx1030 (16GiB), which is why tierB-qwen9b-q6k (7.7GB) was registered to be the model held constant while architecture varies.

Design from adversarial review (dev-gpt-agent, req_157bd6078b914cad).

## Steps

P0 slice -- SINGLE-GPU PQM-v1 only:

1. QualificationMatrix planner emitting: patch_id, contract_id/hash,
   gain_arches, safety_arches, isolated composition (bigcherry-native <->
   +P), release composition (R <-> R+P), release_composition_hash,
   qualification_policy=pqm-v1. Generate lanes automatically from existing
   architecture declarations; FAIL CLOSED on disagreement or unavailable
   architecture.

2. Generic release-delta(P) composition resolver: control = exact current
   release composition, subject = control + P's dependency closure. No
   patch-specific campaign implementation -- the current per-patch
   --run-rdNN-contract pattern must not be extended.

3. Per gain arch: 3v2 as the existing 4..N session inferential campaign;
   4v4-P as a 4..N session non-regression campaign.

4. Per safety-only arch: correctness + activation + attestation, one 3v2
   smoke, one 4v4-P smoke, plus the pre-registered escalation trigger.

5. Baseline build cache for arms 1/2/R. Run 2v1 and 4v1 once per
   release/pin/framework calibration generation. Never consume historical
   baseline MEASUREMENTS as paired promotion evidence.

6. Evidence verifier requires a complete generated PQM matrix before release
   admission.

DEPENDS ON VA25 (execution attestation). Without it a silently-CPU arm
produces a spectacular fake result with tight CIs, and the matrix multiplies
the number of chances for that to happen.

LATER PHASE -- multi-GPU, only after: every participating architecture passes
single-GPU correctness/attestation; device identity/visibility attestation is
enforced; release composition is frozen; the model/workload actually
activates the multi-GPU path; and topology/P2P/collective state is captured
as measurement identity.

    single GPU: gfx1100, gfx1201, gfx1030
    then 2x gfx1100 homogeneous
    then heterogeneous pairwise: 1100+1201, 1100+1030
    then 3/4-device heterogeneous

Multi-GPU uniquely catches: shard placement, split-mode errors,
P2P/host-staging fallback, collective correctness, cross-device
visibility/fencing, synchronisation/deadlock, device-order dependence,
asymmetric VRAM pressure, state-restore bugs. Heterogeneous additionally
catches: per-device ISA/kernel mis-selection, assuming one architecture
describes the whole communicator, unequal shard geometry, architecture-order
dependence, and slow/unsupported-device collective paths.

## Detailed Solution & Technical Design

THE FOUR CONTRASTS, ranked. Do NOT choose between the first two -- they answer different mandatory questions.

    P0  3 vs 2        isolated efficacy / attribution   -> gates PACKAGE validation
    P0  4 vs 4-minus-P  composition / release safety    -> gates ADMISSION to validated-enhancements
    P1  2 vs 1        framework tax                     -> diagnostic, release calibration
    P2  4 vs 1        whole-product gain vs upstream    -> release KPI, not per-patch

CRITICAL ASYMMETRY: the in-situ gate is NON-INFERIORITY, not a second superiority gate.

    3 vs 2          establish a positive effect per contract  (superiority)
    4 vs 4-minus-P  CI must exclude material regression       (non-inferiority)

Rationale: an individually useful patch becoming NEUTRAL through overlap with others is not evidence it is unsafe; a negative production interaction is. Requiring marginal superiority in situ would reject patches whose benefit is merely redundant with an existing one. If we ever want to claim a patch still adds measurable production throughput, that is a separate, explicitly declared marginal-superiority claim.

This maps onto the existing separation between package lifecycle validation (STATE=validated) and deliberate membership in validated-enhancements -- which is exactly the two-axis distinction already encoded in test_external_sources' VALIDATED_RDNA_PATCHES vs SHIPPED_RDNA_PATCHES.

REPLICATE CONTRASTS, NOT ARMS. This is what makes the matrix affordable.

    build artifact reuse                        YES, aggressively
    old measurements as paired gating evidence  NO
    old measurements as diagnostics             YES

BigCherry's own data forbids the tempting shortcut: between-session drift (sd ~0.5-0.6 on RD73) is larger than any single run's standard error, and sessions are the inferential unit with MIN_BOOTSTRAP_SESSIONS = 4. So a cached llama-native number from last week cannot serve as the control observation in a paired A/B today. Cache the BINARY; re-execute it inside every paired session.

    llama-native      periodic cached reference; no per-patch replication
    bigcherry-native  cache binary; re-execute in every 3v2 session
    release R         cache binary; re-execute in every 4v4-P session
    2v1 and 4v1       rerun at release/pin/framework changes only

Cache invalidation: composition hash, source pin/SHA, build options, toolchain/runtime bundle, backend target, or generated-input change. Do NOT invent a freshness window that converts historical measurements back into paired evidence.

GAIN vs SAFETY ACROSS CARDS -- two levels, which is what makes 3 cards affordable:

    arch IN contract.scope.architectures
        full replicated 3v2 superiority + 4v4-P composition gate

    arch in validation-architectures but OUTSIDE gain scope
        correctness + activation + attestation
        + ONE 3v2 paired smoke
        + ONE 4v4-P paired smoke
        + pre-registered gross-regression trigger -> ESCALATE that arch to
          full 4..N non-inferiority

DISCIPLINE POINT: one smoke session establishes 'no breakage / no gross regression observed'. It is NOT a non-inferiority claim. Formal non-inferiority needs >= 4 sessions exactly like superiority -- possibly more, if the CI cannot resolve the declared regression margin. Never label a 1-2 session check as non-inferiority.

COMPOSITION CONTRAST, expressed prospectively so no rebuild-the-world is needed:

    control = source.bigcherry                       (current accepted release R)
    subject = source.bigcherry + experiment.<patch>  (R + P)

That IS full-set vs full-set-minus-patch, stated forwards. The expensive unit is ONE extra composition build, not two full release builds per patch.

Freeze release_composition_hash into the evidence. If another patch is admitted before candidate P, P's composition evidence goes stale:

    base R changed -> rerun ONLY P's 4v4-P admission contrast
                      isolated 3v2 evidence stays valid if its own identity is unchanged

This makes admission ORDER significant and must be modelled, not ignored.

'Patch alone' means patch + its mandatory dependency closure, matching existing experiment/composition semantics.

EDGE CASE to handle explicitly: for an already-shipped patch with downstream dependents, release-minus-P may be an impossible composition. NEVER silently drop the dependents too and call the result P's marginal effect. Record counterfactual_not_composable and fall back to a proven exact runtime negative control if one exists.

AUTHORITY -- zero new per-patch axes. The matrix is DERIVED:

    gain_arches   = contract.scope.architectures        (scientific scope)
    safety_arches = patch.validation-architectures - gain_arches   (ship coverage)
    platform.targets    = capability inventory, never a coverage declaration
    --amdgpu-targets    = execution selector only; must resolve within a planned lane

The ONLY new declaration is a versioned global policy identity:

    qualification_policy = "pqm-v1"

bound by version/hash into evidence. The planner generates the whole matrix from declarations that already exist.

## Effort & Risk

Large but mostly planner/resolver work, not new measurement machinery. Main risks:

1. Admission ORDER becomes significant (each admission stales pending
   candidates' composition evidence). This is genuinely new state to model and
   easy to get wrong.
2. The release-minus-P counterfactual can be impossible for shipped patches
   with dependents; must fail loudly rather than silently changing what is
   being compared.
3. Blocked on VA25. Running a 12-session matrix without execution attestation
   multiplies exposure to the CPU-fallback failure mode.
