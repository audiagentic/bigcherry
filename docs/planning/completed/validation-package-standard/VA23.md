# Bind contract-produced artifacts to the generic performance/controls validators (RD73 errors with 'benchmark artifact requires non-empty metrics')

## Description

A real, reproduced gap found while running RD73's contract qualification on 2026-09-04.

The RD73 contract path (`validation_campaign --run-rd73-contract`) executed successfully and produced real, sha256-bound artifacts:

- rd73-contract-qualification.json (promotion gate, aggregated effects)
- rd73-mtp-lane.json (10 paired rounds, 12 control + 12 subject requests,
  geometric_effect_pct +1.855%, 95% CI [1.482%, 2.169%], 10,000 bootstrap resamples)
- rd73-decode-control.json (max_control_regression_pct 0.0)
- rd73-activation.json

The contract's own gates passed: correctness_gate PASS (bit_identical), resource_gate PASS (graph_cache_entries), trigger_proof PASS (1 lane checked, 0 untriggered). Promotion failed only on the contract's own 3.0% threshold (measured 1.855%).

But the GENERIC validators in the evidence record do not consume any of that:

```
apply                       pass
build                       pass
activation                  blocked
correctness                 blocked
_contract_correctness_gate  blocked
performance                 ERROR   "benchmark artifact requires non-empty metrics"
controls                    ERROR   "benchmark artifact requires non-empty metrics"
```

so `bigcherry patch-verify-evidence 1233_rd73_stable_graph_cache_key` still reports `missing-or-stale` / "no recorded benchmark execution", despite a real benchmark execution having demonstrably happened.

## Detailed Solution & Technical Design

patch 1233's own validation.toml already documents this for the CORRECTNESS capability:

> RD73's real bit_identical evidence is produced by
> validation_campaign.evaluate_rd73_mtp_correctness() (VA06), driven by
> --run-rd73-contract -- but that producer is not wired into this generic
> backend-ops check (ctx.correctness_evidence stays unbound for it).
> ... Stays BLOCKED here until the generic adapter is rebound.

This item extends that known gap to what was newly observed: the same unbound-adapter problem affects `performance` and `controls`, which ERROR rather than BLOCK because the generic benchmark validator receives an artifact with no `metrics` key it recognises.

The fix is an adapter, not new measurement: bind the contract's aggregated_effects / mtp_lane / decode_control artifacts into the ctx fields the generic `benchmark` validator reads, so a contract-qualified run satisfies the declared performance/controls capabilities instead of erroring.

Design constraints to respect:
- Do NOT fabricate a metrics blob to satisfy the validator. The artifacts are
  real and sha256-bound; the adapter must reference them, preserving the
  path-containment and hash-binding the standard requires.
- BLOCKED must not silently become PASS. If a capability genuinely has no
  producer for a given contract, BLOCKED remains the honest outcome; this item
  is only about capabilities where a real producer ran and its output was not
  routed.
- The distinction between ERROR (validator could not evaluate) and BLOCKED
  (external prerequisite unavailable) should be preserved and, where the
  current behaviour conflates them, corrected.

Check whether RD08's `--run-rd08-contract` path has the same issue or already
solves it -- PATCH_VALIDATION.md's workflow note says RD08 is currently the
only contract treated as an authoritative full-qualification path, so its
adapter may be the template to generalise.

## Notes

Filed 2026-09-04 from a real RD73 contract run on dual gfx1100 (see RD73's notes and patches/1233_rd73_stable_graph_cache_key/SUMMARY.md for the full measured result and the check matrix quoted above).

Why this matters beyond bookkeeping: the contract measured a genuine, statistically significant +1.855% (CI excluding zero) with bit-identical correctness, but because the generic checks error, the project's own evidence tooling reports that no benchmark ran. That is a false negative in the direction that hides real results, which is the more dangerous direction for a fail-closed system -- it makes a real measured effect look like an absent one.

Also worth noting for whoever picks this up: this gap plausibly explains why several ported external patches sit at `ported-untested` with no qualifying evidence. If the adapter is unbound for contracts generally, running the campaign correctly still cannot produce qualifying evidence, so the backlog cannot be cleared by running more campaigns alone.



**DONE 2026-09-04.** `patch-verify-evidence 1233_rd73_stable_graph_cache_key`
now reports **`ported-benched-evidence`** instead of `missing-or-stale`. RD73 is
the first patch in this project with a complete, contract-qualified evidence
package.

Four commits, each verified against a real hardware campaign run rather than
assumed. Measured progression of the campaign's own verdict:

| stage | blocking reasons | verdict |
|---|---|---|
| start | 4 | ineligible |
| bind performance/controls | 2 | ineligible |
| thread named bit_identical | 2 | ineligible |
| bind trace + tag correctness ops | **0** | **eligible** |
| register artifacts in hash map | 0 | eligible + verifier accepts |

Final check matrix on the qualifying record (digest 0a7f4fbe, 10 bound
artifacts): `_contract_correctness_gate` passed, activation pass, apply pass,
build pass, controls pass, correctness pass, performance pass.

### What each slice was

1. `run_rd73_contract_qualification()` emits `rd73-performance.json` in the
   shape `_builtin_benchmark()` reads. Values are copied from the lane effects
   the contract gate already consumed, via `dataclasses.asdict()` on the frozen
   `LaneEffect` -- a projection of measured data, not a fabricated metrics blob
   (this item's own design constraint).
2. The named `bit_identical` result is threaded into
   `compute_contract_correctness_gate()`, which previously received `None` for
   RD73 while RD08 and RD58 were already wired.
3. The correctness artifact gained `ops: ["RD73_MTP_BIT_IDENTICAL"]` (the
   identifier patch 1233's own validation.toml declares -- its absence is why
   binding the artifact turned BLOCKED into ERROR), and the activation lane's
   per-log bound refs are bound as `trace_evidence`. Note the validator
   re-reads both logs and re-runs the marker regex itself, so this supplies
   evidence for independent verification rather than asserting the outcome --
   `subject_hit`/`control_hit` are deliberately NOT what it trusts.
4. `_artifact_refs()` in patch/evidence.py lists the artifact names that become
   a record's authoritative `artifact_hashes`. Only RD08's contract artifacts
   were enumerated, so RD73's passing checks referenced artifacts the verifier
   could not vouch for. Added RD73's seven artifacts plus its two activation
   server logs.

### Corrected expectation

I predicted `activation` might legitimately remain BLOCKED because the code
comments argue the generic trace probe is invalid for a graph-cache-keying
patch. That was wrong -- the probe RD73 runs IS a real positive/negative marker
probe, and once its logs were bound the generic validator verified it
independently and passed.

### Design note for the next contract author

`_artifact_refs()` is an explicit enumeration on purpose: only known artifact
names can become evidence, so an arbitrary file dropped into the campaign
workdir cannot. Each new contract's artifacts must be added by name. Do NOT
"fix" this by globbing the workdir -- that would let unverified files acquire
evidentiary status. A comment saying so is now in the source.

### Known wrinkle, not resolved here

The evidence writer is strictly append-or-identical: the same campaign digest
with different content raises `ValidationEvidenceError`. VA19 deliberately
excludes tooling from the digest identity, so a TOOLING fix that legitimately
corrects recorded evidence cannot be re-recorded under the same identity --
hit repeatedly while developing this item, worked around by resetting the
working tree's evidence file (`git checkout --`) before each verification run.
Worth its own item if VA-class work continues.
