# gfx1201 double-env-selector diagnostic-invocation bug (was misdiagnosed as a ROCm 7.2.4 limitation)

## Description

VA15's real-hardware run (2026-08-31, Brutus, gfx1201/device 2, ROCm 7.2.4) found that test-backend-ops (used by RD08's correctness producer, patches/1204_rd08_q6k_mmvq_vdr2/validation/rd08_correctness.py) fails to detect the gfx1201 HIP device -- ggml_backend_dev_count() finds only CPU, so the correctness sweep's subject/control subprocesses exit 0 but never actually run any GPU op or emit a digest. Isolated via direct manual testing on Brutus: (a) llama-bench on the SAME gfx1201 device, SAME linked libggml-hip.so.0 (confirmed via ldd), works fine and produces real bench results; (b) test-backend-ops on gfx1100/device0 (identical binary shape, different arch build) correctly detects and uses the ROCm device. Confirmed identical shared-library dependency sets via ldd on both binaries -- not a linking/env issue (a real HIP_VISIBLE_DEVICES env-clobbering bug in the correctness runner was found and fixed separately, tuning-code-rebase commit 03279cb; this is a distinct, remaining issue after that fix). Looks like a genuine upstream ggml/test-backend-ops device-enumeration quirk specific to (test-backend-ops binary) x (gfx1201 architecture) x (this ROCm 7.2.4 install) -- not something patch-validation-campaign orchestration code can fix.
