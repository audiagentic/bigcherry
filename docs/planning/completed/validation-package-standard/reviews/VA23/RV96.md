# Evidence layer cannot record a second measurement of the same build, making the frozen re-run policy unimplementable

## Notes



## Findings

Found while executing a confirming RD73 contract run (run 3) on real dual-gfx1100 hardware.

The run completed and produced a full, valid contract verdict. Writing its evidence record then FAILED outright:

    ValidationEvidenceError: patches/1233_rd73_stable_graph_cache_key/evidence/validation.json:
    campaign digest adecd397cacf292171dd4d926a8ec644e15dd0d9ffedfe94244281de27c5c948
    already has different evidence

CAUSE. evidence.py::write_record() keys records by campaign_identity_digest and refuses to store a record whose digest matches an existing one but whose content differs (evidence.py:547-553). The campaign identity digest is derived from build/source inputs. Two runs of the SAME build on the SAME hardware therefore produce the SAME digest -- so a repeat measurement is indistinguishable from a tampered record and is rejected.

The guard itself is correct and worth keeping: it is what stops evidence being silently rewritten. The defect is that identity is modelled at BUILD granularity while measurements happen at RUN granularity. There is no way to express 'this is a second, independent measurement of the same build'.

WHY THIS IS SERIOUS, beyond the immediate error:

(1) It makes the frozen re-run policy unimplementable. EXPERIMENT_CONTRACT.md's 'Re-running' section is explicit: never discard a wide run and collect a fresh one; instead pre-declare N_min/N_max, collect further pairs up to N_max, and estimate over ALL valid pairs. Extending a run means producing a second measurement of the same build -- exactly what write_record() refuses to store. The doctrine is currently doctrine only; the evidence layer physically cannot hold its output.

(2) It blocks the most basic scientific act available here -- independent replication of a result on unchanged code. Run 3 was precisely that, and its evidence is unstorable.

(3) It silently biases what gets recorded toward FIRST measurements. Whichever run happens to be written first owns the digest permanently; every later measurement of that build is rejected. If the first run is the optimistic one, the optimistic number is the one that persists. For RD73 the first-written run was the PASSING one (+1.717%) and the failing confirmation (+1.249%) could not be recorded -- the exact direction that flatters a patch.

EVIDENCE THIS IS NOT THEORETICAL. RD73's three contract runs measured +1.855%, +1.717% and +1.249%; only the middle one is in the evidence file. A reader of validation.json today sees a clean PASS and no indication that a later confirming run failed the gate. That is a materially misleading record produced by correct-looking code.

Run 3's artifacts were archived out-of-band under artifacts/patch-validation/1233_rd73_stable_graph_cache_key/run3-rejected-adecd397cacf/ so the measurement is not lost, but that is a workaround, not a record.

## Conclusion

Model measurement identity separately from build identity. A record should be addressed by something like (campaign_identity_digest, measurement_id) where measurement_id distinguishes independent runs of the same build -- so replication is representable and the tamper guard still applies within a single measurement.

The guard's real intent is 'the same measurement must not change'. Keep exactly that, and stop conflating it with 'a build may only ever be measured once'.

This is a prerequisite for implementing the frozen N_min/N_max extension rule, and a prerequisite for RD73's settlement: RD73 cannot be resolved without storing more than one measurement of the same build. Until it is fixed, any patch whose result sits near its acceptance bar cannot be honestly adjudicated, because the evidence file can only ever hold whichever run was written first.
