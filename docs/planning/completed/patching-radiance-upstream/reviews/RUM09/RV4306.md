# Align release gate with the TP1 first lane and enforce the runtime roster

## Notes

RUM09 steps, validation, acceptance criteria and notes were rewritten to match the TP1 first-lane decision and enforceable runtime roster. This review can close; the implementation remains pending.

## Findings

The Gate C step requires a currently deployed helper-on mixed-TP layout, while RUM01 and IMPLEMENTATION-HANDOFF select the actual flashnext-4gpu TP1 deployment as the first lane and explicitly defer mixed-rank qualification. RUM09 notes say unsupported profiles must be withheld, but the current runtime asset packer requires both named TOML profile files and has no narrowed candidate roster, so that exclusion is not presently enforceable. Resolve this before implementing the release gate: the first helper-on canary is the selected TP1 production topology with heterogeneous disjoint helper cards; helper-off is the functional/KL quality control. Keep mixed-TP compatibility gates separate and do not claim it unless the package roster includes and qualifies the affected names. Gate A must reuse the same matched SDK build for full plugin ABI/layout and package validation; current C7 objects and C9 host loader refusal are only partial evidence.

## Conclusion

Incorporated in RUM09. Gate C now targets the selected TP1 helper-on deployment, with the helper-off quality control separate. Mixed-rank activation is required only for profiles actually present in the candidate package roster. Gate E requires the package to enforce the roster; current packer limitations are named as an implementation gate. The v1.17 policy-off baseline is an old-pin workload reference, not candidate performance evidence.
