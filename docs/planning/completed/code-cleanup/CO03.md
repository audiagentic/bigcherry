# Eliminate duplicate overlay target reads

## Description

`tools/bigcherry/patch/overlay.py::copy_overlay()` reads every changed existing
target twice: once as raw bytes for the CRLF-sensitive equality check, then
again as text to populate rollback state. It also repeats the target
`is_file()` probe. Overlay materialization runs before anchored patch
application, so this duplicate filesystem work is paid by apply and dry-run
paths for every changed overlay file.

Reuse the first raw target read as the rollback value. This removes code and
filesystem I/O while preserving the existing equality, simulation, write, and
rollback contracts. It also makes rollback byte-faithful for CRLF targets
instead of normalizing their captured content through `read_text()`.

## Steps

1. Capture the existing target once as raw UTF-8 text.
2. Reuse that value for the unchanged fast path and rollback backup.
3. Add focused tests for I/O count, unchanged targets, dry-run behavior, and
   CRLF restoration.

## Detailed Solution & Technical Design

For an existing target, perform one `is_file()` probe and one
`read_bytes().decode("utf-8")`. Use the resulting `original` value for both the
comparison against overlay text and `backup[relative_str]`. Missing targets use
`None`, matching the existing rollback sentinel.

No API or caller changes are required.

## Validation

- Focused overlay unit tests: 3/3 pass.
- Changed existing target: target content reads drop from two to one; target
  file probes drop from two to one.
- Synthetic 2,000-file changed-overlay comparison (8 interleaved trials in a
  temporary directory): current median 86.4 ms; refactor median 69.4 ms
  (~19.7% lower elapsed time / ~1.24x throughput). This is supporting local
  evidence, not a hardware or end-to-end campaign benchmark.
- CRLF original content is restored byte-for-byte after rollback.

## Effort & Risk

Small, patch-domain-only refactor. Risk is limited to rollback capture
semantics; focused tests cover changed, unchanged, dry-run, and CRLF cases.

## Standards

Keeps one canonical overlay implementation, changes no public API, adds no
compatibility path, and preserves the patch transaction boundary.

## Acceptance Criteria

- No second target-content read is performed for changed existing files.
- Existing unchanged files remain no-op.
- Dry-run still exposes simulated overlay text without modifying checkout
  files.
- Rollback restores the original target bytes, including CRLF line endings.
- Focused tests pass.
