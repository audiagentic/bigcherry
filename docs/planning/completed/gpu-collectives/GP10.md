# Base-level (sub-llama.cpp) collective testing harness -- fast iteration on transforms without a full model/build cycle

## Description

Per explicit operator direction (2026-09-02): 'we should build tooling that allows us to test this at base level rather than always going through llamacpp or bc to validate and test - that way we can quickly assert failure or success - test out other transforms or methods to improve on base or our own.'

Today, testing a candidate collective mechanism (a new algorithm/protocol choice, a chunking strategy, the hierarchical bridge idea in GP09, an RCCL rebuild) requires either (a) rccl_qualify.py driving raw all_reduce_perf directly -- fast, but only tests RCCL's OWN candidates (algorithm/protocol/channels), not a genuinely different transform BigCherry might invent, or (b) building a full patched llama.cpp binary and running llama-bench/completion-bench -- correct as final validation, but slow (full rebuild cycle) and conflates the transform's own real cost with the full inference stack's overhead, making it hard to cheaply iterate on a transform idea before committing to a real patch.

SCOPE NARROWED 2026-09-02 per gpt-dev-agent review: v1 is ONE small compiled HIP/C++ harness, not a generic plugin/callback architecture -- a general transform ABI risks becoming a framework before it's earned, and this item only has ONE concrete consumer (GP09) right now. Add a generic ABI only after >=2 additional real transforms demonstrate the need for one.

## Notes

This is explicitly a lower-confidence, faster-iteration tier -- it does not confer qualification (GP07) or production-readiness (GP08) by itself. Exists specifically so GP09 (and any future candidate transform) doesn't have to pay a full patch-and-rebuild cycle just to get a rough go/no-go signal. Depends on nothing blocking; can start immediately, reusing rccl_qualify.py's existing subprocess-isolation pattern for anything that touches real RCCL.

GP10 COMPLETE (2026-09-02). Built tools/lab/gp10-collective-harness/nway_star_allreduce.cpp -- one standalone HIP/C++ harness (hipcc, no ROCm framework beyond raw HIP), generalizing patch 1001's pairwise pinned-host arrival-token mechanism to N ranks in a star pattern (each rank spins on all N-1 peers, then sums all N-1 peer slots). Compiles in ~5s, full 3-size sweep runs in well under a minute -- meets this item's own validation bar.

Real hardware results (Brutus, {0,1} and {0,1,2}, F32, 3 sizes): correctness exact (max_abs_err=0) at every N and size tested. Latency (median of 20 timed reps, HIP-event measured): N=2 30720 elem 364.72us, N=3 same size 613.36us (+68%); N=2 2621440 elem 24779.98us, N=3 same size 44321.29us (+79%) -- cost scales roughly linearly in N-1, as expected for a star pattern (every rank does N-1 serial blocking peer reads).

This harness is deliberately minimal (1 block, unvectorized) so its absolute numbers are not comparable to production's optimized 8-block vectorized kernel -- but the N=2->N=3 SCALING is the real, portable signal, and it's a structural property of the star pattern, not an implementation detail. See GP11 notes for what this means for the N-way design choice.
