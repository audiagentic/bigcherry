# Diagnostics package: separate VALIDATE (qualification) and OPTIMIZE (performance) tools sharing one identity model

## Description

Per gpt-dev-agent deep review (2026-09-02), answering the operator's direct request for a set of diagnostics that allow us to validate and then test for optimization: use TWO separate execution tools sharing one qualification identity/artifact model, not one runner with two modes. Reason: qualification deliberately executes crash-prone/untrusted RCCL cases in isolated subprocesses (rccl_qualify.py's whole design); optimization must categorically refuse to run an unqualified case at all. Different safety contracts belong in different entry points, not a --mode flag on the same tool.

BASELINE REQUIREMENT (operator direction, 2026-09-02): 'baseline is native llamacpp rccl.' OPTIMIZE's arm set MUST include an unmodified/stock llama.cpp build using its own default RCCL path as a required baseline arm, in addition to BigCherry's own providers (rccl / internal / corrected hybrid / meta). Every comparison this tool produces must be able to answer 'is BigCherry's dispatch actually better than doing nothing' via this baseline, not only 'which BigCherry provider is fastest among itself.' Explicit failure bar: for any topology, if the best BigCherry arm does not beat both this native baseline AND meta/layer-split, that is a failure for that topology (see GP03's rescoped consolidation notes) -- OPTIMIZE's output must make this comparison directly visible, not require a human to cross-reference two separate reports.

Recommended shape:
tools/bigcherry/profiling/ (existing, extended by GP07)
    rccl_schema.py              shared compatibility/topology/op/result model
    rccl_qualify.py             one crash-isolated RCCL Tests case
    rccl_qualify_campaign.py    reusable qualification matrix
tools/bigcherry/campaign/ (new file in the existing campaign domain)
    collective_benchmark.py     end-to-end provider performance comparison

VALIDATE produces a durable qualification artifact keyed by RCCLCompatibilityRevision + TopologyIdentityV1 + ReductionOperationSignatureV1 + RCCL candidate. Required stage order: RCCL Tests process safety/correctness -> exact requested-vs-observed plan verification -> repeated fresh-process gate -> production test-hip-reduce correctness/provenance gate -> qualification PASS artifact. Low-level RCCL Tests correctness and BigCherry production correctness are DIFFERENT gates -- GP05 is the concrete proof why (raw RCCL F32 can be correct while llama.cpp's real production path intentionally BF16-compresses at ne>=32768).

OPTIMIZE takes a qualification_id as required input; if a provider needs RCCL and (revision, topology) has no exact PASS qualification artifact, that arm is refused outright, not silently skipped or downgraded. Compares native-llama.cpp-rccl (required baseline) / bigcherry-rccl / internal (exact F32) / corrected hybrid (0840) / meta using real end-to-end inference (pp512/pp2048/pp4096, tg128, MTP completion throughput where relevant), not all_reduce_perf microbenchmark latency -- reuse campaign.benchmark's existing interleaving/statistics/environment-isolation/bootstrap-comparison machinery (the same paired-schedule methodology GP03's own 1243 A/B/C validation used informally) rather than writing another one-off statistics runner. Generalize its scheduling primitive to arbitrary named arms if the current native/replay-specific semantics don't already support that.

Every benchmark run references the qualification_id it depended on; no benchmark result may itself confer RCCL admissibility -- that authority belongs solely to the VALIDATE side's artifacts.
