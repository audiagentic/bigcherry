# Extend HI18 correctness-harness analytical bound to cover the BF16-compression regime (ne>=32768, <=2 devices)

## Description

Found 2026-09-02 while running GP04's real-signature pre-flight: HI18's reduce_correctness.py analytical F32 summation error bound (gamma=(D-1)*u/(1-(D-1)*u), u=2^-24) assumes pure FP32 precision throughout, but upstream llama.cpp's own ggml_backend_cuda_comm_allreduce_nccl() (ggml-cuda.cu ~line 1075) intentionally compresses BOTH ranks' F32 data to BF16 before the NCCL collective, then converts back, whenever element_count crosses a hardcoded per-device-count threshold (ne<32768 for n_backends<=2; ne<131072 for 3; ne<262144 for >=4) -- a deliberate bandwidth/precision tradeoff, not a bug.

Real hardware evidence (2026-09-02): the two large real-production stress signatures (element_count=2621440/[5120,512,1,1] and 2606080/[5120,509,1,1], from artifacts/hardware/20260820-qwen38-mtp-dual-xtx/reduction.jsonl) both fail HI18's current FP32-only bound by ~30,000x (measured abs error ~0.00095 vs bound ~3.4e-08) on the RCCL provider specifically, while META (a different, non-BF16-compressing reduction implementation in this codebase) computes the exact same input correctly. Root cause confirmed via source read (ggml-cuda.cu:1053-1128) plus exact threshold bisection on real hardware (PASS at ne=30720, FAIL at ne=35840, bracketing the real ne<32768 constant precisely) plus two independent RCCL-bypass confirmations (bare rccl-tests all_reduce_perf, and a standalone hipMalloc+ncclAllReduce reproducer with no ggml/bigcherry code at all) both passing cleanly at the same element count -- proving RCCL itself is correct and the harness's tolerance model is the actual gap.

No env var currently exists to force the FP32-only NCCL path for correctness testing (checked: ggml-cuda.cu's only related knobs are GGML_CUDA_ALLREDUCE for provider selection and GGML_CUDA_AR_BF16_THRESHOLD for the SEPARATE, currently-unwired 'internal' provider from patch 1001 -- see GP03's own notes on that mechanism).

IMPLEMENTED AND TESTED (2026-09-02). Went with option (a) from this item's own steps: extended the analytical bound to be BF16-aware, rather than excluding cases or forcing a synthetic FP32-only path that wouldn't match real production behavior.

tools/bigcherry/tuning/reduction.py:
- Added BF16_ULP (2^-8, BF16's real unit roundoff) and NCCL_BF16_WIRE_THRESHOLD_BY_DEVICE_COUNT (32768/32768/131072/262144 for device_count 1/2/3/>=4, matching the pinned source's real hardcoded constants) plus nccl_bf16_wire_threshold() and provider_uses_bf16_wire() helpers.
- analytical_error_bound() takes a new bf16_wire keyword -- widens the bound by BF16_ULP * sum_abs[i] on top of the existing F32 gamma term when set, otherwise unchanged (zero artificial slack for exact-F32 runs).
- Restructured evaluate_case()/evaluate_provider_run() so the bound is computed PER PROVIDER RUN (keyed off run.effective_provider -- the real servicing provider, not just what was requested -- and that run's own element_count/device_count), not once per case shared across every arm. This was the real fix: BF16 compression is provider-specific (only rccl does it), so a shared per-case bound was structurally wrong regardless of its width.
- Migrated evaluate_provider_run()'s signature from a precomputed allowed_abs_error list to sum_abs (per CLAUDE.md 'always migrate up' -- no compatibility shim, every existing caller including tools/tests/tuning/test_reduce_correctness.py updated in the same change).

6 new tests added (Bf16WireCompressionBoundTests): threshold values match pinned source, provider_uses_bf16_wire gates correctly on both provider AND size, bf16 bound is strictly wider than the f32 bound, and -- the real behavioral proof -- an rccl run above the real threshold with a BF16-quantization-scale perturbation now PASSES, while the IDENTICAL perturbation on a meta run (any size) or an rccl run below threshold still correctly FAILS. 55/55 tests pass in tools/tests/tuning/test_reduce_correctness.py (49 original + 6 new), zero regressions elsewhere in tools/tests/tuning/ (one unrelated pre-existing failure in test_hi104_nested_runtime.py, a separate C++ tuner-codegen test that doesn't touch reduction.py at all).

Next (GP04's own scope, not this item's): re-run the full real-signature corpus (9 signatures from artifacts/hardware/20260820-qwen38-mtp-dual-xtx/reduction.jsonl + RV59's signature) with this fix in place and confirm the two real large-s1 stress signatures (2621440/2606080 elements) now pass cleanly through the rccl arm instead of spuriously failing.
