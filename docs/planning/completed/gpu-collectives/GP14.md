# Investigate: BigCherry default-RCCL baseline ~5.9% slower than native llama.cpp (dual gfx1100 decode)

## Description

Real, unexpected finding surfaced 2026-09-11 while running a native-llama.cpp 3-arm sweep for patch 1001 (internal AllReduce, see its README): BigCherry's own default RCCL AllReduce path measured ~5.9% slower than unmodified native llama.cpp's default RCCL path in the same config (96.52 vs 102.61 t/s, tg128, tierB-qwen9b-q6k, dual gfx1100, -sm tensor, r=5). This is NOT a defect in patch 1001 (1001 doesn't touch the RCCL path at all -- BC-baseline here has 1001 excluded). Caveat: native llama.cpp's own run had a high stddev (3.07 vs BC-baseline's 1.15) relative to the ~6 t/s gap, so treat this as a real signal worth investigating with more repetitions before drawing a firm conclusion, not a settled fact from a single 5-rep run.

## Notes

Real numbers (isolated scratch clone, pin 28ff0958291ce3465fabd7bd679d4b0edd742bd9, controller commit f91db8ce, resolve_source_composition/materialize_composition methodology): native=102.61+-3.07 t/s, bc-baseline=96.52+-1.15 t/s. If real (not noise), candidate causes worth checking: BigCherry's dispatch/autotune layer (GGML_HIP_AUTOTUNE) adding per-call overhead even in native/control mode; a telemetry or split-reduce instrumentation cost (0830) active by default; or a genuine difference in default GGML_CUDA_ALLREDUCE selection/threshold between BC's overlay and stock upstream for this device/model combination. First step: re-run both arms with more repetitions (r=20+) to confirm the gap is real and not within native's own noise band before investigating mechanism.

Ledger event chg_20260911_232110_ran-the-real-hardware-sweep-fo_3437 (mis-linked to PA19 initially, corrected here).

RESOLVED 2026-09-11: not real overhead from BigCherry's framework patches being present. Rebuilt via bigcherry-native:stock:linux-multi (dispatch layer compiled out, GGML_HIP_AUTOTUNE=OFF, no diagnostics) and re-ran the identical dual-gfx1100 tg128 test: 103.51 t/s (+-0.50) -- matches native llama.cpp's 102.61 t/s within noise. The original ~5.9% gap was from using bigcherry-native:control (GGML_HIP_AUTOTUNE=ON, the full tuner/dispatch runtime active) as the 'baseline' arm, which is not a fair parity comparison -- that's the heaviest, not the lightest, BC build option. Existing build-option axis (stock/native/control in config/recipes.toml's [build.*] entries) already isolates dispatch/tuning runtime cost cleanly; no patch-set restructuring was needed to resolve THIS specific finding. Closing as non-issue for the parity question; see PA20 for the separate, still-live discussion about whether to structurally split tuning-scaffolding patches out of patch-set.framework for clarity/build-size reasons independent of this runtime-overhead question.
