# Patch package and validation-policy alignment for RO19-RO22

## Notes

Read docs/reference/patches/PATCH_AUTHORING.md, PATCH_SYSTEM.md, PATCH_REFACTOR_RUNBOOK.md, PATCH_VALIDATION.md and the canonical docs/reference/testing/PATCH_VALIDATION.md. The RO19-RO22 implementation packet must distinguish package construction from validation readiness and must use the existing Experiment Contract, validation campaign, and evidence machinery.

## Findings

Every new production patch must be a package directory named after its patch ID with patch.toml and patch.py. README.md, validation.toml, validation/, and evidence/validation.json become mandatory when the patch enters validation; they are not fabricated for an untested source capture. Experiment Contract is the scientific authority; validation.toml is only an execution adapter. patch-validate inspects existing evidence and does not execute a campaign; real execution uses bigcherry.patch.validation_campaign. Validation uses control/subject roles, which must not be conflated with stock/tune/replay. Current real contract execution is RD08-specific, so CM1 cannot claim ported-benched/validated until a CM1 contract and real named-check executor exist. Multi-contract validation is unsupported.

## Conclusion

Update RE30 and RO19-RO22 to make package lifecycle, contract binding, validation execution, evidence freshness, and status claims fail-closed. Do not create validation evidence during RO19 source capture.
