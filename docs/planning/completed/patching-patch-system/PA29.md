# Atomically migrate live framework/native consumers to semantic sources

## Description

Cut over real consumers after PA28 and PA34. This is a semantic migration, not global string replacement: the current `source.bigcherry-native` is a framework+upstream-fixes control source, while `source.bigcherry` is the release source with validated enhancements. Those roles must remain distinct.

## Steps

1. Inventory every live reference to `patch-set.framework`, `source.bigcherry-native`, and any command/config that assumes a framework-only source. Classify occurrences as live code/config/current docs, test fixture, planned-deletion reference, or immutable historical provenance.
2. Map current control/baseline uses of `bigcherry-native` to `bigcherry-serving-base`.
3. Keep release uses on `source.bigcherry`, while changing that source's patch-set composition from framework to serving-core.
4. Move record/tune/campaign consumers that actually require tune/record support to `bigcherry-tuning`.
5. Move telemetry/direct-op qualification consumers to `bigcherry-qualification` or an explicit named experiment over it.
6. Update campaign profiles, trees, CI/docs, and tests in one migration series. Do not edit historical plans/reviews/ledger receipts merely to erase old names.
7. For every migrated consumer, resolve before/after selector identity and document whether equivalence is expected or the change is intentional.
8. Do not delete the old names in this item; PA30 needs both old and new compositions for direct comparison and PA31 owns removal.

## Detailed Solution & Technical Design

Use PA34's authoritative selector identity and existing campaign/source resolvers. No temporary recipes, alias sources, or fallback from a missing new source to an old one. Build profiles (`stock`, `native`, `record`, `tune`, `replay`) are a separate axis from source composition and must not be renamed just because source names change.
