# Source/patch identity hardening: atomic metadata writes + cross-process plan locking (L6.1/L6.2)

## Description

Review found canonical campaign metadata (campaign/build.py::materialize_source()) uses plain write_text() for its metadata, while HI82 (patch/source.py) already uses temp-file + flush + fsync + os.replace(). A crash mid-write can leave truncated canonical-campaign metadata beside an otherwise-valid source worktree. Separately, two processes computing the same materialization plan can race to create/use the same worktree/cache record; current behavior is described as 'largely fail-closed but can create false corruption/partial-state failures' rather than cleanly handling the race. NOT yet independently verified against current source this session.

## Steps

1. Extract HI82's existing atomic-write helper into a shared utility (atomic_write_json(path, document, fsync_file=True, fsync_parent=True) per review's suggested signature) and have campaign/build.py's materialize_source() use it too, instead of maintaining two implementations.
2. Add plan-scoped locking: <work-root>/locks/source-<plan-id>.lock, held across inspect/reverify-cache -> create-worktree-if-needed -> apply-composition -> attest-output -> atomically-publish-metadata. Must be process-safe, auto-release on process exit, have an explicit timeout/error (never hang forever), and avoid fixed Path.parents[N] assumptions.
