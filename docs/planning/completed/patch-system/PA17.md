# Campaign source-cache hardening: read-only metadata + optional re-materialization proof

## Description

GPT value-validation (2026-08-27, req_15d491b604054c30) concluded PA13's full orchestration-unification scope is NOT worth doing -- source/identity.py already centralizes the real shared Layer-7 primitives; the remaining plan->materialize->verify orchestrations in campaign/build.py and patch/source.py (HI82) are genuinely different policies (different identity payload shapes/hash namespaces serving different real purposes -- e.g. campaign's patch_set_id/classification deliberately prevent cache-aliasing HI82 doesn't need; HI82's variant-transform identity has no campaign equivalent), and forcing them into one shared function would change real behavior (HI82 calls apply_all() once per patch in a loop -- campaign calls it once for the whole composition; HI82 leaves a manifest-less partial dir for next-attempt cleanup, campaign removes it immediately on failure). This item replaces PA13 with the two concrete missing safety properties campaign actually lacks, backported directly into campaign's existing implementation with no shared module and no identity/hash changes.

## Steps

C1: campaign's source metadata sidecar write (campaign/build.py's atomic_write_json(metadata_path, record) call in _materialize_source_locked) passes read_only=True, matching HI82's own write.
C2: add a strict re-materialization verification mode for campaign's cache-hit path: deterministically re-run workspace.materialize() with the already-resolved SourcePlan into a unique scratch worktree (sibling under work_root/sources, e.g. .verify-<plan_id>-<uuid>), compare the resulting source_tree_oid against the cached/verified one, then remove the scratch worktree via UpstreamRepository.remove_worktree() (registration-aware, not a bare rmtree).
C3: run this verification AFTER the existing cheap attestation/re-derivation checks and BEFORE returning cached metadata, inside the SAME per-plan_id lock _materialize_source_locked() already holds -- no new synchronization model.
C4: registration-aware scratch cleanup on both success and failure paths (mirrors HI82's _verify_by_rematerialization's own finally-block cleanup).
C5: initially gate C2 behind an explicit strict/release/source-validation mode, NOT unconditionally on every cache hit -- GPT's flagged concern: with N campaign lanes sharing one cached source plan, always-on re-materialization means every waiter behind the plan_lock repeats a full worktree-add+overlay+composition+tree-hash before releasing it, turning the source cache into repeated rebuilding. Benchmark before considering always-on.
C6: explicitly do NOT touch: HI82's identity schema, campaign's materialization identity, either overlay-hash algorithm (sha256 sorted-entries vs blake2b personalized), source_key/materialization_plan_id namespaces, or either module's transaction/cleanup boundaries -- these are real, deliberate differences, not drift to converge.
C7: regression test equivalent to PA14's original adversarial case -- mutate the cached worktree's tree AND forge every self-consistent metadata field to match; ordinary attestation/re-derivation checks (already in place) can be made to agree with a sufficiently thorough forgery, so this must be the one test that specifically exercises the NEW strict re-materialization path rejecting it.
