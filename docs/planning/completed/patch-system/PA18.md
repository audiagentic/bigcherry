# Package-only patch layout and patch-owned record migration

## Description

Replace the mixed flat/package patch layout with a package-only layout as directed. Audit and relocate patch-specific reference evidence, test fixtures, helper sources, and documentation to the owning patch package. Retain shared patch-system documentation and project-wide evidence only where authority or cross-patch aggregation requires it.

## Steps

- Establish a documented package contract that distinguishes patch-local documentation/helpers/fixtures from permanent domain tests and repository-wide evidence indexes.
- Migrate each root-level patch module to a package, converting catalog metadata to patch.toml and preserving its application identity before retiring the flat representation.
- Move 1005 and RD21/RD50 patch-specific validation bundles to owning packages and update every consumer/path.
- Decide and implement the authoritative location for cross-patch validation evidence without duplicating an evidence framework.
- Update the reference index and patch guides; repair invalid links and classify/relocate non-reference artifacts.
- Run patch discovery/catalog/validation tests and the deterministic check tier.

## Detailed Solution & Technical Design

Use the existing bigcherry.patch registry and packaged-patch contract; do not create a second loader or evidence mechanism. Each migration must prove old/new application equivalence against the same immutable base before the flat file is removed. Move only patch-specific records into a package. Keep permanent tests in tools/tests/<domain>/ when they validate shared behavior, and keep a single repository-wide evidence authority when records are consumed across patches; package-local tests/helpers may supplement that authority.
