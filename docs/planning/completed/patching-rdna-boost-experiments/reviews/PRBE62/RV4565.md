# Retire speculative Vulkan dual-queue design while Vulkan execution is paused

## Notes



## Findings

Upstream already provides the process-scoped GGML_VK_ALLOW_GRAPHICS_QUEUE flag, no local PRBE62/dual-queue patch or selected lane exists. Older per-MoE-graph two-queue design was explicitly rejected as disproportionate; the fork's AMDVLK MoE +4.7% comes with dense -8.1%, not BigCherry, and Vulkan implementation remains paused. Duplicate queue scheduler not warranted.

## Conclusion

Future Vulkan resumption goes through RRVP02 provider/driver/queue-family discovery first. Only if a real installed AMDVLK/proprietary-driver lane changes compute family on the pinned binary should the existing upstream process flag be benchmarked, with transfer/sync, multi-request, MoE+dense/pp and CI95-low >=3% guarded evidence. A dual-queue *new* plan is permitted only with independently demonstrated >=5% mixed-process E2E opportunity after process flag and transfers are accounted for. No Vulkan patch, hardware job or default-on switch is authorised by this archived research.
