# Fan out cold Radiance CI builds across parallel jobs; keep warm builds one job

## Description

A cold Radiance CI build (every pin bump: no compiler cache for the new pin) takes about 60 minutes on one 4-core GitHub runner: engine 21 min, then libr3 18.5, bc-iqr 5, libr2 2.7, moe-remote/ngram/bc-gfx12 ~4 and component tests 4.5, one after another. Components depend only on the engine's runtime prefix and composed source. Warm builds (~4 min) must not get slower, and a split adds an image pull, cache restore and artifact transfer per job (~2-3 min), so fan out only when the build is known to be cold. Owner decision 2026-11-28: split only when cold.

## Steps

1. Cold detection: compiler-cache keys carry the pinned upstream revision; a lookup-only restore finds whether a cache for this pin exists (PR then main); none means cold.
2. Warm path: today's single build job, unchanged.
3. Cold path: an engine job builds the lane's engine and runtime prefix and hands on the prefix, composed source and build metadata; a component matrix (libr3, libr2, bc-iqr, the small rest) builds each component against that prefix and runs its component tests; an assemble job installs the outputs into the runtime home, records the same build plan and component digests the single job records, merges every job's compiler cache into one entry, and continues with packing and the release bundle as today.
4. The lane build gains engine-only and single-component stages through the existing build entry point; no second build system.
5. The cache prune keeps the newest entries under the new key format.
