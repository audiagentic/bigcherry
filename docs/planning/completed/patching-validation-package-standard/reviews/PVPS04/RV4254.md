# Reconcile producer tune/replay build use before cleanup

## Notes

Evidence inspected in task worktree: tools/bigcherry/patch/campaign/scaffold.py; tools/bigcherry/patch/validation_campaign.py; tools/bigcherry/e2e_smoke_campaign.py. No tests or hardware runs were performed.

## Findings

The proposed transfer claims tune and replay builds are built but never executed. Current code contradicts that premise: StandardCampaignScaffold.campaign_build_identities contains tune/replay/stock; validation_campaign.py passes tune_server/replay_server and tune_bench/replay_bench into Campaign; the activation stage executes the tune bench; e2e_smoke_campaign.py has execution paths for tune and replay servers/benchmarks. Therefore the proposed removal would erase a still-live identity and execution boundary. Retain PVPS04 as a separate active audit/optimization item and require an exact producer-path call graph before dropping any build. Historical records must remain verifiable; do not remove build identities or tune/replay functionality until each consumer is proven unused and migrated atomically.

## Conclusion

Do not supersede PVPS04 into PVPS01 on the current evidence. Update its scope to accurately reflect live tune/replay consumers and keep its lifecycle pending.
