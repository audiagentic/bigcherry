### ROOT CAUSE FOUND (2026-08-29) -- P1.10 confirmed, matches gpt's predicted hypothesis exactly

Re-ran the exact gfx1100+gfx1030 (devices 0,3) Ring/Simple 512KiB reproducer with AMD_LOG_LEVEL=4 (ROCclr verbose runtime logging). Immediately before the fatal error, the real log shows:

```
ShaderName : ncclDevKernel_Generic_4(ncclDevKernelArgsStorage<4096ul>)
Pcie atomics not enabled, hostcall not supported
AQL dispatch failed!
hipExtLaunchKernel: Returned hipErrorIllegalState
```

Root cause: RCCL's generic device kernel (`ncclDevKernel_Generic_4` -- the single fat-binary entry point per unroll variant identified earlier via enqueue.cc's `ncclGetKernelIndex`/`ncclKerns[]` table) declares a hostcall requirement in its kernel metadata. Hostcall requires PCIe atomics support from the target device/slot. This device pair does not have PCIe atomics available (consistent with HI84's separate finding that this box has no PCIe P2P bridge for ANY GPU pair, homogeneous or heterogeneous). ROCclr's AQL dispatcher correctly refuses to submit a kernel whose declared hardware requirements the target device cannot satisfy -- this is a real runtime capability check working as designed, not a bug in ROCclr itself. RCCL then surfaces that refusal generically as 'hipErrorIllegalState' / 'the operation cannot be performed in the present state', which is what all prior HI85/HI84 evidence saw without this level of localization.

P1.10 classification (gpt, confirmed): F (RCCL-side cause -- the generic kernel unconditionally declares a hostcall requirement) + J (ROCclr runtime manifestation -- AQL dispatch rejection). NOT A (code objects for both archs exist, confirmed via RQ05), NOT B (no per-rank kernel selection to be wrong -- same symbol used by all ranks), NOT H (no demonstrated event/stream lifetime violation).

Open question for P1.11 (repair direction), sent back to gpt: does the Ring/Simple AllReduce collective actually NEED hostcall functionality for anything in its real execution path, or does RCCL's generic kernel declare the hostcall requirement unconditionally/defensively even when the specific op/algorithm/protocol combination never uses it? If the latter, a scoped RCCL-source fix (make hostcall declaration conditional on actual use, or provide a hostcall-free kernel variant for atomics-incapable topologies) is plausible and admissible per the runbook's P1.11 repair-shape list ('heterogeneous-safe generic-kernel selection'). If the former (hostcall genuinely required for this collective's real work), this is likely Outcome B (source-backed rejection, retain META) territory -- the capability gap is real hardware/platform, not a fixable RCCL defect.

### DEFINITIVE confirmation via kernel driver boot log + gpt research corpus (2026-08-29) -- scope settled

`sudo dmesg`/`journalctl -k` (AMDGPU driver's own boot-time PCIe-atomics self-test, independent of RCCL/ROCclr/HIP entirely) shows exactly ONE line across the whole boot log:
```
amdgpu 0000:17:00.0: PCIE atomic ops is not supported
```
Only device 3 (6900XT, bus 17:00.0). No such line for 03:00.0 (XTX0), 06:00.0 (XTX1), or 09:00.0 (R9700) -- all three passed the kernel's own boot-time atomics test cleanly. This is the authoritative, cheapest, most direct discriminator available (predates and is independent of any RCCL/lspci reasoning) and it matches the lspci AtomicOpsCap/Ctl evidence exactly.

gpt's deep research (real prior art, not speculation) independently corroborates the mechanism and scope:
- ROCm GitHub issues #2429, #6074, #6520 document the EXACT same 'Pcie atomics not enabled, hostcall not supported -> AQL dispatch failed -> hipErrorIllegalState' failure on other RDNA boxes, root-caused the same way (absent/incomplete root-port AtomicOps completion capability -- a per-PCIe-path property, NOT a GPU-architecture or RDNA-generation limitation). #6520 and old issue #237 both document the exact same pattern we found: one CPU-direct GPU unaffected, one chipset-routed GPU on the same motherboard affected.
- No environment variable, kernel boot parameter (`iommu=pt` explicitly ruled out, both in the cited issues and by our own earlier log line being a red herring), or BIOS setting can manufacture missing root-port AtomicOps completion capability -- confirmed via the real Linux kernel `pci_enable_atomic_ops_to_root()` requirements (root port must support 32/64-bit AtomicOp completion; this one doesn't, per lspci AtomicOpsCap 32bit- 64bit- on that root port). Attempting to force it via setpci write is explicitly warned against (a cited report that tried this got a ROCm hang).
- llama.cpp upstream's own documented position: RCCL is optional/disabled-by-default on HIP specifically because it isn't universally beneficial; llama.cpp's internal (non-RCCL) multi-GPU path is the documented safe fallback -- i.e. BigCherry's META path is the same class of solution upstream already endorses, not an unusual workaround.
