# Machine-readable plan/contract lifecycle status, computed not maintained in prose

## Description

External review (2026-08-20): with 65+ RD backlog items plus a growing Experiment Contract registry, plan hygiene needs a COMPUTED status per item, not hand-maintained prose scattered across notes fields. Without this, plan count gets misread as implementation progress -- the review's core finding is that the discovery-to-plan gap is now closed, but the plan-to-proof gap is wide open, and nothing currently makes that distinction visible at a glance.

## Steps

Define and compute a real status enum per RD/EC item: discovered / planned / source-pinned / materialized / contracted / build-proven / trigger-proven / correctness-proven / measured / generalised / promoted / rejected / retired. Compute it from real signals already available (patch file exists = materialized, contract exists in config/experiment-contracts.toml = contracted, tests/CI pass = build-proven, telemetry trigger evidence exists = trigger-proven, etc.) rather than a human/agent hand-maintaining a status field that drifts from reality. Surface it in a generated status report.
