# Reporting: hypothesis, winners, non-trigger envelope, promotion decision

## Description

`report.py` shows hypothesis, source, exact winners, losing/non-trigger envelope, controls, boundaries, correctness, generalised rule, and promotion decision -- one human-readable report per contract that makes both wins AND rejections legible.

## Detailed Solution & Technical Design

Guide §12 step 12: "Report failures and losing envelopes as first-class results; rejected optimizations are useful evidence." This is a deliberate, explicit design requirement -- a contract report is not just a promotion certificate for winners, it's the permanent record of what an optimization does and does NOT help, which is exactly what makes the Appendix A patch-aware map (harvested from existing patch docstrings) valuable enough to preserve in the first place. A report for a REJECTED contract (e.g. one that only regressed controls, or never cleared its boundary envelope) is as much a deliverable as one for a promoted contract.

Minimum report sections (derived directly from the contract schema EC01 defines, so the report is a faithful rendering of what the contract declared plus what was measured against it):
- hypothesis (family, expected_effect, rationale) -- the CLAIM
- source (source_id, commits, atomic_part) -- the PROVENANCE
- exact winners -- signatures where the positive lanes actually won
- losing/non-trigger envelope -- boundary values where the hypothesis did NOT win, stated explicitly rather than omitted
- controls -- regression evidence per control lane
- boundaries -- the full swept-dimension results, not just the winning point
- correctness -- which gates (EC07) were required and their pass/fail state
- generalised rule -- the holdout-proven dispatch envelope from EC08, if any
- promotion decision -- EC09's verdict plus which requirement (if any) blocked it

## Validation

A rejected contract (failed a control regression, say) still produces a complete report with all nine sections populated -- report generation must not short-circuit on rejection. Cross-check: every field the report displays traces back to a section EC01's schema actually defines (no report field with no corresponding contract input) and every schema section EC01 defines appears somewhere in the report (no silently-dropped contract content).
