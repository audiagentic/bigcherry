# GPT review: EC02's contract-family enum is narrower than the guide's stated mission, and _percent() accepted NaN/Infinity

## Notes

Independent GPT review (req_fde980f630ff4a69) of EC02's backfill work. Confirmed: refusing to force-fit 10/15 materialized patches into the closed 5-value hypothesis.family enum (mmvq/mmq/mmvf/mmf/blas) was the correct call -- extending that enum with non-matmul values would blur runtime kernel-family identity with experiment classification. HOWEVER: the guide's own stated mission is to express EVERY imported optimization as a contract, and EC02's own code_samples table explicitly expects backfill coverage for non-matmul patches (RD19/RD20/RD04/RD13/RD22/RD26). Stopping at 5/15 contracts is real, valid progress but should not be read as complete Experiment-Contract coverage of the materialized patch set. Filed as EC16 (schema generalisation: an orthogonal experiment-target classification, e.g. target.kind/target.family, decoupled from the 5 runtime kernel families) so the gap is tracked as real follow-up work rather than silently left implicit. Also found and fixed (real, cheap bug, already committed): _percent() accepted NaN and +/-Infinity because `value < 0` is False for both -- TOML supports these values, so a contract could pass schema validation with a nonsensical threshold. Fixed with math.isfinite(), tests added, full suite green.

Secondary findings recorded but NOT acted on this pass (lower priority, real but not urgent): (1) the RD12/RD17 composition conflict is documented only in contract rationale prose, not machine-readable -- an automated planner has to discover it by attempting patch application rather than being told upfront; the natural fix belongs at the patch/transform composition layer, not the contract schema. (2) known_source_ids_from_external_sources() parses config/external-sources.toml independently rather than reusing sources.py's own load_registry() validation, risking two divergent ideas of "valid registry" over time. (3) RD21's target_kernel_gain_pct=0.6 is defensible as a pre-registered threshold, but the contract schema has no structural way to distinguish 'blocked on hardware, not yet evaluated' from 'evaluated and failed' -- currently that distinction lives only in prose (source_class/status fields elsewhere, not in the contract's own acceptance section).
