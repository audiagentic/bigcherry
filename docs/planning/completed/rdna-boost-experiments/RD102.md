# RD08-VDR2-NUMERIC: new contract testing RD08's VDR2 kernel under numerical-equivalence (not bit-identical) acceptance

## Description

RD08's real --run-rd08-contract qualification (2026-09-01, gfx1100, current pin b10705, gpt-oss-20B Q6_K) failed correctly at the bit_identical correctness gate: subject (VDR2) and control (VDR1) digests genuinely differ on the first tested decode shape/seed (ffn, seed=1), even though NMSE-style error vs a CPU reference matches closely. Luna and GPT (independently, both asked the same question at the time) agreed: RD08's bit_identical requirement must NOT be weakened after seeing this result -- it was a deliberate, documented contract-design choice (EC02/EC07) specifically testing the fork author's stated bit-identical claim, and that claim is now real-hardware-disproven. Do not mutate RD08's original claim.

Both independently suggested the correct path if VDR2 is still worth pursuing: a SEPARATE, new experiment contract with an explicitly numerical-equivalence (NMSE-tolerance-based) hypothesis, matching BigCherry's own normal dispatch-candidate correctness model, rather than retroactively changing what RD08 claims. This item tracks that follow-up: design and land a new contract (working id RD08-VDR2-NUMERIC or similar) that tests VDR2 as a numerically-equivalent-but-not-bit-identical decode kernel, with explicit acceptance criteria that acknowledge non-bit-identical output is acceptable for THIS contract's claim (unlike RD08's).

## Notes

Real determinism risk this new contract must explicitly address before promotion, not just measure NMSE and declare victory: PRBE20 (docs/planning -- decode vs speculative-verify bit-identity) already establishes that bit-identical output across decode/verify batches is a soundness precondition for MTP's speculative accept/reject logic in this codebase. A numerically-close-but-not-bit-identical kernel candidate can silently flip accept/reject decisions if draft and verify passes end up using different kernel variants for the same logical operation, and per-step numerical drift compounds over autoregressive generation. Any new numerical-equivalence contract for VDR2 must either (a) prove draft and verify always route through the SAME kernel variant in production (so cross-variant drift never actually occurs), or (b) explicitly scope acceptance to exclude speculative-decode/MTP workloads, or (c) measure and bound end-to-end output-trajectory divergence directly, not just single-call NMSE. Do not promote VDR2 under a numerical-equivalence contract without addressing this.

Also pending, separate from the new-contract question: patches/1204_rd08_q6k_mmvq_vdr2/validation/rd08_correctness.py has a real, unrelated harness bug -- find_digest_for_tensor()/find_metric_for_tensor() search test-backend-ops stderr for a tensor named "dst", but test_mul_mat's real output tensor (confirmed in vendor/llama.cpp/tests/test-backend-ops.cpp) is always named "out". Every digest comparison has been silently returning None/None and failing for the wrong reason. Both Luna and GPT recommend fixing this (dst->out) regardless of the numeric-equivalence question, adding a regression test, and re-running --run-rd08-contract so committed evidence reflects the real digest mismatch instead of the misleading None/None failure. This is separate, smaller, uncontroversial work that should probably land first.

STALE-TEXT CORRECTION 2026-09-08: this item's description previously still described the rd08_correctness.py tensor-name bug ("dst" vs "out") as unfixed/pending. That work is RD103, already completed (commit b85a2703, 2026-09-01) -- the harness now correctly reads the "out" tensor, and --run-rd08-contract was re-run afterward producing REAL, non-None digest evidence (patches/1204_rd08_q6k_mmvq_vdr2/evidence/validation.json, record index 1): subject/control INPUT digests match (79bd031982421642 both sides, proving identical seeded input), but OUTPUT digests genuinely differ (189c251605d57481 vs 7492b4714c001936) on the first tested shape/seed. max_control_regression_pct also currently reads 1.57374% against the contract's 1.0% budget -- a secondary, separately-tracked performance regression, not part of this item's own bit-identical question.

Second independent GPT review (req_095fa62eda6445d3, 2026-09-08, requested after the user asked for a sanity check on whether this could be a harness/environment artifact rather than a real finding): confirmed the finding is real, not an artifact. No credible concurrency/environment explanation exists -- RD08's MMVQ reduction is a fixed warp-shuffle, not an unordered atomic race, so same-kernel-run-twice nondeterminism is not a plausible cause; the isolated-worktree harness design is sound. The REAL mechanical cause: VDR1 does two separate `d * partial_sum` multiplications, each independently fed into the warp reduction; VDR2 combines the partial sums into one accumulator BEFORE multiplying by `d`, redistributing work across lanes differently before reduction. FP32 add/multiply is non-associative, so this reassociation changing rounding -- while numerically negligible (matching NMSE) -- is EXPECTED to change exact output bytes; it is not by itself evidence of an off-by-one/indexing bug in VDR2. The fork author's own '1194/1194 tests OK' claim was never proof of bit-identity, since that suite is NMSE/tolerance-based, not an exact byte comparison. This GPT review also confirmed bit_identical was the CORRECT bar to have set for RD08 specifically (it was pre-registered to test a real, falsifiable bit-identical claim) -- RD102's own numerical-equivalence-contract proposal remains the right separate follow-up, not a retroactive weakening of RD08's own claim. One minor harness hardening opportunity noted (not required, not blocking): rd08_correctness.py does not pass an explicit `-b <backend>` filter to test-backend-ops, which theoretically could let device enumeration differ between the two processes' runs; GPT judged this hardening-worthy but not a credible explanation of the observed divergence, since RD08 does not touch device enumeration and HIP enumeration order is stable in practice.

Both Luna and GPT sanity-checked this on 2026-08-22/2026-09-01 (original review, request-id not recorded) and again by GPT on 2026-09-08 (req_095fa62eda6445d3, this session) -- two independent passes agree. This item (RD102's own new-contract proposal) remains open/pending and unaffected by either review; nothing here should be read as walking back the bit_identical requirement for RD08 itself.
