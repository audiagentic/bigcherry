# HIP peer-to-peer copy corruption on Windows/RDNA4 (from RD74 fork investigation)

## Description

Filed from RD74's closure (fork investigation of MrLordCat/llama.cpp-rdna-lab, 2026-08-20). While the fork was testing RD74's ORIGINAL hypothesis (pinned host staging -- which it REJECTED with real negative data), the investigation surfaced a different, genuinely useful finding: HIP peer-to-peer copy corrupts data on a Windows / RDNA4 configuration.

This was NOT RD74's hypothesis, so it is tracked here rather than mutating RD74 into an unrelated bug. Relevance to BigCherry is unconfirmed: SPLIT_REDUCE uses peer access (hipDeviceCanAccessPeer / peer-copy in the reduction path), so a peer-copy corruption bug on a Windows+RDNA4 config could matter IF such a config is ever a deployment target. The local Windows workstation is gfx1100 (RDNA3); Brutus is Linux -- so Windows/RDNA4 is not a current known deployment, which is why this is a low-priority assess-first item, not an active defect.

- If no relevant config exists: close as not-applicable to current deployment targets, retaining the reproducer evidence in the fork findings.

Assessment (offline; no hardware needed since no Windows/RDNA4 target exists):
1. The only HIP peer-COPY in the materialized source is the generic UPSTREAM multi-GPU tensor path in ggml-cuda.cu: cudaMemcpyPeerAsync (lines 873, 2802), fired only when src/dst are on different physical devices AND peer access is enabled; disabled wholesale by #ifdef GGML_CUDA_NO_PEER_COPY. The can-access/enable queries (cudaDeviceCanAccessPeer/EnablePeerAccess at 425/427/667) map to hip* via vendors/hip.h.
2. Correction of this item's stale premise: SPLIT_REDUCE in BigCherry's CUDA backend is NOT a "peer-copy reduction path." It appears only as the HI58 telemetry observation hook (hip-autotune-reduce-telemetry.cpp/.h), which QUERIES hipDeviceCanAccessPeer for D x D topology but performs NO peer copy. The real P2P exposure is the generic upstream offload path in (1), reachable only on multi-device + peer-access.
3. BigCherry's own patches add NO peer-copy/P2P (grep patches/*.py: none).
4. Deployment targets: local Windows = gfx1100 (RDNA3); Brutus = Linux; RDNA4 (gfx1201) is a Linux target, not a Windows target. No Windows/RDNA4 multi-GPU target exists, so the finding's demonstrated trigger (Windows/RDNA4) does not apply.

Re-evaluation triggers: (a) a Windows/RDNA4 multi-GPU deployment target is added, or (b) peer-copy corruption is DEMONSTRATED (reproduced, not merely suspected from architecture) on Linux/RDNA4.
