DEPENDENCY EDGES:
- RD09 (per-graph Q8_1 activation cache) is a hard prerequisite for RD10, RD11, RD14, RD15 (all consume the cache RD09 introduces). Nothing in that family can be implemented before RD09 lands.
- RD05/RD06/RD07 (RDNA4 WMMA + Q6_K MMQ, all from commit 18fc188f6) share the same source lines in fattn-tile.cuh and the mmq family -- must be sequenced together, not implemented independently, or they will re-diff against each other's changes.

CONFLICT EDGES (mutually exclusive without a design change first):
- RD10 (RMS norm direct Q8_1) vs patch 1004_rms_norm_mul_rope_fusion.py: BOTH target the same RMS-norm fusion point. Cannot both apply as independent textual patches. BLOCKED until a fusion-capability control point is designed that lets 1004's existing fusion and RD10's Q8_1-write compose (or until one subsumes the other).
- RD16 (SSM conv-output L2 norm pair) vs 1004: same collision family (norm.cu), same blocking condition.
- RD18 (IMRoPE + SET_ROWS BF16 fusion) vs 1004: same collision family (rope.cu) -- this exact dependency was already called out in RD01's own disposition text ("requires fusion capability/1004 control"), RD03 confirms it structurally via the file-overlap evidence from RD02.
- RD05/RD06/RD07 vs patch 1000_rdna4_mmq_q2k_q6k_fix.py AND patch 0300_mmq_forced_j.py (HI71): all three touch MMQ's Q6_K path and eligibility logic. Not a hard conflict (different concerns -- 1000 is a correctness fix, 0300/HI71 is launch-envelope safety, RD05-07 is a performance variant) but any RD05-07 implementation MUST be re-validated against HI71's dense-shape-aware ggml_cuda_mmq_variant_is_eligible() after landing, not merged as if HI71 didn't exist.
- RD08/RD12/RD21 (Q6_K MMVQ VDR=2, paired MMVQ matmuls, gfx1151 nwarps=2) all touch mmvq.cu/.cuh, which BigCherry's own 0600_mmvq_geometry.py and 0650_mmvq_native_variant.py (HI53 native-wrapper restructure) already substantially rewrote. These three external items also overlap EACH OTHER's target region -- if more than one is pursued, they must be sequenced (not built independently in parallel branches) to avoid re-deriving conflicting mmvq.cu diffs.
- RD13 (MUL_MAT+RESHAPE+ADD fusion) and RD17 (MoE topk-into-down-projection fusion) both touch ggml-cuda.cu's dispatch/fusion tables -- sequence, don't parallelize.

BASELINE / EXPERIMENTAL / DIAGNOSTIC / DEFERRED MEMBERSHIP:
- Baseline-safe, independent, no dependency or conflict edges: RD19 (Meta wrapper bypass), RD20 (attn_gate TP split correction) -- both touch only src/llama.cpp or src/llama-model.cpp, zero overlap with any BigCherry patch. These are the lowest-risk candidates to implement first, per RD02.
- Experimental-independent: RD04 (flash-attn native-BF16 tile family) -- no BigCherry patch overlap on its core files, only common.cuh needs adaptation.
- Experimental-dependent (gated on RD09): RD09 itself, then RD11, RD14, RD15 (RD10 excluded -- see conflict edges).
- Experimental-interaction, sequence required: RD05/RD06/RD07 (Q6_K MMQ + WMMA), RD08/RD12/RD21 (MMVQ family), RD13/RD17 (ggml-cuda.cu fusion family).
- Deferred, MUST NOT enter any production arm implicitly: RD21 (gfx1151-specific performance deferral -- diagnostic/opt-in only, per RD23's own scope) and RD22 (integrated-GPU host-buffer backout -- deferred on unresolved hardware correctness, evidence-only, never silently included).
- Blocked, excluded from all arms until unblocked: RD10, RD16, RD18 (1004 fusion-point collision).
- Infrastructure gate, required before ANY experimental RD patch is exercised outside pure diagnostics: RD23 (separate RDNA diagnostic support from performance-test support) -- this is a prerequisite for safely running ANY of the experimental-interaction items above without conflating a diagnostic probe with a production benchmark arm.

SAFETY GATES / PROMOTION STOP RULES:
1. No RD item may be promoted to a production arm without passing bigcherry's existing source_audit (33/33) and the dispatch-safety regression suite (tools/tests/test_dispatch_safety.py), same bar as HI-series fixes this session.
2. Any RD item touching MMQ or MMVQ eligibility (RD05-08, RD12, RD21) must be validated specifically against the HI71 dense-shape-aware launch-envelope check -- a regression there reintroduces exactly the out-of-bounds read class HI71 just closed. Stop rule: do not promote if HI71's regression tests (test_mmq_variant_is_eligible_checks_tail_padding, test_mmq_native_wrapper_dense_safety_precedes_native_return) fail or had to be weakened to accommodate the RD change.
3. RD10/RD16/RD18 (1004-conflicting) may not be implemented at all until a named fusion-capability control point exists in 1004 that both fusions can compose through -- stop rule, not a soft preference.
4. RD21/RD22 must never appear in the [campaign.standard] production lane list (recipes.toml) or any default arm -- they are opt-in diagnostic/deferred only, consistent with RD01's original disposition.
5. No production arm may include an item whose RD-level state is not 'completed' with real hardware evidence -- this mirrors RE15's own promotion discipline (HI34 BH promotion gate) and must not be shortcut for RDNA-boost items specifically.
