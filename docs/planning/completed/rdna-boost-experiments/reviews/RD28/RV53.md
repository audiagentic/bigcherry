# MMQ/MOE cluster (RD28/RD29/RD30/RD31/RD32/RD34): PORT-FROM-DIFF verdict was wrong -- source PRs target a deleted MMQ architecture

## Notes

Scope: RD28 (AMD-MMQ-001), RD29 (AMD-Q8-001), RD30 (AMD-MOE-001), RD31 (AMD-MOE-002), RD32 (AMD-MOE-003), RD34 (AMD-MMQ-002). An earlier validation pass classified all six as PORT-FROM-DIFF against AMD-Ecosystem/llama.cpp PRs #25/#32/#39/#63 (all merged in that fork). A follow-up patch-writing attempt found this classification wrong: all four PRs target ggml/src/ggml-cuda/mmq.cuh functions (get_mmq_y_host/device, mmq_get_nwarps_host/device, mmq_get_granularity_host/device, mmq_get_tile_y_k_padded_*, launch_mul_mat_q<type,mmq_x> two-template-param form, mmq_build_moe_block_map, the mmq_x_best tuning loop) that no longer exist in the b10502-pinned vendor tree. Upstream did a full MMQ kernel-selection rewrite between the AMD fork's base and our pin: those free functions were replaced by a table-driven ggml_cuda_mmq_config system (CASE(...) macro, per-arch config headers mmq-config-{pascal,ampere,blackwell,cdna,rdna2,rdna3,rdna3-5,rdna4}.cuh, rows_per_warp(), launch_mul_mat_q<type,mmq_x,fallback> three-template-param form).

## Findings

mmq-config-rdna3-5.cuh already exists in our tree with a full dedicated RDNA3.5 config table -- upstream independently absorbed RDNA3.5-specific MMQ tuning through a different mechanism than what these six items assumed they'd be porting. This is a structural incompatibility, not an anchor-drift problem a re-anchor could fix.

## Conclusion

Verdict flips from PORT-FROM-DIFF to NEEDS-REDESIGN for all six items. Gate before any new design work: compare the intent of each AMD-fork diff (tile-width/LDS occupancy for RD28, Q8_0 sub-piece for RD29, MoE block-map/tiling for RD30-32, MMQ tile geometry for RD34) against what mmq-config-rdna3-5.cuh's existing table already achieves -- some or all of this may already be covered. Items remain open (pending), re-scoped in their own notes; not superseded or completed.
