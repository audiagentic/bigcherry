# Upstream-equivalent-change detection for baseline/retirement (the "(or an equivalent)" half of RD95)

## Description

RD95 shipped a routine, automated ancestry gate that answers ONE question: is the tracked commit's exact SHA ancestral to the candidate pin? That correctly covers tracked commits that ARE upstream commits (the ggml-org SHAs, e.g. RD50 #16008, RD98 #26909), but NOT a FORK commit that landed in upstream mainline under a different (rebased) SHA -- e.g. an AMD-PR fork merge commit whose change later reaches b10xxx as some other commit. The RD95 card's "or an equivalent" clause is exactly this case, and RD95's exact-SHA gate deliberately does not assert it (fail-closed: an unknown/unresolved fork SHA is never treated as redundant).

This item is that missing half: detect when a tracked FORK commit's change has landed upstream-equivalently, so the matching RD item can be retired as baseline. This is the "exact patch-equivalence resolution" that sources._check already flags as a separate, unsolved problem.

Preferred tractable design (phase 1 -- manual annotation, no heuristic risk):
- Add an OPTIONAL per-tracked-entry field `upstream-equivalent = <40-hex>` to config/external-sources.toml (validated like `original`: 40-hex or absent).
- Extend sources.baseline_candidates_at_pin to check BOTH `commit` and `upstream-equivalent` (when present) for ancestry to the candidate pin; a match on either flags the RD item as now-baseline.
- Populate `upstream-equivalent` by manual annotation when a fork PR's change is confirmed to have landed upstream (low frequency, high signal). No auto-matching heuristic in phase 1.

Phase 2 (stretch, do NOT start before phase 1 is real): automatic fork-commit -> upstream-equivalent matching by patch-id / diff-content similarity. Higher false-positive risk; needs its own validation.

Out of scope: mutating planning cards (still the MCP single-writer domain); the exact-SHA gate itself (done, RD95).

## Steps

- Add optional `upstream-equivalent` (40-hex) field to the external-sources tracked-entry schema + load_registry validation (accept 40-hex or absent, like `original`).
- Extend sources.baseline_candidates_at_pin: for each tracked entry, check ancestry of `commit` AND (if present) `upstream-equivalent`; include the entry in candidates if either is 'ancestral'. Keep fail-closed (unknown never counts).
- Unit tests: a tracked entry with upstream-equivalent ancestral to the pin IS flagged; without the field, behavior is unchanged (exact-SHA only); a non-ancestral equivalent is not flagged.
- Update the sources check/docs + the RD95 gate comment to reference the equivalent-check.
- Manually annotate upstream-equivalent on any currently-tracked fork commit confirmed landed upstream (likely none at b10502 -- verify, don't assume).
