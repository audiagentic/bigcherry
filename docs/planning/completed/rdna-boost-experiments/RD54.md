## RESULT (2026-08-24, dev-gpt-agent session ses_76b0fef0c94c434a + independent real-hardware verification)

**Disposition: VALIDATED, NO PORT.** BigCherry's existing measured/learned MMVQ dispatch already discovers -- and here exceeds -- PR #20831's hard-coded nwarps policy, satisfying this item's own acceptance criterion exactly.

### Upstream claim verified first
PR #20831 ("cuda: dynamic MMVQ nwarps for narrow matrices", still OPEN, head 40dc8a1bebcb2570ea56921a2d1a4aa4d750e170, 45+/20- confined to ggml/src/ggml-cuda/mmvq.cu) pulled and read directly via `gh pr diff`, not taken on GPT's word: adds, for RDNA3_0/RDNA4 MMVQ tables only, `max_useful_nwarps = (blocks_per_row * qi) / (vdr * warp_size)` then rounds down to the nearest power-of-two <= native max. Confirmed against real pinned b10502 source: `ncols_x` is literally `src0->ne[0]`; `has_ids && ncols_dst > 1` routes to a real separate kernel (`mul_mat_vec_q_moe_launch`) that BigCherry's own forced-dispatch entry point (0650) already GGML_ABORTs on rather than silently misattributing -- so only ordinary width-1 (ncols_dst==1) decode is a valid comparison point. Confirmed RDNA3_0's real `calc_nwarps` table: Q8_0/ncols_dst==1 unconditionally returns 8, with zero K-awareness -- native genuinely wastes warps on narrow K today. All of this pinned as regression tests in tools/tests/test_rd54_mmvq_narrow_moe_coverage.py (committed 77590f9).
