## Detailed Solution & Technical Design

### CRITICAL FOLLOW-UP (2026-08-24, same day, user-requested): kernel-level wins do NOT hold end-to-end when forced globally

The 60.7%/16.3% numbers above are real, isolated, per-signature kernel timings. They are NOT a production throughput claim. Checked that directly, because the promotion pipeline itself already refused to certify these candidates for a reason worth stating precisely:

**Promotion was rejected, but not for weak statistics.** `tune-promote` on the real measurements returned `promoted: 0/5`. Both target rows show `promotion_status = rejected_no_correctness_evidence`, `reason = "native retained: no CPU-reference correctness evidence for this candidate"` -- despite `promotion.bh_accepted=True`, `p_value=0.0`, and tight 95% CIs (K=256: 60.68-60.88%; K=2048: 16.10-16.42%). The statistical case is airtight; what's missing is the *separate*, stricter CPU-reference correctness-evidence step (HI80/`hi80_generate_correctness_evidence.py`). That tool is **deliberately MUL_MAT-only** ("any non-MUL_MAT row is reported and skipped") -- both RD54 signatures are MUL_MAT_ID (MoE-routed), so the official promotion path is currently structurally blocked for this exact case, not merely "not yet run." This is a real gap worth its own follow-up item (BigCherry's correctness-evidence tooling doesn't cover MoE ops at all yet).

As partial reassurance: the tuner's own in-process GPU-vs-native comparison (computed during measurement itself, distinct from the missing formal HI80 evidence) already shows both winners match native to floating-point noise: K=256 exact (`nmse=0, max_abs=0`), K=2048 `nmse=1.52e-14, max_abs=2.38e-07` (FP32 rounding-level). Not a substitute for the formal pipeline, but a real, already-computed signal that these two candidates are not numerically broken.

**Real end-to-end throughput test** (since per-signature promotion is blocked, the only mechanism available is `GGML_HIP_FORCE_CANDIDATE`, which forces ONE named candidate globally for every matching-family call, not just the two target MoE signatures -- e.g. it also overrides the model's dense lm_head projection, an unrelated width-1 Q8_0 op). Same binary, same real Qwen3.6-35B-A3B Q8_0 workload, `-sm tensor`, tg128, 3 reps each:

| config | t/s |
|---|---|
| native (baseline, run 1) | 89.35 ± 0.57 |
| native (baseline, re-confirm) | 89.42 ± 0.53 |
| forced `nw1:rpb1:sk0` globally (K=2048's winner) | 85.19 ± 6.94 (**-4.7%**, high variance) |
| forced `nw1:rpb2:sk0` globally (K=256's winner) | 87.28 ± 3.28 (**-2.4%**) |

**Both forced configurations REGRESS real end-to-end throughput**, despite each being a real, statistically airtight win on its own target kernel. The isolated per-kernel gains are real but get outweighed once the same override also degrades other, unrelated width-1 Q8_0 ops that were never part of this item's target shapes (native's nw8 is presumably close to optimal for those, e.g. the large-N lm_head projection) -- this is exactly the failure mode BigCherry's real production mechanism (per-signature promoted-winner replay, not a single global override) exists to avoid, and exactly why `GGML_HIP_FORCE_CANDIDATE` is a diagnostic tool, never a production path.

### CORRECTION (2026-08-24, same day, further investigation with dev-gpt-agent session ses_05a713a4e4e44b2d): the -4.7%/-2.4% regression attribution above is RETRACTED as evidence of a candidate-geometry effect

The measurements above are kept as an audit trail, not deleted, but their causal interpretation does not hold up. What follows is why, with real data.

**The comparison baseline was wrong.** Forcing the dispatcher to explicitly select the *same* candidate as plain native (`GGML_HIP_FORCE_CANDIDATE=mmvq:native:v1` -- identical kernel, zero geometry change) still measured 88.01 ± 3.08 t/s against plain native's 89.61 ± 0.48 t/s, 5 reps each. This plain-native-vs-forced-native comparison was NOT itself interleaved, so given the large common-mode system-state swings found next, that ~1.8%-ish delta cannot be cleanly attributed to the force/dispatcher path alone -- it may include real force/dispatch overhead, contemporaneous system-state variation, or both. What it does establish cleanly: separately-measured plain native is not a valid matched baseline for a forced-candidate comparison, regardless of the exact split. So the original -4.7%/-2.4% numbers were computed against the wrong baseline (an interleaved plain-native-vs-forced-native run would be needed to cleanly separate these two effects, not yet done).

**The bigger issue: real, large, system-level throughput swings independent of candidate choice.** An interleaved run (`forced-native`, `forced-rpb1`, `forced-rpb2` back-to-back, 8 rounds, tg128) showed all three arms swinging together through roughly the same 78-89 t/s range round to round (GPU temps stayed ~42C per rocm-smi -- not classic thermal throttling; the exact mechanism, e.g. a discrete clock/power-state transition, was not identified). This is exactly the kind of system-level noise a non-interleaved, 3-rep, separately-timed block comparison (what produced the original -4.7%/-2.4%) cannot distinguish from a real per-candidate effect.

**Paired within-round comparison (controls for the swing, since all 3 arms in a round share nearby system state), n=7 complete rounds:**

| | rpb1 vs forced-native | rpb2 vs forced-native |
|---|---|---|
| per-round deltas | -0.23%, +3.33%, -1.77%, -1.59%, +5.81%, -11.61%, +0.06% | -0.06%, +1.97%, +2.00%, -1.81%, +6.14%, +0.07%, +0.11% |
| mean | -0.86% | +1.20% |
| median | -0.23% | +0.11% |

Neither reproduces anything resembling the original -4.7%/-2.4%. rpb1's mean is dragged down by one isolated -11.61% excursion (round 8 immediately after shows rpb1 back to 88.64, matching native) -- with that much dispersion, this does NOT establish an effect of either sign for rpb1 (neither a -0.86% regression nor its opposite); the honest reading is that global-force is inconclusive at sub-percent-to-low-single-digit scale, not that it's neutral or positive with confidence.

**Control validated:** confirmed via the real recorded workload that forcing `mmvq:native:v1` does not reroute any signature's real family -- 9/11 signatures naturally resolve to `mmvq:native:v1` already; the other 2 are `mmvf:native:v1` (a different family an `mmvq:...` force name cannot match). So `forced-native` is a legitimate matched control for the two generated candidates.

**Call-weighted kernel accounting** (`sum(calls * (forced_us - native_us))` across all 8 real Q8_0/width=1 signatures this workload produces, weighted by real per-signature invocation counts from the record-mode capture) predicts rpb1 +0.18% and rpb2 +0.29% -- i.e. a small, sub-percent, mostly-noise-floor effect. The paired interleaved results are consistent with an effect this small (not precise enough to confirm the exact figure, but no longer contradicted in direction/magnitude the way the original non-interleaved comparison was).

**What is actually established, precisely:**
- The original non-interleaved global-force regression claim is retracted as evidence of a geometry-caused throughput regression. It is retained above only as a record of an observed-but-confounded measurement.
- The global-force proxy is inconclusive at the scale that matters (sub-percent to low single digits) -- it does NOT prove an end-to-end win either.
- No claim is made about the swing's physical cause (thermal was checked and ruled out; the specific mechanism was not identified).
- The isolated per-kernel wins (60.7% at K=256, 16.3% at K=2048) are unaffected by any of this -- they were never in question.

**Revised disposition:** the mechanism claim stands unchanged (BigCherry's tuner discovers a real, measured win on the target narrow-K MoE shapes PR #20831 addresses, and even beats the PR's own formula on its control case) -- "no port needed" holds, since no one was proposing a global override either. A positive (or negative) real production throughput delta remains unestablished either way, because the only mechanism that can answer it correctly -- real per-signature promoted-winner replay -- is blocked by HI80's MUL_MAT_ID correctness-evidence gap (filed as HI105). `GGML_HIP_FORCE_CANDIDATE` has done its job as a diagnostic (it correctly forced the discovery of the baseline/interleaving methodology issues above) but is not a suitable tool for a production-effect measurement; the decisive experiment is HI105 -> real correctness evidence -> promotion -> per-signature replay -> a clean tg128 A/B with no global override involved.
