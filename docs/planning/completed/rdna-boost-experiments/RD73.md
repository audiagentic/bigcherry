# FORK-MTP-003 (re-scoped): stable shape-fingerprint key for the graph cache (was: warm speculative verification widths)

## Description

RE-SCOPED 2026-08-23 (plan-hygiene, from the fork investigation of MrLordCat/llama.cpp-rdna-lab): the original 'warm speculative verification widths 1..n_max+1' framing was never the actual mechanism. The real finding (commit 7f2e7e4a, fork) is a STABLE GRAPH-CACHE KEY: the cuda-graph cache was keyed by an unstable node pointer, so speculative verify shapes almost never hit a warm slot; keying on an FNV-1a shape fingerprint (node count + first/last node op/name/dims) makes recurring verify shapes replay a warm graph. Same practical outcome (warm MTP verify), different implementation.

Backend: originally filed Vulkan-primary, but the found commit is ggml-cuda (HIP/CUDA graph cache) -- confirm which graph-cache subsystem BigCherry's speculative/MTP path actually uses on the target lane before porting. Source status: real measured gain in the fork (verify ubatch sync 150ms -> 57ms, 3.8k-node Qwen3.6-27B graph), 34-line one-file change, not merged upstream. Q8_0 relevance: High (MTP verify shapes).

## Detailed Solution & Technical Design

RE-SCOPED HYPOTHESIS (2026-08-23, from the fork registry entry for 7f2e7e4a): the real finding is NOT 'prebuild widths 1..n_max+1'. It is: the CUDA/HIP graph cache was keyed by an unstable cgraph NODE POINTER, so speculative verify decodes minted a fresh never-warmed graph slot almost every round; keying instead on a stable FNV-1a shape fingerprint (node count + first/last node op/name/dims) makes recurring verify shapes hit the SAME cache slot and get graph replay -- the same practical warm-MTP outcome the original hypothesis wanted, via a different mechanism.

Mechanism (commit 7f2e7e4a, 34 lines, one file: ggml/src/ggml-cuda/ggml-cuda.cu): graph-cache key = FNV-1a over (node count, first/last node op/name/dims) replacing the node pointer.

Measured (fork's own data): verify ubatch sync 150ms -> 57ms on a 3.8k-node Qwen3.6-27B graph. Not merged upstream. Vulkan-primary per original filing, but the mechanism is cuda-graph (ggml-cuda) -- verify whether the BigCherry port targets the HIP ggml-cuda graph cache or the Vulkan equivalent (Vulkan's graph cache is a different subsystem; check which one BigCherry's MTP/speculative path actually uses before porting).

same prompt, seed=42, temp=0, n_predict=200).

Patch application verified in the materialized source (FNV-1a offset basis
literal present at ggml-cuda.cu:2884).

| metric | control | rd73-only |
|---|---|---|
| **graphs reused** | **65** | **65** |
| large gaps >100us (count) | 615 | 614 |
| large gaps >100us (total) | 523.9 ms | 421.7 ms |
| throughput | 51.54 tps | 52.17 tps (+1.22%) |

**Graph reuse is IDENTICAL (65 = 65).** That is the direct measurement of the
mechanism: if the raw nodes[0] pointer key were unstable for recurring
speculative-verify shapes, control would show FEWER reuses than treatment. It
does not. The large-gap COUNT is also unchanged (614 vs 615) -- only total gap
time differs, with the same number of gaps, which is host-timing variance
rather than fewer recaptures.

**Conclusion: the pointer-instability the fork's fix targets does not occur on
bigcherry's pinned llama.cpp, and this now holds for the MTP speculative-verify
workload specifically, not just the earlier non-MTP qwen0.8b test.** The
earlier finding generalises; it was not an artifact of testing the wrong
workload.

The +1.22% throughput is NOT attributable to this patch and should not be cited
as a win: it is a single sample per arm, it is within the run-to-run variance
this project has already documented, and the mechanism that would have caused
it demonstrably did not activate. Claiming it would be reading a causal effect
into noise.

Why the fork saw 150ms -> 57ms and we see nothing is unresolved and worth one
line of caution for anyone revisiting: the fork ran a different pin, a
different model build (Qwen3.6-27B, 3.8k-node graph) and possibly a different
graph-node allocator behaviour. The port is faithful (byte-for-byte from commit
7f2e7e4a, verified against the real diff) -- the difference is in the base, not
the patch.

**Disposition: patch 1233 stays `state=untested` and unpromoted.** It is
correct and correctness-neutral (verified in the earlier cycle, and nothing
here contradicts that) but delivers no measurable benefit on this project's
hardware and pin. Recorded so this is not re-attempted a third time; if the pin
advances substantially, the cheap re-check is simply comparing `graphs reused`
between arms -- no full A/B needed to know whether the mechanism engages.



**2026-09-04 (LATER, CORRECTION): MY EARLIER "NULL / NOISE" CONCLUSION WAS WRONG.**

The note immediately above concluded, from an ad-hoc single-completion A/B, that
RD73's mechanism does not engage and that the observed +1.22% was noise. **That
conclusion is retracted.** It was based on (a) one sample per arm and (b) the
`graphs reused` counter being identical -- neither of which is an adequate test.

The standardised Experiment Contract has now been run
(`bigcherry.patch.validation_campaign --patch 1233... --run-rd73-contract
--rd73-corpus tools/bigcherry/bench/corpora/mtp-27b-v1.jsonl`, dual gfx1100,
HIP_VISIBLE_DEVICES=0,1, model tierL-qwen27b-q8). Real result:

```
metric            mtp_wall_tps
paired rounds     10 measured (+2 warmup), 12 control + 12 subject requests
geometric effect  +1.855%
95% CI            [+1.482%, +2.169%]   <-- excludes zero
bootstrap         10,000 resamples, seed 0
max control regression   0.0%
correctness gate  PASS (bit_identical)
resource gate     PASS (graph_cache_entries within limits)
trigger proof     PASS (1 lane checked, 0 untriggered)
promotion         FAIL -- 1.855% below the contract's required 3.0%
```

**So RD73 produces a real, statistically significant end-to-end gain on the MTP
workload -- roughly +1.9%, CI excluding zero, with zero regression on the decode
control and bit-identical output.** It fails promotion only because this
contract's own bar is 3.0%, which is a policy threshold, not a statement that
the effect is absent.

Unresolved tension worth recording rather than papering over: `graphs reused`
was 65 in BOTH arms in my ad-hoc capture, which is not what I would expect if
the stable-key mechanism were converting cold misses into warm replays. Either
that counter does not measure what I assumed, or the gain arrives by another
route. The contract does not settle the mechanism -- it settles the effect.
Anyone continuing this should treat the mechanism as open.

Methodological lesson, and the reason this correction exists: a single
completion per arm cannot resolve a ~2% effect against this project's own
documented 0.5-0.9% repetition noise floor, and I should not have drawn a
directional conclusion from one. The project has a paired/bootstrapped contract
path precisely for this, and it disagreed with me.

**Evidence status:** the contract artifacts are real and stored
(rd73-contract-qualification.json, rd73-mtp-lane.json, rd73-decode-control.json,
rd73-activation.json, each sha256-bound). However `patch-verify-evidence` still
reports missing-or-stale, because the GENERIC validator checks did not produce
qualifying artifacts: `performance` and `controls` error with "benchmark
artifact requires non-empty metrics", and `activation`/`correctness` are BLOCKED.
That is the same known adapter gap this patch's own validation.toml already
documents for correctness (the RD73-specific producer is not wired into the
generic check) -- it now demonstrably affects performance/controls too. Not
fabricated around; recorded as the real state.

**Disposition: patch 1233 stays `state=untested` and unpromoted** -- but for the
correct reason: it MISSES THE 3% PROMOTION BAR at a measured +1.86%, not because
it does nothing. If the bar were ever revisited, or if the effect were combined
with other gains, this is a genuine (if small) real win and should be
re-evaluated rather than dismissed.
