CLOSURE 2026-09-08. The isolated bench this item was 'awaiting' since 2026-08-19 has now happened, twice, independently:

1. Real --run-rd08-contract hardware qualification (2026-09-01, gfx1100, pin b10705, gpt-oss-20B Q6_K; patches/1204_rd08_q6k_mmvq_vdr2/evidence/validation.json): subject/control INPUT digests match (both processes generated identical seeded input), but OUTPUT digests genuinely differ (189c251605d57481 vs 7492b4714c001936) -- the fork author's bit-identical claim for VDR=2 is disproven, not a harness artifact (root-caused: RD103 fixed an earlier unrelated dst->out tensor-name bug that had been masking this with None/None; the re-run after that fix is what produced this real digest divergence). max_control_regression_pct also read 1.57% against a 1.0% budget.

2. Independent re-run this session via the NEW VA26 qualification_execution orchestrator + qualification_rd08 adapter (live gfx1100, isolated Brutus clone): produced byte-for-byte IDENTICAL output digests (189c251605d57481 / 7492b4714c001936) to run #1 -- confirming the divergence is deterministic and reproducible, not measurement noise -- plus a new data point: target_kernel_gain_pct aggregated across isolated+release_delta contrasts is 0.0163%, far below the 0.3% required threshold (RD08's throughput effect is negligible once measured in combination with the rest of the release, not just in isolation).

3. Root cause independently confirmed twice (Luna+GPT at the time RD103 landed, and a second GPT review this session, req_095fa62eda6445d3): VDR=2 combines partial sums into one accumulator BEFORE multiplying by d, while VDR=1 multiplies each partial sum by d separately before the warp reduction -- FP32 non-associativity makes this reassociation change exact output bytes even though NMSE is negligible. This is the EXPECTED signature of a reassociation-only change, not evidence of an indexing/off-by-one bug. bit_identical was the CORRECT acceptance bar for RD08's own claim, not a mistake.

Disposition: RD08 (the patch, 1204_rd08_q6k_mmvq_vdr2) FAILS its own qualification -- fails bit_identical, and separately fails on gain-in-combination. It stays in the catalog as state=untested (not validated, not promoted, not removed) with its real qualification evidence attached, per this project's own no-legacy/always-migrate-up and fail-closed doctrine -- there is no 'silently drop the patch' step here, the evidence record itself is the disposition. Do NOT reopen this item to chase a passing bit-identical result; that claim is real-hardware-disproven twice over. If VDR=2 is still worth pursuing, the correct path is RD102 (a NEW contract under numerical-equivalence acceptance, not a retroactive change to this one) -- explicitly separate, tracked there, not here.
