### Pipeline validation results -- real numbers, cannot be re-derived without re-running actual hardware workloads

**Run 1: Qwen3.5-2B (non-MTP, single GPU ROCm0), pipeline mechanics smoke test.**
Full pipeline proven end-to-end: repin(b10362) -> pull -> audit(34/34 pass) -> apply(12/12 core patches applied cleanly against a tree 98 commits newer than they were written for) -> build(record, 684/684 steps) -> record run (56 signatures, types mmq=[q8_0] mmvq=[q6_k,q8_0] mmvf=[f32] widths=[1,2,4]) -> inventory -> build(tune, workload-max, 198 candidates: 61 mmq/85 mmvq/25 mmvf/25 mmf/2 blas) -> tune run -> tune-promote (17/17 promoted) -> build(replay-slim, 12 candidates) -> export dispatch.cache (56 entries) -> native vs replay comparison: throughput within noise (<1% across all 9 bench configs: pp256/512/1024/2048/4096, tg128/256/512/2048), and `replay-coverage.json` confirmed 100% exact cache hits (`exact:56, misses:0, candidate_unavailable:0`), `total_executed == total_dispatched == 47639` across every family -- proves replay genuinely served every call from cache, not a silent native fallback.

**Run 2: Qwen3.5-9B MTP (single GPU ROCm0, real speculative decoding), real signature diversity + the MMQ crash discovery.**
Record run with `--spec-type draft-mtp --spec-draft-n-max 5 --spec-draft-type-k q8_0 --spec-draft-type-v q8_0`: 113 signatures (vs 56 non-MTP), draft widths [1,2,3,4,5,6,8,12,16] (vs [1,2,4] non-MTP) -- confirms TEST.md's documented claim that MTP produces far more signature diversity than llama-bench-driven recording. Generated workload-max: 390 candidates (73 mmf/61 mmq/57 mmvf/197 mmvq/2 blas).

First tune attempt crashed reproducibly (3x total across the session, 2 different instrumentation approaches) on `mmq:q6_k:j112:fb0:t256:o2:i128:sram-q6_k:k256:sk0:v1` -- full investigation and quarantine fix in SE01/EX01.

**Post-quarantine successful tune run (the actual tuning result, real numbers):** 113 signatures measured, 28 non-native winners (85 kept native -- correctly conservative), all winners in the MMVQ family, all p-values ~9.3e-10 (highly significant). Top improvements: 15.02% `mmvq:q6_k:w5:nw1:rpb2:sk0:v1`, 14.05% `mmvq:q6_k:w6:...`, 13.51% `mmvq:q8_0:w1:nw8:...`, 12.93% `mmvq:q6_k:w5:...`, 12.44% `mmvq:q6_k:w4:...`, 12.21% `mmvq:q6_k:w2:...`, down to the smallest winner at ~1.84%. Zero MMQ/MMF/BLAS winners this pass -- native already won those families for this model at this sample scale. Pattern: winners cluster on q6_k/q8_0 at narrow draft widths (w1-w6), exactly the MTP-relevant signature space this run targeted.

**Caveat on the numbers**: measured at smoke-test sample scale (`GGML_HIP_TUNE_SCREEN_SAMPLES=10 FINAL_SAMPLES=30 CONFIRM_SAMPLES=30`), not TEST.md's documented production scale (`20/100/100`). Directionally real, not release-grade confidence -- a production-scale rerun is warranted before treating these specific percentages as final.

**Bugs found and fixed during this validation, beyond the MMQ crash:**
1. `_verify_tree`/`_reset_tree`/`_ensure_tree_state` (part 2, SE02) -- discovered that `build --all` would have compiled `upstream` (the stock baseline) from a PATCHED tree, since `build` never called `apply` and nothing reset between recipes. Real defect: the baseline would have silently carried `1002_hip_unsafe_math_opt_in` and `1004_rms_norm_mul_rope_fusion`'s behavioral changes, invalidating any upstream-vs-bigcherry comparison. Fixed via the tree-state-key mechanism.
2. `GGML_HIP_AUTOTUNE_SIGNATURE_FILE` was being passed to a `stock` (no dispatch layer) cmake configure -- caught in this session's own dry-run output before it shipped. Fixed: signature file only emitted alongside a variant-set.
3. Sequencing bug (mine, not a defect in the tool): built `replay-slim` before exporting `dispatch.cache`, which overwrote the `workload-max` manifest the promoted measurements were keyed against -- `bigcherry.replay_cache` correctly refused with 'measurements and producer manifest differ' rather than silently exporting a mismatched cache. Recovered by regenerating `workload-max` (deterministic, same manifest hash reproduced exactly), exporting, then regenerating `replay-slim` to restore state.
