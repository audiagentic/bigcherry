# Add immutable artifact store and provenance v2

## Description

Publish immutable hashed artifacts atomically and define complete source/build/workload/campaign provenance validation.

## Steps



## Detailed Solution & Technical Design

PROVENANCE HALF, SECOND ROUND (RV48 audit). ArtifactStore itself is sound (verified): path confinement, atomic immutable publication, byte verification. The gap: provenance.validate() only requires the five namespaces to EXIST as dicts - each may be {} - which is a useful early-stage shape but not 'complete production provenance'.

REQUIRED: (1) Add ArtifactDescriptor - frozen dataclass(artifact_id, kind, relative_path, content_hash, provenance: ProvenanceV2), serializable independently of process-local Path; ArtifactStore must persist and rehydrate it (RE11's cross-process resume needs exactly this). (2) Kind-specific provenance contracts: runtime bundle requires source slice + source-plan/patch lineage + build plan + effective build + runtime-bundle identity; inventory requires producer source/build identity; promoted-winner/correctness artifact requires producer tune namespace; release report requires campaign/report identities. (3) Raw-path import must be a VALIDATION boundary, not a provenance-creation shortcut - verified laundering path: _resolve_lane_inputs hashes a raw Path, copies it in, and stamps newly invented provenance claiming the current source_slice_id and run_id without checking the file's own identity; an inventory from source A passed as a raw path while building source B acquires source-B provenance at import time. Production code must never say 'the caller supplied this file while building X, therefore it came from X'. For canonical build, prefer persistent artifact IDs/descriptors; a low-level expert campaign-build command may retain an explicit legacy-file import path ONLY if it parses/validates the file's own producer identity and visibly classifies unprovable cases as imported-legacy evidence.

## Notes

Completed 2026-08-17 (RV48 audit fix); FOLLOW-UP CLOSED 2026-08-17 (GPT re-review). See prior notes above for the original raw-path-laundering fix.

GPT review (2026-08-17, second pass): identified that _sniff_embedded_provenance() was itself still a laundering route, just a smaller one -- it trusted any raw-Path bytes that merely PARSED as a schema_version==2, five-namespace document as 'real embedded provenance', but provenance.validate() is a structural shape check only, with no way to prove a document was genuinely produced by this project rather than hand-crafted by whoever supplied the file. A crafted JSON blob asserting any source_slice_id it liked would have been accepted as real. Also flagged (not yet acted on, see below) that imported-legacy artifacts are still consumable by the canonical production pipeline with no rejection/taint mechanism.

Fixed the spoofing vector: _sniff_embedded_provenance() now unconditionally returns None (kept as a named, documented seam rather than deleted, explaining why raw-Path bytes are never trusted to self-report their own provenance). A raw-Path input is now unconditionally imported-legacy, full stop -- no more attempting to recover 'real' identity from the file's own JSON shape. Verifying an embedded claim for real needs chain-of-custody infrastructure (RE25's ArtifactDescriptor persistence/rehydration) this project does not have yet.

1 test updated (the removed embedded-provenance-preserved test replaced with a spoofing-rejection test proving a crafted JSON blob claiming a fake identity is correctly ignored -- the real lane identity and imported-legacy classification win instead). Full suite green (855 Windows / 858 Linux), ruff-clean.

NOT implemented (deliberately, flagged back to GPT rather than acted on blind): blanket rejection of imported-legacy inputs at the canonical production consumption boundary, which GPT's second-pass review also recommended (RE24 acceptance criterion should require rejection, not just visible classification). Investigated the real record->tune/replay workflow first: those are separate execute_campaign_lane() calls, often genuinely cross-run/cross-process (a record lane's real output, loaded via --inventory days later for a tune/replay build) -- there is currently NO mechanism for a lane to reference another run's real ArtifactRef output except via raw Path, making imported-legacy inherent and unavoidable in TODAY's single-process model for this entirely normal, already-hardware-proven workflow. Blanket rejection would break every real tune/replay production build RE17/RE20/RE21 proved on hardware. This needs RE25's chain-of-custody work (or a narrower within-run lane-chaining mechanism) landing FIRST. Recorded as an open question for GPT/RE25 rather than implemented -- see RE25's notes for the follow-up.
