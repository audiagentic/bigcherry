# Catalog exact patch modules and reviewed production patch sets

## Description

Introduce canonical PatchModule identities, hashes, deterministic exact resolution, dependency/conflict/state validation, and explicit framework/enhancement classification.

## Steps



## Detailed Solution & Technical Design

ARCHITECTURAL CONTRACT (backfilled 2026-08-17 per RV48 audit): patch identity and effective source identity are deliberately different things. patch_set_id represents reviewed logical composition and includes module content hashes; source_slice_id represents resulting source bytes. Two different logical compositions may legitimately produce the same effective tree - they share content identity while retaining distinct lineage. Automatic dependency expansion is FORBIDDEN: a declared source/patch set must list its entire dependency closure, and REQUIRES is a validator, not permission for the resolver to silently mutate the requested set (resolve_exact already rejects missing dependencies rather than adding them).

Verified gap (RV48): campaign_resolution computes patch_set_id from exact (patch_id, content_hash) pairs, but production source resolution discards it - campaign_source.source_plan_for passes only module_ids into workspace.SourcePlan, so nothing downstream of resolution carries the content identity. Closing this is RE03's remaining work via the RE04/RE05 fixes.

Current implementation (verified): PatchModule carries canonical ID, ordering, state, upstream provenance, content hash, requires/conflicts; resolve_exact rejects duplicate, unknown, rejected, wrong-state, missing-dependency and conflicting selections. Shipped framework set: 14 validated modules (13 core + validated 1000 upstream-fixes).

## Notes

RE03 (2026-08-17, commit 9da0eac): closed the remaining provenance-carry-through gap. campaign_resolution.resolve_lane() already computed patch_set_id (reviewed logical-composition identity, distinct from source_slice_id) and classification, but campaign_source.source_plan_for() discarded both before they reached workspace.SourcePlan -- nothing downstream, including the persisted materialized-source .metadata.json, carried them. Both are now SourcePlan fields (optional, default None, so direct construction in existing tests is unaffected), populated by source_plan_for() from resolve_lane()'s result, and persisted into materialize()'s plan metadata. New end-to-end test (test_re04_materialization_safety.py::PatchSetIdentityPersistedTests) proves this against a real materialize_source() run and a real re-read of the persisted metadata file off disk -- verifiable without recomputation, satisfying acceptance criterion (2). Verified on Windows and Brutus (Linux), full suite green both places (897 local).

Acceptance criterion (3) -- 'human validated framework vs enhancement classification recorded explicitly' -- is satisfied structurally by recipes.toml's existing named [patch-set.framework] (14 modules) / [patch-set.validated-enhancements] (currently empty, no promoted enhancement set claimed) split, now also carried into persisted provenance via the classification field above. Not a separate code change; flagging the reasoning here rather than silently treating it as done.

SEPARATE GAP REINFORCED (not fixed here, same one RE24 already documented): campaign_resolution.resolve_patch_set()'s catalog cross-check calls patchset.catalog() with no directory override, defaulting to paths.PATCHES (the real project patches/) rather than any caller-supplied context.patches_root -- an isolated test fixture's own patches are invisible to this check unless paths.PATCHES itself is monkeypatched (worked around again here, same as RE24's harness). A real fix would need resolve_lane/resolve_patch_set to accept an explicit patches directory instead of relying on the module-level default; left as documented technical debt, not RE03's scope to redesign.
