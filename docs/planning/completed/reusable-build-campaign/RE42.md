# Split resolver into resolve_exact() (fail-closed, explicit) and expand_composition() (dependency-closure expansion)

## Description

Adopt the already-implemented two-layer resolver deliberately: resolve_exact() remains the fail-closed explicit HIP-compatible resolver; expand_composition() computes visible REQUIRES closure but is not yet used by production recipes.

## Steps

Add a snapshot-aware expansion API; prove closure against every existing hand-written dependency chain; add explicit opt-in composition mode to one non-production experiment; compare expanded IDs/order/content/patch_set_id/generated source with the current manual recipe; only then simplify recipes.toml in a separate change.

## Detailed Solution & Technical Design

Do not reimplement resolution. Keep resolve_exact() as the safety boundary and make expand_composition() return requested/expanded/pulled_in data for CLI/reporting. Use module REQUIRES/CONFLICTS as the single relationship source. Production HIP standard/replay lanes must remain exact until equivalence evidence is accepted.

## Code Samples & Guidance

```python
expansion = patchset.expand_composition([terminal_id], directory=snapshot.root)
print({"requested": expansion.requested,
       "expanded": expansion.expanded,
       "pulled_in": expansion.pulled_in})
resolved = patchset.resolve_exact(expansion.expanded,
                                  directory=snapshot.root,
                                  required_state=declared.required_state)
```
For adoption, add `composition_mode = "exact" | "expand"` to a non-production experiment or request, never silently change existing recipes. Compare `module_ids`, hashes, source output, and patch_set_id between manually listed and expanded forms before changing config.
