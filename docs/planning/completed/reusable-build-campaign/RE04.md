# Add host-local upstream repository and isolated source materialisation

## Description

Materialise an exact, immutable source-input specification into a detached worktree and reuse it only after BOTH its requested materialisation inputs AND its resulting effective tree have been revalidated (revised objective per RV48 audit - this item needs a correction, not just documentation).

## Steps



## Detailed Solution & Technical Design

VERIFIED DEFECTS (RV48, all against current code): (1) campaign_source.source_plan_id hashes only upstream_revision / overlay_enabled / sorted patch IDs / required_state - no patch content, no overlay content; an in-place edit of a patch module under its canonical ID reuses the old materialisation. (2) materialize_source's cache-hit path compares exactly those same ID-level fields and returns the stored metadata without recomputing anything - the cached worktree is never re-hashed against the stored source_tree_oid/source_slice_id, so a modified cached source dir is another false reuse. (3) The clean-BigCherry check lives only inside workspace.materialize (fresh-creation path); a cache hit returns before it ever runs. (4) campaign_lane._materialize_worker hard-codes allow_dirty_bigcherry=True and execute_campaign_lane exposes no override - dirty-tree execution is implicit in the public lane API, contradicting RE16's design that it be an explicit development/harness escape hatch only.

REQUIRED FIXES: (a) Introduce a materialisation-plan identity containing the fully resolved upstream commit, overlay content identity, patch_set_id with ordered module IDs + content hashes, and required state; key the destination directory by THAT identity. Do not make source_slice_id carry these labels - it remains resulting-content identity (see RE05). (b) On a cache hit, recompute the effective source tree and require equality with the stored source_tree_oid/source_slice_id before reuse; a modified cached worktree fails closed rather than compiling stale bytes. (c) Move the clean-project check so it surrounds BOTH fresh creation and cache reuse: unless an explicit development override is set, dirty BigCherry source rejects either path. (d) execute_campaign_lane defaults to allow_dirty_bigcherry=False with an explicit argument; only the RE14 harness passes True.

Preserve what already works: detached-worktree semantics, temporary-index effective-tree computation, allowed-untracked overlay identity, exact patch application.

## Notes

Completed 2026-08-17 (RV48 audit fix). Implemented all four required fixes (a)-(d) from the audit's detailed_solution.

campaign_source.py: new resolve_materialization_identity(context, plan) resolves real patch content_hash values (patchset.resolve_exact) and hashes overlay file bytes; new materialization_plan_id(identity) hashes that content-aware structure. campaign_build.materialize_source() now keys the destination directory by THIS identity (not the old ID-only source_plan_id), and its cache-hit path additionally re-hashes the actual cached destination tree (source_identity.git_tree_oid) against the stored source_tree_oid, failing closed (CampaignBuildError) on any mismatch. workspace.require_clean_bigcherry() extracted as its own function, called unconditionally at the top of materialize_source() (both fresh AND cache-hit paths) rather than only inside workspace.materialize()'s fresh-creation path. execute_campaign_lane()/campaign_planner.run_campaign() gained allow_dirty_bigcherry: bool = False (real default); only re14_real_run.py (RE14's own harness) passes True explicitly.

Independent bug found and fixed while writing negative tests: patchset._load_module() used importlib's SourceFileLoader, which can serve a stale __pycache__/*.pyc bytecode cache when a patch file is rewritten within one mtime-resolution tick -- directly undermining RE04's own content-safety guarantee (content_hash would correctly show 'changed' while the actually-applied patch effect stayed stale). Fixed to compile+exec fresh source directly, bypassing the cache entirely.

6 new negative/falsification tests (test_re04_materialization_safety.py), all passing: patch-content edit under unchanged ID doesn't reuse, overlay-content edit doesn't reuse, tampered cached worktree fails closed, dirty BigCherry rejects both fresh materialisation and cache reuse, explicit override allows both. Full suite green (838 passed Windows, 841 Linux/Brutus), ruff-clean.

Proven for real on Brutus: a real execute_campaign_lane() materialize call (llama-native:stock, zero patches) succeeded end-to-end through the new content-safe path against the real, clean project checkout. Along the way, the fail-closed checks correctly caught two real leftover-state cases from earlier manual debugging (a source directory that existed without matching metadata, and a stale git-worktree registration after a raw directory deletion) -- exactly the kind of integrity catch RE04 exists to guarantee.

Open, NOT root-caused (out of RE04's scope, flagged for follow-up): attempting the same real-hardware proof against 'bigcherry:stock' (a source with real framework/validated-enhancements patches applied) repeatedly hit the pre-existing git_tree_oid ignored-file rejection on a .ruff_cache directory appearing under ggml/src/ggml-cuda/ inside the worktree -- reappeared even after deletion and even against a freshly re-created worktree. Not caused by patcher.py directly (no ruff invocation found there); likely a concurrent unrelated process on Brutus, or a real interaction between real patch application and something in the toolchain that needs its own investigation. This is a pre-existing gap in the tree-cleanliness check's interaction with real patch content, not introduced by RE04 -- worth a small dedicated follow-up item if it recurs.
