# Pin-consistency guard: one command that detects vendor-checkout / pin / release-record / cross-tree desync, plus the canonical pin-bump procedure

## Description

On 2026-08-21 the project simultaneously carried three upstream revisions across its working surfaces with no tool detecting it:

| surface | value |
| --- | --- |
| config/recipes.toml | pinned = b10502 (0adcc3bb) |
| H: vendor/llama.cpp checkout | 4801e3c = b10362, patches applied |
| J:/Brutus vendor checkout | 0adcc3bb = b10502, stage generated |
| J:/Brutus bigcherry code rev | 5020c68 (4 commits behind H: 202a0c1) |
| S1 kernel-fraction traces | 22dc605 = b10257 |
| releases/ records | b10502 audited, b10362 patched, b10257 patched |

Both recent incidents share this root cause: the S1 stale-trace incident (kernel-fraction evidence captured on the wrong pin) and the J: tooling gap (the 27B campaign ran on pre-HI67-slice-3 promotion tooling, forcing a workarounded S6). The existing machinery is per-surface: `bigcherry repin` moves the pin, `bigcherry pull` moves the checkout, `releases.py` tracks evidence records with `validate_index_consistency()` (index vs source records only), and campaign machinery binds its own descriptor to `upstream_revision`. Nothing reads all surfaces together, so a forgotten bump is indistinguishable from a legitimate mid-rebase state. `doctor` prints `pinned=b10502` but never compares it to the actual vendor HEAD.

## Detailed Solution & Technical Design

(Rvised 2026-08-21 after RV78 GPT review — the original "release-record
existence ⇒ mid-rebase" rule and per-tree-only verdict are superseded.)

### The invariant

One project state may legitimately span two revisions (a bump in flight).
What must never be possible is a state where the surfaces disagree and nothing
names the disagreement — including the case where every tree is individually
fine but the trees disagree with each other (the H:/J: incident).

### Surfaces read (all read-only — this command must never mutate)

| # | surface | source |
| --- | --- | --- |
| 1 | pin | config/recipes.toml `pinned` + upstream resolution → pinned SHA |
| 2 | vendor checkout | vendor/llama.cpp: HEAD SHA, tag, dirty counts (modified/untracked) |
| 3 | pin-transition marker | releases/pin-transition.json (from_sha, to_sha, tag, declaring_commit, set_at) |
| 4 | release records | releases/index.json + releases/*.json (stage/manifest/audit per revision) |
| 5 | campaign descriptors | artifacts/<rev>/*build-descriptor*.json (informational) |
| 6 | bigcherry code rev | project git HEAD (informational for non-campaign trees; gated for campaign trees) |
| 7 | remote trees | config [trees] + one SSH probe per tree |

### The pin-transition marker (RV78 fix 1)

`bigcherry repin <tag>` writes the marker atomically with the recipes.toml
rewrite:

```json
{"schema_version": 1,
 "from_sha": "<currently pinned SHA, resolved>",
 "to_sha":   "<new tag, resolved>",
 "tag": "b10502",
 "declaring_commit": "<bigcherry HEAD at the moment of repin>",
 "set_at": "<iso8601>"}
```

The marker is written UNCOMMITTED, in the same working tree as the pin change:
step 1 of the procedure commits both together. The marker is the machine
declaration that a bump is in flight; without it, no mismatched state is
mid-rebase — it is drift, full stop. This closes RV78's false-safe #1 (vendor
manually at a previously-recorded revision while the pin never moved: with no
marker, that is drift even though a release record for the vendor revision
exists and is audited — which is exactly the state that exists today for
b10502).

Marker lifecycle: written by `repin`; consumed (cleared) by the completion
rule (`pin-status --complete` succeeds and the operator commits the clear);
a stale marker (to_sha no longer equals the current pin) is reported as
`stale-marker` and forces drift classification.

### Local verdict matrix

The claim is **base-revision** consistency. Content verification is not this
tool's job (that is `audit`); "consistent" is therefore always rendered with
`(content-unverified)` and dirty counts are reported, never a verdict input
(RV78 fix 2).

| condition | verdict |
| --- | --- |
| vendor HEAD == pinned SHA | `consistent` (content-unverified) |
| vendor HEAD != pinned SHA AND marker present AND vendor HEAD == marker.from_sha AND pinned == marker.to_sha AND declaring_commit is an ancestor of bigcherry HEAD | `mid-rebase` (the declared bump, in flight) |
| marker present but any marker condition fails (stale marker, from_sha mismatch) | `drift` (stale-marker) |
| vendor HEAD != pinned SHA, no valid marker | `drift` |
| vendor checkout missing / not a git repo | `unavailable` |
| pinned ref unresolvable in the local upstream clone | `unresolvable-pin` (fail; distinct from network states) |

Release records (surface 4) are EVIDENCE, not transitions: shown in output
(stage, audit, manifest) and consulted for one thing only — a `mid-rebase`
whose from_sha record is stage `broken` escalates to `drift` (resuming from a
known-broken base is not a legitimate in-flight state).

### Policy tiers (RV78 fix 3 — three consumers, three gates)

| invocation | consumer | fails on | exit |
| --- | --- | --- | --- |
| `pin-status` | interactive diagnosis | never (reports) | 0 unless config error (2) |
| `pin-status --strict` | pipeline preflight, gated to the tree the pipeline consumes | drift, unavailable, unresolvable-pin, (stale-marker) — mid-rebase PASSES with a loud warning (a pipeline may consume a tree mid-bump only by explicit choice; by default the pipeline pins its source identity anyway) | 1 |
| `pin-status --complete` | bump-completion rule | ANY required tree: unreachable, mismatch, drift, non-consistent aggregate (see below); required-tree set = all [trees] with `required = true` (local always required) | 1 |

Remote-unreachable is never a pass path for `--complete` (RV78 fix 3: network
failure must not be a route to a successful completion), and it is not
reachable as a --strict failure because --strict does not probe remotes.

### Cross-tree aggregate (RV78 fix 5)

Above the per-tree verdicts, one aggregate line for `--complete`:

```
AGGREGATE  H: pin=0adcc3bb  J: pin=0adcc3bb  converged
           J: tooling 5020c68 == expected 5020c68  ok
```

Rules: for every required tree, resolved pinned SHA == local pinned SHA
(convergence); for every tree with `role = "campaign"` in [trees], the remote
bigcherry HEAD must equal the tree's declared `expected-tooling-revision`
(default: local bigcherry HEAD, stated in output). Individual consistency of
each tree is NOT sufficient — H: consistent@b10502 and J: consistent@b10362
is `AGGREGATE diverged` and fails `--complete`. This is the exact incident
shape and it is now a named failure.

### Remote probe (RV78 fix 4 — do less remotely)

One SSH command, argv-constructed (subprocess list, remote command built with
shlex quoting), 10 s timeout:

```
cd <path> && echo VENDOR <(sha)> && echo PIN <(pinned line)> && echo HEAD <(sha)>
```

- PIN read by grepping the `pinned = "..."` line (regex tolerant of
  whitespace, matching recipes.py writer semantics — no sed-TOML).
- Remote verdicts are limited to `consistent` (vendor == locally-resolved
  pinned SHA for the remote's OWN pin), `mismatch`, `unreachable`.
  The controller NEVER infers a remote mid-rebase from its own records —
  that inference is unsound when the remote tree is behind (the J: case).
- Remote pinned ref unresolvable locally → `unresolvable-pin` for that tree
  (distinct from unreachable).

### Enforcement hooks (RV78 fix 6 — mechanical, not procedural)

1. `bigcherry pull` refuses to move the checkout while the pinned line in
   config/recipes.toml differs from the committed version (uncommitted pin
   change) — the load-bearing "commit the pin move first" ordering becomes a
   tool refusal instead of a hope. Error message names the fix.
2. Campaign entry point (execute_campaign_lane preflight) verifies: vendor
   base revision == canonical pin, and bigcherry HEAD == expected tooling
   revision for that tree. A stale-tooling tree (5020c68 vs 202a0c1) cannot
   silently launch a campaign.
3. `--complete` is machine-readable (`--json` always available; a
   `completion: {pass, required, failed[], reasons[]}` block).

### config [trees] (config v2, additive)

```toml
[[trees]]
name = "brutus"
alias = "brutus"
path = "/mnt/vault/development/llmhosts/bigcherry"
required = true            # part of the --complete obligation
role = "campaign"          # "campaign" adds the tooling-revision gate
expected-tooling-revision = ""   # empty = local bigcherry HEAD
```

Top-level `trees` added to the v2 whitelist in config.py (it currently
rejects unknown top-level fields); each entry validated against an explicit
allowed-key set (not "by convention", per RV78 fix 8).

### doctor integration

`doctor.build_report()` gains a `pin_status` section (plain invocation,
diagnostic tier). Doctor's exit code and existing stdout lines are UNCHANGED;
the section is appended.

### docs/reference/PIN_BUMP.md

Written (committed with the implementation). Procedure steps 1–7 with the
marker at step 1 (repin writes it; the commit is one commit covering
recipes.toml + the marker), invalidation table, and the `--complete`
completion rule. The doc explains; the three hooks enforce.

## Validation

Fake-repo test matrix (temp git repos: 3-commit fake upstream; fake bigcherry
project with releases/ JSONs and a recipes.toml). Every RV78 false-safe case:

1. consistent — vendor at pinned SHA, dirty tracked files present ⇒ verdict `consistent (content-unverified)`, dirty counts reported.
2. declared mid-rebase — repin wrote the marker (to_sha = new pin, from_sha = old), vendor still at from_sha ⇒ `mid-rebase`; default and --strict both exit 0 WITH A LOUD WARNING (a --strict pipeline gate that sees mid-rebase must proceed only because the pipeline's own source identity is revision-bound — the warning is the named risk); --complete exits 1.
3. RV78 false-safe #1 — vendor at a recorded+audited revision, pin never moved, NO marker ⇒ `drift`. (Today's real b10502-record state must not read mid-rebase.)
4. pull-before-repin — vendor moved to a target that has a record, pin uncommitted/unchanged, no marker ⇒ `drift`; and the pull() refusal fires in the uncommitted-pin case.
5. uncommitted repin — marker + pin change present but not committed ⇒ distinguishable (marker declaring_commit vs HEAD and working-tree-dirty pin line) ⇒ reported as `uncommitted-transition`, not a clean mid-rebase.
6. stale marker — marker.to_sha != current pin ⇒ `drift (stale-marker)`.
7. mid-rebase from broken base — marker valid but from_sha record stage `broken` ⇒ `drift`.
8. pinned tag record resolving to a different SHA ⇒ `unresolvable-pin`/`pin-record-mismatch` failure.
9. unavailable — no vendor dir ⇒ `unavailable`; --strict fails; plain does not.
10. aggregate divergence — two local fake trees (or one local + one file:// remote) each internally consistent on DIFFERENT pins ⇒ per-tree consistent, aggregate `diverged`, --complete exit 1.
11. campaign tooling lag — remote role=campaign with bigcherry HEAD != expected-tooling-revision ⇒ --complete fails on that tree only.
12. remote unreachable (bogus alias) ⇒ `unreachable`, never a pass for --complete (required unreachable ⇒ exit 1), never a --strict failure (--strict does not probe remotes).
13. remote pin unresolvable locally ⇒ `unresolvable-pin`, distinct from unreachable.
14. controller-has-record/remote-does-not ⇒ remote verdict is never mid-rebase (assert the verdict enum for remote trees excludes mid-rebase).
15. --json carries every surface, all markers, and a `completion` block {pass, required, failed, reasons}.
16. pull() refusal: uncommitted pinned line ⇒ refusal with the fix named; committed pin ⇒ proceeds.
17. doctor: existing stdout lines byte-identical (append-only section), exit code unchanged.

Real-tree acceptance (step 10): 2026-08-21 H: state names as `drift` (honest:
the pin moved outside repin, no marker), and the scratch-clone repin proof
names the declared state `mid-rebase`.
