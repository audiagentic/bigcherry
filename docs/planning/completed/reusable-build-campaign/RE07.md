# Implement content-addressed build plans and effective build identity

## Description

Capture CMake options, environment, toolchain, generated inputs, effective configure state, build IDs, binary hashes, and verified cache reuse.

## Steps



## Detailed Solution & Technical Design

SECOND ROUND (RV48 audit). What already works (verified): source slice, options, target platform, toolchain request, selected environment, effective CMake state, binary SHA and runtime-bundle hash all participate in planning or reuse validation; build dirs are content-addressed by (source_slice_id, build_plan_id); reuse re-hashes the FULL runtime .so closure, not just the launcher.

VERIFIED GAPS: (1) BuildPlan carries separate inventory_hash/winners_hash fields while execution hard-codes SUPPORTED_BUILD_NEEDS = {inventory, promoted-winners} - HI66's candidate-qualification correctness evidence is exactly the case this breaks; do NOT add a third special case. (2) The candidate-generation architecture set is NOT in build_plan_id: campaign_workers deliberately treats a changed generated_compile_inputs_hash as a cache miss INSIDE the same build dir, and the immutable ArtifactStore path is still keyed by that common plan ID - so one 'content-addressed' identity can represent two different generated catalogs at different times. (3) The build worker publishes only the launcher binary into ArtifactStore; the runtime .so closure and build metadata remain in the mutable build directory.

REQUIRED: (a) BuildPlan gains catalog_architectures: tuple[str, ...] (distinct from targets, which correctly means compiled AMDGPU targets) and input_hashes: tuple[(kind, content_hash), ...] replacing the named hash fields - compatibility properties may remain temporarily. Invariant: EVERY external artifact that can affect generated or compiled bytes is represented exactly once in BuildPlan identity (this absorbs HI66's evidence input naturally, whatever shape it takes). (b) Keep post-generation generated_compile_inputs_hash as an independent verification layer - not a substitute for correctly identifying the requested build. (c) Build publishes a runtime-bundle manifest ArtifactRef: entrypoint (bin/llama-bench), regular runtime files + hashes, required symlink/loader layout, runtime_bundle_hash, effective_build_id, generated_compile_inputs_hash, toolchain identity - and CampaignLaneResult returns that ref; downstream smoke/benchmark/release consume the bundle, never the build directory.

## Notes

Completed 2026-08-17 (RV48 audit fix). Implemented all three required fixes (a)-(c) from the audit's detailed_solution.

builds.py: BuildPlan gained catalog_architectures: tuple[str,...] (the generation architecture set, distinct from targets = compiled AMDGPU targets; empty for a build with no generate stage) and input_hashes: tuple[(name, content_hash),...] (generic over every declared need a lane resolved, replacing the hard-coded inventory_hash/winners_hash pair -- those remain as read-only compatibility properties). campaign_lane.py builds BuildPlan with both fields populated from real spec.architectures/input_refs.

campaign_workers.py's make_build_worker now publishes the FULL runtime .so closure to ArtifactStore (previously only the launcher binary), each member individually verified, described by one runtime-bundle manifest artifact (entrypoint, member hashes, runtime_bundle_hash, effective_build_id, generated_compile_inputs_hash, toolchain). CampaignLaneResult gained runtime_bundle_ref.

Real bug caught and fixed while implementing (c): the bundle manifest's first publish-path design (keyed only on source_slice_id/build_plan_id) collided ArtifactStore's immutability check on the exact 'same build_plan_id, legitimately different generated catalog' scenario the audit's item (2) documents as a real supported case (recompiling with a different generated catalog can leave runtime_bundle_hash unchanged -- e.g. identical binary bytes -- while generated_compile_inputs_hash differs inside the manifest itself). Fixed by content-addressing the manifest's own publish path by a hash of its full JSON content, not just the member-file hash.

9 new negative/falsification tests (test_re07_build_identity.py): catalog_architectures and input_hashes each independently change build_plan_id and build_directory() (proving two lanes with the same plan but different architectures can never share a build dir), a third need kind beyond inventory/promoted-winners participates in identity too (proving HI66's correctness-evidence artifact will slot in without a new special case), compatibility properties still work, a real make_build_worker run (fake compiler) proves the runtime bundle includes every .so member not just the launcher, tampered/duplicate-publish bundle bytes fail closed via ArtifactStore. Full suite green (847 Windows / 850 Linux), ruff-clean.

Proven for real on Brutus: a real llama-native:stock lane run on gfx1201 published a complete, real runtime-bundle manifest with 8 real members (libggml-hip.so.0.19.0 -- the real HIP dispatch library RE09 established matters most -- plus every other .so dependency and the launcher), all individually store-verified, runtime_bundle_hash=c1b2998db1845db191359e12ebb918a9. catalog_architectures/input_hashes correctly empty for this build shape (no generate stage, no declared needs).
