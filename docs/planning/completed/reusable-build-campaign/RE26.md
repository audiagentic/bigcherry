# Wire HI70 direct-op evidence corpus into re15_acceptance_run.py's continuous tune stage

## Description

RE15 stage F (replay-full generate) was proven to pass for the first time on 2026-08-19, but only via a manual merge of the HI70 direct-op corpus's measurements (run separately against test-backend-ops) into re15_acceptance_run.py's own tune.measurements.jsonl, outside the harness's continuous A-I flow. This satisfies the underlying mechanism but not RE15 acceptance criterion 1 ('one continuous run on real hardware drives every transition').

## Steps

1. Extend the campaign build config for the 'tune' build role (recipes.toml's [build.tune]) so it also compiles test-backend-ops, not just the named entrypoint binary -- campaign_lane.py's cmake_targets currently builds exactly one target (Path(spec.binary_relative_path).name); this needs either a second target or a role-specific multi-target list.
2. Ensure the tune runtime bundle (published via _verify_runtime_bundle / the bundle manifest) carries test-backend-ops alongside the main entrypoint, so lifecycle.py's execute_tune_stage can locate and run it from the bundle, not from a separately-materialized build directory.
3. Add a new lifecycle.py stage function (e.g. execute_direct_op_evidence_stage) that runs test-backend-ops -o MUL_MAT -p '<HI70 corpus filter>' in tune mode against the SAME dispatch_db/measurements_base path execute_tune_stage already wrote to (append, not overwrite), immediately after the real-workload tune pass and before promotion.
4. Call it from re15_acceptance_run.py's stage D, between the existing lifecycle.execute_tune_stage call and stage E's promotion call.
5. Re-run the full A-I harness fresh (bc-branch checkout, device 2/gfx1201) and confirm stage F passes with zero manual intervention, then continue through G (runtime validation), H (balanced comparison), I (release pointer).
