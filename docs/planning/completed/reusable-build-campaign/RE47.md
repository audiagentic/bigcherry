## Description

## Steps

[NOT STARTED] patchset.py::expand_composition()'s final line re-sorts its correctly-computed topological DFS order by (modules[pid].order, pid) -- discarding the real dependency order and only being topologically valid today by coincidence (the current 1215->1216->1217 chain happens to have ascending numeric order matching dependency order). Fix: use the DFS post-order directly (or numeric order only as a tie-breaker among nodes with no remaining unresolved dependency), with a test using a deliberately-scrambled numeric-order dependency chain (a lower-numbered patch REQUIRES a higher-numbered one) proving the old behavior was wrong and the new behavior is right.
[NOT STARTED] patch_catalog.py's CatalogSnapshot.metadata field is a plain (mutable) dict on a frozen dataclass, and build_snapshot()'s digest only hashes sorted metadata.keys() -- never the CatalogEntry values -- so an entry's kind/backend/etc field can change with no snapshot digest change. Fix: make metadata a genuinely immutable mapping and hash canonically-serialized CatalogEntry values, not just keys; add a regression test proving an existing entry's VALUE change (e.g. a kind edit with no key added/removed) now changes the digest. Also confirm build_snapshot() should call the existing (separate) cross_check() function to validate 1:1 module/metadata coverage.

- patch/catalog.py: CatalogSnapshot.metadata is now a genuinely immutable MappingProxyType, not a plain dict (a frozen dataclass only blocks reassigning the attribute, not mutating a dict inside it).

Digest namespace bumped v1->v2 since the payload shape changed (a v1 digest and a v2 digest are not comparable, deliberate, not a silent reinterpretation).
- Two new regression tests in tools/tests/patch/test_patch_catalog.py: test_digest_changes_when_a_catalog_entry_value_changes_with_no_id_added_or_removed, test_metadata_mapping_is_not_mutable_via_normal_item_assignment.
