# GPT review: parity-oracle loss and work-root/checkout overlap not structurally enforced

## Notes

Independent GPT review (req_6d2f12baf93d4e52) of RE23's legacy-deletion commit (db3079a), conditional GO verdict. Two medium-severity findings recorded here since a follow-up clarification round could not be completed (the review's ChatGPT session had already closed by the time I sent clarifying questions).

1. Retiring tools/bigcherry/re14_parity_run.py (the legacy-vs-new comparison harness) loses a real class of coverage: its own docstring said it was meant to be rerun for future toolchain changes, recipe edits, and new RDNA targets, not just the one-time RE14 cutover gate. The rewritten test_parity_loaders.py tests now compare two independently-published new-path arms against each other -- this still exercises check_parity()'s fail-closed logic well (binary_hash divergence, descriptor divergence), but cannot catch a common-mode bug shared by both new-path builds (e.g. both silently omitting the same CMake option). check_parity() itself is untouched and still callable against any two real arms if an independent second implementation ever exists again.

2. test_new_campaign_work_root_never_overlaps_legacy_checkout_root (in test_campaign_build_flip.py) proves the DEFAULT topology is safe, not that overlap is structurally prevented -- ProjectContext.resolve() does not reject a BIGCHERRY_WORK_ROOT explicitly set to overlap the vendor checkout. This is pre-existing resolver behavior, not a regression introduced by RE23 itself.

Both findings are real but neither blocks RE23/RE14 as already-closed: (1) is a loss of future diagnostic capability, not a current correctness defect (nothing today needs a legacy-vs-new comparison since legacy is gone); (2) would require a deliberately adversarial or careless BIGCHERRY_WORK_ROOT misconfiguration to trigger, not something the project's actual operational pattern does today.
