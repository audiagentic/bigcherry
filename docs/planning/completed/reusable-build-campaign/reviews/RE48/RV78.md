# GPT design review: verdict engine has two false-safe paths — record-existence mid-rebase and per-tree-only consistency

## Notes

Verbatim verdict: 'I would not ship the verdict engine as specified as a gate. It has two serious false-safe paths... Without those [transition-aware local verdict + cross-tree aggregate convergence + separate completion policy + honest reduced remote verdict], the tool will successfully detect the current H: b10362/b10502 state but still miss several structurally equivalent future desyncs.' Also confirmed: the H36 S1b finding (small_k kernel rename between pins with unchanged behaviour) validates the pin-specific invalidation list. Reviewer also noted config.py:120-150 whitelist, recipes.py:308-334 repin (uncommitted rewrite), releases.py:232-267 validate() (pulled-stage records need no strong validation).

## Findings

1. WRONG — record-existence as mid-rebase signal. vendor-at-b10502-while-pin-still-b10362 with an existing audited b10502 record reads mid-rebase under the original rule, but RE48 itself says a checkout that skips the pin move is drift. Reverse-order test: pin stays b10362, manual vendor checkout to b10502, b10502 record exists and is audited (it does, today) ⇒ original engine says mid-rebase. Fix adopted: a pin-transition marker (from_sha, to_sha, tag, declaring_commit) written by repin into releases/pin-transition.json; mid-rebase requires pin==to_sha AND vendor==from_sha AND marker's to_sha==pinned. Without a marker, a mismatched vendor with only a record is drift (the S1-incident class).
2. HONESTY GAP — 'consistent' overclaims. vendor HEAD == pinned SHA with arbitrary manual source edits reads consistent because dirty state is informational. Fix adopted: rename the claim to base-revision consistency (content-unverified by construction); dirty counts reported, never a verdict input; patch verification stays with audit.
3. WRONG as conflated — --strict mixed the two consumers. remote-unreachable-never-fails --strict while completion requires --strict on all reachable trees makes network failure a path to a passing completion. Fix adopted: default = diagnostic (mid-rebase OK); --strict (pipeline preflight) = fail drift/unavailable/mismatch on the gated tree; --complete = every required tree reachable AND converged AND consistent (required unreachable ⇒ fail).
4. SOUND-WITH-FIXES — remote probe evidence. Three-value probe cannot support a remote mid-rebase verdict (no remote release evidence; using the controller's records is unsound when the remote tree is behind — the J: case). Fix adopted: remote verdicts limited to consistent / mismatch / unreachable + raw identities (vendor sha, pinned ref, bigcherry HEAD); ssh argv construction, no sed-TOML (grep the pinned line), distinguish unresolvable-ref from unreachable.
5. WRONG as scoped — cross-tree convergence missing. H: pin=b10502/vendor=b10502 and J: pin=b10362/vendor=b10362 are each internally consistent but the exact incident state. Fix adopted: aggregate verdict over required trees: remote.pinned_sha == local pinned_sha; campaign/execution trees additionally require bigcherry HEAD == declared expected tooling revision (per-tree config).
6. ENFORCEMENT — humans will under-follow 'commit immediately' / 'walk the list' / 'check the other trees'. Fix adopted (cheaper hooks, no orchestrator): bigcherry pull REFUSES to move the checkout while the pin config change is uncommitted (makes the load-bearing ordering mechanical); campaign entry point auto-verifies its execution tree against canonical pin + expected tooling revision; --complete is machine-readable.
7. TEST MATRIX — added GPT's false-safe cases: vendor at historical recorded rev ≠ mid-rebase without marker; pull-before-repin with target already recorded ⇒ drift; uncommitted repin distinguishable from declared bump; vendor==pin with tracked edits ⇒ revision-consistent/content-unverified wording; pinned tag record resolving to different SHA ⇒ fail; H/J each consistent on different pins ⇒ aggregate fail; stale bigcherry on campaign remote ⇒ campaign-tree fail; controller-has-record/remote-does-not ⇒ never infer remote mid-rebase; required remote unreachable during --complete ⇒ fail; vendor at new pin before audit/invalidation ⇒ --complete fails (record stage not advanced).
8. CONFIG — config.py whitelist (v2 top-level unknown rejection) must gain 'trees'; trees.remote entries get explicit allowed-key validation, not convention.

## Conclusion

Revise before implementing: transition-aware local verdict + cross-tree aggregate convergence + separate completion policy + honest reduced remote verdict. All four fixes adopted into the RE48 design (2026-08-21 revision); implementation proceeds from the revised design only.
