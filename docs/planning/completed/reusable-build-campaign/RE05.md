# Derive effective source tree and source-slice identities

## Description

Explain and enforce the three source identities - what we asked for, what Git produced, and BigCherry's durable content-domain identity - and preserve full patch-set lineage in source provenance (revised scope per RV48; today the three are easy to conflate).

## Steps



## Detailed Solution & Technical Design

THE THREE IDENTITIES: source_plan_id answers 'what exact materialisation inputs did we ask for?'; source_tree_oid answers 'what Git tree did those inputs actually produce?'; source_slice_id is BigCherry's durable content-domain identity over the upstream revision/tree/object format. The effective-tree calculation itself is already sound (temporary Git index; does not mutate the worktree index).

REQUIRED: source provenance must retain ALL THREE identities plus the full upstream commit, the BigCherry revision, the overlay identity, and the patch-set lineage (patch_set_id, ordered module IDs, ordered module content hashes). The verified gap (RV48): workspace.materialize records per-patch (patch_id, content_hash) pairs correctly, but campaign_build.materialize_source overwrites metadata['plan'] with an ID-only structure - provenance loss at the campaign boundary. RE05 is the item that fixes the identity model RE04 implements.

Do NOT make source_slice_id carry the materialisation-input labels; content identity and request lineage stay separate even when two logical compositions produce identical bytes.

## Notes

RE05 (2026-08-17, commit 311da3c): closed the remaining identity-completeness gap. The three source identities were previously incomplete in persisted provenance -- source_slice_id/source_tree_oid were present (from source_identity.describe()), but source_plan_id ('what request did we ask for') and materialization_plan_id ('what did that content-resolved request actually produce, keyed by') were only implicit -- materialization_plan_id in particular was literally the destination directory's own name, never a named field in the record's content. campaign_build.materialize_source() now writes both explicitly into the persisted record. New test (ThreeSourceIdentitiesPersistedTests) proves all three identities (four genuinely distinct values for a real materialize_source() run: source_plan_id, materialization_plan_id, source_tree_oid, source_slice_id) are present and none collapses into another. Verified on Windows and Brutus (Linux); full suite green both places (898 local).

The three RV48-flagged 'key missing acceptance tests' (patch-content edit under unchanged ID does not reuse; overlay-content edit does not reuse; tampered cached worktree fails closed) were already covered by RE04's own test suite (test_re04_materialization_safety.py) -- RE05's notes already correctly attributed cache/reuse mechanics ownership to RE04 and identity-completeness/explanation ownership to itself; only the latter remained, and it is now done.
