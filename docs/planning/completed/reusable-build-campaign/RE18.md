# Canonical CampaignLane planner and sequential multi-lane runner

## Description

A small outer planner/runner that expands a campaign request into multiple CampaignLane specs and executes them via execute_campaign_lane() (RE16), replacing legacy cmd_build's --all/--recipe(repeatable)/per-recipe-build-variant looping -- but built over canonical v2 source/build/platform identities, NOT legacy recipes/groups/states (those are transitional compat-only concepts per recipes.py's own _load_v2_compat adapter). Sequential execution of N lanes is sufficient -- do not unify multiple lanes into one giant CampaignGraph; the two-phase materialize/build split exists precisely because source_slice_id is unknown until materialize completes, and campaign_plan.py already documents that boundary.

## Steps

1. Define CampaignLane (source_name, build_name, platform_name, architectures, inputs) as the canonical unit a planner produces.
2. Define plan(request, config) -> tuple[CampaignLane, ...] -- expands an explicit list of (source,build,platform) selections, or a named canonical profile (RE14.22), into concrete lanes.
3. Define a sequential runner: for lane in plan.lanes: results.append(execute_campaign_lane(lane_to_spec(lane), context, store)); aggregate a campaign-level result summary (pass/fail per lane), matching legacy cmd_build's failure aggregation behavior.
4. One lane failing must not corrupt or misidentify another lane's result -- verify via a real fault-injection test (see RE14.25).

## Detailed Solution & Technical Design

gpt-auto-agent design (RE14 round 19). Deliberately smaller in scope than it first looks: NOT a NewCampaignRecipeOrchestrator with groups/states/tree-state grouping -- that would turn transitional compatibility concepts back into permanent architecture. Parallelizing independent lanes or coalescing shared source materializations is explicitly out of scope for the cutover gate -- sequential is adequate.

def run_campaign(lanes: tuple[CampaignLane, ...], context, store) -> dict[str, LaneResult | Exception]:
    results = {}
    for lane in lanes:
        try:
            results[lane_id(lane)] = execute_campaign_lane(to_spec(lane), context, store)
        except Exception as exc:
            results[lane_id(lane)] = exc
    return results

## Notes

Completed 2026-08-17. Implemented per the recorded design (see code_samples/detailed_solution), sized down to the M-effort scope explicitly called for: campaign_planner.py adds CampaignLane (canonical planning unit over real config identities), CampaignRequest (explicit selectors OR a named CampaignProfile from RE19's config.campaigns -- exactly one), plan() (validates every source/build/platform identity against real config before producing lanes), and run_campaign() (sequential execution over execute_campaign_lane(), fault-isolated per lane).

Resolved the run_id collision trap flagged during RE17's design review before writing the runner (not discovered by it): every run-scoped filesystem/ArtifactStore path in campaign_execution.py/campaign_workers.py is keyed on run_id alone (e.g. runs/<run_id>/generate/generated-tree.json), and execute_campaign_lane() was designed for one lane per run_id. run_campaign() derives a distinct execution run_id per lane (campaign_run_id + blake2b digest of lane_id) rather than sharing the campaign run_id across lanes -- fixed at this seam, no changes needed to campaign_lane.py/campaign_execution.py/campaign_workers.py.

10 new unit tests (test_campaign_planner.py): explicit-selector and named-profile expansion, unknown-identity/malformed-request rejection (both/neither selectors+profile_name), distinct per-lane run_ids under one shared campaign run_id (mocked execute_campaign_lane), fault isolation across lanes. Local suite green on Windows (805 passed, 3 skipped) and Linux (all pass), ruff-clean.

Proven for real on Brutus (tuning-code-rebase @ fe0925b): a real two-lane run_campaign() call (stock + tune, sharing one campaign run_id 're18-real-proof') on real gfx1100 hardware -- both lanes succeeded with distinct derived run_ids (...-56b5e231d75a / ...-4d17462ae74e), no path collision; stock correctly skipped generate/workload/smoke (workload_id=None), tune correctly ran the full chain and reused the already-built binary (build_plan_id=a4a2020067301441d029877d1e368c70, matching RE17's proof).

Deliberately excluded from scope (per the recorded design and steps): parallel lane execution, unifying multiple lanes into one CampaignGraph, real gpu_resource_ids wiring (no field exists yet in config.Platform to source them from -- CampaignLaneExecutionSpec.gpu_resource_ids stays at its () default).
