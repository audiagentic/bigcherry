# Canonical CampaignLane planner and sequential multi-lane runner

## Description

A small outer planner/runner that expands a campaign request into multiple CampaignLane specs and executes them via execute_campaign_lane() (RE16), replacing legacy cmd_build's --all/--recipe(repeatable)/per-recipe-build-variant looping -- but built over canonical v2 source/build/platform identities, NOT legacy recipes/groups/states (those are transitional compat-only concepts per recipes.py's own _load_v2_compat adapter). Sequential execution of N lanes is sufficient -- do not unify multiple lanes into one giant CampaignGraph; the two-phase materialize/build split exists precisely because source_slice_id is unknown until materialize completes, and campaign_plan.py already documents that boundary.

## Steps

1. Define CampaignLane (source_name, build_name, platform_name, architectures, inputs) as the canonical unit a planner produces.
2. Define plan(request, config) -> tuple[CampaignLane, ...] -- expands an explicit list of (source,build,platform) selections, or a named canonical profile (RE14.22), into concrete lanes.
3. Define a sequential runner: for lane in plan.lanes: results.append(execute_campaign_lane(lane_to_spec(lane), context, store)); aggregate a campaign-level result summary (pass/fail per lane), matching legacy cmd_build's failure aggregation behavior.
4. One lane failing must not corrupt or misidentify another lane's result -- verify via a real fault-injection test (see RE14.25).

## Detailed Solution & Technical Design

gpt-auto-agent design (RE14 round 19). Deliberately smaller in scope than it first looks: NOT a NewCampaignRecipeOrchestrator with groups/states/tree-state grouping -- that would turn transitional compatibility concepts back into permanent architecture. Parallelizing independent lanes or coalescing shared source materializations is explicitly out of scope for the cutover gate -- sequential is adequate.

def run_campaign(lanes: tuple[CampaignLane, ...], context, store) -> dict[str, LaneResult | Exception]:
    results = {}
    for lane in lanes:
        try:
            results[lane_id(lane)] = execute_campaign_lane(to_spec(lane), context, store)
        except Exception as exc:
            results[lane_id(lane)] = exc
    return results

## Notes

Completed 2026-08-17 (hardened after GPT's round-20 check-in on the RE17/RE18 real implementation, before starting RE20).

Original implementation and real-hardware proof unchanged (see prior notes below the line). Two additional hardening fixes landed per GPT's review:

1. Architecture default: CampaignRequest.architectures defaulting to () and flowing verbatim into every lane meant "unspecified" silently became "generate for no architectures at all" -- architectures feeds make_generate_worker's candidate-universe enumeration directly, independent of platform.targets (compile-time AMDGPU_TARGETS only). This was the exact pre-existing legacy _generate_for() bug (omits --arch, silently falls back to the separate generate CLI's own --arch all) that RE14's own parity harness already had to route around. plan() now resolves empty/unspecified architectures to the selected platform's own targets; an explicit override must be a non-empty subset, never a superset.
2. Duplicate lane rejection: _lane_run_id()/run_campaign()'s result dict are both keyed on source:build:platform alone -- a duplicate selector would silently overwrite an earlier lane's result. plan() now rejects duplicate lane identities, and run_campaign() rejects them defensively too (callers can construct CampaignLanes directly without plan()).

5 new unit tests (15 total in test_campaign_planner.py). Full suite green on Windows (810 passed, 3 skipped) and Linux, ruff-clean.

Proven for real on Brutus (tuning-code-rebase @ 6fbc14a): plan() against the REAL standard profile (5 lanes: llama-native:stock, bigcherry-native:control, bigcherry:record, bigcherry:tune, bigcherry:replay) with no explicit architectures correctly resolved every lane to linux-multi's real targets (gfx1100, gfx1201, gfx1030) -- exactly what bigcherry build --all will ship once RE21 flips the CLI. Duplicate-selector rejection also proven against the real profile's lane list.

GPT's review confirmed: no architectural pivot needed; RE20-23's ordering and scope remain correct as recorded. GPT's specific guidance for RE20 (tighten acceptance evidence to explicitly assert distinct run_ids/matching result keys/expected optional-ref shapes across all five real standard-profile lanes, not just count them; do not wire gpu_resource_ids -- that's a runtime/scheduler concern, not a Platform config concern) and for RE21-23 (canonical `build` should reject ALL untranslatable legacy flags -- --variant-set, --target, --force, --dry-run, bare --recipe, not just --groups/--states; legacy-build keeps accepting --groups/--states during the compat window; exit 1 for a lane execution failure vs exit 2 for invalid/unsupported request syntax) is recorded here for RE20/RE21/RE22 to pick up directly rather than re-deriving.

SCALABILITY LIMITATION (RV48 audit 2026-08-17): inputs_by_build and validation_by_build in CampaignRequest are keyed by BUILD NAME, which cannot express two lanes with the same build name but different source/platform-specific artifacts. The standard profile avoids this because each build name occurs once there. Before calling the planner fully general-purpose, add a per-lane override keyed by canonical lane ID (source:build:platform). Recorded as a known limitation, not a defect in the shipped profile.
