# Backend is now intrinsic to requested BuildPlan identity

## Description

External review (BigCherry_RE30_patch_governance_reassessment_2026-08-20.md) P0-1/P0-2: BuildPlan.cmake_options previously never saw backend-injected cmake options (GGML_VULKAN=ON / AMDGPU_TARGETS=...) unless a source's static recipes.toml options happened to already declare them, so a HIP and a Vulkan lane sharing the same nominal source/build/platform names could produce the SAME build_plan_id/build_dir while compiling different commands -- a cached HIP build could be silently reused for a Vulkan request or vice versa.

## Steps

[DONE] Added backend: str = "hip" field to BuildPlan (tools/bigcherry/builds.py), default preserves existing HIP identity for the field's addition alone.
[DONE] campaign_lane.py::_execute_build_phase now computes backend = cfg.sources[spec.source_name].backend and folds campaign_build._backend_configure_options(backend, platform_cfg) into merged_options (the same dict that becomes BuildPlan.cmake_options), matching what campaign_workers.make_build_worker's real cmake_configure_args() call already receives -- no double-injection, just consistency between requested identity and what actually compiles.
[DONE] Widened builds._EFFECTIVE_CONFIGURE_PREFIXES with "GGML_VULKAN" so effective_build_id()/reuse validation also captures Vulkan's real configure options, not just HIP's.
[DONE] Regression test added: tools/tests/test_campaign_lane.py::ExecuteCampaignLaneTests::test_hip_and_vulkan_produce_different_build_plan_id proves same source/build/platform, backend=hip vs backend=vulkan -> different cmake_options, different build_plan_id, different build_directory().
