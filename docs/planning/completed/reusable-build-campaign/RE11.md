## Detailed Solution & Technical Design

GPT-auto-agent full implementation plan (2026-08-17), fifth/final priority before RE15 -- deliberately scoped to the MINIMUM durable run protocol RE15 needs, not a full scheduler rewrite: static intent + complete operation spec + dependency-output binding + persisted success descriptors + cross-process rehydration/resume. Depends on RE25 (ArtifactDescriptor rehydration) and RE10 (real lifecycle stages to make durable).

New tools/bigcherry/campaign_operation.py: typed OperationSpec union (MaterializeOperationSpec/GenerateOperationSpec/BuildOperationSpec/RuntimeSmokeOperationSpec) capturing every behavior-affecting input per stage kind (currently StageNode's spec hash omits operation details like smoke workload/environment entirely). operation_spec_hash(spec) is the STATIC identity; separately, execution_hash(operation_spec_hash, input_artifact_ids) is what actually governs reuse -- a build's static spec can stay identical while its generate dependency produces different output bytes, so these must not be collapsed into one hash.

StageNode gains a real operation: OperationSpec field. CampaignIntent(schema_version,campaign_plan_id,lane_id,run_id,stages: tuple[StageIntent,...]) is persisted BEFORE work starts, in three layers because materialization is a real identity boundary (source_slice_id doesn't exist until it finishes): work/campaign-runs/<lane-run-id>/request.json (canonical lane request, exists before materialize), materialize/intent.json, then build/intent.json written only after materialization establishes source_slice_id/BuildPlan.

StageRecord becomes state-typed (running/succeeded/reused/failed/blocked/interrupted) with operation_spec_hash/execution_hash/input_artifact_ids/output_artifact_ids/output_content_hashes -- persisted as stages/<stage-id>/running.json (crash marker, not evidence) then stages/<stage-id>/result.json (immutable once published). CampaignStageExecutor.__call__() returns real ArtifactRefs (not just content hashes), gains restore_outputs() for resume, and specially handles restoring the materialize stage's source_slice_id into its holder.

Resume algorithm per stage: dependencies must be succeeded/reused -> rehydrate+verify every dependency output -> compute execution_hash -> if immutable result.json exists, verify operation_spec_hash+execution_hash+every output byte match, then restore (state=reused) -> if running.json exists without result.json, treat as interrupted (NOT success) -> otherwise acquire resources, write running.json, execute, verify outputs rehydrate, atomically publish result.json, remove running.json.

Narrow resource-lock addition: owner_is_live_local_process()/break_if_dead_local_owner() -- break ONLY a dead local-host owner via an explicit resume path, NEVER by age/timeout, and NEVER for another host's lock.

Tests (test_re11_durable_resume.py): successful cross-process resume (second Python process, same run ID, zero compiler invocations because everything rehydrates); crash-after-running-marker correctly treated as interrupted not success; artifact-byte tamper on a completed stage output fails resume closed; descriptor tamper fails closed; intent/request mismatch on the same run ID fails before any work; each operation field (n_gen/environment/architecture/binary path) changing the operation hash; a dependency's output changing (same static build spec) correctly changing execution_hash and forcing re-execution; restored generate outputs available to a restored downstream build; restored materialize source_slice_id correctly populates the holder; dead local resource owner recoverable only via explicit resume; other-host/unknown lock never auto-broken.
