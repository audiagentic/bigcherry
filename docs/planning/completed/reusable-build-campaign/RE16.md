# Promote execute_campaign_lane() into a reusable production API

## Description

Extract the reusable logic out of re14_real_run.py (materialize -> generate -> build -> optional runtime-smoke -> reuse) into a real, importable production function `execute_campaign_lane(spec, context, store) -> LaneResult`. re14_real_run.py becomes a thin harness client of that API rather than owning the logic itself. This is the prerequisite for RE14.20/21 -- nothing else in the multi-lane orchestrator plan can be built until this exists.

## Steps

1. Define the LaneExecutionSpec/LaneResult shapes (see code_samples).
2. Move the body of re14_real_run.main() (materialize call, BuildPlan construction, generate/build/smoke worker wiring, CampaignRun.execute calls, reuse pass) into campaign_lane.py's execute_campaign_lane().
3. Rewrite re14_real_run.py's main() to build a LaneExecutionSpec from its CLI args and call execute_campaign_lane(), keeping only argument parsing and the RE14_PARITY_RESULT_JSON print for harness compatibility.
4. No subprocess/shelling from any future multi-lane orchestrator into `python -m bigcherry campaign-build` -- it must call execute_campaign_lane() directly, in-process.
5. Unit test execute_campaign_lane() directly (it should not require argparse or a subprocess to exercise).

## Detailed Solution & Technical Design

gpt-auto-agent design (RE14 round 19, verified: config.py's v2 Build.needs is a real frozenset[str]; recipes.py's _load_v2_compat compresses it back to a single legacy string -- confirms the v2/legacy split this design relies on is real, not assumed).

This item is purely a refactor/extraction -- no new behavior. The goal is a stable, testable, in-process API that RE14.20 (generalized inputs) and RE14.21 (the planner/runner) build on top of, instead of shelling out to a CLI subprocess the way re14_parity_run.py currently does to re14_real_run.py.

def _require_one_artifact(refs, *, kind, stage_id) -> ArtifactRef:

KEY DELIBERATE BEHAVIOR CHANGE (the one substantive change bundled into this otherwise-pure extraction, because the API cannot safely serve a multi-lane caller without it): inventory publication moves off the single fixed path inputs/inventory.json (which would collide -- ArtifactStore is immutable, so two lanes with different inventories would raise ArtifactError at that shared path) to a content-addressed inputs/inventory/<sha256>.json path.

The same-run reuse proof (run CampaignRun.execute() twice, confirm every stage comes back "reused") is REMOVED from execute_campaign_lane()'s normal semantics -- it is a test/harness concern (proving CampaignStageExecutor+make_artifact_reuse_checker's same-process/same-executor contract), not something a production multi-lane runner should pay a second generate+build+GPU-smoke pass for on every lane. Keep it as a private test-facing helper (_assert_same_run_reuse) or an explicit integration-test/probe path, not part of re14_real_run.py's normal execution anymore.

re14_parity_run.py explicitly KEEPS shelling out to `python -m bigcherry.re14_real_run` as a subprocess after this refactor -- do not switch it to importing execute_campaign_lane() directly. RE14 step 3 requires the new arm to share no checkout/generated-dir/CMake-dir/ArtifactStore-namespace with the legacy arm; process separation is a stronger, useful additional clean-room boundary beyond the textual requirement, and the parity harness is deliberately exercising the exact CLI/new-path composition, not a third slightly-different in-process implementation. Update re14_parity_run.py's module docstring to drop 'reuse' from the described new-arm stage sequence once the automatic second pass is removed.
