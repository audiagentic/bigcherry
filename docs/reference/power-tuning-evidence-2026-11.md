## Rejected, unsafe, or not proven on this host

- The host XTX VDDGFX sweep through -125 mV recorded no resets; this is **not** long-term reliability or permission to apply the offset to any other XTX. The XTX 272 W cap floor makes a lower cap ineffective under these loads.
- A reported **R9700 -100 mV hang**, stable offsets differing per card, and an **R9700 MCLK reduction costing 6.6% decode** are **third-party prior art in PWR02**, not local crash or MCLK-sweep evidence. No R9700 power cap, voltage or MCLK winner was established locally.
- R9700 POWER_SAVING was ineffective; forced-low FCLK only saved ~1 W unloaded and lacks performance acceptance. The R9700 runtime-PM/BACO D3 investigation was read-only, with no forced low state or claimed solution: `${BC_WORK_ROOT}/runs/r9700-deepidle/`. Owner notes possible BIOS PCIe power-saving crashes; no new setting was tested.
- Pending gfx1100 AQL barriers draw ~95 W at idle, resolved operationally by the RAD20 park/drain design (~4–7 W), **not** by board undervolting: `docs/reference/FINDINGS.md`, `tools/lab/radiance/rad20-mes-idle.cpp`.

## XTX -125 mV recheck, 2026-11-11 (kernel 7.0.13-gfxoff, Radiance 1.17.0 build, MTP depth 3)

The 2026-10-27 saving did **not** reproduce. Setting applied through the lease-fenced PowerTransaction on both XTX (read back -125 mV, restored to 0 mV after every arm), ABBA over two lease windows, `flashnext-4gpu`, 6-stream decode, 900-token prompts, 1,500 new tokens x 4 reps, power sampled at 1 Hz only inside the decode window:

| Arm | Per-XTX power, mean (median) | Decode tok/s |
|---|---|---|
| stock C1 | 190 / 190 W (197 / 196) | 325 |
| -125 mV D1 | 194 / 192 W (200 / 200) | 324 |
| -125 mV D2 | 196 / 195 W (202 / 201) | 326 |
| stock C2 | 191 / 190 W (197 / 197) | 326 |

Speed is identical; power is not lower and is about 4 W higher with the offset. A short-protocol ABBA (1- and 6-stream decode, 8K prefill, whole-run power) agreed: 161-165 W stock against 167-170 W undervolted, speed within noise. A saturating single-card stress test (two repeats per arm) shows the mechanism: held near its power limit the undervolted card drew 288 W at 3158 MHz and 989 mV against 272 W at 2915 MHz and 1002 mV stock, so the voltage headroom is spent on clock, and measured voltage fell by only 13 mV. Under serving decode the cards now draw about 190 W (the October decode phase measured 154 W), i.e. they run harder than in the October soak, which used a different workload and build.

Verdict: **-125 mV is not a validated saving on the current build.** That **uncapped offset-only** setting is withdrawn as a current-build apply-profile value; a **fixed-SCLK plus offset** combination needs separate qualification. Raw runs: run folder xtx-undervolt-ab (A1/B1/B2/A2 short protocol, C1/D1/D2/C2 sustained, stress-out).

## Profile decision

Historically, **-125 mV on the two named host XTX cards** had extended October testing; November withdraws the **uncapped offset-only** setting as a current-build apply-profile candidate; capped-clock plus offset is a separate, still-unqualified candidate. Preserve it as historical device-specific evidence only; a new qualified A/B on the current driver/build is required before any opt-in apply candidate exists. Observe/no-write is the default for named profiles; no measured R9700/6900 XT power-control optimum can be populated. A calibrated candidate must never auto-activate from a cached observation. The v2 serving plan owns role/BDF/settings and content digest, while actual probe/apply/restore observations belong in a separate receipt (PWR07–PWR09). CPU EPP/governor controls remain out of scope.

### Common short-lease procedure and acceptance

All proposed work below is **lead-run**, *not performed by this change*. The only controls currently supported by `gpu_power.Setting` / `PowerTransaction` are `sclk_max_mhz`, `vddgfx_offset_mv` and `power_cap_w`; DPM/performance-profile writes are *not supported* by this transaction class. An October-tested value is only evidence that the control was tried on the **old** build, not current acceptance.

1. **Inventory before write:** Resolve the two BDFs from the host layout (do not use GPU index as identity). In each `/sys/bus/pci/devices/<BDF>/` read `pp_od_clk_voltage` (including advertised min/max), `power_dpm_force_performance_level`, `pp_dpm_sclk`, `pp_power_profile_mode`, selected hwmon `power1_cap`, `power1_cap_min`, `power1_cap_max`, `power1_cap_default`, `power1_average`, `freq1_input`, `in0_input`, temp, fan, busy, firmware MES/SMU, driver/ROCm/build identifiers. Sample baseline loaded-idle, decode and prefill. Snapshot pre/post values to the receipt. For cap sweep, a journal snapshot of cap=0 is insufficient; stop until a valid cap and restore are proven. Never write unsupported/out-of-range settings or with a stale journal.
2. **Exact transaction pattern:** Extend a **run-local copy** of `runs/xtx-undervolt-ab/txn.py` to accept an explicit per-arm setting (original only accepts hardcoded -125 mV). For one selected arm, create `PowerTransaction(tag, journal_dir, lease_ok=gpu_lease.held_by_this_process)`, run `tx.prepare({b: gpu_power.Setting(sclk_max_mhz=N, vddgfx_offset_mv=V, power_cap_w=P) for b in xtx_bdfs}, xtx_bdfs)` and `tx.apply()` **before** launch; run fixed build/workload; stop and verify engine+helpers gone; `PowerTransaction.recover(journal, lease_ok=..., processes_exited=True)`, inspect restored readback/receipt. Omit unspecified fields by passing `None`; **do not copy a test command onto the unmodified txn.py**, which would apply -125 mV regardless of label. Existing current-build *stock* command (run from `BC_WORK_ROOT`): `agent-lease acquire -- bash runs/xtx-undervolt-ab/arm2.sh stock STOCK0`. `arm2.sh` measures sustained decode; `arm.sh stock STOCK1` measures 1/6-stream short decode + 8K prefill, but its power CSV is whole-run. Isolated prefill watt windows require extending the sampler before candidate tests. One arm **per lease**, never leave a power change active across leases.
3. **Reproducible measurements:** ABBA across four short leases, **same build, layout, MTP, prompts, seed and warm-up**. Each arm ~8–12 min including startup/1-stream and 6-stream 900→1500 decode (four reps per shape) + separately ≥4 8K prefill reps; budget **15–20 min** if isolated prefill, 60-s idle and thermal steady-state require more time. Sample per-phase 1-Hz all-GPU/CPU watts, effective SCLK/VDDGFX/DPM, temperature, cap and busy, exact token counts, decode/prefill tok/s **separately**, TTFT, text/hash/quality, errors, idle W. Record the interval used, not mixed-window averages. A 40-minute Oct-style soak is an **optional follow-up long lease**, not the short-screening sequence.
4. **No-regression gate (proposed, not measured):** For both single- and six-stream decode **and** isolated prefill, candidate/bracketing-stock speed ≥0.99 and a one-sided 95% confidence lower bound ≥0.99; otherwise reject or mark inconclusive (do not silently accept 2–3% lower speed). Outputs must match quality/hash/KLD policy with no resets, thermal throttling, jitter regression, journal mismatch or restore failure. A *power winner* additionally needs ≥5% less **summed-XTX** integrated J/token and ≥3% less **whole-host** integrated J/token (CPU and other GPUs included) for at least one phase, with no worse J/token or throughput in the other; idle watts unchanged or lower. Integrate sampled joules over actual token intervals; a sum of board median W divided by tok/s is only a proxy. If CPU package energy is missing, whole-host gate remains **unmeasured**, not passed. Require a second session, prolonged correctness soak, per-BDF/build/kernel qualification and explicit v2 profile selection before enabling any candidate.
5. **Emergency handling:** On any failed preflight, write, readback, test, stop or restore, fail closed, keep diagnostic/journal data, and refuse another explicit arm until recovery; do not claim restored unless verified. No GPU lease or sysfs write belongs to the planning/research agent.

## Lead addendum — why stock XTX decode rose ~35 W and how to rerun the October protocol (2026-11-11; card-free)

**Do not start by tuning voltage.** October's valid original stock baseline (`pwr01-baseline-10271708`) was **154.0/155.5 W** on the two XTXs in single-stream continuous decode (~93.5 aggregate tok/s by the October definition); November's C1/C2 *stock*, with a different six-stream benchmark, was **190.3/190.1 and 191.3/190.3 W** (~325 engine decode tok/s under November's definition). The extra **~35–37 W per card occurred at stock**. Neither throughput figure measures isolated XTX tok/s, and the two definitions/concurrencies are not directly comparable. Explain the stock shift before attributing any loss of UV saving to a voltage offset.

**Corrected October configuration discovery:** `git show 710d588:tools/lab/radiance/launch-flashnext-best.sh` explicitly sets `--num-speculative-tokens 3`, engine R9700 TP1, `--max-num-seqs 6` (capacity, not six simultaneous requests), ngram RAM, FP8 KV, two XTX helpers each budgeted **22528 MiB** full-width hot experts. **MTP3 was present in October** and the XTX budgets did **not** increase in November. November's `flashnext-4gpu` launches **three** helpers: the same 22528 MiB head budget on each XTX but a 14336 MiB 6900 XT **tail** helper (November `A1/launch.log` names 9,320 expert assignments per XTX and 5,931 on the tail), new heat/owner map and code paths. The actual October *per-XTX dispatch count, row shapes, expert hits and kernel step timing* were not recorded; **do not assert more per-XTX arithmetic** simply because a tail was added. More concurrent requests can increase duty cycle even if part of the routed expert work moved to the tail.

### Ranked root-cause discriminators for the +35 W stock shift

1. **Shape/duty-cycle and work distribution (highest):** October `pwr01-baseline.sh` is a continuous **single greedy request** (1024 generated tokens), November `arm2.sh` runs **six simultaneous requests** ×1500 tokens ×4 reps. Gather per-BDF utilization, effective gfxclk, memory-busy, kernel time, helper row/split and routing histograms under *both shapes on the same current build and same static placement*. The 2→3-helper owner map and heat source changed; record a helper-work attribution before blaming a board. Diagnostic: if current single-stream stock falls toward October's ~154–158 W while six-stream remains ~190 W *on the same sensor*, the main shift is concurrent duty/work, not a changed power sensor or undervolt.
2. **Clock/DPM/voltage, not assumed cap limitation:** The October research note states decode clock **~3050 MHz** (source measurement is in prior summary, not in raw `pwr01-baseline` CSV). A clock rising while busy is constant suggests boost; busy rising at similar clock suggests duty cycle.
3. **Power-sensor identity/calibration:** October `amd-smi metric -g ID -p` extracted `SOCKET_POWER` by BDF-to-amd-smi lookup. November `watts.sh` reads only `/sys/class/drm/card0` and `card1` `power1_average`, with **no BDF identity check**. Both are nominal socket/SoC power averages on the discrete Navi cards, but exact firmware path, smoothing window, version and alignment are **not proven identical**. Kernel hwmon defines `power1_average` as averaged SoC power (µW), `power1_input` as instantaneous SoC power (µW). **Simultaneously** collect AMD-SMI `SOCKET_POWER`, hwmon `power1_average` and `power1_input` at 1 Hz for each BDF with timestamps and correct units; compare matched-window medians/means and check idle and fixed-load offsets. 4. **Build/kernel/thermals:** October production source was v1.9.0-era, kernel stock 7.0.13, ROCm 7.2.4; November source Radiance 1.17.0 and patched `7.0.13-gfxoff`, ROCm still 7.2.4.
