# Radiance runtime

At revision `a1a48cc0a6bc`, the production source includes the remote-MoE handoff and prefill governor. Both have conditions for activation. The best first experiments are the fused gather on nonconsumer ranks and repeated GPU capability checks. The operation counts below come from source. Where streams or recorded passes hide host work, fewer calls may yield little wall-clock improvement. [Active serving patches and production source](../../../engines/radiance/recipes.toml#L11)

## 1. Retire the fused handoff directly on nonconsumer ranks

**Observed.** On an active fused pass, every rank issues the inject op. Only `consumer_of(layer, world)` can send helper work. All ranks must still mask their own routed expert IDs during publish. After validating shapes, `inject_launch` computes that same consumer, then launches wait, route mark, inject initialization, injection and finish plus one asynchronous clear of `4 × rows × top_k` bytes. On a healthy nonconsumer there are no requests, the injection writes no rows, yet one block per token still launches for it. [Fused merge caller](../../../engines/radiance/patches/rad0002_moe_remote_handoff/patch.py#L630) · [Rank selection and route role](../../../engines/radiance/components/moe-remote/moe_remote_shm.h#L55) · [Host launches](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L1100)

**Small change.** After the existing host argument checks, select a checked nonconsumer finish on the same stream. Validate the immutable pass ticket, require zero published slots and combine generation, and preserve rejection of a negative live count from `eoff[n_expert]`. Retain finish/clear semantics and the downstream parent seal. The consumer keeps its existing sequence. That would remove four kernel launches and one clear per nonconsumer rank per eligible pass. A two-rank run has one such rank. A single-rank run has none. Scope this to fused inject: the ordinary add still computes a local output on nonconsumers. [Injection checks](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L640) · [Retirement and seal](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L796)

**Proof.** Exercise alternating consumer layers with one and multiple ranks, no routed rows, multiple helpers, and back-to-back recorded passes across a placement epoch change. Compare sorted rows, router weights, output and published/consumed counts. Inject an unexpected publication and require rejection. Count actual GPU dispatches, then compare steady decode and prefill on identical inputs. [Exactly-once tests](../../../engines/radiance/components/moe-remote/tp_exactly_once_test.cpp) · [Ticket replay](../../../engines/radiance/components/moe-remote/ticket_replay_test.hip)

## 2. Resolve GEMV capability once per device, variant and geometry

**Observed.** The gfx12 plugin first tries its decode gate/up kernel, falling back to libr4d for unsupported shapes. Each qualifying host launch asks HIP for the current device, device properties, compiled function attributes and occupancy for the same 256-thread kernel and requested dynamic shared memory. On the separate helper path, `select_gemv<TOKEN>` also queries attributes and occupancy on eligible selections, for gate/up and down. These are host calls during launch or enqueue. A captured device pass may replay without paying them again. The gfx12 launch also retains a sorted-input kernel branch after an earlier unconditional return for sorted inputs. [Plugin caller](../../../engines/radiance/components/bc-gfx12/bc_gfx12_plugin.cpp#L120) · [Gfx12 filter, probes and dispatch](../../../engines/radiance/components/bc-gfx12/bc_moe_gemv.hip#L229) · [Helper probe and selector](../../../engines/radiance/components/moe-remote/moe_remote_gpu.h#L49) · [Helper stage choices](../../../engines/radiance/components/moe-remote/moe_remote_gpu.h#L850)

**Small change.** Start with gfx12. Keep the current-device check or use an explicitly device-bound instance. Cache successful immutable property/attribute observations for that device and compiled kernel, and successful occupancy observations for that block size and dynamic byte count. Keep tensor-specific checks and `choose_gemv` on each shape. Preserve fallback when the probe fails and allow retry on a later call. Remove the unreachable sorted-input launch. Use the helper's device-bound lifetime for any subsequent helper cache. Preserve the distinct gate/up and down variants, comparison mode and plugin fallback. A width change or a different device can change eligibility. [Shared geometry decisions](../../../engines/radiance/components/moe-remote/gemv_geometry.h) · [Boundary tests](../../../engines/radiance/components/moe-remote/gemv_geometry_test.cpp)

**Proof.** Count HIP queries for repeated and alternating widths on two devices, including first use, a failed probe and a sorted-input fallback. Compare launch choices, dynamic shared bytes and output to baseline. Report uncaptured host submit time separately from captured replay throughput.

## 3. Pass the owner index directly to mailbox publish

**Observed.** A sealed placement already contains one owner byte per layer/expert. Rank startup and generation preparation expand it into a separate bitmap per helper. The publish kernel launches a single 256-thread block. For each helper it traverses every routed slot, rechecks the slot map and tests membership, with three block barriers per helper in the counting loop. With H helpers, R rows and K selected experts there are H × R × K loop visits. Heat is counted on the first scan. For two helpers, 4,096 admitted rows and top-10 routing, that is 81,920 visits on this one block. This is an illustrative shape, conditional on the configured handoff row limit. [Owner conversion and validation](../../../engines/radiance/components/moe-remote/owner_generation.h#L45) · [Publish scan](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L236) · [Launch dimensions](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L948)

**Candidate.** Keep the same two ticket-selected generation banks, epoch/digest checks, upload events and lifetime. Supply an indexed owner byte to publish. In one slot traversal, count all in-range heat, check protected experts, determine the helper, then append using a per-helper shared counter and mask as before. Keep the helper-specific signaling loop, release fence and request accounting. First prototype this only for multi-helper topologies. An owner byte costs more device memory than one or two bits per expert and may lose on small batches. Recalculate both bank sizes and any memory admission accounting before enabling it. The relative order of atomic appends can change: verify the downstream reduction and actual output even when route sets match. [Generation upload](../../../engines/radiance/components/moe-remote/moe_remote_hook.cpp#L511) · [Request counts and publication ordering](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip#L276)

**Proof.** Replay sparse, dense, protected and all-local layers on consumer and nonconsumer ranks, with heat enabled and disabled. Compare masked IDs, per-helper route tuples including weight and slot, heat, completion counts and model output. Move one expert between generations. Measure publish time by helper count and rows before deciding whether the indexed representation earns its memory.

## 4. Defer the prefill governor's expensive inputs until the decision needs them

**Observed.** The budget gate takes its KV-fit answer by value. Its caller runs `preempted_can_prefill(s)` for every budget candidate reaching the gate, including short prompts admitted unconditionally, reserved long prompts deferred unconditionally, a lone prompt, and prompts already beyond the token budget. `prefill_load(true)` also scans running requests and planned entries, with a linear running-slot search for each eligible planned entry. At the v1.17.0 pin the KV-fit predicate additionally walks paged KV groups and running requests. Multiple candidates repeat the work. The cap path already short-circuits the KV probe. [Gate and scheduler hooks, edits scheduler_cpp-0 and scheduler_cpp-2](../../../engines/radiance/patches/rad0036_prefill_governor/patch.py#L41) · [Pinned KV-fit predicate](https://codeberg.org/StillDeadcode/radiance/src/commit/19d4e8fe0e18071b9b6300f15fc4ccf38dc4fa3d/core/sched/scheduler.cpp#L1603)

**Small change.** Pass a lazy load and KV-fit predicate to the existing policy, or stage its decisions in exactly the existing order. Short and reserved paths should avoid both walks. Only call the KV-fit predicate for a nonempty budget load whose next prompt would fit the token allowance. Preserve prefix-hit handling, undo, priority, reservation and lone-prompt progress. Avoid caching KV headroom across admissions or evictions, which can change it. Under arrival policy the main admission hook is already bypassed. [Governor policy source](../../../engines/radiance/patches/rad0036_prefill_governor/patch.py#L10)

**Proof.** Use the existing scheduler fixtures with counters on both predicates. Assert identical admission order, per-step plans and defer counts for prefix hits, short prompts behind a reservation, lone long prompts, and full cap/budget, plus fewer KV walks. Compare scheduler CPU time with competing long prompts before claiming a serving gain. [Governor tests embedded in patch](../../../engines/radiance/patches/rad0036_prefill_governor/patch.py#L49)

## 5. Stream FP8 expert uploads through the existing bounded buffer

**Observed.** Startup and expert movement both call `upload_weight`. FP8 code and scale bytes already have the runtime layout. For each plane, `load_plane_data` resizes a full vector, reads chunks into the existing bounce buffer and copies each chunk into the vector. Both vectors then remain live through transfer into the device arena or the host move buffer. For code and scale sizes C and S, their logical storage totals C + S bytes, and the intermediate copies move C + S bytes of payload in addition to the final transfer. W4 relayout consumes complete source planes and needs separate treatment. [Startup caller](../../../engines/radiance/components/moe-remote/moe_remote_gpu.h#L421) · [Move caller](../../../engines/radiance/components/moe-remote/moe_remote_gpu.h#L480) · [Read, transfer and FP8 path](../../../engines/radiance/components/moe-remote/moe_remote_gpu.h#L1645)

**Small change.** For the identity-layout FP8 path, verify exact on-disk lengths against planned/stored geometry before allocating the destination. For each bounded read, transfer directly from the existing bounce buffer at the checked destination offset. Keep the current ordering and synchronous ownership of that buffer. Propagate short reads and transfer failures before publishing any new expert or table generation. Extra small H2D submissions can increase startup latency when a plane spans many chunks. The gain to test first is lower peak host memory during reset/load or movement, not inference time.

**Proof.** Compare uploaded bytes for both expert parities, both projections, exact and partial final chunks, and movement versus bootstrap. Force a truncated plane and a mid-transfer error. Check generation visibility and slot reuse, then compare peak host RSS, transfer count and elapsed load time. [Generation-table tests](../../../engines/radiance/components/moe-remote/owner_generation_test.cpp) · [Slot-pool tests](../../../engines/radiance/components/moe-remote/worker_slot_pool_test.cpp)
