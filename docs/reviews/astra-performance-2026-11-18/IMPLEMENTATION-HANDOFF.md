## RAD54 · One checked fused-inject dispatch on a nonconsumer

1. At `moe_mailbox_ops.hip::inject_launch`, branch only after the current argument, shape, contiguity, shadow and mask-only gates and `consumer_of(layer, world)`. Keep the consumer's wait → rmask clear → route mark → inject init → inject → finish. The nonconsumer enqueues one checked retirement kernel on the **same rank stream**, returns the normal HIP launch status, and leaves fused gather/parent seal in their existing order. Ordinary add and shadow have separate semantics. Every rank still publishes its pass ticket and masks its local routed IDs. [Dispatch and retirement](../../../engines/radiance/components/moe-remote/moe_mailbox_ops.hip) · [Route ownership](../../../engines/radiance/components/moe-remote/moe_remote_shm.h)
2. In the kernel decode the four immutable per-pass words at `published_ticket_offset(d->slots, d->max_rows)` with `pass_ticket`. Check required scratch/stamp pointers and capacity, verify the slot's stamp owns the ticket ID, epoch and generation bank. Read `eoff[n_expert]` and trap on negative. Require zero for **every** `published[0..d->slots-1]` and the combine word `published[d->slots]`. Preserve their zero/cleared finish state. Leave lane/combine consumption records and counters untouched. A parent may already have published or consumed requests on previous layers. Checking the parent counters for zero would incorrectly reject a legal pass. Do not clear the four ticket words, reread the mutable rank ticket cell or write tensors/weights/route masks on this branch. [Pass decoder](../../../engines/radiance/components/moe-remote/mailbox_completion.h)
3. Keep publisher system-fence/release, consumer done-sequence acquire/status and immutable request validation, device-scope request counting, rank-stream join and parent seal. The seal validates exact published/consumed equality and ticket ownership, flushes changed lane/combine records, then system-release stores the host stamp's ticket ID last. The rank event follows the last reader and seal. A zero-request pass acknowledges no helper work and cannot advance the parent event or permit early bank reuse. Keep the consumer's BF16 arithmetic, layout and row ownership. [Engine pass hooks](../../../engines/radiance/patches/rad0002_moe_remote_handoff/patch.py)
4. Extend `mailbox_completion_test.cpp`, `tp_exactly_once_test.cpp` and the HIP test coverage. Exercise TP1, TP2 alternating consumer layers, one/multiple helpers, zero remote routes, sparse rows and back-to-back plays that switch epoch/bank. Include a parent with earlier nonzero counts followed by a healthy nonconsumer pass. Compare masked IDs, sorted slot→row mapping, weights, injected BF16 values, final reduced output, per-helper publication/consumption and sealed stamp to the original path. Run intentional GPU traps in separate child processes and synchronize to observe them. Corrupt each ticket field, stamp association, one published slot, combine word, or live count and require rejection. Seed the old scratch with nonzero data, then alternate roles to expose accidental reads or failure to initialize the consumer. Include a real engine recorded/AQL pass with alternating rank roles. The existing HIP graph ticket test is a proxy with fixed pointers and cannot prove engine tape ordering by itself.
