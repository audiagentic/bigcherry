# Native Radiance deployment and serving lifecycle

Reviewed `bc-serve serve/start/replay`, the native `bc-release` installer, their host probes and the associated P1, S8, session, power and release tests at `a1a48cc0a6bc`. The counts below follow executed call paths in source. No deployment, build or timing measurement was performed.

## 1. Keep live occupancy out of the calibration identity

A stored plan can be refused when another process frees memory on a GPU the plan never selected. P1 computes its inventory digest from the JSON for **all** detected GPUs. This includes current PCIe link state and used/available MiB. Replay recomputes that digest and requires exact scope equality before it updates the resource inputs. Meanwhile, replay already checks selected-card identity and measures whether each selected engine and helper still has enough room. The S8 design defines inventory scope in terms of the selected BDF, architecture and VRAM map. [P1 producer](../../../engines/radiance/components/serving/v2/p1_producer.cpp#L238) · [Host detection](../../../engines/radiance/components/serving/serving.cpp#L935) · [Replay scope](../../../engines/radiance/components/serving/s8_replay.cpp#L166) · [Live admission](../../../engines/radiance/components/serving/stored_manifest.cpp#L172) · [S8 contract](../../design/serving-manifest-v2/s8-handoff-calibration.md)

Use the same canonical selected-card projection when issuing and replaying P1. The existing named-cache key already projects ordered role group, BDF, ordinal, architecture and total VRAM. Include any further stable topology field explicitly required by the calibration contract. Keep current room and link observations in their own evidence and admission checks. Version the scope material and require fresh qualification of records created under the old digest. Preserve historical records. Verify with paired fixtures changing only an unselected card's occupancy, then selected free VRAM within budget, then below budget. The first two should retain a valid scope, the third must refuse admission. A change to selected BDF/order, architecture or capacity must invalidate the scope. Count successful warm replays and refusals by reason. [Named-cache projection](../../../engines/radiance/components/serving/session.cpp#L1855)

## 2. Hash an engine generation once per warm start

On the ordinary successful named-cache hit, the owner walks the runtime tree **at least four times**. Cache selection calls `named_cache`. Replay computes an engine identity for authentication, calls `named_cache` again for attestation and computes it again during S8 requalification. Each walk sorts the runtime filenames, reads the entire binary and every runtime file, and constructs a whole-file string before hashing each one. This costs at least four binary-plus-tree byte passes even with a warm filesystem cache. P1 model container identity, full artifact identity and raw SHA-256 are separate contracts. [Cache lookup](../../../engines/radiance/components/serving/session.cpp#L1963) · [Replay authentication and attestation](../../../engines/radiance/components/serving/session.cpp#L2331) · [S8 requalification](../../../engines/radiance/components/serving/s8_replay.cpp#L166) · [Engine identity](../../../engines/radiance/components/serving/plan_cache.cpp#L100)

First stream each file through the existing incremental SHA-256 implementation, preserving the sorted names, separators and raw per-file digests byte-for-byte. Then pass a scoped identity through the named replay, evidence and S8 callers. Bind reuse to the exact binary, runtime-root membership and file generations, rechecking them at admission and refusing or recomputing on change. A standalone replay must establish its own identity. The versioned chunk-record digest in `complete_file_identity` differs from raw SHA-256 and must retain its current output. Remove the temporary chunk-sized string it allocates on each iteration by feeding a view to the raw hashing operation. Check legacy digest parity on an empty file, exact and partial chunks and a large runtime member. Count payload bytes hashed and peak RSS for a named hit, then replace/add/delete a runtime member between lookup and admission and verify refusal. Preserve fresh room checks, sidecar binding, sealing and S8 requalification. [Incremental hash](../../../engines/radiance/components/serving/sha256.h) · [Chunked identity](../../../engines/radiance/components/serving/stored_manifest_cache.cpp#L114)

## 3. Sample GFXOFF across engine cards on the same ticks

The production owner always installs floor and loaded-idle capture hooks. For each phase, it completes all three samples on one engine BDF before beginning the next. Every eligible, readable GFX12 card incurs two explicit one-second waits per phase. For N such cards the two phases schedule **4N seconds** of sleeps before the startup canary completes. Non-GFX12 and unavailable sensors can return early. Cards sampled in sequence also see different wall-clock windows. [Hook wiring](../../../engines/radiance/components/serving/main.cpp#L353) · [Phase order](../../../engines/radiance/components/serving/session.cpp#L928) · [Per-card loop](../../../engines/radiance/components/serving/manifest_power.cpp#L230) · [Sensor and interval](../../../engines/radiance/components/serving/power_diagnostics.cpp#L162)

Change the native sensor operation to accept the ordered engine BDFs for one phase, discover and validate each sensor, then sample all eligible BDFs once per tick. A single owner thread suffices. Keep separate identities, timestamps, raw readings, error outcomes and verdicts per BDF. Preserve the no-process and engine-loaded boundaries, sample count and cadence. Two eligible BDFs should produce three samples each with two injected interval calls per phase, four total. Exercise mixed generations and one failed sensor while the other remains healthy. Confirm one durable verdict per engine role and that receipt failure still stops the session. Outside this sampling path, kernel release, the 7.0.13 patch, its archive digest and the control/patched module identities serve the reproducibility recipe. Changing those constants cannot accelerate serving. [Power acceptance tests](../../../engines/radiance/components/serving/power_transaction_acceptance_test.cpp) · [Kernel recipe](../../../host/kernel/7.0.13-gfxoff/README.md)

## 4. Read helper readiness incrementally and let the owner sleep to its deadline

Both startup paths poll a fresh helper log. The scanner opens at offset zero and checks all prior lines until it sees either supported readiness prefix. On a slow start with evenly growing logs, total bytes scanned grow quadratically with the poll count. Add one cursor per role and launch, with a partial-line buffer for writes split across polls. Treat replacement or truncation explicitly so stale readiness cannot authorize launch. Keep both exact worker markers, the current child/group liveness checks and the final shared-segment check. A fake helper should write many irrelevant lines and a marker split across writes, followed by separate death-after-marker and missing-segment cases. Count bytes scanned for both measuring and serving starts. [Scanner](../../../engines/radiance/components/serving/session.cpp#L740) · [Serving gate](../../../engines/radiance/components/serving/session.cpp#L1230) · [Measuring gate](../../../engines/radiance/components/serving/session.cpp#L1716) · [Worker marker](../../../engines/radiance/components/moe-remote/r3_moe_worker.cpp#L459)

The same owner floors its remaining control-socket deadline to integer milliseconds. During a positive sub-millisecond remainder, it can issue repeated zero-timeout polls. The idle service loop runs on a 200 ms default interval. Round a positive remainder up and break once the deadline passes. Keep the existing 100 ms signal-check cap. Verify the socket still answers status/stop, child failure is observed, and an idle cycle no longer spins. Neither change needs a new operator setting. [Service loop](../../../engines/radiance/components/serving/session.cpp#L1179) · [Default intervals](../../../engines/radiance/components/serving/session.h#L127)

## 5. Reuse the install transaction's verified receipt

When reinstalling the current or previous release, `checked_index` already invokes `verify_one` for that tag under the install root lock. The existing-prefix branch invokes the same function for the same tag a second time. Both passes walk and SHA-256 the installed payload, check file modes and inspect interpreter content. Retain the verified receipt for the requested tag from the index check and compare it to the exact requested release record. An existing unindexed tag still needs independent verification. Scope this reuse to the locked operation and retain detection of external mutation consistent with the install root's ownership guarantees. Keep archive verification, checking the other indexed release, and post-rename verification of newly staged content. [Install flow](../../../engines/radiance/components/serving/release_install.cpp#L251) · [Index verification](../../../engines/radiance/components/serving/release_install.cpp#L221) · [Tree verification](../../../engines/radiance/components/serving/release_archive.cpp#L328)

Count full payload digest passes for first install, reinstall-current and reinstall-previous. Require one verification per existing indexed prefix in the latter two cases. Repeat with altered file bytes, bad mode, mismatched record, corrupt previous and failed rollback. Preserve refusal behavior and the current/previous index. This removes repeated disk work from deployment and has no direct effect on decode. [Installer tests](../../../engines/radiance/components/serving/release_install_test.cpp)

## Ownership and disposition

- **Runtime identities and resource values are derived.** Current room, PCI BDF/ordinal, kernel/module identity and sensor selection come from the host. Child visibility follows admitted rank order. The owner strips inherited project and device-selection variables and sets the process-specific ones explicitly. Preserve those isolation boundaries. [Child environment](../../../engines/radiance/components/serving/session.cpp#L459) · [Rank order](../../../engines/radiance/components/serving/session.cpp#L1973)
- **Observation parameters describe a measurement.** The three-sample GFXOFF window and its cadence belong together in the diagnostics owner. Keep them fixed for the parity comparison. Protocol units, hash framing and tar block size are invariants. A helper startup deadline is lifecycle policy. Serving currently takes it from `Timing`; the measuring path separately spells out 15 minutes and 200 ms. Give both paths a common timing owner where their semantics match, with explicit phase-specific overrides only if operations require them. [Timing](../../../engines/radiance/components/serving/session.h#L127) · [Measuring loop](../../../engines/radiance/components/serving/session.cpp#L1719)
- **Existing retirement gates remain active.** RSC04 owns legacy launcher/Python supervisor removal, RSP01 owns native release acceptance, RSC11 owns dense/helper hardware parity, and RUM owns the upstream migration. The local deletions above concern redundant reads, polls, copies and digest passes. Changing the host's installed kernel or removing its source, configuration or build state has no role in these changes.
